## Findings

**WARNING `wfctl/_pipeline.py:87-89` — the `brainstorm` line is wrong twice, and both errors
run in the permissive direction.**

> `brainstorm  a design doc exists, and some file under the arch root was touched on this branch`

1. Not *some file under the arch root*: `design_block` passes
   `exclude=arch / "design"` to `touched_on_this_branch`, so the `design/` subtree does not
   count. Case B — a level-3 record under `docs/architecture/design/` leaves the step blocked.
   The exclusion is load-bearing, not incidental: `design_block`'s own docstring says #121
   item 3 lands a level-3 record in every such branch diff, so counting it would make the
   check pass vacuously for nearly every branch. An audit line that reads it back as
   "some file under the arch root" describes the check the code deliberately does not do.
2. Touching is not required. `touched_on_this_branch` returns `None` for "git cannot answer"
   (no trunk to compare against, or an arch root outside the repo), and `blocks(inconclusive,
   ambient)` is `False` — case D reads `brainstorm done` with nothing under the arch root at
   all. The paragraph at L106-109 says brainstorm consults `blocks` as `ambient`, which lets
   a reader who already knows the rule derive this; the per-step line still makes the stronger
   affirmative claim, and the per-step line is the half a predicate's author reads first.
   This is the one rung on the ladder where the ambient rule is spent, so it is the line that
   can least afford to omit it.

→ `a design doc exists, and either git says a record outside `arch/design/` was touched on
this branch or git could not say (ambient — silence proceeds).`

**WARNING `wfctl/_pipeline.py:106-109` — "The other six read a file that is there or is not,
which has no inconclusive state" is false for `decompose`, which is one of the six.**

`decompose` reads three things beyond a file's presence, and two of them have an explicit
third state that is resolved as *proceed* without ever reaching `blocks`:

- `_tracker.configured_key_pattern` returns `None` when the repo declared no tracker — case G,
  `decompose done` with an unkeyed map.
- `_unkeyed_issues` returns `None` for "there is nothing here to judge — no map, or a map with
  no rows" (its own docstring) — cases J and K, `decompose done` with tasks still open.
- `load_key_pattern` degrades a missing, non-string or uncompilable `key_pattern` to the
  GitHub default rather than reporting that it could not be read.

That is precisely an inconclusive reading that fails open, and naming it is what #300 scope 2
asks for. As written the sentence also undercuts the audit's own `decompose` line three lines
above, which already describes reading a tracker config and a table — the two statements
disagree about what `decompose` reads.

→ Narrow the sentence to the five it holds for (`specify`, `clarify`, `plan`, `tasks`,
`analyze`) and give `decompose` its own clause: its third states are `no tracker configured`
and `no rows to judge`, both of which proceed, neither of which goes through `blocks`.

**WARNING `wfctl/_pipeline.py:77-116` — nothing pins these thirty-nine lines to the code they
