### WARNING `README.md:L490` — the shipped verb list is now wrong

`scaffold-tracker/SKILL.md` was updated to "eight standard verbs" and grew both
rows, but the README's user-facing list still reads:

> Verbs: `list`, `view`, `close`, `comment`, `create`, `label`.

`wfctl issue --help` (`cli.py:L1025`) was updated; this was not. It is the one
place a consumer reads to learn what the contract offers.

**Fix:** append `` `start` ``, `` `stop` `` to that sentence.

Related, and worth one clause in the same paragraph: the README already says
*"once a repo has a tracker, later installs leave the choice and your edits to
its config alone — re-copy the shipped one with an explicit `--tracker
github`"*. That is exactly the upgrade path for this feature, and it is not
obvious. I traced it: on a bare `install-skills`, the local `tracker` variable
stays `None` when the manifest already carries `tracker: "github"`
(`cli.py:L1998-L2020`), so the `if tracker == "github"` block never runs and a
repo that installed the GitHub backend before this commit gets neither the new
`github.json` nor `github-board.sh`. It degrades correctly — the old config
declares no `start`, so `dispatch` prints *"does not support 'start' — skipped"*
— but the feature reaches only fresh worktrees and repos that re-run with
`--tracker github`. Behaviour is pre-existing and deliberate; the missing bit is
that nothing tells the reader.

### WARNING `tests/test_tracker.py:L344,L349` — the canary poisons itself

```python
["bash", str(script), "$(touch /tmp/wfctl-board-pwned)", "In Progress"],
…
assert not Path("/tmp/wfctl-board-pwned").exists()
```

The path is fixed and outside any fixture. Two consequences:

1. If the guard ever regresses and the marker is created, the test keeps failing
   after the bug is fixed until a human deletes `/tmp/wfctl-board-pwned` by
   hand. A check whose red state survives the repair trains people to delete the
   file rather than read the failure.
2. Any other process (or an earlier run of a sibling worktree's copy of this
   suite — `testpaths` exists precisely because those exist) that touches that
   name fails the test for reasons unrelated to the change.

**Fix:** take `tmp_path`, build the marker inside it, and interpolate:

```python
marker = tmp_path / "pwned"
result = subprocess.run(["bash", str(script), f"$(touch {marker})", "In Progress"], …)
…
assert not marker.exists()
```

The rest of the test is right, and it is the right test to have written — the
argv guarantee ends at `_tracker.dispatch`, and this is what checks the file
dispatch hands the value to.

### WARNING `.workmux.yaml:L96,L138` and `configs/workmux/.workmux.yaml:L72,L100` — the extraction line is outside the guard

```yaml
- |
  ISSUE=$(echo "$WM_HANDLE" | grep -oE '^[0-9]+')
  cd "$WM_WORKTREE_PATH" && uv run wfctl issue start "$ISSUE" || true
```

I checked how workmux actually runs these rather than assuming. `src/cmd.rs`
`shell_command_with_env_output` builds `Command::new("bash").arg("-c")` when
`hook_shell` is unset, and `src/workflow/setup.rs:L113-L119` propagates a
non-zero hook with `?`. So under the default shell the block is safe: `grep`
finding nothing sets `ISSUE=` and execution continues to line 2, which ends in
`|| true`, and the block exits 0. The constraint holds as written.

What is not covered is `hook_shell`, a supported per-repo config key. Point it
at `["bash", "-euo", "pipefail", "-c"]` and line 1 becomes the abort: a handle
with no leading digits ends `post_create` non-zero (the worktree exists, the
tmux window never opens) and — worse — ends `pre_remove` non-zero, which
workmux documents as *aborting the removal*. The new hooks would be the only
lines in either file with that property; the neighbouring `install-skills` line
and the archive block are both immune.

Even under the default shell there is a smaller cost: a handle without a leading
number reaches `wfctl issue stop ""`, which reaches `github-board.sh` with an
empty `$1` and prints the usage error in red on every such teardown. That is
reachable today for any worktree created before this repo's `pre_create` rule,
or in a consumer repo that seeded the template and edited `pre_create` out.

**Fix** (four characters plus a test, in all four blocks):

```bash
ISSUE=$(echo "$WM_HANDLE" | grep -oE '^[0-9]+' || true)
[ -n "$ISSUE" ] && cd "$WM_WORKTREE_PATH" && wfctl issue start "$ISSUE" || true
```

or reuse the shape this repo's own `pre_create` already uses (`if ! echo … |
grep -qE`), which is `set -e`-proof for the same reason.

**And express it as a check.** `a-rule-is-expressed-as-a-check` is accepted and
in force, and the commit message itself calls the `|| true` "the load-bearing
part". A violation of it is visible in an artifact the work already produces —
the shipped template — and `tests/test_bundle.py::test_the_bundled_teardown_hook_names_the_current_command`
is the precedent: it reads the real bundled `.workmux.yaml` and asserts on its
text for exactly this class of regression. Nothing asserts that the two new hook
entries end in `|| true`, and nothing asserts the ordering the comments say is
load-bearing (`issue start` after `install-skills`, `issue stop` after the
archive block). Right now both are prose delivered to nobody.

### WARNING `github-board.sh:L48-L79` — a token without `project` scope fails opaquely

`projectItems`/`updateProjectV2ItemFieldValue` need `read:project`/`project`.
`gh auth login`'s default grant is `repo, read:org, gist, workflow` — no
`project`. On such a machine every `workmux add` prints GitHub's raw
*"Your token has not been granted the required scopes"* blob in red, on a hook
the user did not ask for and cannot connect to a remedy.

This is a consumer-repo problem, not one you will see: I checked this machine
(`gh auth status`) and the active token does carry `project`, which is why the
mechanism works here — I verified the query live against issue 175 read-only and
it returns exactly one `item project field option` line, so the GraphQL itself
is correct.

**Fix:** keep the non-zero exit (the script's stated policy is right — this *is*
a call that should have worked), but capture stderr and, when it mentions the
scope, print the one line that fixes it: `gh auth refresh -s project`.
