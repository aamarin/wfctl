## WARNING — `.workmux.yaml:96,138`, `wfctl/agents/configs/workmux/.workmux.yaml:70,98`

The change adds this snippet four times:

```
ISSUE=$(echo "$WM_HANDLE" | grep -oE '^[0-9]+')
cd "$WM_WORKTREE_PATH" && wfctl issue start "$ISSUE" || true
```

wfctl already knows this value, computed correctly. `_resolve_context`
(`wfctl/cli.py:113-126`) does:

```python
issue = extract_issue_key(branch, _tracker.load_key_pattern(repo_root))
```

— the tracker's *own* `key_pattern`, with the comment right above it naming
Jira/Linear/Shortcut as the reason. `issue_cmd` calls `_resolve_context()` and
then discards that element (`agent_dir, repo_root, _, _ = ...`) in favour of an
argv the caller had to derive itself with a GitHub-shaped `^[0-9]+`.

The consequence is not hypothetical for a non-GitHub consumer. A repo whose
tracker declares `key_pattern: ^[A-Z]+-[0-9]+` and whose handle is
`PROJ-12-slug` gets `ISSUE=""`, and `wfctl issue start ""` reaches the script
with an empty `$1`, which exits 2 with `usage: github-board.sh …` — printed by
`_tracker.dispatch` in red — on every worktree create *and* remove. The commit
message argues at length that a board name in the caller "would teach every
consumer of the tracker contract one tracker's column vocabulary". The same
argument applies to the key shape, and this hook teaches it.

It also matters more than an ordinary duplication because of where it lands.
`install-config` is seed-once and refuses to overwrite (`_check_workmux_hook`'s
docstring says so explicitly), so a line in `configs/workmux/.workmux.yaml`
reaches every repo seeded after it and never reaches the ones seeded before. A
regex committed into consumers' `.workmux.yaml` is expensive to take back.

Fix: let `issue_id` fall back to the branch-derived key when omitted (skipping
when `extract_issue_key` returns `"unknown"`), and every hook collapses to:

```yaml
  - cd "$WM_WORKTREE_PATH" && wfctl issue start || true
```

That is −4 lines of YAML, one derivation instead of two, the correct pattern for
every backend, and it subsumes the third warning below.

## WARNING — `wfctl/cli.py:2016`

`_GITHUB_TRACKER_FILES` is the right idea, and the new install loop and its test
(`test_install_tracker_github_copies_the_script_its_verbs_invoke`) are exactly
the guard the commit message describes. But the *other* place that decides
whether a tracker gets copied did not learn the same thing:

```python
if name:
    if not (repo_root / ".agents" / "trackers" / f"{name}.json").exists():
        tracker = name
```

This is the worktree-inheritance path, and its own comment explains the case it
is written for: `.agents/trackers/` is deliberately not gitignored, so a project
that commits its backend config has the file already. That project now gets
`tracker = None`, no copy is planned, and `github-board.sh` never arrives —
while the committed `github.json` (a copy of the one wfctl ships, which is the
natural thing to commit) declares `start` and `stop` pointing at it.
`bash .agents/trackers/github-board.sh` then exits 127, which is precisely the
failure the new test's docstring says it exists to prevent: "the verbs are
declared, `tracker-check` passes, and every call dies on a missing file."

`test_install_skills.py:3138` is the test that establishes this scenario is
supported, so it is not a corner nobody occupies.

Fix, in the shape the new constant already invites:

```python
if name:
    needed = _GITHUB_TRACKER_FILES if name == "github" else (f"{name}.json",)
    if any(not (repo_root / ".agents" / "trackers" / f).exists() for f in needed):
        tracker = name
```

Adjacent, and worth a line in the PR body rather than a code change: an
already-installed repo running `install-skills` with no `--tracker` never
refreshes tracker files at all, so existing checkouts keep a `github.json` with
no `start`/`stop` until someone re-runs with `--tracker github`. That is
pre-existing behaviour (the tracker copy is what `--tracker` *means* here), but
this is the first change that makes it observable — `wfctl doctor` will report
the bundle hash moved, the re-install will clear it, and the feature still will
not be wired in that checkout. Fresh worktrees are unaffected in this repo
because `.agents/` is gitignored here, so they inherit and copy.

## WARNING — `.workmux.yaml:138`, `wfctl/agents/configs/workmux/.workmux.yaml:98`

`pre_create` refuses a handle without a leading issue key, so `post_create`'s
`$ISSUE` is guaranteed non-empty and the comment saying so is right.
`pre_remove` has no such protection. It runs on worktrees that predate the rule
and on worktrees made with bare `git worktree add` — which `CLAUDE.md` names as
a thing that happens and that "announces itself" only later. For those,
`ISSUE=""` and the teardown prints:

```
usage: github-board.sh <issue-number> <status-name> [--if-open]
```

in red, at the moment the user is destroying something. It is not a gate — the
block's last status is 0 through `|| true`, so removal proceeds (I checked this,
see below) — but it reads like the removal broke.

## Constraint checks (the three you asked about)

**"A status write must never become a gate."** Honoured. workmux runs hooks
through `bash -c` (its own changelog, v0.1.116: "by using bash instead of sh for
execution") with no `-e`, so the failing `grep` in an assignment does not abort
the block, and the block's exit status is the last command's — `… || true` → 0.
`pre_remove` and `pre_merge` are the hooks documented as "aborts on failure";
both new entries end 0 unconditionally. The `pre_remove` ordering comment is also
correct: `stop` runs after `archive-specs`, which is the hook that can refuse.

**`_tracker.py`'s argv-token guarantee.** Preserved, and I tested it rather than
read it:

```
$ bash wfctl/agents/trackers/github-board.sh '$(touch /tmp/pwn-check)' "In Progress"
✗ '$(touch /tmp/pwn-check)' is not an issue number   (rc=2, /tmp/pwn-check absent)
```

More importantly the guarantee survives even without that guard: the script
contains no `eval` and no unquoted expansion, and `$1` only ever reaches quoted
argv positions of `gh` (`gh issue view "$issue"`, `-F num="$issue"`). The status
argument, which *does* reach a jq program, is passed through
`WFCTL_BOARD_STATUS` and read as `env.WFCTL_BOARD_STATUS` — the right call, and
the comment explaining why `gh --jq` has no `--arg` is the kind of comment
`CLAUDE.md` asks for.

**Repo rules.** `uv run pytest -q` → 943 passed in 50s. `uv run ruff check
wfctl/ tests/` → clean. `uv run mypy wfctl/` → clean, 16 files. (`CLAUDE.md`
still says "653 tests" — stale, not this change's doing.) Comments explain
*why this shape* throughout; the new tests' docstrings name the failure they
catch, per the house convention. `NO_COLOR` is not pinned in the new tests
because none of them assert on rich output — they assert on file existence,
`validate_config`, and a subprocess's stderr — which is the right reason to
omit it. I did not run `wfctl verify`, `wfctl doctor`, or any formatter.

`updateProjectV2ItemFieldValue` with `value:{singleSelectOptionId:…}`, and
`gh -f` string values coerce into `ID!` correctly.

Other paths checked and sound:

- **Empty result.** No `Status` field on the project → `field: null` → filtered
  by `select` → empty `$ids` → the `ℹ … nothing set` line on stdout and exit 0.
  `dispatch` passes stdout through verbatim. Matches the header's contract.
- **`--if-open` on the teardown direction.** `gh issue view … || exit 0` means
  an unauthenticated or offline machine skips silently rather than reporting a
  false stop. Correct direction for a hook.
- **bash 3.2.** The script is invoked as `bash <path>` from the config, so the
  `#!/usr/bin/env bash` shebang does not select the interpreter — on stock macOS
  that is bash 3.2.57. Nothing in the file needs bash 4 (`[[ =~ ]]`, `<<<`,
  `read -r a b`, `${x:-}` are all 3.2). `bash -n` passes. Fine as written; worth
  knowing it is load-bearing that it stays 3.2-compatible.
- **Session state.** `dispatch` logs `append_event(agent_dir, "issue", verb=…)`,
  and `session_started` (`_session.py:35`) looks for `event == "start"`, not
  `verb == "start"`. So a `post_create` hook calling `wfctl issue start` does
  **not** make a brand-new worktree report an already-started session. A near
  miss worth recording, since the two names now collide in the log.
- **File mode.** `shutil.copy2` preserves 100755, and `MANIFEST.in`'s `graft`
  carries the `.sh` into the wheel — the packaging note already covers exactly
  this class, so nothing needed adding there.

## NIT — `github-board.sh:12-14` and the test docstring

Two places state a threat model the file does not have:

```
# The numeric check below is what makes that true of this file
# too, since everything under it does interpolate.
```

```
Everything below the guard reaches a shell — `gh api -f num=$issue`, the
jq filter.
```

Neither is accurate. `$issue` reaches no shell (every use is a quoted argv token
of `gh`) and reaches no jq program (the jq filter reads only
`env.WFCTL_BOARD_STATUS`). The guard is still worth keeping — it turns a garbage
key into one clean line instead of a GraphQL type error, and it documents the
argv contract at the boundary — but `CLAUDE.md` says comments explain *why this
shape*, and a reader who trusts this one will believe the file is one edit away
from an injection it is not. Say what it buys: a legible error, and a boundary
check at the one place a future edit could introduce interpolation.

## NIT — `tests/test_tracker.py`, the canary path

`Path("/tmp/wfctl-board-pwned")` is machine-global and never removed. If that
file ever exists — a stray earlier run, another checkout, someone's manual
poke — the test fails permanently for a reason that has nothing to do with the
code. `tmp_path` gives the same canary, scoped to the run:

```python
canary = tmp_path / "pwned"
result = subprocess.run(["bash", str(script), f"$(touch {canary})", "In Progress"], …)
assert not canary.exists()
```

Separately, `test_shipped_github_config_is_valid_and_its_argv_paths_exist`
reaches the real bundle via `Path(_tracker.__file__).parent`. That is correct
and immune to conftest's `bundle` fixture, but `tests/test_bundle.py:180` argues
at length that `importlib.resources` is the house mechanism for "what actually
ships", precisely so the immunity is by intent rather than by import ordering.
Worth matching.

## NIT — `github-board.sh`, the non-single-select case

The header promises exit 0 "when there was nothing to set: an issue on no board,
or a board with no such column". A third shape breaks that promise: a project
whose field named `Status` is *not* a single-select (text, number, iteration).
GraphQL returns `"field": {}` for the unmatched inline fragment, not `null`, so
`select(.project.field != null)` passes it through and `.project.field.options[]`
iterates null. Confirmed locally:

```
$ echo '{…"field":{}…}' | jq '… | .project.field.options[] | …'
jq: error (at <stdin>:1): Cannot iterate over null (null)   rc=5
```

`gh` then exits non-zero and the script exits 1, which per its own comment is
"reserved for a call that should have worked and didn't". Change the guard to
`select(.project.field.options != null)` and the promise holds.

## Passes with nothing to report

- **Security.** Covered above under the argv constraint. No secrets, no
  string-built commands, no `eval`; the one value that reaches a jq program goes
  through the environment. The one thing I would keep an eye on is the new
  precedent — this is the first tracker verb that targets a *script*, and a
  future script written to this pattern will not automatically inherit the
  quoting discipline this one has. The `scaffold-tracker` addition says "pass
  `{id}` as an argument rather than building a shell string", which is the right
  sentence to have added.
- **Performance.** Two API calls for `start`, three for `stop` (`gh issue view`
  first). The query resolving item, project, field and option ids together
  rather than as three `gh project` subcommands is the right call and the header
  says so. `projectItems(first:10)` is bounded. Nothing in a loop, nothing in a
  hot path; the cost is a few hundred ms once per worktree lifecycle event, off
  the critical path in both directions.
- **Over-engineering.** Nothing speculative. `_GITHUB_TRACKER_FILES` as a tuple
  with one consumer is justified by the invariant it names. `start`/`stop` as
  events rather than a status-to-write is the *less* general choice and the
  right one — it keeps column vocabulary out of the contract, and the
  `scaffold-tracker` prose makes that legible to the next backend author. The
  only genuine duplication is the hook snippet, which the first warning removes.
