## Findings

### WARNING — `wfctl/agents/trackers/github-board.sh` L43-46 — `stop` overwrites a column it did not set

`stop` writes `Todo` to *any* open issue on the board, whatever column it is in.
This repo's board has a `Code Review` column, so removing a worktree while its PR
is in review silently relabels the issue `Todo`. The change exists to make the
board able to say what is being worked on; this makes it state something false,
which is worse than the stale `Todo` it replaces.

The L39-42 `ponytail:` note anticipates this and defers it on the grounds that
narrowing the guard "costs another call to find out". That cost claim is false,
and the deferral does not survive without it. One query returns the issue state,
the item's *current* column and all four node ids together — verified live:

```
--jq '.data.repository.issue as $i | $i.projectItems.nodes[]
      | select(.project.field.options != null) | . as $n
      | .project.field.options[] | select(.name == env.WFCTL_BOARD_STATUS)
      | "\($i.state) \($n.fieldValueByName.name) \($n.id) …"'
# → OPEN In Progress PVTI_… PVT_… PVTSSF_… 5182d2dc
```

with `state` and `fieldValueByName(name:"Status"){ ... on
ProjectV2ItemFieldSingleSelectValue{ name } }` added to the existing query.

**Fix:** fold `state` and `fieldValueByName` into the L54-79 query; write only
when the current value is `In Progress`. That subsumes `--if-open` entirely —
the whole L43-46 block and its `gh issue view` call go away, so `stop` drops from
four network calls to three and stops needing a guard argument at all.

### WARNING — `wfctl/agents/trackers/github-board.sh` L74-76 — jq crashes on a non-single-select `Status` field, against the file's own contract

L16-18 promises exit 0 "when there was nothing to set … a board with no such
column". A project whose `Status` field is a text or iteration field returns
`"field": {}` — not `null`, so `select(.project.field != null)` passes — and
`.project.field.options[]` then iterates `null`. Reproduced above: jq exits 5,
`gh` exits non-zero, the script takes `|| exit 1`. Same crash kills the whole
call when an issue sits on two boards and only the *first* one lacks a
single-select `Status`, losing the board that would have matched.

**Fix:** `select(.project.field.options != null)` in place of
`select(.project.field != null)` (or `(.project.field.options // [])[]`).

### WARNING — `tests/test_tracker.py:344,349` — the guard test writes to a fixed `/tmp` path and asserts nothing

`"$(touch /tmp/wfctl-board-pwned)"` with `assert not Path("/tmp/wfctl-board-pwned").exists()`:

- The path is hardcoded and never cleaned up. If the file ever *does* appear —
  or a different user on a shared machine creates it — the test fails
  permanently, including after the bug is fixed. The suite otherwise uses
  `tmp_path`.
- The assertion is vacuous. `$issue` never reaches a shell in this script (see
  the next finding), so the `touch` could not fire whether or not the L30 guard
  existed. The test proves the guard *returns 2*, not that it prevents anything.

**Fix:** take `tmp_path` and interpolate `tmp_path / "pwned"` into the argument,
so the probe is per-test and self-cleaning. Keep the `returncode == 2` and
message assertions — those are the real content.

### WARNING — `github-board.sh` L11-14 and `tests/test_tracker.py:336-340` — the comments misdescribe why the file is safe

> The numeric check below is what makes that true of this file too, since
> everything under it does interpolate.

> Everything below the guard reaches a shell — `gh api -f num=$issue`, the jq
> filter.

Neither is true. `$issue` appears only as `gh issue view "$issue"`,
`-F num="$issue"` and two `echo`s — all quoted argv, none evaluated by a shell —
and `$issue` never enters the jq filter text at all (only `$status` does, and
L51-53 correctly routes that through `env.`). The L30 guard is a validity check,
not the injection barrier; the barrier is the same argv discipline `_tracker.py`
guarantees, which the script inherits.

This matters under this repo's own rule that comments explain *why this shape*:
the next reader is told the guard is load-bearing for injection safety, and the
one after that could remove quoting on the strength of it. It fails safe today,
which is why it is a WARNING and not a BLOCKER.

**Fix:** say the guard rejects a value that is nonsense to `-F num=`, and that
argv — not the guard — is what keeps a shell out.

### WARNING — `.workmux.yaml:137-139` / `configs/workmux/.workmux.yaml:99-101` — the `pre_remove` block is not protected the way `post_create`'s is

```
ISSUE=$(echo "$WM_HANDLE" | grep -oE '^[0-9]+')
cd "$WM_WORKTREE_PATH" && uv run wfctl issue stop "$ISSUE" || true
```

`|| true` covers line 2 only. On a handle with no leading digits:

- `grep` exits 1 on line 1. `workmux docs` documents `pre_remove` as "aborts on
  failure" but does not state the shell flags hooks run under; if it is
  `set -e`, the block aborts at line 1 with status 1 and **the removal is
  refused** — a worktree that cannot be torn down, which is the exact failure the
  constraint in the commit message forbids. I could not settle this from the
  workmux binary and did not run `workmux add` to find out, so treat the
  severity as conditional on that.
- Even without `set -e`, `$ISSUE` is empty and the hook runs
  `wfctl issue stop ""` → the script's usage branch → exit 2 → `dispatch` prints
  the usage line in red. Every removal of a non-issue worktree gains a spurious
  red error. Confirmed by running the script with an empty first argument.

`post_create` is safe from both because `pre_create` refuses such a handle
before it. `pre_remove` has no such upstream guarantee: a worktree predating the
`pre_create` hook, or one made with bare `git worktree add`, reaches it.

**Fix (both files, both directions for symmetry):**

```
ISSUE=$(echo "$WM_HANDLE" | grep -oE '^[0-9]+' || true)
[ -n "$ISSUE" ] && wfctl issue stop "$ISSUE" || true
```

## Pass notes (what was checked, including where nothing was found)

**Correctness.** Traced `wfctl issue start` end to end: `issue_cmd` →
`_tracker.dispatch` → `subprocess.run(argv, cwd=repo_root)` → `bash
.agents/trackers/github-board.sh`. The relative argv path resolves because
`dispatch` passes `cwd=repo_root`; confirmed. Every fallible command in the
script has an explicit `|| exit` (the file sets `-uo pipefail`, not `-e`) and I
found no unguarded one. `read -r item project field option` is safe because node
ids contain no whitespace even though the status name does. `projectItems(first:10)`
truncates silently past ten boards — not worth a finding. The empty-`$ids`,
no-matching-option and closed-issue paths all behave as documented; the
non-single-select path does not (WARNING 2).

**Security.** The constraint from `_tracker.py`'s docstring holds: substitution
still builds argv tokens, the script is invoked as `["bash", path, id, status]`,
and nothing in the script `eval`s or re-shells its arguments. The status name
reaches jq through `env.WFCTL_BOARD_STATUS` rather than being spliced into the
filter text — that is the right call and the L51-53 comment explains it well. No
secrets, no new network surface beyond `gh`'s own auth. The only security-adjacent
defect is descriptive, not behavioural (WARNING 5).

**Architecture.** Two event-shaped verbs rather than a `status` verb taking a
column name is the right boundary, and `ALLOWED`'s comment carries the reasoning
properly. Making the tracker a *set* of files via `_GITHUB_TRACKER_FILES` fits
the existing plan/manifest/backup machinery; `shutil.copy2` preserves the 100755
mode, and `MANIFEST.in`'s `graft` carries the `.sh` into the wheel (verified
against the packaging comment). `uninstall-skills` will remove it, since it lands
in `items`. The hook ordering argument in `pre_remove` — after `archive-specs`,
which deliberately has no `|| true` and can refuse removal — is correct and
verified against that hook's own comment.

**Readability.** Names are clear (`nwo`, `ids`, `item/project/field/option`).
No function is long or deeply nested. The comments are dense with rationale in
the house style; the two that are wrong are called out above, and the
`ponytail:` marker at L39 is the right mechanism for a deliberate deferral even
though this particular deferral does not hold up.

**Performance.** `workmux add` gains three sequential network round trips
(~0.3-1s warm) and `workmux remove` four. `|| true` protects against *failure*,
not against a *hang*: `gh` has no timeout knob, so a blackholed DNS (captive
portal) blocks worktree creation for as long as the resolver takes. Not filed as
a finding because it is inherent to any synchronous hook and the repo already
accepts it for `install-skills`; worth knowing that the `|| true` guarantee is
narrower than the commit message implies. WARNING 1's fix removes one of the four
calls.

**Over-engineering.** The script earns its place — `gh project item-edit`
genuinely has no by-issue-number form (checked its `--help`), and `gh api
graphql` genuinely does not substitute `{owner}`/`{repo}` (tested), so neither
the script nor the `gh repo view` call is avoidable. No dead flexibility, no
speculative abstraction, no reinvented stdlib. `_GITHUB_TRACKER_FILES` as a
2-tuple constant is right-sized. The only shrink available is WARNING 1's, which
deletes the `--if-open` block and its comment.

net: −10 lines possible (WARNING 1's fold-in; every other finding is neutral or
adds a test)

**Verdict: Request changes** — no blockers, but WARNING 1 (board says `Todo` for
work in `Code Review`, fixable at zero API cost) and WARNING 6 (`pre_remove`'s
unprotected first line, in a hook whose failure aborts removal) both land inside
the two constraints the change set for itself, and WARNING 3 leaves the shipped
README stating a verb list the change made wrong.
