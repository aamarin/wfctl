## BLOCKER — a thin `spec.md` routes to `/speckit.clarify`, and drops the reason

`wfctl/_pipeline.py:843-848`, unchanged by this diff but invalidated by it:

```python
if (
    s.name == "specify"
    and s.state == "in_progress"
    and step_map.get("clarify") == "in_progress"
):
    continue
```

Its docstring states the cause it was written for: *"Markers in spec.md leave
specify `in_progress`, but clarify is the step that resolves them."* That held
while an open marker was the only way `specify` reached `in_progress`. This
change adds a second way — missing sections — and the rule cannot tell them
apart, so it skips specify for both.

Traced against the exact case the issue, the record and
`test_a_spec_of_one_character_leaves_specify_in_progress` all name:

| `spec.md` | specify | clarify | current step | `next-step.md` |
|---|---|---|---|---|
| `x` | `in_progress`, annotated `missing: …` | `in_progress` | **clarify** | `/speckit.clarify`, `auto: false`, **no `why:`** |
| `x` + `## Clarifications` | `in_progress`, annotated `missing: …` | `done` | specify | `/speckit.specify` + `why: missing: …` |
| `x` + `plan.md` | `in_progress`, annotated `missing: …` | `skipped` | specify | `/speckit.specify` + `why: missing: …` |

Row 1 is the defect. Reproduced by driving `_infer_steps` →
`_current_step_name` → `next_step_content` → `next_step_file` over a temp spec
dir; the file written is:

```
Next step: /speckit.clarify
auto: false
Run this command to continue.
```

Three things are wrong with that, in increasing order:

1. The agent is told to scan a one-character file for ambiguities. `/speckit.clarify` cannot write the missing sections, so the instruction cannot be carried out.
2. The `missing: …` string this change exists to produce is computed, stored on the specify step, and then never reaches `next-step.md`, because `cli.next:508` reads the reason off the *current* step. `cli.py:530` states the standard the file is held to — *"this file says 'run this to continue' over a step that is blocked, and the one view that carried why — `status` — is not the view an agent reads."* Row 1 is that failure.
3. Row 2 is what happens next. `/speckit.clarify` writes its section into the one-character file, clarify goes `done`, and *then* the current step becomes `/speckit.specify` — which regenerates `spec.md` from the template and destroys the section just written. That destructive sequence is named twice in this file already, at `_pipeline.py:602` (`"routes back to /speckit.specify, which rewrites spec.md from the template and destroys the section"`) and in this change's own `test_a_marked_spec_reports_the_marker_and_not_the_sections` docstring. The marker branch was given priority specifically to avoid it; the missing-sections branch reintroduces it by a different route.

`status` is correct throughout — it shows `specify ▶ missing: …`. Only the routing path is wrong, and routing is what an orchestrated run acts on, which is the run the `automatic` flag is about and therefore the run #309 is about.

**Fix.** `s` *is* the specify step inside that branch, and the marker branch
leaves `specify_reason` at `None` while the section branch sets it, so the two
causes are already distinguishable with no new state:

```python
if (
    s.name == "specify"
    and s.state == "in_progress"
    and s.reason is None          # a marker — clarify's job. Missing sections are not.
    and step_map.get("clarify") == "in_progress"
):
    continue
```

Verified against all four routing cases: `thin spec → specify` (was `clarify`),
`marked spec → clarify`, `marked spec with sections → clarify`, `clean spec →
clarify`. Only the first moves.

## WARNING — a non-empty artifact can read `pending`

Before: the arm asked `_file_exists(spec_md)`; the blanked text was used only
for matching. After (`:586`, `:628`) the arm asks the blanked text, and `_prose`
returns `""` both for an absent file and for a present one whose entire content
is a fence or an inline span:

```
spec.md = '`x`'      (3 bytes)  → prose ''  → brainstorm=done  specify=pending  clarify=pending
spec.md = '```a```'  (7 bytes)  → prose ''  → brainstorm=done  specify=pending  clarify=pending
plan.md = '`x`'      (3 bytes)  → prose ''  → plan=pending
```

Two problems. It inverts FR-003 for exactly the class of artifact this change is
about — the file is on disk, so the writer should be told to continue, and
`pending` tells them to start over — and `pending` cascades, forcing every later
step to `pending`. And it is internally inconsistent: `brainstorm` at `:572`
still reads `_file_exists(spec_md)`, so the same directory reports "we are past
brainstorm, `spec.md` exists" beside "specify has not started".

`_prose`'s docstring argues the collapse is safe because *"every caller here asks
whether there is an artifact rather than whether there is a path"* — but the two
new callers ask the opposite: whether there is a *path*, to choose between
`pending` and `in_progress`.

**Fix.** Restore the presence test to `_file_exists` and leave `_prose` for
matching:

```python
elif name == "specify":
    if not _file_exists(spec_md):
        state = "pending"
    elif has_markers:
        ...
```

and the same for `plan` against a bound `plan_md`. This also removes the reason
`_prose`'s empty/absent paragraph exists.

## WARNING — the routing layer has no test

`test_pipeline_sections.py` asserts `.state`, `.annotation` and `.reason` on
individual steps. Nothing in the diff calls `_current_step_name`,
`next_step_content` or `next_step_file`. That is a coverage-shaped hole rather
than a stylistic one: the blocker above lives entirely in it, and so does the
change's *other* observable effect, which no finding elsewhere mentions.

Setting `specify_reason` / `plan_reason` feeds `next_step_content`, whose
documented rule is **"a blocked step is never automatic, whatever the table
says"** (`:878`). So a thin `plan.md` now writes `auto: false` where it wrote
`auto: true` before — `speckit-orchestrate` halts for a human instead of
proceeding. That is very likely the right outcome and consistent with the
record's reasoning (a pause on *some* runs, not on every run), but it is a change
to the orchestration contract with nothing pinning it.

`test_no_step_changed_the_flag_that_says_it_may_run_unattended` does not cover
it, and its docstring claims more than it checks — *"the one property no run can
observe"*. `_STEPS` is unchanged, but the flag a run actually observes is the one
`next_step_content` returns, and that one did move.

Add, minimally: thin spec → current step is `specify` and `why:` carries the
missing list (the blocker's regression test); thin plan → `auto: false`; full
spec + full plan → `auto: true` on the next step.

## WARNING — `_CORPUS` is bound to one machine

`tests/test_pipeline_sections.py:41`:

```python
_CORPUS = Path.home() / "Development" / "wfctl-specs"
```

`AGENTS.md` states the resolution order for the spec root — `WFCTL_SPEC_DIR`,
then this repo's manifest, then the main checkout's manifest, then
`<repo>/specs` — and says *"Ask `wfctl feature-paths` rather than assuming a
path."* This assumes a path, and one that encodes a single developer's home
directory layout.

The consequence is scoped by the file's own thesis: it argues at length that a
negative-only run *"has tested half of it"*, then binds the positive half to a
path that exists on one machine. Everywhere else it skips, and the skip is
invisible in `-q`. `test_the_corpus_test_is_not_silently_skipping` is the
intended guard and does not close it — its docstring says *"say out loud, once,
whether the corpus was reachable"*, but the body prints nothing and asserts
nothing unless `WFCTL_REQUIRE_CORPUS` is set, which CI does not set. On any
machine but this one, both tests pass while checking nothing.

**Fix.** Resolve through the documented chain (`WFCTL_SPEC_DIR`, then the
manifest) and keep the skip only for the genuinely-absent case. Folding the
env-var escape into the `skipif` condition then makes the second test
unnecessary.

*Verified, for the record:* the corpus claims hold. Running the shipped
predicate over the real spec root gives 24 of 27 specs and 24 of 25 plans
passing, failing exactly the three directories the record names by name
(`24-read-artifacts-from-specs`, `configurable-issue-key`,
`install-config-workmux`). The counts in the record (22/25, 23/24) reconcile
with the two specs and one plan added since it was written. The strictness
argument for `\b` also holds — those three fail on `## Functional Requirements`,
which is what the test asserts.

## Passes with nothing to report

**Security.** No new external input reaches a shell, a query or an output
encoder. The two new regexes are built from module constants via `re.escape`,
never from file content or user input, so no injection surface and no catastrophic
backtracking (`^##[ \t]+<literal>\b` is linear). `_prose` reads files the caller
already located inside the spec dir; no new path is joined from untrusted text.
No secrets, no logging change.

One note rather than a finding: `_prose` widens `read_text()` to `plan.md`, so a
plan with non-UTF-8 bytes now raises `UnicodeDecodeError` out of `wfctl status`
where it previously only had its size checked. `spec.md` and `tasks.md` already
carry that exposure, so this is consistent with the file rather than new
behaviour, and `install-skills` writes UTF-8. Not worth a guard on its own.

**Architecture.** The record is the right shape and in the right place — it names
who owns the question, argues the direct baseline, and its "Considered" section
disposes of the four alternatives I would have raised (read from the shipped
template; read from installed `.specify/`; require unnamed sections; extend
`verify`). `status: proposed` matches the sibling `promised-evidence-blocks-on-silence`,
so it correctly stays out of `wfctl arch context`'s accepted set. The drift test
is where the record says it should be, and the asymmetry between the two halves
(equality for the spec's `_(mandatory)_` declarations, containment for the plan's
undeclared headings) is asserted rather than papered over, with the reason in the
docstring. I checked both against the shipped templates by hand: the four spec
constants are exactly the four `_(mandatory)_` headings in template order, and all
five plan constants are `##` headings the plan template carries, with
`## Complexity Tracking` outside every fence.

**Performance.** Two extra `read_text` + `re.sub` passes over documents that are
kilobytes, on a command a human runs interactively. `plan.md` is now `stat`ed
three times per inference (twice inside `_prose`, once in the clarify arm) —
sub-microsecond, and folded into the `plan_md` NIT above rather than raised
separately. No loop, no fetch, no allocation of consequence.

**Over-engineering.** Nothing speculative. `_missing_reason` is eight lines
including a docstring for a one-line expression, but it has two call sites and
its docstring carries the argument for naming the sections rather than counting
them — it earns its place. `_prose` genuinely deduplicates: it is what lets the
three structural reads share one definition of "text", which is the property the
`_missing_sections` docstring is about. The only removable weight is
`CLARIFY_UNSCANNED` and one of its two comments.
