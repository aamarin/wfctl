BLOCKER  wfctl/_pipeline.py:L843 — the flagship case routes to the wrong command.
`_current_step_name` skips `specify` whenever it is `in_progress` and `clarify` is
too. That skip was written for the marker case; the new missing-sections case now
falls into it, so a `spec.md` holding `x` — the exact input #309 names — reports
the defect and then sends the reader to `/speckit.clarify`, the one command that
cannot fix it. US1 says "the run routes back to the command that writes the file";
it does not. Rendered, from `build_report` on a spec dir whose `spec.md` is `x`:

```
brainstorm   skipped
specify      in_progress  missing: User Scenarios & Testing, Requirements, Success Criteria, Validation Strategy
clarify      in_progress
plan         pending
current: clarify | next: /speckit.clarify
```

`/speckit.clarify` will then scan a one-character document, write its
`## Clarifications` section into it, and read `done` — one wasted step whose only
saving grace is that `clarify` is `review_required`. No test in the diff asserts
`report.current` or `next_command` for the new state, which is why this is invisible.

→ Fix: narrow the skip to the case it was written for — the marker branch sets no
reason, the section branch does:

```python
if (
    s.name == "specify"
    and s.state == "in_progress"
    and s.reason is None
    and step_map.get("clarify") == "in_progress"
):
```

Verified against the four reachable shapes (left: today, right: with the guard):

| spec.md | current today | with `s.reason is None` |
|---|---|---|
| `x` | clarify | **specify** |
| marker, no sections | clarify | clarify |
| marker + all sections | clarify | clarify |
| partial, clarified | specify | specify |

Add the routing assertion beside `test_a_spec_of_one_character_leaves_specify_in_progress`.

WARNING  wfctl/_pipeline.py:L306 — `\b` makes SC-004's promise false for a whole
class of renames. `\b` after a name ending in a non-word character can never match:
if upstream renames the heading to `## Requirements (v2) _(mandatory)_` and the
constant is updated to match, `_missing_sections` reports it missing on every
document — the constants equal the template, so
`test_the_required_spec_sections_are_the_templates_mandatory_ones` stays green and
`specify` becomes unpassable in the field. That is precisely the "changing a verdict
silently in a consuming repository" the record says the build catches. Measured:

```
_missing_sections("## Requirements (v2) _(mandatory)_\n", ("Requirements (v2)",))
  with \b    -> ('Requirements (v2)',)   # present, reported missing
  with (?!\w) -> ()
```

→ Fix: `(?!\w)` instead of `\b` (same rejection of `## RequirementsTODO`, no
dependence on the preceding character), **and** make the drift tests pin the matcher
rather than the string list — `assert _missing_sections((_TEMPLATES / "spec-template.md").read_text(), _REQUIRED_SPEC_SECTIONS) == ()`,
same for the plan half. Both assertions pass against the shipped templates today, and
they are the ones that would have failed on the rename above.

WARNING  wfctl/_pipeline.py:L595 — a held `specify` routes to a command that
rewrites the artifact, with no remedy line saying otherwise. A spec that has been
through clarify and is missing one heading now reads `specify in_progress` and (today
and after the BLOCKER fix) makes `specify` the current step. `speckit-specify`
step 6 writes SPEC_FILE from the template structure, and the clarify arm's own
comment at L610 names the consequence: it "rewrites spec.md from the template and
destroys the section". `specify` carries `automatic`, so an orchestrated run does

exactly this ("how to clear the block, where the reason alone does not say", L505):
tell the reader to add the named headings to the existing file rather than re-run the
generator. No new mechanism, and it renders in `status --json` where orchestrate reads.
