## Findings

**BLOCKER  wfctl/_pipeline.py:844 — `_current_step_name` still skips `specify` on
the assumption that markers are its only `in_progress` cause, so the change's
headline case routes to the wrong command.**

The guard reads:

```python
if (
    s.name == "specify"
    and s.state == "in_progress"
    and step_map.get("clarify") == "in_progress"
):
    continue
```

Its docstring justifies the skip as "Markers in spec.md leave specify
`in_progress`, but clarify is the step that resolves them." This diff adds a
second cause — missing sections — that clarify does **not** resolve, and the
guard does not distinguish them. Reproduced end-to-end on a spec dir whose
`spec.md` is the single character `x` and with no `plan.md` (the exact SC-001
case, minus the plan):

```
brainstorm   –
specify      ▶  missing: User Scenarios & Testing, Requirements, Success
Criteria, Validation Strategy
clarify      ▶  ← current
plan         ○
...
next: /speckit.clarify
```

`clarify` is `in_progress` here because there is no `## Clarifications` heading,
no markers and no `plan.md`. So `specify` is skipped, `clarify` becomes the
current step, and `cli.py:508` reads `blocked` from *clarify* — which has no
reason — so `next-step.md` names `/speckit.clarify` and carries no `why:`. The
missing-sections reason is computed, stored on `specify.reason`, and never
reaches the file an agent acts on.

This defeats FR-003's stated purpose ("reporting otherwise would direct the
writer to start over rather than continue" — it directs them to a third command
instead) and SC-003 in the `next` path, and it is the same failure mode the diff
explicitly guards against for markers at `_pipeline.py:589` ("naming missing
sections beside a marker would route the reader to the wrong command"). Running
`/speckit.clarify` against a one-character spec cannot produce the four missing
headings.

Mitigating, and why this is not catastrophic in an orchestrated run: `clarify` is
`review_required`, so orchestration pauses rather than proceeding — and the
`status` table does show the annotation. The verdict is still wrong and untested.

Fix: qualify the skip on the cause. The marker branch leaves
`specify_reason is None`; the section branch sets it, so one condition separates
them —

```python
        if (
            s.name == "specify"
            and s.state == "in_progress"
            and s.reason is None            # markers, not missing sections
            and step_map.get("clarify") == "in_progress"
        ):
```

and add a test asserting `_current_step_name` (or `next-step.md`) says `specify`
for `{"spec.md": "x"}` with no plan. `tests/test_pipeline_sections.py` asserts
only `state` and `annotation`; nothing in the diff exercises routing, which is
why this got through a green suite.

**WARNING  wfctl/_pipeline.py:274 — `_prose` hand-rolls a fence regex in a package
that ships a fence walker for exactly this, and the diff widens what depends on
it from one read to four.**

`wfctl/_md.py`'s module docstring says it exists because "`_shape`, `_body` and
`_arch` all needed to know which lines of a markdown document sit inside a fenced
code block, and all three answered it differently", and names one of the three
caller shapes as "the text with fenced lines blanked" — i.e. exactly `_prose`.
`_pipeline` is now the fourth module carrying its own, and its version is the
loosest of the four. Demonstrated against the new predicate:

| Document | Regex verdict | Correct |
|---|---|---|
| the four required headings inside a `~~~` block | `specify: done` | held |
| the four headings inside a ```` ````-fence quoting a ```-block | `specify: done` | held |
| headings after an unclosed ```` ``` ```` fence | counted as real | not counted |

All three fail *open* — a documented heading reads as a written one — which is
the same defect class #309 exists to close, now on the gate rather than on the
marker scan. The `~~~` case in particular is reachable: wfctl's own specs quote
fenced examples routinely, and this repo's arch records do it in the same
paragraph.

The regex is pre-existing (it moved out of `_infer_steps`), so this is not a
regression — but the diff is the moment it stopped being a marker heuristic and
became a pass/fail gate with two new callers, and consolidating is a smaller
change now than after. Fix: implement `_prose` over `_md.walk`/`walk_lines`,
dropping `inside` and `fence` lines and blanking inline spans as today. The
existing `clarify` heading scan gets the fix for free.

**WARNING  wfctl/_pipeline.py:254 — `Complexity Tracking` is required of every
plan, and the shipped template tells the author not to fill it.**

`plan-template.md:120–122` is:

```
## Complexity Tracking

> **Fill ONLY if Constitution Check has violations that must be justified**
```

The spec-side list is the template's own `_(mandatory)_` declaration, so it is
upstream's judgment. The plan-side list is wfctl's free choice (record: "wfctl's
own choice from the headings the template does carry"), and this entry requires
an author to keep a heading the template describes as conditional. An author who
deletes the empty section — a reasonable edit — gets `plan: in_progress  missing:
Complexity Tracking` with no way to clear it but re-adding an empty heading.

The corpus is evidence *for* keeping it (24 plans on disk carry it), not evidence
that it is the right requirement — they carry it because nobody deleted it. Fix:
either drop it from `_REQUIRED_PLAN_SECTIONS` (the other four carry the same
signal), or record in the constant's comment why a conditional section is
required anyway. Neither the record nor the code currently says.

**WARNING  wfctl/_pipeline.py:628 — `plan` has no placeholder check, so an
untouched `plan-template.md` reads `plan: done` in green under `automatic`.**

Copying `wfctl/specify/templates/plan-template.md` verbatim into a spec dir and
running inference gives `plan: done`. The spec half is protected by
`has_markers`, which is why the same experiment leaves `specify: in_progress` —
the spec template carries `[NEEDS CLARIFICATION` and the plan template does not
get an equivalent read. So "the file is a plan-shaped stub nobody wrote" still
passes the tightened gate on the plan side.

This is a smaller hole than the one being closed (a template copy is a rarer
accident than a truncated write) and may be a deliberate scope call — but the
record does not name it, and it is the obvious next question a reader of the
record will ask. Fix: either a bracket-placeholder read on `plan_text` mirroring
`has_markers`, or one sentence in `## Consequences` saying the plan half accepts
a template-shaped artifact and why.

**WARNING  tests/test_pipeline_sections.py:41 — `_CORPUS = Path.home() /
"Development" / "wfctl-specs"` hardcodes one machine's layout and bypasses the
project's own spec-root resolution.**

`AGENTS.md` and `wfctl/_paths.py:247` (`spec_root`) define resolution as
`WFCTL_SPEC_DIR` → this repo's manifest → the main checkout's manifest →
`<repo>/specs`. This test consults none of it. On any machine that keeps its
spec root elsewhere the SC-002 half — the half the file's own module docstring
calls "the half that cannot make the pipeline unpassable for genuine work" —
skips silently, and `WFCTL_REQUIRE_CORPUS` only helps someone who already knows
to set it.

Fix: resolve through `wfctl._paths.spec_root(Path(__file__).parents[1])` (or read
`WFCTL_SPEC_DIR` first), falling back to the current path. `tests/` is exempt from
`the-underscore-is-the-module-contract`, so importing it is fine.

**WARNING  tests/conftest.py:337 — `text.get(name) or _default_body(...)` turns an
