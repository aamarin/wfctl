## Findings

**BLOCKER  wfctl/_paths.py:370-405 + :465-471 — a grouping map the parser cannot
read is indistinguishable from no grouping map, so #120 is still reachable on
exactly the legacy format this diff deleted the tolerance for.**

`delivery_issue_keys` collapses three different situations into `set()`: no
`delivery.md`, no grouping map, and *a grouping map whose rows the strict parser
did not understand*. The ancestor walk at :470 reads all three as "claims
nothing → silence, not denial" and inherits the feature. The first two are the
legitimate parent-epic case. The third is #120, arriving quietly.

This is not hypothetical. The skill text this diff removes said so in as many
words — *"Older delivery.md files may predate the standardized
`{issue-key}`-leads-the-cell format — the regex search-anywhere-in-row approach
still finds them"* — and the replacement drops the tolerance without replacing
it with a signal. Reproduced against the current tree (fixture = #120's stack,
foreign feature `562-transaction-balance`, `tasks.md` complete):

```
A  | Issue A (#575) | …   (legacy cell, key not leading)  -> keys: set()  resolved: FOREIGN
B  Issue | Tasks              (GFM table, no leading pipe) -> keys: set()  resolved: FOREIGN
   ------|------
   #575  | T001
```

Both are `wfctl status` reporting `46/46 done — open PR` on unstarted work, which
is the exact defect under fix, and issue #120's AC2 ("a mismatch resolves to
'unresolved', never to the ancestor's feature") is not met for them.

The author already states the governing principle, one screen up, in the comment
at :363-366 — *"a feature that claims nothing is one the ancestor walk still
inherits — which is #120 arriving through a typo."* That reasoning was applied to
the heading and not to the rows.

→ Fix: make "has a grouping map" a separate, answerable question from "which keys
does it claim". E.g. return `None` for *no map* and a (possibly empty) `set` for
*map present*, then at :469-471:

```python
claimed = delivery_issue_keys(found, pattern)   # None == no map at all
if claimed is not None and key not in claimed:
    continue
```

A feature with a grouping map is by definition decomposed; if it does not name
this key, it is not this branch's — whether that is because it claims other keys
or because its rows are unreadable. Nothing legitimate is lost: a decomposed
epic that *does* claim this key is already returned by the forward leg at
:460-463 before the ancestor walk runs (see the WARNING below).

Also worth folding in while there: the row filter at :400 requires a leading `|`,
which is optional in GFM (case B). Cheap to relax; with the fix above it becomes
fail-safe rather than fail-open either way.

**WARNING  wfctl/_paths.py:386-388 — `UnicodeDecodeError` escapes the guard and
turns a resolution fallback into a traceback.**

`read_text(encoding="utf-8")` raises `UnicodeDecodeError`, a `ValueError`, not an
`OSError`. Confirmed: a `delivery.md` beginning `\xff\xfe` makes both
`delivery_issue_keys` and `resolve_spec_dir` raise, which crashes every command
that resolves a spec dir (`status`, `resume`, `start`, `feature-paths`) rather
than falling through. The `except OSError` shows the intent was to be
non-fatal here.
→ Fix: `except (OSError, UnicodeDecodeError):`, or `errors="replace"` on the read.

**WARNING  wfctl/_paths.py:470 — `key not in claimed` is dead; the condition is
exactly `if claimed:`, and reading it as a membership test is what hides the
BLOCKER above.**

Whenever `claimed` is non-empty and contains `key`, the forward delivery leg at
:459-463 already returned that directory — `found` is always a depth-1 child of
`root`, so `root.glob("*/delivery.md")` covers it. And when `key == "unknown"`
the forward leg is skipped, but `"unknown"` is never a parsed key. So the second
conjunct is always true when the first is.

Not a behavioural defect today. It matters because the line *reads* as "verify
this ancestor names me", which is what makes the empty-set path look already
handled. The BLOCKER fix rewrites this line anyway; write it so the predicate is
"does this feature publish a grouping map", which is the question actually being
asked.
→ net: −1 line, +3 for the BLOCKER.

**WARNING  wfctl/agents/skills/speckit-orchestrate/SKILL.md:52-60 — "so an
unresolvable branch resolves to nothing" overclaims, and this is the file that
tells an agent whether to trust `spec_dir`.**

The conclusion only follows when the ancestor's feature is decomposed *and* its
map is readable. Confirmed third shape: an ancestor feature with **no
`delivery.md` at all** but a complete `tasks.md` is still inherited and still
counted — the original #120 rendering, unchanged. That case is genuinely
undecidable from `delivery.md` (it is the same evidence as the legitimate
parent-epic inheritance), so it is a residual to name, not a bug to fix here.

The step's own framing — "`(no spec dir found)` is now an answer, not a gap to
close by guessing" — is right and is the valuable part of the rewrite. But a
skill that promises the false positive is gone will be believed. It should say
what remains: a *non-decomposed* ancestor feature can still be inherited, so a
`spec_dir` the branch did not name itself is worth one sanity check that its
`delivery.md` row for this key exists — which the step already asks for two
bullets later, without connecting it to the risk.
→ Fix: replace the absolute clause with the scoped one ("an ancestor whose
feature publishes a grouping map that does not name this key now resolves to
nothing; an ancestor feature that was never decomposed is still inherited, so
verify the row before trusting the scope").

**4. Readability & simplification.** Comments explain *why this shape*

the choice deterministic when two features claim the same key (first path wins,
silently — not worth a warning at this cost).

`delivery_issue_keys` has one caller, which normally reads `yagni:` — it does not
here, because extracting it is what makes the behaviour testable without a git
fixture, and the tests use it.
