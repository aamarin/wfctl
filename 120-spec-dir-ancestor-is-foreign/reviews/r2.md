## Findings

BLOCKER  `wfctl/_paths.py:392-395` — the section slice keeps **every** pipe table
under the `Issue Grouping Map` heading, not just the grouping map. It stops only
at the next `#`-heading, so any second table under the same heading is read as
grouping rows and its first column is harvested as issue keys. Real evidence, from
this repo's own spec root:

```
005-update-install-skills-default   → claims {'1', '3', '4', '5'}
```

Its grouping map has one row (`| #5 | … |`). The other three come from an
unrelated "Criterion / Issue #5 says / Built instead" table sitting under the same
heading, whose first column is `1`, `3`, `4`. Consequence, measured against the
real spec root:

```
resolve_spec_dir("3-some-unrelated-story")  → …/005-update-install-skills-default
resolve_spec_dir("4-another-one")           → …/005-update-install-skills-default
resolve_spec_dir("1-whatever")              → …/005-update-install-skills-default
```

That is the *same failure class the change exists to remove* — a quiet, plausible
foreign feature handed back with its completion counts — arriving through the new
leg instead of the ancestor one. It violates AC #3 ("`wfctl status` never reports
a completion count sourced from a feature that does not list this issue"): 005's
map does not list issue 3.

→ Fix: bound the scan to the **first contiguous run of table lines** after the
heading — skip blanks, start on the first `|` line, and `break` on the first
non-`|` line once the run has started.

BLOCKER  `wfctl/_paths.py:402` — `re.match(rf"^#?({pattern})\b", cell)` rejects two
Issue-column formats that exist in real files today:

```
| [#45](https://github.com/aamarin/wfctl/issues/45) (Issue A) | …   ← markdown link
| aamarin/wfctl#24 | …                                              ← cross-repo ref
```

Measured: `43-vendor-wf-skills` → `set()`, and `11-agent-artifact-layout` misses
`24`. So:

- **AC #1 fails on real data.** `#45` *does* appear in a grouping map;
  `resolve_spec_dir("45-vendor-sub-issue")` returns `None`, not
  `43-vendor-wf-skills`.
- **Worse, the ancestor guard fails open.** `claimed` is empty, and L470 reads
  empty as "not decomposed → inherit". So a parse failure on a *decomposed*
  ancestor hands back the foreign feature — #120, unfixed, on any repo whose
  delivery plans link their issue column. The guard cannot distinguish "claims
  nothing" from "I could not read the claims", and it resolves that ambiguity in
  the unsafe direction.

  This is exactly the risk the *old* skill text called out and the diff drops:
  "Older delivery.md files may predate the standardized `{issue-key}`-leads-the-cell
  format — the regex search-anywhere-in-row approach still finds them." Those files
  exist; one is `43-vendor-wf-skills`.

→ Fix: `re.match(rf"^\[?(?:[\w.-]+/[\w.-]+)?#?({pattern})\b", cell)`.

**Both blockers share one fix, and I validated it.** With the first-table bound
plus that regex, all 19 real files parse correctly:
`005 → {5}`, `43 → {45, 46}`, `11-agent-artifact-layout → {11, 17, 24}`, every
other file unchanged. That is the acceptance evidence this change needs and does
not currently have.

WARNING  `wfctl/_paths.py:381-383` — the docstring asserts "A parse that is too
strict resolves to nothing, which is the loud failure; one that is too loose hands
back a foreign feature." **That is only true for the delivery leg.** For the
ancestor guard (L469-471) a too-strict parse resolves to *empty*, which means
*inherit*, which is the quiet failure. The comment the same author added at L363-366
says precisely this ("a feature that claims nothing is one the ancestor walk still
inherits — which is #120 arriving through a typo") — so the file now argues both
sides. Strictness is not uniformly safe here, and the docstring is the piece the
next reader will trust.

→ Fix: say that empty is safe for the delivery leg and unsafe for the ancestor
guard, which is why the parser has to be liberal about the *cell* while staying
strict about the *column*.

WARNING  `wfctl/_paths.py:461-463` — no handling of a key claimed by two features;
`sorted()` silently makes the lexicographically-first directory win. This is not
theoretical: in this repo's spec root key `11` is claimed by both
`11-agent-artifact-layout` and `11-gitignore-glob-dedup`, and key `17` by both
`11-agent-artifact-layout` and `17-install-config-substitution`. Today the key-glob
leg happens to cover those two, but nothing guarantees that in general, and a
silent arbitrary winner is the same shape of answer #120 is about.

→ Fix: at minimum document the tie-break in the docstring; better, prefer a
candidate whose own directory key equals the branch key, and otherwise treat a
multi-claim as unresolved (loud) rather than picking one.

WARNING  `wfctl/_paths.py:459 + 470` — **keyless branches silently lose ancestor
inheritance.** When `extract_issue_key` returns `"unknown"`, `key not in claimed`
is true for any non-empty `claimed`, so a branch with no issue key is now refused
by *every* decomposed ancestor. Previously it inherited. wfctl's own worktrees
always carry a key (`pre_create` enforces it), but wfctl ships to repos that do
not. The docstring describes the guard as skipping "an ancestor that claims *other*
issues and not this one", which does not cover this case.

→ Fix: skip the guard entirely when `key == "unknown"` (there is no claim to check),
or document the refusal deliberately and test it.

WARNING  `wfctl/agents/skills/speckit-delivery-plan/assets/delivery-plan-template.md:55-58`
— stale cross-reference, shipped as package data into consumer repos:

> Either way, `speckit-orchestrate`'s epic-inherited spec check is what resolves
> it: it globs the spec root for `*/delivery.md`, matches the branch's issue key
> against the table above, and takes that row's `Tasks` column as the sub-issue's

The "epic-inherited spec check" no longer exists — step 1 is now "Sub-issue

`test_no_shipped_skill_cites_an_orchestrate_step_by_number` only guards *numeric*
citations, so a by-name reference rotting is exactly the gap that test was written
next to and does not cover. Same paragraph should now point at `resolve_spec_dir`.

NIT  `wfctl/_paths.py:470` — `key not in claimed` is unreachable in its true form.
If `found`'s delivery.md claimed `key`, the leg at L461-463 would have returned a
dir already (it scans the whole root). So the effective rule is `if claimed:
continue` — "skip any *decomposed* ancestor". That is a stronger and more
interesting statement than the docstring makes, and it is worth saying out loud
rather than leaving the reader to infer that the condition is half-dead.

NIT  `tests/test_paths.py` — no regression test for either blocker shape. Every
fixture comes from `_delivery_map`, which emits one table in template form, so the
suite cannot see a second table under the heading or a linked issue cell. Two cases
worth adding alongside the existing ones: a grouping-map section followed by a
second unrelated table (assert only the real key), and a row whose Issue cell is
`[#45](url)` (assert `{"45"}`). Also unpinned: that the delivery leg *loses* to the
exact-name and key-glob legs — the diff's ordering is correct but nothing holds it
there.

NIT  `wfctl/_paths.py:363` — `_GROUPING_HEADING` is separated from `is_in_tree` by
one blank line; the rest of the file uses two. Ruff's E4/E7/E9/F set does not catch
it (E3 is not enabled, correctly — not proposing to enable it). L397 `keys = set()`
would read better as `keys: set[str] = set()` given the annotated return type.

NIT  `wfctl/agents/skills/speckit-orchestrate/SKILL.md:56-58` — "Read `spec_dir`
off `wfctl status --json`" does not say whether to reuse step 0's payload (which
already ran that exact command) or run it again; step 0 → step 1 → step 2 currently
implies three `status` invocations. And "when `spec_dir` is a feature the branch did
not name itself" leaves the agent to work out how to tell — comparing the basename
against the branch is the obvious rule and is worth stating.

## What the change gets right

- **Leg ordering is correct and does not change any previously-working
  resolution.** Exact-name and key-glob still run first, so every branch that
  resolved before resolves to the same directory. The new leg only occupies ground
  that previously fell through to the ancestor walk. Verified by reading `match()`
  and by the suite's existing exact/prefix tests.
- **Performance is a net improvement, not a cost.** `load_key_pattern` is hoisted
  out of `match()` (was re-read per candidate, now once), and putting the delivery
  scan *before* the ancestor walk means the common sub-issue case never spawns
  `_ancestor_branches`' two git subprocesses per local branch. The new I/O — up to
  N `delivery.md` reads on an unresolved branch, N=19 and ~5 KB each here — is
  under a millisecond and never runs for a branch that resolves by name or for a
  keyless branch such as `main`. No finding.
- **`--json` gaining `spec_dir` is the right shape for AC #4**, and the console
  path already printed `(no spec dir found)`, so both halves of that criterion are
  met.
- **Security pass: nothing.** The parsed value only selects among directories that
  already exist under the resolved spec root (`delivery.parent`), so no traversal
  is reachable from `delivery.md` content. The `pattern` interpolated into the
  regex is validated-compilable by `load_key_pattern`, so the `re.error` path
  `extract_issue_key` guards against cannot be reached here. `str(spec_dir)` in the
  JSON exposes an absolute path already printed by `feature-paths`.
- **Architecture pass: nothing.** `delivery_issue_keys` sits beside the resolver
  that is its only caller, public like `extract_issue_key`/`is_in_tree` in the same
  module because the tests exercise it directly. Consistent.
- **Test docstrings carry their weight** — each names the failure it exists to
  catch, per CLAUDE.md. The local `import subprocess` inside the two new helpers
  matches the file's existing convention; not flagging it.

---

net: −1 line possible (L470 → `if claimed: continue`). Otherwise lean — the two
blockers need *more* lines, not fewer.

**Verdict: Request changes (2 blockers).** The design is right and the ancestor
guard is the correct place for the check; the parser underneath it is not yet
faithful to the files it will be pointed at, and one of its two failure directions
reinstates the exact bug being fixed.
