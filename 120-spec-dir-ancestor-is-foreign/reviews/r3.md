## Findings

### BLOCKER

**BLOCKER `wfctl/_paths.py:402` — the first-cell key regex cannot read a
bold-wrapped key, so the ancestor guard is inoperative on the exact `delivery.md`
from #120.**

`re.match(rf"^#?({pattern})\b", cell)` requires the key at character zero. Real
maps write the Issue cell as `**#575** — the invariant`. I ran the shipped
parser over every `delivery.md` under `~/Development/pfms-specs`:

```
562-transaction-balance      map=True  keys=[]   <-- HAS MAP, PARSED NOTHING
497-budget-error-states      map=True  keys=[]   <-- HAS MAP, PARSED NOTHING
440-editable-table-row       map=True  keys=[]   <-- HAS MAP, PARSED NOTHING
422-extract-python-tools     map=True  keys=[]   <-- HAS MAP, PARSED NOTHING
286-catalog-tier-restructure map=True  keys=[]   <-- HAS MAP, PARSED NOTHING
018-extract-api-routes       map=True  keys=[]   <-- HAS MAP, PARSED NOTHING
001-add-session-mgmt         map=True  keys=[]   <-- HAS MAP, PARSED NOTHING
```

7 of 45. The first entry is `562-transaction-balance` — **the foreign feature
named in the bug report**. Its map is:

```
| Issue | Branch | Tasks | Files | Size | Base |
| **#575** — the invariant | `575-transaction-invariant` | T001–T028, … |
| **#576** — From → To entry | `576-transaction-entry-form` | T029–T041, … |
```

It plainly claims 575 and 576 and the parser returns `set()`. The ancestor leg
(`_paths.py:469-471`) then reads that as *claims nothing*, which it treats as
"not yet decomposed", and **inherits it** — the precise behaviour #120 exists to
stop. AC-2 and AC-3 do not hold against the reporter's own data.

The one saving grace, which I verified: `555-taxonomy-redesign` parses to
`['562','563','564','565','566','567','568']`, so the new delivery leg does fix
the literal repro (`567-readers-to-chart-accounts` → `555-taxonomy-redesign`).
The fix works; the *guard behind it* does not.

Fix — tolerate leading emphasis, one character class:

```python
m = re.match(rf"^[*_ ]*#?({pattern})\b", cell)
```

Verified: this recovers `562` (`{'575','576'}`) and `497` (`{'497','528'}`).
Add a regression case to `test_delivery_issue_keys_*` using `| **#575** — the
invariant |`; every current fixture uses the synthetic `| #575 |` shape, which
is why the suite is green on a parser that cannot read the bug's own file.

### WARNING

**WARNING `wfctl/_paths.py:393` — section truncation stops at *any* heading,
including a sub-heading that belongs to the map.**

`re.search(r"^#+[ \t]", section, re.M)` does not compare heading levels.
`422-extract-python-tools/delivery.md` is

```
## Issue Grouping Map

### pfms

| Issue | Tasks | …
```

The `###` truncates the section before a single row is seen. Fix — stop only at
a heading of equal or shallower level:

```python
_GROUPING_HEADING = re.compile(r"^(#+)[ \t]*Issue Grouping Map", re.M)
...
level = len(heading.group(1))
next_heading = re.search(rf"^#{{1,{level}}}[ \t]", section, re.M)
```

Verified: recovers `422` → `{'422'}`. It also keeps the template's
`### Getting this spec into a sub-issue worktree` correctly *outside* the map,
since that is `###` under a `##` heading — wait, it is deeper, so it would now
be included; its lines do not start with `|`, so no keys leak. Confirm that
against the template before landing.

**WARNING `wfctl/_paths.py:370-405` — `delivery_issue_keys` conflates "no
delivery.md" with "delivery.md present, nothing parsed", and only the first is
safe to inherit.**

This is the structural version of the BLOCKER. Even after both parser fixes, 4
real files (001, 018, 286, 440) still parse to `set()` because their Issue cell
genuinely is not a key (`Wave 0 — Setup & Schema` with the key in a separate
`Number` column; `Child A`; `Child #304`; `Issue A (#461)`). For those, the
ancestor leg says "not decomposed, inherit" about a feature that is fully
decomposed. The docstring's claim that "a parse that is too strict resolves to
nothing, which is the loud failure" is **only true of the delivery leg**; on the
ancestor leg a too-strict parse is the *quiet* failure, and it is #120.

Fix — let the caller distinguish the two. Cheapest form, in the ancestor leg:

```python
if (found / "delivery.md").exists() and key not in claimed:
    continue
```

A never-decomposed epic has no `delivery.md` at all (`/speckit.decompose` is
what writes it), so this preserves the legitimate inheritance case while
refusing anything that has been decomposed and does not name this key.

Note this contradicts the premise of
`tests/test_paths.py:242 test_resolve_spec_dir_still_inherits_an_epic_that_claims_nothing`,
whose fixture writes a `delivery.md` with no grouping map and calls that
"has not been decomposed". A decomposed-but-unparseable map is the same
`set()`, and the fixture is even named `440-editable-table-row` — which in the
real spec root **is** decomposed, into #461/#462, and parses to nothing. The
test encodes the risky reading as the intended one. Whichever way this is
resolved, the docstring at `_paths.py:373-376` and that test docstring should
say which of the two conditions is actually being relied on.

**WARNING `wfctl/_paths.py:387` — `except OSError` misses `UnicodeDecodeError`,
against this repo's own established convention.**

`read_text(encoding="utf-8")` raises `UnicodeDecodeError` (a `ValueError`, not
an `OSError`) on a stray non-UTF-8 byte — a latin-1 em dash pasted into a
`delivery.md` is enough. Confirmed by direct call: `RAISED UnicodeDecodeError`.
That traceback escapes `resolve_spec_dir` and kills `wfctl status` /
`feature-paths` / `resume` on a path whose whole point is to degrade quietly.
The house convention is explicit — `wfctl/_arch.py:122` reads a markdown file
with `except (OSError, UnicodeDecodeError):`, and `wfctl/cli.py:2585` carries a
comment saying exactly why. Fix: `except (OSError, UnicodeDecodeError):`.

**WARNING `wfctl/agents/skills/speckit-delivery-plan/assets/delivery-plan-template.md:55-57`
— stale cross-reference shipped to consumer repos.**

```
Either way, `speckit-orchestrate`'s epic-inherited spec check is what resolves
it: it globs the spec root for `*/delivery.md`, matches the branch's issue key
against the table above, and takes that row's `Tasks` column as the sub-issue's

```

Both halves are now false: the step is renamed **Sub-issue scoping**, and it no

`test_no_shipped_skill_cites_an_orchestrate_step_by_number` was written because
this very file cited the step by number. The rename broke the by-*name*
reference the test recommended instead, and nothing caught it. Fix the prose to
"`resolve_spec_dir` resolves it by matching the branch's issue key against this
table; the row's `Tasks` column is the sub-issue's range", and consider widening
the guard test to the step's name as well as its number.

**WARNING `wfctl/agents/skills/speckit-orchestrate/SKILL.md:63-64` — the
operative condition of the step has no procedure.**

> What is still yours, when `spec_dir` is a feature the branch did not name
> itself — the sub-issue inherited it:

Everything after this bullet is gated on that condition, and the step never says

The removed step carried "(Older delivery.md files may predate the standardized

not resolve; fix the cell." Otherwise the failure is a silent `brainstorm` on a
planned story with no breadcrumb.
