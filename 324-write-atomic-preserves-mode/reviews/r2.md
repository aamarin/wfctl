WARNING  wfctl/_io.py:L38 — `path.exists()` then `path.stat()` is two syscalls with a
gap: a target deleted between them makes `write_atomic` raise `FileNotFoundError`
where it previously created the file. Confirmed empirically (raises; no `.tmp`
orphaned). The raised type is the same one L28 uses for "parent directory does not
exist", so a caller catching it misattributes the cause. Likelihood is low — one
writer per branch state dir — but the fix is strictly shorter and removes the race
and a syscall, and it is the shape L32's own comment argues for:
```python
try:
    mode = path.stat().st_mode & 0o777
except FileNotFoundError:
    mode = None
```

WARNING  wfctl/cli.py:L2526-L2539 — out of this branch's scope; report, don't fix.
`_write_settings` now carries a redundant second copy of the fix, and its docstring
is now false: "it would hand back whatever mode `mkstemp` chose rather than the one
they set" is exactly what `write_atomic` no longer does. Worse, its `target.chmod(mode)`
sits *after* `write_atomic` returns — the post-replace window that `_io.py:L43-45`
correctly identifies as the wrong shape. The cleanup is already covered:
`tests/test_install_hook_merge.py:L393` (`test_the_merge_keeps_the_consumers_file_mode`,
0o664) passes off `write_atomic` alone, and `path.resolve()` at L2533 must stay — the
symlink guarantee is a separate one that `write_atomic` does not provide (see NIT 3).
File a follow-up to delete L2534 and L2538-L2539 and rewrite that docstring paragraph.

WARNING  wfctl/_io.py:L35 — the comment names `_write_settings_json`. No such symbol
exists; it is `wfctl.cli._write_settings` (L2510). A reader who greps the name to see
"what the other shape looks like" finds only this comment. One-word fix, but the
comment's whole job is to be the pointer.

NIT  wfctl/_io.py:L38 — `& 0o777` drops setuid/setgid/sticky. Verified: a 0o2755
target comes back 0o755. Meanwhile L23 promises "An existing file keeps its
permissions" and every new test asserts through `stat.S_IMODE`, which is 0o7777. It
matches `cli.py:L2534`, so consistency argues for leaving it — but then say so, or
use `stat.S_IMODE(...)` and make the promise true. Nothing wfctl writes is setgid
today; this is about the claim, not a live defect.

NIT  wfctl/_io.py:L34,L37 — "all seven want it" / "the eighth caller" hardcodes a
count that drifts with the next call site, and the comment is then wrong with no
failing test. AGENTS.md takes the same position about numbers in prose in its own
mypy-strict paragraph ("no number is written down here on purpose … it drifts").
"every caller" / "the next caller" carries the same argument and cannot go stale.

NIT  wfctl/_io.py:L23 — "An existing file keeps its permissions" is not true of a
symlink. Verified: `write_atomic` onto a symlink now reads the mode *through* the
link (0o644), then `os.replace` swaps the link for a regular file at that mode and
leaves the real file holding stale content. The replace half is pre-existing; the
mode read through the link is new, and `cli.py:L2533` plus
`test_a_symlinked_settings_file_is_written_through_not_replaced` exist precisely
because of it. One clause would close it: "a symlink is replaced, not written
through — resolve first if the link must survive."

NIT  wfctl/_io.py:L23-L25 — the docstring reasons carefully about the *new-file* case
and is silent on the mirror case the same shape creates: a target already wider than
0600 is no longer re-narrowed on rewrite. Verified: a 0o666 `mode.json` stays 0o666
where every prior rewrite hardened it to 0600. `resolve_agent_dir` (`_paths.py:L675,L681`)
mkdirs with the default umask, so the state dir is typically 0755 and `mode.json`
(the auto-approve grant) and `notify.json` rely on the file mode for containment.
The behaviour is the right call — preserving is the feature, and nothing writes a
wide state file — but the docstring argues one half of the tradeoff and not the other.

NIT  tests/test_io.py:L117 — `def recording_replace(src: str, dst: str)`: `dst`
receives a `Path` (`write_atomic` passes `path`). `str | os.PathLike[str]`.

NIT  tests/test_io.py — two gaps, both cheap, neither blocking: no test pins the
symlink behaviour of `write_atomic` itself (the guarantee lives in a `cli` test
today, so a future refactor that "fixes" `write_atomic` to write through would break
`_write_settings`'s contract silently), and nothing exercises a 0o444 target. The
0o444 case works — verified, content replaced, mode preserved — but it is a genuine
behaviour change worth a line: a read-only target used to come back owner-writable
at 0600, and now stays unwritable to a caller that later uses plain `write_text`.

### Passes run

**1. Correctness** — traced `write_atomic` and all seven call sites (`_arch.py:L495`,
`_session.py:L110,L306,L483`, `_verify.py:L112`, `cli.py:L1313,L2535`). The fix matches
the stated requirement: existing target's mode is carried, new target stays 0600. The
docstring's load-bearing claim that `_session.end` only ever *creates*
`session-summary.md` checks out — `_session.py:L481` guards on `not summary_file.exists()`.
`os.chmod` ignores umask, so the preserved mode is exact. The chmod sits inside the
`try`, so a chmod failure still unlinks the temp file. Edge cases executed: setgid
(dropped — NIT), symlink (link destroyed, target's mode used — NIT), 0o444 target (works),
wider-than-0600 target (preserved — NIT), concurrent delete between `exists` and `stat`
(raises — WARNING).

**2. Security** — the widening direction is the one that matters and it is handled:
mode is set on the temp file *before* `os.replace`, so a 0600 target rewritten to a
0644 mode is never live at the wrong mode, and `test_write_atomic_sets_the_mode_before_it_replaces`
pins the ordering rather than the end state — it fails if the chmod moves after the
replace. No secrets, no external input, no new trust boundary. The one residual is the
state-dir hardening the change gives up, filed as a NIT above.

**3. Architecture** — the fix belongs in `write_atomic`, not the call sites: seven
callers want it and none can be trusted to remember. The only structural cost is the
duplicate it leaves standing in `cli._write_settings`, filed as a WARNING.

**4. Readability** — names are fine, nesting unchanged, no new branch beyond one
`if mode is not None`. The comments explain *why this shape* rather than narrating the
change, as AGENTS.md requires; the two defects in them are the stale symbol name and
the hardcoded count.

**5. Performance** — one extra `stat` and one `chmod` per write, both on paths that
already do a `mkstemp` plus a `replace`. Immaterial; the WARNING's fix removes the stat.

**6. Over-engineering** — nothing speculative. No flag, no branch nobody takes, no
abstraction. `net: −2 lines possible` (collapse `exists()`/`stat()` into one try/except);
a further −3 in `cli.py` once the duplicate is removed, which is a separate change.

**Regression tests** — four, and each is discriminating: without the chmod the mode
assertions read 0600, and the ordering test reads 0600 if the chmod moves after the
replace. Docstrings say why the test exists and name the failure, per AGENTS.md.
`test_write_atomic_creates_a_new_file_owner_only` is the one that earns its place
most — it pins a deliberate non-fix so the next person does not "finish" #324 by
widening the handoff.
