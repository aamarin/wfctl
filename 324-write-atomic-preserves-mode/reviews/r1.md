**The defect is fixed and the regression tests are real.** Removing the `os.chmod`
fails `..._rewrite_keeps_the_existing_files_mode`; moving it past `os.replace` fails
`..._sets_the_mode_before_it_replaces`. Every finding below is about the *stated
rationale* being wrong, not about the behaviour — three of them are one-line text
edits inside this branch's own scope, one is a follow-up in `cli.py`.

WARNING  wfctl/_io.py:L43-45 and tests/test_io.py:L105-108 — the ordering rationale is
false. `mkstemp` creates its file `0600` *always*, so the window a chmod-after-replace
opens is at `0600` and the final mode is the target's own — the window can never be
wider than owner-only, and never reaches group or other. "a disclosure the moment a
`0600` target is rewritten" is backwards: a `0600` target's chmod-after is `0600 →
0600`, no window at all.
The real argument for chmodding first is better than the one written down, and worth
keeping: an `os.replace` that lands and a chmod that then fails, or a process killed
between the two, leaves the file permanently at `0600` — #324 back, non-deterministically
and with no torn write to point at. That is also exactly the shape `cli.py:L2532-2539`
still has.
→ Restate both the code comment and the test docstring on the crash/partial-failure
argument. The assertion in the test is the right assertion; only the prose is wrong.

WARNING  wfctl/_io.py:L23-25 — the new-file carve-out asserts something untrue of the
call sites. Two of the seven create files in the **working tree**, not the state dir:

- `wfctl/cli.py:L1313` (`wfctl arch declare`) writes `<arch_root>/declarations/<branch>.md`,
  created on a branch's first declaration and then committed — it must be, `touched_on_this_branch`
  is checked on the next line. That is a file under `docs/architecture/`, which is the
  directory #324 names.
- `wfctl/cli.py:L2535` (`_write_settings`) writes the consumer's `.claude/settings.json`,
  created when absent — `_merge_hooks` computes `created` (L2582-2586) precisely for that case,
  and `_write_settings`'s own `if mode is not None` skips the chmod on create.

Both land at `0600` in a repository. That is #324's user-visible symptom reached by create
rather than by rewrite, so "fixed" is half true. Leaving the create case at `0600` may still
be the right call — the `session-summary.md` argument holds — but the docstring must not
claim the repo-file creators do not exist.
→ In scope: correct the docstring (say the new-file case is pinned for the state-dir
handoff, not that only the state dir creates). Out of scope: file a follow-up for the two
working-tree creators.

WARNING  wfctl/cli.py:L2532-2539 (out of scope — follow-up) — `_write_settings` now
duplicates the guarantee and keeps the shape `_io.py:L43` condemns: its own
`target.stat()` + post-`os.replace` `target.chmod(mode)`. `write_atomic` already reads
the same mode off the same resolved `target` and applies it before the replace, so the
trailing chmod is a no-op and its docstring paragraph ("it would hand back whatever mode
`mkstemp` chose rather than the one they set") is stale. Nothing in `tests/` covers that
chmod — the new `_io` tests are what makes deleting it safe.
→ Follow-up issue: delete L2534 and L2538-2539, trim the last docstring paragraph to the
symlink-resolve reason (which is still load-bearing and is *not* subsumed).

NIT  wfctl/_io.py:L38 — `& 0o777` drops setuid/setgid/sticky while L23 promises "An
existing file keeps its permissions", and the tests assert with `stat.S_IMODE` (`0o7777`),
so code and test disagree about what "the mode" is. No wfctl target plausibly carries
those bits, so this is wording: say "permission bits", or use `stat.S_IMODE` on both sides.

NIT  wfctl/_io.py:L34 — "all seven want it" hardcodes a call-site count into a comment.
AGENTS.md makes this exact argument about the mypy-strict count ("no number is written
down here on purpose … it drifts"). "every caller" says the same thing and never goes stale.

NIT  wfctl/_io.py:L32 — "Read before the temp file exists, so a stat failure orphans
nothing" is not load-bearing: the `except Exception` at L49 unlinks `tmp` on *any*
exception, so a stat inside the `try` would orphan nothing either. Reading early is fine;
the reason given for it isn't the reason.

NIT  wfctl/_io.py:L38 — `path.exists()` then `path.stat()` is two stats and a small TOCTOU:
a target deleted between them now raises `FileNotFoundError` where `write_atomic` used to
just create the file. One syscall, no race:
`try: mode = stat.S_IMODE(path.stat().st_mode)` / `except FileNotFoundError: mode = None`.

NIT  tests/test_io.py:L117 — `def recording_replace(src: str, dst: str)`: `dst` is a `Path`
(`write_atomic` calls `os.replace(tmp, path)`). `mypy` runs on `wfctl/` only, so nothing
catches it. `str | os.PathLike[str]` is accurate.

NIT  tests/test_io.py — no test proves the temp file is cleaned up when the *chmod* fails.
It is (the chmod is inside the `try`), but the existing `..._target_unchanged_on_failure`
only patches `os.replace`. One `patch("os.chmod", side_effect=OSError)` case would pin
the new statement's failure path; low value, author's call.

1. **Correctness** — traced `write_atomic` against all seven call sites (`_arch.py:L495`,
   `_session.py:L110/L306/L483`, `_verify.py:L112`, `cli.py:L1313`, `cli.py:L2535`) and
