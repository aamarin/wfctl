## Review: `origin/main...324-write-atomic-preserves-mode` (reviewer r3)

Target: `a23fb75 fix(io): write_atomic carries the mode it replaces` — `wfctl/_io.py` (+19), `tests/test_io.py` (+76).

The fix itself is correct and the regression tests are the right ones: a rewrite
now carries mode, the executable bit survives, the new-file case is pinned, and
the ordering is asserted on what `os.replace` sees rather than on the end state.
Every finding below is about *rationale written into the code and docstrings* and
about the create path the fix deliberately leaves alone — none of them is a
defect in the mode-preserving behaviour.

WARNING  wfctl/_io.py:L43-45 — the comment's stated reason for chmod-before-replace is false, and the same false reason is written into `tests/test_io.py:L105-108`. The window after `os.replace` can only ever be *narrower* than the preserved mode, never wider: `mkstemp` creates at `0600`, so during the window group and other bits are always `000`, and the only bits a post-replace chmod can add are owner bits. "A disclosure the moment a `0600` target is rewritten" cannot happen — a `0600` target preserves `0600`, which is exactly the mode the file already has in the window. AGENTS.md says existing comments are dense with rationale and the next reader should be able to act on them; a reader who acts on this one will defend the wrong property. The ordering is still right, for two reasons worth having instead: (a) a chmod that fails *after* the replace leaves the file live at the wrong mode with no way back, while a chmod that fails before it aborts into the existing cleanup and leaves the target untouched — this is precisely the shape `_write_settings` (cli.py:L2534-2539) has and this function is replacing; (b) a reader that opens the file in the window sees `0600` — a hook that is momentarily not executable, a group-readable record momentarily unreadable. → replace the disclosure argument in both the comment and the test docstring with the failure-atomicity argument; keep the test.

WARNING  wfctl/_io.py:L35 — `_write_settings_json` does not exist anywhere in the tree (`grep -rn "_write_settings_json" .` matches only this comment). The function meant is `_write_settings`, `wfctl/cli.py:L2510`. A comment whose only job is to point the next reader at the counter-example points them at nothing greppable. → name it `_write_settings` (`cli.py`).

WARNING  wfctl/cli.py:L2534-2539 (out of scope — report, don't fix) — with this change landed, `_write_settings`'s hand-rolled stat-and-chmod is dead: it resolves the symlink first, so `write_atomic` stats the same inode and preserves the same mode, and the trailing `target.chmod(mode)` now sets the mode to what it already is. Worse, its docstring still asserts the reason ("it would hand back whatever mode `mkstemp` chose rather than the one they set"), which is no longer true, and `tests/test_install_hook_merge.py:L393` ("The write goes through mkstemp + os.replace, which installs a fresh file carrying the temp file's 0600") now passes for a reason its docstring contradicts. This is the eighth-caller argument the new comment makes, so the branch that makes the argument is the one that should collect the follow-up. → file a follow-up: drop the stat/chmod pair from `_write_settings`, trim the last paragraph of its docstring to the symlink-resolution half (which is still load-bearing), and rewrite the test docstring to say the mode now comes from `write_atomic`.

WARNING  wfctl/_io.py:L23-25 (out of scope — report, don't fix) — the new-file case is left at `0600` on the premise that new-file callers write into the state dir. Two of the seven do not. `wfctl arch declare` (`cli.py:L1313`) creates `docs/architecture/declarations/<branch>.md`, a file the command's own comment calls committed and hand-authored; `_write_settings` creates `.claude/settings.json` in a consumer repo when the file is absent (`cli.py:L2611-2613`). Both land at `0600` beside neighbours that are `0644` (`ls -l docs/architecture/declarations/` in this worktree: every existing declaration is `-rw-r--r--`). That is #324's own complaint — "a committed file under `docs/architecture/` is owner-only" — reached by the create path instead of the rewrite path. Not a regression (the create path behaved this way before), and the handoff argument for `session-summary.md` is sound, so `write_atomic` is not obviously the place to fix it. → file a follow-up for the create path, and until it is fixed narrow the docstring: say the new-file case is pinned `0600` for the state-dir callers and that a caller creating a file in the working tree gets it too, rather than implying every new-file caller is a state-dir one.

NIT  wfctl/_io.py:L38 — `path.exists()` then `path.stat()` is two syscalls with a race between them: a target that vanishes in the gap turns into a `FileNotFoundError` out of a function whose only documented raise is the missing-parent one. → `try: mode = path.stat().st_mode & 0o777 / except FileNotFoundError: mode = None` — one syscall, no gap, same result.

NIT  wfctl/_io.py:L38 — `& 0o777` silently drops setuid/setgid/sticky, while the tests assert with `stat.S_IMODE`, which is `0o7777`. Nothing wfctl writes carries those bits today and dropping setuid is the safe direction, so this is a defensible choice — but it is an undocumented one in a comment block that documents everything else. → either `stat.S_IMODE(path.stat().st_mode)`, or the issue's own suggestion `shutil.copymode(path, tmp)` (stdlib, one call, copies `0o7777`); if `0o777` is deliberate, say why in the comment.

NIT  wfctl/_io.py:L47 — `os.chmod(tmp, mode)` is a second path lookup on a name the process already holds an fd for. → `os.fchmod(f.fileno(), mode)` inside the `with`, which cannot be redirected and needs no path.

NIT  wfctl/_io.py:L34 — "all seven want it" writes a call-site count into a comment that will drift the moment an eighth is added; AGENTS.md declines to write such a number down for exactly this reason ("no number is written down here on purpose"). → "because every caller wants it".

NIT  tests/test_io.py:L117 — `recording_replace(src: str, dst: str)` is called with `dst` as a `Path` (`write_atomic` passes `path`). Harmless at runtime and `mypy` does not see `tests/`, but the annotation is wrong for anyone reading the stub to learn the signature. → `dst: str | Path` (or `os.PathLike[str]`).
