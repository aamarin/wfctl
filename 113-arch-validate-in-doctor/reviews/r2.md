## Findings

**WARNING  wfctl/cli.py:L3292 — the new check contradicts `doctor_cmd`'s own
written admission criterion, and the diff neither answers nor amends it.**

`doctor_cmd`'s docstring (`cli.py:3477-3492`) states the rule for what belongs
here:

> A check belongs here when it describes something wfctl installed or seeded that
> no longer matches its source, and can name the command that repairs it. A check
> describing what the *user* has or hasn't done belongs wherever that work happens
> — this command runs unprompted at every session start, which makes it a magnet
> for anything you want noticed, and each arrival costs the exit code some of its
> meaning.

Architecture records satisfy neither clause. `_arch.py`'s module docstring is
explicit that "wfctl reads records; it never mediates their content" — they are
hand-authored user work, not something wfctl installed or seeded. And the check
names a *path*, not a repair command; the comment at L3316 acknowledges this
directly ("The one repair is editing the records, so the reader needs the path
rather than a command"). The new docstring's justification — "drift is what this
command already looks for" — argues the conclusion without engaging the rule it
breaks.

The same docstring also inventories the checks and sets a splitting trigger:

> Two of the checks below are freshness (the tool version, the content hash) and
> three are integrity (the teardown hook, the spec-root move, abandoned entries)
> … Kept together while the whole report is five lines a session; a sixth check
> is the sign to split them.

That inventory was already two checks stale on `main` (`_check_verify_config`,
`_check_managed_hooks` are unlisted), so this diff does not create the drift —
but it is the seventh check arriving past a threshold the file asked the author
to respond to at the sixth, and it leaves the paragraph unamended.

I am *not* asking to move the check — the issue chose `doctor` over `arch
context` for a good reason and I agree with it. The defect is that the file now
carries a rule its own code violates, which is exactly the failure mode `#113`
was about in the other direction. **Fix:** amend `doctor_cmd`'s docstring to
widen the admission criterion (it plainly is wider now: "state in this repo that
wfctl can check and a person must repair" covers all seven), refresh the
freshness/integrity inventory to match the code, and either restate or retire the
"sixth check" trigger. One paragraph, in this diff.

**WARNING  wfctl/cli.py:L3319 — path printed without `soft_wrap=True`, against a
rule this file states twice.**

```python
console.print(f"    records: {_arch_location(root, repo_root)}/")
```

`_check_workmux_hook` (`cli.py:3075-3080`) documents why every path line in
`doctor` carries `soft_wrap=True`:

> rich would otherwise wrap this at the terminal width and could split the path
> itself, which both reads badly and breaks assertions on it.

`_check_abandoned_entries` follows the same rule at its `    {path}` line. An
out-of-tree arch root is printed absolute (`_arch_location`'s documented
behaviour), so this is the check most likely to emit a long path, and it is the
one that opts out. The failure is machine-dependent — it will not show up in CI
and will bite whoever first asserts on this line in a narrow terminal.

**Fix:** `console.print(f"    records: {_arch_location(root, repo_root)}/",
soft_wrap=True)`. Same for L3314 if a VR-004 message listing several successors
is expected to run long.

**WARNING  wfctl/_arch.py:L136 (`load_records`) — the check does not cover the
Level-3 design-record tier, and nothing in the diff says so.**

`load_records` globs `root.glob("*.md")` — flat, not recursive. This repo's arch
root already has two subdirectories holding real records:

- `docs/architecture/design/122-a-record-persists-no-routing-state.md`
  (`status: proposed`)
- `docs/architecture/declarations/59-deployment-key-metadata.md`

`wfctl/agents/skills/software-design-decisions/design-record-template.md` puts
design records at `<arch-root>/design/<issue>-<decision>.md` and gives them a
`supersedes:` frontmatter field with its own status vocabulary (`proposed ->
approved -> superseded | rejected` — note `approved`, which is not even in
`_arch.STATUSES`). So the tier that the templates actively teach people to write
`supersedes:` into is invisible to `validate()`, and stays invisible after this
change.

The issue's premise is "a broken record set was indistinguishable from a healthy
one." After this diff that sentence is still true for every design record. Worse,
the exposure is asymmetric: a *top-level* record naming a `design/` slug in
`supersedes:` would produce a false VR-003 **error** and exit 1 at every session
start, with a message ("which is not a record here") that is factually wrong.

This is inherited from `_arch.py`, not introduced here — but this diff is what
promotes the limitation from a silent gap into a hard exit-1 gate, so it owns
naming it. **Fix (minimum):** one sentence in `_check_arch_records`'s docstring
stating that it validates the flat top-level tier only, and that design records
under `<arch-root>/design/` are out of its reach — so the next reader does not
assume `doctor` covers the whole tree. **Fix (better, but file it, don't smuggle
it in):** a follow-up issue for whether `load_records` should recurse or whether
the tiers need separate validation.

**NIT  wfctl/cli.py:L3314 — colon separator reads oddly against predicate-style
messages.**

Every `Finding.message` in `_arch.validate` is written as a predicate meant to
follow its subject directly: `"supersedes itself"`, `"is superseded, but no
record supersedes it"`, `"is superseded by 2 records: …"`. The colon renders them
as `⚠ orphan: is superseded, but no record supersedes it`. A space would give
`⚠ orphan is superseded, but no record supersedes it`, which is the sentence the
messages were written to be. Note VR-004's message already contains a colon, so
the current form emits two. Author's call — the tests assert on slug and message
separately and would not need changing.

---

**NIT  wfctl/cli.py:L3312 — findings print with errors and warnings interleaved.**

`_arch.validate` returns VR-003 errors, then VR-002 warnings, then VR-004 errors,
and `_check_arch_records` prints in that order — so a mixed set renders `✗ … ⚠ …
✗ …`. Every other multi-line block in `doctor` is homogeneous, and the review
rubric's own "most-severe first" instinct applies to a report a human skims at
session start. `sorted(findings, key=lambda f: f.level != "error")` is a stable
one-line fix. Equally defensible to leave it: source order groups by rule, which
is its own kind of readable.
