## Probe results

Commands are run from the feature worktree. `<main>` is the main checkout.

| Command | Spec root | State root | origin/main | HEAD |
|---|---|---|---|---|
| `git -C <main>/state add x` | `<main>` | `<main>/state` | **allowed (exit 0)** | refused (exit 2) |
| `git -C <main>/state commit -m x` | `<main>` | `<main>/state` | **allowed (exit 0)** | refused (exit 2) |
| `git -C <main> commit -m x` | `<main>` | `<main>/state` | refused | refused |
| `git -C <main>/specs commit -m x` | `<main>` | `<main>/state` | refused | refused |
| `git -C <main>/specs commit -m x` | `<main>/specs` | `<main>/state` | refused | refused |

The old guard let a commit through onto `main` in this layout, and the new code stops it. This works because `committable` asks only about the spec root (`shared[:1]`), and it vouches for any target below that root whose top level is the root. On `origin/main` the spec root `<main>` qualified, so it vouched for `<main>/state`. `refusal` then keeps a vouched folder whenever it sits under *any* exempt root (`_guard.py:670`, `_owner(c, exempt)`). `_shareable` drops `<main>` but keeps `<main>/state`, which is the state root. So the folder was vouched for through one shared root and exempted through another, and the commit landed on `main`.

## Passes

### 1. Correctness

The code change is correct, and it closes the hole the issue describes.

- `owns_branch` now returns False when `realpath(root) == _main_worktree(here)`. The check comes after the test for a different repository, so a store that is a repository of its own still passes. It comes before the `symbolic-ref` read, so a main checkout with a detached HEAD is refused here too.
- When `_main_worktree(here)` returns None, the comparison is False and the existing branch test runs. That is the same answer as before, so nothing new can fail open.
- A subfolder of main, such as `<main>/specs`, was already refused by the `taken` loop, because the main checkout's own block names it. A root spelled with a different case of the same path (macOS) misses the new check and is then refused by the `taken` loop, so it also fails safe.
- When `here` is the main checkout, `owns_branch(main, main)` now returns False where it returned True before. Neither caller is affected. `layout` returns `in_repo` first, and the guard never needs an exemption for a write in its own worktree.
- `layout` gives the same answer for every input. Its own check still runs before the detached test, so a main checkout with no branch still reads `in_repo`.
- The only callers of `owns_branch` are `committable` and `layout` (`git grep`, tests and docs excluded). No caller breaks.

The record's claims are partly false. See W1.

### 2. Security

The change makes the guard stricter, and it takes no new input. W1 is a security fix that the change reports as a refactor.

### 3. Architecture

Putting the rule in `owns_branch` fits the module: `_main_worktree` already lives there and runs with `_quiet_env`, which `test_every_git_call_runs_without_a_prompt` enforces. Dependencies are unchanged, with `_hook` importing `_spec_store` lazily as before. The level-2 "no boundary" declaration holds: no component gains or loses authority. The level-3 record compares the decision against a direct baseline, which is right for its shape.

### 4. Readability and simplification

The comments explain why, in the style of the file. Two wording nits follow, N2 and N3.

### 5. Performance

On the same-repository path, `owns_branch` now runs `git worktree list --porcelain` twice: once in `_main_worktree(here)` and once for the `taken` loop. That is one extra git subprocess, which I estimate at about 5 to 10 ms. The guard pays it only for a `git` command that was already headed for a refusal, and `layout` pays it once per call. The record states this cost honestly. See N1 for the trade.

### 6. Over-engineering

- `wfctl/_spec_store.py:L124-L126`, `shrink`: the listing could be read once and its first block used as the main checkout, saving the second subprocess. This would duplicate `_main_worktree`'s parsing, though, and the record's argument is that the rule should live in one place. I lean toward keeping it as written. This is N1.

Nothing to delete. The two tests are the minimum.

The design record also says "Currently, no commit gets through". The probe above disproves both claims. On `origin/main`, with the spec root at the main checkout (`.`, or an absolute `WFCTL_SPEC_DIR`) and a state root inside it, `git -C <main>/state commit -m x` from a feature worktree exits 0 and commits onto `main`. HEAD refuses it. `_shareable` refusing the main checkout did not cover this, because the folder was exempted through the state root, not the spec root. The release note is in the wrong category, and it publishes a false statement in the GitHub release. The record's "Verified" list is incomplete: its eight commits all had a single shared root. → Rename the note to `changes/603.fix.md`, with text like "The worktree guard no longer allows a commit onto the main checkout's branch when the spec root names the main checkout and the state root sits inside it." Correct the declaration's last clause and the record's Context and Consequences to name this case. Add the probe to Verified. Also mention it in the PR body's Before / After. The declaration's "no new boundary" verdict still stands.
