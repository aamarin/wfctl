# Review r2: `603-guard-main-checkout` (`git diff origin/main...HEAD`, three commits)

## Summary

The change does what it says. The `owns_branch` function now returns False for the project's `main` checkout, so the guard's `committable` function no longer returns the `main` checkout or any folder in it. The guard's end-to-end verdicts are unchanged, and I confirmed that against real git with and without the fix. Both new tests fail without the fix and pass with it. I found no blocker. One warning concerns a test the design record lists under Verification that does not exist, and the rest are nits on comments and the record.

## Evidence gathered

1. `uv run pytest -q tests/test_spec_store.py tests/test_worktree_guard.py tests/test_guard_entry.py` passed 324 tests.
2. `uv run ruff check wfctl/ tests/` passed, and `uv run mypy` on `_spec_store.py` and `_hook.py` reported no issues.
3. I ran both new tests with the old behaviour restored in memory. I patched `_main_worktree` to return None only when `owns_branch` calls it. `test_the_main_checkout_never_owns_a_branch` and `test_the_main_checkout_never_takes_the_stores_commits` both failed, and `committable` returned `<main>` and `<main>/specs`. That means both tests are real regression tests.
4. I built a scratch project in a temporary directory with a manifest of `{"spec_root": "."}` in the `main` checkout, once with the feature worktree beside the `main` checkout and once nested under `<main>/wt/`. Then I sent commands through the real hook (`wfctl hook worktree-guard`) from the feature worktree, both with the fix and with the old behaviour patched back in:

   | Command | Old | New |
   |---|---|---|
   | `git -C <main> commit -m x` | 2 | 2 |
   | `git -C <main>/specs commit -m x` | 2 | 2 |
   | `git -C <main> add . && git -C <main> commit -m x` | n/a | 2 |
   | `git -C <feature> commit -m x` | 0 | 0 |

   The refusal message is the same in both runs ("is in another worktree ..., and `git` is not a read command"). The reason is that `refusal()` keeps a `committable` entry only when it sits inside an exempt root (`_guard.py:670`), and `_shareable` never puts the `main` checkout in the exempt set. As a result, the set of vouched commits is empty either way.
5. `owns_branch` has two callers, `committable` (`_hook.py:123`) and `layout` (`_spec_store.py:212`). `tests/test_guard_entry.py:140` also reaches it, but with a `here` of `/r/a` that does not exist, so `_common_dir` returns None before the new check runs.
6. Commit 9ddb8cd exists and added the `_main_worktree(repo)` check to `layout`, as the record says. `test_every_git_call_runs_without_a_prompt` exists at `tests/test_spec_store.py:875`, and `spec-storage-read-from-git` is in force according to `wfctl arch context`.

## Passes

1. **Correctness.** I traced `owns_branch`, `_main_worktree`, `layout`, `committable`, `_shareable`, `refusal` and `_exempt`. The new check sits after the different-repository test, so a spec repository of its own still passes. `<main>/specs` already failed the branch test before the change, because the `main` checkout's branch is taken by a worktree whose path differs from `<main>/specs`. The new check therefore adds an answer only for the root equal to the `main` checkout, including a symlink to it, since both sides go through `realpath`. In a bare-repository layout, `_main_worktree` returns the bare directory, which no checkout equals, so nothing changes there. When `here` is the `main` checkout itself, `owns_branch(main, main)` flips from True to False. `layout` blocks that case before it asks, and `_shareable` refuses it in the guard, so no verdict changes. I found no defect.
2. **Security.** The change narrows what `committable` vouches for and widens nothing. `_main_worktree` runs git through `_read`, which uses `_quiet_env`. A failure in `_main_worktree` returns None and falls through to the branch test, so it never vouches for anything the old code did not.
3. **Architecture.** Putting the rule inside `owns_branch` gives every caller the same answer and matches the store's existing rule. The record's choice over the baseline is argued and fits `spec-storage-read-from-git`. The level-2 declaration that no boundary moves is accurate. The module dependency direction is unchanged, since `_main_worktree` already lived in `_spec_store`.
4. **Readability.** The findings are N1 - N4 below. Test names are sentences, and both docstrings name the failure they pin.
5. **Performance.** `owns_branch` now runs `git worktree list --porcelain` twice when the root and `here` share a repository, once in `_main_worktree` and once for `taken`. One call measured about 7.6 ms in this repository. The guard pays it only on its second pass, but that pass includes every ordinary commit into a `specs-trunk` worktree from a feature worktree. See N5.
6. **Over-engineering.** Nothing to delete. The change adds three lines of code, and the docstring and record carry the rest.

## Findings

WARNING `docs/architecture/design/603-owns-branch-refuses-main-checkout.md:L79` — The fourth Verification bullet says "The hook, run against a real `git commit` aimed at the `main` checkout, refuses it, and a commit inside this worktree is still allowed." No test does this. The two new tests call `owns_branch` and `committable` directly, and the existing hook tests with a `main`-checkout spec root (`test_a_shared_root_covering_a_worktree_is_not_honoured`, `test_the_main_checkout_is_never_the_spec_root`) check `rm -rf`, not a commit. The release note's `none` category rests on the claim that verdicts are unchanged, and nothing in the suite pins that claim for a commit. → Add a hook-level test in `tests/test_worktree_guard.py` that writes `{"spec_root": "."}` into the `main` checkout's manifest and asserts `_hook(feature, f"git -C {main} commit -m x").exit_code == 2` and `_hook(feature, f"git -C {feature} commit -m x").exit_code == 0`. The table above shows it passes today. Or reword the bullet as a manual check.

NIT `wfctl/_spec_store.py:L203-L206` — The rewritten `layout` comment ends with "both are still turned away here, before the detached test below, so a code checkout with no branch reads as code". That reason is complete for the `main` checkout, but not for the caller's own checkout. `owns_branch(here, here)` still returns True, because the root's own worktree is left out of `taken`, so `top_level(repo)` in the tuple is still what stops the store from committing onto the code's branch. The removed sentence "It has to be turned away before that rule runs" said that. The word "still" also only makes sense next to the diff. → End with something like "`owns_branch` blocks the main one itself, but not this one, so this one has to be blocked here before that rule runs. Both are blocked before the detached test below, so a code checkout with no branch reads as code rather than as a broken store."

NIT `wfctl/_spec_store.py:L104-L108` — The new docstring paragraph narrates history: "`layout` refused it before asking and the guard did not, so the guard vouched for a commit onto `main` (#603)." After this change that state no longer exists, so it belongs in the commit message. "Refused by name" is also inaccurate, since the check compares resolved paths, and "the code's whatever it is called" needs a comma. → "The main checkout is refused by its path, because its branch is the code's, whatever it is called. From a feature worktree no other worktree has that branch checked out, so the branch test alone would pass it."

NIT `docs/architecture/design/603-owns-branch-refuses-main-checkout.md:L22-L24` — The Verified line numbers are from `origin/main`, not this branch. On HEAD, `layout`'s check is at line 207 (not 196), its `owns_branch` call is at 212 (not 201), `_main_worktree` is at 224 (not 213), and `return branch not in taken` is at 138 (not 129). The record is durable, so readers will open it against the merged code. → Cite function names only, or say the numbers are as of `origin/main` at 31d9f39.

NIT `docs/architecture/design/603-owns-branch-refuses-main-checkout.md:L66` — "a commit in the agent's own worktree never reaches `committable`" is imprecise. `committable` is asked about shared roots, not commit locations. When the spec root resolves to the agent's own worktree, for example `spec_root: "."` read from that worktree's own manifest, `committable` does evaluate it and `owns_branch` returns True. That costs nothing, since the guard never refuses a commit in the session's own worktree, but the sentence states it as a fact. → "the guard never refuses a commit in the agent's own worktree, so it has no use for the own-checkout case."

NIT `wfctl/_spec_store.py:L124-L133` — `owns_branch` reads `git worktree list --porcelain` twice, about 7.6 ms each here. Reading it once and taking the first block as the `main` checkout saves one subprocess per call. It would also let the function return False when the listing fails. Currently, a failed listing leaves `taken` empty and the function returns True, which contradicts the docstring's "False whenever git cannot answer, for `root` or for `here`". That behaviour predates this change, so it belongs in a follow-up issue rather than this diff.
