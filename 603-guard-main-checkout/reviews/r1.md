# Review r1: `git diff origin/main...HEAD` on 603-guard-main-checkout

Reviewer r1. Rubric: `.agents/skills/code-review/SKILL.md`, all six passes, run by hand (no sub-reviewers).

## Summary

The code change is correct, and the new tests fail on `origin/main` and pass on HEAD. The problem is the claim that the guard's verdicts do not change. That claim is false. On `origin/main` the hook **allows** a commit onto `main` from a feature worktree in a layout the test suite already exercises: the spec root is the main checkout and the state dir sits inside it. This branch closes that hole. So the release note category (`none`), the release note text, the level-2 declaration, the design record's Context and Consequences sections, and one test docstring all describe a refactor when the change is really a fix.

## Evidence run (read-only; temp repos under `tempfile`, removed on exit)

1. `uv run pytest -q tests/test_spec_store.py tests/test_worktree_guard.py` gave 314 passed. `uv run ruff check wfctl/ tests/` passed, and so did `uv run mypy wfctl/`.
2. **The new tests are real regression tests.** I ran them against `git archive origin/main wfctl` with `python -P -m pytest --import-mode=append` and `PYTHONPATH=<extracted>`, so the base code is imported rather than the worktree's (I checked `wfctl._spec_store.__file__`). `test_the_main_checkout_never_owns_a_branch` failed with `owns_branch(project, feature)` returning True. `test_the_main_checkout_never_takes_the_stores_commits` failed with `committable` returning `[<main>, <main>/specs]`. Both pass on HEAD.
3. **The end-to-end verdict changes.** I used the `_store_layout` shape: main checkout, a `specs-trunk` worktree beside it, and a feature worktree at `<main>/wt/129-x`. I set `WFCTL_SPEC_DIR=<main>` and `WFCTL_STATE_DIR=<main>/.state`, then ran `_hook.worktree_guard` with cwd set to the feature worktree on the command `git -C <main>/.state commit -m x`:

   | code | exit | meaning |
   |---|---|---|
   | `origin/main` | 0 | allowed; `git -C <main>/.state symbolic-ref HEAD` is `refs/heads/main` |
   | HEAD | 2 | refused, "would not land on a branch of its own" |

   `git -C <main>/.state add x/n` and `git -C <main>/.state/x add n` give the same 0 → 2 change. `git -C <main> commit` is refused on both, which is the case the record checked.

   The mechanism: `committable` is asked about the spec root only (`shared[:1]`), and on base it qualified `<main>` and every target whose top level is `<main>`, `<main>/.state` included. `refusal` then filters those targets by `_owner(c, exempt)`. `exempt` holds the *state* root `<main>/.state`, which `_shareable` accepts because it is neither `roots[0]` nor holds a worktree. The two rules the record says "happen to line up" do not line up when the exempt root and the root `owns_branch` vouched for are different shared roots. `test_the_hook_honours_the_state_dir_override` already treats `WFCTL_STATE_DIR=<main>/.state` as a supported layout.
4. **The bare-repository layout is unchanged.** It was open before this branch and is still open after it. With `git clone --bare` and worktrees `main` (on `main`) and `42` (on `42-feature`), `git worktree list` puts the bare dir first. On HEAD, `owns_branch(<main-wt>, <42>)` returns True, and the hook exits 0 for `git -C <main-wt> commit -m s` with `WFCTL_SPEC_DIR=<main-wt>`.
5. `git worktree list --porcelain` costs about 7 ms per call in this repo, which is the cost of the one call this diff adds.

## Passes

**1. Correctness.** The code does what the issue asks. `owns_branch` returns False when `realpath(root) == _main_worktree(here)`. The check runs after the different-repository test, so a spec repository of its own still passes. Moving `real` up does not change the later `taken` loop. A case-variant spelling of the main checkout on macOS does not match `real`, but it still fails the branch test, because `taken` then includes `main`. So it is not a bypass. The findings in this pass are about the claims made around the code (see the BLOCKER below), the bare-repo gap that is still open, and one pre-existing fail-open path.

**2. Security.** The change narrows a write exemption in a guard. It adds no input handling. It closes one real escalation path (evidence 3) and leaves another one open (evidence 4). `_main_worktree` runs under `_quiet_env`, and `test_every_git_call_runs_without_a_prompt` covers it.

**3. Architecture.** Putting the rule in the shared predicate fits `spec-storage-read-from-git` and the existing pattern of one rule for the guard and the store. `layout`'s own check is redundant but justified, because it has to come before the `detached` test. The record states that. No new dependency.

**4. Readability.** The comments are mostly "why". A couple of lines narrate history, and one sentence is missing a comma (NITs below).

**5. Performance.** The change adds one subprocess, about 7 ms, per same-repository root. The guard pays it only on a git command that was already headed for a refusal. `layout` now runs `worktree list` three times. That is acceptable, and the change is small enough to shrink (NIT).

**6. Over-engineering.** The code diff is minimal. The 84-line design record is how this project works, not bloat. One `shrink:` item is listed below.

## Findings

BLOCKER  changes/603.none.md:L1, docs/architecture/declarations/603-guard-main-checkout.md:L3, docs/architecture/design/603-owns-branch-refuses-main-checkout.md (Context ¶3 "Currently, no commit gets through", Consequences "The guard's verdict does not change for any command") — these claim that nothing the guard allows or refuses changes. That is false. On `origin/main`, with the spec root at the main checkout and the state dir inside it, the hook allows `git -C <main>/.state add|commit` and the commit lands on `main` (evidence 3). HEAD refuses it. Shipping this as `none` puts a guard fix into the release text as "nothing changed", and leaves two durable records asserting something the code disproves. → Rename to `changes/603.fix.md` and say what a user notices, for example: "The worktree guard no longer lets a feature worktree commit into a state or spec folder inside the main checkout when the spec root is the main checkout itself. Such a commit landed on `main`." Rewrite the declaration's last sentence and the record's Context ¶3 and Consequences to describe the hole. Add a Verified bullet for this layout, and say that the `_owner(c, exempt)` filter at `_guard.py:669-671` can pass a folder `committable` qualified under a *different* shared root. Then check whether the "no new boundary" conclusion still holds. It probably does, since no authority moves, but the reason given for it is the false one.

WARNING  tests/test_worktree_guard.py:L995-1004 — the only guard-side test is a unit test of `committable`, and its docstring repeats the false claim ("The hook still refused, but only because `_shareable` drops the main checkout first"). No test shows the user-visible verdict change. That leaves `owns_branch` free to be edited later with the hole coming back silently. → Add a hook-level test, verified to fail on `origin/main` and pass on HEAD:
```python
def test_a_state_dir_in_the_main_checkout_takes_no_commit_when_the_spec_root_is_the_main_checkout(
    tmp_path: Path, monkeypatch: pytest.MonkeyPatch,
) -> None:
    main, _, feature = _store_layout(tmp_path)
    monkeypatch.setenv("WFCTL_SPEC_DIR", str(main))
    monkeypatch.setenv("WFCTL_STATE_DIR", str(main / ".state"))
    (main / ".state").mkdir()
    refused = _hook(feature, f"git -C {main}/.state commit -m x")
    assert refused.exit_code == 2
    assert "would not land on a branch of its own" in (refused.stderr or refused.output)
```
Then fix the docstring so it names this case.
