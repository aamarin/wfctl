### Findings

WARNING  wfctl/_archive.py:L389 — An empty spec dir, or one holding only empty subfolders, now counts as something to save. With a clean worktree, `save` writes an `unsaved/` holding one empty folder, moves any earlier `unsaved/` aside, and the hook prints `✓ saved 0 files → …/unsaved` (reproduced). That is the state `test_nothing_to_save_creates_no_folder` exists to prevent: "an empty `unsaved/` would read as a save that found nothing it could name" (FR-022). An empty spec dir is plausible, for example one made by `mkdir -p` before any step wrote into it. → Drop an outside folder that holds no file or symlink before the `if not files and not folders and not outside` test, for example with `any(os.scandir)` or a walk, and add a test beside `test_nothing_to_save_creates_no_folder`.

WARNING  docs/architecture/spec-storage-read-from-git.md:L66 (accepted), docs/architecture/design/store-specs-at-removal.md:L90, docs/architecture/removal-copy-destinations.md:L44 — Three docs still describe the old behaviour. The accepted record still says a plain folder "is not backed up anywhere, and removal says so". The design doc says removal "does nothing and says … that nothing backs them up". `removal-copy-destinations` defines `unsaved/` as worktree-relative paths only, and now one folder in it is something else. The diff touches none of them, so the next reader of the record learns the behaviour that was removed. → Add a log line to the accepted record and correct item 3 of the design doc. Add a consequence to `removal-copy-destinations` saying that a spec dir outside the worktree lands at `unsaved/<name>/` and why that name can clash.

NIT      wfctl/cli.py:L1612 — The `ℹ … a copy is saved with the unsaved work` line prints before the save runs. When the save fails, the output says "a copy is saved" and then, on the next line, `✗ couldn't save unsaved files … removal stopped` (reproduced). → Say "a copy goes into unsaved/ with the untracked files", or something else that doesn't claim the save already happened.

NIT      wfctl/cli.py:L1750 — `lines[0], extra = _plain_spec_dir_backup(...)` assumes that `report_lines` puts the `not_applicable` line first and nothing after it that has to change. That is true today. If `report_lines` ever adds a line to this outcome, the replacement silently swaps out the wrong one. → Build the removal's line list here for `unmanaged` and leave `report_lines`' output alone. Or split the tuple assignment into two statements, so the replacement shows at a glance.

NIT      wfctl/_archive.py:L366 — `outside` is keyed by `path.name`, so two outside folders with the same name keep the last one and drop the other with no error. There is only one caller with one path, so it can't happen today. But `save(extra=...)` accepts a list, and the drop is silent data loss. → Raise `SaveFailed` on a repeated name, as the worktree clash already does, or note in the docstring that names are unique.

NIT      changes/56.addition.md — A removal that used to go ahead can now stop (exit 1) when the copy fails. Under AGENTS.md, that is something users rely on behaving differently, which is `change` rather than `addition`. → Consider `56.change.md`. This is the author's call.

### Over-engineering

wfctl/_archive.py:L382: shrink `p in name.parents` is dead code, because `name` is always a single path part (`Path(path.name)`), so its only parent is `Path(".")`, which no file or folder entry ever equals. Use `p == name or name in p.parents`, which is `_under(str(p), name)`, a helper already in the module.
