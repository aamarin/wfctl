### Findings

BLOCKER  wfctl/cli.py:L1612, wfctl/_archive.py:L365 — a relative spec folder path is copied as if it were inside the worktree → pass `spec_dir.resolve()` (or `.absolute()`) out of `_plain_spec_dir_backup`, and add a hook test with a relative `WFCTL_SPEC_DIR`.

`spec_root` returns `WFCTL_SPEC_DIR` as written, so a relative value such as `../specs` gives a relative `spec_dir`. The store reads its layout through `os.path.abspath`, so it reports `unmanaged` correctly. Then `save` puts every relative path in `inside`, because of `not path.is_absolute()`, and `_copy_into` copies from `worktree / rel` to `staging / rel`. Previously this layout copied nothing, so the path never reached `save`. I ran two cases.

1. Working directory is the worktree, `WFCTL_SPEC_DIR=../outside-specs`. The copy is written to `<state>/outside-specs/40-feature`, outside `unsaved.staging`, so the rename never moves it. The hook prints the "a copy is saved" line and then `✓ saved 0 files → <state>/unsaved`, and leaves an empty `unsaved/`, which is the case `test_nothing_to_save_creates_no_folder` exists to prevent. The second removal on that branch then fails with `[Errno 17] File exists: …/unsaved.staging/../outside-specs/40-feature` and exits 1. Every later removal stops the same way until someone deletes the stray folder by hand.
2. Working directory is anywhere else, `WFCTL_SPEC_DIR=outside-specs`. The copy reads `<worktree>/outside-specs/40-feature`, which doesn't exist, so the removal stops with `[Errno 2]`. That is a stopped removal for a folder that survives the removal anyway.

This means a `..` in the path can also write anywhere relative to the state dir. The manifest's `spec_root` is anchored to the folder that declares it, so as far as I can tell the environment variable is the only way to reach this.
