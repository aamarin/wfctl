## Findings

WARNING  wfctl/agents/skills/start-session/SKILL.md:L4 — `allowed-tools` does not
mean the same thing on a SKILL.md as it did on the command wrapper, and the diff
carries no evidence the moved key was exercised.
On a slash command the key is a **pre-approval** (these calls skip the prompt).
On an Agent Skill it is a **restriction** — the documented behaviour is that
tool access is narrowed to the listed set while the skill is active. The commit
message frames the move as preserving a pre-approval at no cost; under skill
semantics it also *narrows*, and it narrows the one workflow this change exists
to make reachable. Two facts make the risk concrete rather than theoretical:
(a) this is now the **only** `SKILL.md` in the bundle carrying the key — every
other occurrence is a command wrapper (`grep -rn allowed-tools wfctl/agents/`:
13 commands, 1 skill); and (b) the value is space-separated
(`Read Bash(wfctl start*) …`) while the documented form for both commands and
skills is comma-separated. A space-separated value that is parsed on commas
yields one unmatched entry — harmless on a command (you just get prompted),
potentially a hard denial on a skill.
→ Fix: install into a scratch repo (`uv run wfctl install-skills --agent claude`)
and actually invoke `Skill(start-session)`, confirming `wfctl start` /
`wfctl doctor` / `wfctl install-skills` run rather than being refused; if they
are refused, switch the value to comma-separated. `CLAUDE.md`'s definition of
done already requires this step verbatim for any change under `wfctl/agents/`
("not verified by the test suite alone: run `uv run wfctl install-skills` and
exercise the thing you changed"), and nothing in the commit records that it ran.

WARNING  wfctl/agents/skills/start-session/SKILL.md:L4 — the list does not cover
what the skill's own workflow runs.
Two gaps, both readable off the SKILL.md body:
  - Step 5's block opens with `BASE=$(git symbolic-ref --short
    refs/remotes/origin/HEAD 2>/dev/null || true)`. Run as one Bash call — which
    is how a single fenced block reads — the command string starts with `BASE=`
    and matches none of `Bash(git symbolic-ref*)`, `Bash(git log*)`,

  - Step 7 instructs `wfctl issue view <id>` to confirm a likely-done issue. Only

Both were already wrong on the wrapper, so the diff did not introduce them — but
it moved the key into a context where being wrong costs a denial instead of a
prompt, which is exactly when a stale list stops being invisible.
→ Fix: add `Bash(wfctl issue view*)`, and either split step 5 into three
separate commands or accept that the block will prompt (and say so).

WARNING  wfctl/cli.py:L1332-1335 / wfctl/agents/skills/start-session/SKILL.md:L4
— "it costs no other layer" is verified for the command layers only; the skill
layers were not considered.
The commit message argues: "`.claude/commands/` was the only place it ever ran
unstripped, `_copy_command_for_bob` strips it, and copilot gets no commands at
all." That covers `agents/commands`. It does not cover `agents/skills`, which is
where the key now lives. Tracing the copy loop (`wfctl/cli.py:L2237-2243`):
`_copy_command_for_bob` is reached only for `rel_dest.startswith(".bob/commands/")`;
everything else under `agents/skills` is a plain `shutil.copytree`. So
`allowed-tools` now ships **unstripped** into three trees that never carried it:
`.agents/skills/start-session/` (base layer, every agent), `.bob/skills/` (bob),
and `.github/skills/` (copilot — the comment at `wfctl/cli.py:L1106-1108`
explicitly says "a plain copy — no frontmatter transform"). `wfctl/cli.py:L1353-1359`
declares `allowed-tools` a member of `_CLAUDE_ONLY_FRONTMATTER_KEYS`, i.e. a key
with "no meaning in Bob Shell". The change therefore pushes a key the codebase
labels Claude-only into two non-Claude trees, on the strength of an argument that
only examined the command path. Most likely inert; it is unverified, and it
crosses a boundary the code states in a constant.
→ Fix: either confirm Bob Shell and Copilot ignore an unknown `allowed-tools` on
a SKILL.md and say so where the boundary is declared, or note the exposure in the
ADR consequences.

**Verdict: Request changes** (0 blockers, 4 warnings).

The change is the right shape and improves code health — the frozenset entry is
correct, the wrapper's key was moved rather than exempted, the new test binds
three separate failure modes, and the suite/lint/types are green. What holds it
is that its central claim — that the pre-approval survived the move intact — is

`allowed-tools` means something different on the file it moved to, and the list
it moved is already out of step with two of the skill's own steps. Run the skill,
fix the two missing entries, refresh the record; then this is an Approve.
