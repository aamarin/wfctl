# Tasks: check an open change

**Branch**: `302-check-an-open-change` | **Spec**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

## Format: `[ID] [P?] [Story] Description`

`[P]` marks a task that touches a file no incomplete task also touches.
`[US1]` and `[US2]` map to the user stories in `spec.md`. Every
implementation task names where it is verified.

## Path Conventions

Paths are relative to the repository root. `wfctl/agents/` is source;
`.agents/` is generated by `install-skills` and is never edited by hand
(`layer-model`). Every command runs through `uv run` — this repo has two wfctl
installations and only the one that installed last reports `doctor` clean.

**Field and key.** These tasks say *field* when talking about the sidebar a
person fills, which is what `opening-a-change` calls it, and *key* only when
talking about the JSON mapping a tracker returns. They are the same thing seen
from two sides; the two words are not interchangeable drift.

**Test homes.** `tests/test_tracker.py` is extended rather than duplicated — it
already covers `change list`/`view`, the verb table and its rejections. New files
are created only for the new module and the new command.

## Phase 3: User Story 1 - Find out what the change is missing (Priority: P1) 🎯 MVP

**Goal**: someone runs one command against an open change and is told which
fields the issue carries that the change does not.

**Independent Test**: with `change_check` absent entirely, run the check against
a change whose issue carries a label the change lacks; confirm the label is
reported, and that adding it makes the run go quiet.

### Verification for User Story 1

Unit tests over the pure comparison, one per row of the table in
`data-model.md`, with both payloads handed in directly so no test needs a
tracker. Then the live exercise in `quickstart.md`, both halves.

### Tests for User Story 1 ⚠️

- [ ] T007 [US1] Create `tests/test_change_check.py` covering inherited findings: a scalar set on the issue and unset on the change, a list on the issue not covered by the change's, and a change carrying extra list values that must not be findings
- [ ] T008 [US1] Extend `tests/test_change_check.py` with the satisfied cases: every expected key set, and a key set on the change that neither source expects, asserting the second prints nothing

### Implementation for User Story 1

- [ ] T010 [US1] Implement list comparison as a set difference and scalar comparison as empty-versus-set, choosing by the payload's shape rather than the key's name; verify with the extra-values case in T007

**Checkpoint**: US1 is independently shippable — the check reports inherited findings and goes quiet when they are satisfied, with no repository policy configured at all.

## Implementation Strategy

### MVP First (User Story 1 Only)

T001-T013 delivers a check that reports what the issue carries and the change
does not, with no repository configuration at all. That is already the failure
#301 demonstrated, and it ships without `change_check` existing.

### Incremental Delivery

US2 adds the repository's own requirements, every degrade path, and the step that
calls the check. Each phase leaves the suite green.

### Parallel Team Strategy

One worker. US1 and US2 share three files, so splitting them across two people
costs more in coordination than it saves. #306 is the parallel work, and it has
its own branch.
