BLOCKER  `wfctl/cli.py:L1586,L1605` — the two `could not read` lines interpolate
`detail` into a rich markup string without `escape()`. `detail` is the backend's
raw stderr. Two failures, both reproduced:

- stderr containing a closing-tag shape raises out of the command:
  `_answers(change=(1, "error: unexpected [/tag] in response"))` →
  `MarkupError("closing tag '[/tag]' at position 51 doesn't match any open tag")`,
  uncaught. Under `typer` that is a traceback, not a sentence.
- stderr containing a plain bracketed token is **silently eaten**:
  `"gh: [error] not found"` renders as `"gh:  not found"`, with color on or off.
  The reader is handed a truncated diagnostic and no sign that it was truncated.

This is the diff's own declared invariant. `tests/test_change_cli.py`'s module
docstring: *"Every one of them has to end in an exit code and a sentence, because
a check that raises has told the reader about the wrong file."*
`302-the-tracker-flattens-its-own-shapes.md` under **Consequences**: *"That must
surface as a finding naming the config, not as a traceback."* And
`test_a_payload_the_verb_never_flattened_names_the_config_not_a_traceback` pins
exactly that property for the sibling case one branch away.

`escape` is already imported at L1571 and already applied at L1608/L1611. This is
an oversight, not a decision.

→ Fix: `escape(detail)` at L1586, `escape(issue_detail)` at L1605. Add a test
feeding stderr containing `[/x]` and asserting `result.exception is None or
isinstance(result.exception, SystemExit)` — the same assertion the flatten test
already uses.

WARNING  `wfctl/cli.py:L1615-1622` — the `ℹ` line's *reason* is wrong in two
reachable states, and both are the exact conflation this feature exists to
prevent. The marker is right; the sentence after the dash is false.

`where` has two values chosen on `issue_fields is not None`, but three upstream

| Upstream state | Printed | True? |
|---|---|---|

Verbatim from the second row (branch `342-x`, config with `changes.fields` and no

```
ℹ 301: nothing to check — wfctl.json requires no fields, and there is no issue to inherit from
```

The second row is not hypothetical: `AGENTS.md`'s own new paragraph says

Then pin all four in `test_change_cli.py` — today only row three is asserted, and
`test_nothing_required_and_nothing_to_inherit_says_so_rather_than_passing`

WARNING  `wfctl/agents/trackers/github.json:L14,L24` — the shipped `fields` verbs
request `projectItems`. GitHub's GraphQL gates that field behind the
`read:project` scope, which a stock `gh auth login` does not grant
(default scopes: `gist, read:org, repo, workflow`). If gh errors rather than
returning null there, `wfctl change check` on the *default* config exits 1 with
an unactionable scope error — and `opening-a-change` Step 6 now tells the reader
`Exit 1 means this step is unfinished`.

I could not falsify this here: this machine's token carries `project`, and the
verb runs clean against a real PR —
`{"assignees":["aamarin"],"labels":["enhancement","P1"],"milestone":null,"projectItems":[],"reviewRequests":[]}`.
The design record's **Verified** section was written from the same privileged
token, so it does not settle the question either.

→ Fix: verify with a token lacking `read:project`. If it errors, drop
`projectItems` from the shipped defaults (nothing in the check needs it — it is
never required and only compared when the issue carries it) or document the scope
in `AGENTS.md` beside the `--tracker` paragraph.

Related, lower reach: `.reviewRequests[].login` yields `null` for a *team*
review request (teams key on `name`), which `_as_list` then drops. A repo putting
`reviewRequests` in `change_check` and requesting only a team review would get a
false `empty; required by wfctl.json`.

## What I checked and found sound

- **`_read_verb` extraction is behaviour-preserving on the notify path.**
  Token-by-token, the `section="verbs", verb="labels"` path produces the same
  three states and the same detail strings as `main`'s inline body — including
  the `"'labels' must be a list of strings"` wording and the empty-stdout →
  `set()` case (`out == ""` is falsy but not `None`, and the guard tests `is
  None`). `tests/test_notify_grant.py` exercises it through 30 tests covering
  declined verb, malformed template, non-mapping `verbs`, unreachable tracker and
  substring matching; all green. This was the change's highest-risk edit and it
  is the best-covered part of the diff.
- **`compare` is genuinely pure and exhaustively unit-tested.** The set-difference
  choice (not emptiness) is pinned by
  `test_a_label_the_change_earned_itself_is_not_a_finding`, and its docstring
  names the concrete failure — #301's filled sidebar that still lacked #280's
  label — which is the standard `AGENTS.md` sets for a docstring. The
  `unreported` source is the non-obvious half of the design and it carries its
  own test with the spelling mismatch spelled out. `_as_list`'s scalar/list
  unification is correct including `None`, `""` and partial-overlap lists.
- **No tracker-specific field name in wfctl.** Confirmed by inspection of
  `_change.py`, `_tracker.py` and `cli.py` — every key is data. The only field
  names in the diff are in `github.json`, `AGENTS.md` and the two records, all of
  which are outside the constraint.
- **The three markers carry three meanings, and the empty check never prints `✓`.**
  Pinned by `test_nothing_required_and_nothing_to_inherit_says_so_rather_than_passing`'s
  `assert "✓" not in result.output`, which is the sharp half of that test.
- **`check` cannot collide with a backend verb.** `ALLOWED_CHANGES` omits it and
  `test_check_is_never_a_backend_verb` pins the rejection; the honest docstring
  ("Nothing new enforces this") is right to say so rather than imply the diff
  added a guard.
- **`change list` / `view` still dispatch**, with argv asserted — the one test in
  the file that does check argv.
- **`load_required`'s degrade-to-silent behaviour** matches `_verify.load_config`
  and every malformed shape has a test, including the half-valid-discards-all
  rule with its reason.
- Both new architecture records are substantive: real rejected alternatives with
  the reason each loses, a **Verified** section with actual command output, and
  a **Consequences** section that names the failure mode the design introduces.
  The level-3 record's diagram earns its place — the two graphs differ by which
  side of the divider the unwrapping sits on, which is the decision.

## Summary

The design is right and the pure half is well-tested. Every finding is in the
composition layer — `_render_change_check` and the CLI tests that were supposed
to cover it. Three of the five WARNINGs are the same shape: a test that passes on
behaviour the code does not have.

net: −8 lines possible (`SOURCES` and its comment, −6; `_render_change_check`'s
three-line signature, −2). Lean otherwise.

**Verdict: Request changes** (1 blocker, 5 warnings)
