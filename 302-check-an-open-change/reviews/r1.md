BLOCKER  wfctl/cli.py:L1586,L1605 — backend `stderr` is interpolated into `console.print` with rich markup **on**, so the one message on the failure path is mangled or raises → print it the way `_tracker.dispatch` already does.

  Reproduced against the real command surface (stub `subprocess.run` returning
  exit 1 with the given stderr, `NO_COLOR=1`):

  | tracker stderr | what the user gets |
  |---|---|
  | `[/x] boom` | uncaught `MarkupError("closing tag '[/x]' at position 33 doesn't match any open tag")`, **no output at all** |
  | `[not found]` | `✗ could not read 301: ` — the entire reason deleted |
  | `[nope] boom` | `✗ could not read 301:  boom` |
  | `graphql: field [a] b` | `✗ could not read 301: graphql: field  b` |

  This is not a hypothetical class. `scaffold-tracker` invites hand-authored
  backends (`.agents/trackers/<name>.json` pointing at a shell script), and
  `[error] …` / `[warn] …` / `[not found]` prefixes are ordinary shell-script
  stderr. The repository has already decided this question once, in the sibling
  path: `wfctl/_tracker.py:L346` prints backend stderr as
  `console.print((result.stderr or "").rstrip(), style="red", markup=False)`.
  The new reader's producer documents "Never raises" (`_tracker.py:L388`), and
  `docs/architecture/design/302-the-tracker-flattens-its-own-shapes.md` says a
  bad payload "must surface as a finding naming the config, not as a traceback
  out of a comparison" — the consumer reintroduces exactly the traceback the
  producer was written to avoid.

  Exit code is 1 either way, so the *verdict* is never wrong; what is destroyed
  is the diagnostic, on the only path where the reader has nothing else to go
  on. Same treatment needed at L1577 (`err`) and L1584 (`change_id`, a raw CLI
  argument).

  Fix — escape at the boundary, keeping the markers coloured:

  ```python
  console.print(f"[red]✗[/red] could not read {escape(change_id)}: {escape(detail)}")
  ```

## What I checked and found sound

Recording these so the parent can see the passes were run rather than skimmed.

- **`_read_verb` extraction is behaviour-preserving for `read_issue_labels`.**
  The three-state contract survives: `out is None` is tested with `is`, so an
  empty stdout still yields `(set(), None)` and not a false decline; the
  `verbs`/`labels` shape guards, the `_MissingParam` path and the 15s bound are
  the same code, only parameterised. The notify grant at `_session.py:L246`
  reads `(labels, detail)` exactly as before. No regression on the path that
  gates outward-facing actions.
- **No tracker-specific field name in wfctl.** Grepped: `labels`, `assignees`,
  `milestone`, `projectItems` appear only in `wfctl/agents/trackers/github.json`,
  the skills, the records and test fixtures — never in `_change.py`, `_tracker.py`
  or `cli.py`. The stated invariant holds.
- **The `⚠` / `✓` / `ℹ` separation is real and load-bearing.** `compare` emits
  no row for a key neither source expects, so `✓` cannot be printed by a check
  that had no opinion, and the empty-`rows` branch prints `ℹ` and never `✓`.
  Pinned by `test_a_key_neither_source_expects_is_absent_from_the_result` and
  `test_nothing_required_and_nothing_to_inherit_says_so_rather_than_passing`.
  This is the requirement the feature exists for and it is correctly built.
- **Set difference, not emptiness.** `test_a_label_the_change_earned_itself_is_not_a_finding`
  is the right regression test for the failure the issue names, and its docstring
  names the failure rather than restating the assertion — matching the convention
  AGENTS.md sets.
- **Half-valid `change_check` yields no keys**, mirroring `_verify.load_config`,
  and a malformed `wfctl.json` degrades to silence rather than duplicating
  `doctor`. Both decisions are argued in the code and pinned by tests.
- **Security.** `argv` list, no `shell=True`, `cwd=repo_root`, 15s timeout,
  errors caught as `(OSError, TimeoutExpired)`. Payload is treated as untrusted
  (`_is_flat` rejects anything not scalar-or-flat-array before comparison). The
  one residual — a `change_id` beginning with `-` becoming a `gh` flag — is the
  pre-existing `_substitute` contract that `wfctl change view` already has, not
  introduced here.
- **Live run.** `uv run wfctl change check 301` against the real PR returned
  `⚠ projectItems  empty; issue has wfctl`, exit 1, matching
  `gh issue view 302 --json projectItems` → `["wfctl"]` and
  `gh pr view 301` → `[]`. The command does what it claims end to end.
- **`check` cannot be captured by a backend** — `ALLOWED_CHANGES` rejects it, and
  `test_check_is_never_a_backend_verb` pins that; `test_list_and_view_still_dispatch_to_the_backend`
  proves the new branch did not swallow its neighbours. Both are the right tests
  to have written.
