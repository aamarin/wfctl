## WARNING 1 — the shipped default nags forever on `projectItems`

`verbs.fields` reads `projectItems` from the issue, and `changes.fields` reads it
from the change. In this repository issues are boarded and PRs are not:

```
issue #302  projectItems: ["wfctl"]
PR   #301   projectItems: []
PR   #295   projectItems: []      (merged)
PR   #289   projectItems: []      (merged)
```

Feeding the two real payloads through `compare([], issue, pr)` produces exactly
one finding, on every PR this repository will ever open:

```
⚠ projectItems  empty; issue has wfctl
```

That is unactionable unless the author starts adding every PR to the issue
board, and `the-repo-names-the-fields-a-change-must-carry` names this precise
outcome as the thing that kills the check: *"a noisy check is learned around and
then ignored, which loses the prose and the check together."* The level-3
record's own Verification section asks for a run "with it filled — the second
half is what shows the check can pass"; with the shipped default in this repo
there is no filled state short of boarding the PR.

GitHub's common shape is issues-on-a-board, PRs-not, so this is the default
behavior for consumers too, not a local quirk. Fix: remove `projectItems` from
the *issue-side* `fields` verb. It stays available on the change side for a repo
that genuinely wants it, via `change_check`.

## WARNING 2 — the new step is a silent no-op in every existing install

`cli.py:2746-2752` sets `tracker_skip_existing = True` on a bare
`install-skills`, and the copy loop at `cli.py:2921-2924` then skips any tracker
file already present. AGENTS.md's new section states this correctly. The
consequence for the shipped skill is not stated anywhere a consumer sees:

- `/start-session` runs the bare form, so it will never deliver the new `fields`
  verbs.
- Every repo with an existing `.agents/trackers/github.json` therefore runs
  `wfctl change check <pr>` and gets
  `ℹ No `fields` verb for changes — skipping check of <pr>`, exit 0.
- `opening-a-change` L307 says *"Exit 1 means this step is unfinished"*, so the
  reader correctly infers exit 0 means finished. The check did nothing.

The `--tracker <name>` remedy lives only in wfctl's own `AGENTS.md`, which is not
installed into consumer repos. One line in `opening-a-change` beside the `ℹ`
sentence closes it: *if it reports no `fields` verb, the backend predates it —
`wfctl install-skills --tracker <name>`.*

## WARNING 4 — the `ℹ` sentence collapses "declined" into "absent"

Reproduced against a scratch repo with `changes.fields` declared and
`verbs.fields` omitted, on branch issue `302`:

```
ℹ 301: nothing to check — wfctl.json requires no fields, and there is no issue
  to inherit from
exit: 0
```

There *is* an issue; the backend has no `fields` verb for issues. `cli.py:L1615-1619`
derives `where` from `issue_fields is not None`, which is None for both "no
branch key" and "backend declined". `_read_verb`'s own docstring insists these
two are "not the same fact", and `read_fields` keeps them apart — the CLI then
throws the distinction away in the one sentence a reader acts on. Track whether
the issue read was attempted and say `the backend has no 'fields' verb for
issues` in that case.

This also makes the `scaffold-tracker` claim "Declare `fields` on both sections
or on neither — a check with only one side has nothing to compare" wrong:
`changes.fields` plus a `change_check` list is a fully working configuration that
the code supports and `test_the_issue_being_unreadable_leaves_required_keys_still_checked`
pins.

## WARNING 5 — team reviewers flatten to nothing

`"reviewRequests":[.reviewRequests[].login]`. From `gh`'s own exporter
(`cli/cli:api/export_pr.go` L206-222, read via the API):

```go
case "User": {"__typename", "login"}
case "Team": {"__typename", "name", "slug"}      // no login
```

So a requested team exports with no `login`, `.login` yields `null`, `_is_flat`
accepts `[null]`, and `_as_list` drops the `None`. Confirmed:

```
compare(["reviewRequests"], {}, {"reviewRequests": [None]})
→ ⚠ reviewRequests  empty; required by wfctl.json
```

A repo that requires `reviewRequests` and requests a team is told the field is
empty while a review is genuinely pending — a false finding of the same class the
design set out to avoid. `[.reviewRequests[] | .login // .slug]` covers both.
(I could not find a public PR with a *visible* team request to demonstrate this
end-to-end; the evidence is gh's export source plus the observed User shape.)

## WARNING 6 — unescaped interpolation into `console.print`

`escape()` is imported and applied to `_change.describe(row)`, and to nothing
else on the same lines. Reproduced:

```
$ wfctl change check '[/red]'
rich.errors.MarkupError: closing tag '[/red]' at position 51 doesn't match any open tag
```

Same exposure for `detail` (subprocess stderr, L1586/L1605) and `row.key`
(backend payload, L1608/L1611). A `[bold]`-shaped substring is silently swallowed
rather than printed. The `TimeoutExpired` string is safe — I checked, `['gh', …]`
is not valid markup — which is why
`test_a_timed_out_read_exits_non_zero_without_a_traceback` passes and does not
cover this. The level-3 record says a bad payload "must surface as a finding
naming the config, not as a traceback"; the same standard applies to a bad
stderr. One-line fix: escape all four.

## Passes with nothing to report

**Correctness.** `compare`'s state space is fully covered by
`tests/test_change_check.py`, including the set-difference case that would have
green-lit #301. The `required` × `present` × `inherited` matrix works out
correctly on every combination I traced. Exit codes are right: findings → 1,
satisfied-only → 0, `ℹ` → 0, failed issue read → 1 *after* printing the
checkable half. `test_list_and_view_still_dispatch_to_the_backend` is the right
regression test for the intercept — the branch that makes `check` wfctl's is
exactly the kind that captures its neighbours.

**Security.** Argv tokens throughout, no shell string; `subprocess.run` bounded
at 15s on both reading paths; no secrets; the payload is treated as data. The
markup issue above is a robustness bug, not an injection.

**Architecture.** `_change` sits in `domain`, imports only `_verify.CONFIG_PATH`,
and introduces no cycle. `_read_verb` is a genuine extraction — `read_issue_labels`
loses nothing (empty stdout still yields an empty set, as before) and the
three-state contract is preserved verbatim. Splitting `fields` from `view`
rather than reshaping `view` is right for the reason the record gives.

**Performance.** Two subprocess calls, both bounded, both skipped when the
backend declines. Nothing to say.

**Over-engineering.** Dense but earning it, one exception (`SOURCES`). `Field`
carries four payload attributes and `describe` reads all four. The `_as_list`
one-shape trick is a real simplification, not speculation.

**Tests.** Names are sentences, docstrings name the failure each test exists to
catch, `NO_COLOR` handled by `conftest.py`. The one gap worth naming: no test
covers the `ℹ` wording for a declined *issue*-side read (WARNING 4) — the state
exists and nothing pins its sentence.
