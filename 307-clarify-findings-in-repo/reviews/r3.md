### WARNING — a scan file is counted as an architecture record by two callers the records did not audit

`docs/architecture/*.md` is not the only thing that reads the arch root. Two
callers read the **whole subtree**, recursively, and neither is mentioned in
`the-scan-is-attested-where-the-reviewer-reads.md § Consequences` or in the
level-3 record's `Verified` list — both of which enumerate `arch check`
(`cli.py:1233`), `load_records` (`_arch.py:146`) and `design_block`
(`_predicates.py:520`) and stop there.

1. **`records_on_this_branch`** (`wfctl/_paths.py:357`, called at `cli.py:443`) —
   `git status --porcelain -uall -- <arch>` plus `git diff --name-only trunk...HEAD`,
   then `{Path(p).stem for p in found if p.endswith(".md")}`. No depth limit, no
   exclude. This is what `wfctl status` prints under the auto-approve notice, whose
   own comment says its job is that "the records are already in the branch diff;
   what is missing is anyone knowing to look."

   Rendered, on this branch, right now:

   ```
   auto-approve — design gates answered into the record, approval moves to the PR
     record: 307-analyze
     record: 307-clarify
     record: 307-the-coverage-map-is-the-evidence
     record: the-scan-is-attested-where-the-reviewer-reads
   ```

   Two of those four are scan files. A scan file is explicitly *not* a decision —
   `AGENTS.md`'s new paragraph says "nothing here joins the set of decisions in
   force", which is true of `wfctl arch context` and false of the line above.

2. **`_observe`** (`cli.py:639`) — `boundary=_BOUNDARY[touched_on_this_branch(repo_root,
   arch_root(repo_root))]`, called with **no `exclude`**. `_BOUNDARY`'s own comment:
   *"calling a missing answer 'answered' is the kind of claim #70 is about."*

   Isolated repro — a branch whose only arch-root content is a scan file:

   ```
   records_on_this_branch: ['999-clarify']
   boundary as _observe asks: True      # → `wfctl end` writes "boundary answered"
   design_block-style:        True      # gated off by the spec.md guard — safe
   ```

   So `/speckit.clarify` alone now flips a branch from `boundary unanswered` to
   `boundary answered` in the session handoff, with no boundary question answered
   and no record written.

The `design_block` half of the record's argument holds — I confirmed
`_predicates.py:520` returns `None` once `spec.md` exists, and both steps run
after `specify`, so the design gate genuinely cannot be spoofed. The two callers
above have no such guard.

This partly pre-exists for `<arch>/design/`, but a level-3 record at least means
*the design step ran*; a scan file means nothing about the boundary happened at
all, which is the first case where the word is simply wrong.

**Fix** — one of:
- (preferred) filter `scans/` out of `records_on_this_branch`, and pass
  `exclude=arch / "scans"` at `cli.py:639`. Regression homes already exist:
  `tests/test_end_reports_observations.py:49` asserts the literal string
  `"boundary unanswered"`, and `tests/test_auto_approve_mode.py` covers the
  `record:` listing.
- if "adds no Python" is a hard constraint for this PR: say so in the level-2
  record's `Consequences` and file the follow-up. What is not acceptable is
  `AGENTS.md` asserting nothing joins the decision set while `wfctl status` prints

### WARNING — `git commit` with no pathspec sweeps the index

`speckit.clarify.md:L108-111` and `speckit.analyze.md:L108-111`:

```bash
git add <root>/scans/<issue>-clarify.md
git commit -m "docs(scans): clarification scan for #<issue>"
```

This repo's own `software-design-decisions/SKILL.md:78` writes the same three-step
dance as `git commit -m "<subject>" -- <path to the record>` — pathspec-scoped,
for exactly this reason. Both steps run mid-pipeline in a worktree where the
author may have staged work; a bare `git commit` takes the whole index under a
`docs(scans):` subject.

Latent rather than proven here (the two dedicated scan commits are clean), but the
branch's own history is consistent with it: the re-scan session appended to
`307-clarify.md` — the file itself says it was "Run against the installed wrapper" —
landed inside `81538dc feat(speckit): …` as 51 lines, not as its own
`docs(scans):` commit. Either the instruction's commit step did not run, or the
commit that ran was not the one specified. Both are worth closing.

**Fix**: `git commit -m "docs(scans): … for #<issue>" -- <root>/scans/<issue>-<step>.md`
in both wrappers. This also narrows the practical reach of the `Bash(git commit*)`
grant (see NIT below).

### NIT — `Write` is granted; the load-bearing rule is "append"

`allowed-tools` grants `Read` and `Write`, not `Edit`. The instruction's single
most emphasised rule — *"A re-run never discards an earlier session"*, backed by a
dedicated test — is only reachable as read-whole-file / rewrite-whole-file. That is
the exact operation the rule warns against, performed correctly by convention.
Granting `Edit` makes the append structurally an append.
