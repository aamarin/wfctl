## Findings

### BLOCKER  `wfctl/agents/commands/*.md` (destination choice) — `wfctl status` now reports scan files as architecture records

The change's stated premise is that it adds no Python behaviour. That is true of the
source and false of the observable behaviour, because a fourth subdirectory under the
arch root is not inert. `records_on_this_branch` (`wfctl/_paths.py:357-396`) passes the
**arch root itself** as a git pathspec — recursive, by construction — and takes
`Path(p).stem` of every `.md` it finds. Scan files match.

Reproduced live in this worktree, no arguments:

```
$ uv run wfctl status
#307  307-clarify-findings-in-repo
...
auto-approve — design gates answered into the record, approval moves to the PR
  record: 307-analyze
  record: 307-clarify
  record: 307-the-coverage-map-is-the-evidence
  record: the-scan-is-attested-where-the-reviewer-reads
```

Two of those four are scan files. The listing's purpose is stated in its own comment at
`wfctl/cli.py:436-443`: under `auto_approve` "a run nobody watched has to make what it
decided hard to scroll past … what is missing is anyone knowing to look." A scan file
decided nothing. On a branch that runs `/speckit.clarify` and writes no architecture
record — the common case, since most changes draw no boundary — this prints
`record: <issue>-clarify` and tells an unattended reader a decision was recorded when
none was. That is wrong output shipped to every repo that installs this.

Second reader, same root cause: `_observe` at `wfctl/cli.py:639` computes
`boundary=_BOUNDARY[touched_on_this_branch(repo_root, arch_root(repo_root))]` with **no**
`exclude`, unlike `design_block`, which passes `exclude=arch / "design"`
(`wfctl/_predicates.py:530`). A committed scan file therefore flips the session handoff's
`boundary` from `unanswered` to `answered`. Verified:

```
touched (no exclude):        True
touched (exclude design):    True     # scans/ is not excluded either
```

`design/` already loosens `_observe` today, so this widens a pre-existing looseness
rather than creating it — but `scans/` is the entry with no argument for being counted at
all.

The level-2 record's `## Consequences` enumerates the readers of the arch root and names
exactly two — `arch check` (unchanged, correct) and `load_records` (globs one level,
correct, and I confirmed `arch context` is unaffected). It misses these two. So does the
new `AGENTS.md` paragraph, which tells the next reader that "subdirectories of the arch
root are invisible to `wfctl arch context`" and leaves the impression that subdirectories
are inert generally.

**Fix** — one of:
- filter in `records_on_this_branch`: drop paths whose parent is `scans` (`design/` and
  `declarations/` are listed on purpose, so a blanket "top level only" is the wrong
  narrowing), and pass `exclude=arch / "scans"` at `cli.py:639`; or
- accept it in writing: add the two readers to the record's `## Consequences` and say why
  a scan file listed as a record is tolerable. The severity here is the *undocumented*
  wrongness — an argued acceptance clears it.

Not a gate risk: `design_block` returns `None` once `spec.md` exists
(`_predicates.py:519`), and both steps run after `specify`, so a scan file can never
satisfy the design gate. The record already reasons about this and is right.

### WARNING  `wfctl/agents/commands/speckit.analyze.md:16-116` — the wrapper instructs writes against a skill that says STRICTLY READ-ONLY, and never names the override

The wrapper's body tells the agent to read `speckit-analyze/SKILL.md`, which says twice:

- `:63` — "**STRICTLY READ-ONLY**: Do **not** modify any files."
- `:280` — "**NEVER modify files** (this is read-only analysis)"

Then the new section tells the same turn to `Write` a file, `git add` it and `git commit`
it. The frontmatter `description:` on the same file still reads "Perform a
**non-destructive** cross-artifact consistency and quality analysis". Nothing in the new
prose acknowledges the constraint it overrides.

This repo already solved this exact problem, in the file the wrapper cites as its
precedent. `speckit.brainstorm.md` names each upstream pause it overrides, in a table,
and states "they still read as unconditional and this file is the layer above them."
The analyze wrapper takes the layering pattern and drops the half that makes it legible —
so an agent following the wrapper meets a flat contradiction with the file it was told to
read one paragraph earlier, and which way it resolves is not determined.

**Fix**: one sentence in the new section, e.g. "The skill's *STRICTLY READ-ONLY* rule is
about the artifacts under analysis; this file is new, outside them, and is the one write
this step makes." Optionally reword the `description:` so "non-destructive" is not
contradicted by the same file's frontmatter grant of `Write`/`git commit`.

### WARNING  both wrappers — a clarification that was asked, answered and then dropped

`spec.md:18` records the answer: *"FR-011 keys a session by date — do two runs on one day
collide? → A: the second extends that day's section, as `/speckit.clarify` already does in

1. **FR-011 was never amended.** `spec.md:145-149` still says only "one section per scan
   session, appended, in the `### Session YYYY-MM-DD` shape" — no same-day rule.
2. **Neither wrapper states it.** `grep -n "same day\|same-day\|extends that day"` over
   both wrappers returns nothing. The next run on a day that already has a section has no
   rule to follow.
3. **The exemplar does the opposite of the recorded answer.**
   `docs/architecture/scans/307-clarify.md` opens a *second* `## Session 2026-09-09
   (re-scan, after implementation)` heading — a new section for the same day, which is the
   option the clarification explicitly decided against. That file is what the next agent
   will imitate.
4. **Heading level drifts too.** FR-011 and `speckit.clarify.md:53` say `### Session
   YYYY-MM-DD`; both templates (`speckit.clarify.md:63`, `speckit.analyze.md:57`) and both
   shipped scan files use `## Session`.

A clarification answered and lost between the spec and the deliverable is the failure
class this feature exists to expose, landing inside the feature itself.

**Fix**: amend FR-011 with the same-day rule, put one line in both wrappers ("a second run

one heading level, and reconcile `307-clarify.md`'s second session with whichever answer

Both wrappers gained the grants the new prose needs — `Write`, `Bash(wfctl arch-root*)`,
`Bash(wfctl arch check*)`, `Bash(git add*)`, `Bash(git commit*)`. No test holds them. Every

Today a wrapper can lose `Bash(git commit*)` or `Write` and the entire new suite stays
green while the feature is dead.

**Fix**: parametrize the existing brainstorm test's shape over
`("clarify", "analyze")` for `Write`, `wfctl arch-root`, `wfctl arch check`, `git add`,
`git commit`.

### WARNING  both wrappers, `allowed-tools` — `Edit` is not granted, but append is the required operation

The instruction that both wrappers now make load-bearing is *append a session, never
replace*, and it is the one behaviour the suite guards in prose
(`test_each_review_wrapper_appends_a_session_rather_than_replacing`). The grant is `Read`
and `Write` — no `Edit`, no `Bash(cat >>*)`, no `Bash(tee -a*)`.

`Write` overwrites whole files. So the only sanctioned route to "append" is: read the
existing scan file, reconstruct it in full, write it back. That is exactly the mechanism
most likely to silently drop an earlier session — the failure the rule exists to prevent —
and it gets worse each session, since analyze's file grows with every re-run. An agent
reaching for `Edit` (the correct tool) hits the ceiling instead.

**Fix**: add `Edit` to both wrappers' `allowed-tools`.
