### Findings

WARNING  .github/scripts/check_release_note.py:L96, L185-190 — The check reads only committed state (`git diff base HEAD`), but `wfctl verify` runs on dirty trees by design: `_verify.py` records `dirty` and only warns. Pytest, ruff, and mypy judge the working tree, so this is the one verify command that doesn't. In practice an agent runs `towncrier create 571.change.md`, then `wfctl verify`, and is told "no release note for #571, add changes/571.<category>.md" while that file sits on disk. The likely next move is a second `towncrier create`, which writes `571.change.1.md` because the name is taken (towncrier `create.py:211`). The spec's own Independent Test says adding the file and re-running records a pass. → When no committed note matches, look for an uncommitted one (`git status --porcelain -- changes/`) and say "changes/571.change.md isn't committed yet, commit it and check again". Keep judging committed state only, so CI and verify still agree.

WARNING  AGENTS.md:L51-52 — "All three commands above green. That is the whole bar for a code change, and CI runs exactly these" is now false. `wfctl verify` runs a fourth command, and CI requires a fifth job, `release-note`. An agent reads the definition of done before it reads Releasing, so it learns the old bar first. → Add the release note to the definition of done, for example "and a release note committed under `changes/`; see Releasing", and drop "exactly these".

WARNING  .github/scripts/release.py:L103-109, L164-171, L349-350 — Any file under `changes/` that the script doesn't recognise is deleted without ever reaching the draft. A note whose category isn't in the towncrier table is counted as releasable and copied into the draft directory. Towncrier then skips it silently, because `build` is strict only when `ignore` is configured (`build.py:215`). A file that doesn't match `NOTE_NAME` is never read at all. Either way, `git rm -r changes` deletes it. It can happen today when a category is renamed in `pyproject.toml` while notes using the old name are still waiting. That pull request's check passes, because it only inspects added files, and the next release drops those notes with nothing on screen. That is the failure the feature exists to stop, though it is rare. → Before proposing, refuse with the file names when any tracked file under `changes/` either fails `NOTE_NAME` or names a category that isn't in the table. That's about 4 lines.

NIT      .github/scripts/check_release_note.py:L149 — `PLACEHOLDER in text` also rejects a written note that quotes the phrase, such as a note describing this very check. `towncrier create` without `--content` writes exactly the placeholder. → Use `text.strip() == PLACEHOLDER`.

NIT      .github/scripts/release.py:L356, L328-333 — The exit codes of `git add`, and of the rollback's own `git restore` and `git switch`, are never checked. "Stopped, nothing was changed." prints even when the restore failed, which is the exact case the docstring says would carry the bump onto `main`. → Check the restore's exit code, and when it fails, print what is left in the tree instead of the reassurance.

NIT      tests/test_release_script.py — Nothing exercises a rollback after `git rm` has run, with `removed_notes` set to True, for example a failing commit. That branch carries the contract's most specific claim, about the `changes/` pathspec. User Story 2 scenario 5 also says the `+bump-ruff` note "appears in the draft", and the test checks only that the merge isn't listed. → Add a commit-failure test, for example a `commit-msg` hook that exits 1, and assert `"Ruff is updated." in out`.

NIT      tests/conftest.py:L95-96 — The helper slices `pyproject.toml` between `[tool.towncrier]` and `[tool.ruff.lint]`, so it depends on the order of those two tables. Any table later placed between them gets copied too, and reordering them raises `ValueError`. It fails loudly, so it isn't urgent. → Slice from `[tool.towncrier]` to the next line that starts with `[` and isn't `[[tool.towncrier.type]]`.

NIT      .github/workflows/ci.yml (tag job, `rel=$(git log ... --grep ...)`) — `--grep` searches the whole message, so a later non-merge commit that quotes "chore(release): cut X.Y.Z" in its body is picked first and fails the subject check. The release then waits until someone fixes it by hand. It only matters while the tag or the release is missing. → Use `git log --no-merges --format='%H %s' HEAD | awk -v s="chore(release): cut $v" '$0 ~ " "s"$" {print $1; exit}'`, or accept the current behaviour, since it fails closed.
