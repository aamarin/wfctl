## Review: 7369213..HEAD (571-release-automation), reviewer r3

The change does what spec.md asks of it, and I found no defect that has to be fixed before merge. The release note check, the release script, the tag job, and the ruleset each match their requirements (FR-001 to FR-020), with one gap in FR-018 that the plan narrowed on purpose. The findings below are two warnings about robustness and a handful of nits.

### Passes run

1. Correctness. I read both scripts in full, along with the tag job, the ruleset, the conftest helper, and the drift-test exemption. I traced each one against the spec's requirements and edge cases. I checked the check script in the pull request context: `GITHUB_HEAD_REF` on the detached merge ref, `merge-base` against `origin/main` once `fetch-depth: 0` has fetched it, and the release branch version comparison. In the release script I traced the precondition order, version parsing, the `[project]`-scoped `set_version`, and the roll back after each failing step. I confirmed against the locked towncrier 26.9.0 source that `towncrier create` names a second note `571.change.1.md` and writes "Add your info here", and that both regexes accept that name. In the tag job I checked the `--no-merges` lookup, `bash -e` behaviour without `pipefail` in `at=$(git show | python3)`, and the retry path when the tag exists but the release does not. I also confirmed that v0.23.0 is tagged and released, so the first push to `main` after this merges exits at "already released" rather than failing the lookup for a commit that predates this flow. The 60 release tests pass, as do the 43 install-config and shape tests. `ruff check .` and `mypy` are clean, and mypy is also clean when pointed at both scripts.
2. Security. `GITHUB_HEAD_REF` is attacker-controlled on a fork pull request, and it is read in Python, never interpolated into a `run:` block. `$v` is quoted wherever the tag job uses it, and the release body reaches `gh` through a file. The `release-note` job runs on `pull_request`, not `pull_request_target`. The ruleset has an empty bypass list, as FR-020 requires. `edit()` runs `GIT_EDITOR` through `sh -c`, which is the same trust git itself gives that value. I found nothing.
3. Architecture. The two scripts follow the existing `.github/scripts/` pattern. towncrier is a dev-only extra, so runtime dependencies are unchanged (SC-005). I looked up the dependency: MIT licensed, 26.9.0 released 2026-09-04, and roughly one release a year (24.8.0, 25.8.0, 26.9.0). PyPI lists no advisories for it. It adds click, jinja2 3.1.6, and markupsafe to the lock. I did not measure install size, though all four are small pure-Python packages. Nothing in the existing stack drafts release notes. One finding: the note-name rule and the settings reading are duplicated across the two scripts (W1).
4. Readability and simplification. The functions are short and named for what they hold. `cut_release` with its `roll_back` closure runs about 80 lines but reads in order. The comments explain why. One comment states a wrong reason (N2).
5. Performance. `merges_since` runs one `git diff` per merge since the last tag, which means tens of subprocesses per release. `fetch-depth: 0` in the `release-note` job adds a few seconds on a repository this size. Neither matters.
6. Over-engineering. Three small items, listed at the end.

### Findings

WARNING  .github/scripts/release.py:L37, L103-109, L349-352 — The release script keeps its own copy of the check's `NOTE_NAME` (check_release_note.py:L26), and `notes_by_category` silently skips any tracked file under `changes/` that its copy does not match. `git rm -r changes` then deletes that file anyway. The two regexes agree today. If the check is later widened, for example to accept a new towncrier name form, and only the check is edited, a note it accepted will disappear in the release commit without ever reaching the draft. → Import `NOTE_NAME` and `towncrier_settings` from `check_release_note` (the script's own directory is on `sys.path` when it runs as `python .github/scripts/release.py`). Then have `main` stop with an `Abort` naming any tracked path under `changes/` that does not parse, instead of deleting it.

WARNING  .github/workflows/ci.yml:L198-253 — The tag job's new logic has no automated test. That covers the `--no-merges` subject lookup, the subject and version checks, the empty-body refusal, and the retry when the tag exists but the release does not. The spec chose to verify this by reading it in review, and I traced it and found it correct. But the first real release is its first run. A slip there leaves a bumped version on `main` with no tag, which is the state #55 exists to prevent, until a follow-up pull request merges. → Move the step body into `.github/scripts/tag_release.sh` (or a Python script, like its siblings) and test it the way `test_release_script.py` tests the release script. That means a scratch repository holding a merge commit whose body quotes the release subject, plus a stub `gh` on `PATH`.

NIT  .github/workflows/ci.yml:L215 — If `gh release view` fails for a reason other than "not found", such as a transient API or auth error, `released` stays false on an ordinary push to `main`. The lookup then fails with "no commit with the subject chore(release): cut 0.23.0", which points at the wrong cause. → Run the lookup only when `HEAD`'s version differs from the latest tag's version, or test `gh`'s exit status and stderr for "release not found" before treating the release as missing.

NIT  pyproject.toml:L26-29 — The comment says a minor pin "would expire within a month". towncrier releases about once a year, so `>=26.9,<26.10` would admit 26.9.x patches and stop at the next yearly release, which is what `<27` does in practice. → Say that towncrier releases about once a year, so `<27` admits that year's patch releases and stops at the next release.

NIT  .github/pull_request_template.md:L73 — FR-018 says this repository's template "MUST describe the new process". The plan narrowed that to removing "Type of Change", and the template now never mentions release notes. An author learns about them only when the check fails. → Add one line to the template, for example under Issue Links: "Commit a release note under `changes/` (see AGENTS.md, Releasing)." Alternatively, record in the spec that FR-018's template clause is met by the removal alone.

NIT  AGENTS.md:L311 — The spec's edge case about a change that merges while the release pull request is open is not in AGENTS.md. In that case the change's code ships in this release while its note waits for the next one, and the fix is to merge soon, or close the pull request and run the script again. The spec lives outside the tree, so a later reader of Releasing will not see it. → Add one sentence after "Merge that pull request as a merge commit once its checks pass."

NIT  .github/scripts/check_release_note.py:L96, release.py:L105 — `git diff --name-only` and `git ls-files` quote paths that contain non-ASCII characters (`core.quotePath`). A note such as `+café.fix.md` therefore fails the check as a badly named file, even though towncrier accepts it. → Pass `-z` and split on `\0`, or run git with `-c core.quotePath=false`.

NIT  pyproject.toml:L106 — `[tool.mypy] files = ["wfctl"]` leaves the two release scripts out of CI type checking, although they are the most consequential code in this diff and both are clean today. → Add `".github/scripts"` to `files`. This predates the change for the other two scripts there.

### Over-engineering

release.py:L174-179: delete: the `DRAFT_MARKER` split "in case a later version moves it onto stdout". towncrier is pinned `<27`, and the draft tests would catch a move at the next `uv lock --upgrade`. Nothing replaces it.
release.py:L35: shrink: `LABELS` maps `addition` and `fix` to themselves, and the fix branch of `propose` never reads it. Use `LABELS = {"change": "behaviour change"}`, since `LABELS.get(c, c)` already falls back.
release.py:L140: shrink: `{c: len(notes.get(c, [])) for c in notes if c != "none"}` becomes `{c: len(paths) for c, paths in notes.items() if c != "none"}`.
release.py, check_release_note.py: yagni (duplication): `git()`, the towncrier table read, and the version parsing exist twice. Sharing them through W1's import removes about 10 lines.
