## Review: `git diff 7369213..HEAD` on 571-release-automation (r1)

Sixteen files: two new scripts under `.github/scripts/`, the ruleset, the CI
jobs, AGENTS.md, the pull request template, `pyproject.toml` and `uv.lock`,
`wfctl.json`, the release note, and the tests. I read it against spec.md
(FR-001 to FR-020, the edge cases, and the validation strategy), CLAUDE.md, and
the code of the pinned towncrier 26.9.0 in `.venv`.

`uv run pytest tests/test_release_note_check.py tests/test_release_script.py tests/test_ruleset.py tests/test_install_config.py -q`

### Passes that ran

1. **Correctness.** I traced both scripts line by line, and the tag job's shell.
   Against towncrier's source I confirmed four things: `create` writes "Add your
   info here" as its placeholder, a duplicate name becomes `571.change.1.md`
   (which `NOTE_NAME` accepts), a `+name` note renders as an orphan with no
   issue link, and `build --draft` prints its marker on stderr. I checked that
   the tag job's first run after this merges is safe, because v0.23.0 is tagged
   and its `chore(release): cut 0.23.0` commit exists. I also checked that
   `--no-merges` is needed: `--fill` makes the PR title equal the commit
   subject, and the merge commit's body carries that title. I reproduced
   finding 1 in a scratch repository. Findings 1, 2, 4, 5, 6, 7, 8 and 9.
2. **Security.** The `release-note` job uses `pull_request`, not
   `pull_request_target`, and interpolates no `${{ }}` into `run:`. The branch
   name reaches Python only through the environment. In the tag job, `$v` is
   quoted everywhere and comes from `main`, which the ruleset protects. The
   editor runs through `sh -c` exactly as git runs it, from the user's own
   config. The release-branch exemption lets a branch named `release/vX.Y.Z`
   skip the note when it raises the version, which the spec accepts on purpose.
   The one gap is finding 4, a fork whose head branch is named `main`.
3. **Architecture.** The new dependency is towncrier 26.9.0, uploaded on
   2026-09-04, plus click 8.5.0, jinja2 3.1.6 and markupsafe 3.0.4. All four are
   MIT or BSD-3. jinja2 3.1.6 is the release that fixed the 2024 - 2025 sandbox
   CVEs. All four sit behind the `dev` extra, so SC-005 holds. I didn't look up
   current advisories on a live database. The stdlib-only check script fits the
   runner-Python CI job. The main structural issue is finding 2: the note-name
   grammar has two copies. Importing helpers from `tests/conftest.py` matches
   the 20+ existing test files that already do it.
4. **Readability & simplification.** The comments explain why, in the repo's
   house style. Two functions are long but read top to bottom: `cut_release` is
   about 80 lines including its nested rollback, and `main` in the check is
   about 50. Findings 3 and 10.
5. **Performance.** `merges_since` makes one `git diff` per merged pull request,
   about 20 per release. The check makes one `git diff` plus one `git show`
   per added note. The tag job's `git log --grep` walks the whole history once
   per push to `main`, in milliseconds. Nothing here is worth changing.
6. **Over-engineering.** See the lines before the metric.

### Findings

```
WARNING  AGENTS.md:L313, .github/scripts/release.py:L379 — the documented way to
         change the release text strips its section headings. `git commit --amend`
         opens the editor, so git applies its default `strip` cleanup and drops
         every line starting with `#`. Every `## Behaviour changes` / `## Fixes`
         heading goes with it. I reproduced it: a body of "## Behaviour changes\n\n-
         Releases are scripted. (#1)" comes back as "- Releases are scripted. (#1)".
         The tag job only checks that the body isn't blank, so the release is
         published without its headings and nothing reports it. `edit()` already
         works around this same cleanup for the first draft. If an agent does the
         amend, its attribution trailers also land in `%b`, so they get published
         on the release page.
         → Say `git commit --amend --cleanup=verbatim` in both places.

WARNING  .github/scripts/release.py:L37, L350 — the note-name grammar exists
         twice, here and in check_release_note.py:L26, and the release script
         deletes whatever its own copy doesn't recognise. `notes_by_category`
         keeps only names its regex matches, and it never checks a category
         against the towncrier table. Then `git rm -r changes` deletes every file
         in the folder. So if the two regexes drift, or a stray file or unknown
         category reaches `main` before the ruleset is applied, that note is
         deleted in the release commit and never appears in the draft.
         → Before drafting, have the release script refuse any file under
           `changes/` that fails its name match or names a category missing from
           `[[tool.towncrier.type]]`, and name the file. Or add one test that runs
           both patterns over the same accepted and rejected names.

NIT      .github/scripts/release.py:L157, .github/workflows/ci.yml:L172, L251 —
         these are the first code comments in the repo that name Andre. They go
         stale the day a second person cuts a release.
         → Say "the person cutting the release".

NIT      .github/scripts/check_release_note.py:L159 — a fork pull request whose
         head branch is named `main` passes the required check with no note,
         because `GITHUB_HEAD_REF` is "main".
         → Take the `main` shortcut only when `GITHUB_HEAD_REF` is unset.

NIT      .github/workflows/ci.yml:L229 — `git log -1 --grep` returns the newest
         non-merge commit whose message contains the subject anywhere, body
         included. On a retry after a failed `gh release create`, a later commit
         that quotes "chore(release): cut X" in its body is picked instead. The
         subject check then fails, and the release can't be retried.
         → Match the subject exactly. One way is
           `git log --no-merges --format='%H %s' HEAD | awk -v s="chore(release): cut $v" 'substr($0,42)==s{print $1; exit}'`.

NIT      .github/workflows/ci.yml:L13-15 — the existing concurrency group cancels a
         pending run on `main` when a newer push arrives. If the release merge's
         run is still pending when another PR merges, the tag lands on that
         later merge. The tag then ships code whose note waits for the next
         release, and AGENTS.md's "CI tags the merge" isn't quite true. The
         sole-user cadence makes this rare.
         → Tag the first-parent merge that brought `$rel`, not `HEAD`. Or
           accept the risk and say so in the comment.

NIT      .github/scripts/release.py:L87 — `last_tag` is the highest `v*` tag,
         whatever `pyproject.toml` carries. If the script runs before the
         previous release's tag job has finished, the previous release pull
         request shows up under "Merged with no release note".
         → Refuse when `v{current_version}` has no tag yet, and say to wait for
           the tag job.

NIT      .github/scripts/check_release_note.py:L85 — it reads `pyproject.toml`
         relative to the working directory. Run from a subdirectory, it crashes
         with FileNotFoundError, while `release.py` handles this by changing to
         the repository top first. `wfctl verify` runs from the root, so only a
         direct run hits it.
         → `os.chdir` to the `git rev-parse --show-toplevel` output first, as
           release.py does.

NIT      pyproject.toml:L29 — the comment says the note file name format "gets
         re-checked at the next `uv lock --upgrade`", but nothing does that
         check. Every test writes note names by hand, and none runs
         `towncrier create`.
         → Drop the claim, or add a test that runs `towncrier create` twice and
           feeds both files to the check.

NIT      tests/test_release_script.py:L241 — US2 scenario 5 says the `+bump-ruff`
         note "appears in the draft". The test asserts only that the merge isn't
         listed.
         → Also assert "Ruff is updated." in `out`.

NIT      .github/scripts/ — the scripts are outside `[tool.mypy] files` and
         outside `wfctl verify`'s ruff paths. CI's `ruff check .` covers them,
         but nothing type-checks them, and `pyproject_at -> dict` is already a
         bare annotation.
         → Add `.github/scripts` to `[tool.mypy] files`.
```
