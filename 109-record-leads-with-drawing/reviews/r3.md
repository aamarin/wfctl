## Findings

**BLOCKER `wfctl/_arch.py:257` (`_drawing`) — a fenced block whose interior is
only whitespace passes as "a drawing," letting `accept_blockers` return empty
and `wfctl arch accept` promote a record with nothing actually drawn.**

`data-model.md`'s own truth table for `_drawing` (lines 61–70) states three
outcomes: no section → `""`, section present but **empty interior** → `""`,
and a real interior → the text. The implementation only satisfies the empty
case when the fenced block has *zero* interior lines. A block whose sole
interior line is blank/whitespace-only reports `line.inside = True` for that
line (per `wfctl/_md.py`'s walker, which does not special-case blank lines),
so `_drawing` collects it and returns `"   "` — a non-empty, truthy string.
Reproduced directly:

```python
body = "## Boundary\n\n```mermaid\n   \n```\n\n## Log\n"
r = Record(slug="x", path=None, status="proposed", supersedes="", body=body, diagram="component")
_drawing(r)          # -> '   '   (truthy)
accept_blockers(r)   # -> []      (accept would succeed)
```

This defeats FR-004/SC-001 ("every record accepted after this ships carries a
drawing") for the one shape most likely to occur by accident — an author
scaffolds a fence and forgets to fill it in, or a template placeholder is
copied without deleting a blank line. No test in `test_arch_sections.py` or
`test_arch_accept_drawing.py` exercises a whitespace-only interior. Fix:
`_drawing` (or its caller) should treat an interior that strips to empty as no
drawing — e.g. `"\n".join(interior).strip()` and check truthiness of that.

**BLOCKER `wfctl/_arch.py:257` (`_drawing`) — when the first fenced block
under `## Boundary` has zero interior lines, the function silently falls
through and returns the *second* block's content, contradicting its own
docstring and `data-model.md`.**

The docstring states "The first block, not all of them" and `data-model.md`
(line 76) is explicit: "A second fence under the same heading is a second
drawing... the check that a drawing exists is satisfied by the first." The
loop only breaks on `elif collecting and line.fence`, and `collecting` is
never set to `True` for a block with no interior lines — so a truly empty
first fence's closing delimiter does not stop the walk, and the loop
continues into a later fence, collecting *that* one's content instead.
Reproduced directly:

```python
body = (
    "## Boundary\n\n```mermaid\n```\n\nprose here\n\n"
    "```mermaid\nA --> B: real content\n```\n\n## Log\n"
)
_drawing(Record(slug="y", path=None, status="proposed", supersedes="", body=body, diagram="component"))
# -> 'A --> B: real content'   — the SECOND block, not the first
```

Lower practical blast radius than the whitespace bug (a real drawing does
exist somewhere in the record, so FR-004 is nominally satisfied), but it is a
documented contract violation: the function is supposed to be indifferent to
which one, but its stated indifference is "always the first," not "whichever
one it happens to fall into." A first block left empty for any reason (a
scratch draft, a half-finished edit) silently swaps in unrelated content as
"the drawing," which also feeds VR-007's label-agreement check against the
wrong section. Fix: track whether an opening fence was seen for this pass and
`break` unconditionally at its matching close, independent of `collecting`.

**WARNING `wfctl/_arch.py:163` — `validate`'s docstring ("Link integrity
across the record set: VR-002, VR-003, VR-004.") no longer describes the
function.** This diff adds two more rule blocks to the same function
(VR-006 at line 218, VR-007 at lines 224–252) without touching the one-line
summary. A reader trusting the docstring undercounts what `validate` already
does. Low cost to fix: extend the list to `VR-002, VR-003, VR-004, VR-006,
VR-007` (there is no VR-005 check here by design — it's the frozen-body rule,
enforced by convention, not code).

**WARNING `wfctl/cli.py:5651` (`_check_arch_records`) — its docstring's claim
that a repo which never adopted this tool's conventions "cannot be failed" is
no longer true given VR-006, added by this diff.** The docstring (lines
5663–5669, untouched by this diff) reasons that only a `supersedes:`-based
check can produce an `error`-level finding for a foreign ADR corpus, because
`supersedes:` is wfctl's own convention. VR-006 (`wfctl/_arch.py:218`) breaks
that: it raises `error` for *any* record whose frontmatter carries a
`diagram:` key outside `DIAGRAM_KINDS`, with no dependency on `supersedes:` or
on the record having ever gone through this tool's acceptance flow. A repo
that already used a `diagram:` frontmatter key for something else (unlikely,
but exactly the scenario this docstring was written to rule out) would now
get an unexpected `error` from `wfctl doctor`/CI. This diff didn't write the
docstring, but it made the claim false and should update it — the same
standard the diff already holds itself to for `validate`'s and `acceptable`'s
own docstrings.

**NIT `wfctl/_arch.py:212-241` — the VR-007 loop scans `## Boundary`'s bounds
twice per record: once inside `_drawing(record)` (line 273), and again
immediately after via a direct `_section_bounds(lines, "## boundary")` call
(line 240) to strip the section out of `rest`.** Same lines, same heading,
recomputed. Harmless at this corpus's size (tens of short files), and not
worth restructuring `_drawing` just to expose the bounds — flagging only
because it's an easy one-line note for a future reader wondering why the same
scan appears twice in ten lines.

**NIT `wfctl/cli.py:1641-1649` — the three-kind blurb table is matched to
`DIAGRAM_KINDS` by position via `zip`, with no test asserting the two
sequences stay the same length.** If `DIAGRAM_KINDS` ever gains or loses an
entry without the blurb tuple being updated in lockstep, `zip` truncates
silently — the "no declared kind" guidance table would quietly print fewer
rows than kinds, with no test failure. `test_kinds_match_the_shipped_template`
guards the template but not this table. Low priority: `DIAGRAM_KINDS` is
described in its own comment as "the closed set," so this is unlikely to move,
but a one-line `assert len(blurbs) == len(DIAGRAM_KINDS)` (or building the pair
as a single dict literal instead of two parallel sequences) would remove the
silent-truncation risk for free.
