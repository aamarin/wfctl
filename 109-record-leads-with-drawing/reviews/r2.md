## Findings

**WARNING** `tests/test_skill_cross_references.py:545` —
`test_the_record_template_carries_every_section_a_record_needs` asserts a
fixed tuple of headings (`Context, Direct baseline, Decision, Owns truth,
Considered, Log`) and its docstring claims to check "every section a record
needs." This PR promotes `## Boundary` from optional to required
(`record-template.md`, `SKILL.md`) but did not add it to this tuple. The
test's own name is now false, and a later edit that dropped `## Boundary`
from the shipped template would pass this test though nothing else in the
suite would catch it (`test_arch_sections.py`'s `test_kinds_match_the_shipped
_template` only checks that the three kind *names* appear as substrings
somewhere in the template, not that the section itself exists) →
add `"Boundary"` to that tuple.

**WARNING** `wfctl/cli.py:1638-1651` — the kind→blurb table printed on a "no
declared kind" refusal (`"a value moving between two sides"`, `"a line
between components"`, `"a sequence one thing passes through"`) is a literal
tuple `zip`'d against `_arch.DIAGRAM_KINDS` by position, with no test tying
the two together and no shared source. `DIAGRAM_KINDS`'s own module comment
says "the three names are typed once here and nowhere else" — true of the
*names*, not of this prose, which is now typed independently a third time
(`cli.py`, `SKILL.md`'s table, `record-template.md`'s comment; `SKILL.md`'s
copy also carries an extra clause each row that `cli.py`'s doesn't). If
`DIAGRAM_KINDS` ever gains a fourth value, `zip` silently drops it from the
CLI table with no error and no failing test → at minimum, a comment at the
`zip` site noting the coupling to `DIAGRAM_KINDS`'s order/length, or move the
blurbs into a `dict[str, str]` keyed by kind (removes the position-coupling
risk for one extra line).

**NIT** `wfctl/_arch.py:191-201` (`_STOPWORDS`) — `"his"` and `"then"` each
appear twice in the frozenset literal. Harmless (a `frozenset` display
dedupes), but it's a copy-paste tell worth cleaning up.

**NIT** `wfctl/_arch.py:230-236` (VR-007's `for record in records:` loop in
`validate`) — recomputes `_section_bounds(lines, "## boundary")` to build
`rest`, even though `_drawing(record)` (called two lines above) already ran
the identical scan internally to find the same bounds. Not a correctness
issue and not measurably slow at record-file sizes, but it's a second
definition of "where does Boundary end" existing beside the one
`_section_bounds` was extracted to be the only definition of. A version of
`_drawing` that also handed back `(heading, end)` would close this.

**Note, not a finding** — `Record.body` is the whole file text including the
frontmatter block (`parse_record`'s `body=text`), so VR-007's "rest of
record" word set also picks up frontmatter tokens verbatim — e.g. a record
declaring `diagram: state` always has the word "state" available to satisfy
any drawing label spelled "state". FR-008 says a label is reported when no
content word appears "in any other **section**" of the record, and
frontmatter isn't a section, so the implementation is slightly more lenient
than the requirement's literal wording. This is consistent with how
`research.md`'s R-004 corpus measurement was actually run (same `.body`
field), so the calibrated numbers already price it in — flagging only so a
future reader doesn't mistake it for a regression if a frontmatter-derived
word ever "saves" a label that looks wrong by eye.
