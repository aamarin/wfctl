### Six passes

**1. Correctness** — No blockers. Traced the whole call chain:
`check_body_cmd` → `_verification_finding` → `verification_block` →
`_verify.load_config` / `load_record` / `code_identity`. Verified by hand and
by test:
- Silent when `wfctl.json` is absent (`load_config` short-circuits before any
  git call — matches the "must cost nothing" requirement in
  `verification_block`'s own docstring and FR-002).
- Reports `verification: unverified` when a definition of done exists and no
  record covers the tree.
- Goes quiet again once `_verify.perform` records a pass.
- Reports `verification: stale` once the branch commits past the recorded sha
  (record names a commit that is no longer HEAD).
- `_verification_finding` swallows `get_repo_root()`'s `SystemExit` outside a
  git repo — matches `opening-a-change` Step 5's own instruction to skip the
  command there, and is the same `except SystemExit: return`/`pass` pattern
  used 5 other times already in `cli.py` (line 121, 2191, 2866, 3131, 4629), so
  it isn't a new failure mode being introduced untested-in-kind.
- `test_shape.py`'s pre-existing `test_check_body_exits_one_on_a_finding_and_zero_without`
  was updated to pin `WFCTL_REPO_ROOT` at an empty tmp dir. This is a real fix,
  not incidental: this worktree's own `wfctl.json` declares a 3-command
  definition of done (`pytest`, `ruff`, `mypy`), so before this change that
  test would have silently started reading this repo's real verification
  state and gone flaky/order-dependent. Good catch by the author.
- Ran the full suite read-only: `uv run --frozen --extra dev pytest -q` →
  **1110 passed**. `uv run --frozen --extra dev ruff check wfctl/ tests/` →
  clean. `uv run --frozen --extra dev mypy wfctl/` → clean. All three
  Definition-of-Done commands this repo declares are green.

**3. Architecture** — Matches the two cited records. `verification_block`
