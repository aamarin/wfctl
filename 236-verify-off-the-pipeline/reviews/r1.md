**BLOCKER — the new finding's own precondition is violated by the workflow
that produces it.**
`wfctl/agents/skills/opening-a-change/SKILL.md:151-198` (Step 5) tells the
agent to "Write the body to a file and pass the file" and then run
`wfctl check-body <path>`, with no instruction about *where* that file must
live. But `verification_block`'s staleness check
(`wfctl/_verify.py:code_identity`, via `git status --porcelain`) reads
`--porcelain` untracked-file state, and if the body file lands inside the
repository (the plain reading of "write the body to a file" — no scratch
directory is named anywhere in this skill; `grep -rl scratchpad
wfctl/agents/skills/` is empty), the new `verification:` finding fires
**purely because the PR description exists**, even immediately after a clean
`wfctl verify` pass. Reproduced end to end with the real CLI (throwaway repo,
not the tracked tree):

```
$ uv run wfctl verify
✓ verified — 1 of 1 passed at e406f03
$ # write the PR body file inside the repo, as Step 5 literally instructs
$ uv run wfctl check-body pr-body.md
⚠ verification: stale — verified at e406f03, tree has uncommitted changes
```

This directly falsifies the skill's own claim, three lines above where the
finding is introduced (`SKILL.md:172`): **"Its third finding is not about the
file."** In the common case — an agent following Step 5 literally, with no
external scratch-file convention of its own — it *is* about the file, every
time, and never clears without either deleting the body file, gitignoring it,
or moving it out of the tree first. This is not a rare edge case: Step 5 is
the step that both creates the file and invokes the command that now reads
tree cleanliness, and nothing between them tells the agent to keep the two
apart. A false "stale" on a genuinely clean, verified tree trains the reader
to distrust or ignore the line — the exact failure mode
`wfctl-runs-the-verification` and `a-rule-is-expressed-as-a-check` argue
against for self-reported completion, arriving here as a false machine
report instead.

Notably, the test suite already knows this trap exists and works around it —
`tests/test_verify.py`'s `_body_file` helper writes explicitly *outside* the
repo (`root.parent`) with a docstring spelling out exactly this failure mode
("a check reporting on the artifact it was handed") — but that knowledge
never made it into the shipped skill instructions real agents follow.

**Fix (either is sufficient, the first is cheaper):**
- Add one line to Step 5 telling the agent to write the body file outside the
  repository (a scratch/tmp path), matching what the test helper already
  does and documents.
- Or exclude the exact `path` argument from `code_identity`'s dirty check
  when it resolves under `repo_root` (e.g. `git status --porcelain --
  . ':!<relative path>'`), so the command is robust regardless of where the
  file is placed.

**WARNING — the new `except SystemExit` branch in `_verification_finding`
has no test.**
`wfctl/cli.py:3301-3311`: `_verification_finding` catches `SystemExit` from
`get_repo_root()` and returns `[]` so `check-body` stays quiet outside a git
repo. This exact pattern (`monkeypatch.setattr("wfctl.cli.get_repo_root",
<raiser>)`, assert graceful degrade) is already established in this test
suite for an analogous case —
`tests/test_archive_specs.py::test_a_non_git_checkout_still_exits_zero`. No
equivalent test exists for `check-body`. The existing
`test_check_body_names_the_file_it_cannot_read` doesn't exercise it either —
it fails on the file read, before `_verification_finding` ever runs. Given
the project's own convention ("A bug-fix diff with no regression test" is
called out as a red flag, and this repo already has the exact test pattern
to copy), this is a real, cheap-to-close gap rather than a style nit.
