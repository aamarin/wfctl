## Findings

**WARNING  docs/architecture/mirrored-skills-ship-no-wrapper.md:L42-50 — the
"Owns truth" claim is false for a member of its own set → narrow it to
discoverability, and name the exception.**

The record asserts `_MIRRORED_SKILLS` owns *"may an agent invoke this skill
without being asked?"* and that *"there is no second place to state it"*. There
is a second place, and it is occupied:

- `wfctl/agents/skills/i-have-adhd/SKILL.md:5` carries
  `disable-model-invocation: true`. It ships, it mirrors, and it stays
  non-model-invocable — membership in `_MIRRORED_SKILLS` does not decide it.
- The record's supporting argument — *"`disable-model-invocation` is not an
  Agent Skills frontmatter key, so `test_every_shipped_skill_declares_only_spec_keys`
  rejects it"* — is contradicted by that test, which exempts `i-have-adhd` **by
  name** for exactly this reason (`tests/test_skill_frontmatter.py:31-34,46`).
- A shipped contract from #59 already allocates this the other way:
  "A skill in `.claude/skills/` is *discoverable*. Whether the model may invoke
  it unprompted is decided by that skill's own frontmatter, not by membership."
  (`wfctl-specs/59-deployment-key-metadata/contracts/skill-frontmatter-and-layout.md`).
  The new record silently reverses a prior allocation without superseding it or
  saying why.

The author already knows this — the reworked docstring in
`tests/test_skill_cross_references.py` says `i-have-adhd` "carries upstream's
`disable-model-invocation`". The record is the one place that does not.

Fix: state what mirroring actually owns — *is this skill natively discoverable,
and does a typed `/name` exist for it* — and record the frontmatter override as
the documented exception, naming `i-have-adhd` as the live case. Worth doing
before the record leaves `proposed`: per `architecture-decisions`, an accepted
record is immutable.

**WARNING  wfctl/cli.py:L1278-1285, tests/test_skill_cross_references.py:L52-69 —
a Claude-only justification is used to delete files that install for every agent;
the renamed test promises a cross-agent property it does not check.**

The comment and the record both rest on one premise: *"Claude Code creates
`/name` for a skill exactly as it does for a command, so deleting the wrapper
costs no human path."* True for Claude. The deleted files are **base-layer**
artifacts, and `_AGENT_TARGETS["bob"]` copies `agents/commands → .bob/commands`
(`wfctl/cli.py:1097-1100`). A `--agent bob` install therefore loses
`/i-have-adhd`, `/conversation-response-shape`, `/worktree-handoff` and the other
four, and the compensating mirror does not reach it — `_AGENT_SKILL_EXTRAS` is
`{"claude": _claude_native_skill_mirror}` (`wfctl/cli.py:1377`).

Nothing in the repo establishes that Bob Shell turns `.bob/skills/<name>` into a
typed `/name`. Two signals point the other way: wfctl installs Bob's skills and
Bob's commands to separate roots (README:222), and it strips
`disable-model-invocation` *specifically for Bob* because "Bob Shell interprets
that key literally … the skill body never executes" (`wfctl/cli.py:1314-1317`) —
i.e. Bob runs commands, and wfctl already had to reason about that separately.

`test_each_output_style_skill_is_typeable_by_name` renames the old wrapper
assertion and now asserts only `name in _MIRRORED_SKILLS`. Its docstring says
"that route has to exist somewhere" — but the set it checks is the Claude mirror,
so under `--agent bob` the property the test names is no longer true while the
test stays green. A test whose name is broader than its assertion is the shape
that hid #170 in the first place.

Fix, either:
- scope both the comment and the record to the Claude layer explicitly, add a
  Consequences bullet for what a Bob install loses, and rename the test to what
  it proves (`..._is_reachable_by_name_under_claude`); or
- verify Bob's skill→slash-command behavior and put the evidence in the record,
  at which point the current wording stands as written.

**NIT  docs/architecture/mirrored-skills-ship-no-wrapper.md:L83-85 — Consequences
names the wrong `doctor` mechanism, for one of the two directions.**

Reproduced the upgrade path in a scratch repo (old bundle installed with the
0.16.0 wheel on PATH, then re-installed with `uv run` from this worktree): the
leftover wrappers are reported by the **recorded-but-no-longer-shipped** check,
which names all 14 paths — both `.agents/commands/*.md` *and*
`.claude/commands/*.md` — and offers `--prune`. The abandoned-entry scan
(`_scanned_dirs` / `_scan_owns`) is the mechanism for the *other* direction, the
orphaned `.claude/skills/<name>` after un-mirroring (#110); it never sees
`.claude/commands` at all, by design. Saying "abandoned-entry scan … under
`.agents/commands/` either way" sends a future reader to the wrong code and
understates the report, which already covers the copy that actually causes the
collision.

Worth adding while there: in an already-installed repo the collision survives a
plain re-install (both copies stay on disk, `doctor` exits 1) until
`install-skills --prune` runs. That self-heals for anyone on `/start-session`,
which already prescribes `--prune --yes`
(`wfctl/agents/skills/start-session/SKILL.md:44-45`) — but the record does not
say so, and it is the one operational consequence a reader would want.
