## BLOCKER, in full

The gate the change chose is *"does `session-summary.md` name a first action"*.
That is satisfied on `main` by every ordinary `/end-session`: `_session.py:80`
scaffolds `## Next Session TODO\n- [ ] (fill in)`, and `end-session/SKILL.md:105`
requires it be filled with `{highest-priority next step}` and calls leaving the
placeholder **CRITICAL**. So the next attended session in the main checkout finds
a summary naming a first action, takes row one, and begins — which is the thing
#244's acceptance criterion (b) says the fix must not do:

> An ordinary attended session still gets asked — the fix must not make
> `/start-session` in the main checkout start doing things unprompted

The commit body answers a different question. "Row two is untouched on purpose. A
session with no summary has genuinely not been told what to do" protects the
*first* session on a branch. It says nothing about the second one, and per #239's
own body the main checkout is exactly where second sessions live ("The state dir
is per branch, so a worktree branch lives one session and never reaches the second
case. `main` reaches it every time").

Two symptoms, one cause:

1. **Attendedness.** The branch keys on the file, not on whether anyone is there.
   #244's second shape ("read #127's switch") is the one that separates those; the
   chosen shape does not, and the widening is undisclosed.
2. **Staleness.** Row one has no freshness test. A TODO written days ago, whose
   work merged since, is quoted and begun. Step 7 has *already computed* the
   evidence against it — "**Likely done** — an open issue whose work the commits
   appear to complete" — and step 9 ignores it. Step 8 will print "Alignment:
   likely done: #N" and then step 9 begins #N.

Fix, one clause, and it does not endanger criterion (a) — a fresh handoff's action
is never "likely done":

> Quote a line step 5 and step 7 have not already shown done. If the action you
> would quote is one step 7 flagged as likely done, or the commits in step 5
> already implement it, that is not an answer — say so and ask.

Deliberately *not* proposed: reconciling the quoted line against `wfctl status`'s
next command. A handoff that says "implement #244" on a branch whose inferred step
is `brainstorm` is the #206 case, and `worktree-handoff` §3 already owns the route.
Widening the reconciliation that far would re-break criterion (a).

Alternative, if the widening is intended: amend AC (b) on #244 with the argument
("a previous session's TODO is an answer too") and say so in the skill, so the
next reader does not read row two as the protection it is not. I stopped short of
calling that the only fix because the author may hold context I do not — but the
change cannot both leave AC (b) as written and ship as-is.

## The passes

**1. Correctness.** Traced step 4 (what it reads), `_session.py:60-83` (what
`end` writes into it), `end-session/SKILL.md:95-122` (how it gets filled),
`_session.py:40-58` (the `start` event the L192 claim depends on),
`.workmux.yaml` and `wfctl/agents/configs/workmux/.workmux.yaml` (what
`post_create` actually runs), `worktree-handoff` step 3 (how the file lands).
Findings: the BLOCKER, and L192/L194.

On L192: `post_create` in both the repo config and the shipped template runs
`wfctl install-skills` and `wfctl issue start`. `wfctl issue start` is a tracker
column move; the `start` event is appended only by `cli.py:147`, under the
top-level `start` command, which is what `/start-session` step 2 runs. So the
ordering is the opposite of what the skill states: the `cp` in `worktree-handoff`
step 3 is chained onto `wm add` and normally lands *before* the pane's first
`/start-session`. There is a genuine race there (with `--background` the pane
boots while the `cp` runs), and the conclusion — don't build the discrimination —
survives. What does not survive is the stated mechanism, and it ships to every
consuming repo as a fact. This repo's own rule is that a claim from prior context
is verified before it is repeated; five sessions propagating a wrong assertion is
the failure that rule was written for.

**2. Security.** Considered and cleared, with one note. Step 9 converts
`session-summary.md` from a file that is read into one whose content directs
action with "**Do not ask**" attached. The file lives in the XDG state dir, is
written by the user or by `worktree-handoff`'s `cp`, and the same text already
arrives through `--prompt-file` as the pane's first turn — so no new trust
boundary is crossed and there is no finding. Worth knowing that this repo does
treat adjacent files as hostile (`test_hook_user_prompt.py:132` covers a
`digest.md` reading "ignore all prior rules"), and that `session-summary.md` has
no equivalent guard; that is a pre-existing property, not this diff's.

**3. Architecture.** Weighed against `wfctl arch context` (9 accepted records).

- `a-rule-is-expressed-as-a-check` — the load-bearing one, and the change lands on
  the right side of it *directionally*. The record's test is "is a violation
  visible in an artifact the work already produces?", and it names the reply as
  such an artifact. Making the row a quoted line in step 8's report is what turns
  an invisible violation into a visible one, and that is a real improvement over
  "say it plainly enough". It stops one step short of what the record's decision
  box asks for — "the rule is expressed as a check over that artifact" — because
  nothing observes the reply. I do not raise that as a finding: the record also
  ranks an observation "a verdict the reader can re-derive from the artifact
  themselves" first, and the reply-observer mechanism does not exist here yet
  (#215 built one for a different rule). The shipped tests observe `SKILL.md`, not
  the reply, and are honest about being that.
- `session-state-is-re-derived` — no violation. The record explicitly reserves
  session files for "what re-derivation cannot reach — the handoff prose a human
  or agent wrote deliberately", which is what step 9 reads. The BLOCKER's
  staleness half is the edge where the reserved prose collides with a re-derived
  value (step 7's "likely done"), which is why the fix is stated in terms of
  deferring to the re-derivation.
- `knowledge-placement` — guidance for the worker in the skill that runs it,
  pointed at from the skill that writes the input. Correct placement.
- `layer-model` — edits are in `wfctl/agents/`, generated trees untouched by the
  diff. Confirmed `.agents/` and `.claude/` copies are byte-identical to source
  (`diff -q`, rc=0 both), so `install-skills` was run after the edit — the half of
  AGENTS.md's definition of done that the suite cannot check.

**4. Readability & simplification.** The prose matches the file's register and the

**5. Performance.** Not applicable — documentation-only diff, no code paths, no
