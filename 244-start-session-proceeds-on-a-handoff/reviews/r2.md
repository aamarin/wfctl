## Findings

**BLOCKER  wfctl/agents/skills/start-session/SKILL.md:198–200 — a file on disk
can pre-authorize irreversible actions, and the clause that lets it is a tone
judgment → delete the `unless` clause.**

> Push, comment, open a change, merge are asked for when you reach them, **unless
> the summary said in its own words to carry through.**

Two defects in one clause.

First, it contradicts the change's own thesis. The commit body's third paragraph
argues that "say that first action plainly enough to be the default" failed
*because* it was a judgment about tone, and replaces it with a quote test. This
clause then reintroduces exactly that judgment — "said in its own words to carry
through" is unquotable, uncheckable, and asks the agent to read intent — and
puts it in front of the *higher*-stakes decision. The gate got stricter where the
stakes are local and reversible, and looser where they are not.

Second, it hands authority for #131's outward-facing and irreversible rows to a
text file. #244's own body quotes those rows:

```
   outward-facing            push, comment, open an issue
   irreversible              merge, close, force-push, delete
```

The commit body cites #131 to justify row one ("beginning implementation is the
first row") and then, four lines later in the skill, lets `session-summary.md`
reach rows two and three with no human present. `session-summary.md` is written
by `end-session` or copied in by `worktree-handoff`
(`cp "$HANDOFF" "$(wfctl state-dir --branch <branch>)/session-summary.md"`) —
neither of which requires a human to have read the line that grants the
authority. Nothing in the diff tests this clause and the commit body does not
mention it, so it is a scope expansion arriving unargued.

Fix: delete `, unless the summary said in its own words to carry through`. It
costs nothing #244 asked for — the issue is about *beginning*, not about
finishing — and the sentence before it is already complete and correct.

**BLOCKER  wfctl/agents/skills/start-session/SKILL.md:177–180 — row one captures
every ordinary attended session, so acceptance criterion (b) is not met → gate
row one on something narrower, or amend AC (b) explicitly before merge.**

The table's first row fires on "a summary naming a first action". `end-session`
step 4 (`wfctl/agents/skills/end-session/SKILL.md:83–110`) writes this template
into `session-summary.md` on **every** session close:

```markdown
## Next Session TODO
- [ ] {highest-priority next step}
```

and its CRITICAL note forbids leaving placeholders. There is no "None" escape
offered for that heading the way there is for commits and blockers. So the
normal state of any branch that has ever run `/end-session` is a
`session-summary.md` carrying a quotable first action — and `- [ ] Wire the
--json flag` is a literal line an agent can copy, which is the whole of the gate.

#244's AC (b), verbatim:

> An ordinary attended session still gets asked — the fix must not make
> `/start-session` in the main checkout start doing things unprompted

Under this diff, an attended `/start-session` in the main checkout on Monday
begins editing files against Friday's TODO without a reply. That is the stated
criterion, failing. The commit body sees the widening — "a handoff and a previous
session's TODO both answer 'what next'" — and argues it is the right call, but it
argues it against #239's discrimination problem, not against AC (b), which it
never names. "Row two is untouched on purpose" answers a different objection: row
two is the *no summary* case, and the AC is about the *ordinary resumed* case,
which the diff moves out of row two and into row one.

The second regression test does not defend the criterion either — it asserts only
that the string `"no summary"` and the question survive in the text, which is
true of a change that hands every repeat session to row one.

Two honest fixes:

- **Narrow row one.** A stale `- [ ]` in a nine-day-old TODO is not the same
  artifact as a handoff written for a branch that has never run. #239 says the
  *ordering* discrimination is unavailable; it does not say no discrimination is.
  A marker the handoff writes and `end-session` does not is available today —
  `worktree-handoff` already tells authors to open with a line naming itself as a
  handoff ("Say so in the handoff's first line", `worktree-handoff/SKILL.md:144`),
  which is a quotable string, not a timestamp.
- **Or keep the widening and get AC (b) amended in #244 before merge**, in
  writing, with the argument the commit body makes. Andre's own standing note is
  that wfctl defaults are his approach, so this may well be the wanted behavior —
  but it changes when work starts unprompted in *every repo wfctl installs into*,
  and that decision should not arrive as a side effect of a bug fix. A change
  that moves who decides when work begins is also not obviously the "no new
  state" class `design-levels` excludes from the pipeline.

**WARNING  wfctl/agents/skills/start-session/SKILL.md:4 — the skill's
`allowed-tools` allowlist is read-only, and row one now instructs the skill to
write → widen the frontmatter, or make step 9 explicitly the skill's exit
point.**

```
allowed-tools: Read Bash(wfctl start*) Bash(wfctl status*) Bash(wfctl arch context*)
  Bash(wfctl state-dir*) Bash(wfctl doctor*) Bash(wfctl install-skills*)
  Bash(wfctl issue list*) Bash(wfctl issue view*) Bash(wfctl change list*)
  Bash(git status*) Bash(git log*) Bash(git symbolic-ref*)
```

No `Edit`, no `Write`, no unrestricted `Bash`. `start-session` is the only skill
in `wfctl/agents/skills/` that carries this field at all — under the old step 9
that was coherent, because the skill genuinely ended by asking a question and
whatever happened next happened outside it. Row one now says "and begin" *inside*
the skill.

I could not verify enforcement semantics from this tree, so this is a WARNING
rather than a BLOCKER — but if the harness honours the allowlist while the skill
is active, row one is a step whose remedy the model is not permitted to invoke,
which is #204's failure class exactly, on #147's road, filed against the change
closing the third instance of it. Worth ten minutes to settle before merge.

Cheapest fix that is right either way: end step 9's first row with an explicit
hand-off out of the skill ("the skill ends here; the work happens in the session
that follows"), and add `Edit Write Bash` to the frontmatter if the answer is
that the allowlist binds.

**WARNING  tests/test_start_session_asks_conditionally.py:19–22 — the check is
over the skill's source text, not over the artifact the rule's violation appears
in → file the check `a-rule-is-expressed-as-a-check` asks for, or record why this
rule sits on the prose side.**

The record's test is "is a violation of it visible in an artifact the work already
produces?", and its own text names the answer set: *"it includes **the reply**,
the PR body, the diff and the tree — which is where every violation above was
observed."* A step-9 violation is a reply that reports the first action and then
asks — #244 pastes two of them. So this rule lands on the **yes** branch, and the
record is unambiguous about what that requires:

> Stating it correctly and delivering it reliably, with nothing observing what
> was written, is not a partial implementation of the rule — it is the rule's
> absence, documented.

These three tests observe that the *rule text* is present in `SKILL.md`. That is
"delivering it reliably". Nothing observes a reply. And step 8's report — the
mechanism the commit body offers as the observation — is the constrained party
volunteering an account of its own compliance, which the record refuses by name:

> Nor can the reader answer it… the reader is the party the rule constrains, so
> an account of having followed it is a self-report.

I want to be fair about how much this costs. The record explicitly does not
decide "which mechanism carries a check", #215's `Stop` hook + CLI command is
prior art in this repo, and a genuinely cheap observer here is not obvious. But
AC (c) — "whatever wins is checkable, not a rephrasing of 'say it plainly
enough'" — is the criterion this finding bears on, and the tests as written
satisfy a weaker reading of it than the one the record supports: they prove the
prose did not revert, not that the rule holds. Either file the follow-up for a
check over the reply, or write down why this one takes the record's **no**
branch. Silence is the outcome the record exists to prevent.

Credit where due: I verified the regression value is real. Running the three
assertions against `dd187f4~1`'s step 9 fails all three (`Do not ask` False,
`session-summary.md` False, `no summary` False, `Quote the line` False; only the
question string survives). A straight revert is caught.
