## BLOCKER — `spec_dir is None` gets `auto: true` too, and that is the branch the
argument skips

`_infer_steps` returns early before any of the reasoning the commit message
relies on:

```python
if spec_dir is None:
    return [_PipelineStep(name, "pending", None) for name in _STEP_NAMES]
```

`_current_step_name` then returns `brainstorm`, `next_step_content` reads the
table, and `build_report` hands back `auto: true`. The commit argues:

> Its arm in `_infer_steps` produces `done` (design.md present), `skipped`
> (spec.md present, moved on without one) or `pending` … It is the current step
> only when nothing exists yet, which is precisely the state
> `/speckit.brainstorm` resolves.

That is a correct reading of the `brainstorm` arm, and the `brainstorm` arm is
only reachable when `spec_dir is not None`. The other route to `brainstorm` —
no feature claims this branch at all — is a different situation with a different
correct answer, and it is the one the flip changes most.

**What now happens unattended.** `speckit-orchestrate` step 1 handles a null
`spec_dir` as an answer rather than a lookup failure, and its remedy is a human
one:

> Until the epic has decomposed, nothing claims the branch and `null` is the
> correct answer — say that, rather than treating it as a lookup that failed.

Step 1 says *say that*. It never says **Stop** — compare step 0, which says it
twice. So the loop proceeds to step 5, which branches on `auto` alone, and now
emits `EXECUTE_COMMAND: speckit.brainstorm`. `speckit.brainstorm.md` runs
`wfctl feature-paths` and `mkdir -p`s what it prints; `feature_paths_cmd`
(`wfctl/cli.py:794`) prints `spec_root(repo_root) / branch` when `spec_dir` is
None. So the loop creates `<spec root>/<branch>/` and writes `design.md` into it.

**Why that is not local-and-reversible.** The repo's own test docstring names
this exact sequence and says it has no recovery path
(`tests/test_paths.py:299`, `test_resolve_spec_dir_keeps_a_branchs_own_dir_over_a_later_epic_claim`):

> A child of an epic that had not decomposed gets `<spec root>/<branch>` from
> `feature-paths` and starts writing there. When the epic decomposes later and
> its grouping map names that key, resolution stays on the child's own
> directory — the name legs run ahead of the claimant scan.
>
> Reported against the record on #269 as a recovery path that does not exist,
> and it does not.

Once that directory exists, `resolve_spec_dir` never returns the epic again, and
`speckit-orchestrate`'s own key comparison reads "same key → branch owns the
feature", losing the epic's `Tasks` range. The specs then reach `specs-trunk`.
The #131 row the commit invokes — "local and reversible", everything lands in the
working tree — is true of the *bytes* and false of the *routing consequence*.

Before this commit, the `False` is what stopped the loop and put that decision in
front of a human, which is where step 1 puts it. This is the guard question #283
told the author to check first, answered against one of the two branches that
reach the flag.

**Concrete fix — the `_verification_block` / `_decompose_block` shape #240 used.**
`next_step_content` already takes `spec_dir` optionally and already has an
`implement` arm keyed on it:

```python
if step == "brainstorm" and spec_dir is None:
    # No feature claims this branch. `/speckit.brainstorm` would mkdir one,
    # and a branch that grows its own spec dir stops resolving to the epic
    # that later claims it — `resolve_spec_dir`'s name legs run ahead of the
    # claimant scan, and #269 established there is no way back.
    return _STEPS["brainstorm"][0], False
```

Alternatives, either of which I would accept over the status quo:

- **B.** Make `speckit-orchestrate` step 1 say **Stop** on `spec_dir: null`,
  the way step 0 does. That fixes the loop rather than the table, and it is the
  more honest place for it — but it is a skills change, so it needs
  `uv run wfctl install-skills` and a manual exercise per `CLAUDE.md`, and the
  suite would not cover it.
- **C.** Argue it explicitly in the commit message: that a null `spec_dir` is
  overwhelmingly a genuinely new feature, that the epic-sub-issue corner is rare
  enough to accept, and that the mkdir is the intended behavior. I do not find
  that persuasive against a documented no-recovery consequence in a mode that
  removes the human, but the author has context I do not, and a written
  paragraph is a decision rather than an omission.

Whichever route, **the `spec_dir is None` case has no test.** Nothing in
`tests/` asserts the flag for a missing spec dir — `test_state_1_nothing_exists_yet`
(`tests/test_pipeline_commands.py:963`) asserts the glyph and the command and
stops short of `auto`. The flip changed that payload and no assertion moved.

## WARNING — `test_resume_says_the_mode_on_its_own_line` is now vacuous

`tests/test_auto_approve_mode.py:218-233`. The fixture is
`start --auto-approve` on an empty feature, so the step is `brainstorm`. Its
docstring states the defect it pins:

> #127's named mitigation: `auto` and `auto_approve` are different questions …
> Folding the mode into that parenthetical is what the issue says will make the
> two read as one axis.

Before the flip the two values *diverged* — `auto: false`, `auto_approve: true`
— and `assert "(auto: false)" in output` positively proved `resume` was printing
the step's flag and not the mode. After the flip both are `true`, and a
`resume_cmd` regression that printed `(auto: {report.auto_approve})` would pass
this test unchanged. The mitigation's test no longer tests the mitigation.

This is the same reasoning the commit applies to the other three tests —

> a report asserted at the same value twice cannot show the flag was read rather
> than emitted

— and it is the fourth test, missed. Fix, in the shape already used at
`tests/test_pipeline_commands.py:371-375`:

```python
runner.invoke(app, ["start", "--auto-approve"])
storyctl_dir.make_spec_artifact("brainstorm")
storyctl_dir.make_spec_artifact("specify", "# Spec\n\n[NEEDS CLARIFICATION: which?]\n")
output = runner.invoke(app, ["resume"]).output

assert "auto-approve" in output
assert "(auto: false)" in output     # the step's flag, not the mode
```

`clarify` is the current step there (`design_gate` fires only on `specify`, so
no `arch none` is needed), `auto` is `False`, `auto_approve` is `True`, and the
two axes are visibly distinct again.

## Passes run, and what each checked

**1. Correctness.** Traced `_STEPS` → `next_step_content` → `build_report` →
`resume_cmd`/`next_cmd`/`status_cmd`, and `_infer_steps` → `_current_step_name`
for every state that can make `brainstorm` current. Verified the commit's two
central claims:

- *`brainstorm` blocks only when nothing exists.* True on the `spec_dir is not
  None` path — `done` and `skipped` are both excluded by `_current_step_name`,
  so `/speckit.brainstorm` is only ever emitted for a feature with neither
  `design.md` nor `spec.md`. False as a statement about the whole function: the
  `spec_dir is None` early return is the second route, and it is the BLOCKER
  above.
- *`decompose`'s guard has no analogue here.* Correct. `_unkeyed_issues` gives
  `decompose` a `done`-with-blocking-`in_progress` state that the table's flag
  could not see; `brainstorm` has no sub-state, so no `next_step_content` arm is
  needed for the reason #240 needed one. The reason a guard may still be wanted
  is a different one.
- *#100 does not have to land first.* I agree. #100's argument is about steps
  whose evidence is a claim the working agent wrote. The transition this flag
  governs is *into* brainstorm, and its evidence is two absent files — ambient,
  not asserted. The transition *out* is `specify`, already `True`, already gated
  by `design_gate` on a git fact, and untouched here.
- *#280 is not a blocker.* Verified against `speckit.brainstorm.md`'s frontmatter:
  `allowed-tools: Read Glob Write Bash(wfctl feature-paths*) Bash(wfctl status*)
  Bash(mkdir*) Bash(git log*)`. No `gh`, no tracker write. Correct as stated.
- Attended behavior: `speckit-orchestrate` step 5 branches on `auto` alone, so
  the command now launches in attended sessions too. That is benign —
  `speckit.brainstorm.md` reads `auto_approve`, gets `false`, and pauses at all
  four of `brainstorming`'s gates. The human is asked inside the command instead
  of before it.
- `PipelineReport.__post_init__`'s None-together invariant is untouched; no
  branch can now produce a `current` without a `next_command`.
