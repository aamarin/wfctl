## Findings

WARNING  wfctl/_pipeline.py:L24 — the "three states" argument misses a fourth
path to `brainstorm` being current: `_infer_steps` returns early with every step
`pending` when `spec_dir is None`, never reaching the `brainstorm` arm the commit
message enumerates. Verified:
`next_step_content(_current_step_name(_infer_steps(None, root)))` → `('/speckit.brainstorm', True)`.
That matters because `speckit-orchestrate` step 1 names `spec_dir: null` as a
*specific* state — "a sub-issue of an epic … until the epic has decomposed,
nothing claims the branch and `null` is the correct answer" — and it says *say
that*, not *stop*, so the loop runs on to step 5 and now emits `EXECUTE_COMMAND:
speckit.brainstorm` where it previously printed "run … when ready" and stopped.
`/speckit.brainstorm` `mkdir -p`s `<spec_root>/<branch>` and writes `design.md`
there, and `resolve_spec_dir` tries the exact branch dir (`_paths.py:500`) *before*
the epic's grouping-map leg (`_paths.py:512`), so the unattended run manufactures
a claim that supersedes the epic's. Damage is local and deletable, so this is not
a blocker — but it is a state the commit's evidence argument ("its evidence is
two absent files") does not cover, since a null spec dir is a third absence with a
different meaning. → Fix: either extend the argument in the commit/issue to say
why a null spec dir is acceptable here (a fresh feature and an unclaimed sub-issue
are indistinguishable in the payload, and the fresh-feature case is the one #283
is *for*), or close it on the consumer side — `speckit-orchestrate` step 1 stops
when `spec_dir` is `null` **and** the branch's issue key parses to something a
decomposed epic could later claim. Do not guard it in `_pipeline` by returning
`auto=False` for a null spec dir: a fresh feature has no spec dir either, so that
would undo the change entirely.

WARNING  tests/test_auto_approve_mode.py:L231 — the fourth test that reads the
flag was flipped without the treatment the other three got, and it is the one
where collapsing the values costs the most. Its whole subject is #127's named
mitigation that `auto` and `auto_approve` are different questions; the test
distinguished them by *value* (`(auto: false)` beside an auto-approve notice that
is on). With `brainstorm` at `True` both facts now read `true`, so a `resume` that
printed the mode into the `(auto: …)` parenthetical passes — the exact
substitution the docstring says the test exists to catch. The surviving
`assert "(auto:" not in mode_line` only catches the two being merged onto one
line, not the wrong one being read. → Fix: put the feature at a `False` step
before `resume`, the same way the other three were fixed:
`storyctl_dir.make_spec_artifact("specify", content="# Spec\n\n[NEEDS CLARIFICATION: which?]\n")`
after `start --auto-approve`, then assert `"(auto: false)"`.
