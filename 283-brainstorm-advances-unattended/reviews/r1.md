## Findings

**WARNING** `wfctl/_pipeline.py:24` (fix belongs in
`wfctl/agents/skills/speckit-orchestrate/SKILL.md:58-68`) — the commit's central
claim, *"[brainstorm] is the current step only when nothing exists yet, which is
precisely the state `/speckit.brainstorm` resolves"*, has one branch where the
second half is false: **`spec_dir is None`**. `_infer_steps(None, …)` returns
every step `pending`, so `current` is `brainstorm` and the flag now rides out as
`true`. Reproduced against the working tree, unclaimed branch, no spec dir:

```
$ WFCTL_BRANCH=999-unclaimed-subissue … uv run wfctl status --json
  "spec_dir": null,
  "current": "brainstorm",
  "next_command": "/speckit.brainstorm",
  "auto": true          ← was false before this commit
```

`null` there is not "nothing has happened to this feature yet". It is
`resolve_spec_dir` saying **no feature claims this branch** — the sub-issue of an
epic that has not decomposed, which `speckit-orchestrate` step 1 spends thirty
lines establishing is *an answer, not a gap to close by guessing*. That step
tells the agent to "say that"; it never says **stop**, and steps 2–5 run
unconditionally after it. So the payload the loop branches on now says: run the
design pass.

The consequence is not local-and-reversible in the way #131's row is being
claimed. `/speckit.brainstorm` reads `FEATURE_DIR` from `wfctl feature-paths` and
`mkdir -p`s it (`speckit.brainstorm.md`, "Create the destination directory"), so
the run creates `specs/<sub-issue-branch>/`. From then on `resolve_spec_dir`'s
**exact-name leg wins over the `delivery.md` claimant leg** (`_paths.py:486-514`),
so when the epic finally decomposes and names that key, its claim is shadowed —
permanently — and orchestrate's own key comparison ("`999` vs `999` → owned")
reports the branch as owning a feature it does not. That is the #120 shape: quiet,
plausible, and it says proceed.

The skill's step 1 says the old behaviour here was *"loud, obviously wrong,
harmless"*. This commit removes the "harmless".

→ **Fix (one line, no code):** make `spec_dir: null` terminal in
`speckit-orchestrate/SKILL.md` step 1 — after naming the remedy, "Stop." — the
way the session gate at step 0 does. Do **not** guard this in
`next_step_content`: `spec_dir` is optional there and ~30 call sites pass none,
so `None` cannot distinguish *unresolved* from *not asked*. A guard in
`build_report` (`auto=False` when `spec_dir is None`) would work and would still
satisfy the None-together pairing, but it puts a second axis in the table the
`brainstorm-is-one-step-with-addressable-levels` record just refused to add — the
skill is the cheaper and more honest place.

Severity is WARNING rather than BLOCKER for one reason, and it is a temporary
one: `EXECUTE_COMMAND` still has no consumer anywhere in the repository (grep
returns emitters only — seven skills — and #204/#147 say the same), so today the
flip changes what the loop *prints* in this state, not what runs. When #204 lands
a consumer, this becomes a real unattended run against the exact state that was
supposed to wait.

**WARNING** `tests/test_auto_approve_mode.py:231` —
`test_resume_says_the_mode_on_its_own_line` is #127's named mitigation, and its
whole subject is that `auto` and `auto_approve` are two axes. It previously held
`auto_approve: true` beside `(auto: false)`; after this diff both read `true`, so
the assertion pair no longer discriminates by value. A `resume` that sourced the
parenthetical from `report.auto_approve` — precisely the folding this test exists
to forbid — now passes it. The remaining `"(auto:" not in mode_line` assertion
still catches the *layout* half only.

This is the standard the commit message applies, correctly and at length, to the
other three tests ("a report asserted at the same value twice cannot show the
flag was read rather than emitted"). The fourth test was missed. The suite is not
holed — `test_resume_reports_the_auto_flag_of_the_step_it_resumed_to` kills that
mutant, since it asserts `auto: true` with `auto_approve` off — so this is about
this test's stated purpose, not about coverage overall.

→ **Fix:** restore the value-level discrimination, e.g. add a second
`start --no-auto-approve` invocation asserting `(auto: true)` with no mode line,
or advance the fixture one step so the mode is on while `auto` is `false`.

## Passes run, and what each checked

**1. Correctness** — traced `_STEPS` → `next_step_content` → `build_report` →
`cli.status_cmd`/`resume_cmd` → `speckit-orchestrate` step 5. Enumerated every
