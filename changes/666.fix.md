Renaming a branch no longer resets its review round count. wfctl now keeps a tally of the rounds each review group has run under the issue the branch names. Previously, `git branch -m` gave a branch at the round cap an empty count and three more rounds. Two branches on the same issue now share that count, so a stacked PR starts with the rounds the first branch used. The run records, the last reviewed commit, and the sign-off stay with each branch, so a rename means the branch is reviewed again from the trunk and needs a new sign-off at the cap. In a worktree, `wfctl review start` now refuses a branch that names no issue, since renaming to one would restart the count. A branch already in review starts its count again once.
