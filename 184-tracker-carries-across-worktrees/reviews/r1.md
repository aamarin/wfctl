# Review: cb4de1a — `fix(install): inherit the tracker from the main checkout so worktrees have one` (reviewer r1)

Target: `git diff main...HEAD` on `184-tracker-carries-across-worktrees` — one commit,
`wfctl/cli.py` (+16) and `tests/test_install_skills.py` (+34).

## Findings

**BLOCKER  wfctl/cli.py:L1899-1906 — the inherited tracker feeds the *install* path, not just
the manifest key, so in a repo that commits `.agents/trackers/<name>.json` every worktree
install either aborts outright or silently overwrites the project's committed config.**

`manifest["tracker"] = tracker = inherited["tracker"]` writes the local `tracker` variable,
which is the same variable the plan builder tests at L2073 (`if tracker == "github": … plan.append(…)`)
and the overwrite guard at L2076-2078 (`if tdest.exists() and trel not in prior_items: foreign_overwrites.append(…)`).
Until this commit, `tracker` in a worktree install was always `None`, so neither line was ever
reachable there. It is now reachable on *every* worktree install.

The trigger is a repo that commits its tracker config — which is the arrangement wfctl
deliberately supports: `.agents/trackers/github.json` is excluded from the gitignore list on
purpose, pinned by `tests/test_install_skills.py:L63` ("Tracker config is project-owned and
meant to be committed"). In a fresh worktree that file is therefore present on disk (checked
out from git) while the manifest is absent (gitignored), so `prior_items` is empty and the
file is classified as a **foreign overwrite**.

Reproduced on this branch, in a scratch repo outside the worktree (`uv run wfctl`, this tree):

*Face 1 — `post_create` (no TTY, no `--yes`; `.workmux.yaml:58` runs
`wfctl install-skills … || true`):*

```
The following existing file(s) will be overwritten (originals will be backed up,
restored by `wfctl uninstall-skills --agent base`):
  .agents/trackers/github.json
Proceed? [y/N]: Aborted.
```

Nothing is installed — no skills, no commands, no `.specify/`. The `|| true` in the hook
swallows the exit code, so the worktree comes up empty and says nothing, which is precisely
the failure mode `CLAUDE.md` calls out under *Worktrees* ("Neither failure announces itself").
The identical run with the `tracker` key removed from the main checkout's manifest exits 0 and
installs normally, so the abort is introduced by this commit and by nothing else.

*Face 2 — `/start-session` (`--yes`):* the prompt is skipped and the copy proceeds, so the
project's committed, customised `github.json` is replaced by the bundle's default on every
session start:

```
$ git -C wt2 status --porcelain
 M .agents/trackers/github.json      # `identity: "@me-custom"` gone, bundle default in its place
```

The original is backed up under `.wf-skills-backup/`, so this is recoverable rather than lost —
but it recurs on every install, it leaves a modified tracked file the user did not touch, and
in between `wfctl issue` runs against the wrong config. Worse, the path is now recorded in the
worktree manifest's `base` items, so `wfctl uninstall-skills` in that worktree will delete a
file that is committed to the repo.

Fix: the inheritance must set the recorded choice without also asserting "install this backend's
config over whatever is there". Keep the two meanings apart — e.g.

```python
inherited_tracker = False
if tracker is None and "tracker" not in manifest:
    ...
        manifest["tracker"] = tracker = inherited["tracker"]
        inherited_tracker = True
```

and at L2073 plan the copy only when it is not already present under an inherited choice
(`if tracker == "github" and not (inherited_tracker and tdest.exists())`). An inherited install
has no mandate to overwrite a project-owned file; an explicit `--tracker github` still does.

---

**WARNING  wfctl/cli.py:L1899-1906 — a custom tracker inherits the name but not its config, so
the bug the commit exists to fix is not fixed for non-`github` backends — and the worktree now
prints a warning telling the user to author a file they already authored.**

Only `github.json` ships in the bundle (L2073 comment). For any other backend the config is
hand-authored under `.agents/trackers/<name>.json`, and if the project has not committed it,
a worktree has no copy. Reproduced (main checkout: `tracker: "jira"` plus an untracked
`jira.json`; fresh worktree, `install-skills --yes`):

```
⚠ selected tracker 'jira' but no .agents/trackers/jira.json found — author it with /scaffold-tracker
$ wfctl issue list
⚠ Tracker 'jira' config missing or invalid (.agents/trackers/jira.json) — skipping 'list'.
```

`wfctl issue` still no-ops for the life of the worktree; the change converts a silent no-op into
a warned no-op. The manifest key alone is not the unit of inheritance — `_tracker.dispatch` and
`_load_tracker_config` both read the *config file* from `repo_root`, so the name without the file
buys nothing. Fix: when the value is inherited and `repo_root/.agents/trackers/<name>.json` is
missing, copy it from `<main>/.agents/trackers/<name>.json` (this is also the shape that makes the
BLOCKER's fix natural: inheritance fills a gap, it never overwrites).

---

**WARNING  tests/test_install_skills.py:L2903-2935 — the regression test covers only the path
that works, and omits the one that breaks.**

The test asserts the happy case (`"github"` and `None`) in a worktree whose `.agents/` is empty.
Four cases the diff changes behaviour for are untested, and the first is the BLOCKER:

- worktree where `.agents/trackers/github.json` already exists (committed) — abort / clobber;
- explicit `--tracker` in a worktree still wins over the inherited value;
- a worktree that has already recorded its own tracker is not re-inherited over;
- a main checkout with no `tracker` key leaves the worktree's key absent (and does not crash).

Per the review skill, a bug-fix diff is reviewed together with its regression test; this one
pins the fix but not its blast radius.

---

**NIT  wfctl/cli.py:L1892-1893 — the comment claims parity with `spec_root`, but the mechanism is
the opposite one.** `spec_root` *resolves* through the main checkout on every read
(`_paths._root_declaration`), so the main checkout stays authoritative forever. This *snapshots*
the value into the worktree manifest at install time; once written, `"tracker" in manifest` is
true and the worktree never consults main again. Switch the project's tracker later and every
existing worktree keeps the old one, with nothing (`doctor` included) reporting the divergence.
That may well be the right trade — the config file has to be local, so a read-time resolver alone
would not have worked — but the comment should say "inherited once, like a copy" rather than
"the same main-checkout fallback", or the next reader will assume the `spec_root` semantics.

**NIT  wfctl/cli.py:L1791-1795 — `--tracker none`'s help ("'none' to clear") is no longer true in
a worktree.** L2210 pops the key, and the very next non-interactive install re-inherits it from
main. Defensible (the choice is the project's), but it is now undocumented behaviour on a
documented flag.

**NIT  tests/test_install_skills.py:L2917-2919 — redundant local imports.** `json` and
`subprocess` are already module-level imports (L5, L8); only `os` needs the local import that the
file's other tests use.

**NIT  tests/test_install_skills.py:L2926 — the fixture nests the worktree inside the main
checkout** (`tmp_path / "wt" / "184-tracker"`, where `tmp_path` *is* the repo root). It resolves
correctly, but no real layout looks like this — `workmux` puts worktrees in a sibling tree, and
a worktree inside its own repo leaves an untracked directory in the main checkout's status.
`tmp_path.parent / "wt"` costs nothing and matches reality.
