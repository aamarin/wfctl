## BLOCKER — inheriting a tracker re-installs its config over a committed file

**Where.** `wfctl/cli.py:L1906`

```python
manifest["tracker"] = tracker = inherited["tracker"]
```

**Why it breaks.** `tracker` is not just "what gets recorded" — it is the same
local variable `--tracker <name>` sets, and it does double duty. At
`wfctl/cli.py:L2073`:

```python
if tracker == "github":
    tsrc = bundle_root / "agents" / "trackers" / "github.json"
    if tsrc.exists():
        ...
        plan.append((_BASE_LAYER, "tracker", trel, tdest, tsrc))
        if tdest.exists() and trel not in prior_items:
            foreign_overwrites.append((_BASE_LAYER, trel))
```

That block is what `test_install_skills_keeps_existing_tracker_config` relies on
to leave a hand-edited config alone: a plain re-install passes no `--tracker`, so
the config never enters the plan. Setting `tracker` from the inherited value
makes every first install in a worktree behave exactly as if the user had typed
`--tracker github`, so the config *does* enter the plan and gets copied over.

The destination exists in a worktree because `.agents/trackers/<name>.json` is
deliberately *not* gitignored — `test_install_skills_does_not_gitignore_tracker_config`
pins that, and `CLAUDE.md` states the rationale ("it's project-owned,
user-editable, and meant to be committed"). A committed file is checked out into
every fresh worktree. And `prior_items` is empty there, because the manifest is
gitignored and starts empty — the very premise of this fix. So the committed
config is classified as a *foreign* overwrite.

**Two failure modes, both verified.** Fake bundle, main checkout with a committed
customised `github.json` and `{"tracker": "github"}` in its manifest, fresh
`git worktree add`, `install-skills` invoked with empty stdin:

| run | `main` (baseline) | `cb4de1a` |
|---|---|---|
| `install-skills` (post_create: no TTY, no `--yes`) | exit 0, config preserved, tree clean | **exit 1** — `Proceed? [y/N]: Aborted.` |
| `install-skills --yes` (`/start-session`) | exit 0, config preserved, tree clean | exit 0, **config replaced** by the stock bundle copy, `M .agents/trackers/github.json` |

The first is worse than it looks: `post_create` is what installs the skills tree,
so the worktree comes up with none of it — the exact silent failure `CLAUDE.md`'s
Worktrees section describes ("the first sign is a session that has no
`/start-session` to run"). It fires even when the committed config is
byte-identical to the bundle's: `foreign_overwrites` tests existence, not content.
Any project that committed the file at all is affected.

The second replaces the project's verbs/`identity` with the defaults and leaves a
modified tracked file in every worktree's branch. The original is backed up under
`.wf-skills-backup/`, but with `--yes` nothing says so, and the next `wfctl issue`
runs the stock config rather than the project's.

**Why the suite is green.** This repo gitignores `.agents/` wholesale
(`.gitignore:12`, a hand-written line predating per-path ignoring), so its own
worktrees never have the file and never hit it. The new test's main checkout has
the manifest key but no config on disk, so it reproduces the same blind spot —
and its `assert (wt / ".agents" / "trackers" / "github.json").exists() is installs`
asserts that the copy *does* happen, pinning the defect.

**Recommended fix — put the fallback in the reader, not the writer.** The comment
at L1893 says this is "the same reasoning `spec_root` resolves on". `spec_root`
resolves *through* to the main checkout at read time; it copies nothing.
`_tracker.py` reads the key in exactly two places, `load_key_pattern:L131` and
`dispatch:L178`, both as `load_manifest(repo_root).get("tracker")`. One helper:

```python
def active_tracker(repo_root: Path) -> str | None:
    """The tracker this repo uses — its own manifest, then the main checkout's.

    Same fallback and same reason as `spec_root`: the manifest is gitignored, so
    a worktree's copy is empty at the moment the pipeline first runs there.
    """
    manifest = load_manifest(repo_root)
    if "tracker" in manifest:
        return manifest["tracker"]
    main = main_checkout(repo_root)
    return load_manifest(main).get("tracker") if main is not None else None
```

That is genuinely the `spec_root` shape. It touches no files, so there is nothing
to overwrite and no prompt to abort; it stays live rather than going stale; it
fixes `load_key_pattern` too; and it works in every worktree that *already
exists*, with no re-install — which the current fix cannot do, since those
worktrees have already had their (trackerless) install.

**Minimal fix, if the install-time copy is wanted anyway.** Stop the alias, and
make an inherited tracker seed-only:

```python
manifest["tracker"] = inherited["tracker"]   # not `tracker = ...`
```

and gate the copy so an inherited choice never overwrites and never lands in
`foreign_overwrites`, e.g. carry an `inherited_tracker` flag and use
`if tracker == "github" and not (inherited_tracker and tdest.exists())`.

## WARNING — `--tracker none` is reverted by the next install in a worktree

`--tracker none` pops the key (`wfctl/cli.py:L2208-2209`). In a worktree the key
is then absent again, so the very next install re-inherits it. Verified:

```
install-skills --tracker none   → manifest tracker: <ABSENT>, github.json absent
install-skills --yes            → manifest tracker: 'github', github.json present
```

`/start-session` runs the second command unattended, so the opt-out survives
roughly until the next session. The flag's help says "'none' to clear" and the
comment at L1922 says "`--tracker none` clears it and re-opens the question" —
in a worktree it now does neither, and says nothing about it.

Recording `manifest["tracker"] = None` in a worktree instead of popping would
make the opt-out stick, and it is the shape the interactive decline already uses
for the same reason ("the decline is a decision too"). If reverting is the
intended semantics — the tracker being a project-level choice that a worktree
may not override — then say so in the output rather than leaving it silent.

---

## WARNING — the inheritance is silent

`install-skills` narrates every other repo-level decision: `✓ wrote <manifest>`,
`✓ gitignored it in …`, `⚠ Will replace an install from …`. Adopting a project
config decision that the user was never asked about, and writing it into this
repo's manifest, is at least as worth saying. It prints once per worktree (the
condition is `"tracker" not in manifest`), so it is not noise. Under `--yes` this
is the only signal the user could get.

## The other passes

**Correctness (beyond the BLOCKER).** The guard `tracker is None and "tracker"
not in manifest` is right on both halves — verified that an explicit `--tracker
none` in a worktree is not overridden by the inherited value, and that a worktree
manifest already carrying the key does not re-read main. Both parametrised cases
of the new test behave as claimed: `"github"` inherits and installs, `None`
inherits and installs nothing, and `manifest["tracker"]` is `None` rather than
absent, so `_tracker`'s falsy check keeps the no-op quiet and the question
closed. Ordering is safe: `prior_items` / `prior_layer_items` are read before the
mutation, and `tracker` is in `_NON_LAYER_KEYS` so `_layer_keys` never sees it.
`main_checkout` correctly returns `None` in a main checkout, so this is
worktree-only. Malformed-main-manifest: `install-skills --yes` in a worktree now
exits 1 with an uncaught `JSONDecodeError` where it previously succeeded (`--yes`
short-circuits the only prior read of that file, at L1946); the project's stance
is that a malformed manifest should raise, but that was argued about *this*
repo's file, and here a broken file in a sibling directory takes down every
worktree's `post_create` as a traceback rather than the `[red]✗` shape.

**Security.** No new trust boundary in practice: `main_checkout` already refuses
anything but a standard `.git` layout, and `--tracker` already accepted an
arbitrary name out of the local manifest, which `_tracker.dispatch` turns into an
argv it executes. Substitution still builds tokens, never a shell string. What
does change by one hop is `CLAUDE.md`'s caution about a *committed*
`.wf-skills-manifest.json`: a `tracker` key in one now propagates into every
worktree with no prompt and (per the WARNING above) no message. Worth a sentence
in the Safety section, not a code change.

**Architecture.** Covered in the BLOCKER and the third-copy NIT. The one further
observation: the fix is write-time, so it only helps worktrees created *after*
this release — existing ones have already run their install and recorded nothing.
A read-time fallback would need no migration at all.

**Readability.** Names are fine; `inherited` for the main checkout's manifest
reads well. The comment block is dense with rationale, matching the file — the
one thing it asserts that is not true is the `spec_root` equivalence (see NIT).
`manifest["tracker"] = tracker = inherited["tracker"]` is a chained assignment
whose two targets mean different things; splitting them is what the BLOCKER fix
does anyway.

**Performance.** One extra `git rev-parse --git-common-dir` per install, and only
while the local manifest has no `tracker` key — once per worktree lifetime.
`install-skills` already shells out to git repeatedly. Not a concern.

**Over-engineering.** The block carries no speculative flexibility; at 8 lines it
is about as short as the write-time approach gets. The saving is in choosing the
other approach: `−16` in `cli.py` (block plus comments) for `+~6` in
`_tracker.py`.

wfctl/ tests/` → clean. `uv run mypy wfctl/` → clean. All three green; `wfctl
doctor` and `wfctl verify` deliberately not run (shared worktree).
