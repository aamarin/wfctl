## Findings

### BLOCKER `wfctl/cli.py:L1906` — the inherit re-triggers the bundle's tracker-config copy, so the first install in a fresh worktree of any project that commits `.agents/trackers/github.json` either aborts or clobbers the project's copy

`manifest["tracker"] = tracker = inherited["tracker"]` assigns the *variable*
`tracker`, not just the manifest key. Downstream, `tracker` does not mean "this
repo has a tracker" — it means **"the caller selected a tracker on this run"**,
and it is what drives the config install at L2072-2078:

```python
    # 'github' is the only tracker the bundle ships; copy just its config.
    if tracker == "github":
        ...
            plan.append((_BASE_LAYER, "tracker", trel, tdest, tsrc))
            if tdest.exists() and trel not in prior_items:
                foreign_overwrites.append((_BASE_LAYER, trel))
```

`.agents/trackers/<name>.json` is deliberately **not** gitignored by
`install-skills` — the path is never appended to `gitignore_targets`, and
`tests/test_install_skills.py:L63` pins that with the rationale *"Tracker config
is project-owned and meant to be committed, not managed as install-skills
output"*. So in a consumer project the file is a **tracked** file, and a fresh
worktree checks it out. The worktree's manifest is empty, so `prior_items` is
empty, so that existing file is classified as a *foreign overwrite*.

Reproduced both halves against this worktree's `wfctl` (temp repo in scratch, a
committed `.agents/trackers/github.json`, `tracker: "github"` in the main
checkout's manifest, `WFCTL_REPO_ROOT` pointed at a real linked worktree):

**a. `post_create` path — no `--yes`, no TTY (exactly the path #184 names):**

```
The following existing file(s) will be overwritten (originals will be backed up,
restored by `wfctl uninstall-skills --agent base`):
  .agents/trackers/github.json
Proceed? [y/N]:Aborted.
exit: 1
```

`typer.confirm(..., abort=True)` sits *before* the copy loop, so the entire
install is lost — no skills, no commands, no manifest. `.workmux.yaml:L81` ends
that hook with `|| true`, so nothing announces it. This is the failure
`CLAUDE.md` describes as "the first sign is a session that has no
`/start-session` to run" — strictly worse than the silent `wfctl issue` no-op
being fixed.

The same command on `main` (pre-change, identical fixture): exit 0, no prompt.

**b. `/start-session` path — `--yes`:**

```
config unchanged: False
config now: {"verbs": {"list": ["gh", "issue", "list"]}}     # bundle's stock copy
git status:  M .agents/trackers/github.json
```

The project's committed, hand-edited tracker config is replaced by the bundle's
stock one, leaving a **tracked** file modified in every fresh worktree (which
`wfctl verify`'s dirty-tree check then sees). The backup lands in that
worktree's own `.wf-skills-backup/` and dies with the worktree.

Note this fires for a *stock* committed `github.json` too — the foreign-overwrite
test is `dest.exists() and rel_dest not in prior_items`, content-independent. Any
consumer project that commits the shipped config is affected on every new
worktree. wfctl's own repo is the one place it cannot happen, because
`.gitignore` here ignores `.agents/` wholesale — which is why the suite stays
green and why the new test passes.

**Fix** — inheritance needs the manifest key; it only needs the *copy* when this
checkout genuinely has no config:

```python
            if "tracker" in inherited:
                manifest["tracker"] = inherited["tracker"]
                # Install the config only when this checkout has none. A worktree
                # of a project that commits `.agents/trackers/github.json` already
                # holds it, and the bundle's stock copy would land on the
                # project's own edits — or, without --yes, stop the install dead
                # on the overwrite prompt no hook can answer.
                if inherited["tracker"] == "github" and not (
                    repo_root / ".agents" / "trackers" / "github.json"
                ).exists():
                    tracker = "github"
```

The existing test still passes under this (in wfctl's own repo the config is
absent, so it installs). Do **not** fix it by widening what `--yes` skips or by
suppressing the prompt — the prompt is correct; what is wrong is planning a copy
the caller never asked for.

### WARNING `wfctl/cli.py:L1892-1898` (and the commit message) — the reasoning rests on a premise that is true only of this repo

The commit body says: *"A custom backend inherits its name but not its config —
`.agents/trackers/` is gitignored and only github ships in the bundle."* The
first clause is false in general. `.agents/` is gitignored **in wfctl's own
`.gitignore`**; `install-skills` never gitignores the tracker path in a consumer
project, on purpose. That premise is what hides the BLOCKER above: it predicts
"the worktree has no config", which is exactly backwards for the projects the
convention targets.

The new test inherits the same blind spot — it exercises only the
config-absent shape. **Fix:** correct the reasoning where it is recorded, and add
the missing regression case (worktree checkout already contains
`.agents/trackers/github.json` → install exits 0, prompts nothing, and leaves the
file byte-identical).

### WARNING `wfctl/cli.py:L1899-1906` — the inherit is silent, unlike every neighbouring write

A value the user never chose in this repo is written into this repo's manifest
with no line of output. One screen below, the `spec_root` block prints
`✓ wrote <path>` for its cross-checkout write, and `test_spec_root.py:L166` pins
that convention outright: *"a write elsewhere is never silent"*. Same class of
event here, read in the other direction — and it also silently closes a question
the user would otherwise have been asked interactively.

**Fix:** one line before the question block, e.g.
`ℹ tracker '<name>' inherited from <main>` (and, for the null case,
`ℹ no tracker — inherited that decision from <main>`).

### NIT `wfctl/cli.py:L2213-2218` — a custom backend inherits a name whose config the worktree may not have, and the remedy printed is wrong for that case

When the inherited name is not `github` and the config is not committed, the
end-of-run branch prints *"selected tracker 'linear' but no
`.agents/trackers/linear.json` found — author it with /scaffold-tracker"* on
every fresh worktree. The user already authored it — in the main checkout. The
manifest still records the name, so `wfctl issue` moves from
`ℹ No tracker configured` to `⚠ Tracker 'linear' config missing or invalid`
(both no-op, exit 0 — no functional regression, and the new message is the more
accurate diagnosis).

The commit acknowledges this as a deliberate trade. It stands, but if it is
closed later the shape is the same as the BLOCKER's fix: copy
`<main>/.agents/trackers/<name>.json` alongside the key when this checkout lacks
it, rather than naming a backend with no definition.

---

### NIT `wfctl/cli.py:L1893` — "the same main-checkout fallback" overstates the parity with `spec_root`

`spec_root` resolves *at read time* through `_paths._root_declaration`, so a
change in the main checkout propagates to every worktree immediately and no
install is needed. This copies *at install time*. Two consequences the comment
does not admit: a project that switches trackers leaves existing worktrees on the
stale value forever (`"tracker" not in manifest` is false thereafter), and
worktrees that already have a manifest only heal on their next install.

The choice is defensible — the tracker key is useless without the config file
physically present, which only an install can put there, and `/start-session`
re-installs on drift so existing worktrees do heal after a version bump. But
"the same fallback" invites a future reader to assume read-time resolution.
Suggest: *"the same main-checkout fallback `spec_root` resolves through, taken
here as a copy rather than a resolution because the key is useless without the
config file an install has to place."*

## Passes run, and what was checked

**1. Correctness (adversarial).** Traced `tracker` from the new assignment to
every downstream reader in `install_skills_cmd`: the plan copy (L2072), the
foreign-overwrite classification (L2077), the interactive question (L1911), and
the end-of-run manifest write (L2208-2218). Built a real linked-worktree fixture
and ran the changed code against it under three shapes — config absent (passes),
config committed + no `--yes` (aborts, BLOCKER a), config committed + `--yes`
(clobbers, BLOCKER b) — and re-ran the config-committed shape against `main`'s
`cli.py` to confirm the regression is new. Also checked, and found sound:
`--tracker none` still short-circuits the inherit (`tracker is None` is false)
and still pops the key; an inherited `None` correctly leaves `tracker is None` so
the end-of-run `elif` does not re-set it, while the key is already in `manifest`;
`_layer_keys` skips `tracker` via `_NON_LAYER_KEYS`, so a `null` value cannot
reach `manifest[key].get("items", …)`; a worktree that already recorded its own
choice (including a `null` decline) is not clobbered; the main checkout itself
never inherits, since `main_checkout` returns `None` there; a malformed main
manifest now raises out of `install-skills` in a worktree, which matches the
documented stance in `_manifest.load_manifest` and is not a finding.

**2. Security.** No new input parsing, no shell, no secrets. `_load_manifest` on
the main checkout reads a JSON file the user already owns; `main_checkout` is the
existing guarded resolver that refuses bare / separate-gitdir layouts precisely
so a neighbouring project's manifest cannot be read. The only value crossing the
boundary is a tracker *name*, and every consumer of it (`_tracker._load_tracker_config`)
joins it under `repo_root/.agents/trackers/` — a `../`-shaped name would escape,
but that is pre-existing and unreachable from this diff's inputs (the value comes
from a manifest the same user wrote). No finding.

**3. Architecture.** Compared against the two existing precedents:
`_paths._root_declaration` (read-time fallback for `spec_root`/`arch_root`) and
`_spec_root_question_answered` (L1673-1676, this-repo-then-main for a bool). The
new block is a third, inline copy of the same walk — acceptable at two lines and
consistent with the repo's ponytail bias, so not flagged as duplication; the
mechanism mismatch it implies is the last NIT. Also noted the asymmetry that
reads now come from the main checkout while an interactive *answer* in a worktree
is still written only to the worktree's dying manifest (unlike the `spec_root`
block below, which writes to `main_checkout(repo_root) or repo_root`) —
pre-existing, out of this diff's scope, and worth a follow-up issue rather than a
finding here.

**4. Readability & simplification.** Comment density matches the file's house
style and explains *why this shape*, not what the lines do — correct per
`CLAUDE.md`. Names (`main`, `inherited`) are apt. `manifest["tracker"] = tracker
= inherited["tracker"]` is the one place clarity was traded for brevity, and it
is where the BLOCKER lives: the chained assignment hides that the two names carry
different meanings. Dash style is the NIT.

**5. Performance.** One extra `git rev-parse --git-common-dir` per install, and
only while the key is unrecorded — the guard `"tracker" not in manifest` short-
circuits it from the second install onward, which matches the deliberate
lazy-`main_checkout` reasoning in `_root_declaration`'s docstring. Negligible.

**6. Over-engineering.** Nothing speculative, nothing to delete; no hand-rolled
stdlib, no new abstraction, no flag nobody sets. The change is 10 lines of code.
Lean already — the BLOCKER's fix adds ~5.

**Tests.** Read them first. The regression test is well-shaped: it names #184,
its docstring says why the test exists rather than restating the assertion, it
builds a real linked worktree (matching `test_spec_root.py:L148`'s established

worktree that already holds the config (the BLOCKER — must be added), no negative

recorded a tracker → not clobbered", and no case for "explicit `--tracker` wins
over the inherit". The last three are cheap and guard the block's three guard
conditions.
