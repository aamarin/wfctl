## BLOCKER

**BLOCKER  wfctl/_stall.py:L112 (`find_stall`) + wfctl/cli.py:L522 — a *finished*
story is reported as a stalled run.** → guard the verdict on there being a loop
to bound: return `None` when the trailing run's step is `complete`, or have
`build_report` pass `stall=None` when `next_command` is `None`.

`resume_cmd` records `step_name = report.current or "complete"` (cli.py:L636) and
appends a digest with it, so a completed branch writes `{"step": "complete", …}`
passes. After completion the artifacts by definition stop moving, so every
subsequent pass carries the same digest. Three of them — three orchestrate
invocations, or three `wfctl resume` calls across sessions on a branch waiting on
review — trip the bound. Reproduced:

```
LAST RESUME: {'ts': …, 'event': 'resume', 'step': 'complete', 'command': 'complete',
              'auto': False, 'digest': 'c3a4c9068432'}
implement    ●  1/1 done
⊘ complete ran 3 times and changed nothing
  unchanged: spec.md, plan.md, tasks.md
  this needs a person — re-running it has not moved the work
next: Story complete — open PR or run `/end-session`.
NEXT: None  STALL: {'step': 'complete', 'passes': 3, 'unchanged': [...]}
```

The console self-contradicts in adjacent lines, and orchestrate is worse:
SKILL.md:L123 puts the `stall` branch **ahead** of the story-complete branch, so
the agent displays "Stopped — `complete` ran 3 times and changed nothing" and
never reaches "Story complete — open PR". That inverts the record's own stated
consequence — "what makes an unattended run that stopped distinguishable from one
that finished" (`wfctl-counts-the-passes` § Consequences) — and it fires on the
success path, which is the most-travelled path this feature touches.

**BLOCKER  wfctl/_stall.py:L36 (`STALL_AFTER = 3`) + wfctl/cli.py:L524 — the
bound fires after the step has run *twice*, and the sentence says three.** → count
executions, not observations: compare against `STALL_AFTER + 1`, or subtract the
arrival pass when reporting (`passes - 1`). Whichever is chosen, the rendered
number and the threshold have to mean the same thing.

`_current_step_name` returns "the first step that still blocks" (`_pipeline.py:L272`),
i.e. the step *about to run*, and orchestrate's step 3 runs `wfctl resume` before
step 5 emits `EXECUTE_COMMAND`. So the pass recorded on arrival at a step is
taken before that step has run once. Verified: a repo staged at `implement 0/1`
records `{'step': 'implement', … 'digest': '41ccb404158e'}` with `implement` not
yet run.

The real sequence for the issue's own example is: arrival at `clarify` (pass 1,
digest d) → clarify runs, changes nothing (pass 2, digest d) → clarify runs,
changes nothing (pass 3, digest d) → stop. Two executions, reported as three.

That is not only a wording defect. `_stall.py:L33-35` gives the reason for three
rather than two — "a step legitimately taking a second run is common, and a bound
that fires on the first repeat would stop working automation" — and as built the
bound *does* fire on the first repeat. The analyze scan reached the same reading
independently: "the third runs and the run then stops"
(`docs/architecture/scans/332-analyze.md`, finding B). FR-003 says three
consecutive passes, and the spec's Key Entities define a pass as "one traversal of
a single pipeline step by a run" — a traversal, not a look at the log before one.

If the author's definition of pass is the orchestrate loop iteration rather than
the traversal, then the threshold is defensible and only cli.py:L524's "ran N
times" and SKILL.md:L124's "ran {stall.passes} times" are wrong. I do not think
that reading survives the spec's own wording, but the author has the context to
overrule it — what cannot stand is the two meanings coexisting.

## WARNING

**WARNING  wfctl/_stall.py:L118-136 — a new sitting on a parked branch stops on
its first pass, and the docstring claims the opposite.** → break the run at a
`start` event: keep the session boundary in `_resume_events`' output and stop the
reverse walk when it is crossed.

`find_stall`'s docstring says "a branch resumed days later … is not the same
situation as a step that cannot get out of its own way", and reading from the end
does not deliver that. Two unchanged passes yesterday plus today's arrival pass
(same step, same digest, because nothing moved overnight) is a run of three, and
today's session halts before the step has been entered once. `/start-session`
writes a `start` event into the same log, so the boundary is on disk and free to
read; `_resume_events` filters it away. This is the spec's fourth Edge Case, and
the failure direction the design record forbids.

**WARNING  wfctl/cli.py:L680-684 + wfctl/_stall.py:L122 — the pass record carries
no branch, so under a shared state dir it counts another branch's passes.** → append
`branch=branch` beside `step`, and filter on it in `find_stall`, exactly as
`_last_resolved` (`_session.py:L369-373`) does for `notify-resolved`.

`resolve_agent_dir` is per-branch only while `WFCTL_STATE_DIR` is unset
(`_paths.py:L672-676`, README.md:L755). Under an override the log is shared, which
is precisely how a grant made on a feature branch leaked to the trunk
(`tests/test_notify_declined.py:L150`); `start` has carried `branch=` since
(cli.py:L316). The new `resume` field does not. Mixed branches usually break the
trailing run and merely delay the bound, but epic sub-issues are the sharp case:
`resolve_spec_dir`'s grouping-map leg resolves several branches to *one* spec dir,
so their digests are identical and their step names often are too — three passes
across three sub-issue branches then read as one stalled step.

**WARNING  tests/test_stall.py — nothing exercises the write side, so the field
name is only asserted against itself.** → add one test that runs `wfctl resume`
through `CliRunner` and asserts the appended event carries `digest`, then a second
`resume` after an artifact edit and assert the digest moved.

Every log in this file is hand-seeded by `_pass()`, which hardcodes `"digest"`.
Rename the key in cli.py:L681-684 and all fourteen tests still pass while the feature
is inert. It does work today — I confirmed the written event carries
`'digest': '41ccb404158e'` — but nothing guards it. The spec's own Validation
Strategy makes this point: "A test asserting the bound fires, with no run that
watched it fire, does not validate this feature." The same gap covers the console
path end-to-end (`resume` ×3 → `status` reports a stall), which is one test.

**WARNING  wfctl/_pipeline.py:L535 — a branch with no resolved spec dir is
outside the bound, and nothing records that.** → either say so in
`332-progress-is-measured-in-artifacts` § Consequences beside the `decompose`
carve-out, or note it in `_stall.py`'s module docstring.

`evidence_digest` is `None` when `ev is None`, and `ev` is `None` whenever
`spec_dir` does not resolve — every pass before `brainstorm` has produced a
feature dir, and every pass on a sub-issue branch no grouping map has claimed
(`speckit-orchestrate` step 1 treats that as an answer, not a gap). Those passes
record no digest and `find_stall` never compares them, so a loop wedged there is
unbounded. That is the right behaviour — there is nothing to compare — but the
design record documents only the `decompose` hole, and this one is wider.

## What holds up

- The level-3 record earns its place: digesting `Evidence` bytes rather than the
  rendered step line is the right call, and the `clarify`-renders-identically
  argument is checked, not asserted.
- The test file is aimed at the failure that matters — five of eleven unit tests
  are false-positive cases — and the docstrings name why each exists.
- `stall` present-and-null rather than omitted (cli.py:L446), for `notify`'s
  reason, with a test pinning it.
- The separator between artifacts (`_SEP`), with the test that would fail without
  it.
- No new state file; the digest rides an event that already existed (FR-009).

net: −4 lines possible (`Stall.unchanged`, the `TypeError` arm). Lean already.

**Verdict: Request changes** (2 blockers, 4 warnings). The design is right and
the code is close; the two blockers are both off-by-one in what a "pass" counts —
one at the end of the pipeline, one at the start of each step.
