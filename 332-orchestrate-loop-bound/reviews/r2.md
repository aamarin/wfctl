## Findings

### BLOCKER — `_stall.py:112` / `cli.py:680` — a finished story reports as a stall

`resume` records `step_name = report.current or "complete"` and, at story
complete, still records a digest (the feature dir resolves, so
`evidence_digest` is set). Three orchestrate invocations after the pipeline
finishes therefore produce three `resume` lines with `step: "complete"` and one
digest, and `find_stall` returns a `Stall` for the sentinel.

Reproduced on a scratch repo with every artifact complete, three `wfctl resume`
calls, then `wfctl status --json`:

```json
"current": null,
"next_command": null,
"stall": { "step": "complete", "passes": 3,
           "unchanged": ["spec.md", "plan.md", "tasks.md"] }
```

`speckit-orchestrate/SKILL.md` step 5 checks `stall` **ahead of** the
story-complete branch, so a finished story is announced as
"Stopped — `complete` ran 3 times and changed nothing … this needs a person"
instead of "Story complete — open PR or run `/end-session`." That inverts the
one distinction the record says the feature exists to make: a run that stopped
versus one that finished. `wfctl status` prints the ⊘ block directly above
`next: Story complete — open PR…`, i.e. two contradictory verdicts in one
screen.

Cheapest fix: don't record a digest when there is no command — the branch
already exists in `resume` for "no feature directory", and "no step" belongs in
it. Belt and braces: `find_stall` returns `None` when `step == "complete"`.
Either way this needs a test; the suite has none for the completed-story case.

### BLOCKER — `_stall.py:112` — the count is of observations, not executions

A `resume` line is written once per *orchestrate invocation*, not once per
*step execution*. Two consequences, both in the direction the design record
says the feature can least afford:

1. **Off by one.** In the loop, orchestrate runs `resume` *after* a command
   finishes and *before* it emits the next `EXECUTE_COMMAND`. So a run of three
   `(step, digest)` lines spans only two executions of that step — the first
   line was written by the pass that *entered* the step. The stop therefore
   fires on the second unproductive run, and the sentence says three. This
   contradicts FR-003 ("after three consecutive passes … that made no
   progress"), FR-005/SC-003 (the reported count is wrong), and the record's
   own threshold argument — "a bound that fires on the first repeat would stop
   working automation" is exactly what it does.
2. **Any three invocations will do, even with zero executions.** Reproduced: on
   a scratch repo I ran `wfctl resume` four times (two collapsed into one second
   — see NIT below) and never executed `/speckit.specify` once. `wfctl status`:

   ```
   specify      ▶  missing: Validation Strategy  ← current
   ⊘ specify ran 3 times and changed nothing
   ```

   `wfctl resume` is documented in `using-wfctl/SKILL.md` as "the thing to run
   after any spec/plan/tasks artifact changes underneath you", and six skills
   end by invoking orchestrate, which runs `resume` at step 3 on every
   invocation — including invocations that stop without emitting anything. So a
   person or agent that looks at a branch three times poisons the log, and the
   next real loop refuses to run a step that has never run. That is a false stop
   of automation, unattended, looking like the feature working.

Fixes, cheapest first:
- Count only passes carrying `auto: true`. The field is already in the event,
  and a pass where the loop did not (and would not) execute anything is not a
  pass through the step. This also fixes WARNING 3 below.
- Better: count the execution rather than the observation — an event written
  when a command is actually emitted.
- Whatever else changes, the rendered sentence must stop claiming a number of
  executions the log cannot support ("3 consecutive passes saw no change" is
  true; "ran 3 times" is not).

### WARNING — `_stall.py:41,52` / `cli.py:528` — `unchanged` names files that do not exist

`Stall.unchanged` is always `COVERED`, so the report claims three artifacts did
not change regardless of whether any of them exists. From the same scratch run,
one `wfctl status` screen:

```
artifacts written          ○  missing plan.md, tasks.md
⊘ specify ran 3 times and changed nothing
  unchanged: spec.md, plan.md, tasks.md
```

FR-005 asks for "what did not change". Fix: name the artifacts that actually
exist (`build_report` holds `ev` and can pass them), or reword to "no change in
spec/plan/tasks", which claims only what the digest covers.

### WARNING — `speckit-orchestrate/SKILL.md:123` — the stall branch swallows `reason`/`remedy`

The stall branch stops without displaying the current step's `reason` or
`remedy`; only the `auto: false` branch does that, and the stall branch runs
ahead of it. A blocked step keeps the same digest for exactly as long as the
person has not yet supplied the missing thing, so the third look at a blocked
step replaces "missing: Validation Strategy" plus its remedy with "re-running it
has not moved the work" — the actionable half is dropped at the moment it is
most needed. Fix: display `reason`/`remedy` inside the stall branch too, or stop
counting `auto: false` passes (BLOCKER 2's first fix covers this).

### WARNING — no way back once a stall is recorded

The verdict clears only when the bytes of `spec.md`/`plan.md`/`tasks.md` change.
A person who unblocks the step any other way — filling issue keys in
`delivery.md`, recording a verification, answering in the tracker, writing code
for `implement` without ticking a task — leaves the branch permanently stalled:
every later `resume` appends another matching line and the count only grows.
Nothing in the SKILL, the two records, or the CLI help tells them how to hand
the work back. FR-006 hands the work to a person; nothing specifies how the
person hands it back. Fix: name the reset (in the skill and in
`wfctl-counts-the-passes`), and/or break the run at a session boundary.

### WARNING — `_stall.py:112` — the docstring claims a distinction the code does not make

> Read from the end, because only consecutive passes count: a branch resumed
> days later … is not the same situation

Nothing in the code distinguishes it. `_resume_events` filters to `resume`
events only, so an intervening `start` — a new session, days later — does not
break the run, and no timestamp gap is considered. A fresh session on a branch
whose last two passes match is stopped on its first pass, and told the step
"ran 3 times" across a week. spec.md's edge case ("earlier passes … belong to a
different sitting. Consecutive passes are what count") reads as the code being
wrong rather than the prose. Either break the run on a `start` event / a
timestamp gap, or delete the claim.

### WARNING — the false-stop half of the acknowledged gap is not recorded

`332-progress-is-measured-in-artifacts` names the assumption that the three
artifact texts cover every step whose progress matters, and records only one
consequence: "a stall there is not detected". The other consequence is the
serious one — a step making real progress *outside* those three files is
declared stalled. `decompose` (automatic) filling `delivery.md` keys pass by
pass changes none of the three; `implement` writing code without ticking a task
changes none of the three. Both are false stops, which the record elsewhere
calls the failure it can least afford. Add the direction to Consequences, and
consider whether `decompose`'s `delivery.md` belongs in the digest.

### WARNING — coverage: the write side of the bound is untested

`tests/test_stall.py` tests `find_stall` and `digest` thoroughly and the console
well, but nothing asserts that `wfctl resume` writes `digest` into the event —
the single field the whole feature depends on. If `evidence_digest` were always
`None`, the bound would silently never fire and all 1532 tests would still pass.
Likewise the *stalled* JSON payload shape is untested; only the null case is
asserted, and `speckit-orchestrate` branches on `stall.step` / `stall.passes` /
`stall.unchanged` by name. (I confirmed by hand that `resume` does write it —
`"digest": "07952f09fd20"` — so this is a coverage gap, not a defect.) Add: a
CLI test that runs `resume` and reads the appended line, and one asserting the
stalled payload's keys.

### NIT — `cli.py:524` — `report.stall.step` printed without `escape()`

Two lines below sits a comment explaining why repo-supplied strings are escaped
here. `step` comes off a JSON file on disk that `find_stall` type-checks but
does not validate, so a line carrying `[/bold]` in `step` raises
`rich.errors.MarkupError` and takes down `wfctl status` — the opposite of
FR-011's "a damaged record slows the bound rather than halting a run".
Confirmed the raise. One `escape()` call.

### NIT — `_stall.py:41,52` — `unchanged` is a constant dressed as a field

`Stall.unchanged` is only ever `COVERED`; `cli.py` then `list()`s it back. yagni:
drop the field, have both renderers read `_stall.COVERED` — unless WARNING 3 is
fixed by computing it, in which case the field earns its place. net −4.

### NIT — `_pipeline.py:531` — the comment is false on the `resume` path

"Read from the event log, which `resume` has already written this pass into" —
`resume` builds the report *first* and appends afterwards, so its own report is
always one pass behind. True for `status`, which is the reader that matters;
reword so the next reader does not trust it on the other path.

### NIT — `_stall.py:100` — unreachable `TypeError`

`splitlines()` yields only `str`, so `json.loads` cannot raise `TypeError` here.
Drop it and keep `json.JSONDecodeError`.

### NIT — `_stall.py:105` — the same-`ts` collapse is wider than legacy pairs

Two records that both *lack* `ts` compare equal (`None == None`) and collapse.
And two genuine current-format passes landing in the same second collapse too —
observed in my scratch run, where two of four `wfctl resume` calls shared
`22:28:47` and counted as one. Both undercount, which is the chosen direction,
but the missing-`ts` case is worth a guard:
`record.get("ts") is not None and out[-1].get("ts") == record.get("ts")`.

### NIT — `cli.py:515-521` — comment orphaned by the insertion

The new stall comment block was inserted between the `next:` print and the
comment that belonged to it ("The completion sentence rather than a second
spelling of it…"), which now reads as a preamble to the stall block. Move it
back down beside its line.

### NIT — `tests/test_stall.py:190` — unused `monkeypatch` parameter

Also, the three CLI tests import `CliRunner` and `app` inside their bodies while
the rest of the file imports at module level; no reason is given for the
difference.

### NIT — the running exemplar is a step the loop never auto-enters

`_stall.py`'s module docstring, the design record, and several test docstrings
use `clarify` as the step the loop cannot get out of. `clarify` is
`_REVIEW_REQUIRED`, so `next_step_content` reports `auto: false` and orchestrate
already stops there — a `clarify` stall can only accumulate from manual
`resume`/orchestrate invocations (see BLOCKER 2). The steps this bound actually
guards are the `_AUTOMATIC` ones — `implement` above all, then `specify`,
`plan`, `tasks`, `decompose`. One sentence saying so would stop the next reader
concluding the bound covers the clarify-needs-a-person case.
