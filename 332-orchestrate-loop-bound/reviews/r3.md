BLOCKER  `wfctl/_stall.py`:L36 + `wfctl/cli.py`:L524 — **a counted "pass" is a
`resume` line, not a pass through the step, and the two differ by one.**
`speckit-orchestrate` runs `wfctl resume` at step 3 and emits `EXECUTE_COMMAND`
at step 5, and the executed command re-invokes orchestrate at its end
(`speckit-clarify/SKILL.md`:L225, `speckit-implement/SKILL.md`:L209). So the
first `resume` line naming step X is written *before X has ever run*, and its
digest already equals the one X will leave behind if it changes nothing. Over
k consecutive unproductive executions of X the log holds k+1 matching lines:

```
resume(step=clarify, digest=d)   ← X has not run yet
EXECUTE clarify                  ← execution 1, changes nothing
resume(step=clarify, digest=d)
EXECUTE clarify                  ← execution 2, changes nothing
resume(step=clarify, digest=d)   ← run == 3, stall fires
```

Three consequences, all real:
1. The bound fires after the step ran **twice**, not three times. FR-003 says
   "after three consecutive passes through the same step", and `STALL_AFTER`'s
   own comment justifies 3 as *not* firing "on the first repeat" — which is
   exactly what it does. `data-model.md` worries about the legacy double-write
   because "the bound fires a pass early"; this ships that same early fire
   structurally.
2. The sentence a person reads — "`clarify` ran 3 times and changed nothing" —
   states a count that is false. SC-003/FR-005 make naming what happened half
   the feature.
3. Reproduced: three bare `wfctl resume` calls with **no step executed at all**
   yield `stall: {"step": "implement", "passes": 3, ...}` and the console line
   "implement ran 3 times and changed nothing". `using-wfctl/SKILL.md`:L21
   documents `resume` as a command a person runs directly, so this is reachable
   outside the loop, and once it fires orchestrate refuses to run the pipeline
   at all (the `stall` branch precedes `auto`) until one of the three artifacts
   changes. There is no other escape hatch in the code or in the skill.

→ Fix: count executions, not observations. Either raise the run threshold to 4
(one entry line + three executions), or report `passes - 1` and say so, or —
better, because it also fixes (3) — record the digest only on a `resume` that
follows an execution, e.g. by having orchestrate's pre-execution read be
`status` alone. Whichever is chosen, the rendered sentence and `data-model.md`'s
`passes` definition have to agree with FR-003 on what a pass is.

BLOCKER  `wfctl/cli.py`:L636 — **a finished story reports a stall.**
`step_name = report.current or "complete"`, and `report.evidence_digest` is
still computed and appended when there is no next command, so three `resume`
calls on a complete branch produce a stall on the pseudo-step `complete`.
Reproduced verbatim:

```
⊘ complete ran 3 times and changed nothing
  unchanged: spec.md, plan.md, tasks.md
  this needs a person — re-running it has not moved the work
next: Story complete — open PR or run `/end-session`.

stall: {'step': 'complete', 'passes': 3, ...}  next_command: None
```

`speckit-orchestrate/SKILL.md` step 5 checks `stall` **before** the story-complete
branch, so an agent in this state displays "Stopped — `complete` ran 3 times and
changed nothing" and stops, on a story that finished. That inverts the one thing
`wfctl-counts-the-passes` says the payload must preserve: "what makes an
unattended run that stopped distinguishable from one that finished". It is also
a false stop, the direction `332-progress-is-measured-in-artifacts` explicitly
chose against.
→ Fix: do not record a digest where `report.next_command` is None (the `resume`
event already carries `command: "complete"`, so `_resume_events` could also drop
those lines), and/or move the story-complete branch above the stall branch in
the skill. The first is the real fix; the second alone still leaves `wfctl
status` printing ⊘ on a finished branch.

WARNING  `wfctl/_pipeline.py`:L534 — **the verdict is stale the moment the
artifacts move.** `find_stall` reads only the log; `build_report` computes the
current pass's `evidence_digest` two lines below and does not use it. Reproduced:
after a person edits `spec.md` to resolve the thing the step was stuck on,
`wfctl status` still prints "implement ran 3 times and changed nothing /
unchanged: spec.md, plan.md, tasks.md" — a claim now false about the files on
disk — until some later `resume` writes a new digest. The loop recovers (its
step 3 resumes before its step 4 read), so this is what a *person* is told, on
the exact screen they look at after doing the work the stall asked for.
→ Fix: `find_stall(agent_dir, current=report_digest)` returning `None` when the
current digest differs from the trailing recorded one. The state is already in
hand; it costs a parameter.

WARNING  `wfctl/cli.py`:L681 — **the `resume` event carries no `branch`, and
this reader does not filter by one.** `resolve_agent_dir` honours
`WFCTL_STATE_DIR`, and a state dir shared across worktrees holding every
branch's events is treated as a live hazard in this same codebase —
`_pipeline._corrected_grant` names it ("reading the newest regardless of whose
it was is how one feature's grant answered for another"), which is why
`notify-grant` records `branch=` (`_session.py`:L313) and `resolved_notify`
filters on it. `find_stall` takes the trailing lines regardless of branch:
interleaved branches mostly *mask* a stall, and where two branches sit on the
same step with all three artifacts absent the digest is the same constant for
both, which fabricates one.
→ Fix: append `branch=branch` in `resume_cmd` (it is already in scope) and pass
the branch into `find_stall`, skipping lines that name another. Lines written
before the field exists carry no digest anyway on the first pass, and a missing
`branch` can be read as "this branch" for the legacy case.

WARNING  `tests/test_stall.py` — **the populated `stall` payload is never
asserted.** `test_the_json_payload_carries_the_verdict_as_null_when_progressing`
pins the null case; the console test pins the prose. Nothing asserts the shape
orchestrate actually branches on — that `stall.step`, `stall.passes` and a JSON
*list* `stall.unchanged` are present and correct when a stall exists. That is
the contract, and a serialization change (say `asdict`, leaving `unchanged` a
tuple) would pass the suite. Nothing covers `resume` writing the `digest` field
either, so the event shape `data-model.md` specifies is untested end to end.
→ Fix: one test asserting the non-null payload body, one asserting the `resume`
event line carries `digest`.

NIT  `wfctl/_stall.py`:L60 — the digest is over `_quoted_out(spec_md)` /
`_quoted_out(plan_md)`, not the file bytes: fenced blocks and inline spans are
blanked before `Evidence` holds them (`_predicates.py`:L937,L940). An edit
confined to a fenced block — plan.md's structure block is the obvious one —
reads as no progress, while the report names the whole file as "unchanged".
Defensible (it is what the level-3 record chose), but the rendered word
overstates it. → say "unchanged (outside quoted blocks)", or note it in the
`digest` docstring, which currently says "the artifact text this inference
already read" without saying what that read dropped.

NIT  `wfctl/_stall.py`:L55 — `yagni:` `Stall.unchanged` is a dataclass field
whose value is `COVERED` in every instance that can exist, since the digest
covers exactly those three. → drop the field and read `COVERED` at the two
render sites; the constant is already exported for that purpose.

NIT  `wfctl/cli.py`:L446 — `shrink:` the hand-built dict is

NIT  `wfctl/cli.py`:L522 vs `speckit-orchestrate/SKILL.md`:L123 — the stall

NIT  `wfctl/cli.py`:L645-660 — `next-step.md` is written with no stall marker,

why this is a NIT and not a WARNING.

NIT  `docs/architecture/design/332-progress-is-measured-in-artifacts.md`
§ Assumed — the `decompose` claim is backwards. A step whose evidence lives
outside `spec/plan/tasks` leaves the digest *unchanged*, so a stall there is
detected (spuriously easily); what is invisible is its *progress*, which means
the exposure is a false stop on a step doing real work, not a missed one. The
same paragraph's neighbouring assumption gets the direction right, so this reads
as a slip rather than a position. → restate as: `decompose`'s progress is
outside the fingerprint, so consecutive productive passes through it read as a
stall.

**Verdict: Request changes** (2 blockers, 4 warnings).

Both blockers are one condition each and neither touches the shape of the
design: the ownership decision and the artifact-digest decision are the right
calls and the module is well argued. What is wrong is the unit being counted —
`resume` invocations rather than step executions — which makes the bound fire a
pass early, makes the reported count false, and lets a finished story and three
idle `resume` calls both present as stalls.
