## WARNING 1 — the guard lost its UnicodeDecodeError handling

`wfctl/_entry.py:29`, `wfctl/cli.py:3638`, dead arm at `wfctl/_hook.py:73`.

On `main` the read sat *inside* the try:

```python
try:
    payload = json.loads(sys.stdin.read() or "{}")
except (json.JSONDecodeError, UnicodeDecodeError):
    return
```

`UnicodeDecodeError` is in that tuple precisely because `sys.stdin.read()` — not
`json.loads` — is what raises it. The refactor split the two: the read moved up
into `_entry.main()` (and `cli.hook_worktree_guard_cmd`) with no handler, while
the `UnicodeDecodeError` arm stayed behind in `_hook.worktree_guard()`, where it
is now unreachable — `json.loads` on a `str` cannot raise it.

Reproduced against the built console script in this worktree:

```
$ printf '\xff\xfe{"tool_input":{"command":"ls"}}' | .venv/bin/wfctl hook worktree-guard
Traceback (most recent call last):
  File ".venv/bin/wfctl", line 10, in <module>
    sys.exit(main())
  File "wfctl/_entry.py", line 29, in main
    raise SystemExit(worktree_guard(sys.stdin.read()))
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xff in position 0
EXIT=1
```

Exit 0 on `main`, silently. This is the exact outcome `_hook.py`'s own docstring
says the block exists to prevent ("a traceback from it reaches the agent as a
hook error on work that had nothing wrong with it"), and the brief's constraint
was that exit codes are unchanged. `cli.py:3578` (the `Stop` hook) still uses the
house pattern, so the guard is now the one hook that has broken away from it.

**Not a BLOCKER** because it fails in the safe direction: exit 1 is non-blocking
for `PreToolUse`, so the Bash call still proceeds and nothing is wrongly allowed
or lost. It is noise on the agent's screen, not a hole. I also could not
construct a realistic trigger on this platform — macOS CPython uses UTF-8 for
stdio even under `LC_ALL` unset + `PYTHONCOERCECLOCALE=0` (checked:
`sys.stdin.encoding == 'utf-8'`), so it takes genuinely invalid bytes in the
payload. But the previous code handled it deliberately and this one doesn't.

Fix — put the read where the try already is, so the surviving arm goes live again:

```python
# _hook.py
def read_stdin() -> str:
    """Undecodable bytes describe no command. Same failure direction as a
    payload that will not parse."""
    try:
        return sys.stdin.read()
    except (UnicodeDecodeError, OSError):
        return ""
```

then `worktree_guard(read_stdin())` at both call sites. `stdin_text or "{}"`
already turns `""` into the allow path.

## WARNING 2 — `cli._worktree_roots` is dead, and its docstring says it isn't

`wfctl/cli.py:3405`. Its new docstring: *"This name stays because it is what the

```

wfctl/cli.py:3405:def _worktree_roots(cwd: str) -> tuple[str, list[str]]:

The definition is the only hit in the whole repo. `hook_worktree_guard_cmd` now

## NIT 1 — `monkeypatch` is the house convention

`tests/test_guard_entry.py:65-71` and `:86-94` swap `hook.worktree_roots` by hand
under try/finally, with `lambda cwd: (calls.append([cwd]), ("", []))[1]`. 21 test
files in `tests/` use `pytest.MonkeyPatch`. The tuple-index lambda is the
"clever trick that needs a mental pause" the review skill's readability pass
names, and it forces two `# type: ignore[assignment]`s. The two copies also
disagree for no reason — one appends `[cwd]` (a list), the other `cwd` (a str).

```python
def fake_roots(cwd: str) -> tuple[str, list[str]]:
    calls.append(cwd)
    return "", []

monkeypatch.setattr(hook, "worktree_roots", fake_roots)
```

# What I checked and found sound

## Pass 1 — correctness

**The `"/" not in command` early-out is provably decision-preserving.**
`_guard.refusal` returns non-`None` only through `trespass`, which requires
`_ABS_PATH.findall(segment)` to be non-empty. `_ABS_PATH` is
`r"/[^\s'\"`;|&<>()]+"` — it cannot match a string containing no `/`. So for
every command the early-out short-circuits, `refusal()` on `main` was already
returning `None` unconditionally. Not "no test covers it": there is no input
class where the two differ. Acceptance criterion (b) holds by construction, not
just by the suite passing.

**It opens no new bypass.** Every escape a `/`-free command has — relative paths,
`cd ..`, a path in a variable, `$(…)` — was already in `_guard`'s documented
"What this cannot catch" list and is unchanged. The check is strictly cheaper
than, and implied by, the regex it guards.

**Refusal text is byte-identical.** `_guard._message` is untouched, and the
end-to-end output above matches the README sample verbatim.

**Exit codes.** Fast path: 2 with the message on stderr, 0 otherwise — verified
live. `SystemExit(int)` from `main()` reaches the setuptools stub as
`sys.exit(main())`; stderr is flushed at interpreter exit (confirmed, the message
appears). Slow path still raises `typer.Exit(2)`.

**Argv match is exact, not a prefix.** `sys.argv[1:] == ["hook",
"worktree-guard"]` means `--help` and any future flag fall through to typer
rather than being silently ignored — confirmed by running the console script with
`--help` (exit 0, help printed, no stdin hang). Shell decoration in a
`settings.json` entry (`2>/dev/null || true`, an absolute path, `uv run`) does
not change `argv[1:]`, so the installed command string in README.md:435 still
takes the fast path.

**`wfctl/__init__.py` is empty**, so `from wfctl._hook import …` drags in nothing
beyond `json`/`sys`.

## Pass 2 — security

`_entry` and `_hook` add no new input surface: the same stdin payload, the same
`isinstance` checks on `payload`, `tool_input` and `command`, in the same order.
`payload.get("cwd")` still flows into `git -C` as a list argument to
`subprocess.run` (no `shell=True`), unchanged. No secrets, no new file writes.
The guard is a correctness rail, not a security boundary, and its threat model
(documented in `_guard`'s docstring) is untouched.

## Pass 3 — architecture

`_entry → {_hook, cli}` (same band), `_hook → _guard` (downward), `cli → _hook`
(same band). No cycle; `_hook` does not import `cli`.
`docs/architecture/views/current-state.md`'s ```layers block was updated to
`surface cli _entry _hook`, and
`tests/test_architecture_view.py::test_every_module_has_a_band`,
`::test_only_the_declared_edge_runs_upward` and
`::test_the_private_crossings_are_the_four_the_view_draws` all pass — so the view
is mechanically consistent with the new module set, not just narratively. The
view's "what this costs" paragraph (the `--help` membership proxy stops working)
is an honest admission and belongs there.

The dispatcher-over-second-console-script choice is well argued in
`_entry.py`'s docstring and is the right call given README.md:435 and the
already-deployed `.claude/settings.json` entries.

## Pass 4 — readability

Docstrings are dense with *why*, matching the house style. One factual error
(WARNING 2). The `hook_worktree_guard_cmd` docstring correctly explains that it
is now the typer-visible shell for a decision that lives elsewhere.

## Pass 5 — performance

Measured on this machine, warm, 10 invocations × 3 runs of the built console
script:

| path | per call |
|---|---|
| fast path, command has no `/` | ~27 ms |
| fast path, command names a path (2 git subprocesses) | ~58 ms |
| old `cli:app` route, same payload | ~105 ms |

Acceptance criterion (a) holds: `-X importtime` on the no-path branch shows
`wfctl._entry` (0.7 ms) + `wfctl._hook` (2.0 ms, of which `json` is 1.7 ms) and
**no** `typer`, `rich`, `wfctl._guard` or `re` — the `from wfctl import _guard`
sits below the `"/"` check, so a `ls -la` pays neither the regex module nor the
subprocesses. Numbers are consistent with the 81.7 → ~34 ms claim quoted in
`_hook.py` and `current-state.md`; criterion (c) is a PR-body matter I can't
check from here.
