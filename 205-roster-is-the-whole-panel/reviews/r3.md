WARNING  SKILL.md:L249 — the new check reports a legitimate free panel member as `UNDISPATCHED`; nothing says the reviews directory is the roster's alone.

  Step 1 says "Reviews go in `$FEATURE_DIR/reviews/`, one file per reviewer".

  The fence's `case " r1 r2 r3 "` is the roster *of dispatched ids*, but the

  panel members are collected out of band and never filed under `reviews/`, or
  say the case list carries them too (`" r1 r2 r3 codex "`). One sentence beside
  the fence; the current text says neither.

WARNING  SKILL.md:L327 — the rule's stated enforcement ("visible to anyone reading the table") does not work for the source it just added.

  The claim is that a name in the Reviewer column that is neither on the roster
  nor a comment "is visible to anyone reading the table — which is the only place
  it is visible at all." But the roster line (L334) carries dispatched ids only.
  So a bot comment in the Reviewer column and a stranger in the Reviewer column
  look identical to a reader of the table: both are names absent from the roster
  line. The rule is two-sourced and the artifact records one source, so the
  inspection it describes cannot distinguish the legal case from the illegal one.

  This is the shape `a-rule-is-expressed-as-a-check` is about — the violation *is*
  visible in an artifact the work produces, and the remedy as written doesn't make
  it so. Fix: have the roster line carry the free members explicitly, e.g.
  `roster: r1 ✓  r2 ✓  r3 ✓  + codex (review comment on the PR)`, and say that a
  Reviewer name absent from that line is the finding.

  (The notification-channel rule *is* correctly left as prose — the skill says so
  in as many words, "Nothing is on disk for a check to look at", and the record's
  test is whether an artifact exists. That half passes; this half does not.)

WARNING  test_review_fanout_skill.py:L243 — the zsh assertion in `test_the_undispatched_check_survives_an_empty_reviews_directory` is vacuous for the failure its own docstring names.

  The docstring says the empty directory "is where a bare `"$REVIEWS"/*.md`
  fails: zsh aborts the whole script on a glob that matches nothing, so the check
  would not run at all … Both failures are in the fence."

  The `sh` half catches its failure. The `zsh` half cannot catch its own.
  Reproduced directly with the glob form and an empty directory:

  ```
  zsh -f:  no matches found: …/reviews/*.md   → stderr, exit 1, stdout EMPTY
  sh    :  UNDISPATCHED  *                    → stdout non-empty
  ```

  `_run_undispatched` returns `out.stdout.split()`, so the zsh abort yields `[]`
  — exactly what the test asserts. Rewrite the fence to the glob form today and
  the zsh assertion still passes; only the sh assertion fires. A test asserting
  that a check "ran at all" while being blind to the check not running is the
  failure #133 was filed for, one level up.

  Fix: assert the run succeeded, not just that it was quiet — have the helper
  return the `CompletedProcess` (or a `(stdout, returncode, stderr)` tuple) and
  add `assert out.returncode == 0 and out.stderr == ""` on the zsh path. That
  distinguishes "the check ran and found nothing" from "the check aborted".

## What passed

**1. Correctness.** The fence was executed against real fixtures under both `sh`
and `zsh`: correct on the happy path, on an empty directory, on a missing
directory (`2>/dev/null` absorbs it), and on filenames containing spaces
(`read -r f` plus `${f##*/}` handle them). Output ordering is deterministic via
`sort`. The `while` subshell sets nothing it needs to export. Composition with
#173 holds: `UNDISPATCHED` never enters the three-state vocabulary, the two
fences are keyed on disjoint words, and `_undispatched_command`'s
`assert "MISSING" not in blocks[0]` is what keeps `_roster_command` from
retargeting. The prose "Reading the directory is the right question here and the
wrong one above" correctly preserves #173's out-of-scope rule rather than undoing
it. Issue requirements (a) and (c) are met cleanly; (c)'s argument — that
`ListAgents` typed one agent a fork and did not list the other, so type catches
one of two — is faithful to #205 as filed.

**2. Security.** No new input trust boundary. The check reads filenames the
session's own reviewers wrote; ids are not eval'd or executed, and the only
expansion into a shell construct is the `case` pattern (NIT above). `eval
"$(wfctl feature-paths)"` matches the existing, already-argued pattern.

**3. Architecture.** Fits the file's existing shape: a rule, its argument, a
fence, and the rejected alternative. Nothing is restated from `code-review`
(`test_the_panel_skill_does_not_restate_the_rubric` still passes). No other file
in the repo references the deleted sentence "A reviewer nobody dispatched still

no stale cross-reference was left behind. The change is wfctl's own skill, not
vendored, so `vendor-upstream-skills` does not bind.

**4. Readability.** Comments inform rather than narrate; no "this was added
because". Test docstrings name the failure they exist for, per `AGENTS.md`, and
the `test_a_report_from_outside_the_roster…` docstring's note about non-`r`-prefixed
ids is the strongest one here — it names the wrong implementation the test rules

what earns it over a table.

**5. Performance.** One `find` over one small directory, once per roster read.

**6. Over-engineering.** Two `shrink:` items above. No dead code, no speculative
