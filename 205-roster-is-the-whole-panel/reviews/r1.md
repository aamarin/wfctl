BLOCKER  SKILL.md:L244-254 — the `UNDISPATCHED` fence cannot tell a stranger from **this branch's own earlier panel**, so a second run on a branch prints its previous reviewers as agents nobody dispatched → scope `find` to files newer than this run's dispatch.

  `$FEATURE_DIR/reviews/` is outside the worktree, per-branch, and persists
  across sessions and across panel runs. Measured against the real spec root:
  5 of 72 existing `reviews/` directories already hold `.md` reports outside a
  three-id roster, and the shape is a re-run, not a stranger —
  `170-skill-command-collision` and `240-decompose-advances-unattended` each
  hold `r1..r6` (a second panel dispatched under fresh ids so it would not
  overwrite the first), `100-gate-evidence-contract` holds `r1..r9`, and
  `133-review-fanout-skill` holds `p1.md`, `p2.md`, `rebase-r1.md` beside
  `r1..r3`.

  On the second of those runs, with `ROSTER="r4 r5 r6"` correctly substituted,
  the fence prints `UNDISPATCHED r1/r2/r3` and L274-278 instructs the session to
  publish `not read: 3 reports from agents this panel did not dispatch`. That is
  an untrue sentence about the panel's own work put under the table — the exact
  harm class #173 documents ("it spends that reviewer's work twice and puts an
  untrue sentence in the table below"), arriving through the fix for its sibling.
  It also sends a reader hunting a contamination that did not happen.

  Fix (cheap, testable, and it generalises to any stale file): mark the dispatch
  and filter on it.

  ```bash
  # at dispatch (Step 2): mkdir -p "$REVIEWS" && touch "$REVIEWS/.dispatched"
  find "$REVIEWS" -name '*.md' -newer "$REVIEWS/.dispatched" 2>/dev/null | sort | ...
  ```

  A `-newer` marker is the only form that separates the three populations
  (this run's reviewers, an earlier run's reviewers, a stranger) without asking
  the reader to remember which ids a past session used. Add the regression test
  alongside: an `r1.md` written before the marker is silent, one written after
  is `UNDISPATCHED`.

WARNING  SKILL.md:L247 — `2>/dev/null` makes the new check fail *silent*, and silence is its pass signal → drop it and let `find` report a bad `$REVIEWS`, or test the directory explicitly.

  Confirmed by running the fence: against a `$REVIEWS` that does not exist it
  prints nothing and exits 0 — indistinguishable from a clean panel. The
  failure is reachable the same way the sibling loop's is: `eval "$(wfctl
  feature-paths)"` binding nothing (outside a wfctl repo, or `wfctl` not on
  `PATH`) leaves `REVIEWS=/reviews`.

  The asymmetry is what makes it a finding rather than a nit. On the same
  mis-binding the roster loop at L136-148 prints `MISSING`/`RUNNING` for every
  id — loud, and wrong in the direction that gets looked at. This one prints
  the all-clear. A check whose broken state and whose passing state are the same
  string is the shape this whole skill exists to remove.

  The suite cannot currently tell the two apart either:
  `test_the_undispatched_check_survives_an_empty_reviews_directory` asserts
  `== []` for a directory that exists and is empty, which is byte-identical to
  the output for a directory that was never resolved. Either keep `2>/dev/null`
  and add a `[ -d "$REVIEWS" ] || { echo "NO REVIEWS DIR  $REVIEWS"; }` guard, or
  drop the redirect — `find` on a missing path already writes to stderr and the
  reader sees it.
