## Findings

WARNING  wfctl/cli.py:1358 — FR-006's CLI path is an unhandled traceback, not a refusal.
`_arch.accept` is called with no `except ValueError`. The `record.status !=
"proposed"` pre-check at :1300 absorbs the guard `accept` raises itself, but it
cannot absorb the two `_set_status` raises. A `proposed` record with no `##
Log` section — or one whose only `## Log` is inside a fence, which
`_log_bounds` deliberately skips — reaches `_set_status` and the user gets a
rich traceback ending in `ValueError: <path>: no '## Log' section to append
to`. Reproduced:

```
$ WFCTL_ARCH_DIR=<tmp> uv run wfctl arch accept no-log --agreed "on #321"
... ValueError: <tmp>/no-log.md: no '## Log' section to append to
EXIT=1
```

Nothing is written, so FR-006's "changing nothing" half holds and there is no
data-loss risk — which is why this is not a BLOCKER. What fails is the half the
command's whole design is about: `_not_promotable` exists because "the reader's
next action differs by status", and this fourth failure mode gives the reader a
stack trace. The record set is by `parse_record`'s own docstring "a directory
anyone can drop a file into", so a malformed record is the case the module
already plans for everywhere else. Every record in `docs/architecture/` carries
a `## Log` today, so this is latent rather than live.
→ Wrap the call: `except ValueError as e: console.print("[red]✗[/red] ..."); raise typer.Exit(1)`,
and add a CLI test beside the other refusals. `test_arch_records.py` covers the
`_arch` half; nothing covers the console half of FR-006.

WARNING  wfctl/cli.py:1367 — the echo hardcodes the column `_LOG_STATUS_WIDTH` was introduced to own.
`f"  [dim]Logged:[/dim] {date}  accepted    — {escape(citation)}"` — four literal
spaces. `_arch.py:404`'s comment for the new constant says, in its own words,
"a column nobody names is one the third caller gets wrong", and this is the
third caller, naming nothing. The two hardcodings agree today (`accepted` + 4 =
12), and no test asserts they agree: `test_arch_records.py` pins the on-disk
line and `test_arch_accept.py` pins the console line, both with literal spaces,
so a future change to `_LOG_STATUS_WIDTH` that updated one test would leave the
✓ line quoting a line the file does not contain. That defeats the stated point
of the echo ("the line it wrote, quoted back").
→ Have `_set_status` return the line it inserted and let `accept` pass it up, so
the console prints the string that was written rather than a reconstruction.
Alternative if the return value is unwanted: build the echo from
`_arch._LOG_STATUS_WIDTH`.

WARNING  wfctl/_arch.py:534-538 — `accept`'s docstring states a caller behaviour no caller has.
"the current status travels out on the exception **so the caller can say which
of three things went wrong**". The only caller pre-checks `record.status !=
"proposed"` at `cli.py:1300` and never catches the exception; the payload is
read by `test_the_refused_status_travels_out_on_the_exception` alone. Under this
repo's rule that comments carry rationale for the next reader, a rationale that
describes the wrong mechanism is worse than none — the next reader will look for
the `except` and not find it. Related: `ValueError(record.status)` on an
unreadable record raises `ValueError("")`, which would surface as a blank
exception message if it ever escaped (the branch above makes that reachable).
→ Restate the docstring as what is true — the guard is defence-in-depth for a
second in-module caller, and the status is on the exception so a *future* caller
need not re-read the file. Or make the CLI actually catch it and delete the
pre-check, which would also fix the first finding in the same edit.

WARNING  docs/architecture/design/321-one-status-mutation.md:35 — a "Verified" bullet that is falsified by the file it appears in.
"Every `Log` line in `docs/architecture/` pads the status to a 12-character
column", and the Assumed section's falsifier is "finding a record whose column

## Passes that found nothing, and what they checked

**Security.** `slug` reaches no path construction — the record is selected by
equality against `load_records`' glob output, so the traversal hazard
`arch_none_cmd` guards with `Path(branch).name` does not exist here. `citation`
is free text, `escape()`d on both console prints and written into a markdown
file that nothing executes. No secrets, no network, no subprocess. Writes go
through `write_atomic` to a path derived from `arch_root`.
Noted and judged out of scope: nothing gates an agent from running `arch accept`
under `auto_approve`, and the record's Consequences says "An agent working
unattended cannot finish the transition" — which is a statement about the
skill's instruction, not a control the code carries. NFR-001 and the record's
own "tamper-evident, not unforgeable" paragraph state that ceiling explicitly,
so this is a stated accepted risk rather than a finding. Worth the author
confirming the Consequences sentence reads as instruction rather than as
enforcement, given `a-rule-is-expressed-as-a-check` is in force.

**Performance.** One `load_records` glob over ~25 files, one `difflib` pass over
the slug list on the miss path only, one atomic write. Nothing in a loop,
nothing unbounded, no I/O per record beyond the read `parse_record` already
does. Local imports in the command body match the file's established pattern
(`arch_none_cmd` does the same) and keep `difflib`/`datetime` off the startup
path.

**Architecture.** The `_set_status` extraction is the right seam and the design
record argues it correctly: `_frontmatter_end` and `_key_value` both document
that they exist so the parser and `supersede` cannot disagree, and a copied body
is where that guarantee is spent. `supersede`'s output is byte-identical
(`superseded` padded to 12 is the two literal spaces it already wrote), and
`test_the_log_column_matches_what_supersede_already_writes` pins it. `_arch`
gains no import of `_pipeline`, so FR-008's real form — the module boundary,
per the analyze scan — holds. The `proposed`-only guard sits in `_arch` rather
than the CLI, which the design record argues for and I agree with; the finding
above is that the CLI then duplicates it instead of consuming it.

**Correctness (beyond the findings).** Exercised by reading and by the suite:
repeated `status:` key edits the last one (the line `_frontmatter` reads);
CRLF preserved byte-for-byte with exactly two changed lines; missing trailing
newline does not weld entries; every refusal path leaves the file
byte-identical (asserted in 8 tests, `test_arch_accept.py` and
`test_arch_records.py` both); `accept` twice appends no second line;
end-to-end SC-003 through both real commands shows the withheld count drop.
NFR-002's read-then-write race is stated in the spec and not designed around,
correctly. Placeholder refusal covers `<where>` and the exact string the help
text and the refusal listing print, which closes the loop the check exists for.

**Tests.** Docstrings say why the test exists and name the failure — house rule
met, and several name the earlier draft they caught (`test_naming_no_record_with_nothing_promotable_still_exits_one`,
`test_a_slug_resembling_nothing_falls_back_to_the_listing`). `NO_COLOR` comes
from `conftest.py`'s module-level set, so the console assertions are
machine-independent. Behaviour is asserted, not implementation, except
`test_the_refused_status_travels_out_on_the_exception`, which is the one test
that pins an internal contract — and per the third finding, that contract's
stated purpose is currently unused.
The gap is the one named above: no CLI-level test for FR-006.

**Over-engineering.** Nothing to delete. `accepted_on` has one caller but is a
tested module-boundary read with a real reason to live in `_arch` rather than
the CLI. `_LOG_STATUS_WIDTH` earns its name. `_not_promotable` at 30 lines for
three sentences is defensible — the analyze scan and the tests both argue the
three refusals are three different next actions. The comment-to-code ratio is
high and that is this repo's stated style, not bloat. `arch_accept_cmd` is ~45
executable lines under a 20-line docstring, inside the "split 50+ line
functions" bar.

net: Lean already — the two structural suggestions (returning the written line
from `_set_status`; catching `ValueError` at the CLI) are roughly line-neutral
and remove a duplication and a crash rather than shrink the diff.

Verdict: **Approve with changes requested** — no blockers. Four WARNINGs, of
which the FR-006 traceback and the hardcoded column are the two I would fix
before merge; the docstring and the design record's Verified bullet are accuracy
fixes in prose this repo holds to a high bar. The change does what #321 says,
the extraction is the right shape, and the refusal design is unusually careful.
