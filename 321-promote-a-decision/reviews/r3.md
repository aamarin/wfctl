### BLOCKER — a multi-line `--agreed` forges Log entries

`wfctl/cli.py:L1352` validates the citation for emptiness and for the `<...>`
placeholder shape, and for nothing else. `_set_status` then interpolates it into
a single-line list item (`_arch.py:L469`). A citation containing a newline
therefore writes more than one line into the `## Log`, and the extra lines are
indistinguishable from genuine entries.

Reproduced against `_arch.accept` directly:

```python
_arch.accept(rec, "2026-09-10",
             "agreed in review\n- 2026-01-01  accepted    — fabricated")
```

Resulting file:

```
- 2026-01-01  proposed    — x
- 2026-09-10  accepted    — agreed in review
- 2026-01-01  accepted    — fabricated
```

`_arch.accepted_on()` then returns **`2026-01-01`**, not `2026-09-10` — it takes
the *last* matching line by design (`_arch.py:L497`), so the injected entry wins
the read. The refusal message on a second `arch accept` would report the forged
date as the acceptance date.

Why this is a blocker and not "tamper-evident, not unforgeable": that ceiling, as
`a-human-accepts-a-decision` states it, is *"a promotion with nothing behind it
has to say something false in the file a reviewer reads."* This defeats the
mechanism rather than living under the ceiling — the record ends up carrying an
entry the operator never typed as a log line, and the field the whole feature
exists to make trustworthy reads back wrong. The accidental case is at least as
likely as the deliberate one: pasting a two-line quote out of a review thread is
the natural way to answer "where did the human agree?".

Fix, one line beside the placeholder guard:

```python
if "\n" in agreed or "\r" in agreed:
    console.print("[red]✗[/red] --agreed must be one line: the citation is a "
                  "single Log entry.")
    raise typer.Exit(1)
```

A test belongs in `tests/test_arch_accept.py` beside the placeholder parametrize,
and a `_arch`-level one asserting the log gains exactly one line — the module
guard is where a second caller would need it, by the same argument
`321-one-status-mutation.md` § Considered uses to put the `proposed`-only guard
in `accept` rather than in the CLI.

### WARNING — the fourth failure mode has no message

`_not_promotable` gives three tailored refusals for three status states, and the
docstring argues carefully for why they are three sentences and not one. But the

catches it. Reproduced through `CliRunner` on a git repo:

```
exit 1
exc: ValueError("…/docs/architecture/r.md: no '## Log' section to append to")
```

No output at all — in a real terminal, a traceback. Reachable: `wfctl arch check`
validates commit state, not sections (confirmed — it passes a record with no
`## Log`), and `test_a_mismatched_closer_leaves_the_fence_open_and_hides_the_log`
already proves a well-formed record can present as having no Log. The remedy
("add a `## Log` section") is exactly the kind a reader can act on, which is the
standard the other three refusals set.

Fix: wrap the `_arch.accept` call in `except ValueError` and print the fourth
sentence. `test_accepting_a_record_with_no_log_section_writes_nothing` covers the
module; the console path is uncovered.

### WARNING — the CLI is the third caller the column constant warned about

`_arch.py:L405` introduces `_LOG_STATUS_WIDTH` with the comment *"a column nobody
names is one the third caller gets wrong."* `cli.py:L1367` is that third caller,
and it hand-writes the column:

```python
f"  [dim]Logged:[/dim] {date}  accepted    — {escape(citation)}"
```

Four literal spaces, and `test_the_success_line_quotes_the_log_entry_it_wrote`
asserts only on the *output*, never comparing it to the file. Change
`_LOG_STATUS_WIDTH` and the echo silently stops matching what was written while
every test stays green — which is precisely the failure the constant was
introduced to prevent, one call site later. Fix: build the line from
`f"{_arch.IN_FORCE:<{_arch._LOG_STATUS_WIDTH}}"`, or have `_set_status` return the
line it wrote and quote that.

### WARNING — no `touched_on_this_branch` guard

`arch none` (`cli.py:L1222`) refuses with a ⚠ when its write lands outside the
change under review, with a comment explaining that both failure modes (root
outside the working tree, root gitignored) are silent. `arch accept` writes into
the same configurable `arch_root` and carries no such check. FR-010 ("acceptance
survives the branch") depends on the record being committed; in a repo that
declared its arch root outside the tree — which `CLAUDE.md` says is supported —
the acceptance is durable to nobody. The asymmetry may be intentional (the record
already exists, so it is the *author's* problem, not the command's), but nothing
in the diff says so. Either add the guard or write the paragraph.

falsification test is reported as run and passing when it was not. Fix: scope both
sentences to the top-level tier, and align this record's own Log line.
