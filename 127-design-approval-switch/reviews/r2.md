## BLOCKER — `wfctl/_session.py:L79-84`

`auto_approve()` catches `OSError` and `json.JSONDecodeError`, then calls
`data.get(...)` on whatever `json.loads` produced. Any JSON scalar or array
parses fine and has no `.get`:

```
'null'   -> RAISES AttributeError 'NoneType' object has no attribute 'get'
'true'   -> RAISES AttributeError 'bool' object has no attribute 'get'
'[1,2]'  -> RAISES AttributeError 'list' object has no attribute 'get'
'"yes"'  -> RAISES AttributeError 'str' object has no attribute 'get'
'123'    -> RAISES AttributeError 'int' object has no attribute 'get'
```

`auto_approve()` is called from `build_report`, which every state-resolving
command calls, so a two-byte file takes out the whole CLI for that branch:

```
$ D=$(mktemp -d); echo 'true' > $D/mode.json; WFCTL_STATE_DIR=$D wfctl status
...
❱  84 │   return data.get("auto_approve") is True
AttributeError: 'bool' object has no attribute 'get'
```

Three things make this a blocker rather than a warning:

1. The docstring states the opposite contract — *"Absent, malformed or
   unreadable reads as `False`, never as granted."* `true` is malformed for this
   reader and it does neither; it raises.
2. `verify.json` is named in `MODE_NAME`'s own comment as the shape being
   copied, and `_verify.load_record` (`_verify.py:L100`) does exactly the check
   that is missing here: `if not isinstance(data, dict) ... return None`.
3. Recovery requires a user to know that an XDG state-dir file they have never
   heard of is what broke `wfctl status`. The traceback names the file, which
   helps, but nothing else in wfctl fails this way.

The most plausible source is a hand-edit — the feature invites one, since
`mode.json` is a two-key file whose whole content is a boolean, and someone
flipping it by hand is as likely to write `true` as `{"auto_approve": true}`.

Fix:

```python
    except (OSError, json.JSONDecodeError):
        return False
    return isinstance(data, dict) and data.get("auto_approve") is True
```

`test_a_lost_or_damaged_mode_file_reads_as_attended` already owns this case in
its docstring (*"a truncated write or a hand-edited file"*) and tests only two
of its shapes. Extend it with `write_text("true")` and `write_text("null")`.

## WARNING — #127 scope item 5 is absent

The issue is explicit about the sequencing:

> Item 5 of #121 is the hard dependency. An unattended run whose records are
> invisible at review time is strictly worse than the pause it removed.

The half that removes the pause is here. The half that replaces it is not:
`.github/pull_request_template.md` gains no section listing records written on
the branch, `doctor` gains no check, and `status` lists the mode but not the
records. `design-levels`' new checklist item (`SKILL.md:L298`) is the agent
self-checking its own work — the same shape `wfctl-runs-the-verification`
removes from the agent's side elsewhere — not reviewer visibility.

This compounds with the accepted self-grant risk. The arch record's answer to
"an agent can grant itself the mode" is *"the grant is recorded, so a run that
granted itself autonomy says so in its own log"* — and nothing instructs anyone
to read that log at review time. `wfctl log` renders the event
(`mode  auto_approve=True`, confirmed), so the evidence exists; the reviewer's
path to it does not.

The commit says `Refs #127`, so this may be deliberate staging. The rubric's bar
for deferring a WARNING is a written follow-up, not "later" — so either land the
cheap form (a PR-template section listing `<arch-root>/**` files touched on the
branch) or file the issue and say in the PR that the mode should not be used
until it lands.

## NITs

**`cli.py:L168`** — the guard is `auto_approve != report.auto_approve`, so a
flag that restates the current mode writes nothing and prints nothing:

```
$ wfctl start --auto-approve     # mode already on
ℹ Already initialized (use --force to reset)
```

That output is character-for-character the case the comment four lines above
calls the bug the placement exists to prevent (*"a grant swallowed by the guard
below would print 'Already initialized' over a flag that did nothing"*). The
state is correct; the report of it is not distinguishable from the failure. Keep
the write and the event conditional on a change — restating a mode is not a
grant and should not log as one — and move the `console.print` out of the `if`,
under `if auto_approve is not None`.

**`cli.py:L147`** — `auto_approve: bool = typer.Option(None, ...)`. The
annotation says the value is never `None`; the very next use is
`auto_approve is not None`, and the tri-state is the whole design. `bool | None`
is honest and typer handles it. Precedent for the loose form exists at
`cli.py:L1111-1115`, so this is convention-consistent rather than novel — worth
tightening because this is the first option where `None` is a semantic third
state rather than "argument absent". mypy is green either way (`typer.Option`
returns `Any`), so nothing catches it today.

**`cli.py:L170-173`** — a conditional expression spanning a `console.print`
argument, with `[green]✓[/green]` repeated in both arms. Two lines shorter and
one less mental pause as:

```python
        msg = _AUTO_APPROVE_NOTICE if auto_approve else "auto-approve off — design gates stop for a human"
        console.print(f"[green]✓[/green] {msg}")
```

**`cli.py:L476`** — `log_cmd`'s `_STYLES` maps `start`/`end`/`resume`/`next`/
`issue` and falls back to white. `mode` is the one event that records a change
of authority and it renders in the unknown-event colour, next to coloured
routine events. If the log is the mitigation, it should not be the dimmest line
in it.

**`wfctl end`** — `session-summary.md` is what the next session reads, and it
does not say which mode the feature is in. #127 scope item 2 names only `status`
and `resume`, so this is beyond the ask; noting it because a handoff that omits
the mode is the same shape as the visibility gap above, and `end` already builds
the report that has the field on it.

**`tests/test_auto_approve_mode.py`** — no test asserts an invoked command's
exit code. `test_a_later_bare_start_does_not_revoke_the_mode` is the one where
it matters: if the second `wfctl start` tracebacked, `mode.json` would still
hold `true` and the test would pass green on a broken command. One
`assert result.exit_code == 0` per invocation makes the tests witness the
command rather than the file it left behind.
