## Findings

WARNING  wfctl/_session.py:L82 — `auto_approve()` promises "absent, malformed or
unreadable reads as `False`" and does not deliver for two real corruption
shapes. Verified by running the function:

```
mode.json = 'null' / '[]' / '3' / '"x"'   → AttributeError: 'NoneType' object has no attribute 'get'
mode.json = valid JSON with an invalid UTF-8 byte → UnicodeDecodeError
```

`json.JSONDecodeError` does not cover a *valid* JSON scalar, and
`UnicodeDecodeError` is a `ValueError`, not an `OSError`, so neither is caught.
`cli.py` has no top-level handler, so any of these tracebacks out of `wfctl
status`, `start`, `resume` and `end` for that branch until someone deletes the
file by hand — the fallback lands on "unusable", not on "stopping for a human".
`test_a_lost_or_damaged_mode_file_reads_as_attended` names "a corrupted byte" in
its docstring and then tests only `"{not json"` and an unlinked file, which is
the one shape `json.JSONDecodeError` already covers.
→ `except (OSError, ValueError): return False`, and
`return isinstance(data, dict) and data.get("auto_approve") is True`; extend the
existing test with a `null` body and a non-UTF-8 byte.
Not a BLOCKER: no writer in wfctl produces a non-object (`write_json_atomic`
always writes a dict and `os.replace` makes the write atomic), so it takes a
hand edit or filesystem corruption to reach.

WARNING  wfctl/agents/skills/brainstorming/SKILL.md:L13 — the rewritten HARD-GATE
contradicts the mode it was rewritten for. It now reads "until the design has
been presented **and approved**", while L18 defines approval under
`auto_approve: true` as happening *at the PR* — i.e. after descending. An agent
that reads the gate line stops; one that reads to L18 descends. The file itself
forbids the reconciliation an agent would otherwise make: L136 says "Do not
paraphrase that as approval you were given." The original text ("the user has
approved it") was unambiguous and merely wrong for the new mode; the passive
rewrite is ambiguous, which is worse in the strongest-worded block in the file.
→ Make the gate condition name the mode: "…until the design has been presented
and, with `auto_approve: false`, approved by the user; with `auto_approve: true`,
until each gate's answer is written into its record."

   `grant_auto_approve → write_json_atomic/append_event`. Confirmed

   fire), that `_remove_session_fossils` deletes `current.md`/`current.json` and

   they test behaviour through the CLI, cover default/grant/revoke/persistence/
   corruption/story-complete/`resume` line separation, and the docstrings name
   the failure each exists to catch, per `CLAUDE.md`. The gap is the corruption
   test's coverage, not its shape.
2. **Security** — the switch grants an agent autonomy, so this is the pass that
   matters. Self-grantability is real, is argued in the record rather than
   hidden (`Bash(wfctl start*)` glob, `Bash(wfctl *)` allowlist), and the
   mitigation is evidence rather than prevention, consistent with #100 and
   `wfctl-runs-the-verification`. The state dir is user-owned and anyone who can

   boundary. `Bash(wfctl status*)` added to `speckit.brainstorm.md` is read-only
   and is the minimum needed. No secrets, no untrusted input beyond the JSON read
   covered above. Failure direction is conservative by design and correct except
   for the crash finding.
3. **Architecture** — the record is thorough and its Considered list covers the
   alternatives I would have raised (event-only, file-only, manifest, `_STEPS`,
   `current.json`, a dedicated verb). It respects `pipeline-state-is-one-payload`
   (one field, every view a rendering), `session-state-is-re-derived` (the
   carve-out argument is sound: nothing on disk implies intent), and
   `io-owns-durability-not-domain-files` (path and field names live in
   `_session`, not `_io`). One finding: the derived-skill edit against
   `vendor-upstream-skills`. Noted but not filed: `next_cmd` (`cli.py:293`)

   drift from `pipeline-state-is-one-payload`, not this diff's to fix, and #127
   scope item 2 names only `status` and `resume`.
4. **Readability** — comments explain *why this shape* and match the repo's
   density; none narrates the diff to a reviewer. Names are right (`MODE_NAME`
   mirrors `verify.json`'s pattern; `grant_` vs `auto_approve` separates writer
   from reader). `_AUTO_APPROVE_NOTICE` correctly shares one string across three
   call sites. Findings are in the skill prose, which is where this feature's
   behaviour actually lives.
5. **Performance** — one extra `read_text` of a ~30-byte file per `build_report`.
   Nothing else added to any path. Nothing to report.
6. **Over-engineering** — the two-store design (file + event) is not gold
