BLOCKER `wfctl/agents/skills/fanning-out-code-review/SKILL.md:108` — the roster
check the skill is built around reads `$REVIEWS`, a variable nothing in the
skill ever sets. Step 1 establishes `FEATURE_DIR` (`wfctl feature-paths`) and
says "Reviews go in `$FEATURE_DIR/reviews/`" (line 58); Step 2 tells reviewers
to write to `$FEATURE_DIR/reviews/<id>.md` (line 86). Step 3's fenced command is:
```bash
for id in r1 r2 r3; do
  if [ -s "$REVIEWS/$id.md" ]; then echo "reported  $id"; else echo "MISSING   $id"; fi
done
```
An agent that pastes this verbatim, as the skill's own framing assumes it will
("the fenced block" is what `test_review_fanout_skill.py` treats as the literal
command — see its module docstring: "It is a shell command inside a skill, so
it ships whether or not it works"), runs it with `REVIEWS` unset. `$REVIEWS/$id.md`
then expands to `/r1.md`, `/r2.md`, `/r3.md` — filesystem root — which is never
where a reviewer wrote its report, so the check reports every reviewer
`MISSING` regardless of whether they actually reported. That's the exact
failure this skill exists to catch, reintroduced one layer up: the roster check
itself now can't tell "reported" from "didn't," it just always says "didn't."
The test suite doesn't catch this because `_run()` in
`tests/test_review_fanout_skill.py:42` injects `REVIEWS` as an environment
variable directly (`env={"REVIEWS": str(reviews), …}`) rather than deriving it
the way the skill's own prose would have to — the test validates the loop
logic, not that the loop is reachable from the rest of the skill's stated
variables.
→ **Fix:** either inline the real path instead of introducing a second variable
name (`if [ -s "$FEATURE_DIR/reviews/$id.md" ]; then …`), or add a line before
the loop that derives it explicitly: `REVIEWS="$FEATURE_DIR/reviews"`. Either
fix should also update the test fixture/env plumbing so it exercises the
derivation, not just the loop with `REVIEWS` handed to it externally.

WARNING `wfctl/agents/skills/fanning-out-code-review/SKILL.md:107-110` — the
roster loop hardcodes `r1 r2 r3`. Step 1 calls three "the default," not a fixed
count ("Two leaves a disagreement with no way to read it; past three you are
mostly buying the same reading again" — phrasing that allows a parent to choose
otherwise for a given change). If a parent dispatches two or four reviewers, the
roster check silently checks the wrong roster: too few ids and a real reviewer
is never checked; too many and a MISSING is reported for an id that was never
dispatched. → **Fix:** parameterize over the ids actually assigned in Step 1/2
(e.g. `for id in $IDS; do …` with `IDS` set once when reviewers are assigned)
rather than a literal `r1 r2 r3`, or state explicitly that 3 is not just a
default but the only supported count and the loop is written to match.
