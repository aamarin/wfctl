## Findings

**WARNING** `wfctl/agents/skills/fanning-out-code-review/SKILL.md:58-63` and
`:112-117` — Step 3's roster fence (`REVIEWS="$FEATURE_DIR/reviews"`) only
works if `FEATURE_DIR` is bound as a real shell variable in the same Bash
invocation. Step 1 never says to bind it in the normal case (only `wfctl
feature-paths` prints it as text, and Step 1's prose says "Substitute the real
path"). Confirmed the failure by running the exact fence text with
`FEATURE_DIR` unset — every reviewer, including ones that reported, comes back
`MISSING`:

```
$ sh -c 'REVIEWS="$FEATURE_DIR/reviews"; for id in r1 r2 r3; do
  if [ -s "$REVIEWS/$id.md" ]; then echo reported $id; else echo MISSING $id; fi
done'
MISSING r1
MISSING r2
MISSING r3
```
(against a directory where `r1.md` genuinely has content). This is the exact
class of bug 70f3190 already fixed once — but only for the "no feature dir"
fallback sentence ("set `FEATURE_DIR` yourself... picking a path without
binding the name leaves that check looking somewhere else"); the primary path,
where `FEATURE_DIR` comes from `wfctl feature-paths`, has no equivalent
instruction to bind it before Step 3 runs. It fails toward over-asking, not a
false clean pass (the one failure mode this skill exists to prevent), so it's
not a blocker. → Add one line to Step 1, next to the `wfctl feature-paths`
fence: `FEATURE_DIR='<the printed value>'` (or fold the binding into the same
Bash call Step 3 uses), so the roster check does not depend on a shell
variable persisting across separate tool calls — which this project's own
Bash tool contract says does not happen.

**WARNING** `tests/test_review_fanout_skill.py:84-89` — The docstring for
`test_the_panel_skill_names_every_skill_it_layers_over` claims
"`vendor-upstream-skills` forbids editing the three skills this one
orchestrates." That's false: `docs/architecture/vendor-upstream-skills.md`
names exactly one vendored skill — `i-have-adhd`, "identified by `license:` in
its frontmatter — the only skill carrying one." `code-review`,
`requesting-code-review`, and `receiving-code-review` carry no `license:` key
(checked all three files' frontmatter directly) and are first-party wfctl
skills the project can edit freely; the ADR's "never fork/edit" reasoning
(upstream owns the file, a local edit is lost on the next pull) does not apply
to them at all. The actual reason not to restate them is duplication —
`knowledge-placement.md` plus issue #50 — which is what commit 37c5e79's own
message cites ("`knowledge-placement` and #50 are what a copied rubric would
cost"). The wrong ADR got into the shipped docstring. This won't break
anything today, but it will actively mislead the next person who checks
`vendor-upstream-skills.md` looking for these three skills and finds only
`i-have-adhd` there. → Reword the docstring to cite `knowledge-placement` (and
#50) instead of `vendor-upstream-skills`.
