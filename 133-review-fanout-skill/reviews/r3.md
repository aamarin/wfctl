BLOCKER  wfctl/agents/skills/fanning-out-code-review/SKILL.md:108 — the roster
check the skill exists for references `$REVIEWS`, a variable nothing in the
skill ever defines. Step 1 (line 58) establishes `$FEATURE_DIR` (from
`wfctl feature-paths`, line 55) and says reviews go in `$FEATURE_DIR/reviews/`;
Step 3's fenced command tests `[ -s "$REVIEWS/$id.md" ]` instead. Run exactly as
written, with no `REVIEWS` in the environment, `"$REVIEWS/$id.md"` becomes
`"/r1.md"` (leading slash, no such file) and every reviewer — including ones
that filed real reports — comes back `MISSING`:
```
$ unset REVIEWS; sh -c 'for id in r1 r2 r3; do [ -s "$REVIEWS/$id.md" ] && echo reported $id || echo MISSING $id; done'
MISSING   r1
MISSING   r2
MISSING   r3
```
This is the exact failure the skill's own text calls out at line 95 ("this is
the step the skill exists for") — a check that's supposed to distinguish a
reporting reviewer from a silent one, but as written can't do that distinction
at all; it always reports MISSING regardless of what's on disk. The new test
(`tests/test_review_fanout_skill.py::test_the_roster_check_names_the_reviewers_that_did_not_report`)
passes only because it injects `REVIEWS` into the subprocess env itself
(`_run`, line ~39) — it validates the command's logic in isolation, not that
the skill's own prose ever produces a working `$REVIEWS`. → Fix: define it in
the same fence, right before the loop, using the name Step 1 already
established:
```bash
REVIEWS="$FEATURE_DIR/reviews"
for id in r1 r2 r3; do
  if [ -s "$REVIEWS/$id.md" ]; then echo "reported  $id"; else echo "MISSING   $id"; fi
done
```
(Still one fence containing "MISSING", so the test's `_roster_command` lookup
keeps matching it.) Verified the fix works once `REVIEWS` is set — confirmed by
the existing test passing when it supplies that same variable.
