## Findings

**WARNING** `wfctl/agents/skills/fanning-out-code-review/SKILL.md:55-92` (Step 1 →
Step 3) — Step 3's roster-check fence reads `$FEATURE_DIR` as a live shell
variable:

```bash
REVIEWS="$FEATURE_DIR/reviews"
for id in r1 r2 r3; do
  if [ -s "$REVIEWS/$id.md" ]; then echo "reported  $id"; else echo "MISSING   $id"; fi
done
```

Nothing in the skill tells the agent to bind `FEATURE_DIR` in *that* shell
invocation — no `export`, no inline `FEATURE_DIR=…` line, no
`eval "$(wfctl feature-paths)"` (which is what `feature-paths`'s own docstring
says it's for: "Consumed via `eval`"). The only instruction is "Substitute the
real path," stated once at line 58, attached to a different sentence, ~35 lines
before Step 3. This project's own Bash tool does not persist shell state between
separate invocations ("The working directory persists between commands, but
shell state does not" — this session's own tool description), so an agent that
runs Step 1's `wfctl feature-paths` and then copies Step 3's fence verbatim into
a second Bash call gets `REVIEWS="/reviews"` and reports every reviewer
`MISSING` regardless of whether they actually wrote a report — wrong output from
"the step the skill exists for" (SKILL.md:96).

This is the same defect class already caught and half-fixed in commit
`70f3190` ("bind FEATURE_DIR in the fallback the roster check reads") — that fix
covers the no-feature-dir fallback only; the primary path (the common case, feature
dir found automatically) has the identical gap and was not covered by that fix.

Mitigating: it fails noisy (spurious `MISSING`), not silent-clean, so it doesn't
reproduce the exact failure #133 was filed for, and it matches how ~10 other
wfctl skills use `$FEATURE_DIR` as a substitution placeholder rather than a
persisted shell variable (`speckit.brainstorm.md`, `end-session/SKILL.md`,
`idea-refine/SKILL.md`, etc.) — so a careful agent generalizing "substitute the
real path" across the whole document gets it right. But Step 3 is the one block
in this skill that looks like a script meant to be run as-is (multi-line,
`for`/`if`), which is exactly the shape most likely to get copy-pasted verbatim
without a re-read of a rule stated two sections earlier.

Fix: make Step 3 self-binding, e.g. prefix the fence with a line the agent fills
in itself:
```bash
FEATURE_DIR='<paste the value Step 1 printed>'
REVIEWS="$FEATURE_DIR/reviews"
...
```
so the substitution point is at the place the command is actually run, not
inferred from a sentence attached to something else.

this skill's own frontmatter comment) instead of `vendor-upstream-skills`, or —
if these three really are meant to be governed by that record — file the
separate fix of adding them to `vendor-upstream-skills.md`'s table (out of scope
for this diff, but the current citation shouldn't assert a fact the record

**NIT** `wfctl/agents/skills/fanning-out-code-review/SKILL.md:92` — "Under wfctl
that is `wfctl verify`, which writes one record per branch outside the
worktree." True in this repo (confirmed: `wfctl feature-paths` here prints
`FEATURE_DIR='/Users/…/wfctl-specs/133-review-fanout-skill'`, outside the
worktree) — but AGENTS.md is explicit that `<repo>/specs` is "the default, not
the truth": a wfctl-managed repo with no `spec_root` manifest configured falls
back to `FEATURE_DIR` *inside* the worktree, and Step 2's dispatch instruction
("Write findings to `$FEATURE_DIR/reviews/<id>.md`") would then have reviewers
writing under the tree the "report-only, never touch the tree" rule is guarding.
`specs/` being gitignored means it wouldn't show up in the diff other reviewers
are evaluating, so this is low-stakes, but the skill's isolation story is only
guaranteed for repos with a configured spec root, and nothing says so.
