## Findings

**BLOCKER** `wfctl/agents/skills/fanning-out-code-review/SKILL.md:108` — the roster
command references `$REVIEWS`, a variable the skill never defines. Step 1 (line 55) sets
`FEATURE_DIR` via `wfctl feature-paths` and states (line 58) "Reviews go in
`$FEATURE_DIR/reviews/`"; Step 2 (line 86) writes findings to `$FEATURE_DIR/reviews/<id>.md`.
Step 3's fenced block switches to a different, unset name:

```bash
for id in r1 r2 r3; do
  if [ -s "$REVIEWS/$id.md" ]; then echo "reported  $id"; else echo "MISSING   $id"; fi
done
```

Run verbatim (as the prose instructs — this is a literal command, not illustrative, per the
`test_skill_commands.py` convention this test file follows), `$REVIEWS` is empty, so the
paths become `/r1.md`, `/r2.md`, `/r3.md` — the filesystem root, not the reviews directory.
Every id reports `MISSING` regardless of what reviewers actually wrote. This is "the step
the skill exists for" (the skill's own words, line ~103) and, as shipped, it doesn't run
against the right directory. `tests/test_review_fanout_skill.py::_run` masks this by
injecting `REVIEWS` as an environment variable directly (line ~28) — the test never proves
the skill's own instructions produce a working `$REVIEWS`, only that the extracted command is
internally consistent once something else defines the variable. That's exactly the shape
`test_skill_commands.py`'s docstring warns about ("both failures are silent and both end the
same way: the agent takes the fallback shape").
→ Fix: use `$FEATURE_DIR/reviews` directly in the loop (`"$FEATURE_DIR/reviews/$id.md"`),
matching Steps 1–2's naming, or add `REVIEWS="$FEATURE_DIR/reviews"` as an explicit line
immediately before the loop. Either way, update the test's `_run` helper to exercise the
real derivation instead of injecting `REVIEWS` as a bare env var, so the test can't pass
against a skill whose own prose wouldn't produce a working value.

**WARNING** `wfctl/agents/skills/fanning-out-code-review/SKILL.md:107` — the roster loop
hardcodes `r1 r2 r3`. The skill explicitly allows a different reviewer count ("Three
reviewers is the default" — line ~62, implying not fixed), but nothing tells the agent to
edit the id list to match how many it actually dispatched. A 4th reviewer (`r4.md`) added for
a larger fan-out would silently never be checked — which is the exact failure mode (#133's
own trigger: "a reviewer that did not report is indistinguishable from one that found
nothing") reproduced by the checking mechanism itself. Contrast with Step 1's `<branch>`,
which is called out in prose as "a placeholder, never a directory name" — Step 3 has no
equivalent call-out that `r1 r2 r3` is a placeholder list to edit.
→ Fix: either state explicitly ("substitute the ids you assigned") next to the fence, the way
Step 1 does for `<branch>`, or derive the list from what's on disk
(`for f in "$FEATURE_DIR"/reviews/*.md`) so it can't drift from what was actually dispatched.
