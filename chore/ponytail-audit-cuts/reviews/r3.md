## WARNING — `_shape._blocks` silently changed behavior on unclosed fences

`main`'s `_split_fences` appended to `blocks` **only on a close**, so an unclosed
fence contributed nothing to either return value, and its docstring said so:

> An unclosed fence — what a reply cut off mid-block leaves — takes its tail with
> it.

`_blocks` now derives blocks from `Line.opened`, which every line inside an
unclosed fence carries. Demonstrated on this tree:

```python
body = "intro\n```\nA   ok. Then more.\nB   also. Also more.\nC   yes. Yes more.\n"
_shape.body_findings(body)
# this branch: ["SKILL.md:322 — the fenced block at line 2 aligns columns by hand …"]
# main:        []            (old _split_fences(body)[1] == [])
```

So `wfctl check-body` now fires the hand-aligned-columns rule on a truncated PR
body where it previously stayed silent. `_prose` is unaffected (it still drops
the tail), which means the two halves of the module now disagree about what an
unclosed fence *is*: prose treats it as a block that swallows the rest,
`_blocks` treats it as a block that ends at EOF.

The new reading is arguably the more consistent one. What is not arguable is
that a diff filed as "one walker instead of three" changed a user-visible check
with no test and no note. `_blocks`'s new docstring says only that grouping
comes from `opened` — the paragraph `main` spent on unclosed fences was deleted
rather than moved.

**Fix:** decide it explicitly, put the sentence back in `_blocks`'s docstring,
and add `test_an_unclosed_fence_is_still_a_block_for_body_findings` (or restore
the old behavior with `if line.opened in closed`).

## What I checked and found nothing wrong with

Recorded so the passes are auditable, not as filler.

**Correctness of `_md.walk_lines` itself.** State machine traced by hand against
CommonMark: the opener is yielded `fence=True, inside=False` *before* `marker` is
set, so it is never mis-tagged as its own content; a fence-shaped line inside a
block that fails the close test falls through to the `inside=True` yield rather
than being dropped; `opened` is only ever read on lines where it is set. The
`keepends=True` claim at :65 verified — `.` does not cross `\n` and `$` sits
before it, so `"```\n"` gives `group(2) == ""` and closes, `"```python\n"` gives
`"python"` and does not; CRLF (`"```\r\n"`) still closes because `group(2)` is
`"\r"` and `.strip()` empties it. The four-leading-space rule at :25 is a real
(and correct) tightening over `_arch`'s old `stripped[:3]`, which opened a fence
on an indented-code-block ```` ``` ````.

**`_body._blank_fences` equivalence.** Line-for-line output preserved (one output
line per input line, delimiters blanked not dropped), `splitlines()`/`"\n".join`

**Dead-code deletions.** `load_agentconfig` and `_body._RESULT_CELLS` have zero
