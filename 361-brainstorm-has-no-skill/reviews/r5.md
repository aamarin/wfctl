### WARNING — the generalised regression check passes on the defective tree

`tests/test_skill_cross_references.py:L169`, `test_every_pipeline_step_reaches_a_skill_an_agent_can_invoke`.

Its docstring: *"#361 as a check rather than as eight files that happen to comply … the next `_STEPS` row added with an inline wrapper reintroduces the defect with the suite green, which is exactly how this one arrived."* Commit `83cd3e1` repeats the claim and says it was verified by mutation.

Neither is true. The check is `_REFERENCE.findall(wrapper.read_text())`, and `_REFERENCE` matches **any** `.agents/skills/<name>` string anywhere in the file. Main's inline brainstorm wrapper carried one, at line 102:

```
(`.agents/skills/reading-design-records/SKILL.md`), and they take **only** the
```

Replayed against `main` with the test's own regex and `_STEPS`:

```
inline on main (pre-fix): {}
```

So the check would have shipped green over the exact state the issue was filed about. The mutation that was run must have been over the *skill's* existence or the reference in the new pointer, not over the pre-fix wrapper. Under `a-rule-is-expressed-as-a-check`, this is prose wearing a check's clothes, and the docstring convention in `CLAUDE.md` — *"docstrings say why the test exists, usually naming the failure it caught"* — is broken in the direction that matters: it names a failure it does not catch.

Fix — require the wrapper to name the skill *for its own step*, with the one real exception declared rather than absorbed:

```python
_WRAPPER_SKILL = {"decompose": "speckit-delivery-plan"}  # the one step whose skill is not its command's name
...
want = _WRAPPER_SKILL.get(step, spec.command.lstrip("/").replace(".", "-"))

    inline[step] = want
```

Verified both directions:

```

```

The `decompose` entry is worth having on its own account — it is the only step in the pipeline whose skill name cannot be derived from its command, and nothing in the tree currently says so.

Secondary note on the same test: its name promises *"reaches a skill an agent can invoke"*, but for seven of the eight steps the referenced skill is not in `_MIRRORED_SKILLS`, so it lands only under `.agents/skills/` and no agent resolves it by name — reaching it still means reading the wrapper as text. The docstring is honest about the narrower assertion ("Asserts the wrapper names a skill"); the name and the commit message are not.

### WARNING — the first mirrored skill that pre-approves writing and committing

`wfctl/agents/skills/speckit-brainstorm/SKILL.md:L4` carries `Write`, `Bash(git add*)`, `Bash(git commit*)`, `Bash(mkdir*)` — and the skill is in `_MIRRORED_SKILLS` with `disable-model-invocation` deliberately absent, so a model can now reach all of it unprompted.

The `cli.py` comment (added in `a9d0901`) argues the widening and I agree with the argument: a step that cannot write `design.md` or commit its records is the same dead end from the other side. What is unargued is the *breadth*. `start-session` — the only other mirrored skill carrying `allowed-tools` — grants `Read` plus read-only `wfctl`/`git` prefixes plus `grep`/`tail`, nothing that mutates. This entry is a category jump, and its globs admit any flag: `Bash(git add*)` admits `git add -A`, `Bash(git commit*)` admits `--no-verify`, `Write` is unqualified. That is the same breadth `a-human-grants-outward-facing-authority.md:L46` and `approval-mode-is-stored-intent.md:L70` already call out about `Bash(wfctl start*)` — *"whose glob admits any flag"* — so the repo has the vocabulary for it and has not applied it here.

Two acceptable resolutions, author's call:

- narrow on both surfaces (the equality assertion keeps them in step): `Bash(git add docs/architecture*)`, `Bash(git commit -m*)`;
- or leave the grant and record it — this is a boundary being moved (who may commit on the branch without a human typing anything), and the existing record on the neighbouring question is `a-human-grants-outward-facing-authority`.

Note also, for whoever writes that: `disable-model-invocation: true` survives on the wrapper and is now inert as an expression of intent. The model cannot invoke `/speckit.brainstorm`, but it can invoke the identical workflow one file over. That is the fix working, and the flag is now a statement about a file rather than about a workflow — worth saying out loud somewhere, because the next reader of the wrapper will read it the old way.
