## The blocker, in detail

`wfctl resume` refuses when the design step is being left with the boundary
question unanswered (`cli.py:L211-244` → `_pipeline.design_gate:L287`). It raises
`typer.Exit(1)` **before** `next-step.md` is written, and `next` is gated
identically. That is deliberate: the comment at `cli.py:L217` says gating only
`next` "would leave the orchestrated path — the one that actually runs — walking
straight past the check", and `test_resume_is_gated_too`
(tests/test_pipeline_commands.py:L329) pins it.

`wfctl status` is not gated, and correctly so — it is a read, and `start-session`
depends on `status --json` answering. But that means, in exactly the state the
gate refuses:

| | before this diff | after |
|---|---|---|
| step 2 `wfctl resume` | exit 1, refusal printed, nothing written | same |
| step 3 source | `next-step.md` — written only by two gated commands, so it can never hold a value from past the gate | `wfctl status --json`, ungated |
| what step 3 sees | the last pre-gate step, e.g. `/speckit.brainstorm`, `auto: false` | `next_command: "/speckit.specify"`, `auto: true` |
| step 4 does | displays "Next: run …", stops | emits `EXECUTE_COMMAND: speckit.specify` |

Concretely: `design.md` present, `spec.md` absent, no architecture record touched
on the branch — the `test_resume_is_gated_too` fixture. `_current_step_name`
returns `specify`; `_STEPS["specify"]` is `("/speckit.specify", True)`. So the
JSON the skill now reads says `auto: true` for the transition the gate exists to
stop, and step 4 has an unconditional auto-execute branch for it.

The old flow held the gate by construction — accidentally, because both writers
of `next-step.md` are gated. The new flow depends on the agent inferring "stop"
from a non-zero exit that no step mentions. Step 2's new prose *names* the
refusal ("refuses here if the boundary question went unanswered") and then hands
the reader to step 3 anyway; naming a failure without naming the stop is weaker
than the accident it replaced. This repo's stated position on gates is that they
should be unconstructible-past, not hoped-past (`_pipeline.py:L406`, "so no
future branch can produce one").

Fix belongs in the skill, not in `status`: adding the gate to `status` would make
a read refuse and break `start-session`. One sentence on step 2 closes it.

## Passes run

**1. Correctness.** Traced `build_report` → `next_step_content` → `_STEPS`, and
both `next_cmd` / `resume_cmd` end-to-end. The substitution
`command, auto = report.next_command or "", report.auto` is behaviour-preserving
for `command`: the old call was `next_step_content(step_name, repo_root,
spec_dir)` with `step_name = report.current or "complete"`, and `build_report`
makes that identical call with identical arguments — `_STEPS.get("complete")`
returns `("", False)`, matching `next_command or ""`. `auto` differs in exactly
one place: `False` → `None` on the story-complete branch, which reaches only
`append_event` (NIT 4). Nothing in `wfctl/` or `tests/` reads `auto` back out of
`events.jsonl`; `log_cmd` (`cli.py:L392`) prints it verbatim, so the change is
visible as `auto=None` in `wfctl log` and nowhere else. The `__post_init__`
three-way invariant is sound — `len({a,b,c})` over booleans is 1 iff all agree —
and `auto=auto if command else None` in `build_report` cannot violate it. Both
new tests pass for the right reason: `spec_tree` does
`mkdir(parents=True, exist_ok=True)` into one fixed directory
(tests/conftest.py:L263), so the docstring's ordering caveat is accurate, and
`CLEAN_SPEC` carries a `## Clarifications` section, so the second assertion's
`current == "plan"` is earned rather than incidental. The blocker above is the
one correctness defect found, and it is in the skill, not the Python.

**2. Security.** No new input parsing, no secrets, no shell. The one boundary
crossed is the design gate — covered above as correctness, since what it protects
is a review process rather than data.

**3. Architecture.** The change is squarely what
`pipeline-state-is-one-payload` asks for: `auto` was "a fact added to the
printing branch [that] reaches the human and silently not the agent", which the
record's *Considered* section rejects by name, and `--json` gaining a field is "a
second format over one inference, not a second path". The skill migration is
`session-state-is-re-derived` applied to the last artifact that was being read as
authoritative. No new pattern, no new dependency, no cycle. Two residues: the
record's own enumeration of console-invisible facts is now stale (NIT 7), and
`next_cmd` still holds the second inference path that `resume_cmd` just gave up
(NIT 5) — the diff halves a duplication rather than removing it, which is an
improvement, not a regression.

**4. Readability.** Names are the existing ones. The replacement comment at
`cli.py:L310-314` explains why the shape changed and carries the rationale
forward rather than narrating the diff — it reads correctly to someone who never
saw the old call, which is CLAUDE.md's test. The removed comment's substance
(passing `repo_root`/`spec_dir` is what routes an unverified implement to `wfctl
verify`) is not lost: it now lives inside `build_report`, and
`test_the_file_an_agent_reads_names_the_command_status_prints`
(tests/test_pipeline_commands.py:L981) still guards it — Chesterton's fence
checked and intact. `len({...}) != 1` is a mild trick; the comment above it
carries the reader, so it stands. Test docstrings say why each test exists and
name the defect, per convention.

**5. Performance.** `resume` now makes one inference instead of two — strictly
fewer filesystem reads, and on the `implement` arm it drops a second
`_verification_block`, which shells out to git (`_verify.code_identity`). The
skill costs one extra process (`wfctl status --json`) on a path that already runs
two; `wfctl resume` already prints both facts on its own output line
(`cli.py:L321`), so step 3 is arguably redundant — but JSON is the more robust
thing for an agent to parse than a rich-formatted sentence, so this is a
deliberate trade, not a defect. Checked that `console.print_json` does not
line-wrap a >80-column payload on a non-tty (verified by running rich directly
with a long `annotation`) — the JSON stays parseable.

**6. Over-engineering.** Nothing speculative. `auto` is not derivable from
`next_command` (`wfctl verify` is not in `_STEPS`), so it is a real field, not a
convenience. The two new tests are the minimum for the two halves of the change.
Deletable: `or ""` at L315 (NIT 6), and `next_cmd`'s three inference calls
collapsing to one `build_report` (NIT 5, ~−5 lines).
