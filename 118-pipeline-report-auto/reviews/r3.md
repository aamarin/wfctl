## BLOCKER — the orchestrated path can now walk past the design gate

`_refuse_unless_boundary_answered` is called from exactly two places,
`next_cmd` (wfctl/cli.py:L265) and `resume_cmd` (wfctl/cli.py:L309). **`status`
is not gated and never has been** — it is a read, and gating a read would be
wrong.

What made the refusal bind on the orchestrated path was not the exit code. It
was the sequencing the comment at wfctl/cli.py:L223 states outright:

> Before the file is written, never after. `next-step.md` is what the agent
> reads next, so a refusal that still wrote it would be a message nothing acts on.

Step 3 used to read that file. A refused `resume` left it holding the *previous*
step, so the agent displayed a stale, harmless "Next: run … when ready" and
stopped. The refusal acted on the agent because it withheld the agent's input.

After this change step 3 reads `wfctl status --json`, which succeeds
unconditionally and re-derives the *real* next step. Trace the gated transition:

1. `design.md` exists, `brainstorm` is done, boundary unanswered.
2. Step 2: `wfctl resume` → prints `DESIGN_GATE_REFUSAL`, exits 1, writes nothing.
3. Step 3: the skill has no instruction to stop, so it runs `wfctl status --json`
   → `{"current": "specify", "next_command": "/speckit.specify", "auto": true}`.
4. Step 4: `auto` is `true` → `EXECUTE_COMMAND: speckit.specify`.

Two details make this worse than a theoretical hole. The gate fires on exactly
one transition — `_AFTER_DESIGN`, the step after `brainstorm`
(wfctl/_pipeline.py:L38, L325) — and that step is `specify`, the pipeline's first
`auto: true` entry (`_STEPS`, wfctl/_pipeline.py:L23). So the single transition
the gate protects is also a transition the skill self-executes without pausing.

This is the failure `test_resume_is_gated_too`
(tests/test_pipeline_commands.py:L329) was written against, in its own words:
"a gate wired only into `next` is walked past by the one path that actually
runs." The gate is still wired into `resume`; the diff moved the path that
actually runs so it no longer has to care.

Step 2's new prose is aware of the refusal — "refuses here if the boundary
question went unanswered — none of which the read below does" — but naming a
refusal is not acting on one. The skill is the agent's control flow, and it
currently has no branch for "step 2 failed".

The same shape applies to `resume`'s other refusal, the no-session exit at
wfctl/cli.py:L297–L299: previously a missing `next-step.md` stopped the agent,
now step 3 answers anyway.

**Fix** — one sentence, at the end of step 2:

> If `wfctl resume` exits non-zero, display its output and stop. Do not continue
> to step 3: `status` is a read and is not gated, so it will hand you the very
> command `resume` refused.

Worth considering as an alternative (not required): `resume` already prints both
values it just derived — `Resumed — step: X, next: Y (auto: true)`
(wfctl/cli.py:L321). Reading step 2's own output would keep the refusal binding
by construction and drop one command per advance. Against it: parsing a console
string is what `--json` exists to avoid, and the arch record's dashed edges say
a view is a leaf. The stop-on-failure sentence is the cheaper, more faithful fix.

## WARNING — `status --json` emitting `auto` is untested

`cli.py:L177` is the entire contract between `PipelineReport.auto` and the skill
that now depends on it. Delete that one line and all 824 tests still pass:
the new tests in `tests/test_pipeline_state_names.py:L221–L244` assert on
`build_report`, and `test_the_json_view_and_the_console_view_agree`
(tests/test_pipeline_commands.py:L830) compares the JSON against the console —
which has no `auto` to compare with, so an absent key is invisible to it.

That is the exact drift that test's docstring names ("a fact added to one branch
and not the other"), except here the fact is present in the payload and only the
serializer can lose it.

**Fix**: assert the key in the JSON view — `payload["auto"] is True` for a
plan-current fixture, `payload["auto"] is None` for a finished story. The second
half also pins the null the skill's story-complete branch reads.

## WARNING — `resume`'s `auto` output has no test

The diff replaced the source of `resume`'s `auto` (wfctl/cli.py:L315). Every
`auto: true` / `auto: false` assertion in the suite exercises `next`
(tests/test_storyctl.py:L390, L397, L416, L426), and the one test that
parametrizes `["next", "resume"]` (tests/test_pipeline_commands.py:L981) asserts
only the *command*, not the flag. `test_resume_reports_the_step_the_artifacts_say`
(tests/test_remaining_commands.py:L35) asserts the step name only.

So the changed line's behavior — that `resume` writes `auto: true` for `plan` and
`auto: false` for `clarify` — rests on the type checker and on `__post_init__`,
not on a test. Given the project's own framing that `next-step.md` and the
printed line are "two views of one payload", the cheap fix is to extend
`test_the_file_an_agent_reads_names_the_command_status_prints` (already
parametrized over both commands) with an `auto:` assertion, or to parametrize the
`test_storyctl.py` auto cases over `["next", "resume"]`.

I traced the refactor for behavior equivalence and found none beyond NIT 1:
`report.next_command` is `next_step_content(_current_step_name(raw), repo_root,
spec_dir)[0] or None`, and `report.current` is `None` only when that command is
empty — which `_current_step_name` produces only for `"complete"`, since every
other name it can return is a `_STEPS` key. So old
`next_step_content(step_name, repo_root, spec_dir)` and new `report.next_command`
agree on every input, including the `implement` → `wfctl verify` route.

## NIT — the event log's `auto` now disagrees between `next` and `resume`

On a finished story `resume` appends `auto: null` (wfctl/cli.py:L326, since
`report.auto` is `None`) where it previously appended `false`; `next` still
appends `false` (wfctl/cli.py:L285). No code reads that field — `events.jsonl` is
consumed only by `_session.py:L49` and `cli.py:L396`, neither of which touches
`auto` — so nothing breaks, and `null` is arguably the more honest value for
"there is no next step". But two commands now write different values for the same
situation into the same key, which is the kind of divergence this codebase
usually closes deliberately. Either normalize (`auto=report.auto or False`) or
change `next` to log `None` when there is no command.

## NIT — the alias assignment at wfctl/cli.py:L315

```python
command, auto = report.next_command or "", report.auto
```

The tuple shape is a fossil of the `next_step_content(...)` call it replaced; it
now reads as an unpack that unpacks nothing. `if report.next_command:` with the
fields used directly drops both locals and removes the `or ""` that exists only
to make an empty string falsy where `None` already is. `step_name` is still
needed for the event and the console line, so only these two go.

## NIT — `next_cmd` is now the last hand-rolled inference

`next_cmd` (wfctl/cli.py:L250–L273) still does `_infer_steps` +
`_current_step_name` + `next_step_content` where `resume` now reads the payload.
It writes `next-step.md`, which is a view, so under `pipeline-state-is-one-payload`
it is the remaining second inference path. Pre-existing and explicitly outside
#118's scope (the issue names `resume`, `status --json` and the skill), and per
the skill's step 6 it should be filed rather than smuggled in — but this diff is
what makes it the odd one out, so it is worth an issue now.

## Passes run, and what each checked

**1. Correctness.** Traced `build_report` → `next_step_content` → `_STEPS` and
`_current_step_name` for equivalence of the `resume` refactor (equivalent on
every input, see above). Checked the widened invariant
`len({current is None, next_command is None, auto is None}) != 1` — a set of
three booleans is never empty, so `!= 1` and `> 1` are the same test and the
"all three agree" reading is correct; `auto=auto if command else None` cannot
produce a `False`/`None` confusion because the guard is on `command`, not on
`auto`. Walked the skill's step 4 branches against every value the payload can
carry, including `next_command == "wfctl verify"` (auto is `False` there, so the
"strip the leading `/`" branch is unreachable for it). Found the gate bypass
above.

**2. Security.** No untrusted input, no secrets, no shell interpolation added.
Net positive: step 3 now parses JSON from a subprocess instead of scraping a
markdown file whose contents an agent could otherwise have influenced.

**3. Architecture.** Conforms to both in-force records.
`pipeline-state-is-one-payload`: `resume` stops being a second inference path and
becomes a rendering of the payload; `--json` gains a field rather than a branch.
`session-state-is-re-derived`: the skill stops treating `next-step.md` as
authoritative for a value that is recomputable — the record's exact prohibition.
The record's own field list in `docs/architecture/pipeline-state-is-one-payload.md`
does not enumerate `next_command` or `session_started` either, so `auto` needs no
amendment there. `next_cmd` remains off the payload (NIT 6).

**4. Readability & simplification.** Comments explain *why this shape* and match
the file's density; the deleted `resume` comment was correctly replaced rather
than dropped, and the `__post_init__` comment was extended instead of restated.
Test docstrings name the defect they exist for, per `CLAUDE.md`. The new test's
comment about `spec_tree` accumulating into one directory is accurate —
`conftest.py:L263–L269` uses `mkdir(exist_ok=True)` on a fixed path — so the
ordering dependency it warns about is real and documented. One fossil shape
(NIT 5).

**5. Performance.** An orchestrate cycle now runs three inferences
(`status`, `resume`, `status --json`) where it ran two plus a file read. Each is
a handful of `stat`/`read_text` calls over one spec dir, plus at most one
`_verification_block` for a done-but-unverified `implement`; sub-millisecond
against a subprocess launch that is already tens of milliseconds. Not a finding.

**6. Over-engineering.** Nothing speculative: `auto` has a caller on day one, no
new abstraction, no config, no flag. The invariant widening is three fields in
one set rather than a second `if`. Only NIT 5's two lines are removable.
