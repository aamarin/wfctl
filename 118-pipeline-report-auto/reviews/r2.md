## BLOCKER — the design gate is walked past on the orchestrated path

`wfctl/agents/skills/speckit-orchestrate/SKILL.md:L59-67`

**The defect.** Step 2 runs `wfctl resume`, which is gated:
`wfctl/cli.py:L309` calls `_refuse_unless_boundary_answered` and exits 1 before
writing anything. Step 3 now runs `wfctl status --json`. `status_cmd`
(`wfctl/cli.py:L152-179`) does **not** call that gate — `grep` confirms the only two
call sites are `next_cmd:L265` and `resume_cmd:L309`. So `--json` cheerfully hands
back the command the gate just refused to hand back.

The concrete sequence, from the code paths involved:

1. `/speckit.brainstorm` completes and writes `design.md`. The boundary question
   is unanswered — no arch record on this branch, no `wfctl arch none`.
2. Step 2: `wfctl resume` prints `DESIGN_GATE_REFUSAL` and exits 1.
   `next-step.md` is deliberately **not** written (`_refuse_unless_boundary_answered`
   docstring: "Before the file is written, never after… a refusal that still wrote
   it would be a message nothing acts on").
3. Step 3: `wfctl status --json`. `design_gate` fires only inside the refusal
   helper, so `build_report` returns
   `{"current": "specify", "next_command": "/speckit.specify", "auto": true}` —
   `_STEPS["specify"] == ("/speckit.specify", True)`.
4. Step 4, branch `auto is true`: the agent emits
   `EXECUTE_COMMAND: speckit.specify`.

The pipeline self-executes straight past a refusal whose entire reason for existing
is to stop that. `test_resume_is_gated_too` (`tests/test_pipeline_commands.py:L329`)
states the intent in its own docstring: "`speckit-orchestrate` advances the pipeline
with `wfctl resume`, not `wfctl next` — so a gate wired only into `next` is walked
past by the one path that actually runs." This diff re-opens that hole one layer up,
in the skill rather than in the CLI, which is why no test catches it.

**This is a regression, not a pre-existing hole.** Under the old step 3 the agent
read `next-step.md`, which the refusal left holding the *previous* write —
in the normal sequence `Next step: /speckit.brainstorm` / `auto: false`, so the
agent displayed "Next: run `/speckit.brainstorm` when ready" and stopped. Stale and
badly worded, but it stopped. If the file did not exist at all, the `Read` failed
and the agent stopped. Neither old path auto-advanced.

**Second instance of the same shape.** `resume_cmd:L297-299` also exits 1 with
`_NO_SESSION` when no session is recorded. `status --json` has no such check either
(it exposes `session_started` but the skill never reads it), so a no-session run also
falls through step 2 into an `EXECUTE_COMMAND`. One fix covers both.

**Fix — pick one:**

*A (smallest).* Make step 2 terminal on failure. One sentence closes both instances:

> 2. Run `wfctl resume`. It re-infers the step, records the advance, and refuses
>    here if the boundary question went unanswered or no session is open — none of
>    which the read below does. **If it exits non-zero, display its output verbatim
>    and stop. Do not run step 3: `wfctl status --json` is not gated and will hand
>    back the command `resume` just refused.**

*B (better, larger).* Give `resume` a `--json` flag and collapse steps 2 and 3 into
one gated command. That is the shape `pipeline-state-is-one-payload` actually wants:
today the skill reads pipeline state three times in three processes (`status`,
`resume`, `status --json`) while the diff's own commit rationale is that a second read
of the same artifacts can disagree with the first. B removes the gate hole *and* the
extra inference; A only removes the gate hole. A is fine to land now with B filed.

Either way the fix is in the skill, so per CLAUDE.md it is not verified by
`uv run pytest` alone — `uv run wfctl install-skills` and exercise the refusal path.

## WARNING — `resume` and `next` now disagree about `auto` when the story is complete

`wfctl/cli.py:L315` and `L326`, against `L285`.

`command, auto = report.next_command or "", report.auto`. On the terminal position
`build_report` sets `auto=None` (`_pipeline.py:L439`, `auto if command else None`),
so `append_event(agent_dir, "resume", …, auto=auto)` writes `"auto": null`.

Before this diff, `resume` called `next_step_content("complete", …)`, which returns
`("", False)` by the `_STEPS.get(step, ("", False))` default — so it logged
`"auto": false`. `next_cmd:L285` still logs `"auto": false` on that same path,
because it still makes that call at `L273`.

Two writers of the same event field now produce different values for the same
pipeline position. It is user-visible: `wfctl log` (`cli.py:L390-420`) prints every
non-`ts`/`event` key, so the log renders `auto=None` for a `resume` line and
`auto=False` for a `next` line describing the identical state. Nothing else reads it
(`grep events.jsonl` → `_session.session_started`, which looks only at `event ==
"start"`), which is why this is a WARNING and not a BLOCKER.

Either value is defensible — `null` arguably reads better ("no step, so no flag") —
but the two commands should not each pick a different one silently.

**Fix:** `append_event(agent_dir, "resume", …, auto=bool(auto))` to preserve the
prior shape, or, if `null` is the deliberate choice, change `next_cmd:L285` to match
and say so in the commit body.

## NIT — the invariant check is clever where it could be plain

`wfctl/_pipeline.py:L413`

```python
if len({self.current is None, self.next_command is None, self.auto is None}) != 1:
```

Correct — a set of booleans has cardinality 1 exactly when all three agree — but it
reads as an idiom before it reads as a rule, and the rubric's readability pass calls
out "clever tricks that need a mental pause". The comment above it explains *why the
three are bound*, not *what the line computes*, which is right; the line itself is
the part that costs the pause.

**Fix:**

```python
absent = (self.current is None, self.next_command is None, self.auto is None)
if any(absent) and not all(absent):
```

Same length, no pause. Author's call.

## What each pass checked and found clean

**1. Correctness.** Traced `build_report` → `_infer_steps` → `_current_step_name` →
`next_step_content` → `_STEPS`, and both `resume_cmd` and `next_cmd` end to end.

- The three-way invariant is *derivable*, not merely asserted: `build_report` keys
  `current`, `next_command` and `auto` off the same `command` truthiness
  (`L437-439`), so it cannot construct a report that trips its own `__post_init__`.
- Terminal position: `_current_step_name` returns `"complete"`,
  `next_step_content` falls through `_STEPS.get` to `("", False)`, `command` is
  falsy, all three fields become `None`, and `step_name = report.current or
  "complete"` reproduces the string the gate and the event log used before.
  The `--json` `next_command: null` that step 4 branches on is correct.
- `auto_str = "true" if auto else "false"` is only reached under `if command:`,
  where `auto` is a real bool — no `None`-renders-as-`false` path.
- The `implement` → `wfctl verify` routing (`next_step_content:L376-381`) survives:
  `build_report` passes `repo_root` and `spec_dir`, so `resume` reading off the
  report gets `("wfctl verify", False)` exactly as the direct call did. This was the
  live risk in swapping the call for a field read, and it is handled.
- `--json` payload key order and shape: `auto` added alongside `next_command`,
  serialized by `console.print_json`; `bool | None` round-trips as `true`/`false`/
  `null`, which is what the skill branches on.

**2. Security.** Nothing here touches input parsing, subprocess arguments, secrets,
or file paths derived from untrusted data. `auto` is a bool sourced from a module
constant table. The skill emits `EXECUTE_COMMAND: {command-without-slash}` from
`_STEPS` values only — no user string reaches it. One security-adjacent note is the
BLOCKER: a control that exists to stop unattended execution is bypassable, which is
an authorization-shaped failure even though no credential is involved.

**3. Architecture.** The `_pipeline.py` and `cli.py` half moves *toward*
`pipeline-state-is-one-payload` and `session-state-is-re-derived` — one inference,
every view a rendering, `auto` no longer reachable only through a written file. The
skill half is the tension: it swaps a stale-file read for a third live inference in a
third process rather than for the payload the gated command already computed. Not a
violation (it does re-derive, which is what `session-state-is-re-derived` asks), but
fix B above is the version that satisfies both records.

`next-step.md` remains written by `next` and `resume` and now read by nobody in the
shipped skills (`grep` over `wfctl/agents/`: only `using-wfctl/SKILL.md` describes
it). That is the deliberate out-of-scope call stated in the issue; noting it so the
follow-up has the fact.

**4. Readability.** Names are honest (`auto` matches `_STEPS`'s own column and the
`next-step.md` key). No nesting added, no function grew past a screen. Two NITs above.

**5. Performance.** Irrelevant at this scale — the change *removes* one
`_infer_steps` walk per `resume`. The skill adds one extra `wfctl` process
invocation per orchestrate cycle, which is milliseconds and not worth a finding on
its own; it matters only as the mechanism of the BLOCKER.

**6. Over-engineering.** Nothing speculative: `auto: bool | None` has one producer
and three consumers; no new abstraction, no flag nobody sets, no dependency. The only
`shrink:` is the comment at `cli.py:L311-314`. `net: −3 lines possible.`

**Tests.** Read first, per the rubric.

- `test_the_report_carries_the_auto_flag_of_the_step_that_is_current` asserts
  `(current, auto)` off a report `build_report` actually built, and its docstring
  says why that matters ("constructing a `PipelineReport` by hand and checking the
  field exists tests the dataclass, not the defect"). That is the right axis and it
  would have failed on `main`.
- `test_a_report_with_a_command_and_no_auto_flag_cannot_be_built` covers the new leg
  of the invariant; the set-cardinality form covers the other mixed combinations,
  so one negative test is enough.
- Both docstrings name the failure rather than restating the assertion, per
  CLAUDE.md. The inline comment about `spec_tree` accumulating into one directory is
  the kind of fixture fact the next reader needs.
- **The gap is the BLOCKER.** No test exercises `resume` refusing and then `status
  --json` answering, because the sequencing lives in a markdown skill and the suite
  "checks that skills ship and cross-reference correctly, not that they read well"
  (CLAUDE.md). A test that asserts `status --json` is *deliberately* ungated —
  paired with a skill that stops on a non-zero `resume` — would pin the contract the
  skill now depends on. Worth adding beside `test_resume_is_gated_too`.
