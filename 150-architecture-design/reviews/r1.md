### NIT tests:20-22 — the guard's comment overstates what the regex covers

```python
# … `wfctl verify` records `inconclusive`. Matched case-sensitively — the skill's
# prose says a driver must be specific enough to fail, and lowercase "fail" is
# that sentence, not a verdict.
_VERDICTS = re.compile(r"\b(PASS|FAIL|BLOCKED|INCONCLUSIVE)\b")
```

Two small mismatches between the comment and the pattern:

- `wfctl verify` records the token as lowercase `inconclusive`
  (`wfctl/_verify.py:219,231`). The pattern only matches `INCONCLUSIVE`, so the
  spelling the comment cites as in force is the one spelling the test cannot
  catch — and `SKILL.md:57` already contains "inconclusive-evidence", which is
  why blanket-lowercasing is not the fix. Either drop `inconclusive` from the
  comment's list of guarded tokens, or add a targeted lowercase alternative and
  say why `inconclusive-evidence` is exempt.
- `BLOCKED` is in force nowhere in the bundle (`grep` across
  `skills/*/SKILL.md` and `commands/*.md` returns only `speckit-implement`'s
  PASS/FAIL, `verification-before-completion`'s FAIL, and this skill's
  `inconclusive`). Guarding a word #100 might mint is defensible, but the
  comment presents all four as already in force.

Neither weakens the test's real value — it is a cheap static tripwire on a
guarantee that otherwise has no enforcement, and it does fail if a `PASS` is
added.
