WARNING  `wfctl/agents/trackers/github-issue-create.sh:L57` — an issue added with
`--project` lands on the board with **no Status**, which is the second symptom #232
measures. Verified live today:

```
$ gh api graphql -f query='{user(login:"aamarin"){projectV2(number:1){
    workflows(first:20){nodes{name enabled}}}}}'
   ✗ Item added to project        (still disabled)
```

#232's own table reads "Item added to project | off means an added item gets no
status | 21 items with no status", and `opening-a-change` Step 6 already states the
rule for the PR side in as many words: "`--add-project` … only *adds* the item. The
board's 'item added' workflow then writes the default status … Set it deliberately."
This change adopts the half of that instruction the skill warns is not enough. Every
issue `wfctl issue create` files from now on joins the statusless population that had
to be reconciled by hand the same afternoon. `github-board.sh` is already in the
bundle and already does this write.
→ Fix: `gh issue create` prints the new issue's URL on stdout; capture it, take the
trailing number, and follow a successful `--project` create with
`bash "$(dirname "$0")/github-board.sh" "$num" Todo`. If that is deliberately out of
scope, say so in the header block — the file argues its other boundaries and is
silent on this one.

WARNING  `wfctl/agents/trackers/github.json:L10` — the board title `"wfctl"` is a
literal in the config that `install-skills --tracker github` writes into *every*
repository that installs this tracker. Two consequences, neither of them this repo's:

1. For any other repository under an owner who has a project titled `wfctl`, the
   lookup succeeds and the issue is filed onto **wfctl's** board. Verified:
   `gh project list --owner aamarin --format json --jq '[.projects[].title]'` →
   `["wfctl"]`, exactly one project, so every other repo of this owner that installs
   the tracker hits this.
2. For everyone else, every `wfctl issue create` prints
   `ℹ no project titled 'wfctl' — filing without a board` forever, naming a project
   the user has never heard of and giving no hint that the name is settable.

The escape hatch is weak: in a consuming project `.agents/trackers/*.json` is not
added to `gitignore_targets` by the installer, so it can be committed and edited —
but in **this** repo `.gitignore:L12` ignores `.agents/` wholesale, and
`/start-session` re-runs `install-skills --from <path> --yes`, which re-plans the
tracker files. A hand-edited board name is not durable on the path the tool actually
takes.
→ Fix (in preference order): (a) resolve the board from the repository's own linked
projects rather than a shipped title; (b) put the board title in
`.wf-skills-manifest.json` and pass it via a placeholder, which puts repo-specific
data where repo-specific data lives; (c) at minimum, ship the token empty — the
`""` path is already implemented and tested (`test_create_script_skips_the_lookup…`)
— and document the one-token edit. Note `knowledge-placement`: a board title is a
fact about one repository, and a generated file is not where it belongs.

WARNING  `wfctl/agents/trackers/github-issue-create.sh:L46` — the lookup can report
"no board" for a board that exists, and that false negative reproduces #232 exactly:
issue filed, off the board, exit 0, one informational line, nothing downstream
notices. Two mechanisms:

- `gh project list` defaults to `--limit 30` (`gh project list --help`:
  `-L, --limit int  Maximum number of projects to fetch (default 30)`). An owner
  with 31+ projects can have the board silently missed.
- The lookup is **owner-scoped**, while `gh issue create --project` resolves a title
  against the repository's projects as well as the owner's. A board linked to the
  repo but owned elsewhere reads as absent here and would have been found by `gh`.

→ Fix: `--limit 100` on the listing (one token), and either widen the lookup to the
repo's linked projects or record in the header why owner-scope is the intended
answer. Separately, the two `ℹ` branches at L49 and L51 are not equally ordinary —
L49 is a misconfiguration (the file's own header says the `project` scope is *not*
granted by `gh auth login`), L51 is a legitimate absence. Distinguish them in the
output (`⚠` vs `ℹ`); note that moving L49 to stderr would make it *invisible*, since
`_tracker.dispatch` prints stderr only when the exit code is non-zero.

WARNING  `wfctl/agents/trackers/github-issue-create.sh:L42` — a board-side lookup
failure costs the filing, which contradicts the invariant the file and its test both
state. Reproduced with a stub whose `gh repo view` exits 1:

```
$ CALLS=… REPO_VIEW_FAIL=1 bash github-issue-create.sh "t" "b" "wfctl"
gh: could not resolve repo
rc=1
ARGV: repo view --json owner --jq .owner.login      # and nothing else
```

Nothing was filed. The header says "*no* board is an ordinary outcome, reported and
carried past", and the parametrized test's docstring says "The issue is filed in all
four. Nothing here is allowed to cost a filing." This is the fifth row, it does not
hold, and it is the one branch with no test. Practical impact is limited — a `gh`
broken enough to fail `repo view` will usually fail `issue create` too — but a
header block that asserts an invariant the code does not hold is precisely what
`CLAUDE.md`'s comment rule is protecting against.
→ Fix: `owner=$(gh repo view …) || owner=""`, treat an empty owner as the L49
branch, and add the row to the parametrize table.

WARNING  `tests/test_tracker.py` — nothing pins the shipped `create` argv's *shape*.
`test_shipped_github_config_is_valid_and_its_argv_paths_exist` only asserts that
tokens starting with `.agents/trackers/` name a file that exists, so deleting the
`"wfctl"` token from `github.json:L10` — or reordering `{title}`/`{body}` — leaves
the whole suite green while every issue files boardless. That is the same drift
class the diff's own new docstring names ("a second copy of that tuple is what goes
stale"), one file over. The script is well covered; the wiring that invokes it is
not.
→ Fix: one assertion on the shipped config, e.g. that `verbs["create"]` ends with
`["{title}", "{body}", <board>]` and that its board token is non-empty (or exactly
the intended value, once F2 settles what that is).

NIT  `tests/test_tracker.py:L271` — `_GITHUB_TRACKER_FILES[1:]` encodes "element 0
is the JSON config" by index. Reordering the tuple would write a bash stub named
`github.json` and skip a script, and the install assertion would still pass.
→ Fix: `for script in (f for f in _GITHUB_TRACKER_FILES if f.endswith(".sh")):`.

NIT  `tests/test_tracker.py:L734,L766` — rows 1 and 4 of the table pass `note=""`, so
`assert note in result.stdout` is vacuously true for them and the table reads as
though it checks four outputs when it checks two. Row 1 in particular has something
worth asserting: on the happy path nothing about a board should be printed at all.
→ Fix: assert `"board" not in result.stdout` when `note` is empty, mirroring what
`test_create_script_skips_the_lookup_when_no_board_is_named` already does.

## Passes that found nothing, and what was checked in each

**Security.** The injection surface is the one the diff names and it holds. The
script is reached as argv tokens from `_tracker.dispatch` (`subprocess.run(argv,
…)`, no `shell=True`), `title`/`body`/`board` are only ever expanded inside `"$…"`
and appended to an array, and `gh issue create "${args[@]}"` is the single
expansion point — no `eval`, no command string, no `$(…)` re-entry. The canary test
is real, not decorative: it passes ``$(touch …) `touch …` `` as the title and
asserts both that the file was not created and that the token reached `--title`
byte-for-byte, so deleting the quoting fires it. The board title reaches `jq` via
`env.WFCTL_BOARD` rather than being spliced into the filter text, matching
`github-board.sh`'s handling of `WFCTL_BOARD_STATUS` — correct, and the reason is
written down. No secrets, no logging of credentials, `--project` scope requirement
documented in-file. Manually confirmed a title beginning with `--` is consumed as
`--title`'s value and cannot smuggle a flag.

**Architecture.** Fits the established seam rather than inventing one. "A verb whose
backend needs more than one call is still one argv. Point it at a script the backend
ships beside its config" is `scaffold-tracker` SKILL.md's own rule, and this is its
second instance. The board name lives in the *backend's* config, not in the caller,
which respects the constraint that skill states for `start`/`stop` ("a board name in
the caller would make every consumer of this contract know one tracker's column
vocabulary") — the objection in F2 is to the shipped *value*, not to its location in
the layer. `_GITHUB_TRACKER_FILES` was already the right seam and extending it was
enough: `_tracker_files()` feeds both the inheritance gap-fill (`cli.py:L2191`) and
`doctor`'s prune protection (`cli.py:L2547`), so the new script is covered by both
without further edits. Verified against `layer-model` (source under `wfctl/agents/`,
generated tree at `.agents/`) and `install-modes`; `MANIFEST.in` grafts the tree, so
the new `.sh` ships without a packaging change. No new pattern, no cycle, no
duplication with `github-board.sh`.

**Correctness (beyond the findings).** Traced every branch. Exit codes: 2 on empty
title (checked), 1 on a board that refuses (checked, and the test asserts `--project`
was actually on the create argv rather than only that the run failed), and otherwise
`gh issue create`'s own status, since it is the last command. `set -uo pipefail`
without `-e` is correct here — every failure is handled explicitly and `-e` would
turn the `if !` lookup into an abort. `--body ""` is accepted by `gh` and matches the
pre-change behavior. A count of 2+ matching projects passes `--project` and lets `gh`
decide, which is consistent with the stated "a named board that refuses is an error"
rule; reproduced, and it is defensible rather than a defect. The `ℹ` lines land on
stdout, which is the only stream `dispatch` prints on success — correct choice.
Backward compatibility of the config change checked: a repo that installed the old
tracker and hits the inheritance path gets `tracker_skip_existing`, so it receives
the new script and keeps the old `create` verb — degraded to the previous behavior,
not broken.

**Performance.** Two extra API round-trips (~300–600ms) per `wfctl issue create` when
a board is named; zero when it is not, and the diff has a dedicated test asserting
the zero (`test_create_script_skips_the_lookup_when_no_board_is_named` asserts the
recorded call list is exactly `[["issue","create"]]`). `create` is not a hot path.
Nothing to raise.

**Readability & over-engineering.** Comment-to-code ratio is high (≈30 lines of
header on 27 lines of shell) and that is this repo's house style — the header
explains *why this shape*, names the rejected alternative (`gh issue create --project`
alone, and matching gh's error text), and states the operator prerequisite. It reads
as instruction to the next maintainer, not narration of the diff, which is what
`CLAUDE.md` asks for. Test names are sentences, docstrings name the failure each
test exists to catch. Nothing dead, nothing speculative, no abstraction with one
implementation, no hand-rolled stdlib. The `_CALL` sentinel with one-token-per-line
recording is the minimum that can distinguish `--project` as an argument from
`--project` inside a title, and the docstring says exactly that. I found nothing to
delete.

**Residual gap, not a finding.** The change closes the `wfctl issue create` path
only. #232 attributes 17 of 23 misses to "unattended worktree agents … which file
issues for what they find and have no instruction that says a board exists" — an
agent that reaches for `gh issue create` directly still bypasses this, and no rule
or check says not to. `end-session` SKILL.md:L149 is the only place in the bundle
that files an issue and it does use `wfctl issue create`, so nothing shipped is
wrong; the exposure is instructions that do not exist. Per
`a-rule-is-expressed-as-a-check`, worth a follow-up issue rather than a scope
expansion here.
