## Findings

WARNING  `wfctl/agents/trackers/github-issue-create.sh:L42` — a failing
`gh repo view` costs the filing, which the file promises it never does.

The lookup is two calls. The second one (`gh project list`) degrades: it prints
`ℹ could not read …` and files anyway. The first one does not — `|| exit 1`
aborts before `gh issue create` is ever reached. So a rate limit, a network
blip, or `gh` not being authenticated at that instant means **no issue is
filed**, and the only thing on screen is gh's own error, which says nothing
about a board. Verified:

```
$ CALLS=… PATH=<stub>:$PATH bash wfctl/agents/trackers/github-issue-create.sh t b wfctl
gh: API rate limit exceeded
rc=1
--- calls ---
ARGS:repo view --json owner --jq .owner.login
```

That contradicts the file's own header — "*no* board is an ordinary outcome,
reported and carried past … so that a board outage cannot read as a board that
was never configured" — and contradicts the test that states the invariant in
one line: `tests/test_tracker.py:L751` "The issue is filed in all four. Nothing
here is allowed to cost a filing." Both calls are board resolution; only one of
them degrades, and nothing explains why.

Fix — make the owner lookup fail the same way its sibling does, and give it a
row in the existing table:

```bash
if ! owner=$(gh repo view --json owner --jq '.owner.login'); then
  echo "ℹ could not read this repository's owner — filing without a board"
elif ! found=$(WFCTL_BOARD="$board" gh project list …); then
  …
```

WARNING  `wfctl/agents/trackers/github.json:L10` — the shipped default hardcodes
*this* repository's board title, with no supported way for a consumer to change
it.

`"wfctl"` is a proper noun, not a preference. In every other repo that installs
this tracker, each `wfctl issue create` now costs two extra API calls and prints
`ℹ no project titled 'wfctl' — filing without a board` — an explanation of the
absence of a thing that repo never had. The script's own header calls the
skipped-lookup case out as something that must be free ("`wfctl issue create`
runs where a person is waiting"); the shipped config denies that to everyone but
this repo.

Editing the installed `github.json` is not the escape hatch it looks like: the
next `install-skills --tracker github` re-copies the bundle's copy and lists it
as a foreign overwrite. #232 named the constraint — "the tracker abstraction has
no concept of a board" — and this is where that bites.

Cheapest fix that keeps the default: let the environment win inside the script,
which changes nothing here and costs a consumer one line in their shell profile
or hook.

```bash
board=${WFCTL_BOARD_TITLE:-${3:-}}
```

(Then rename the jq-side variable so the two do not collide.) Alternative:
default to the repository name when the third argument is empty — self-correct
for anyone whose board is named after the repo, which is the common shape.

WARNING  delivery — the fix does not reach a repo that already installed the
tracker.

`cli.py:L2376` copies tracker files only `if tracker == "github"`, i.e. only
when *this run* selected one. The inherit-and-fill branch at `L2167-2197` — the
one that notices a missing file via `_tracker_files` — is gated on
`tracker is None and "tracker" not in manifest`, so it never runs in a repo whose

`install-skills --yes` will not deliver `github-issue-create.sh` or the new

The half-state is at least safe (old config keeps naming plain `gh issue
create`, so nothing exits 127), and the mechanism predates this diff. But it
decides whether #232 is closed anywhere except the worktree it was written in.
Either widen the fill branch to run whenever `_tracker_files` reports a missing
file, or file the follow-up and say so in the PR body.

NIT  `wfctl/agents/trackers/github-issue-create.sh:L50` — the `elif` treats
anything that is not the literal `0` as "the board exists", empty string
included. A successful call that prints nothing therefore passes `--project` and
loses the filing to gh's resolution error. Verified:

```
$ # stub: `project list` exits 0 with no stdout
ARGS:project list --owner owner --format json --jq [.projects[] | …] | length
ARGS:issue create --title t --body b --project wfctl
rc=0
```

Unlikely — `[…] | length` always emits a number when the filter runs — but the
guard is free: `elif [[ ! "$found" =~ ^[1-9][0-9]*$ ]]` folds the empty and
malformed cases into the "could not read" branch that already exists.

NIT  `wfctl/agents/trackers/github-issue-create.sh:L15` — "exits non-zero with
nothing filed" overstates gh's guarantee. gh resolves `--project` titles before
the create mutation (which is what the paragraph above it correctly relies on)
but performs the *add* after the issue exists. A board that resolves and then
refuses the item leaves the issue filed and this script exiting 1 — and an agent
reading that exit code as "nothing happened" files a duplicate on retry. Narrow
the claim to the case it holds for: "nothing filed when the board cannot be
resolved."

NIT  `tests/test_tracker.py:L738` — row `("", "0", False, "")` is fully subsumed
by `test_create_script_skips_the_lookup_when_no_board_is_named`, which asserts
strictly more about the same input (call count, and that `board` never appears
in stdout). Drop the row.

NIT  `tests/test_tracker.py` — nothing pins the contract between the config and
the script's positionals. `test_shipped_github_config_is_valid_and_its_argv_paths_exist`
checks that the named file is shipped, not that argv slot 3 is the board;
swapping `$2` and `$3` in the script keeps the whole suite green because every
direct-invocation test passes the same order the script reads. One assertion on
`config["verbs"]["create"]` closes it.

**4. Readability.** Names are right (`found`, `board`, `args`). One `if/elif/

`env.` rather than filter text) and none of them narrate the diff. The test
docstrings name the failures they exist to catch, per the project's convention.
Nothing found beyond the header's overstated claim, filed as a NIT.

**5. Performance.** `wfctl issue create` now costs up to two extra round trips
