WARNING  github-issue-create.sh:L14-15,L53,L57 — the file's central promise, "a
named board that refuses the issue … exits non-zero with **nothing filed**", is
not what `gh issue create --project` does for a Projects **v2** board. gh builds
the issue first and adds the project afterwards (`api.IssueCreate` strips
`projectV2Ids` out of the `createIssue` mutation, runs the mutation, then calls
`UpdateProjectV2Items`; `createRun` prints `issue.URL` only after that returns).
So on an add failure — project write revoked, board archived between the two
calls, an API hiccup — the issue **exists**, its URL is **never printed**, and
the script exits 1. The caller reads "nothing filed", refiles, and the repo now
has a duplicate plus an orphan issue that is off the board and whose number
nobody knows: #232's own failure mode, produced by the fix for #232.
`test_create_script_fails_when_a_board_that_exists_refuses_the_issue` cannot
catch it — its stub creates nothing, so it asserts the exit code against a
premise that never holds.
→ Split the two calls the way `github-board.sh` already splits its two:
`url=$(gh issue create --title … --body …)`, echo the URL, then
`gh project item-add "$board" --owner "$owner" --url "$url"` and exit non-zero on
*that*. Filing and board-add become independently observable, the URL survives a
failed add, and the header comment becomes true as written (the promise changes
from "nothing filed" to "the issue exists, here it is, the board step is
unfinished"). Add a stub row where create succeeds and the add fails.
(I could not execute gh against the API from here — confirm the ordering before
merging. The fix above is the right shape either way.)

WARNING  github-issue-create.sh:L46 — `gh project list` caps at
`--limit 30` by default (verified: `gh project list --help`, gh 2.91.0,
`-L, --limit int  Maximum number of projects to fetch (default 30)`). An owner
with more than 30 open projects gets a listing that does not contain the board,
the script takes the `found == "0"` branch, and the issue is filed off the board
with a message saying the board does not exist. Silent recurrence of #232 for
exactly the heavy user the board exists for. Secondary: the lookup's search space
is narrower than the one gh's own `--project` resolution uses — gh matches a
title across the repository's, the organisation's *and* the viewer's v2 projects,
while this asks only for `--owner <repo owner>` — so a personal board tracking an
org repo reads as "no board".
→ `--limit 100` at minimum, and consider resolving over the same set gh does.

WARNING  github-issue-create.sh:L49-51 — the distinction the lookup exists to buy
is never acted on. The header argues at length (L16-18, L23-27) that "could not
read the projects" must not read as "there is no board", and the message does
distinguish them — but both branches then fall through to the same `exit 0` with
no board attached, and nothing downstream reads the message. A token without the
`project` scope (which `gh auth login` does **not** grant, per L23) therefore
files every issue in *this* repo off the board, quietly, exit 0. That is #232
verbatim: "no check anywhere notices."
→ A board that was *named* and could not be looked up is not an ordinary
outcome — file the issue, print its URL, and exit non-zero so the step is
observable as unfinished. Only "no board named" (empty `$3`) should be exit 0.
That is the asymmetry the issue asks to close.

WARNING  github.json:L9-10 — the board title `"wfctl"` is a literal in the config
that ships to **every** repo. `install-skills --tracker github` copies this file
verbatim, so any other project that adopts the GitHub tracker gets a `create`
verb that prints `ℹ no project titled 'wfctl' — filing without a board` on every
single issue, forever. Note the asymmetry with the sibling: `github-board.sh`
needs no board name at all — it discovers the board from the issue's
`projectItems` — so `create` is the only place in the shipped bundle that hard-
codes this repository's identity into another repository's config. There is also
no supported place to change it: `.agents/` is generated package output under
`layer-model`, and an explicit `--tracker github` rewrites `github.json` without
a prompt once wfctl's manifest already records it as installed (cli.py:L2378 only
skips on the *inheritance* path).
→ Make it resolvable rather than literal: default the board to the repository
name (`gh repo view --json name`) when the third argument is a sentinel, or read
it from `.wf-skills-manifest.json` / `WFCTL_BOARD`, which is per-repo state wfctl
already owns and does not overwrite.
