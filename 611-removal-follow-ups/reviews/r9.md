## BLOCKER: an entry that leaves the repository through a link and comes back stops every check

### What goes wrong

The removal hook runs `_archive.check()` inside a catch-all that warns and exits 0, so that a bug in the hook can't leave a worktree stuck. The check fills `edits`, `unmerged`, and `untracked` first, and then runs `_listed_paths`. When `_listed_paths` raises, `check()` never returns, and the refusals it already found are thrown away with it. The hook then lets the removal go ahead.

This commit adds a call that can raise. Line 325 resolves the entry's parent folder and calls `relative_to(root)` on it. `declared_paths` only checks that the entry itself resolves inside the repository, and never checks the parent. So an entry like `out/back` gets through when:

- `out` is a link to a folder outside the repository, and
- `outside/back` is an absolute link back to `<worktree>/.venv/notes`.

`declared_paths` accepts `out/back`, since it resolves inside. `path.parent.resolve()` is the outside folder, and `relative_to(root)` raises ValueError.

### Evidence

I ran this layout through `wfctl hook worktree-remove` from a scratch copy of 5fccf5d, with a staged edit to `README.md` and an untracked `untracked.md`:

```
exit: 0
⚠ worktree-remove failed ('…/outside' is not in the subpath of '…/wt' OR one path is relative and the other is absolute.) — continuing so the removal is not blocked
```

I ran the same layout with the parent commit's `_archive.py`:

```
exit: 1
✗ removal stopped — this worktree holds work saved nowhere else
  uncommitted edits:
    README.md
```

This means the commit regresses that layout from "removal stopped" to "removal goes ahead, and the uncommitted edit and the untracked file are deleted".

### Why it is a blocker despite being rare

The layout is unusual, since it needs a link out of the repository whose target links back in. I am rating it a blocker because the failure is data loss and it is deterministic, it is a regression against the parent commit, and the fix is one guard. The reconciler can downgrade it knowing that.

### Fix

Wrap line 325 in a `try`, and on ValueError append a `wfctl.json: … resolves outside the repository through a link — skipped` warning and `continue`. A stricter alternative is to refuse such an entry in `declared_paths`, so that `check config` reports it too. Either way, add a test that drives `hook worktree-remove` and asserts exit 1 with the edit named.

The wider exposure was already there before this commit. Any exception in `_listed_paths` or `declared_paths` turns into "removal goes ahead without the refusals". For example, `Path.resolve()` raises RuntimeError on a symlink loop in Python 3.11. Catching exceptions in `check()` around `_listed_paths`, and turning them into a warning, would protect the refusals from every future raise site. That is out of scope for this commit, so I'd file it as a follow-up.

## WARNING: the link-to-folder tests pass without the code they are named for

`_declare_save_on_remove` writes `.gitignore` as `notes/\nresearch/\n.venv/\nspecs/\n`. A pattern with a trailing slash matches only directories, and git treats a symlink as a file. So in `test_a_listed_link_to_a_folder_saves_what_the_folder_holds` and `test_a_listed_link_to_the_specs_folder_saves_the_spec_dir_once`, the link `notes` is untracked and not ignored, and it is saved through the untracked list whether or not `_listed_paths` records it. I confirmed this with a probe: `untracked: ['notes']`.

Mutation result: changing L332 to `if (root / at).is_symlink() and not path.is_dir():`, so a link to a folder is never recorded as a link, leaves all 77 tests in the two files green. That is the exact behaviour this commit changed, a top-level link to a folder saved as a link rather than as a folder.

Fix: in those two tests, write a `.gitignore` that ignores the link itself (`notes` with no slash), or assert `"notes" in _archive.check(...).listed_files`. With `notes` ignored, the current code still saves the link and the target. I probed that too: `files: ['notes']`, `folders: ['.venv/n']`.
