### Findings

WARNING  wfctl/_archive.py:L325 — The new `relative_to(root)` raises `ValueError` when an entry's parent folder resolves outside the repository but the entry resolves back inside. Here is an example:
- `wfctl.json` lists `ext/back/`.
- `ext` is a link to `/outside`.
- `/outside/back` is a link to `<worktree>/notes`.

`declared_paths` accepts this entry, because it only checks where the entry itself resolves. The exception escapes `_archive.check`, and the hook's catch-all prints "worktree-remove failed (...) — continuing so the removal is not blocked" and exits 0. This happens before any refusal is read. This means workmux deletes the worktree with uncommitted edits, unmerged commits, and untracked files all unchecked and unsaved. I reproduced this with a real uncommitted edit and an untracked `draft.md`, and the hook exited 0. At 1a0115e the same entry saved `ext/back/a.md` without error, so this is a regression. I rated it a WARNING rather than a BLOCKER only because the trigger needs a link out of the repository that points back in. The consequence is the data loss the hook exists to prevent, so the lead may reasonably upgrade it. → Make `declared_paths` refuse an entry whose parent resolves outside the root, using the same "resolves outside the repository" problem it already reports, so `check config` reports it too. At minimum, catch the `ValueError` at L325 and skip the entry with a warning.

WARNING  wfctl/_archive.py:L325, docs/architecture/removal-copy-destinations.md:L48 — When the link in a parent folder is ignored, a listed path is no longer saved at its listed path. For example, `lnk/todo.md` with `lnk` → `.venv/x` and `lnk` in `.gitignore` saves only `.venv/x/todo.md`. `lnk` itself is not listed and not untracked, so `unsaved/lnk/todo.md` doesn't exist. When `lnk` is untracked rather than ignored, `lnk` is saved as a link and the listed path works. That is the case the new test covers. The record's item 3 still says listed files are "copied ... also at their original paths", which is now false for this case. Nothing is lost, since the file is in the printed list, but you won't find it where you listed it. → Record each linked folder on the entry's path as a link in `listed_files`, at its own parent-resolved path, so the listed path resolves inside `unsaved/`. Otherwise, amend item 3 to say a path behind a link is saved at its real path.

WARNING  wfctl/_archive.py:L332 with L391 — An absolute listed link to a folder now saves worse than it did at 1a0115e. For example, `notes` → `<worktree>/.venv/n`, made with `ln -s "$PWD/.venv/n" notes`. Previously the folder's files were saved at `unsaved/notes/`. Now `unsaved/notes` is saved as a link to the deleted worktree's absolute path, and the files are at `unsaved/.venv/n/`, so the saved link dangles. Nothing is lost. The commit message accepts this outcome for a chain of links as rare. Absolute links are a common way to make a link, and the message doesn't mention them. → In `_copy_into`, write a link whose absolute target is inside the worktree as a relative link (`os.path.relpath(target, src.parent)`). Otherwise, add absolute links to the record's sentence on links.
