## Review: 1a0115e (fix(remove): follow a listed symlink so the folder or file it points at is saved)

Reviewer r4. Target is `git diff e1e4355..1a0115e`, read against the whole branch `origin/main..1a0115e`.

The commit does what it says. A listed link to a folder is copied as the folder again, which matches `main`, where `_listed_folders` used `is_dir()` and that follows links. A listed link to a file is saved as the link, and its target is saved beside it. The renamed test now fails when the check against the untracked list is removed (I confirmed this with a mutation). The new hook test pins the case where the spec dir goes to the `main` checkout. The `excluded` field going from a list to a single path is safe, because there is only one spec dir. `uv run pytest tests/test_archive_unsaved.py tests/test_worktree_remove.py` passes 72 tests, and ruff and mypy are clean on the changed files.

I found no blocker. The findings below are one inconsistency the commit introduces, two test gaps, and one bug from e1e4355 in the same area.

5. Performance. The change adds one `resolve()` for each listed link. Nothing found.
6. Over-engineering. `excluded` became a single path, which is shorter. `dict.fromkeys` is needed (see the second warning). Lean already.

**WARNING `wfctl/_archive.py:L321-324`, the spec-dir checks for a folder link use the unresolved path.** The commit resolves a file link's target before calling `in_spec_dir` (L328-329), but the folder branch still checks the path as it is written in `wfctl.json`. A listed link that points at the spec dir, or at a folder that holds it, is therefore copied whole, with no warning and no exclusion. This means the spec files are saved twice, which FR-018 rules out, and the line this commit adds to the `removal-copy-destinations` record ("A listed folder that holds the spec dir is copied without it") is not true for a link. I reproduced three cases:

- `myspec -> specs/40-feature`, with `myspec/` listed, saves `unsaved/myspec/spec.md`.
- `specs -> .data/specs`, with `specs/` listed, saves `unsaved/specs/40-feature/spec.md` and sets `excluded` to `None`.
- The same layout with no `main` checkout saves the spec dir twice inside `unsaved/`, once as `.data/specs/40-feature/` and once as `specs/40-feature/`.

No file is lost, and `main` had the same gap. I rate it a warning rather than a nit because this commit made file links resolve and left folder links unresolved, so the rule is now applied differently depending on what the link points at. To fix it, compute `resolved = path.resolve().relative_to(worktree.resolve())` once and use it for the `in_spec_dir` check and for the containment test. Then store the exclusion as the lexical path the copy will walk, `rel / spec_rel.relative_to(resolved)`, so that `ignore` in `_copy_into` still matches it.

**WARNING `wfctl/_archive.py:L425`, `dict.fromkeys` is untested.** I replaced it with a plain `check.listed_files` on a scratch copy, and all 72 tests in both files passed, along with `test_paths.py` and `test_copy_out.py`. The dedup is needed: an ignored link listed twice, such as `["notes/todo.md", "./notes/todo.md"]`, puts the same link in `listed_files` twice, and the second `os.symlink` raises. That raises `SaveFailed`, which stops every removal in that repository. With the current code, the probe saves it once. To fix it, add a test that lists an ignored link twice in two spellings and asserts exit code 0.

**WARNING `wfctl/_archive.py:L325-330`, the guard on a file link's target has no test.** I replaced `if not in_spec_dir(target):` with `if True:`, and every test still passed. Without the guard, a listed link to a file inside the spec dir saves that file into `unsaved/` as well, which is another FR-018 duplicate. To fix it, add one test with `s.md -> specs/40-feature/spec.md` listed, and assert that the link is saved and `unsaved/specs` doesn't exist.

**WARNING `wfctl/_archive.py:L325` and L375, a listed file reached through a link to a folder (from e1e4355, not this commit).** This comes from listing files, which e1e4355 added, but it is the same kind of path that 1a0115e says it handles. It goes like this:

1. `lnk -> .venv/real` is an untracked link and isn't ignored, so `.venv/` is ignored and `lnk` is not.
2. `lnk/todo.md` is listed in `wfctl.json`.
3. The untracked list saves `lnk` as a link first, and that link dangles in staging.
4. The listed file `lnk/todo.md` then runs `dest.parent.mkdir(exist_ok=True)` on that dangling link, which raises `FileExistsError`.
5. The removal stops with `SaveFailed: [Errno 17] File exists: .../unsaved.staging/lnk`.

This means the removal is refused every time until the user runs the `--force` command the hook prints. If `lnk` is ignored, the same listing saves without error. To fix it, list a file by its resolved parent, `Path(os.path.relpath(path.parent.resolve(), worktree.resolve())) / path.name`, so that no listed path in staging goes through a link. If it isn't fixed here, file a follow-up issue for it.

**NIT `wfctl/_archive.py:L328-330`, a saved link can dangle.** For a chain such as `todo -> .venv/mid -> todo.md`, the final file is saved, but the middle link is not, so `unsaved/todo` dangles. For an absolute link, the saved link points into the deleted worktree. In both cases the file's content is kept, so nothing is lost. A sentence in the docstring is enough.

**NIT `docs/architecture/removal-copy-destinations.md:L49-62`.** The record says listed files and folders are saved, but the rule that a listed link is followed while an untracked one is not exists only in the `_listed_paths` docstring. Separately, L62 ("keeping, through a list in `wfctl.json`. wfctl shouldn't guess, because generated folders and") is rewrapped about 20 characters longer than the lines around it.
