Reviewer r6. The commit does what its message says for the cases its tests build: a top-level listed link to a folder is copied as the folder again, as it was on `main`, and a listed link to a file is saved with the file it points at. The regression it fixes is real. I confirmed it against `origin/main`, where `_listed_folders` used `is_dir()` and so followed a link, and against e1e4355, where the link branch came first and saved only the link. ### Findings

WARNING  wfctl/_archive.py:L297-301, L420-421 — A listed link nested under another listed folder is not followed, so the folder it points at is deleted with the worktree. With `save_on_remove: ["notes/", "notes/link/"]` and `notes/link -> ../.venv/other`, the removal reports "saved 2 files", which are `notes/a.md` and the link `notes/link`, while `.venv/other/keep.md` is lost (probe A). The cause is the nested-folder filter in `save`, which drops `notes/link` because `notes` is its parent, and then `copytree(..., symlinks=True)` copies the link as a link. This is the same loss the commit fixes for a top-level link, and the new docstring says "A listed symlink is followed" without exception. `main` behaves the same way, so this is not a regression, but the commit now states an invariant that does not hold. → Treat a link to a folder the way the commit treats a link to a file: keep the link where it is, and add its resolved target to `folders` (skipping it when `in_spec_dir(target)` is true). The nesting case then works without special handling, because the parent's `copytree` carries the link and the target folder is saved beside it. The fix also covers the NIT on probe D below. The cost is that a top-level link to a folder is saved as a link plus `.venv/notes/`, not as a real `notes/` folder, so `test_a_listed_link_to_a_folder_saves_what_the_folder_holds` would change. If you would rather keep the folder copy, a narrower fix is to add the resolved target as a folder candidate only when the link sits under another listed folder. Either way, add a regression test for the nested case, or file a follow-up issue and narrow the docstring to top-level links.

NIT  wfctl/_archive.py:L327-330 — Only the final target of a chain of links is saved. With `notes/todo -> ../.venv/hop` and `.venv/hop -> todo.md`, `unsaved/` holds `notes/todo` and `.venv/todo.md` but not `.venv/hop`, so the saved link dangles (probe C). The content survives, so nothing is lost. → Save each hop by walking `os.readlink` until the path is no longer a link, or leave it and say in the docstring that only the final file is saved.

NIT  wfctl/_archive.py:L327-330 — A link to a tracked file copies that tracked file into `unsaved/` (probe G, where `notes/readme -> ../README.md` saves `README.md`). The record tells you to copy `unsaved/` back, and doing that would overwrite a newer `README.md` with the version from the removed worktree. → Add the target only when git does not track it, for example by checking it against `git ls-files`, or accept the copy and leave it.

NIT  wfctl/_archive.py:L321-324 — A listed link to a folder that holds the spec dir, such as `notes -> specs`, copies the spec dir a second time into `unsaved/notes/40-feature` (probe D). That breaks the FR-018 rule that spec files are saved only once, though nothing is lost. `main` did the same thing. The containment checks compare the unresolved `rel`, and a link hides containment from them. → The fix proposed for the WARNING covers this. Otherwise, compare against `path.resolve()` relative to the worktree.

### Out of scope for this commit, noted for a follow-up

`declared_paths` (wfctl/_archive.py:L250) calls `Path.resolve()` on every entry. On Python 3.11, which CI runs, that raises `RuntimeError: Symlink loop` for a listed link that loops, and I confirmed this with Python 3.11.14. This was already true on `main` (`declared_folders`), and 1a0115e does not touch it. I did not trace whether the removal hook's catch-all turns this into "removal goes ahead" or into a crash.
