## Review: 5fccf5d (git diff 1a0115e..5fccf5d), read against origin/main..5fccf5d

Reviewer r8. The commit does what its message says for every shape it names. A listed link to `specs/` no longer saves the spec dir twice, `lnk/todo.md` no longer stops the removal with "File exists", and a link listed inside a listed folder now saves its target. I confirmed each of these with the new tests and with probes. There are two problems that should be fixed before merge. The new parent resolution adds a way for `check()` to raise, and the removal hook lets a removal go ahead with nothing saved when `check()` raises. The other problem is that recording a link by its real parent path, which is the fix for the "File exists" class, has no test that fails when it is reverted.

### Passes run

1. Correctness. I traced `_listed_paths` into `save`, `_copy_into` and `_staging_files`, and into the hook's catch-all in `worktree_remove_cmd`. I ran ten edge-case probes against `_archive.check` and `save` on real git repositories. The shapes were a parent link that leaves the repository and comes back, a spec file reached through a parent link, an absolute link to a folder, an entry spelled `specs/<branch>/..`, two links to one folder, a link behind a link, a file behind an ignored parent link, and a symlink loop. I also ran eight mutations of the new lines against `tests/test_archive_unsaved.py`, plus a canary mutation that has to fail. The canary failed, so the probe copy was the code under test.
2. Security. The listed paths come from a committed `wfctl.json`, and I checked whether one could make the copy read or write outside the repository. It can't. `real` is checked against the root, and `at` is only used as a destination when it is a symlink, which a `..` final component never is. The probe for `a/b/..` confirmed that. The saved link holds `readlink` text that nothing follows. I found nothing in this pass.
3. Architecture. The change fits the existing shape. `save` deduplicates by path containment, and that is only correct if every candidate is a real path. Untracked paths from git are real paths, `extra` is resolved, and now the listed entries are too. The invariant holds, but `save`'s docstring doesn't state it. The change adds no dependency.
4. Readability. I read the new docstrings and test docstrings against the code, and checked the doc and release note against what the code does. The findings are below.
5. Performance. Each listed entry costs one or two extra `resolve()` calls, and the list has a handful of entries. There is nothing to report.
6. Over-engineering. I found two dead lines in the new tests, listed below. The `entries, limit = saved.shown, 20` binding in `cli.py` reads the `shown` property once instead of three times, and it is fine as written.

### Findings

WARNING  wfctl/_archive.py:L325 — `path.parent.resolve().relative_to(root)` raises `ValueError` when an entry's parent folder resolves outside the repository even though the entry itself resolves inside it. `declared_paths` only checks the entry, so it accepts such an entry. One example is `ext/back`, where `ext` links to a folder outside the worktree and that folder's `back` links back to the worktree's `notes/`. In my probe, `check()` raised `ValueError: '.../outside' is not in the subpath of '.../wt'`. In the removal hook, this exception goes to the catch-all, which prints "worktree-remove failed … continuing so the removal is not blocked" and exits 0. This means the untracked files are never saved, and the uncommitted-edit and unmerged-commit refusals that `check()` had already found are thrown away, so the removal deletes all of it. 1a0115e had no raise site like this, because it only resolved the entry and the target of a file link, and both are already known to be inside. The trigger needs a link layout that goes out of the repository and back, so it is rare. The consequence is the data loss the hook exists to prevent, and I would call it a blocker if that layout were common. → Wrap that line in a `try`, and on `ValueError` add a `wfctl.json: … resolves outside the repository — skipped` warning and `continue`. Alternatively, have `declared_paths` refuse an entry whose parent resolves outside, so `check config` reports it as well.

WARNING  tests/test_archive_unsaved.py (no test) — No test fails when the listed link is recorded as written instead of at its real parent path. I changed `found.listed_files.append(at.as_posix())` (L333) to append `rel`, and all 44 tests in the file still passed. That revert brings back the "File exists" stop the commit fixes, for a link instead of a file. The shape is a listed `lnk/inner/`, where `lnk` is an untracked link to `.venv/x` and `.venv/x/inner` is a link. With the revert, `save()` raised `[Errno 17] File exists: …/unsaved.staging/lnk`. With the real code, it saved `lnk -> .venv/x`, `.venv/x/inner -> ../y`, and `.venv/y/f.md`. The existing test `test_a_listed_file_behind_a_link_to_a_folder_is_saved` pins the same fix only for a file, through `real`. → Add that test with `.gitignore` set to `.venv/` only, so `lnk` is untracked, and assert exit 0 along with those three saved entries.

NIT  wfctl/_archive.py:L326 — Nothing tests the warning for an entry that reaches the spec dir through a parent link, such as `lnk/spec.md` where `lnk` links to `specs/<branch>`. When I changed `in_spec_dir(at)` to `in_spec_dir(rel)`, every test still passed. The file is still skipped in that case, because the later `in_spec_dir(real)` check catches it, but without the warning. → Add a test asserting "is the spec dir or inside it" for that entry, or accept that only the warning is unpinned.

NIT  tests/test_archive_unsaved.py:L785, L839 — Two of the new tests write `.gitignore` and then call `_declare_save_on_remove`, which writes `.gitignore` again with `notes/ research/ .venv/ specs/`. The first write is dead code, and it misleads the reader about what is ignored. Both tests still pass for the reason their docstrings give. → Delete the two lines.

NIT  docs/architecture/removal-copy-destinations.md:L50, L65 — Item 3 still says listed paths are copied "at their original paths". A listed file behind an ignored parent link is now saved only at its real path. In my probe, the entry `lnk/todo.md` was saved as `.venv/x/todo.md`, and neither the link `lnk` nor the path `lnk/todo.md` appears in `unsaved/`. Separately, the reflow in this commit left L65 at 95 characters while the other lines are under 80. → Add one sentence: "An entry reached through a link in its parent folders is saved at the path the link leads to." Then rewrap L62 - 66.

NIT  changes/611.fix.md — The new sentence, "A listed link is saved along with the file or folder it points at", reads as new behavior for both kinds. On `main`, a listed link to a folder was already saved, because `copytree` followed the link and copied the folder's contents to `unsaved/notes/`. What changes for a folder link is where the contents land. They now go to the target's own path, such as `unsaved/.venv/notes/`, and `unsaved/notes` becomes a link. With an absolute link, the saved `unsaved/notes` points into the deleted worktree. The contents are still saved, but you have to find them under the target path. → Say where the contents land: "A listed link is saved as a link, and the file or folder it points at is saved at its own path."

NIT  wfctl/_archive.py:L37 — The `UnsavedCheck` docstring says `listed_files` and `folders` are "the real paths of the `save_on_remove` entries that exist". A listed link is recorded at its real parent path plus its own name, not at the path it resolves to, and a listed link whose target is missing is recorded even though `exists()` is false for it. → "the paths of the `save_on_remove` entries with the links in their parent folders resolved, and the real path of what a listed link points at".

### Outside this commit

An entry spelled `specs/<branch>/..` is skipped as "the spec dir or inside it" even though it holds the spec dir, and that also predates this commit. Neither is a reason to hold 5fccf5d, and both could be filed together with the first warning.
