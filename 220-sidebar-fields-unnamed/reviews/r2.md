## Findings in detail

### WARNING — L204-211 the read-back still says "done when it carries the issue's set"

```
gh pr view <pr> --json labels,assignees,milestone,projectItems,reviewRequests

The step is done when that output carries the issue's set. An empty sidebar here
is this step unfinished, not a PR that happens to have no attributes.
```

The diff adds `reviewRequests` to the query and leaves the criterion alone. Two
consequences:

1. The new paragraph states outright that **an issue has no reviewers**
   (L185-186). So `reviewRequests: []` *always* "carries the issue's set". The
   field is now printed with nothing that can judge it, and an agent that reads
   the very next sentence concludes the step is done. That is issue #220's
   headline sentence — "its closing line declares the step done when the read-back
   'carries the issue's set' — so a PR can satisfy the skill exactly and still
   reach a reviewer with nothing on it" — still true after the fix.

2. The new bare-issue paragraph asserts that copying a bare issue "produces a PR
   the read-back below reports as unfinished". The read-back does not report
   that. For a bare issue, sentence one says done ("carries the issue's set" —
   the set is empty and the PR carries it) and sentence two says unfinished
   ("an empty sidebar here is this step unfinished"). #220 named this exact
   self-contradiction; this diff does not remove it, it makes the skill *depend*
   on the reader picking the second sentence.

This matters more than a normal prose nit because Step 4 (L123-126) stakes the
whole two-step design on the read-back being an observation: "A step can be
observed as unfinished. That is the whole reason the two are separate."

**Fix** — one sentence, e.g.:

> The step is done when that output carries the issue's set, plus whatever this
> step decided where the issue was bare, plus the readers this project relies on.
> Empty is never the answer here.

### WARNING — L207 the Development panel is instructed but never observed

Step 3 now requires `Closes #N`. Nothing checks it. `gh pr create --body-file`
writes whatever it is handed and never looks — the skill's own opening paragraph
says so — so a body that lost the keyword produces a PR whose Development panel
is empty, and Step 5's read-back reports success. Of the six fields in #220's
table this is now the only one with no verification at all, which is the same
shape as the reviewers gap the diff set out to close.

`gh pr view --json closingIssuesReferences` exists (confirmed against the field
list). **Fix:**

```bash
gh pr view <pr> --json labels,assignees,milestone,projectItems,reviewRequests,closingIssuesReferences
```

### WARNING — L193-196 the reviewers probe points at the wrong PR

```bash
gh pr view <pr> --json reviewRequests,latestReviews   # who arrived unasked
gh pr edit <pr> --add-reviewer <login>                # only who is missing
```

The prose above it says "Look at **an open PR nobody has touched**". The command
uses `<pr>`, and `<pr>` in every other Step 5 block — `gh pr edit <pr> ...`, the
jq `select((.content.number//0)==<pr>)`, the read-back — means *the PR you just
created*. An agent following the block literally queries its own seconds-old PR,
gets two empty lists, concludes nothing is missing and requests nobody: the
outcome the paragraph exists to prevent, and the same failure the read-back would
then wave through per the first finding.

**Fix** — separate the placeholder and show how to find one:

```bash
gh pr list --state open --limit 5 --json number,title     # pick one nobody touched
gh pr view <other-pr> --json reviewRequests,latestReviews # who arrived unasked
gh pr edit <pr> --add-reviewer <login>                    # on this PR, only who is missing
```

### WARNING — L185-196 the probe cannot answer the question it is asked

GitHub's `reviewRequests` is the *pending* list: submitting a review removes the
requester from it. So on the recommended probe target:

- **No review has landed yet** → `latestReviews` empty, `reviewRequests` shows
  only manual requests. You learn nothing about who self-subscribes.
- **A review has landed** → the reviewer is in `latestReviews` and gone from
  `reviewRequests`, *whether or not they were requested*.

In the second case a reader who is requested on every PR and then reports looks
identical to one who arrives unasked — so the agent concludes "already covered",
requests nobody, and the PR reaches no one. The paragraph half-knows this ("a
merged PR's reviewers are not evidence of who will read this one") but scopes the
caveat to *merged* PRs, when it holds for any PR with a landed review — including
the open one it recommends, since a self-subscribing bot reports within minutes.

**Fix** — either read the distinction off the timeline, which does keep it:

```bash
gh api repos/{owner}/{repo}/issues/<other-pr>/timeline \
  --jq '.[] | select(.event=="review_requested") | .requested_reviewer.login'
```

(absent from that list + present in `latestReviews` = arrived unasked) — or drop
the probe entirely and rest on the three recorded sources L199-201 already names
(a subscribed bot, `CODEOWNERS`, the contributing guide), which is the more
durable half of the paragraph anyway.

### WARNING — L111-112 copies a rule the shipped template owns

> A change that closes nothing links its source issue instead, without the
> keyword.

The shipped PR template, Issue Links comment block (L81-96):

> An issue referenced for context or partial progress goes under Related, without
> a closing keyword.

Plus its checklist L149: "Every fully completed issue is under `Closes` with a
closing keyword, not only `Related`." The skill's own L70-73 forbids exactly
this — "A second copy of the project's sections would be a copy to keep in sync,
and the copies that fall behind do not announce themselves" — and CLAUDE.md says
the skill must not grow a copy of anything another file owns.

Note that `test_the_change_description_skill_does_not_restate_the_template`
exists to catch this and **passes**, because it compares *headings* only. The
duplication arrived through the hole in the guard rather than past it.

The rest of the bullet is genuinely unowned and worth keeping: that the keyword
is the one sidebar value no Step 5 flag can set, so it lives in the body. That
half also earns its place in repos whose template has no Issue Links section.

**Fix** — delete the final sentence. If the "closes nothing" case must stay, make
it a pointer rather than a copy ("the template's Issue Links section says what a
change that closes nothing does instead").

### WARNING — L153-154 tells every repo to set a board

> Set the label the change's own subject earns and the board the project runs on

Unconditional imperative. This skill installs into every repo that installs
wfctl, and most run no Projects v2 board; `gh pr edit --add-project <title>`
against a title that does not exist errors mid-step (and needs the `project`
token scope besides). The pre-existing text was safe here because it only ever
said to *copy* what the issue had — an empty board field copied nothing. The
generalisation removes that safety.

**Fix:** "Set the label the change's own subject earns and, where the project
runs a board, the board it runs."

### NIT — L148-155 milestone is exempt without saying so

The heading claims all four fields — "An empty field on the issue is not an
answer to copy" — and the body then supplies a fallback for assignees, labels and
projects only. #220's proposed fix confirms the omission is deliberate, but the
reason is not on the page, and this file's convention is that the rationale is on
the page. A reader who applies the heading literally invents a milestone; the
next editor "completes" the list. One clause fixes it: a milestone is a
release-planning decision the change's author is not in a position to invent.

### NIT — L148-163 the same fallback, twice, adjacent

New paragraph: "…and say in the description that you decided those rather than
copied them." Next paragraph: "…make it, and say in the description that you
did." Same instruction, same rationale shape ("a decision you are making rather
than one you are copying"), touching paragraphs. Merging the bare-issue case into
the no-issue paragraph would cover both under one rule and shorten the step.

### NIT — L109-110 GitHub UI vocabulary in a forge-neutral step

Steps 1-3 are deliberately forge-agnostic — the frontmatter names merge requests
and patchsets, Step 1 handles GitLab's `merge_request_templates/`, Step 2's
fallback says "Issue links". The new bullet lands "the Development panel", "the
sidebar's fields" and "no Step 5 flag can set" in that neutral stretch. The
keyword itself survives on GitLab; the panel name does not. `end-session` L99-100
shows the house pattern for this exact keyword: "include your tracker's close
keyword if it has one, e.g. GitHub `Closes #N`". Saying what the keyword *does*
(links the issue and closes it on merge) and leaving the panel name to Step 5
costs nothing.

### NIT — L189-196 an external login flows into a write

The procedure reads a login off an open PR and hands it to `--add-reviewer`. On a
public repository anyone with read access can submit a review, so "who arrived
unasked" can include a drive-by account that the skill then teaches the agent to
request on subsequent PRs. The guard — "the readers this project relies on" — is
prose, not a filter. Low probability, and the timeline/recorded-sources fix in
finding 4 removes the flow entirely.

### NIT — L200 CODEOWNERS never yields a gap

CODEOWNERS entries are auto-requested by GitHub when the PR opens, so of the three
sources named as places the decision is recorded, that one can never produce a
reader that is "missing". Harmless (`--add-reviewer` on an already-requested login
is a no-op) but it makes the list read as three equivalent sources when only two
are actionable.
