## Detail

### BLOCKER — L204-211: the check that the issue was filed about is unchanged

Issue #220's headline is that "its closing line declares the step done when the
read-back *carries the issue's set*", so a PR satisfies Step 5 and reaches a
reviewer with nothing on it. The diff adds `reviewRequests` to the read-back
command and stops there. The sentence that consumes that output is untouched:

```
The step is done when that output carries the issue's set.
```

The new paragraph 20 lines above states, correctly, that **an issue has no
reviewers**. So the field added to the observation is definitionally excluded
from the criterion that reads it: an agent that runs the read-back, sees
`"reviewRequests": []`, and applies the stated rule concludes *done*. The exact
failure mode the change is named after survives.

This is not a nit about wording, because the skill argues the point itself.
Step 4 (L123-126):

> a flag dropped from an invocation cannot be observed as missing, and this step
> reports done the moment the PR exists. A step can be observed as unfinished.
> That is the whole reason the two are separate.

By its own standard, an instruction whose omission the read-back cannot report
is the defect, not the fix. The trailing sentence ("An empty sidebar here is this
step unfinished") does not close it either — a sidebar carrying labels,
assignee, milestone and project is not empty.

**Fix:** make the criterion name what it now reads back, e.g. *"The step is done
when that output carries the issue's set, plus the two fields the issue cannot
supply: a linked issue under `closingIssuesReferences`, and either a requested
reviewer or a stated reason there is none."*

### WARNING — L204-208: Development is instructed but never verified

The change's other half — `Closes #N` — is a Step 3 bullet with no
counterpart in the only verification the skill has. `closingIssuesReferences`
is a valid `gh pr view --json` field (verified against the installed `gh`), so
covering it costs one word in the existing command. Without it, the Development
gap is fixed by instruction only, and instruction-only is what #220 records
failing on PR #211.

### WARNING — L193-196: `<pr>` denotes two different PRs in one fence

```bash
gh pr view <pr> --json reviewRequests,latestReviews   # who arrived unasked
gh pr edit <pr> --add-reviewer <login>                # only who is missing
```

The prose above it says "Look at **an open PR nobody has touched**" — a
*different* PR. The line below acts on **this** PR. Same placeholder, adjacent
lines, opposite referents; the near-certain reading is that both are this PR,
which is also a defensible procedure but not the one the prose describes. The
skill is otherwise careful here (`<issue>` vs `<pr>` are kept distinct at
L140-142), so this reads as an oversight rather than a convention.

Two further gaps in the same procedure, and they compound:

- **No fallback when the sample PR does not exist.** A repo installing wfctl
  opens its first PR through this skill; at that moment there is no "open PR
  nobody has touched". Same for a repo where every open PR already has a
  requested reviewer. The step has no branch for either.
- **Two methods, no precedence.** The fence says the answer comes from observing
  another PR; L199-202 says the answer is already recorded in "a subscribed bot,
  a `CODEOWNERS` entry, a line in its contributing guide". These are not the
  same source and the section never says which wins. Worth noting that a
  `CODEOWNERS` entry auto-requests on open, so it can never be the thing that is
  "missing" — listing it as a source to request *from* is at best inert.

**Fix:** `gh pr view <sample-pr>` for the observation, and make the recorded
sources the primary route with the sample PR as the confirmation.

### WARNING — L107-112: a second, lossier copy of rules the template owns

The shipped template (`wfctl/agents/configs/github/.github/pull_request_template.md`)
already owns this ground, in its `## Issue Links` comment block:

> Use GitHub closing keywords for every issue this PR fully resolves. They
> auto-close **only on merge into the default branch**. […] An issue referenced
> for context or partial progress goes under Related, **without a closing
> keyword**.

plus a `### Closes` / `### Related` skeleton and a checklist line. The new
bullet's last sentence — "A change that closes nothing links its source issue
instead, without the keyword" — is that rule again, one file over.

Step 1 of this same skill forbids exactly this (L70-73): *"This skill does not
carry a section list of its own, and must never grow one … the copies that fall
behind do not announce themselves — they contradict the file that is actually
installed."* The guard that enforces it,
`test_the_change_description_skill_does_not_restate_the_template`, only matches
`#`-prefixed headings, so it passes on a prose restatement — the drift is
unguarded, not absent.

And the copy is *already* lossy in a way that bites this repository: "what
closes the issue on merge" drops the template's "only on merge into the default
branch". This repo runs stacked PRs (base PRs merge into other branches), where
`Closes #N` on a stacked child closes nothing on merge. The skill's shorter
claim is wrong there; the template's is right.

The first half of the bullet is not duplication and should stay — that the
keyword is the one sidebar value no Step 5 flag can set is a fact the template
does not carry and #220 exists to add.

Counter-argument, stated for the author: Step 2's no-template path lists "Issue
links" with no rules attached, so in a template-less repo this bullet is the only
carrier. If that is the reason to keep it, the fix is to say *what* to write
under the template's own Related heading rather than to restate the template's
rule for repos that have one.

### WARNING — L148-155: a rule that assumes this repository's furniture

> Set the label the change's own subject earns and the board the project runs on

Unconditional imperative, in a skill that installs into every repo. A repository
with no labels defined and no Projects v2 board is not untriaged — it is a repo
that does not use those fields — and an agent following this literally runs
`gh pr edit --add-label <name>` against a label that does not exist (error) and
`--add-project <title>` against no board (error, and it needs the `project`
OAuth scope besides). #220's own "Out of scope" section draws this line: "That is
a project decision recorded in the project, not in a skill that installs into
every repo."

Note the pre-existing paragraph immediately below handles the analogous case
more carefully — "triage is a decision you are making rather than one you are
copying" — without naming which fields exist.

**Fix:** condition it — the label the change earns *if the repo uses labels*, the
board *the project runs, where there is one* — and keep the falsifiable half
(say in the description that you decided rather than copied).

### NIT — L110: "it lives in the body or nowhere"

False as stated on GitHub: an issue can be linked to a PR manually from the
sidebar's Development panel (and such a link also closes on merge), and a
closing keyword in a commit message is parsed too. Operationally true for a
CLI-only agent, which is presumably the intent — so say that: *"no `gh` flag and
no API sets it; it lives in the body."* The same file already sends the reader to
the project UI for the Status column (L180), so "nowhere" is inconsistent with
the skill's own posture toward the web UI.

### NIT — L151: "Nor is a bare one"

By proximity "one" resolves to *field* (from the bold sentence), which makes the
clause a tautology; by intent it resolves to *issue* (from "An unassigned
issue"). It is the topic sentence of a new normative rule, so it should not need
a second pass. "Nor is a bare issue:" fixes it.

### NIT — L185-202 and L153-154: two restatements

- L198-202 ("A reviewer the project has stopped using does not become one again
  because the flag still accepts it. Which readers a repository wants is a
  decision it has already made…") is the same claim as L190-191 ("request only
  the readers this project relies on and is missing"), at length. One of the two
  earns its place; both do not.
- "say in the description that you decided those rather than copied them"
  (L154-155) and "make it, and say in the description that you did" (L162-163)
  are the same instruction in adjacent paragraphs.

Also pre-existing but now doubled: both sentences ask the author to write into a
description that Step 3 already finished and Step 4 already pushed. Neither says
`gh pr edit --body-file`. Not introduced by this diff — flagging so it is a
choice rather than an oversight.
