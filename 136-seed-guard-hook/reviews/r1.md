## Findings

### BLOCKER `cli.py:L2213` — an *absent* settings file reads as drift, and the whole install refuses

`_permission_drift` calls `_read_settings`, which returns `({}, None)` for a
missing file (`cli.py:L2047`, "A missing file is `({}, None)` — not an error").
The next line only guards `settings is None`, so a receipt plus a missing
`.claude/settings.json` reaches `permission_present({}, rule) is False` and is
reported as drift.

Reproduced:

```
$ wfctl install-skills --agent claude --yes     # ok, writes the receipt
$ rm -rf .claude                                # file gone, manifest still there
$ wfctl install-skills --agent claude --yes
✗ .claude/settings.json no longer carries Bash(cd:*), which wfctl installed.
  Nothing was installed. ...
EXIT=1
$ ls
README.md            # .agents/ never created — the entire install was refused
```

Why this is a defect rather than FR-017 working as written:

- The spec's own state table row 1 is `absent | creates it`. The implementation
  turns "absent + a receipt" into a hard refusal, and that pair is not in the
  eight states.
- FR-014 already settled the principle for the neighbouring case: "drift cannot
  be established in a file that will not parse, and refusing on an unknown is
  refusing on a guess." A file that is *gone* is at least as much an unknown as
  one that will not parse — and the code deliberately handles the unparseable
  case and not this one.
- The blast radius is the whole install, in the two places that run it
  unattended. `.wf-skills-manifest.json` is gitignored *by convention* and
  `CLAUDE.md` says a repo may commit one anyway (#146 gave it a `source` key
  precisely so it can be); `.claude/` is gitignored in this repo and in most
  consumers. A fresh clone or a new `workmux add` worktree of such a repo has
  the receipt and no settings file, so `post_create`'s `install-skills` exits 1
  and the worktree comes up with **no skills tree at all** — the failure mode
  `CLAUDE.md` calls out under "Worktrees", except now it also fails
  `/start-session`'s repair loop on every run.
- Same trip for the ordinary human case: delete `.claude/` to start clean, or
  move settings to `.claude/settings.local.json`, and every later install
  refuses.

Fix: skip the target when the file does not exist, alongside the unparseable
arm the docstring already describes —

```python
path = repo_root / rel
if not (path.exists() or path.is_symlink()):
    continue
settings, _ = _read_settings(path)
```

Regression test: install, `rm -rf .claude`, install again → exit 0 and the file
is recreated with the rule (state 1's behaviour, reached through a receipt).

### BLOCKER `_settings.py:L149` — correcting the matcher rewrites the scope of the consumer's own hooks in the same group

`merge_hook` now sets `group["matcher"]` whenever the adopted hook's group
disagrees. It never checks whether that group holds anything but wfctl's hook.
Claude Code groups several hooks under one matcher, and the README this change
is retiring told people to wire the guard by hand — so a hand-wired entry
sharing a group with the consumer's own hook is exactly the population FR-010
targets.

Reproduced (pure function, no I/O):

```python
s = {"hooks": {"PreToolUse": [{"matcher": "*", "hooks": [
        {"type": "command", "command": "./my-audit.sh"},
        {"type": "command", "command": "wfctl hook worktree-guard"}]}]}}
merge_hook(s, "PreToolUse", GUARD, "Bash")   # -> True
# s["hooks"]["PreToolUse"][0]["matcher"] == "Bash"
```

`./my-audit.sh` silently stops firing on Edit, Write, Read and every other tool.
Nothing is printed, and the install reports ✓. That is a straight violation of
FR-003 ("MUST leave every hook, permission and setting the project already had
exactly as it was") and of the promise the summary prints two lines later
("Your own hooks, permissions and settings are still there").

It also does not heal: `remove_hooks` correctly keeps the consumer's hook and
drops wfctl's, but leaves the group pinned at `"Bash"` — so `uninstall-skills`
returns a file whose own hook is still narrowed.

Fix: only correct the matcher when the group is wfctl's alone; otherwise split
rather than mutate —

```python
if matcher is not None and group.get("matcher") != matcher:
    if len(_hooks_of(group)) == 1:
        group["matcher"] = matcher
        changed = True
    else:
        # theirs stays scoped as they wrote it; ours moves to its own group
        group["hooks"] = [h for h in _hooks_of(group) if h is not hook]
        _groups(settings, event).append({"matcher": matcher, "hooks": [hook]})
        changed = True
```

(Any resolution is fine as long as a foreign hook's matcher survives.) The
existing test `test_adopting_a_hand_wired_entry_corrects_its_matcher_in_place`
pins the single-hook group; it needs a sibling pinning the shared group, which
is the case it currently passes by not exercising.

### WARNING `cli.py:L2247` + `cli.py:L3385`, `cli.py:L3527` — one unparseable file now produces four identical warnings

`_merge_hooks` appends one problem per managed event and `_merge_permissions`
appends a fourth for the same file, and both callers print every entry.

```
$ printf '{not json' > .claude/settings.json && wfctl install-skills --agent claude --yes
⚠ .claude/settings.json: Expecting property name ... — left untouched; the managed hook was not added or updated
⚠ .claude/settings.json: Expecting property name ... — left untouched; the managed hook was not added or updated
⚠ .claude/settings.json: Expecting property name ... — left untouched; the managed hook was not added or updated
⚠ .claude/settings.json: Expecting property name ... — left untouched; the managed hook was not added or updated
```

Four again on `uninstall-skills`. This went 2 → 4 in this diff, and it is the
exact thing `_check_managed_hooks` takes care to avoid one screen away ("Read
once per file, not once per event: an unparseable settings file is one problem
however many entries wfctl keeps in it") and that
`_check_managed_permissions`'s own comment says it is deliberately not doing
("saying it twice about one file helps nobody"). Doctor's rule and install's
behaviour now disagree.

Two things to fix together: de-duplicate the problems before printing (they are
identical strings — `dict.fromkeys(...)` at the print site is enough), and stop
the trailer claiming a hook. Both trailers name only hooks —
"the managed hook was not added or updated" and "wfctl's hook entry may still be
in this file" — over a list that now includes the deny rule, which is the
under-reporting FR-021 forbids in the sibling summary line.

### WARNING `cli.py:L3583` — the declined-uninstall message asserts a descendant it cannot know, and drops the rest

`related_rules` prefix-matches on `rule.split(":", 1)[0]`, i.e. the string
`Bash(cd`. The message then prints `related[0]` as fact:

```
⚠ .claude/settings.json: left Bash(cd:/tmp/*) in place
  wfctl installed Bash(cd:*) and it has since been edited, so it was not removed.
```

Two problems. `Bash(cdk:*)` (AWS CDK — an entirely unrelated rule a repo could
plausibly hold) matches that prefix and would be named as the edited form of
wfctl's rule, telling the reader their own unrelated deny rule descends from
wfctl. And when `related` holds more than one entry, `[0]` is chosen with no
rule and the rest are dropped silently.

The docstring is honest about the guess ("the closest honest guess", "inventing
a candidate would be worse than saying nothing") but the console line is not —
it states the relationship rather than offering it. Either match on the full
verb token (`rule.split(":", 1)[0] + ":"`, so `Bash(cd:` — `Bash(cdk:*)` no
longer qualifies) and print every match with hedged wording ("these rules also
deny `cd`: …"), or drop `related` from the message and keep only the second,
certain line. The second option removes ~25 lines including the helper.

### WARNING `wfctl/agents/skills/start-session/SKILL.md` — the unattended repair loop was not told about the refusal

`CLAUDE.md`: "A change to anything under `wfctl/agents/` is not verified by the
test suite alone" — the inverse applies here. No skill changed in this diff, but
the skill that runs `install-skills --prune --yes` unattended now has a new way
to exit 1 that it has no instruction for. Its step reads "Then run `wfctl

removal case doctor is *green by design* (FR-012) while the repair the step just

the user's call and not the agent's to make unprompted, and that a refusal means
the drift repair did not run. This is the operational half of #313; the README
paragraph covers the human reader, and the skill covers the one that runs it
with nobody watching.

### NIT `cli.py:L2213` vs `cli.py:L4998`/`L3546` — two conventions for reading a manifest record

`_permission_drift` uses `record.get("path")`/`.get("rule")`;
`_check_managed_permissions` and `_unmerge_permissions` use `record["path"]`,
`record["rule"]` and would `KeyError` on a hand-edited manifest. The bracket form

a bug — but `_merge_hooks` argues explicitly for `.get` ("the manifest is on
disk, gitignored and hand-editable, and an install that raises on a record
missing a key is a crash"), and `test_a_manifest_record_without_created_does_not
_crash_the_install` exists because of it. Pick one and say which.

## What I checked and found sound

- The refusal's *placement* (before any copy) is right and pinned by
  `test_the_refusal_copies_nothing`; a check beside `_merge_permissions` would
  have refused over a half-installed tree.
- `created` moving to one question asked after both unmerge passes, with
  `_unmerge_hooks` writing `{}` rather than unlinking. Correct, and the comment
  explains the ordering trap it closes.
- `GUARD_HOOK_COMMAND` is byte-identical to `_entry.py`'s `_GUARD_ARGV`
  (`["hook", "worktree-guard"]`), so every seeded hook takes the fast path and
  no consumer pays typer + rich per Bash call. Worth keeping a test on that
  equality if one does not exist — the two constants live in different modules
  and nothing fails if they drift.
- No `|| true` on the guard command, unlike `Stop`. Right: exit 2 is the feature.
- `remove_permission` dropping every copy and pruning `permissions` upward only
  when empty; `merge_permission` raising rather than overwriting a foreign
  `permissions` shape.
- Doctor's two tiers (hook missing → exit 1, rule missing → warning only) match
  FR-012, and `_check_managed_permissions` sits outside the `any([...])` list
  with a comment saying why. `test_doctor_says_nothing_about_a_rule_the_repo
  _wrote_themselves` pins the `added: false` silence.
- The install-refuses / doctor-stays-silent asymmetry for an `added: false`
  receipt is deliberate (FR-017 vs FR-012), pinned by
  `test_a_receipt_of_theirs_refuses_the_same_way`, and its residual friction is
  tracked as #313 (verified open: "A project cannot record a standing preference
  that differs from a wfctl default"). Not raised as a finding — but note the
  BLOCKER above is *not* an instance of #313: a file that is absent is not a
  divergence anyone chose.
- Both architecture records carry `status: proposed`, consistent with the other
  12 in `docs/architecture/` and the 3 in `docs/architecture/design/`.
- Tests are behavioural, docstrings name the failure each one catches, and
  `NO_COLOR` handling comes from `conftest.py`. This is the house style, held.

net: −25 lines possible (only if the `related_rules` guess goes; the rest is
load-bearing)

**Verdict: Request changes** (3 blockers — the absent-file refusal, the
matcher rewriting a consumer's group, and the failing `ruff` gate)
