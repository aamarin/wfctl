## BLOCKER

**`docs/architecture/install-modes.md` — accepted, in force, and now contradicted
by the code it governs. Not amended.** [still open]

`wfctl arch context` lists `install-modes` among the nine accepted decisions, so
it binds. Three of its statements are now false:

- L38 (the mode table): merge owns *"one entry per managed event"*. The deny
  rule is an entry with no event.
- L40–41: *"A merged entry is recognised by what it runs. Every managed hook's
  command starts `wfctl hook `, so the installer finds its own rows by reading
  the file rather than by trusting a list… the file itself is the authority on
  whether it still does."* For the deny rule the manifest is the authority and
  the file cannot answer — which is precisely what the new level-2 record says.
- L74–75: *"the consumer owns the file and wfctl owns exactly the entries whose
  command carries its prefix."*

L114–120 also describes doctor's merged-entry check as one thing ("the entry is
present and its command matches"); there are now two vocabularies with different
exit-code semantics.

This is not a nit about docs hygiene. The record's own Log shows the convention
for exactly this class of change:

```
- 2026-09-05  amended  — merge owns one entry per event, not one entry (#212
  added a `Stop` hook beside the `UserPromptSubmit` one in the same file). No
  change to the mode: ownership was already drawn at the command entry.
```

#212 added a second hook and amended the record. #136 adds an entry that is not
a hook and inverts where ownership is readable from, and does not. A future
reader running `arch context` gets an accepted record and a proposed record that
disagree, with nothing saying which won.

**Fix:** amend `install-modes.md` — adjust the table row and the "recognised by
what it runs" paragraph to carve out the unmarked entry, point at
`the-manifest-owns-what-carries-no-marker`, and add a Log line
(`2026-09-0x amended — merge owns an entry that carries no marker (#136);
ownership for that one lives in the manifest`). The level-2 record does not
substitute for this: it is `proposed`, and `arch context` prints only accepted
ones.

One related note, in the working tree's favour: L42–45 of the same record
guarantees *"a consumer is free to put their own command in the same group as
wfctl's"*. The **committed** `merge_hook` broke that guarantee outright —
verified live, it rewrote a shared group's `matcher` from `*` to `Bash`, silently
re-scoping the consumer's own hook, and `remove_hooks` left it narrowed after
uninstall. The working tree fixes this by moving wfctl's hook into its own group.
Worth keeping in the amend, because the record's sentence now describes an
outcome reached by a different mechanism than the one it names.

## WARNING

**1. `doctor` is blind to matcher drift on the `PreToolUse` hook — a guard that
never fires reports green.** [still open]
`wfctl/cli.py:5074` `_report_hook_drift` compares only
`_settings.managed_command(settings, event)`, and `managed_command` searches
every group regardless of its matcher. Verified against the current working tree:

```
install-skills --agent claude, then set the group's matcher to "Read"
DOCTOR EXIT 0 | mentions PreToolUse: False
```

The hook is present and correct, scoped to a tool it will never see, and
`doctor` — which `/start-session` runs and which the README now advertises as
what catches a missing hook — says nothing. This is the same failure the change
already decided is worth exit 1 (`_HOOK_GONE[PRETOOL_EVENT]`: "nothing stops a
Bash call reaching into a sibling worktree"), reached by a different route.

It is also newly *likely* rather than theoretical: the matcher is now the one
part of a managed entry a consumer can edit without touching a string that
starts `wfctl hook `, and `test_adopting_a_hand_wired_entry_corrects_its_matcher_in_place`
exists because hand-wired entries with the wrong matcher are the expected
population.

**Fix:** give `_report_hook_drift` the expected matcher (it already takes
`event`; `_HOOK_MATCHER.get(event)`) and report a group whose matcher is not it
as drift, with its own `state` string — the entry is neither *gone* nor *behind*,
it is scoped wrong. Then a test that installs, rewrites the matcher, and asserts
exit 1.

**2. Uninstall claims a rule was edited and left in place when it was deleted and
nothing was left.** [still open]
`wfctl/cli.py:3636-3651`. Verified on the current working tree, install then
`del settings["permissions"]` then uninstall:

```
⚠ .claude/settings.json: nothing there matched, so nothing was removed
  wfctl installed Bash(cd:*) and it has since been edited, so it was left in place.
```

The two lines contradict each other, and the second is false twice: the rule was
not edited, and nothing was left in place. The first line is also printed under a
run that deleted `.claude/settings.json` outright, which reads worse than saying
nothing.

FR-020 scopes this report to "declines to remove … because its text no longer
matches". `_unmerge_permissions` reaches `declined` for both that case and
"the rule is simply absent", and only the first deserves a warning at all.

**Fix:** split the two. `related` is already the discriminator the code computes:
when it is empty and the rule is absent, there is nothing wfctl owns in the file
and nothing to report — `continue` instead of appending to `declined`. Keep the
warning for the case FR-020 names. Then a test for the empty-`related` branch,
which nothing currently exercises (`grep "nothing there matched" tests/` → no
hits).

**3. README: "the entry keeps its position in the array either way" is now
false.** [still open — introduced by the working tree's own fix]
`README.md:507-508`. The working tree's shared-group fix appends wfctl's hook as
a **new group at the end** of the array, so an adopted hand-wired entry in a
shared group does move. `wfctl/_settings.py:129` carries the same promise in
`merge_hook`'s docstring, and it is still true there for the single-hook case
only.

**Fix:** qualify both — the entry keeps its position when wfctl's hook is alone
in its group; a hook sharing a group with the consumer's moves into a new group
of its own, which is what leaves theirs untouched.

## What I checked and found sound

- **Mutation walk.** Dropping the receipt carry-forward
  (`"added": added or bool(keep and …)` → `"added": added`) is caught, by
  `test_uninstall_prunes_the_file_after_an_upgrade_added_a_second_event` — an
  existing test, not a new one, but it does fail. The `added` gates in
  `_unmerge_permissions` and `_check_managed_permissions`, the `_touched_created`
  intersection, the matcher on a fresh group and the matcher correction in place
  are each pinned by a test that fails without them.
- **Docstrings.** Every new test names the failure it exists to prevent rather
  than restating its assertion. `test_remove_permission_drops_every_copy` and
  `test_a_shared_group_keeps_its_matcher_and_wfctls_hook_moves_out` are the
  strongest of them.
- **Machine independence.** Every new console assertion is a substring of a line
  printed with `soft_wrap=True`, so nothing depends on terminal width; `NO_COLOR`
  and `FORCE_COLOR` are handled by `conftest.py` as the convention requires.
- **The level-3 record.** `wfctl arch check
  docs/architecture/design/136-the-receipt-is-a-sibling-of-merged.md` → committed
  and added by this change. Its "Verification" bullets hold:
  `grep -n 'record\["event"\]' wfctl/cli.py` returns one hook call site (2364)
  and one comment; the sibling list, the unioned file count, and doctor's second
  vocabulary are all implemented as decided.
- **The level-2 record.** Every claim in its "Decision" and "Owns truth"
  sections matches the code: the receipt is carried forward rather than
  re-derived, uninstall requires both `added` and an exact text match, and a
  missing receipt reads as not-wfctl's.
- **README accuracy** otherwise: "four entries", the deny-rule ownership
  paragraph, the two-tier doctor semantics and the `--force` remedy all match
  what the code does.
