## BLOCKER

### B1 `_permission_drift` reads a *missing* settings file as a *removed* rule — a fresh clone with a committed manifest installs nothing

`wfctl/cli.py:2232`

```python
settings, _ = _read_settings(repo_root / rel)
if settings is None or _settings.permission_present(settings, rule):
    continue
return rel, rule, _settings.related_rules(settings, rule)
```

`_read_settings` documents its own collapse: *"A missing file is `({}, None)` — not
an error"* (`cli.py:2042`). So a `.claude/settings.json` that does not exist yet
returns `{}`, `permission_present({}, rule)` is `False`, and the gate declares
drift. The refusal then exits 1 before a single file is copied.

Reproduced (scratchpad script, real git repo, real bundle):

```
# committed .wf-skills-manifest.json carrying {"claude": {"items": [], "permissions":
#   [{"path": ".claude/settings.json", "rule": "Bash(cd:*)", "added": true}]}}
# no .claude/, no .agents/ — i.e. a fresh clone
$ wfctl install-skills --agent claude --yes
exit: 1
✗ .claude/settings.json no longer carries Bash(cd:*), which wfctl installed.
  Nothing was installed. ...
agents tree: False   claude tree: False
```

Also reproduced from the other direction: install once, `rm -rf .claude/`, install
again → same exit 1, nothing restored.

Why this is a blocker rather than an edge case, in this repo's own terms:

- `CLAUDE.md` § Safety: *"`.wf-skills-manifest.json` is gitignored **by
  convention**, and a repo can commit one anyway. Since #146 it names the *source*
  a layer was installed from"* — committing it is a supported configuration, and
  `.claude/` is the thing that is gitignored in practice.
- `CLAUDE.md` § Worktrees: `post_create` runs `install-skills` **unattended**, and
  *"Neither failure announces itself; the first sign is a session that has no
  `/start-session` to run."* An exit 1 there is exactly that failure, now reachable
  by ordinary use rather than by a mistake.
- The test that is supposed to cover this, `test_a_fresh_install_never_trips_the
  _refusal` (`tests/test_install_hook_merge.py:797`), only covers the *no manifest*
  case. Its docstring claims the broader property — *"This is what makes a refusal
  safe to put in a command a `post_create` hook runs with nobody watching"* — and
  that property does not hold.

**Fix:** a missing file is not drift. Distinguish it from an empty parse before the
check, the same way `_unmerge_permissions` (`cli.py:2317`) already skips a path
that does not exist:

```python
path = repo_root / rel
if not path.exists():
    continue
settings, _ = _read_settings(path)
```

Add a regression test that seeds a receipt with no `.claude/` on disk and asserts
exit 0.

## WARNING

### W1 Correcting the group matcher silently re-scopes a consumer's own hook, and uninstall never puts it back

`wfctl/_settings.py:150-152`

`merge_hook` reaches the *group* now, and a group can hold more than wfctl's hook.
A consumer who hand-wired the guard following the old README into a group they also
use for their own audit hook:

```
before:  {"matcher": "*", "hooks": [wfctl guard, "./my-audit.sh"]}
merge:   {"matcher": "Bash", "hooks": [wfctl guard, "./my-audit.sh"]}
uninstall: {"matcher": "Bash", "hooks": ["./my-audit.sh"]}
```

Verified directly against `_settings.merge_hook` / `remove_hooks`. Their
`./my-audit.sh` fired on every tool and now fires only on `Bash`; `remove_hooks`
prunes wfctl's row but leaves the narrowed matcher, so the change is permanent.

This contradicts the contract the README states twice in this same diff — *"adds
four entries to `.claude/settings.json` and edits nothing else in it"*, *"leaving
every other byte of the file alone"* — and the failure direction is a security hook
that quietly stops covering `Edit`/`Write`.

`test_adopting_a_hand_wired_entry_corrects_its_matcher_in_place` only exercises a
group containing wfctl's hook alone, which is why this passes.

**Fix:** correct the matcher only when the group holds nothing but managed hooks;
otherwise split wfctl's hook out into its own `{"matcher": "Bash", ...}` group and
leave theirs where it was. Cover the mixed group in a test.

### W2 "left untouched" is now false — the permission pass writes a file the hook pass just declared unmergeable

`wfctl/cli.py:3387`

`merge_problems.extend(perm_problems)` (`cli.py:3159`) folds both passes into one
warning whose text is `"— left untouched; the managed hook was not added or
updated"`. But the two passes are independent, so a `hooks` key the consumer
malformed fails the hook pass while the permission pass proceeds and rewrites the
same file.

Reproduced with `{"hooks": "not a map", "model": "opus"}` at indent 4:

```
⚠ .claude/settings.json: `hooks` in the settings file is not an object — left untouched; ...   (×3)
file unchanged: False
{ "hooks": "not a map", "model": "opus", "permissions": { "deny": [ "Bash(cd:*)" ] } }   # reflowed to indent 2
```

Three warnings say the file was left alone; the file was rewritten, reflowed, and
gained a rule. The mirror case is just as wrong: a `permissions` key that is not an
object produces a problem line saying *"the managed hook was not added or updated"*
about something that is not a hook.

**Fix:** give the permission problems their own sentence (they are already a
separate list, so this is a second loop, not a branch), and stop claiming
"untouched" when the other pass may have written.

### W3 The refusal asserts authorship the receipt explicitly disclaims, and install and `doctor` disagree about the same record

`wfctl/cli.py:2226-2237`, `cli.py:2770`, `cli.py:4985-4988`

`_permission_drift` matches on `path` + `rule` and never looks at `added`.
`_check_managed_permissions` opens with `if not record.get("added", False):
continue`. Same receipt, opposite readings.

Reproduced with a repo that wrote `Bash(cd:*)` itself:

```
receipt: added=False        # correct, and what test_a_rule_the_repo_already_had... asserts
after they delete the rule:
  install →  exit 1  "✗ .claude/settings.json no longer carries Bash(cd:*), which wfctl installed."
  doctor  →  exit 0, does not mention the rule at all
```

Refusing here is a deliberate decision — `test_a_receipt_of_theirs_refuses_the_same
_way` says so, and the reasoning ("a receipt is wfctl's record that it looked at
this entry, not a claim of ownership") is sound. Two things still need fixing:

1. **The sentence is untrue.** "which wfctl installed" is precisely what
   `the-manifest-owns-what-carries-no-marker.md` built the `added` field to deny.
   A reader who never let wfctl near their deny list is told wfctl put it there.
   Word it off the receipt: `added: true` → "which wfctl installed"; `added:
   false` → "which wfctl recorded as already yours".
2. **The remedy takes ownership.** Following `--force` on an `added: false` receipt
   flips it to `true` (`cli.py:2277`, `added or bool(keep and keep.get("added"))`),
   so the next `uninstall-skills` deletes a rule the repo authored. That is the
   exact loss the architecture record calls "the failure the receipt is built to
   prevent"; it now merely requires one `--force`. At minimum, say so in the
   refusal text.

Related, and worth a line somewhere: `doctor` exits 0 on this while every
`install-skills` exits 1. `/start-session` refreshes unattended with `--yes`, so a
repo in this state has a green `doctor` and a silently failing refresh. The
`restore:` line should say that installs refuse until it is resolved.

### W4 `doctor` and `uninstall` crash on a partially written receipt; `_permission_drift` in the same change does not

`wfctl/cli.py:4991`, `cli.py:2319` — both `record["path"], record["rule"]`.

```
doctor,    receipt {"rule": ..., "added": true}      → exit 1, KeyError('path')
uninstall, receipt {"path": ..., "added": true}      → exit 1, KeyError('rule')
```

`_permission_drift` reads the same two fields with `.get` (`cli.py:2229-2230`), so
the change is internally inconsistent about it. The design record singled this out
as the shape to copy: *"`created` is read back as `p.get("created", False)` — the
same defensive shape a new receipt needs"*, and `added` does follow it. `path` and
`rule` do not.

The hook records have the same unguarded reads on `main`, so this is a pre-existing
pattern rather than a new class — but a `doctor` that raises is one
`/start-session` runs, and `test_a_manifest_record_without_created_does_not_crash
_the_install` shows the project already treats this class as worth a test.

**Fix:** `rel, rule = record.get("path"), record.get("rule")` and skip when either
is missing, in both call sites.

### W5 Uninstall warns about a file it was never going to touch, and calls a rule a hook

`wfctl/cli.py:2317-2331`, `cli.py:3529`

Two small ordering/wording defects in one place:

- `_unmerge_permissions` does `_read_settings` **before** `if not
  record.get("added", False): continue`. For an `added: false` record on an
  unparseable file it emits a problem about an entry it will not touch either way.
  Move the `added` check above the read.
- The shared warning at `cli.py:3529` reads *"wfctl's hook entry may still be in
  this file"*. `perm_problems` is now folded into it (`unmerge_problems +
  perm_problems`), so it says "hook entry" about the deny rule. Same fix as W2:
  two loops, two sentences.

## What the change gets right

Worth saying explicitly, because most of the above is detail on top of a sound
design:

- The ownership problem is correctly identified and correctly located. A deny rule
  genuinely cannot carry `MANAGED_PREFIX`, and moving authorship to the manifest is
  the only side that was ever in a position to observe it. Both records argue their
  baselines honestly rather than as strawmen.
- Keeping `permissions` a sibling of `merged` is right, and the design record's
  verification step (`grep -n 'record\["event"\]'` returns only hook call sites)
  holds — checked.
- The receipt is carried forward rather than re-derived (`added or prior.added`),
  with the reason written down. That is the non-obvious half and it is correct.
- `_touched_created` — asking "should this file be deleted" once, after both passes,
  rather than per pass — is the right call and the comment explains why the naive
  version leaves `{}` behind. Covered by
  `test_uninstall_deletes_a_file_both_passes_emptied`.
- The exit-code split (missing hook fails, missing rule warns) is well argued and
  well tested from both sides.
- The guard hook correctly ships **without** `|| true`; `hook_worktree_guard_cmd`
  exits 2, which is the only code `PreToolUse` treats as blocking, and the constant's
  comment says why the `Stop` entry differs.
- Test docstrings name the failure they catch, per `CLAUDE.md` § Testing
  conventions. `test_the_refusal_copies_nothing` and
  `test_an_unreadable_settings_file_warns_rather_than_refusing` in particular are
  testing the risk rather than restating the code.
