WARNING  wfctl/cli.py:2950 — `_last_exchange` accepts `isMeta` user records as the prompt,

slash-command expansions, injected skill bodies, `<local-command-caveat>` blocks from

## What each pass checked

**1. Correctness.** Traced `_last_exchange` → `_message_text` → `_reply.findings` → `_prose`
against real transcripts rather than the fixtures. `[::4]` on a one-group `re.split` is
right, and the unclosed-fence reasoning holds (a lone trailing fence drops its tail; a reply
that is entirely one block yields empty prose and no findings). Turn segmentation is right
on the parts the tests pin: `tool_result` user records do not open a turn, an assistant
message carrying `tool_use` resets the reply so narration between tool calls is excluded,
and a truncated final JSONL line is skipped. Two segmentation defects the tests do not
reach are the meta-record and table-row findings above. Checked and cleared: no
`isSidechain` records appear in main-thread transcripts in this Claude Code version, so a
subagent's reply cannot be mistaken for the terminal one; `system`, `attachment` and
`queue-operation` records fall through the type guards; the `UserPromptSubmit` digest is
*not* written into the user message content, so it cannot poison `_ASKED_FOR_DEPTH` (I
checked — this was my first suspicion and it is unfounded). `_ASKED_FOR_DEPTH` has no
`how`/`what`, which produced Q3 on `how will address flags?` and `so what's the verdict on
section 1 again?` in the corpus; I am not raising it as a finding because the issue's
founding case *is* a short question answered at length, and adding `what` would swallow it.
That tension is real and the author's call.

**2. Security.** The hook reads a path handed to it by the harness and prints text the agent
itself wrote, embedded through `json.dumps` — heading and lead-in excerpts go through `!r`
and then JSON escaping, so a reply containing quotes, newlines or control characters cannot
break the envelope. No secrets, no shell interpolation, no network. `2>/dev/null || true`
in the settings entry is scoped to the managed command and cannot swallow a consumer's own
hook. The `Stop` command still starts with `MANAGED_PREFIX`, so `_is_managed` claims it and
uninstall can remove it — I verified the file is deleted rather than left as `{}`, which is
what the `existed`-per-pass fix is for.

**3. Architecture.** `_reply` is pure, imports only `re`, and sits in the domain band beside
`_guard` — the constraint its docstring claims, and it holds. The lazy `from wfctl import
_reply` inside the command matches the file's convention. `MANAGED_HOOKS` collapsing three
call sites (merge, uninstall record, `doctor`) onto one map is the right move and is why
`_check_managed_hooks` needed no per-event branching. `install-modes.md` is amended rather
than superseded, correctly — ownership was already drawn at the command entry, so nothing
about the mode changed. One latent edge in `_check_managed_hooks`: for an event recorded by
an older wfctl that this one no longer manages, `MANAGED_HOOKS.get(event)` is `None`, so a
hook the consumer has already deleted now compares equal and reports no drift where the old
code reported "is gone". Harmless today (the fallback string shows the case was thought
about) and not worth a change.

**4. Readability.** Comments explain *why this shape* throughout and match the density the
project asks for; the `_ASKED_FOR_DEPTH` note on why `?` is deliberately absent, and the
`_COUNTED` note on the colon being the whole discriminator, are the two that earn their
lines. Test names are sentences and the docstrings name the failure rather than restating
the assertion — `test_the_same_long_reply_is_not_flagged_when_the_prompt_asked_for_depth`
is the one carrying the most weight and it says so. The four AC pairs are the first four
tests, as the file header claims. `test_every_finding_names_the_check_the_reader_already_
agreed_to` asserting `["Q4", "rule", "Q3"]` splits `"rule 6"` mid-token, which reads as a
typo until you check it; a prefix assertion would say what it means.

**5. Performance.** Measured, not guessed: `wfctl hook response-shape` against a 2.5 MB
transcript is 0.12 s wall against 0.09 s for the existing `user-prompt` hook — the read is
~35 ms of it and the rest is CLI import, which the repo already pays every turn. The
`ponytail:` note about seeking to the tail is honest and premature in the right direction.

**6. Over-engineering.** Nothing to delete. `existed` is a dict keyed by `rel` where every
`rel` is the same value today, which is two lines more than a scalar, but it is the shape
that makes the "sampled once per pass" invariant readable and I would not trade it. The
`gone` lookup with an `"is gone"` default has one unreachable arm, justified by manifests
written by other wfctl versions. `MANAGED_HOOKS`, `STOP_HOOK_COMMAND` and the `|| true`
test each have three consumers or a stated failure they prevent.
