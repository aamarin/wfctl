## BLOCKER 1 — machine-written `user` records become the prompt

`wfctl/cli.py:L2950`

```python
if record.get("type") == "user" and "tool_result" not in kinds:
    prompt, reply = _message_text(message), []
```

`tool_result` is not the only `type: "user"` record a real transcript carries.
Two other classes arrive as plain user messages and are picked up as the
reader's words:

| class | discriminator in the JSONL | count in corpus |
|---|---|---|
| task notifications, usage-limit notices | `promptSource: "system"` | 137 terminal replies |
| skill bodies injected on `Skill` invocation, pasted-image stubs | `isMeta: true` | 334 terminal replies |

**471 of 1975 terminal replies (24%) have their prompt attributed to text the
reader never wrote.** A `Skill` invocation injects the whole `SKILL.md` — 2 to
12 KB — as a user message beginning `Base directory for this skill: …`; a
pasted image injects `[Image: source: /…/4.png]`; a subagent completion injects
`<task-notification>…<result>…`.

This breaks the AC that the issue calls the load-bearing one — *"A long reply
that **was** asked for is not flagged"* — in both directions, and the direction
that matters is the one the issue predicted:

- **False positives.** Concrete instance from the corpus: the reader typed
  `why does this matter`, a system record (`Your claude.ai usage limit has
  reset…`) landed between the prompt and the reply, and the Q3 finding fires on
  a reply whose depth was explicitly requested. `why` is in `_ASKED_FOR_DEPTH`;
  the check never sees it.
- **Silent suppression.** Q3 fired **0 times across all 137** replies attributed
  to a `system` record — subagent result text reliably contains `review`,
  `analysis`, `why`. After any subagent completes, the length signal is off for
  the rest of the turn and nothing says so. The relay-the-findings reply is
  exactly the shape #212 was filed about.

`_ASKED_FOR_DEPTH`'s docstring argues the list is deliberately over-broad so a
miss costs nothing and a false positive costs the check. That reasoning is
right and it is defeated here by the input, not by the regex: for a quarter of
turns the string being searched is not the prompt at all.

**Fix** — one guard, both fields already present in every record:

```python
if record.get("type") == "user" and "tool_result" not in kinds:
    # Not every `user` record is the reader. A task notification, a usage-limit
    # notice and the SKILL.md body injected on a `Skill` call all arrive this
    # way, and taking one as the prompt judges the reply against text nobody
    # typed — in both directions, since a skill body asks for everything and an
    # image stub asks for nothing.
    if record.get("isMeta") or record.get("promptSource") == "system":
        continue
    prompt, reply = _message_text(message), []
```

`continue` rather than a reset: these records only ever arrive after a tool
call, so the reply has already been cleared, and leaving `prompt` alone is what
keeps the reader's actual words in scope.

Regression test to add beside `test_a_tool_result_does_not_start_a_new_turn`,
which is the same test one case short:

```python
def test_a_notification_the_reader_did_not_write_is_not_the_prompt(tmp_path):
    """A task notification and an injected skill body both arrive as `user`
    records. Taking one as the prompt judges the reply against text nobody
    typed — Q3 fired on none of the 137 notification-attributed replies in the
    corpus this was tuned on, and on one where the reader had typed "why"."""
```

## BLOCKER 2 — the `{}` scaffold survives on the upgrade path

`wfctl/cli.py:L1567`

The commit message says the per-pass `existed` sampling closes this:

> `created` is sampled once per pass rather than per target, or the second event
> sees the file the first just created and uninstall leaves an empty `{}` behind.

It closes it for a fresh install. It does not close it for the sequence every
existing consumer will take — installed under the previous wfctl (one event),
re-installed under this one (two events). Reproduced:

```
records after the upgrade install:
   UserPromptSubmit created= True
   Stop             created= False
file still present after uninstall: True
leftover content: {}
```

The cause is that `created` is keyed per `(path, event)` while the fact it
encodes — *did wfctl bring this file into existence* — is per **file**. On the
upgrade pass the file exists (wfctl made it), so the new `Stop` record honestly
records `created: False`; `_unmerge_hooks` unlinks only when the record that
empties the file says `created`, and that is now the `Stop` record. The
`prior` carry-forward that `existed` was meant to complement only reaches the
`UserPromptSubmit` record, because a `Stop` record has no prior.

This is the exact failure `test_uninstall_prunes_the_group_when_wfctls_entry_was_alone`
exists for, and that test cannot see it — it installs once, so both records get
`created: True`.

**Fix** — one derivation per file rather than per target, before the loop:

```python
# Per file, not per entry: `created` answers "did wfctl bring this file into
# existence", and two events share one file. Sampling it per target is wrong on
# the upgrade path as well as within a pass — a repo installed when wfctl
# managed one event gets `created: False` on the second, and uninstall, which
# unlinks on the record that empties the file, leaves the `{}` behind.
created = {
    rel: next(
        (p["created"] for (path_, _), p in prior.items() if path_ == rel),
        not existed[rel],
    )
    for rel, _, _ in targets
}
```

then `records.append({..., "created": created[rel]})`. The `keep` lookup drops
out of that line entirely.

The regression test is the existing one with an install in front of it:

```python
def test_uninstall_prunes_the_group_when_a_later_wfctl_added_a_second_event(...):
    """#212 added a `Stop` entry beside the `UserPromptSubmit` one. A repo
    installed before that has one record saying wfctl created the file and one,
    written on upgrade, saying it did not — and uninstall unlinks on the second."""
```

## WARNING 3 — a table is a drawing, and it is counted as prose

`wfctl/_reply.py:L130`

`_prose` strips fenced blocks, and the docstring gives the right reason:

> rule 6 exempts "a drawing", and a fifty-line diff is not fifty lines of prose.

Markdown tables are the *other* drawing the skill endorses — the SKILL.md's own
"Three surfaces that are not prose" and its selection table — and they are
counted. Over the corpus:

**162 of 450 Q3 findings (36%) fall below the 250-word threshold once
`|`-leading lines are excluded.** Examples, prose words after the arrow:

```
285 → 222   "You're right, and the rule I broke is already in the file…"
259 → 150   "Written: `judgment-test.md`, 124 lines."
298 → 247   "PR #130 is open and all four CI jobs pass: …"
```

The finding's own wording — `Q3 — 259 words of prose` — is false in those
cases, which matters more than the count does: this is the finding the issue
says must not read as a word budget, and a third of the time it is charging the
reader for a table it also tells them to prefer.

**Fix** in `_prose`, keeping the existing fence split:

```python
    outside = "".join(_FENCE.split(reply)[::4])
    # Table rows go with the fences. A table is the other drawing rule 6
    # exempts — the skill's own "surfaces that are not prose" — and counting its
    # cells put 36% of the Q3 findings in this corpus over the line on cells
    # rather than sentences.
    return "\n".join(
        line for line in outside.splitlines() if not line.lstrip().startswith("|")
    )
```

Note this also removes table rows from the heading and counted-lead-in scans,
which is correct — neither regex can match a line starting `|` today anyway.

## WARNING 4 — `doctor` cannot see an event it has no record for

`wfctl/cli.py:L3672`

`_check_managed_hooks` iterates `manifest[layer]["merged"]`. A repo installed by
the previous wfctl has one record, that record's command is unchanged, so the
check is silent — and the `Stop` entry is never installed. Reproduced against a
hand-built pre-#212 manifest:

```
drift reported: False
settings still has a Stop entry: False
```

Nothing else covers it. `_bundle.content_hash` walks only `wfctl/agents` and
`wfctl/specify` — deliberately, per its own comment, *"hashing `cli.py` would
make every code edit read as installed-content drift"* — and **this commit
touches no file under `wfctl/agents/`**, which is also what AC "nothing added to
the skill's prose" required. So the bundle hash is unchanged, `doctor` exits 0,
`/start-session` re-installs nothing, and AC 1 — *"Something inspects the
response after it is written"* — is satisfied for a fresh install and for
nobody else. This repo's own definition of done hides it: the author runs
`uv run wfctl install-skills` by hand.

Before this commit the record-driven check was complete, because there was one
event. This commit is what makes it partial.

**Fix** — report an event this wfctl manages that the layer has no live entry
for, not only a recorded event that drifted. The layers that qualify are those
already holding `merged` records:

```python
for layer in _layer_keys(manifest):
    merged = manifest[layer].get("merged", [])
    if not merged:
        continue
    # Every event this wfctl manages, not only the ones the record names: a
    # repo installed when wfctl managed fewer events has no record for the new
    # one, and the bundle hash cannot see it either — `content_hash` walks the
    # skills trees, and adding an event changes no file in them.
    events = {r["event"] for r in merged} | set(MANAGED_HOOKS)
```

with the per-record `path` for a known event and `SETTINGS_PATH` for one that
has no record yet.

## WARNING 5 — the counted lead-in check does not reach the coda it documents

`wfctl/_reply.py:L58`. The comment above the regex says:

> Anywhere in the reply, not only the opening: the observed shape is a coda —
> the answer lands, then "One thing I couldn't finish:" starts a second block.

`findings` applies it with `_COUNTED.match(line)`, so "anywhere" means *at the
start of any line*. A coda that follows the answer inside the same paragraph —
which is how these replies are written, one long unwrapped line per paragraph —
is invisible:

```
Merged. Two things worth flagging: a and b.        -> []
```

**112 of 1975 corpus replies** carry a counted lead-in after a sentence boundary
and are flagged for nothing. That is 25× the measured false-positive rate of the
same finding (Warning: NIT 8, 3 hits), so the trade the module's docstring
strikes — *"A missed real violation costs nothing"* — is being paid at a rate
the docstring does not anticipate for the one finding the issue names as a
binding AC.

**Fix** — let it start at a sentence boundary as well as a line start, and
search rather than match:

```python
_COUNTED = re.compile(
    r"(?:^|(?<=[.!?—]) )\s*(?:\*\*|_)?(one|two|three|four|five|six|seven|eight"
    r"|nine|ten|both|several|a few)\b[^\n]*:",
    re.IGNORECASE | re.MULTILINE,
)
```

If the extra reach is judged too risky against the FP budget, the honest
alternative is cheaper: cut the "Anywhere in the reply" paragraph, since it
describes behaviour the code does not have and the next reader will trust it.

## NIT 8 — the colon a URL brings with it

# The six passes

## 1. Correctness — adversarial

Ran. Blockers 1 and 2 and Warnings 3–6 came out of this pass, each reproduced.
Also checked and found **sound**:

- **`_prose`'s `[::4]` slice.** `re.split` with one capturing group yields
  text/marker/text/marker; pieces outside a block land four apart. Verified on
  an unclosed fence (`'a\n```\ncode\n'` → `'a\n'`, tail dropped as documented)
  and a four-backtick fence (splits on the first three, leaves a stray backtick
  in prose — one word, harmless).
- **Terminal-reply reconstruction.** Text is appended before `reply` is cleared
  on a `tool_use`, so a message carrying both is handled correctly. Thinking and
  tool blocks contribute nothing. Verified against 60 real transcripts.
- **No sidechain contamination.** I expected subagent turns in the main JSONL
  (`isSidechain: true`) to be picked up as the terminal reply. `grep` over every
  wfctl transcript returns **zero** such records — subagent transcripts are
  separate files. Not a finding.
- **`|| true` on `Stop`.** Correct and load-bearing. Confirmed empirically: the
  bare `wfctl` on PATH answers `No such command 'response-shape'` with a
  non-zero exit, which on `Stop` blocks the stop. The guard turns exactly that
  into a no-op. The test pinning the string is worth its line.
- **Uninstall ordering.** The unlink does not depend on record order within one
  pass — the file is only empty after the last removal. (It depends on `created`,
  which is Blocker 2.)
- **`doctor`'s `MANAGED_HOOKS.get(event)`.** For an event wfctl no longer
  manages: entry present → `None` ≠ command → drift, "is behind this wfctl",
  correct; entry absent → `None == None` → silent, also correct.
- **Idempotence.** Re-install writes nothing (`merge_hook` returns False on both
  entries), so the consumer's file is reflowed once. Confirmed by the passing
  suite.

## 2. Security

Ran. No finding.

- `transcript_path` is taken from a payload Claude Code writes, and is opened
  read-only with `errors="replace"`. A hostile path would leak file content into
  a `systemMessage` in the same session that supplied it — no privilege gained.
- Reply text reaches the `systemMessage` through `!r`, so an embedded newline
  cannot forge a second bullet. This matches the escaping discipline `cli.py`
  documents for skill names and digests, and it is the right call — worth
  keeping if the wording is ever edited.
- No secrets, no shell interpolation of transcript content. The `2>/dev/null`
  swallows stderr, which the comment justifies and I agree with.
- Every field is type-checked before use; `test_a_payload_this_hook_cannot_read_describes_no_reply`
  covers `""`, `not json`, `[]`, `{}`, and a non-string path.

## 3. Architecture

Ran. Fits.

- `_reply.py` is pure, imports only `re`, and holds the decision table — the
  `_guard`/`_workmux` shape, stated as such in its docstring. Correct band in
  `views/current-state.md`, and the drawing was updated (`_reply 137`).
- `MANAGED_HOOKS` as one map is the right call: three call sites (merge,
  uninstall record, `doctor`) had to agree, and the comment says so. The one gap
  is that `doctor` still reads records instead of the map (Warning 4).
- `install-modes.md` amended rather than superseded, with the right verdict —
  ownership was already drawn at the command entry, so per-event is not a new
  mode. The dated amendment line follows the file's existing form.
- `wfctl arch context`'s eight accepted records: `no-hardcoded-agent` is the only
  one in range and is satisfied (`wfctl hook response-shape` names no agent).
- Nothing added to `conversation-response-shape`'s prose — AC met, and it is what
  makes Warning 4 invisible to the bundle hash.

## 4. Readability & simplification

Ran. No blocking finding. The comments explain *why this shape* throughout and
match the house style; the `|| true` comment in particular earns its length.
Three small things:

- The docstring's coda paragraph in `_reply.py:L52-55` describes reach the code
  does not have (Warning 5). A comment that will be trusted and is wrong is
  worse than none.
- `existed = {rel: ... for rel, _, _ in targets}` at `cli.py:L1521` uses a
  hanging-indent style the surrounding file does not; `E501` is not in the ruff
  set so nothing enforces it either way. Author's call.
- `[line.split(" ")[0] for line in found] == ["Q4", "rule", "Q3"]` in

  the fragment `"rule"`. It reads oddly next to two real labels; `line[:6]`
  or a `startswith` triple would say what it means.

Test docstrings are sentences and name the failure they exist for — the
convention `CLAUDE.md` asks for, met better than most of the suite.

## 5. Performance

Ran. Acceptable, quantified:

- `_last_exchange` over the largest real transcript (2.93 MB, ~1200 records):
  **25.5 ms**. End-to-end `wfctl hook response-shape` on the installed binary:
  **0.23 s wall**, dominated by interpreter and typer import, not the read.
- That is once per turn, and the `ponytail:` comment already names the tail-seek
  as the escape hatch if transcripts grow. Right call not to build it now — a
  tail seek has to handle a turn boundary above the window, which is more code
  than 25 ms is worth.
- `_reply.findings` is linear in the reply, sub-millisecond.

## 6. Over-engineering

Ran. **`Lean already.`** — I found nothing to delete.

- `MANAGED_HOOKS` has two entries and three consumers; not speculative.
- `_message_text` is a second function for a real second shape (bare string vs
  block list) and is used twice.
- `_prose` is one line and load-bearing.
- The `gone` dict in `_check_managed_hooks` looks like a lookup for two cases,
  but its `.get(event, "is gone")` fallback is reachable — a record can name an
  event this wfctl no longer manages. Keep.
- Every fix I propose above *adds* lines (roughly +18 net across the six). The
  diff is not carrying weight it should shed.
