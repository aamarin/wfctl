## Findings

**WARNING** `wfctl/_tracker.py:L291` — a hold filed as `issue-<verb>` is lifted
by *any* later success of that verb, including one against a different issue.
`dispatch` records `issue-{verb}` with no id, and `standing_blocks` matches on
the action string alone, so the block `end-session` files when the host refuses
a comment on the branch's issue is silently released by a successful
`wfctl issue comment` on a follow-up issue created in the same turn. `status`
then reads the step as done with the refused write never made — the exact state
the hold exists to prevent. The reachable sequence is real: `speckit.analyze`
and `speckit-delivery-plan` both file `issue-create` and both call
`wfctl issue create` more than once in a run. This was not reachable before the
change (holds were filed as `issue-create`, writes recorded bare `create`), and
neither `spec.md`, `contracts/cli.md`,
`384-an-action-is-named-by-the-verb-that-takes-it` § Consequences nor
`384-the-agent-reports-through-two-flat-verbs` names the case.
→ Fix: `dispatch` already holds `params["id"]`, so an id-scoped name
(`issue-<verb>:<id>`) is available, but it would need the skills to file the same
string and is a larger change than this diff wants. The cheaper fix, and the one
consistent with keeping `action` free text, is to write the limitation down:
add it to that record's Consequences and qualify
`docs/reference.md:L613` ("**Taking the action lifts its own hold.**"), which as
written tells a reader the lift means *that* action happened.

**NIT** `wfctl/agents/commands/speckit.decompose.md:L8` — `Bash(wfctl
report-action*)` in `allowed-tools` has no call site left in the skill it wraps.
The only mention of `report-action` in `speckit-delivery-plan/SKILL.md` is
addressed to a person ("a person who creates the issue outside wfctl lifts it
with `wfctl report-action issue-create`"); the grant it replaced
(`Bash(wfctl notify*)`) existed for the `--declined` recording #384 removed.
`speckit.analyze.md` and `speckit.implement.md` correctly took `report-block`
alone for the same shape. → Drop it; the cross-reference test asserts only
`wfctl report-block`, so nothing holds it in place.

**NIT** `wfctl/cli.py:L103` — the comment above `_FACT_NAME_WIDTH` says "the
block and its tests both need it", and no test references the constant. Checked
`origin/main`'s `test_four_facts.py` too: it never did either, so the claim was
already false, but the diff re-derives the value here (26 → 21) on the strength
of it. → Either add the assertion the comment promises in `test_status_facts.py`,
or drop the "and its tests" clause so the next reader does not go looking for a
pin that is not there.

**NIT** `wfctl/_session.py:L251` — `record_notify_action` keeps "notify" in the
*function* name. The docstring's argument for keeping the *event* name
(`notify-action`) is right and well made — storage versus interface, and
`_restart`'s reader plus every written log depend on it — but the function is
interface-side, and "notify" is the proxy word the level-2 record removes.
→ `record_action`, leaving the `append_event` string untouched.
