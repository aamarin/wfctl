## Pass 1 — Correctness

Traced `hook_main` → `run_hook` → `threshold` / `occupancy` / `_repo_root` /
`resolve_branch` / `resolve_agent_dir` / `read_events` / `decide` / `message` /
`spawn_worker`, and `_restart_send.run` → `_alive` / `_send` / `append_event`;
then `merge_hook` / `prune_unshipped` / `_remove_where` / `subcommand_of` /
`managed_command` / `managed_subcommands` through `_merge_hooks`,
`_unmerge_hooks` and `_report_hook_drift`. Checked every state in
`data-model.md`'s table against `decide`, and the `end` event name against its
only writer (`wfctl/_session.py:666` — `append_event(agent_dir, "end", …,
continued=continued)`; it matches).

**What holds.** The ordering rules are right. `last(kind, match, after)` uses
`range(len-1, after, -1)`, so `after` is exclusive and "after the send" really
means strictly after — the property `test_a_stop_before_the_send_is_not_the_handoff`
pins. `planned_clear` before `planned_end` is the correct precedence: once a
clear is decided, the end branch can no longer be re-entered. Every retry path is
closed — a failed `/end-session restart` send goes to `not-taken` and is never
resent (Q2), and a `not-taken` already recorded after the deciding event returns
`NOTHING`. The `tokens < limit` guard at the top is also what makes a *successful*
clear safe if Claude Code ever preserved `session_id` across `/clear`: the window
is small afterwards, so the stale `session-restart` events can never be re-read as
a clear that did not take.

decision tests are unaffected — `test_restart_decide.py` passes explicit mappings
throughout, which is the pattern the CLI file should have copied.

**WARNING — the hold message fires on the happy path.** This branch's own event
log is the evidence; a successful restart at 13:58–14:00 on 2026-09-15 recorded:

| ts | event | decision |
|---|---|---|
| 13:58:43 | `session-restart` | `end` |
| 13:58:45 | `session-restart-send` | `/end-session restart`, exit 0 |
| 13:59:05 | `session-restart` | **`hold`** |
| 13:59:31 | `end` | `continued: true` |
| 14:00:42 | `session-restart` | `clear` |

A reply end landed 20 s after the send and 26 s before the handoff turn recorded
its stop — a person typing, or the in-flight reply finishing while the send sat
queued. The decision is right (`FR-010a` and US2 scenario 1 both say hold). The
*message* is not: `session restart held: /end-session recorded no stop — context
not cleared` tells the person the handoff failed, at the moment it simply has not
run yet, and `SC-003`'s "no condition produces none" is satisfied while the pane
gets a false alarm on the ordinary path. `decide` cannot distinguish the two
today, but it does not have to report on the first one: holding silently once and
reporting on the second consecutive reply end with no stop would keep the real
condition (US2's "handoff turn asked a question") reported and drop this one. A
reword — "waiting for /end-session to record its stop" — is the cheaper half fix.

**WARNING — a send event that never lands wedges the session.** `decide` returns
`NOTHING` whenever a decision is recorded and its send is not (`_restart.py:213`
for clear, `:222` for end). The worker writes that event only after `_send`
returns, so a worker killed between `Popen` and `append_event` — machine sleep, a
tmux teardown, an OOM — leaves a session that decides nothing on every subsequent
reply end, shows nothing, and never restarts, with a window that only grows. This
is the failure mode the personal script had and #371 was filed over, reached by a
different route. `FR-010a` specifies the *transient* case and says nothing about
the unbounded one. A decision with no send after (say) three reply ends, or after
a wall-clock gap, is indistinguishable from a dead worker and could be reported
once through the same `not-taken` channel that already says "never sent".

**Checked and clear.** `landed` deliberately counts any `end` on the branch
(two panes on one branch — spec's "not guarded"). `_alive` returning `True` for a
zombie is covered by `SETTLE` and `WAIT_CAP`. `occupancy` returning `None` rather
than `0` is load-bearing and tested. `subcommand_of` handles `wfctl hookup`,
`wfctl hook ` and a bare consumer command. `_merge_hooks` re-reads the settings
file per target, so the two `Stop` rows compose correctly across targets 2 and 3.
`_unmerge_hooks` sees two `Stop` records and `remove_hooks` is event-wide, so the
second call is a no-op rather than a bug. `_HOOK_GONE[subcommand]` cannot
`KeyError` — all four shipped subcommands are keys.

## Pass 2 — Security

No finding. Every subprocess is an argv list with `shell=False`: `workmux list
--json`, `workmux send <handle> <text>`, `git -C <cwd> rev-parse`, and
`[sys.executable, "-m", "wfctl._restart_send", json.dumps(plan)]`. The two texts
are module constants; `handle` comes from `workmux list --json` and is never
interpolated into a string. Both `subprocess.run` calls carry timeouts, and the
worker's send does too. No secret reaches the log — the events carry a session
id, a token count and an exit status. The new capability is real (a hook that
types into a terminal, installed by default in every repo with the claude layer)
and it is documented in README, gated behind a state dir wfctl has actually run
on, disarmed by one env var, and covered by `wfctl-performs-the-session-restart`;
`stdin` from the harness is validated field by field before use.

## Pass 4 — Readability & simplification

Names, guard clauses and function lengths are fine; `decide` is 75 lines but is a
first-match-wins table with the comments the table needs, and splitting it would
separate a rule from its reason. Comments explain *why* throughout and match the
repo's density. The docstrings claiming measured facts check out — `SETTLE=2.0` /
`GAP=5.0` match the contract's "2 s … 5 s", `_entry 43` / `_restart 415` /
`_restart_send 121` match the files, README's "five entries … four are hooks"
matches `MANAGED_HOOKS`.

**NIT — `END = "end"` collides with the stop event's name.** `_restart.py:64`
defines the decision kind `END = "end"`; `_restart.py:232` reads the *stop* event
with the literal `"end"`. Two different facts spelled identically, eight lines
apart, in the function where confusing them would clear a session that never
handed off. `SEND_END` (or keeping the constant and naming the event via a
constant of its own) removes the trap.

**NIT — `_restart.py:355`'s `assert isinstance(...)` restates line 353.** It
exists to narrow for mypy after `all(...)`, which does not narrow. `python -O`
strips it, so it is not a runtime check either. Three `isinstance` checks written
out, or one small helper, says the same thing without an assertion that looks like
a safety net and is not.

**NIT — `run_hook` is half-injected.** It takes `environ` for the threshold but
`resolve_branch` and `resolve_agent_dir` read `os.environ` directly. Tests work
because monkeypatch writes through to `os.environ` — which is also exactly how the
BLOCKER above slipped in.

**NIT — doctor's early return hides an unshipped row.** `_report_hook_drift`
returns `False` as soon as `actual == expected`, so a stale `wfctl hook <old>` row
sitting beside two current ones is never reported. `prune_unshipped` removes it on
the next install, so the cost is only that doctor is quiet about a row that runs
on every turn.

## Pass 5 — Performance

No finding. `occupancy` is on every reply end, before the threshold is known, so I
measured it against the largest real transcript on this machine rather than the
1.6 MB the spec cites: **6.6 MB read in 18–22 ms**, comfortably inside `SC-004`.
`decide` asks workmux only on the reply ends that would send — `find_handle` is a
callable, and `test_under_the_threshold_decides_nothing_and_never_asks_workmux`
pins that. `read_events` reads the whole log, which is ~100 lines after a full
feature. The `limit == 0 or tokens is None or tokens < limit` guard duplicated
between `run_hook` and `decide` earns its keep: it skips the `git rev-parse`
subprocess, and the `if limit else None` before it skips the transcript read
entirely when the restart is off.

One note on the reading itself, since it is the feature's whole trigger:
`occupancy` matches any record with `message.usage` — it does not filter on
`type == "assistant"` or `isSidechain`. I swept 80 transcripts under
`~/.claude/projects/`: **0 files carry a sidechain usage record, and 0 files end
on a zero-usage (`<synthetic>`) record**, though 22 of 60 contain one somewhere.
So there is no live defect; a harness that started writing subagent turns into the
main transcript would introduce one, and the worst case is one reply end reading
low and deciding nothing.

## Pass 6 — Over-engineering

**NIT — `yagni:` `managed_command`'s `subcommand=None` default (`_settings.py:83`).**
Every production caller passes a subcommand (`cli.py:5834` is the only one).
The `None` branch and the docstring sentence explaining it are kept alive by three
tests that exist because the parameter does. Drop the default, make the argument
required, and update those three call sites.

`shrink:` candidates and nothing else: the assert at `_restart.py:355`. Nothing to
`delete:`, `stdlib:` or `native:` — the injected `spawn` and `handle_for`
parameters each have a second implementation in the tests, which is the pressure
that justifies them, and `Decision` as a frozen dataclass with a `texts` property
is smaller than the tuple-plus-lookup it replaces. The tests are dense and each
docstring names the failure it guards; none is padding.
