## Findings

### BLOCKER

**B1 — `tests/test_restart_hook_cli.py`:L72,83,95,121,162 — the suite's verdict
depends on the reviewer's own `WFCTL_RESTART_THRESHOLD`; it is red in this
worktree right now.**

Every in-process test in the file passes the live `os.environ` straight into
`run_hook`, and nothing pins `WFCTL_RESTART_THRESHOLD`. This shell exports
`WFCTL_RESTART_THRESHOLD=90000`, so the full suite fails today:

```
FAILED tests/test_restart_hook_cli.py::test_over_the_threshold_records_the_decision_and_starts_the_worker
E   Differing items:
E   {'threshold': 90000} != {'threshold': 200000}
1 failed, 1711 passed in 132.33s
```

With `WFCTL_RESTART_THRESHOLD=0` — the off-switch US3 and the README both tell
developers to set — seven of the file's seventeen tests fail: the decision test,
the clear test, all four report parametrisations, and the detach test. CI is
green because CI never sets the variable, so the red appears only on the
machines that adopt the feature, which is the worst place for it to appear.

Two things make this a blocker rather than a nit. The project's definition of
done is `uv run pytest -q` green, and it is not. And the repo has already
decided this class of dependency is not allowed: `conftest.py` pins `NO_COLOR`
at import time and stubs the version check autouse, with the reason written
down — *"Autouse rather than per-test so a future test cannot reintroduce the
dependency by forgetting."* This change reintroduced it by forgetting.

Fix (either):
- `monkeypatch.delenv(_restart.THRESHOLD_ENV, raising=False)` in the `repo`
  fixture, plus an explicit `{**os.environ, THRESHOLD_ENV: "150000"}` mapping in
  any test that means a particular threshold; or
- an autouse fixture in `tests/conftest.py` beside `_tool_version_is_not_under_test`,
  which is the shape that also protects tests nobody has written yet.

`tests/test_restart_decide.py` is immune — it builds `environ` dicts by hand.
Only the CLI file reaches for the real environment.

### WARNING

**W1 — `wfctl/cli.py`:L5838-5841 — `doctor` is blind to an unshipped wfctl row
when the shipped rows are all current.**

`renamed` is computed only under `actual is None`. So a `Stop` array carrying
`response-shape`, `session-restart` *and* a leftover `wfctl hook old-name`
reports no drift: the per-command loop finds both shipped rows byte-correct and
returns `False` twice, and nothing ever looks at the third row. Meanwhile
`install-skills` prunes it. `doctor` therefore says "clean" about a file the
next install will change, while the stale hook runs on every reply end.

`prune_unshipped` is the write side of exactly this fact and the new record
names it as "what keeps a rename from leaving its predecessor running beside
it". There is no read side. Fix: after the `for event, command in MANAGED_HOOKS`
loop in `_check_managed_hooks`, report once per event any
`_settings.managed_subcommands(settings, event)` entry not in
`_shipped_subcommands(event)`.

Reachable only once wfctl renames a hook subcommand — which is the scenario this
whole identity change exists to serve, so the gap sits directly on the new
seam.

**W2 — `wfctl/cli.py`:L5857 — `_HOOK_GONE[subcommand]` is an unguarded index on
a hand-synchronised table, and nothing checks the two agree.**

`_HOOK_GONE` moved from event keys (three, self-evident from `MANAGED_HOOKS`
being a three-entry map) to subcommand keys (four, in a different literal
twenty lines away). A fifth managed hook added without its `_HOOK_GONE` line
makes `wfctl doctor` raise `KeyError` instead of reporting — on the command
whose entire job is to report.

This is `a-rule-is-expressed-as-a-check` on a rule the code already depends on,
and the violation is visible in an artifact the work produces. One line:

```python
assert {_settings.subcommand_of(c) or "" for _, c in MANAGED_HOOKS} == set(_HOOK_GONE)
```

as a test, or a `.get()` with a generic fallback if the crash is preferred to a
missing cost line. Either beats the current silence.

### NIT

**N1 — `wfctl/_restart.py`:L237,243 — the skip message can print twice in one
session, where FR-008 says once.** The post-handoff branch scopes its check to
the `END` decision's index (`decided(SKIP, pos)`); the pre-handoff branch scopes
it to the whole session (`decided(SKIP)`). A pane that disappears, returns long
enough for the `/end-session restart` send, and disappears again prints the skip
twice. Defensible — they are two different conditions and both are actionable —
but it diverges from the requirement with nothing saying so. Either use
`decided(SKIP)` in both, or put the reason in the comment that already explains
the branch above it.

**N2 — `wfctl/_restart.py`:L262 — `message()` hardcodes `/clear` in one arm and
reads `send.get('text')` in the other.** Unreachable today (an `exit == 0`
`NOT_TAKEN` only arises on the clear path, because the end path returns
`NOT_TAKEN` solely for `exit != 0`), but it is a message that names the wrong
command the first time another text can reach state F. `send.get('text')` costs
nothing and the contract string is unchanged for `/clear`.

**N3 — `wfctl/_settings.py`:L82-92 — `yagni:` `managed_command`'s
`subcommand=None` mode has no production caller.** `_report_hook_drift` always
passes one; only `test_managed_command_reads_back_what_was_installed` and
`test_managed_command_is_none_when_the_consumer_deleted_the_entry` exercise the
default. Make the parameter required and update those two.

**N4 — `wfctl/_restart.py`:L359 vs L188 — `shrink:` `run_hook` repeats `decide`'s
own below-threshold guard, −2 lines.** It is defensible as written: it
short-circuits `_repo_root`'s `git` call before `decide` is reached, and
`decide` has to stand alone as a pure function. A nit only because the comment
beside it does not say that is the reason, so the next reader reads it as
duplication.

**N5 — `wfctl/_restart.py`:L405 — `sys.stdin.isatty()` sits outside
`hook_main`'s `try`.** The docstring promises "Exit 0 on every path"; a closed
or absent `sys.stdin` tracebacks out past it. The installed row's
`2>/dev/null || true` covers the consequence, not the promise. Move the isatty
check inside the try.

**N6 — `wfctl/_settings.py`:L401 — `managed_matcher` is the one reader the new
identity did not reach.** It still answers per event, taking the first managed
group. Harmless today, because `_HOOK_MATCHER` holds only `PreToolUse` and that
event carries one wfctl row — but the record's whole claim is that a row is
identified by event *and* subcommand, and this function still says otherwise. A
line in its docstring naming the assumption is enough.

**N7 — `docs/architecture/install-modes.md`:L38 (accepted) now contradicts the
code.** Its merge row still reads "one entry per managed event".
`a-managed-hook-is-owned-by-its-subcommand` (proposed) names the `Log` line as
an on-acceptance step, so this is the repo's deliberate holding pattern rather
than drift — recorded here only so the coordinator knows the *accepted* set is
one line behind the shipped behaviour while the amending record waits.

**N8 — `CLAUDE.md` says nothing about the restart.** A worker in this repo will
now have its pane cleared automatically, and learns it from the pane. Under
`knowledge-placement`, guidance for the worker goes to `AGENTS.md`; one line
under "Session state" naming `WFCTL_RESTART_THRESHOLD` and what a restart does
would carry it.

## The six passes — what each covered

**1. Correctness (adversarial).** Traced `decide()` state by state against
`spec.md`'s FR list and the three clarifications, walking the event log
forwards: below threshold; `END` planned but unsent (FR-010a); `END` sent with
`exit != 0` (clarification Q2, reported once, never resent); `END` sent, no
stop (hold, once per send); any `end` after the send, continued or not
(clarification Q1); `CLEAR` planned but unsent; `CLEAR` sent `exit 0` with the
session still alive (state F); `CLEAR` send failed; no pane at each of the two
points it is asked for; threshold `0`; a second session inheriting the first's
events. First-match order (`CLEAR` before `END` before the fresh plan) is right,
the `session` filter is applied on every lookup, and `last(..., after)`'s
`range(len-1, after, -1)` covers index 0 at `after=-1`. The `landed` check reads
`e.get("event") == "end"` — the decision events are `event: "session-restart"`
with `decision: "end"`, so the two do not collide despite sharing the string.
Ordering is line position, never `ts`, as the module docstring claims, and the
decision event is appended before `spawn`, which is what makes `sent(text, pos)`
well-founded.

Checked `occupancy()` against real data rather than the tests: the last usage
record wins, and I confirmed against 401 transcripts on this machine that no
sidechain (subagent) record carries a `usage` block, so the "last record" cannot
be a subagent's window — the failure mode I went looking for is not present.
Measured the read cost on the three largest transcripts here: 12.1 MB / 64 ms,
8.5 MB / 28 ms, 8.0 MB / 38 ms, comfortably inside SC-004.

Checked `_restart_send.run()`: waits on the parent pid with a cap, settles,
sends in order, records each exit, stops at the first failure so `/start-session`
cannot land inside the session `/clear` was meant to end. `_send` returns `-1`
for both `OSError` and timeout, which is what `message()`'s "never sent" arm
reads.

Checked `_merge_hooks`' `created` derivation under two `Stop` targets sharing
one file — it is keyed per file and `next(...)` over any prior record for that
path, so the duplicate target does not double-count; and the manifest key
widened to three fields on both the write and the read side.

Found: B1, N1, N2.

**2. Security.** No secrets, no shell. Every subprocess is a list argv
(`git -C`, `workmux list --json`, `workmux send`, `sys.executable -m`), so the
pane text and the handle cannot reach a shell. `handle` comes from `workmux
list --json` and is matched on `Path(path).resolve() == repo_root.resolve()`,
not on a directory name. The `Stop` payload is treated as untrusted:
`session_id`, `transcript_path` and `cwd` are each checked non-empty `str`
before use, a non-dict payload returns `None`, and malformed JSON on either
stdin or the event log is skipped rather than raised. The worker's plan travels
as one argv element and therefore shows in `ps` — it holds a repo path and a
workmux handle, nothing sensitive. `resolve_agent_dir(create=False)` is the
right call for a hook that fires in repos wfctl was never installed in. No
findings.

**3. Architecture.** `_restart` placed in `domain` and `_restart_send` in
`surface` in `current-state.md`, with the `layers` fence updated; imports run
downward (`_entry` → `_restart` → `_paths`/`_io`; `_restart_send` → `_restart`),
so `test_only_the_declared_edge_runs_upward` and
`test_every_module_has_a_band` both still hold — the view is falsifiable here
and was updated. `_restart` reaches `_restart_send` by process spawn, not
import, which the view's new paragraph states explicitly. The hook keeps to
stdlib + `_paths` + `_io` on the fast path, matching `_hook.py`'s measured
reason, and `_entry.py`'s exact-argv rule is reused rather than reinvented.
`a-managed-hook-is-owned-by-its-subcommand` is carried consistently through
`merge_hook`, `prune_unshipped`, the manifest key, and `_report_hook_drift` —
with the two exceptions in W1 and N6. Uninstall stays event-wide on purpose and
says why. Found: W1, N6, N7.

**4. Readability & simplification.** Names carry their content
(`planned_clear`, `landed`, `sent`, `decided`, `subcommand_of`,
`prune_unshipped`). No nesting past two levels; `decide()` is a guard-clause
chain, not a tree. Comments explain *why this shape* throughout and match
`CLAUDE.md`'s standard — the `Decision` kinds as strings because they are
written into the log verbatim, the `find_handle` callable because only the
reply ends that would send should pay for a subprocess, the `2>/dev/null ||
true` note on the new hook row. Nothing narrates the diff. Docstrings on the new
tests are sentences naming the failure they caught, per the repo's convention;
`test_restart_occupancy.py` and `test_restart_decide.py` are the strongest
examples. Found: N4, N5, N8.

**5. Performance.** The per-reply cost is `occupancy()` reading the whole
transcript, measured above at 28–64 ms on 8–12 MB files; `read_events`, the
`git` calls and `workmux list` all sit behind the threshold check, so a reply
end that decides nothing does one file read and nothing else. The `_entry.py`
fast path keeps `typer` and `rich` out of that path and
`test_the_exact_argv_takes_the_fast_path_and_loads_no_cli` asserts it on
imports rather than timing. Reading the transcript backwards would be faster and
is not worth the complexity at these numbers. No findings.

**6. Over-engineering.** Looked for `delete:`, `stdlib:`, `native:`, `yagni:`
and `shrink:` across both new modules, the `_settings.py` split, and the
`cli.py` table change. `Decision.handle` is written to the log and never read
back, but it is one field of forensic value on an event a human reads — not
flagged. The decision kinds as module constants rather than an enum is argued in
the code and correct. `_USAGE` and the isatty path follow the #385 precedent.
Two real candidates only: N3 (`managed_command`'s unused `None` mode) and N4
(the repeated threshold guard).

`net: −5 lines possible` — effectively lean already.
