## Findings

### BLOCKER

**`tests/test_restart_hook_cli.py:99` (fixture at `:35`) — the suite is red whenever
`WFCTL_RESTART_THRESHOLD` is set in the environment, which is the environment this
feature exists for.**

`test_over_the_threshold_records_the_decision_and_starts_the_worker` asserts
`"threshold": DEFAULT_THRESHOLD` but passes the ambient `os.environ` into `run_hook`.
On this machine `WFCTL_RESTART_THRESHOLD=90000`, so:

```
Differing items:
{'threshold': 90000} != {'threshold': 200000}
FAILED tests/test_restart_hook_cli.py::test_over_the_threshold_records_the_decision_and_starts_the_worker
1 failed, 1711 passed in 122.21s
```

Reproduced deterministically, three ways:

| Run | Result |
|---|---|
| `uv run pytest tests/test_restart_hook_cli.py -q` (ambient 90000) | 1 failed, 16 passed |
| `env -u WFCTL_RESTART_THRESHOLD uv run pytest tests/test_restart_hook_cli.py -q` | 17 passed |
| `WFCTL_RESTART_THRESHOLD=50000 uv run pytest tests/test_restart_{hook_cli,decide,end_session}.py -q` | 1 failed, 54 passed |

The `repo` fixture already scrubs `WFCTL_STATE_DIR` — it just misses the one variable
this change introduced. `CLAUDE.md` makes all three commands green "the whole bar for a
code change"; CI is green only because CI has no such variable, which means the failure
lands on whoever tunes the threshold — the documented use.

Fix, in the `repo` fixture:

```python
monkeypatch.delenv("WFCTL_RESTART_THRESHOLD", raising=False)
```

`run_hook` already takes `environ` as a `Mapping`, so passing an explicit dict from each
test is the cleaner variant. `_entry(...)` at `:205` also inherits (`env=None`) and needs
the same treatment for `test_the_exact_argv_takes_the_fast_path_and_loads_no_cli`.

### WARNING

**`tests/test_restart_hook_cli.py:67` — the same env leak silently disarms the
under-threshold test, which is worse than the one that fails.**

`test_under_the_threshold_prints_nothing_and_creates_no_state_dir` feeds
`DEFAULT_THRESHOLD - 1` = 199999. With an ambient threshold below that, the hook goes
*over*, resolves the repo root, and returns `None` only because the state dir is absent.
The assertion `not (tmp_path / "xdg").exists()` still passes, so the test named for the
under-threshold path reports green while testing the never-ran-here path instead. Same
fix as the blocker; worth a line in the docstring naming why the fixture scrubs it, since
`CLAUDE.md` asks docstrings to say what failure the test exists to catch.

**`wfctl/_restart.py:388–396` — a `spawn()` that raises leaves the session permanently
stalled, at a full window, with nothing said in the pane.**

`run_hook` appends the `end` decision and *then* calls `spawn(...)` outside any `try`.
`spawn_worker`'s `subprocess.Popen` has no guard of its own, and `hook_main`'s bare
`except Exception: return 0` swallows the failure. From that point on, every later reply
end takes the `planned_end` branch, finds `sent(END_TEXT, pos) is None`, and returns
`NOTHING` — forever, by design ("a reply end decides nothing until the send's own event
exists"). The three unsafe conditions the spec requires to be reported do not cover "the
worker never started", so the outcome is exactly the state the feature exists to prevent,
silently.

Reachable two ways: `Popen` failing (rare — fork/resource limits), and the detached
worker being killed inside its ~12 s wait-and-settle window before it records anything.

Fix — record the failure as the send it would have been, which routes straight into the
existing `not-taken` report ("never sent … — run it yourself"):

```python
if decision.texts:
    try:
        spawn({...})
    except OSError:
        append_event(state_dir, SEND_EVENT, session=session,
                     text=decision.texts[0], exit=-1)
```

That closes the `Popen` half outright. The killed-worker half needs a bound — e.g. the
`hold` report also firing when a `planned_*` has gone N reply ends with no send beside
it — and is defensible as a follow-up issue rather than in this diff, but it should be
written down rather than left implicit.

### NIT

`wfctl/_restart_send.py:82–84` — `yagni:` `run()`'s `sleep` and `clock` parameters are
never passed by any caller. All four test call sites are `run(_plan(...))`; every timing
override arrives on the plan, as the module docstring itself says ("Timings come in on
the plan, so a worker that waits two seconds in a pane waits milliseconds here"). Delete
both and call `time.sleep` / `time.monotonic` directly. −4 lines, one fewer concept.

`wfctl/_restart.py:83` — `threshold()`'s docstring promises "an unreadable value falling
back to the default is the documented behaviour rather than a guess", but `str.isdigit()`
is not the predicate that gives that. Verified:

| `WFCTL_RESTART_THRESHOLD` | `threshold()` |
|---|---|
| `"²"` | raises `ValueError` (`isdigit()` True, `int()` refuses) |
| `"١٢٣"` | `123` — accepted, not a value anyone typed meaning 123 |
| `"abc"`, `"-5"`, `"1e5"`, `"200_000"` | `200000` ✓ (as the parametrized test asserts) |

The raise is swallowed by `hook_main`, so the cost is the contract, not a crash. Fix:
`raw.isascii() and raw.isdigit()`.

`wfctl/cli.py:5838–5841` — the `renamed` heuristic is event-wide, so it mislabels the
finding this change was made to sharpen. Verified in-process: a `Stop` carrying
`response-shape` plus a stale `wfctl hook recycle`, with `session-restart` genuinely
absent, prints

```
⬆ claude: managed Stop hook session-restart in .claude/settings.json
  is behind this wfctl
```

rather than the new per-subcommand cost line `_HOOK_GONE[_SESSION_RESTART]` ("a full
window is compacted or cleared with no handoff written first"). Both are cured by the
same install, so this is cosmetic — but the per-subcommand cost message is the point of
the change. Fix: only treat a row as this one's predecessor, not any unshipped row on
the event.

`wfctl/cli.py:5069` — `wfctl hook session-restart --help` prints a private Python
identifier at a user: "Over `WFCTL_RESTART_THRESHOLD` tokens (`_restart.DEFAULT_THRESHOLD`
when unset, `0` for off)". Forced by `test_the_default_threshold_is_written_once`, which
forbids a second literal `200000` anywhere under `wfctl/`. Fix: say "the default" in the
help text and let the README carry the number — it already does, in the env-var table.

`wfctl/cli.py:2874–2881` — the comment on the post-merge prune ("the order that never has
the event running neither") holds for one managed row per event, not two. With `Stop`
carrying two targets, the prune run for the *first* target can remove a renamed
predecessor whose successor the *second* target has not appended yet, and
`_write_settings` lands between them. Transient inside one `install-skills` run, so the
code is fine; the comment overstates its guarantee, and comments here are dense with
rationale that later readers rely on.

## What each pass covered

**1. Correctness.** Traced `decide()` against `data-model.md`'s rule table line by line —
the implementation matches it exactly, including the two rules the clarifications settled
(any stop after the send counts, continued or not; a failed `end` send reports once and
is never resent) and `find_handle` being a callable so the common reply end pays no
subprocess. Walked the full state machine by hand: below threshold → END → send → handoff
→ CLEAR; the HOLD, SKIP and NOT_TAKEN once-only loops; recovery when a pane appears after
a SKIP; and the post-`/clear` new session, whose events are excluded by the `session`
filter. Traced `occupancy` (last usage record, not a sum; `None` for every unreadable
shape), `read_events`, `find_handle`, `spawn_worker`, `_repo_root`, `run_hook`,
`hook_main`, and the worker's wait/send/record loop including its stop-at-first-failure
rule. Also traced the called-but-unchanged functions: `_io.append_event`,
`_session.end_session` (confirming `wfctl end --continued` exists and that a second `end`
keeps an existing `session-summary.md`, which the skill's step 4 overwrites by hand
anyway), `resolve_branch`, and the `_settings` merge/prune/remove family. Found the
spawn-failure stall (WARNING) and the threshold predicate (NIT).

Three things I expected to be bugs and confirmed are not:

- `landed` does not filter by session — it cannot, because `_session.py:666` writes `end`
  with no `session` field. On a branch with one pane this is exact, and the alternative
  does not exist. Fine as written.
- The `not-taken` "still here" report depends on `/clear` giving the session a new id.
  Even if it did not, the decision short-circuits on `tokens < limit` before reading any
  events, and a cleared transcript reads low — so a successful clear cannot produce a
  false "did not take" either way. Robust by accident or design.
- Subagent (`isSidechain`) turns do not corrupt the occupancy reading. Sampled 60 real
  transcripts: 0 carry a sidechain record with `message.usage`, and 0 end on one.

**2. Security.** Every subprocess uses the list form, no shell: `workmux list --json`,
`workmux send <handle> <text>`, `git -C <cwd> rev-parse`, and
`sys.executable -m wfctl._restart_send <json>`. The plan crosses the process boundary as
one argv JSON blob and the worker re-derives nothing from it. `handle` comes from
`workmux list --json` and the texts are module constants, so nothing consumer-controlled
reaches a command line. No secrets, no network, no new file writes outside the branch
state dir. The one genuinely privileged act — typing `/clear` into a pane — is gated on
the threshold *and* a recorded handoff, and `find_handle` matches on resolved `path`
rather than directory name, so a send cannot land in a sibling worktree's pane. The
worst case if a matched pane is not running Claude is a shell rejecting `/end-session`.
Nothing to report.

**3. Architecture.** Checked the change against all 11 accepted records.
`session-state-is-re-derived` is honoured explicitly — every state comes back out of
`events.jsonl` on each reply end, and the module docstring says why the personal script's
marker files were rejected. `no-hardcoded-agent`, `install-modes` and `layer-model` are
untouched. `knowledge-placement` is followed: the constraint went to
`docs/architecture/`, the per-file facts to the modules, the worker guidance to the
skill. The four new records are `status: proposed`, consistent with
`a-human-accepts-a-decision` and with the 23 proposed records already held. The
`current-state.md` update places `_restart` in domain and `_restart_send` in surface, and
`tests/test_architecture_view.py` re-derives the bands from the AST, so that claim is

**4. Readability & simplification.** Read every new docstring and comment against the

**5. Performance.** The hook runs on every reply end, so the per-reply cost is
`occupancy()` alone — `_repo_root`, `read_events` and `find_handle` all sit behind the
threshold gate, and `find_handle` behind a send path on top of that. Measured `occupancy`
on a real 12 MB / 6572-line transcript at 135 k tokens: **53 ms**, stable warm. Linear, so
~90 ms at a 20 MB transcript. That is the whole cost and it is not worth a tail-read
optimisation. Branch event logs are ~100 lines (largest on this machine: 99), so
`read_events` is free. The worker's 0.05 s poll is bounded at 10 s and runs detached.
Nothing to report.

**6. Over-engineering.** One finding: the two unused injection points in
`_restart_send.run` (NIT above). Everything else earns its place — `run_hook`'s `spawn`
and `handle_for` *are* overridden by tests; `managed_subcommands` has a real caller;
`prune_unshipped` is what makes a future rename safe and the merge change forces it; every
decision constant is reachable; `Decision.texts` collapses two call sites. The duplicated
`limit == 0 or tokens is None or tokens < limit` between `run_hook` and `decide` is a
`shrink:` candidate I am deliberately not calling, because it is what keeps `decide` a
pure function testable without a transcript. The test suite is 817 new lines for 415 lines
of decision logic, which is the right ratio for a hook that types `/clear` into a pane.

**Tests, read first as the skill asks.** They test behaviour, not implementation: an event
log is a list of dicts and a pane is a callable, so `test_restart_decide.py` covers all
sixteen rows of the rule table with no fixtures. `test_restart_end_session.py` is the
strongest piece here — it pins the two halves of the split (`END_TEXT` vs the skill's
section heading, the step *numbers* the section overrides, `$ARGUMENTS` in the wrapper,
and that `200000` appears exactly once in the package), which is the drift nothing at
runtime could catch. `test_restart_send.py`'s stub-`workmux` ordering assertion and
`test_restart_hook_cli.py`'s out-of-process detach test both prove the thing the worker
exists for. Coverage gap: no test asserts what happens when `spawn` raises — which is the
WARNING above.
