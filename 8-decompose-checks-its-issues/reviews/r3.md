### WARNING `wfctl/_pipeline.py:208` — the lazy-import comment states a constraint that isn't there

```python
from wfctl import _tracker  # lazy: avoids an import cycle at module load
```

There is no cycle. `_tracker`'s module-level wfctl imports are `_io` and
`_manifest` (`_tracker.py:18-19`); neither imports anything from `wfctl`
(`grep -n wfctl wfctl/_io.py wfctl/_manifest.py | grep -i import` → empty), so no
path from `_tracker` reaches `_pipeline`. A top-level `from wfctl import _tracker`
here loads fine.

The comment is copied from `_paths.py:379`, where the cycle *is* real — and where
it is the entire subject of `docs/architecture/tracker-owns-the-issue-key-shape.md`,
which calls `_paths ↔ _tracker` "the only cycle in wfctl" and complains that it is
"survived rather than managed … a reader of `_tracker` has no way to learn that the
import's position inside the function is load-bearing". This change adds a third
function-local `_tracker` import that reads like a fourth sighting of that cycle,
in a module where the position is *not* load-bearing for that reason.

There is a real reason to keep it lazy, and it is a different one: `_tracker`
builds a `rich.Console` at import (`_tracker.py:23`), and `_pipeline` is otherwise
render-free — its own docstring makes a point of `cli` owning the glyphs, and
`current-state.md` already lists `_tracker`'s module-scope Console as one of the
three places the bands do not hold. Say that instead. CLAUDE.md's rule is that
comments explain *why this shape*; a false why is worse than none, because the next
author either preserves a lazy import for an imaginary reason or deletes it and
takes rich into `_pipeline` without noticing.

Same finding, lower weight: the import sits above the `if spec_dir is None:` early
return, so it runs on every `_infer_steps` call including ones that never reach the
decompose arm. `_verification_block` puts its lazy imports at the top of the
narrowest function that needs them; this could sit in the decompose branch.

Band check, for the record: `_pipeline` and `_tracker` are both in the `domain`
band (`current-state.md` `layers` block), so the new edge runs sideways and is
legal. `test_architecture_view.py` passes — no drawing drift.

### WARNING `wfctl/_pipeline.py:314` — a repo that declined a tracker is now stuck at decompose

`load_key_pattern` returns the GitHub-shaped default `\d+` for four different
situations, one of which is *"this repo was asked and said no"*. `cli.py:1955`
records that as `manifest["tracker"] = None` and tells the user, in so many words,
that `wfctl issue` / `wfctl change` will no-op from then on. A non-interactive
first install (`--yes`, CI, the worktree hook) also leaves it unset.

In such a repo nothing creates issues, so an Issue Grouping Map authored with
placeholders never gains keys. `decompose` reads `in_progress` forever;
`_current_step_name` returns the first blocking step, so `next` pins to
`/speckit.decompose` with `auto=False`, and there is no flag, marker or override
that gets past it — the only exit is hand-editing `delivery.md`.

Every other tracker-shaped read in wfctl degrades the other way. `_tracker.dispatch`
returns 0 and prints an informational line, on the stated principle that "a session
must not fail because a tracker step could not run". `_unkeyed_issues` already has
the vocabulary for this — `None` means unjudgeable — and already uses it for a
missing map and an uncompilable pattern. A repo with no tracker is the same kind of
answer.

Fix: return `None` when `load_manifest(repo_root).get("tracker")` is falsy. The
tradeoff to state out loud, because it is not free: that also drops the check for a
GitHub repo that simply never ran the tracker prompt, which is probably the second
most common repo shape after a configured one. If you keep the current behavior,
the annotation is the place to say so — "plan written, 2 issues not created" gives a
trackerless reader nothing to act on.

### WARNING `wfctl/_pipeline.py:133` — the column is positional, the docstring says it is by name

```python
return sum(1 for row in rows if not key.search(row.split("|")[1]))
```

`[1]` is the first cell, unconditionally. The docstring and the module comment both
describe this as "the `Issue` cell", and the block comment at :78 defends *not*
matching header labels — but that argument is about identifying which lines are
rows, not which cell is the Issue column. Two different claims; only the row one is
actually made by the code.

Verified against the shipped shapes (`uv run python -c` against `_unkeyed_issues`):

| input | result |
|---|---|
| `assets/delivery-plan-template.md` as shipped (prose between heading and table) | `3` ✓ |
| same table with `Tasks` first and `Issue` second, all rows `_(TBD)_` | `0` — reads **done** |
| `\| TBD (sub of #490) \| T001 \|` | `0` — reads **done** |
| GFM table with no leading pipes | `None` — reads **done** |

The reordered case is the one that matters: a silent false-`done`, which is the
exact failure this change exists to remove. It is not a regression (every
`delivery.md` read `done` before), but it is an open flank, and `speckit-orchestrate`
already documents that pre-standard delivery files exist in the wild: *"Older
delivery.md files may predate the standardized `{issue-key}`-leads-the-cell format"*.
The header row is sitting on the line directly above the separator and is currently
thrown away; locating `issue` in it and falling back to index 1 is about four lines.
If you'd rather not, change the docstring to say "the first cell" — the cheap fix is
making the code and its description agree.

### NIT `wfctl/_pipeline.py:133` — `.search` where the precedent anchors

`extract_issue_key` (`_paths.py:31`) applies this same `key_pattern` as
`re.match(rf"^({pattern})(?:[-_]|$)", branch)` — anchored. This uses an unanchored
`.search`, which is why `TBD (sub of #490)` above counts as created.

`.search` is almost certainly *correct* here: the table writes GitHub keys as `#251`,
and `\d+` anchored at position 0 would reject the leading `#`. But nothing in the
code or the tests records that, and the divergence from the one existing caller is
the kind of thing a later reader "fixes" — breaking every GitHub repo at once. One
sentence in the docstring, or a test with a `#`-prefixed key asserting `done`, pins it.

### NIT `wfctl/_pipeline.py:125-131` — dead defensive branch

```python
try:
    key = re.compile(key_pattern)
except re.error:
    # `load_key_pattern` degrades an uncompilable pattern to the default, so
    # this is only reachable via a caller passing its own. ...
    return None
```

The comment concedes it is unreachable through the only caller, and the function is
private with exactly one. `re` caches compiled patterns internally, so the whole
block collapses to the expression it guards:

```python
return sum(1 for row in rows if not re.search(key_pattern, row.split("|")[1]))
```

`delete:` — eight lines including the comment, no behavior change for any input the
function can actually receive. (If you want the defense anyway, it is one line as
`re.error` is a subclass of `Exception` — but the honest version is that
`load_key_pattern` is the guarantee.)
