## WARNING — wfctl/_pipeline.py:L133: the match is not anchored to the cell

```python
return sum(1 for row in rows if not key.search(row.split("|")[1]))
```

`re.search` over the whole cell means the default GitHub pattern `\d+` is
satisfied by *any* digit in it, not by a leading key. The delivery-plan template
(`assets/delivery-plan-template.md:26-31`) states the contract the check should
be reading:

> The **Issue** column must lead with the tracker's native key exactly as
> returned — no other format. […] a consistent leading position matters more
> than the label that follows it.

and `speckit-orchestrate/SKILL.md:66` builds its own matcher as `#?{key_pattern}`
for the same reason. The Python check honours neither.

Observed, on a repo whose only difference from the passing fixture is a numbered
parenthetical after the placeholder:

```
| Issue             | Tasks | Title      | Estimate | Closes With |
|-------------------|-------|------------|----------|-------------|
| _(TBD)_ (Issue 1) | T001  | `[490] a`  | 3h       | PR #1       |
| _(TBD)_ (Issue 2) | T002  | `[490] b`  | 3h       | PR #2       |
```
```
analyze      ●
decompose    ●
implement    ▶  0/2 done  ← current
next: /speckit.implement
```

Same table with `_(TBD)_` alone gives the intended `decompose ▶ plan written, 2
issues not created`. `TBD-1`, `TBD #1` and `(group 1)` fail the same way. The
template's own labels are letters (`Issue A/B/C`), which is why the PFMS fixture
does not hit it — the check is correct only for the placeholder shapes that
happen to be digit-free.

Fix (keeps all six new tests green — verified against every fixture cell in the
diff, under both `\d+` and `[A-Z]+-\d+`):

```python
cell = row.split("|")[1].strip()
...
return sum(1 for row in rows if not re.match(rf"#?(?:{key_pattern})", cell))
```

`#?` is what lets `#251` satisfy a bare `\d+`, exactly as `speckit-orchestrate`
already documents; `(?:...)` keeps a pattern with a top-level alternation from
binding wrong. (An anchored `key_pattern` such as `^[A-Z]+-\d+$` breaks under
either form — `_paths.extract_issue_key` has the identical exposure, so the
tracker contract already excludes it. Not this diff's problem.)

## WARNING — wfctl/_pipeline.py:L208: the import comment states a cycle that does not exist

```python
from wfctl import _tracker  # lazy: avoids an import cycle at module load
```

There is no cycle here. `_tracker` imports `_io`, `_manifest` and `rich`, plus
`_paths` lazily; none of them reaches `_pipeline`. Verified by hoisting the
import to module level in a throwaway copy of the package — `import
wfctl._pipeline` succeeds. `docs/architecture/tracker-owns-the-issue-key-shape.md`
says so directly: *"`_paths` and `_tracker` import each other. It is the only
cycle in wfctl."* The comment is a copy of `_paths.py:379`, where it is true.

This matters more than a stray comment normally would: #149 phase 2 is a
scheduled pass over exactly these two lazy imports, and this one now looks like a
third member of the cycle it is not part of. `CLAUDE.md` asks comments to explain
*why this shape*; one that explains it wrongly is worse than none.

Both modules sit in the `domain` band (`docs/architecture/views/current-state.md`
`layers` block), so a module-level `from wfctl import _tracker` is a sideways
edge the view permits and needs no entry in `upward` or `crossings` —
`test_architecture_view.py` stays green either way. Fix: hoist it, or replace the
rationale with the true one (import cost of pulling `rich` into `_pipeline`, or
consistency with the `_verify` import six lines into `_verification_block`).

## NIT — wfctl/_pipeline.py:L107: code fences are not blanked first

`_ISSUE_MAP_SECTION` searches the raw text, so a `delivery.md` that quotes the
map inside a fence (documenting its own format, pasting the template) has those
rows counted as real — confirmed, a fenced placeholder table returns 1. Sixty
lines above, the `spec.md` read does the opposite for exactly this reason
("*so a spec that documents a marker … doesn't read as having one*"). Fix: reuse
that `re.sub(r"```.*?```", "", text, flags=re.DOTALL)` before the section search.
Same shape, lower stakes: a GFM table written without leading pipes finds no
separator, returns `None`, and reads `done` silently — acceptable while the
template is the only writer, worth a line in the docstring saying so.
