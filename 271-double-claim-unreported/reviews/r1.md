**WARNING  wfctl/cli.py:L4170-4171 — `Resolution returns {c.own[0]}.` is false
when the own directory's name is a bare key.**

`claim_conflicts` admits a directory as an own claimant via `extract_issue_key`,
whose regex accepts a key with no slug (`^(pattern)(?:[-_]|$)`). `resolve_spec_dir`
finds an own directory two ways: exact branch-name match, else
`root.glob(f"{key}[-_]*")`, which requires a separator. A directory named bare
`200` is therefore an own claimant that the glob cannot reach. Reproduced:

```
conflicts:            [ClaimConflict(key='200', own=[…/specs/200],
                                     mapped=[…/specs/100-parent])]
resolve('200')        → …/specs/200          # doctor's sentence is true
resolve('200-child')  → …/specs/100-parent   # doctor's sentence is false
```

The directory is reachable: `cli.py:L724` names a new feature dir
`spec_root(repo_root) / branch`, and a branch named `200` passes `pre_create`.
The `elif c.own:` branch already carries the correct, branch-dependent wording;
the bare-key case belongs in it.

Fix → gate the definite sentence on the name `resolve_spec_dir` can actually
reach, e.g. `if len(c.own) == 1 and fnmatch(c.own[0].name, f"{c.key}[-_]*")`,
falling through to "chosen by branch name" otherwise.

## Passes that found nothing, and what was checked

**Security** — clean. The check reads only; no shell, no network, no writes. The
regex comes from `_tracker.load_key_pattern`, which is documented and tested to
return a compilable pattern and degrade to `DEFAULT_KEY_PATTERN` otherwise, so
`re` calls in `extract_issue_key` / `delivery_issue_keys` cannot raise on it. A
`delivery.md` that is unreadable or not UTF-8 is already absorbed by
`delivery_issue_keys`' `except (OSError, ValueError)` → `set()`, whose docstring
names this scan as the reason the catch exists — so one bad file under the spec
root cannot take `doctor` down. `root.is_dir()` guards the absent spec root, and
that is pinned by `test_claim_conflicts_reads_a_missing_spec_root_without_raising`.
No secrets, no untrusted input crossing a boundary. (`iterdir()` on an unreadable
existing root would still raise, but `_check_spec_root_migration:L3946` has the
identical shape — pre-existing, not this diff's.)

**Architecture** — fits. `a-rule-is-expressed-as-a-check` is satisfied on its own
terms: both claims are artifacts the work already produces, so the rule is a
check rather than prose. `claim_conflicts` sits beside `resolve_spec_dir` in
`_paths.py`, reuses `spec_root` / `extract_issue_key` / `delivery_issue_keys`
rather than re-deriving any of them, and repeats the same lazy `_tracker` import
with the same cycle-avoidance comment. `resolve_spec_dir` is untouched —
verified by diff and by the full suite, so `a-branch-is-claimed-not-inherited`
still holds and no new state is introduced. Placement ahead of the manifest gate
matches the block's own comment and `_check_spec_root_migration`'s precedent, and
the check is added inside the `any([...])` list, so it cannot short-circuit a
later check. No new dependency, no cycle.

**Correctness of the scan itself** (as distinct from the report) — the three
shapes I tried to break it on all behave: a feature whose map lists its own key
is one claimant (`claimed != key`), so the ordinary decomposed epic is silent;
duplicate rows in one map collapse because `delivery_issue_keys` returns a set;
a directory whose name parses no key still contributes its map rows, since
`key == "unknown"` never equals a parsed `claimed`. `or ()` handles both `None`
and the empty set identically, which is correct here — `resolve_spec_dir`'s
docstring says no caller separates them yet, and this one does not either.

**Performance** — not a concern. One `iterdir` plus one `read_text` per feature
directory, on a root of ~60 entries here; the reads are already what
`resolve_spec_dir` does on its fallback path. No N+1 across a boundary, no
unbounded growth per run. The cost that does grow is report *length* (four lines
per conflict, twelve today), which is the BLOCKER's territory, not this pass's.

**Readability** — the docstrings carry rationale rather than narration, matching
the file around them; `ClaimConflict`'s two-list docstring earns the shape it
argues for. `c`/`d`/`k` are terse but consistent with `_paths.py`. Comments
explain *why* (the `soft_wrap` note, the `elif` note about the exact-name match
running ahead of the glob) and none of them narrate the diff, per CLAUDE.md.
