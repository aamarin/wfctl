## Findings

**BLOCKER  wfctl/cli.py:L4500** — the check reaches the exit code and fires on
this repo's own spec root, permanently, with nothing anybody will repair. `uv run
wfctl doctor` on `437a29e` in this worktree:

```
✓ wfctl 0.18.0 — latest
⚠ issue 11 is claimed by 2 features:
    …/wfctl-specs/11-agent-artifact-layout — its own directory
    …/wfctl-specs/11-gitignore-glob-dedup — its own directory
  Resolution returns one of the directories above, chosen by branch name.
⚠ issue 17 is claimed by 2 features:
    …/wfctl-specs/17-install-config-substitution — its own directory
    …/wfctl-specs/11-agent-artifact-layout — a row in its Issue Grouping Map
  Resolution returns …/wfctl-specs/17-install-config-substitution.
⚠ issue 24 is claimed by 2 features:
    …/wfctl-specs/24-read-artifacts-from-specs — its own directory
    …/wfctl-specs/11-agent-artifact-layout — a row in its Issue Grouping Map
  Resolution returns …/wfctl-specs/24-read-artifacts-from-specs.
✓ base: skills current (wfctl 0.18.0)
✓ claude: skills current (wfctl 0.18.0)
exit 1
```

Every other line is `✓`; the exit 1 is this check alone. #17 and #24 are
sub-issues of epic #11 that shipped months ago —
`11-agent-artifact-layout/delivery.md`'s Issue Grouping Map names them, and each
grew its own directory. The two repairs available are editing a merged epic's
delivery record to delete rows that state real history, or deleting a completed
feature's spec directory. Neither is a repair; so doctor stays red forever.

Three consequences, each grounded in the repo's own text:

1. `CLAUDE.md` — "Then `uv run wfctl doctor` … Exit 1 means a finding that still
   stands." The change makes its own definition of done unreachable on the repo
   that ships it.
2. `start-session/SKILL.md` L62 — "Then run `wfctl doctor` again and check it is
   green before moving on." Every session start now begins with three
   unactionable findings.
3. `doctor_cmd`'s own docstring — "each arrival costs the exit code some of its
   meaning", and "Uncommitted spec artifacts are the worked example: mid-feature
   they are the normal state, so reporting them here turns the one green signal
   red for a condition that is not wrong." A finished epic beside its finished
   children's directories is the same class.

The commit message anticipates exactly one noise source — "A feature claiming its
own key twice … is one claimant. That is the ordinary decomposed epic, and a check
that fires on it is noise" — and the empirical noise source is the adjacent one:
an epic whose map row names a child that *does* have its own directory. On the
only real spec root available, that shape is 2 of the 3 hits.

→ Fix, cheapest first: print the block but `return False`, so it names the state
without holding the exit code. `doctor_cmd`'s legend already carries the
vocabulary for this — "dim ℹ named, not a finding — it does not reach the exit
code" — and the check's own docstring already concedes the reason ("clearing it
means dropping one of the two claims, which is … not one a check can make"), which
is precisely the case where doctor should not fail. Alternatively, narrow what
fires (e.g. only when the map-row claimant's row names a key whose own directory
carries a `spec.md` newer than the epic's `delivery.md`), but the `ℹ` demotion is
the one that costs no new heuristic. If the finding must stay red, the repo's own
three hits have to be cleared first, and the diff has to say how.

**WARNING  wfctl/cli.py:L4171** — the stated winner restates `resolve_spec_dir`'s
precedence in prose instead of asking it, and the two already disagree. A spec dir
named for a bare key with no slug is claimed by `claim_conflicts` — `extract_issue_key`
accepts `342` standing alone (`_paths.py:L30-L41`) — but `resolve_spec_dir`'s glob
is `f"{key}[-_]*"` (`_paths.py:L466`), which requires a separator. Reproduced:

```
specs/342/                (empty dir)
specs/100-epic/delivery.md  → Issue Grouping Map row "**#342** — the child"

conflicts:            [('342', ['342'], ['100-epic'])]
resolve_spec_dir('342')       -> …/specs/342
resolve_spec_dir('342-child') -> …/specs/100-epic     ← the check says specs/342
```

So the check prints "Resolution returns …/specs/342." for a branch that resolves
to the epic. Narrow — it needs a slugless directory name — but the whole job of
the line is to be the authoritative answer.
→ Name the winner by asking the resolver: `resolve_spec_dir(c.own[0].name,
repo_root)`. It cannot drift from resolution, and it collapses the L4171/L4176
split into one call.

## Passes that found nothing

  filed as a NIT above, output-fidelity rather than security.
- **Performance.** One `iterdir` plus one `delivery.md` read per feature dir, per

  feature count, no nesting, no repeated scan.

  lets `cli.py` name a winner at all, and the docstring argues it. No speculative
