Every other line in that run is `✓`, so the three `⚠` are the only contributors
to the exit code: **`doctor` was 0 on this repo before the commit and is 1 after
it, and stays 1.**

What the three are. `…/11-agent-artifact-layout/delivery.md:37-39` is a real,
correct, *merged* Issue Grouping Map:

```
| #11 (parent epic)  | —                     | … | PR 2 (final) |
| aamarin/wfctl#24   | T001–T013, T028       | … | PR 1         |
| #17                | T014–T027, T030–T031  | … | PR 2         |
```

Both sub-issues were worked on their own branches and so hold their own spec
dirs. Issue 11's second claimant is a second finished feature that also begins
`11-`. All three features shipped. There is no state here that is wrong, and no
repair anybody will perform — renaming an archived spec dir severs it from the
branch it is named for.

Why this is a blocker rather than a taste call, in the project's own words:

- `CLAUDE.md`, *Definition of done*: "Then `uv run wfctl doctor` … Exit 1 means a
  finding that still stands." Every future change on this repo now fails that
  step for a condition unrelated to it, and `/start-session` runs `doctor`
  unattended at the top of every session.
- `cli.py:4452` (`doctor_cmd`'s own admission contract): "What stays out is
  anything whose answer depends on where the user is in their work. This command
  runs unprompted at every session start, which makes it a magnet for anything
  you want noticed, and each arrival costs the exit code some of its meaning …
  reporting them here turns the one green signal red for a condition that is not
  wrong."
- `README.md:339`: "`doctor` doubles as a freshness gate in scripts."

The commit message anticipates one noise source (an epic whose map lists its own
key) and excludes it. It does not anticipate the other, which is history: a
collision has no clearing path, so the first one a spec root ever accumulates
is permanent.

Note the acceptance criteria are still literally met — "a repo with no such
collision reports nothing and its exit code is unchanged" is true. The gap is
that wfctl's own spec root is not such a repo, and neither will be any
long-running project that decomposed an epic before #120.

Fixes, in the order I'd rank them:

1. **Demote to `ℹ`, off the exit code.** `doctor_cmd`'s docstring already ships
   the category for exactly this: "dim `ℹ` named, not a finding — it does not
   reach the exit code." Drop `_check_double_claimed_keys` out of the
   `any([...])` list at `cli.py:4497` and call it beside `_warn_missing_bootstrap`
   at `cli.py:4508`, which is already there for the same reason. The issue's AC
   ("`wfctl doctor` reports a key claimed by more than one feature, naming both
   claimants and which one resolution returns") is satisfied by the report; it
   nowhere requires exit 1.
2. **Narrow the condition to a live collision** — only report when the own-dir
   claimant's pipeline is unfinished. Rejected on the same grounds the author
   would reject it: it needs state or a tracker call, and the issue forbids both.
3. **Keep exit 1 and add the repair** (see WARNING-4), accepting that this repo
   must first be cleaned by hand. That is a decision about the maintainer's own
   spec root and has to be made before merge, not after.

### WARNING  cli.py:4167, 4169, 4171 — paths printed into rich without `escape()`; a bracketed directory anywhere in the spec root prints a path that does not exist

`doctor_cmd` carries the comment for this defect, 400 lines below the new check,
at `cli.py:4573`:

> A recorded source is a path off this repo's disk, and every line below prints
> it. Bracketed directory names are legal and parse as rich style tags, so an
> unescaped `/x/[old]/wfctl` prints as `/x//wfctl` — a different path, with
> nothing said about it.

The three new lines print paths off the same disk and do not escape them.
Reproduced with `WFCTL_SPEC_DIR=<tmp>/[archive]/specs`:

```
⚠ issue 200 is claimed by 2 features:
    /var/folders/…/tmpm49ink4i//specs/200-child — its own directory
    /var/folders/…/tmpm49ink4i//specs/100-parent — a row in its Issue Grouping Map
  Resolution returns /var/folders/…/tmpm49ink4i//specs/200-child.
```

`[archive]` is gone. A directory named `200-[x]y` prints as `200-y`, and a name
containing `[/…]` raises `rich.errors.MarkupError` outright (confirmed directly
against `Console.print`) — a traceback out of the command `/start-session` runs
first.

This is precisely the failure the author added `soft_wrap` for at `cli.py:4165`
("a path rich folded at the terminal width reads as two paths and pastes
broken"): the reasoning covered wrapping and missed markup. `spec_root_cmd`
(`cli.py:951-954`), `_check_arch_records` (`cli.py:814-834`) and the
recorded-source branch all escape; only `_check_spec_root_migration` does not,
and it prints roots rather than the per-feature names a user chose.

→ `from rich.markup import escape` (function-local, as everywhere else in this
file) and print `escape(str(d))` / `escape(str(c.own[0]))`.

### WARNING  cli.py:4171 — "Resolution returns {own[0]}" names the wrong directory when the own dir's name is the bare issue key

`claim_conflicts` decides own-directory membership with `extract_issue_key`,
which accepts a key with **no slug** (`_paths.py:31-41`: "it may stand alone
(`342`)"). `resolve_spec_dir`'s glob does not — it is `root.glob(f"{key}[-_]*")`
(`_paths.py:466`), which requires a separator. The two disagree on exactly one
shape, a spec dir named the bare key, and the CLI then states the loser as the
winner. Reproduced:

```
specs/200               (no delivery.md)
specs/100-parent        map row: **#200**

claim_conflicts   → own=[specs/200], mapped=[specs/100-parent]
doctor prints     → "Resolution returns …/specs/200."
resolve_spec_dir("200-child")  → …/specs/100-parent      ← the printed answer is wrong
resolve_spec_dir("200")        → …/specs/200             ← right only for this one branch
```

A bare-key spec dir is reachable: `feature_paths_cmd` names the dir after the
branch (`cli.py:724`), `workmux`'s `pre_create` only requires the handle to
*start* with the key, and a tracker with `PROJ-123`-shaped keys makes a branch
named exactly the key ordinary. The whole value of this check is naming which
claimant wins; a confidently wrong answer there is worse than the silence the
issue was filed about.

→ Only assert a named winner when the directory would satisfy resolution's own
glob, e.g. gate the `len(c.own) == 1` branch on `c.own[0].name != c.key` and let
the bare-key case fall through to the branch-dependent wording already written
at `cli.py:4176`.

## Passes that produced nothing

**Security.** No new input reaches a shell, a subprocess, a query or a filesystem
write. `claim_conflicts` reads only, matching the AC. The one input-shaped risk —
a repo-supplied `key_pattern` regex driving `delivery_issue_keys` across more
files than before — is a pre-existing ReDoS surface from `_tracker`-owned config,
not widened in kind. The markup issue above is output integrity, filed as a
WARNING there rather than here.

**Architecture.** Placement is right and the reasoning holds under checking: the
resolver is asked about one branch and cannot see claims that do not bear on it,
so it genuinely cannot be the thing that notices, and `a-rule-is-expressed-as-a-check`
(accepted) says a violation visible in an artifact the work already produces is a
check. `claim_conflicts` is a public name in `_paths` imported by `cli`, so it
adds no private-member crossing under `the-underscore-is-the-module-contract`
(proposed) and does not move `tests/test_architecture_view.py`'s count of four.
It does add a third function-local `_paths → _tracker` import, with the same
"lazy: avoids import cycle at module load" comment the record
`tracker-owns-the-issue-key-shape` (proposed) asked for — one more call site for
phase 2 to move, and correctly annotated. `resolve_spec_dir` is untouched, so the
"no change to what the resolver answers" AC holds by construction.

**Correctness, beyond the findings above.** I ran the scan against five
constructed shapes and the repo's real 65-feature spec root:

|---|---|

**Performance.** One `iterdir` plus up to one `delivery.md` read per feature, per

**Over-engineering.** The diff is lean. `ClaimConflict`'s two lists are not

**Verdict: Request changes** (1 blocker, 5 warnings)

The blocker is not a defect in the code as written — the check does what the
issue asked, and the reasoning behind every design choice in it survives
