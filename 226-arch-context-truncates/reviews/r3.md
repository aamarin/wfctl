## Findings

### WARNING `wfctl/cli.py:L807` — the block is printed through `console.print`, so rich re-wraps it and drops the indent; the alignment the fix exists to preserve is destroyed below ~78 columns

The comment two lines up says *"filling it would reflow the alignment that is its
content"* — and then hands the block to `console.print`, which reflows it anyway.
This is the same failure the comment at `L794` says `textwrap.fill` exists to
prevent for the paragraph; the block path has no equivalent guard.

Reproduced against the real record, not a synthetic one:

```
$ COLUMNS=50 uv run wfctl arch context
knowledge-placement
  Placement is decided by scope first, then by
what is constrained:

  ```
  a fact about one file            → that file
  a constraint on the system       →
docs/architecture/
  guidance for the worker          → AGENTS.md
  ```
```

The `→ docs/architecture/` mapping — the exact thing #226 exists to stop losing —
is broken across a line at column 0. It survives today only because the piped
default is 80 columns and the widest block line happens to be 50; a tmux split
pane (which is how this project is worked) is routinely narrower, and the
paragraph is already filled at 74, so anyone under ~78 columns is in range.

Fix (verified in a scratchpad — `no_wrap=True, crop=False` does **not** work, rich
still crops at the width):

```python
console.print(escape(textwrap.indent(block, "  ")), soft_wrap=True)
```

### WARNING `wfctl/_arch.py:L302` — an unclosed fence projects the whole rest of the record, defeating `decision_text`'s own "not the whole section" rationale

`body = takewhile(lambda ln: not ln.strip().startswith(fence), rest[1:])` has no
section bound. A record whose Decision fence is never closed projects
`## Considered`, `## Log` and everything else into the contract:

```
'Like so:\n\n```\na -> b\n\n## Considered\n\n- lots of text\n\n## Log\n\n- 2026 accepted - why\n```'
```

The inline comment at `L303` shows the runaway fence was thought about, but only
its cosmetic half (an unbalanced delimiter) was handled — the substantive half is
that the docstring's stated reason for not projecting whole sections *("takes
`arch context` from 52 lines to 245 and buries the records around each one")* is
undone by one missing backtick. Nothing in the corpus check catches it: the
projected text ends in a fence, not a colon.

Fix — stop the body at a heading as well:

```python
body = takewhile(
    lambda ln: not ln.strip().startswith(fence) and not ln.startswith("#"),
    rest[1:],
)
```

### WARNING `wfctl/cli.py:L793,L802-807` — the rendering half of the fix has no test

All five new tests target `_arch.decision_text`. Nothing asserts that `wfctl arch
context` prints the block, prints it un-reflowed, or indents it — and the CLI is
where the change's entire user-visible value lives. `tests/test_remaining_commands.py`
already has `_record(root, slug, status, decision=...)`, so this is one test:
write an accepted record whose decision is `"Decided by this:\n\n```\na  → b\n```"`,
invoke `["arch", "context"]`, and assert the fence line and the aligned `a  → b`
appear verbatim. That test is also what would have caught the WARNING above.

The skill's own red-flag list names "a bug-fix diff with no regression test";
here it is half a diff with no regression test.

### WARNING — issue AC #3 is unmet and the deferral has no ticket; the issue's stated Verification command does not return what it claims

Two separate reporting problems that will bite whoever closes #226:

1. **`the-underscore-is-the-module-contract` still truncates.** Flipping it to
   accepted locally projects
   `'The underscore is the contract, and it governs **members, not modules**.'` —
   the executable-check sentence is still lost, so AC #3 ("projects its
   executable-check sentence if accepted") is not met. `_arch.py`'s docstring
   defers it as *"a record to edit while it is still `proposed`, not a case for
   here"*, which is a defensible call — but `gh issue list` shows **no follow-up
   issue exists**, and the code-review skill is explicit that a deferred WARNING
   needs a filed ticket, not a paragraph. The record is `proposed` and therefore
   editable under the immutability rule, so the cheap option (fold the sentence
   into its lead paragraph, or end that paragraph in a colon) is still open in
   this change.

2. **`uv run wfctl arch context | grep -c ':$'` returns 2, not 0.** The issue's
   Verification block asserts 0. Under option (a) it will always be 2 — the
   dangling colon line is *retained* and the block printed below it. Not a code
   defect; the meaningful check is the projected decision's tail, which is what
   the new test encodes. But the issue text needs correcting so nobody claims
   done against a command that reports a failure.

### NIT `wfctl/_arch.py:L300` — a fourth hand-rolled copy of "what a fence opener looks like"

`_unfenced`'s docstring says it is *"shared by the two heading scans so they
cannot disagree about what a fence is"*. `decision_text`'s `takewhile` (`L258`)
and `_pointed_at` (`L300`, `L302`) now hold two more copies of that predicate, so
there are four and the invariant that docstring asserts no longer holds. Extract
`_fence_of(line) -> str` (returns the delimiter or `""`) and call it from all
three sites — a net line reduction, and it closes the next nit as a side effect.

### NIT `wfctl/_arch.py:L300` — `[:3]` truncation breaks a 4-backtick fence

````
'Like so:\n\n````\n```'
````

A ` ```` ` opener is read as ` ``` `, so the first *nested* ` ``` ` closes it: the
content is dropped and an unbalanced delimiter pair is projected into the
contract. Consistent with `_unfenced`'s existing `[:3]`, so this is not a
regression, and no record uses a 4-backtick fence today — but `_pointed_at` is
the first place the truncated delimiter becomes *output* rather than scanner
state, since `L305` re-emits `fence` as the closer. `_fence_of` taking the full
run of fence characters fixes both sites at once.

### NIT `tests/test_arch_records.py:L594` — the corpus test passes vacuously if the arch directory moves

`_arch.load_records(Path("/nonexistent"))` returns `[]` (verified), so
`dangling == []` holds trivially. The issue itself makes the argument: *"a check
that has never been seen failing is a check nobody has reason to believe."* Add
`assert records, "no records loaded — the corpus path is wrong"` (or a floor on
the count) before the assertion.

### NIT `tests/test_arch_records.py:L601` — the assertion gives no remedy, and lists are an unargued gap

`assert dangling == []` reports `assert ['some-slug'] == []` and nothing else. The
author who trips it is writing a *record*, not reading `_arch.py`, so the pointer
to `_pointed_at` has to be in the failure message.

It will trip on a shape that is not obviously wrong: a colon pointing at a bullet
list, an indented code block, or a blockquote all carry nothing (verified — all
three return the bare colon). `_pointed_at`'s docstring argues carefully why
*prose* is excluded ("one sentence continued") but never why a list is, and
"decided by these:" + bullets is the most common markdown shape after a colon.
Either say why a list is not "content a sentence cannot hold", or carry it.

### NIT `wfctl/_arch.py:L241-246` — the `the-underscore-is-the-module-contract` paragraph is a fact about another file, parked in this one

Four lines of `decision_text`'s docstring describe a *different* record's current
`status: proposed`, what it will project when accepted, and what edit someone
should make to it. That goes stale the day the record is accepted or edited, and
by this repo's own `knowledge-placement` record ("a fact about one file → that
file") its home is the record or the tracker, not `_arch.py`. Fold it into the
follow-up issue from WARNING 4 and delete it here. The `install-modes` /
`vendor-upstream-skills` paragraph above it should stay — that one explains why
*this function* stops where it does, which is exactly the rationale the file
should carry.

## Passes run, and what was checked in each

**1. Correctness (adversarial).** Traced `decision_text` → `_pointed_at` →
`_unfenced` and the CLI printer. Hand-exercised eight shapes against the real
parser: fence with and without a preceding blank line, fence with an info string,
4-backtick fence, unclosed fence, table followed by prose, bullet list, indented
code block, blockquote, colon followed by a heading, and a Decision with no
following block. Confirmed `after[len(para):]` is a correct remainder slice (`para`
is always a prefix of `after`); confirmed `_pointed_at` cannot cross a section
boundary in a well-formed record because the next non-blank line is always the
heading; confirmed `partition("\n\n")` in the CLI is safe because `text` is a
`" ".join` and cannot contain a blank line, and because `partition` splits only at
the first occurrence so a fence with an interior blank line survives intact.
Verified the projection against all three named records and the latent one.
Two defects found (WARNING 2, NIT 2), plus the rendering defect under 1.

**2. Security.** Nothing reachable. Input is repo-local markdown; the only sink is
`console.print`, and `escape()` is applied to both the paragraph and the block
consistently with the surrounding code. No secrets, no subprocess, no path
construction from record content. Clean.

**3. Architecture.** `_pointed_at` is placed with the other private helpers below
the public surface, matching the module's existing layout, and `decision_text`
keeps its single-return-per-branch shape. One finding: the fence predicate is now
duplicated four ways against a docstring that claims it is shared (NIT 1). The
model/render split is respected — `_arch` returns `"paragraph\n\nblock"` and `cli`
decides how to lay it out — though that contract is implicit in a `"\n\n"`
separator and is what makes the untested CLI half (WARNING 3) a real risk.

**4. Readability & simplification.** Code is lean and reads well; the docstrings
are long but that is the house style `CLAUDE.md` asks for, and they explain *why
this shape* rather than narrating the change — with the one exception in NIT 5.
No nesting, no clever tricks, names are accurate (`_pointed_at` is a good name).
Applied Chesterton's Fence to the deleted inline fence-stop comment: it was moved
into the docstring and *sharpened* (it now says the stop reads the raw line and
does not go through `_unfenced`, which the old comment got wrong) — that is the
issue's AC #5 met properly.

**5. Performance.** Irrelevant at this scale: one extra pass over a record's
Decision section, 15 records, and `after` is now materialized as a list (a few
dozen strings). No loops over the corpus, no I/O added — `decision_text` still
reads `record.body` rather than re-reading the file.

**6. Over-engineering.** Nothing speculative: `_pointed_at` has one caller and one
job, no flags, no config. The fence-vs-table split is two branches for two shapes
that both exist in the corpus, not dead flexibility. Removals available are NIT 1
(extract `_fence_of`, ~6 lines) and NIT 5 (~4 docstring lines).
