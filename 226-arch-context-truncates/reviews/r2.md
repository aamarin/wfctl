**WARNING  wfctl/_arch.py:L305–307 — `_pointed_at` excludes lists, and the
failure mode is a red suite on a well-formed record.**
The docstring's stated principle is "what the colon cannot say in a sentence is a
drawing or a table". A bullet or numbered list is the third shape a colon
conventionally points at, and these records use lists heavily (every `Considered`
section is one). Verified: a record with `## Decision` / `The rule has three
parts:` / blank / `1. a` projects `'The rule has three parts:'` and lands in
`dangling`, so `test_no_in_force_record_projects_a_decision_ending_in_a_colon`
fails. The author's only remedies are to reword the record or to extend
`_pointed_at` — i.e. the tool dictating the record's prose style, which is the
exact objection the issue raised against option (d) ("which is the code choosing
the records' prose style"). Nothing in either docstring mentions lists, so the
next author meets this as a surprise, not as a decision.
→ Fix: either add the branch (`if rest[0].lstrip()[:2] in ("- ", "* ") or
re.match(r"\d+[.)] ", rest[0].lstrip())` → `takewhile` to the next blank), or name
lists in `_pointed_at`'s docstring as deliberately excluded, with the reason.
Two lines either way; the silence is the part that costs.

**NIT  wfctl/_arch.py:L297–304 — three fence edge cases in `_pointed_at`, all
verified by probe.**
- A four-backtick fence (the idiom for wrapping a block that itself contains
  ```` ``` ````) truncates at the inner fence and emits an unbalanced pair:
  `'see:\n\n````\n```'` — the content is dropped *and* the projection is malformed.
  `fence = rest[0].strip()[:3]` is the same `[:3]` limitation `_unfenced` carries,
  so it is consistent with the file, but `_unfenced` never *emits* a mismatched
  closer.
- An indented fence loses the indent on the re-emitted closer:
  `'see:\n\n  ```\n  x\n```'`. The comment explains why the closer is re-emitted
  but not that the indent is dropped.
- An unclosed fence swallows the rest of the file, `## Log` included, into the
  projected block. Mitigating: such a record is already broken louder — `_unfenced`
  stops yielding after the opener, so its `## Log` is unfindable and a transition
  append fails.
→ Fix: bound `body` at an unfenced `#` heading, and take the closer's indent from
`rest[0]`. Or leave all three and say in the docstring that `_pointed_at` inherits
`_unfenced`'s three-character fence assumption.

**NIT  wfctl/_arch.py:L215 / wfctl/cli.py:L793 — the two-part return string is an
undocumented cross-module contract.**
`decision_text` now returns `paragraph + "\n\n" + block` and `cli` recovers the
halves with `.partition("\n\n")`. It is safe today only because `paragraph` is
`" ".join(...)` and can never contain a blank line — a fact stated nowhere. The
docstring says "as the projection prints it", which does not tell the caller there
is a separator to split on.
→ Fix: one sentence in the docstring naming the blank line as the separator, or
return `tuple[str, str]` and drop the `partition`. Not shorter, but the contract
stops being implicit.

**NIT  wfctl/_arch.py:L306–307 — the table branch has zero instances in the
corpus.** Removing it changes nothing about what ships: I stubbed a fence-only
`_pointed_at` and the corpus check still returned `[]`. `no-hardcoded-agent` does
have a table, but under its *second* paragraph, so the branch is reached only by
the synthetic test. The test docstring argues for it (a future record's table would
otherwise be reported as a defect in the record), it costs two lines, and
`layer-model`/`install-modes` show tables are a live shape here — so this is
`yagni:` in form only. Author's call; recorded so the panel does not mistake the
synthetic coverage for corpus coverage.

**NIT  tests/test_arch_records.py:L594 — inlines

## What I checked and found clean

- **Correctness of the projection.** Probed 8 shapes: colon + fence, colon + table,
  colon + prose, colon + heading immediately after, colon at EOF, no-colon + fence
  (`a-rule-is-expressed-as-a-check`, `layer-model` — both correctly leave the block),
  empty Decision, and a Decision opening on a fence. All behave as the docstring
  claims. `after[len(para):]` correctly re-includes the line `takewhile` rejected;
  the `list()` calls are what make that index valid, and the change makes them.
- **The corpus check is live, not decorative** — the issue asked specifically for the
  negative case. Verified three mutations against the real `docs/architecture/`:
  stubbing `_pointed_at` to `[]` (pre-#226 behaviour) →
  `['knowledge-placement', 'no-hardcoded-agent']`; stripping
  `knowledge-placement`'s fenced mapping from a scratch copy of the corpus →
  `['knowledge-placement']`. Both would fail the assertion. Baseline → `[]`.
- **AC 2 met.** `wfctl arch context` now prints both the scope→destination mapping
  and the `${WFCTL_AGENT:+…}` expansion, alignment intact, at 62 lines — matching the
  issue's measured +19%.
- **AC 5 met.** The docstring now describes the code: the raw-string fence stop, and
  why it does not go through `_unfenced`. That was the issue's specific complaint.
- **AC 4 met.** `install-modes` and `vendor-upstream-skills` are named as deliberately
  unchecked, with `a-rule-is-expressed-as-a-check` cited as the deciding record — in
  both the docstring and the corpus test. Confirmed against both records' actual text.
- **Security.** Input is repo-local markdown; both new print paths go through
  `rich.markup.escape` after `textwrap.indent`, so bracket markup in a record cannot
  inject styling. No new file reads — `decision_text` still works off `record.body`.
- **Performance.** Two `list()` materialisations of a Decision section, plus one
  linear scan of the lines below it. Bounded by record length; `arch context` is 15
  files.
- **Blast radius.** `decision_text` has exactly one production caller
  (`cli.py:791`). No skill or script parses `arch context` output — the three
  references in `wfctl/agents/` are prose telling a session to read it — so the extra
  blank line inside a record's stanza breaks no consumer.
- **Test quality.** Names are sentences; docstrings say why the test exists and name
  the failure (`test_a_decision_that_stands_on_its_own…` names `layer-model` as the
  false positive that rules out the "paragraph followed by a block" heuristic —
  that is the load-bearing one). Matches the convention in `CLAUDE.md`.
- **Project rules.** ruff's narrow rule set unchanged; no new imports; both new
  functions annotated (`mypy` clean under `disallow_untyped_defs`); no `version`
  bump in `pyproject.toml`.

net: −7 lines possible (−5 docstring paragraph that belongs in the commit body,
−2 optional table branch), against +8 recommended for the missing CLI test.
Essentially lean already.

**Verdict: Request changes** — 0 blockers, 3 warnings. What unblocks it: the CLI
rendering test (WARNING 1) and an explicit disposition on AC 3 (WARNING 2, edit
the proposed record or amend the issue). WARNING 3 is satisfied by two lines of
docstring if the list branch is not wanted. The change is a real improvement and
the corpus check is the right shape — I am withholding only because the half of
the fix a user sees is the half nothing tests.
