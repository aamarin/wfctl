## Finding

WARNING `.github/pull_request_template.md:140` and
`wfctl/agents/configs/github/.github/pull_request_template.md:140` (mirrored) —
the new checklist line and the new comment-block prompt disagree on what
satisfies the requirement.

Checklist (line 150):
> `- [ ] Anything this change turned up in passing is filed as its own issue, or
> named under Additional Context`

This reads as either/or — filed **or** named, either one is enough to check the
box.

Comment block (lines 170-171):
> "Name each one and say whether it was filed."

This reads as both — every finding gets named in `Additional Context`
regardless of whether it was also filed as an issue.

Failure this reproduces: an author who finds something, files it as its own
issue, and follows only the checklist wording will check the box and write
nothing under `Additional Context` — because the checklist's "or" tells them
naming and filing are alternatives. A reviewer scanning the PR body for what was
found (the exact behavior issue #219 is trying to create — see #214's fourth
row, "nothing prompted it, it evaporated") sees no trace of the finding at all,
even though it was in fact filed. The reviewer would have to already know to go
check `Related`/linked issues to discover it, which is the same "reviewer has to
happen to ask" failure mode this issue exists to close, just moved one level
down (from "was it written down" to "is what's written down complete").

Fix: make the two agree. Either the checklist should also require naming
regardless of filing status (drop the "or"), or the comment block should say a
filed finding can be referenced rather than fully restated (e.g. "name it —
either describe it here, or link the issue it was filed as"). The issue's own
proposed checklist text (`"Named it and say whether it was filed"`) matches the
comment block; the merged wording in the diff is the version that introduced the
"or".

Not a blocker on its own (both templates are correct prose in isolation, and the
underlying prompt does get an author to *notice* the requirement) — but it
undercuts the one property #219 is written to guarantee, so I'd want it fixed
before merge rather than left for a later PR to notice.
