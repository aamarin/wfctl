## Findings

**WARNING** `speckit.analyze.md:L129-135` — the safety argument for not gating on
`auto_approve` rests on a false premise. It says an in-scope fix "stays inside
three artifacts the pipeline regenerates and **lands in the branch diff the
reviewer reads**". It does not. `wfctl feature-paths` on this very branch resolves
`FEATURE_DIR` to `/Users/andremarin/Development/wfctl-specs/331-…`, outside the
working tree, and `.gitignore` carries `specs/` for the in-tree default. The
bundle says so in the same breath: `writing-a-scan-file/SKILL.md` opens with
"both write everything they find into `FEATURE_DIR` — which resolves outside the
working tree in most repos and is gitignored in the rest. A reviewer opening the
change sees none of it (#307)." So this change authorises an unattended agent to
edit `spec.md`/`plan.md`/`tasks.md` on the grounds that a reviewer will see the
edit, in a repo where the reviewer sees none of it.
→ The reviewable artifact is the scan file's `→ Fixed: <what changed>` line,
which *is* committed to the branch — the same argument the `Not filed:` line
makes three paragraphs down. Say that, and drop the branch-diff claim.

**WARNING** `speckit.analyze.md:L214-218`, `speckit.clarify.md:L90-94` — both
`a-rule-is-expressed-as-a-check` deferrals point at an issue that, as scoped,
will not check these rules. #335's body scopes itself to two *other* rules ("no
marker survives the scan", "the step is never left without its scan file") and
proposes exactly two blocks: `clarify_block` (markers standing *and* a
`## Clarifications` section present) and `analyze_block` (the scan file is
absent). Neither reads a `Basis:` line, neither counts `Acted on + Accepted ==
Findings`, neither checks a reason on an `Accepted` row. The paragraphs say "#335
is the mechanism that would observe it" — it is not, and nothing tracks the two
rules this change ships as prose. This is the same prose-vs-check gap the review
bot raised as P1 on #334, arriving through the remedy instead of the rule.
→ Either extend #335 out loud to cover the basis field and the count arithmetic
(a comment on it, and the wrapper citing that), or file the follow-up and cite
it. As written, the deferral is a pointer to nowhere.

**WARNING** `speckit.clarify.md:L52-53` — the derivability test describes the
wrapped skill inaccurately, and the inaccuracy is load-bearing. "Step 4's
recommendation is grounded in the spec, the plan, the tracker and this feature's
design records." Step 4 (`speckit-clarify/SKILL.md:L142-146`) grounds it in *best
practices for the project type, common patterns in similar implementations, risk
reduction, and alignment with explicit project goals or constraints visible in
the spec*. The tracker and the design records appear nowhere in it; `plan.md`
does not exist yet at all, since the skill's own Outline says clarification "is
expected to run (and be completed) BEFORE invoking `/speckit.plan`". The
consequence is behavioural, not cosmetic: the skill's primary ground —
best practice — is reachable from none of the four sources listed, so for the
commonest recommendation the table's row 1 says *take the answer step 4 already
computed* and `### A question the repository cannot settle` says *such a question
is not asked*. Two agents split on that, which is precisely the failure #331
exists to close.
→ Write the grounds as an imperative rather than as a description of step 4, drop
`the plan` (or qualify it as present only on a post-plan re-run), and say
explicitly whether a recommendation resting on best practice alone counts as
derivable. My read is that it must — otherwise the rule withdraws most of the
queue — but the file has to say it.

**WARNING** `speckit.clarify.md:L58-61` — "the next candidate step 3 ranked takes
its slot" has no referent, so the protection the paragraph claims does not exist.
Step 3 generates "a prioritized queue of candidate clarification questions
(**maximum 5**)" and, where more categories remain, "select the top 5". The queue
*is* the cap. There is no sixth ranked candidate to promote, so a withdrawn
question leaves four asked and the coverage narrows by exactly the amount the
sentence says it must not — while the reasoning given ("the cap is on questions
asked") contradicts a skill in which the cap is on the queue too.
→ Either instruct step 3 to rank a replacement candidate when a question is
withdrawn (the only way to keep five), or delete the claim and state plainly that
a withdrawal costs the pass one question.

**WARNING** `speckit.clarify.md:L58-66` — the withdrawal rule writes the scan-file
side and leaves `spec.md` saying the opposite. A run whose candidates are all
withdrawn asks nothing; the skill's only bullet for that state is `- No critical
ambiguities detected.` (behaviour rule L213, and step 6's validation licenses no
other), which `_predicates.clarify` reads as `done`. The spec then records that
no critical ambiguity was found, while the scan file records `### Outstanding`
and `Verdict: unsatisfied` about the same scan. Issue #331's definition of done
asks for a terminal state, and this reaches one by writing a false artifact. The
marker rule above has the same shape, but this change is what makes the
all-withdrawn case reachable.
→ Require the withdrawn question to leave a `- Q: <question> → A: Outstanding —
<why underivable>` bullet in `## Clarifications`, and say the empty-scan bullet
is not written when anything is Outstanding.
