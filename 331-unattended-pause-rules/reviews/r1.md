WARNING  speckit.analyze.md:L125 + L207 — *"the counts in the scan file say which each
one was"* is not something the counts can say. The fields are
`Findings · Critical · Acted on · Accepted`. Applied → `Acted on`; **filed → `Accepted`**;
refused-and-not-filed → also `Accepted` (L178: *"Where filing is refused the finding is
still `Accepted`"*). The arithmetic `Acted on + Accepted == Findings` holds, but the
counts distinguish applied from everything-else, never filed from not-filed — which is
the one distinction L188-189 says the policy exists to preserve. Two related gaps:
(a) the mapping "a filed finding counts as `Accepted`" is stated only by implication in
the word "still", so one agent will count a successful filing as `Acted on` (an action
was taken) and another as `Accepted`; (b) the section shape has `Not filed: <why nobody
was told>` but **no counterpart for a filing that succeeded** — nothing records the issue
key, so `### Filing` (scoped by L198 to *refused* filings) leaves a granted run's output
unrecorded.
→ State the mapping in one sentence, and give the Findings template a `Filed: #<n>` line
beside `Not filed:`.

WARNING  speckit.analyze.md:L339-344 — the illustration contradicts the rule it sits

WARNING  speckit.clarify.md:L58-61 — an instruction the wrapped skill cannot satisfy.
*"It leaves the queue without being put — so it never counts against the five, and the
next candidate step 3 ranked takes its slot."* Step 3 of `speckit-clarify/SKILL.md`
is *"Generate (internally) a prioritized queue of candidate clarification questions
(maximum 5)"* and *"If more than 5 categories remain unresolved, select the top 5 by
(Impact \* Uncertainty) heuristic."* Step 3 ranks exactly the five it keeps; there is no
retained sixth candidate to promote. The next candidate is one **step 2** produced as a
"candidate question opportunity" and step 3 discarded. As written, one agent re-ranks
from step 2's coverage map and another concludes the queue is simply short — and the
second outcome narrows coverage by exactly the amount this rule was written to protect.
→ *"…and the next opportunity step 2 recorded, re-ranked by step 3's heuristic, takes
its slot."*

WARNING  speckit.clarify.md:L52-53 — the rule misdescribes the skill it layers over.
*"Step 4's recommendation is grounded in the spec, the plan, the tracker and this
feature's design records."* Step 4 actually lists *best practices for the project type,
common patterns in similar implementations, risk reduction, and alignment with any
explicit project goals or constraints visible in the spec* — the spec and general
practice, not the plan, the tracker or design records. Two consequences:
(a) `plan.md` does not exist at this step at all — clarify runs before plan
(`speckit-clarify/SKILL.md` L60: *"expected to run … BEFORE invoking `/speckit.plan`"*;
step 1 captures `IMPL_PLAN` only *"for future chained flows"*), so on a first pass the
agent is sent to a file that isn't there; (b) the sentence is phrased as a *description*
of existing behaviour, so an agent may never go read the tracker or the records — yet the
diff adds `Bash(wfctl issue view*)` to `allowed-tools`, which only makes sense if it is
meant as an *instruction*. It is also the sentence that decides whether a question is
"underivable", and therefore whether the verdict becomes permanently `unsatisfied`.
→ Make it imperative and drop `plan.md` (or qualify it "the plan, on a post-plan re-run"):
*"Ground the recommendation in `spec.md`, the branch's issue (`wfctl issue view`), and
this feature's design records, as well as the sources step 4 already names."*

WARNING  speckit.clarify.md:L58 vs L36-38 — two rules in the same section contradict each
other, and the override is undeclared. L36-38: *"The trigger is a pause reached with no
answer, not a mode read. Ask each question as step 4 renders it, recommendation and all.
Where an answer comes back, it is the answer and this section changed nothing about the
run."* L58: *"Such a question is not asked."* A question the repository cannot settle is
the one a person sitting there is best placed to answer — withdrawing it unconditionally
*does* change an attended run, which L38 says this section never does. It also overrides
step 4, which mandates rendering `**Recommended:** Option [X]` for every multiple-choice

it points at teaches the reader to discount both"); the clarify half does the same thing
and declares nothing.
→ Either scope the withdrawal to the unattended case ("where no answer will arrive…"), or
keep it unconditional and declare it as an override of step 4 with the same sentence
`speckit.analyze.md` uses.
