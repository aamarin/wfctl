## BLOCKER  speckit.clarify.md:L67-72 — a withdrawn question is now an *asked* question, and the wrapper still says it does not count against the five

The skill's cap is on asked questions, stated twice and absolutely:

- `speckit-clarify/SKILL.md:171` — *"You reach 5 asked questions."*
- `speckit-clarify/SKILL.md:215` — *"Never exceed 5 total asked questions (clarification retries for a single question do not count as new questions)."*

Before this commit the wrapper was consistent with that: *"Such a question is not asked.
It leaves the queue without being put — so it never counts against the five."* Not put,
not asked, slot not spent, total asked ≤ 5.

The commit changed the antecedent to *"put like any other and withdrawn only when no
answer arrives"* — and kept the consequent and its justification verbatim:

> Withdrawn, it never counts against the five, and its slot is refilled by re-running
> step 3's ranking … the cap is on questions asked, and a withdrawal that spent one would
> narrow coverage by exactly the amount this rule was supposed to protect.

The question is now asked. "The cap is on questions asked" is the sentence that used to
prove the slot was unspent; under the new antecedent that same sentence proves the
opposite — the slot *was* spent. A load-bearing justification survived the edit that
inverted it.

Trace it: unattended run, three of five candidates are underivable. Each is put, none
answered, each withdrawn, each slot refilled from step 3's re-ranked map, each refill
asked. Total asked: 8. The skill says never exceed 5. The wrapper is now an unstated
override of an upstream hard rule — and this file's sibling states its overrides out loud
for exactly this reason (`speckit.analyze.md:126`, `L286-299`: *"a wrapper that silently
contradicts the skill it points at teaches the reader to discount both"*).

→ Fix: pick one and say it. Either (a) a withdrawn question spends its slot — delete
"it never counts against the five" and the refill, and accept the coverage narrowing the
old paragraph was protecting against; or (b) keep the refill and state it as an override:
*"This overrides the skill's 'never exceed 5 total asked questions' — a question put and
not answered bought no coverage, and the cap exists to bound what a person is asked to
answer, not what was rendered at them."* Silence is the one answer that cannot stand,
because the sentence still in the file argues against the rule it is attached to.

## BLOCKER  speckit.clarify.md:L36-40 vs L32 — two rules now fire on the identical trigger with opposite outcomes, and the tie-breaker was deleted

The commit removed the sentence that resolved the collision:

> ~~The withdrawal rule below is the exception and is unconditional: a question the
> repository cannot settle is not put to anyone, attended or not.~~

and replaced it with one that *creates* the collision:

> Ask each question as step 4 renders it, recommendation and all — including the ones the
> withdrawal rule below covers.

`speckit-clarify/SKILL.md:141-148` renders `**Recommended:** Option [X] - <reasoning>` for
**every** multiple-choice question, grounded in best practice and risk reduction — it does
not need the repository to reach the answer. So for a withdrawal-covered question the new
sentence guarantees a rendered `**Recommended:**` with 1–2 sentences of reasoning sitting
in the transcript when the pause is reached.

Now no answer arrives. Two rules apply to that exact state:

| Rule | Location | Outcome |
|---|---|---|
| Step-4 row of the pause table | `L32` | Take the `**Recommended:** Option X` and record it with the reasoning it was rendered with |
| The withdrawal rule | `L67` | Withdraw it; `Outstanding` row; verdict `unsatisfied` |

Both preconditions are met. Nothing in the file now says which governs. The nearest thing
is `L63-65` — *"deriving an answer to it is the silent decision the first row above rules
out"* — but that sentence predates the commit and was written when the question was never
put. It no longer bites: what the first row rules out is *a recommendation recorded
without its reasoning*, and under the new sentence the reasoning is present, rendered by
step 4 before the pause. The run that reads `L32` and records the best-practice guess is
following the file correctly.

Outcome if it resolves that way: a question only a person can settle is closed by a
best-practice guess, no `Outstanding` row, verdict `satisfied` — which is the exact
failure `L53-87` exists to prevent, and makes a scan that hit an unsettleable question
render identically to a clean one. #331's own standard (quoted in this module's test at
`tests/test_unattended_pause_rules.py:165-170`) is that a policy silent at a collision
"will be resolved by whichever agent hits it first, which is the failure this issue exists

The new sentence also collides with itself at close range: *"recommendation and all"* for
withdrawal-covered questions, against *"**Do not invent a recommendation in order to have
one.**"* (`L55`) — which is the only rule in the file that speaks to whether these
questions get a `**Recommended:**` line at all.

→ Fix: restore an explicit precedence in the L36-40 paragraph. Something like: *"Where an
answer comes back it is the answer, and nothing in this section changed the run. Where
none comes back, the first row takes the computed answer — except for the questions the
withdrawal rule covers, which have no computed answer this file will accept, and are
