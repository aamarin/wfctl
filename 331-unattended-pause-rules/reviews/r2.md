### BLOCKER

**BLOCKER  speckit.analyze.md:L125,L139,L205-212,L370-380 — the applied/filed split is never
mapped onto the `Acted on`/`Accepted` split, so a successfully filed finding has no defined
count, no row form, and an undefined effect on the verdict.**

The section states two binary partitions and never joins them:

- L139: "A finding whose fix is in scope is applied. Every other finding is **filed**."
- L207-208: "`Findings: N · Critical: N · Acted on: N · Accepted: N`, and **`Acted on` plus
  `Accepted` equals `Findings`**."

Applied → `Acted on` is obvious. Filed → *which*? Both readings are defensible:

- `Acted on`, because opening an issue is an action the run took.
- `Accepted`, because L333-337 says "A CRITICAL this run fixed does not stand; one it **filed**
  does" and L336 says "An `Accepted` CRITICAL keeps the verdict `unsatisfied`" — which only
  coheres if a filed CRITICAL is counted `Accepted`.

The two readings produce different counts *and* a different `Verdict` for the same run. #331's
own definition of done is "writes a scan file whose counts match what it did", so this is the
deliverable, not a detail of it.

Compounding it, the section shape has no form for a *successful* filing. L178-184 defines the
`Accepted:` / `Not filed:` pair for the refused case only; L198-203 defines `### Filing` as
"a filing **that was refused** keeps its title and body". The template at L377-380 then renders
`### Filing` unconditionally with a command and no issue key. So a run that files successfully
has nowhere to put `#412`, and a reader cannot tell the block "these were filed" from
"these still need filing" — which is the exact distinction L188-189 says the `Not filed:` line
was added to buy.

→ Fix: state the mapping in one sentence next to the arithmetic ("a filed finding counts
`Accepted`; `Acted on` is applied-only"), and give the `### Filing` bullet a per-cause outcome
slot — `Filed: #<n>` or `Not filed: <why>` — so success and refusal render differently.

**BLOCKER  speckit.analyze.md:L143-155 vs L57-83 — the in-scope definition makes every pass G
finding against a `proposed` design record auto-remediable, which has an unattended run rewrite
`tasks.md` to conform to a decision no human has ratified.**

Condition 1 (L145) is met: the fix edits `tasks.md`. Condition 2 (L149-150) is "It decides
nothing those three, **and this feature's design records**, have not already decided" — and a
design record, by construction, has decided. So a pass G finding is in scope and gets applied.

That contradicts pass G's own rationale forty lines above. L71-73: "`proposed` means the decision
was put and not ratified, so **a task reversing it may be the design moving**: HIGH". L80-83 adds
that "every record in this repository is `proposed` today". The pass deliberately grades a
proposed-record reversal lower *because the task may be the correct party*; the new policy then
resolves that open question in the record's favour, silently, on a run nobody is watching.
`a-human-accepts-a-decision` reserves the `proposed → accepted` transition for a human, and this
route enforces an unratified record without one.

This is not hypothetical scoping — pass G is a wfctl-added pass that runs on every analyze, and
the diff's own L99-101 rewrite explicitly routes pass G findings into this policy ("What step 8
does about a finding is settled by *When nobody answers* below").

→ Fix: exclude pass G findings against a record whose `status` is not `approved` from condition 2
— they are filed, with "the record is `proposed`; whether the task or the record is right is not
this step's call" as the stated reason. One sentence under L155.

**WARNING  speckit.analyze.md:L126 vs L236-246 — the read-only override is stated as "for an
in-scope fix, and for nothing else", and then the same cell names a third mandated write it
explicitly leaves unreconciled.** L126 ends: "its own step 6b mandates writing

reads as authorized by the skill rather than overridden by it" — instead of flagging it as
unreconciled inside the cell that says nothing else is permitted.

**WARNING  speckit.analyze.md:L339-344 — "Read the other way" flips the value of a counted
field.** The bold rule is `Critical: N` counts what was *found*. The following sentence —
"Read the other way, a run that found a CRITICAL and fixed it reports `Critical: 0 · Verdict:
satisfied` — a clean row for the run that did the most work, and the one finding a reviewer would
most want to see" — is arguing *against* the rejected reading, but it reads as "conversely, under
this rule". Nothing in the sentence marks the outcome as bad; "a clean row for the run that did
the most work" reads as praise. Two agents will write `Critical: 1` and `Critical: 0` for the same
run. This is the one paragraph in the diff whose misreading is invisible in the artifact.
→ Fix: "Under the rejected reading a run that found a CRITICAL and fixed it would report
`Critical: 0` — the run that did the most work rendering as the cleanest, and the one finding a
reviewer would most want to see going missing."

**WARNING  speckit.analyze.md:L143 vs L165-168 — "In scope is two conditions, and a fix meets both
or it is out" is a closed definition that the next paragraph adds a third condition to.** L165:
"**Materially larger is a third route out of scope.**" An agent building a checklist from L143
has a complete-sounding two-item test and never reaches the size test. The collision is sharpened
by "there is no third **door**" at L140 meaning something else entirely (fixed vs. filed), so the
word "third" carries two unrelated senses eight lines apart.
→ Fix: make it "In scope is two conditions and a size bound, and a fix meets all three or it is
out", and number the size bound as 3.

**WARNING  speckit.analyze.md:L125 vs L191-196 — two rules in the same section make opposite

counts in the scan file say which each one was**." L194-196: "It also puts `Accepted: 4` and

outstanding — the `### Filing` block below is what does." The second is correct; the first is the
sentence a reader of the table hits first.
→ Fix: drop the clause from L125 and point the row at `### Filing`.

**WARNING  speckit.analyze.md:L127, L346-349 — the post-remediation values the policy requires
have no artifact that holds them, and one of them contradicts the artifact `Detail:` points at.**
Two parts:

- *Next Actions* (L127) must be "computed against what stands *after* remediation", with a
  bespoke line for "a standing HIGH with no CRITICAL above it". In the skill's ordering that block
  is step 7 console output; step 6b (L209-213 of the skill) wrote `analysis-report.md` already,
  and nothing rewrites it. The scan file's section shape (L353-385) has no Next Actions field. So

- *`Requirement-to-task coverage`* (L346-349) is recomputed post-remediation into the scan file,

  pre-fix `Coverage %` from step 6. A reviewer who follows the `Detail:` pointer to check the
  number finds a different one, with nothing saying which is current.

→ Fix: require `analysis-report.md` to be rewritten after step 8 (and add it to the override at
L236-246, which resolves the previous finding too), or add a Next Actions line to the scan file's
section shape and mark the report's metric as the pre-remediation baseline.

**WARNING  speckit.clarify.md:L52-53 — the sentence that defines "underivable" misdescribes the
