## Findings

**BLOCKER** `wfctl/cli.py:405-408` — the sitting-boundary `start` append drops
the caller's identity, silently reopening the branch to *any* caller after the
very next stall. Reproduced:

```
start --session-id mine   → holder = mine
resume (env: mine)        → marks a completed sitting (opens_a_new_sitting)
start --session-id mine   → "Already initialized" — appends a bare
                             {"event": "start", ...} with NO session_id
status --json (env: mine) → session_holder: "unknown"   (not "self"!)
resume (env: someone-else)→ exit 0, proceeds — NOT refused
```
Full transcript: `events.jsonl` ends up
`start(mine) / notify-resolved / resume / start(<no session_id>)`, and
`last_session_id` reads only `start` events — the last one has no
`session_id`, so it returns `None` and every later `session_open_for` call
answers `"unknown"`, which is the same bucket as "nobody ever configured this."
A completely different, never-before-seen identity then passes both the
`resume` and `end` guards this feature adds, because `"unknown" != "other"`.
This is the exact defect #200 exists to close, reopened by the code's own
"almost every sitting after the first" path (`cli.py:391` comment) — i.e. the
common case, not an edge case.

It also contradicts the accepted design record directly:
`docs/architecture/design/200-session-id-rides-on-the-start-event.md` §
Decision: *"`wfctl start` appends a `start` event when there is no session on
the branch, when `opens_a_new_sitting()` is true, **or when the id presented
differs from the last one recorded**."* All three append conditions are
supposed to carry the id; this one doesn't.

→ Pass `session_id=caller` (via `_identity_kwarg(caller)`, already defined at
`cli.py:262` and already used at the analogous branch-first-start call site
one screen down) into the `append_event` call at `cli.py:406-408`. No test
catches this today — `test_agent_session.py`/`test_session_is_open.py` never
call `resume` between two `start`s with the same id, which is the one sequence
that triggers `opens_a_new_sitting`.

**WARNING** `wfctl/_session.py:601-635` (`end`) — ending a session does not
stop that same identity from reading `session_open`/`session_holder` as
`"self"`/open afterward. Reproduced: `start --session-id mine`, `end` (as
`mine`), then `status --json` (as `mine`) → `session_open: true,
session_holder: "self"`. The accepted design record states the criterion
explicitly, twice: § Decision — *"A session is open when the id a command
presents matches the id on the most recent `start` event, **and no `end`
event follows it**."* — and § Consequences — *"`wfctl end` gains a reason to
clear the recorded id beyond writing its event, so that a session wrapped up
deliberately does not read as open to the conversation that follows it in the
same process."* Neither `end()` nor `session_open_for` ever inspects `"end"`
events. Narrower blast radius than the BLOCKER above (it doesn't let a
*different* caller through — `resume`/`end`'s `"other"` guard is unaffected),
but it's a named requirement with no test and no implementation. → Either have
`end` append an `"end"` marker `session_open_for` checks for (mirroring
`opens_a_new_sitting`'s scan), or write a follow-up record that narrows the
decision text if this was deliberately deferred — right now the code and the
accepted record disagree.

**WARNING** `wfctl/_session.py:87-117` (`last_session_id`) and
`:119-146` (`session_open_for`) — neither filters by `branch`, unlike
`opens_a_new_sitting(agent_dir, branch)` (`wfctl/_stall.py:174`), which scans
the identical log shape and does. `docs/architecture/session-identity-comes-from-the-caller.md`
§ Consequences names this exact risk: *"The id has to be branch-scoped where
it is stored. `resolve_agent_dir` allows one `WFCTL_STATE_DIR` to serve
several branches, which is why `_stall.py` filters its own reads by branch; an
owner record that skipped that would let one branch's session answer for
another."* `build_report` already has `branch` in scope
(`wfctl/_pipeline.py:496`, one line before `session_open_for` is called at
:516) and doesn't pass it through. Under a shared `WFCTL_STATE_DIR` (the
override path at `_paths.py:672-676`), a `start` on branch A would be read as
branch B's holder. `session_started` has the same gap, but it's pre-existing
and outside this diff's claim; `last_session_id`/`session_open_for` are new
and the design record specifically promises branch-scoping for them. → Add the
same `branch` filter `opens_a_new_sitting` uses.

**NIT** `wfctl/_pipeline.py:515-516,562` — `session_open=holder == "self" or
(holder == "unknown" and started)` reads `events.jsonl` two or three times per
call (`session_started(agent_dir)` directly at :515, then again inside
`session_open_for` at `_session.py:120`, then again inside `last_session_id`
at `_session.py:132` when it gets that far) — and the comment directly above
(`_pipeline.py:509-514`) claims *"Both session answers from one pair of
reads, so the two cannot disagree about the same log,"* which isn't what the
code does. It also happens to be dead weight: `session_open_for` only ever
returns `"unknown"` after it has already confirmed `session_started(agent_dir)`
is `True` (`_session.py:120-121`), so `holder == "unknown"` implies `started`
is always `True` when it's reached — the `and started` conjunct never
evaluates to anything but `and True`. → `session_open = holder in ("self",
"unknown")`, and drop the separate `started = session_started(agent_dir)` call
(keep using `session_started(agent_dir)` directly for the `session_started=`
field, which is the one place it's actually needed).

**NIT** `wfctl/_session.py:110-113` (`last_session_id` docstring) — *"Malformed
lines are skipped, matching `session_started`."* They don't match:
`last_session_id` guards with `isinstance(data, dict)` before calling `.get`;
`session_started` (`_session.py:41-61`) calls `json.loads(line).get("event")`
with no such guard, so a line that parses as valid JSON but isn't an object
(e.g. `"3"`, `"[]"`, `"null"`) raises `AttributeError` there, uncaught (only
`json.JSONDecodeError` is caught). Confirmed: `json.loads("3").get("event")`
raises `AttributeError: 'int' object has no attribute 'get'`. This is a
pre-existing latent bug in `session_started`, not introduced by this diff, and
not a blocker for this review — but the new docstring asserts a parity that
doesn't hold, which will mislead the next reader who takes it at face value.
→ Either fix the claim ("skipped here; `session_started` would raise on the
same input") or, since this diff is already touching the area, add the same
`isinstance` guard to `session_started`.

## Verdict

**Request changes** (1 blocker). The BLOCKER defeats the feature on its own
most common path — every session that spans a `resume` (i.e., the ordinary
multi-turn/multi-day case `/start-session` is built for) — and the shipped
test suite is green with it present, so it needs a regression test alongside
the one-line fix, not just the fix. The two WARNINGs are both places where the
accepted design record makes an explicit promise the code doesn't keep; fix or
formally narrow the record before merge so the two don't drift further apart.
