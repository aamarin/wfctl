## Findings

**BLOCKER** `wfctl/cli.py:384-390` — `start`'s takeover check compares the raw
last identity and ignores whether an `end` closed it, so a conversation that
ends its own session and restarts with the *same* `--session-id`/
`WFCTL_SESSION_ID` gets permanently refused by `resume` and `end` afterward,
with `start` itself reporting success. → Reuse `report.session_holder`
(`!= "self"`) instead of a second, ended-blind scan.

Reproduced directly (isolated tmp-path repo, not this worktree):

```
$ wfctl start --session-id mine        # ✓ Session started — step: brainstorm…
$ wfctl end                            # ✓ Session closed — …
$ wfctl start --session-id mine        # ℹ Already initialized (use --force to reset)
$ wfctl status --json | jq '.session_open, .session_holder'
false
"other"
$ wfctl resume
✗ No wfctl session for this conversation — the last session on this branch was
opened by a different one. Run `/start-session`.
(exit 1)
```

`start_cmd` reads:

```python
holder = last_session_id(agent_dir, branch)
if caller is not None and holder != caller:
    append_event(agent_dir, "start", branch=branch, ..., session_id=caller)
    console.print("... took over from another conversation")
    return
```

`last_session_id` (`_holder_since_last_boundary`) returns the identity on the
most recent `start` line and discards whether an `end` followed it. Here
`holder == "mine" == caller`, so the condition is false, no line is appended,
and the branch is left with `start(mine), end` as its last two lines. Every
later reader of that log computes the holder relation through
`session_open_for`, which *does* look at `ended` and returns `"other"` for
that exact `(holder, ended)` pair — so `resume`/`end`/the orchestrate gate all
refuse the very conversation `start` just told "Already initialized."

This isn't a judgment call between two reasonable readings — `data-model.md`
(the accepted contract this PR implements) says explicitly, under "Not a
state": *"a branch whose session was wrapped up is still state C to the next
conversation — the same string, the same remedy"*, and state C's own
transition table says the exit from C is `caller runs start → takeover,
appends a start line → B`. That applies regardless of whether the identity
running `start` is the same one that ended it — the diagram doesn't split C by
identity. `start_cmd`'s literal `holder != caller` check silently carves out
exactly the case the contract says should still take over, and nothing in
`contracts/cli.md`'s "Behaviour by case" table lists an "ended" row at all —
the table and the state model disagree, and the code followed the table.

Fix: `start_cmd` already computed `report = build_report(spec_dir, repo_root,
agent_dir, caller)` above this block, and `report.session_holder` already
folds `ended` in correctly (it's what `resume`/`end` trust). Replacing the two
lines with

```python
if caller is not None and report.session_holder != "self":
```

closes the gap, deletes the now-unneeded `last_session_id` import, and removes
a redundant second scan of the log in the same call (see the NIT below) —
strictly fewer lines, not more.

No existing test catches this: `test_a_second_sitting_with_the_same_id_keeps_the_holder`
covers `start → resume → start`, never `start → end → start`, and
`test_a_wrapped_up_session_no_longer_reads_open_to_itself` only asserts
`session_open_for` directly — it never re-invokes `start_cmd` afterward to
check the CLI actually recovers. A regression test belongs at that exact seam:
`start(id) → end() → start(id)` should append a fresh `start` line and print
the takeover line (or some other announcement), and a following `resume(id)`
must then succeed.

**WARNING** `wfctl/cli.py:64-77` — `_HELD_ELSEWHERE`'s wording ("the last
session on this branch was opened by **a different one**") is false in
exactly the state `data-model.md` deliberately routes through this same
string: a conversation that ended its *own* session and then calls
`resume`/`end` again (or hits the BLOCKER above) sees a message asserting a
different conversation holds the branch, when the last session was opened by
itself. The design record chose to give the two cases "the same remedy" — it
did not choose to make the wording assert something false in one of them.
Reproduced in the same session above: `wfctl resume` after `wfctl end` (same
identity throughout) prints the "different one" string. Suggest neutral
phrasing that covers both origins, e.g. "No wfctl session for this
conversation — this branch has no session open for it. Run `/start-session`."

**WARNING** `wfctl/_session.py:41-64` (`session_started`) vs
`wfctl/_session.py:79-124` (`_holder_since_last_boundary`) — `session_started`
is not branch-scoped, while the new holder-relation code deliberately is (per
`session-identity-comes-from-the-caller`'s own "exact risk" language about a
shared `WFCTL_STATE_DIR`, `AGENTS.md`, `_paths.py:672-676`). `session_open_for`
gates on `session_started(agent_dir)` first, so on a shared state dir a branch
that has *never itself* run `wfctl start` reports `session_started=True` /
`session_open=True` / `session_holder="unknown"` (instead of the correct
`"none"`) purely because a sibling branch's events live in the same file.
Reproduced:

```
$ WFCTL_STATE_DIR=<shared> WFCTL_BRANCH=branch-a WFCTL_SESSION_ID=someone \
  wfctl status --json | ...
{'session_started': True, 'session_open': True, 'session_holder': 'unknown'}
```

for a branch whose own log has no `start` line at all. This predates the diff
(`session_started` was always branch-blind, and `speckit-orchestrate` already
read it unscoped before #200) — it isn't a fresh regression — but this PR adds
branch-scoping to the sibling function and leaves the gating check unscoped,
so the two halves of `session_open_for` now disagree about what "this branch"
means. It doesn't produce a false refusal (worst case is `"unknown"` instead
of the more informative `"none"`, and `"unknown"` never blocks a gate), so it
stops short of the BLOCKER above, but it undercuts the exact scenario the
design record spent a paragraph on. Fix: scope `session_started`'s scan by
branch too (`_holder_since_last_boundary(agent_dir, branch)[0] is not None or
<has some start line for branch>`), or derive "started" inside
`session_open_for` from the same branch-scoped pass instead of calling the
unscoped helper.

**NIT** `wfctl/_session.py:79-124`, `wfctl/_stall.py:174-207`,
`wfctl/_session.py:41-64` — three independent copies of "parse each
`events.jsonl` line, skip `JSONDecodeError` and skip non-dict, optionally
filter by `branch`." `_holder_since_last_boundary` mirrors `opens_a_new_sitting`
line-for-line in that scaffolding. A shared `_iter_events(agent_dir, branch)`
generator would remove ~15 lines across the three call sites; not blocking
since the duplication follows an established local shape rather than
inventing a new one.

**NIT** `wfctl/cli.py:296` / `wfctl/cli.py:246` — the env var name
`"WFCTL_SESSION_ID"` is spelled out twice as a plain string literal (typer's
`envvar=` and `_caller_identity`'s `os.environ.get`). `_paths.py` names its own
override as a module constant (`_BRANCH_OVERRIDE`); doing the same here removes
one way the two could drift on a rename.

net: −15 lines possible (dedupe NIT) plus a few more from the BLOCKER fix
removing the redundant scan.

## What's solid

- `identity()`'s strip-to-None and its symmetric application on write
  (`test_a_blank_identity_on_a_start_line_leaves_the_holder_absent`) and read
  (`test_empty_session_id_is_absent_not_an_identity`) — no divergence between
  the two `${VAR:+…}`-collapsed shell forms.
- Append-only discipline is real: `test_takeover_appends_and_never_rewrites`,
  `test_the_identity_adds_no_file_to_the_state_dir` both pass against the
  actual code, not just the design intent.
- `session_started`'s own semantics are provably unchanged
  (`test_session_started_is_unchanged`, parametrised over every new state) —
  SC-006 is genuinely defended, not just asserted.
- The unwired path (`test_no_regression_unwired.py`) is thorough: all four
  branch shapes × three commands, and it's the file that would have caught a
  regression in FR-006 had one existed. It didn't need to catch anything —
  FR-006 holds.
- `test_session_identity_rules.py`'s regex-based checks (no host variable
  named in source or in the shipped skill, no skill reads `events.jsonl`
  directly) are checks, not prose — they'll actually go red if someone adds
  `os.environ.get("CLAUDE_CODE_SESSION_ID")` as a "convenience."
- Docs (`README.md`, both SKILL.md files) match what the code does for every
  path except the one the BLOCKER covers.

## Verdict

**Request changes** (1 blocker). The blocker sits in the single most ordinary
flow the feature exists to support — end a session, come back, restart with
the same identity — and is a straightforward fix already sitting one line away
in `start_cmd` (the report it already built). The two warnings are real but
neither causes a wrongful refusal on its own; worth fixing before merge but
don't block on them if the author disagrees with priority.
