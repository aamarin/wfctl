## Findings

### BLOCKER `wfctl/cli.py:380-381` — the takeover check ignores the `end` flag, so a caller can lock itself out of its own branch

`_holder_since_last_boundary`/`session_open_for` (`wfctl/_session.py:71-140`)
correctly track *both* who the last `start` named and whether an `end`
followed it — that's the whole point of the design record's "no `end` event
follows it" clause. But `start_cmd`'s takeover decision doesn't use that
relation; it calls `last_session_id` directly (line 380), which returns only
the identity, never whether it was subsequently ended:

```python
holder = last_session_id(agent_dir, branch)
if caller is not None and holder != caller:      # takeover
    ...
# else: falls through to "Already initialized" — no new start line unless
# opens_a_new_sitting() is true, which requires an intervening `resume`.
```

Reproduced live (`start --session-id mine` → `end` (as mine) → `start
--session-id mine` again):

```
=== start mine ===
✓ Session started — step: brainstorm, next: /speckit.brainstorm
=== status (as mine) ===
True self
=== end (as mine) ===
✓ Session closed — brainstorm, boundary unanswered, tree dirty.
=== start mine again (right after end) ===
ℹ Already initialized (use --force to reset)
=== status (as mine) after restart ===
False other
=== resume (as mine) after restart ===
✗ No wfctl session for this conversation — the last session on this branch was
opened by a different one. Run `/start-session`.
```

The same conversation, presenting the same identity it started with, ends its
session and immediately reruns exactly the command `/start-session` runs
(`wfctl start --session-id mine`). It gets a success message
("Already initialized") — and is then refused by `resume` and `end`,
told a *different* conversation holds the branch, with no way back short of
`--force`. This is #200's own defect reproduced one call later: the
conversation that most needs "is a session open now?" to be trustworthy — one
resuming its own work — gets a false negative about itself.

`holder != caller` is the wrong comparison; `report.session_holder != "self"`
(already computed by `build_report` two lines above, and already accounting
for `ended`) is the one that matches the design record's stated criterion.
Fix: replace the `holder = last_session_id(...)` / `holder != caller` pair
with a check against `report.session_holder`; `last_session_id` and its extra
full-log scan become unnecessary at this call site.

None of the shipped tests exercise `start → end → start` with the same
identity — every takeover test uses a *different* id, and the only
same-id-after-`end` test (`test_a_wrapped_up_session_no_longer_reads_open_to_itself`)
stops at asserting `session_open_for`, never calls `start` again. This is the
gap that let it ship.

### BLOCKER `wfctl/cli.py:405-409` — an unwired caller's ordinary `start` can silently erase a wired holder's identity

The sitting-boundary append (reached when `opens_a_new_sitting()` is true — a
`resume` occurred since the last boundary) writes `session_id` only via
`_identity_kwarg(caller)`, which is `{}` whenever the *current* caller
presents nothing — regardless of whatever identity is already recorded as the
branch's holder. Since `last_session_id`/`session_open_for` read only the
**most recent** `start` line, appending any `start` line with no
`session_id` unconditionally clears the recorded holder.

Reproduced live: `someone-else` opens the branch → an **unwired** `resume`
succeeds (unwired callers pass every gate, by design, FR-006) → the following
**unwired** `start` hits the sitting-boundary branch and appends a bare
`start` line with no identity:

```
{"event": "start", "branch": "999-scratch", "step": "brainstorm", "session_id": "someone-else"}
{"event": "resume", "branch": "999-scratch", ...}
{"event": "start", "branch": "999-scratch", "step": "brainstorm"}          ← wipes "someone-else"
```

A wholly unrelated caller can now take the branch over uncontested:

```
=== a NEW attacker starts with --session-id attacker ===
✓ Session started — took over from another conversation
=== status as someone-else ===
False other
```

`someone-else` never ran `end`, never lost, never was told anything — a
completely unwired third party's ordinary, gate-passing `resume`+`start`
sequence erased its identity, and the console never printed a takeover
notice for the step that actually caused the loss (only for the *next*
caller, who reads as a normal takeover from "another conversation" rather
than from no one). This directly contradicts FR-006 ("an unwired caller must
never displace a wired holder") and the design record's "an id the host
issues is not the agent's to forge" — the erasure isn't a forgery, but it has
the same effect: a wired holder's claim on the branch evaporates through a
path that was supposed to be a no-op.

Root cause is shared with the previous finding: the sitting-boundary append
should carry the *existing* holder forward when the caller presents no
identity, not silently drop the field. Fix: `session_id=caller if caller is
not None else last_session_id(agent_dir, branch)` (or the already-computed
holder from the fix above) instead of `**_identity_kwarg(caller)` at
`wfctl/cli.py:408` (the unconditional append at line 414 has the same defect
and needs the same fix, though it's less reachable since it only fires when
`report.session_started` is false, meaning there is no prior holder to
protect there today — worth the same treatment for symmetry and to survive
future changes to that guard).

`test_no_regression_unwired.py::test_start_never_takes_over_for_an_unwired_caller`
covers the *no-resume* case (`held-by-another` with no intervening `resume`)
and passes — it just never exercises the sitting-boundary path against a
branch that already has a holder, which is the gap.

## WARNING

`wfctl/_session.py:679` — `append_event(agent_dir, "end", branch=branch, ...)`
adds `branch=` to the `end` event where it was absent before this diff. That's
a real, silent fix: without it, `_holder_since_last_boundary`'s branch filter
(`data.get("branch") not in (None, branch)`) would have let an `end` on one
branch clear `ended` for every other branch sharing a `WFCTL_STATE_DIR` — the
exact risk `session-identity-comes-from-the-caller` names, and it would have
also affected `opens_a_new_sitting`'s pre-existing branch filter in
`_stall.py`, which relies on the same field. Good catch, but it ships with no
regression test analogous to
`test_a_shared_state_dir_does_not_let_one_branch_answer_for_another` (which
only exercises `start` lines). Add one covering `end` under a shared state
dir, or a future refactor that reintroduces the omission goes unnoticed the
same way this one apparently did.

`wfctl/cli.py:380` + `wfctl/_pipeline.py` (`build_report`) — `build_report`
already computes the holder relation via `session_open_for` internally
(one full scan of `events.jsonl`); `start_cmd` then does a second full scan
via `last_session_id` to get essentially the same fact. Fixing the first
BLOCKER above (use `report.session_holder`) removes this duplication as a
side effect — noted here in case the fix is done differently and the
redundant scan is kept.

## NIT

`wfctl/cli.py:386-387` — the takeover message "took over from another
conversation" will fire for the fixed BLOCKER-1 scenario too (same identity,
after its own `end`) once that's corrected to trigger on
`session_holder != "self"` rather than `holder != caller`. Worth a wording
check once fixed — "another conversation" is misleading when it's the same
identity reclaiming its own branch after ending it; consider distinguishing
"resumed after ending" from "took over from a different conversation" in the
console line (the JSON/`session_holder` distinction between prior-`"self"`
and prior-`"other"` is already available to make this call).

## Over-engineering

Nothing to flag — no dead code, no speculative flexibility, no unjustified
abstraction. `identity()`, `_identity_kwarg()`, `_holder_since_last_boundary()`
are each used more than once and each earn their existence. The two BLOCKERs
above are a correctness gap in the *use* of the holder relation at one call
site, not excess machinery.

`net`: no simplification finds lines to remove; the fix for the BLOCKERs
likely nets slightly negative (removing the redundant `last_session_id` call)
rather than adding code.

## Verdict

**Request changes** (2 blockers).

The design intent in both accepted records is implemented correctly at the
`_session.py` layer — `session_open_for`, `last_session_id`, and
`_holder_since_last_boundary` all match their records precisely, are well
covered by `test_agent_session.py` and `test_session_is_open.py`, and the
branch-scoping risk the records call out by name is handled correctly there.
The defect is narrower: `start_cmd` in `cli.py` reimplements a piece of the
holder relation (`holder != caller`) instead of reusing
`report.session_holder`, and that shortcut misses the `ended` state in one
direction (self-lockout) and the "no identity presented" state in the other
(silent erasure of someone else's holder). Both are real, both were
reproduced against a live `wfctl start`/`resume`/`end` sequence in an isolated
scratch repo, and both undermine the specific guarantee #200 exists to
provide — that "is a session open now" is a trustworthy, actionable answer,
including for the conversation asking about itself.
