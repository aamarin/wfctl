## Verdict: **request changes** (2 blockers)

The identity-comparison primitives (`identity`, `_holder_since_last_boundary`,
`session_open_for`) are correct and well covered — blank/whitespace handling,
branch-scoping, malformed-line handling, and the "ended" criterion all have direct
tests and held up under adversarial probing. The defect is at the two call sites in
`start_cmd` that convert "who's the holder" into "should this call mutate the
record," which don't fully thread the `ended` state and the absent-caller case.

## BLOCKER

### B1 — An unwired `wfctl start` at a sitting boundary silently erases the recorded holder

`wfctl/cli.py`, the sitting-boundary append in `start_cmd`:

```python
if opens_a_new_sitting(agent_dir, branch):
    append_event(
        agent_dir, "start", branch=branch, step=report.current or "complete",
        **_identity_kwarg(caller),
    )
```

`_identity_kwarg(None) == {}`, so when the *current* caller presents no identity,
this appends a `start` line with **no** `session_id` key. In
`_holder_since_last_boundary` (`wfctl/_session.py`), every `start` line
unconditionally resets `holder` — including to `None` when the line carries no
`session_id` — so this line wipes whatever identity was previously recorded, with
no error, no "took over" message, nothing in the console at all (it still prints
"Already initialized").

Reproduced directly against the library functions (bypassing the CLI):

```
holder after start A:                       A
opens_a_new_sitting now:                    True
holder after unwired sitting-boundary start: None
session_open_for(agent_dir, 'A', branch):    unknown
session_open_for(agent_dir, 'random-new-id', branch): unknown
```

Sequence: `start --session-id A` → a `resume` happens (any caller — this only
needs one `resume` event to make `opens_a_new_sitting` true) → later, an ordinary
unwired `wfctl start` runs (env var unset — e.g. a script, a shell that hasn't
sourced the profile, or a host `start-session`'s `${WFCTL_SESSION_ID:+…}`
expanding to nothing because the variable isn't set on that machine). That third
call is exactly `/start-session`'s own re-run path (step 2 of
`start-session/SKILL.md`), so this is not a contrived edge — it's the normal
"pick the branch back up tomorrow" flow, minus one environment variable.

After it, **A's own identity is gone**: `A` itself now reads `"unknown"` rather
than `"self"` (harmless to A, since `"unknown"` never refuses), but so does *any
other* identity — the branch's guard has been silently dropped back to
"nobody recorded," and the next caller to present *any* id takes it over freely,
with the same "took over from another conversation" message a legitimate FR-012
takeover would print, even though nothing legitimate happened. This is exactly the
property `session-identity-comes-from-the-caller` and
`200-session-id-rides-on-the-start-event` exist to build ("wfctl … never derives
the id … a session is open when the id a command presents matches the id on the
most recent `start` event"), and it is lost by a code path that isn't the takeover
branch at all.

No test exercises this path — `test_a_second_sitting_with_the_same_id_keeps_the_holder`
only covers the case where the *same* identified caller re-runs `start` across a
sitting boundary (which commit `1e7c7ad` fixed); it never covers an *unwired*
caller re-running `start` across a sitting boundary on a branch an identified
caller already holds.

**Suggested direction**: the sitting-boundary append needs to carry forward the
*existing* recorded holder when the current caller presents nothing, not
`_identity_kwarg(caller)` verbatim — e.g. write `last_session_id(agent_dir, branch)`
when `caller is None`, so an unwired call is truly a no-op on the identity, matching
FR-006's "every gate MUST behave exactly as it does in the released version" read
as "and MUST NOT change branch state it doesn't need to."

### B2 — A conversation that ends its own session cannot get it back with `wfctl start` and the same identity

`wfctl/cli.py`, the takeover check in `start_cmd`:

```python
holder = last_session_id(agent_dir, branch)
if caller is not None and holder != caller:
    append_event(..., session_id=caller)
    console.print("… took over from another conversation")
    return
```

`last_session_id` returns the identity on the most recent `start` line — it does
not know about a subsequent `end`. `session_open_for` *does* fold that in
(`"self" if holder == caller and not ended else "other"`), which is exactly the
distinction the accepted record's Decision states twice ("no `end` event follows
it") and Consequences names as the reason `end` exists ("does not read as open to
the conversation that follows it in the same process"). `start_cmd`'s takeover
check uses the wrong one of the two: identity equality alone, not the holder
relation.

Consequence: `start` → `end` → `start` **with the same `--session-id`** neither
takes over (holder == caller, so the takeover branch is skipped) nor appends
anything else (`opens_a_new_sitting` is false — no `resume` happened between the
`end` and this `start`), so the log is left exactly as `end` left it. The console
prints `"Already initialized (use --force to reset)"` — reads as success — but
`session_open_for` for that same identity still returns `"other"`, so the very
next `wfctl resume`, `wfctl end`, or `speckit-orchestrate` step-0 gate refuses this
conversation with `_HELD_ELSEWHERE`: *"the last session on this branch was opened
by a different one"* — false; it's the same one, mid-lockout.

Reproduced directly:

```
after start:                    self
after end, presenting mine:     other
holder: mine caller: mine takeover_fires: False
opens_a_new_sitting:            False
session_open_for(mine) STILL:   other
```

The only stated recovery is `_HELD_ELSEWHERE`'s own text, "Run `/start-session`" —
which runs exactly `wfctl start ${WFCTL_SESSION_ID:+--session-id "$WFCTL_SESSION_ID"}`
with the *same* env value, so the documented one-command recovery (SC-003: "a
refused conversation reaches a working state in exactly one command") does not
work in this specific state. The only way out is `--force` (not mentioned by
`_HELD_ELSEWHERE`) or presenting a *different* identity and taking it back the
long way.

No test covers `start → end → start` (same id) → `resume`/`status`; every existing
"wrapped up" test (`test_a_wrapped_up_session_no_longer_reads_open_to_itself`)
stops at asserting `session_open_for` reads `"other"` after `end`, and never
exercises the follow-on `start` a real conversation would run next.

**Suggested direction**: gate the takeover on the holder *relation*, not raw
identity — `if caller is not None and session_open_for(agent_dir, caller, branch)
!= "self":`. This also removes B1's asymmetric handling for free at this call
site (though B1's sitting-boundary branch is separate and still needs its own
fix), and incidentally removes the redundant second full-log scan noted in N1
below, since `report.session_holder` already carries this and the extra call to
`last_session_id` becomes unnecessary.

### W2 — `session_started` itself stays branch-unscoped, so a shared `WFCTL_STATE_DIR` still lets one branch answer for another's gates

`session_started(agent_dir)` (`wfctl/_session.py:41`) scans the whole log for any
`"start"` line, with no branch filter — unlike `last_session_id`,
`session_open_for`'s own internals, and `opens_a_new_sitting`, which are all
explicitly branch-scoped by this feature or `_stall.py`. Under a shared
`WFCTL_STATE_DIR` (`_paths.py:672-676`, explicitly named in both accepted
records as a real, supported configuration), a branch that has never itself run
`start` still passes `resume_cmd`'s and `end_cmd`'s
`if not session_started(agent_dir): raise typer.Exit(1)` guard (`cli.py`) — and
also `session_open_for`'s own first check, `if not session_started(agent_dir):
return "none"` — purely because *some other branch* sharing the directory has a
`start` line. `session_holder` then resolves to `"unknown"` for that branch
(never `"other"`), so this doesn't defeat the *new* refusal this PR adds, but it
does mean `resume`/`end` proceed on a branch that never opened a session at all,
which is the same shape of cross-branch leak this feature exists to close for the
identity, just left open for the older boolean it sits beside.

This is pre-existing (true on `origin/main` before this branch too) and neither
accepted record claims to close it — `session-identity-comes-from-the-caller`'s
Consequences scopes branch-scoping to "the id," not to `session_started`. Flagging
because commit `4c8e156` on this branch is titled "stop … one branch answering for
another's," which a reader could easily take as covering this case too; it
doesn't, and nothing in the diff says so explicitly.

## NIT

### N1 — `start_cmd` re-scans `events.jsonl` a second time for the takeover check

`build_report(...)` already computes `session_holder` via `session_open_for`,
which scans the log once (via `_holder_since_last_boundary`). `start_cmd` then
calls `last_session_id(agent_dir, branch)` again, a second full parse of the same
file, purely to recover the raw identity for the `holder != caller` comparison.
Fixing B2 by switching to `report.session_holder != "self"` removes this
duplication as a side effect.

### N2 — `build_report` reads `session_started` twice per call

`session_open_for` calls `session_started(agent_dir)` as its own first line;
`build_report` then calls `session_started(agent_dir)` again a few lines later to
populate `PipelineReport.session_started`. Three full scans of `events.jsonl` per
`build_report` call (two `session_started` reads plus the holder scan) where the
log shape would allow one. Minor on typical log sizes, but `status` runs this on
every call.

### N3 — The `session_holder == "other"` refusal is copy-pasted between `resume_cmd` and `end_cmd`

Identical four-line block in both:

```python
if report.session_holder == "other":
    console.print(_HELD_ELSEWHERE)
    raise typer.Exit(1)
```

Not wrong, but a future change to the refusal condition (e.g. fixing W2, or
adding a state) has two call sites to remember rather than one.

## What held up well

- `identity()`'s blank/whitespace collapsing is applied consistently on both the
  write path (`--session-id`, `WFCTL_SESSION_ID`) and the read path (a
  malformed/blank `session_id` on an old `start` line), with direct tests for
  both directions (`test_empty_session_id_is_absent_not_an_identity`,
  `test_a_blank_identity_on_a_start_line_leaves_the_holder_absent`).
- Branch-scoping in `_holder_since_last_boundary` is correct and tested against a
  genuinely shared state dir
  (`test_a_shared_state_dir_does_not_let_one_branch_answer_for_another`); the
  `data.get("branch") not in (None, branch)` filter matches `opens_a_new_sitting`'s
  existing pattern exactly, so legacy unscoped lines still count everywhere as
  intended.
- `session_open` correctly mirrors `session_started` under `"unknown"` in every
  case — verified this isn't accidental: `"unknown"` is only reachable once
  `session_started(agent_dir)` is already known true (the `"none"` branch inside
  `session_open_for` catches the false case first), so `holder in ("self",
  "unknown")` really does equal `session_started` whenever the caller is unwired.
- The identity is never surfaced by `status` (`test_the_payload_never_carries_the_identity_itself`),
  never written to a second file (FR-010, `test_the_identity_adds_no_file_to_the_state_dir`),
  and no shipped skill reads `events.jsonl` directly or names a host variable
  (`test_session_identity_rules.py`) — all three checks are real static/behavioral
  assertions, not just docstring claims.
- `test_no_regression_unwired.py` genuinely exercises the four branch shapes
  (never-started / started-with-no-identity / held-by-another / wrapped-up)
  against an unwired caller across `status`/`resume`/`end`/`start`, and none of
  them trip a refusal or a takeover — this held up under my own probing too, for
  every path except the sitting-boundary one in B1 (which isn't in the shape
  matrix because it requires *two* prior actors, not one).
- `wfctl arch accept`'s human-agreement requirement was respected — the
  `## Log` sections of both records show a person's citation, not the
  implementing run's own say-so, consistent with the `200-analyze.md` finding
  that flagged and fixed exactly this risk (T030).
