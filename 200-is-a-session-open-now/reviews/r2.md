### The blocker, in detail

`opens_a_new_sitting(agent_dir, branch)` firing means: this conversation ran
`start`, then `resume`, then `start` again with the *same* identity — exactly
the shape of an ordinary `/start-session` re-run mid-work, which is the normal
case AGENTS.md describes (`/start-session` on every handoff). On that path
(`wfctl/cli.py:405-408`):

```python
if opens_a_new_sitting(agent_dir, branch):
    append_event(
        agent_dir, "start", branch=branch, step=report.current or "complete"
    )
```

This appends a fresh `start` line with no `session_id`, even though `caller`
(the presented identity) is in scope one line above at the takeover check. Since
`last_session_id` reads the *most recent* `start` line, the holder becomes
`None` — "unknown" — immediately after. Reproduced directly (scratch pytest
run against an isolated tmp-path repo, not committed):

```
start --session-id conv-A   → holder = conv-A
resume                      → (marks a sitting as "worked")
start --session-id conv-A   → holder becomes None
```

`_session.last_session_id(agent_dir)` returns `None` after this sequence, not
`"conv-A"`. Consequences:

1. **FR-005 violation** ("Opening a session while presenting the branch's
   recorded identity MUST leave the branch's recorded state unchanged") — the
   recorded holder changed from `conv-A` to nobody, purely from re-presenting
   the same id.
2. **The feature defeats itself on the next ordinary turn.** Any *other*
   conversation that now runs `wfctl start --session-id conv-B` sees
   `holder=None != "conv-B"` and takes the branch over — silently, per the
   existing FR-012 "holder absent" rule — while `conv-A` is still actively
   working on it. This is the exact failure #200 was opened to close, now
   reproduced by the fix itself after one resume cycle.

No test in `tests/test_agent_session.py`, `tests/test_session_is_open.py`, or
`tests/test_no_regression_unwired.py` calls `start` → `resume` → `start` with
the *same* identity — every takeover test presents a *different* id on the
second `start`, and the unwired-caller tests never present one at all. The gap
in coverage is why the full suite (`uv run pytest -q`, 1644 passed) is green
despite this.

The design record itself requires the fix: `200-session-id-rides-on-the-start-event.md`'s
Decision says `start` appends "when there is no session on the branch, when
`opens_a_new_sitting()` is true, or when the id presented differs from the last
one recorded" — three conditions for *appending*, none of them license dropping
the id on an append that happens for the second reason while an id is present.

### Passes run

- **Correctness** — adversarial; found the blocker above by tracing
  `session_open_for` → `last_session_id` → every `append_event(..., "start", ...)`
  call site in `cli.py`, then reproduced it against an isolated tmp-path repo
  (not `tests/`) rather than trusting the reading. Also checked: `identity()`'s
  strip/empty handling, `session_open_for`'s four-state table against
  `contracts/cli.md`'s table (matches), and the takeover/refusal asymmetry
  between `start` (reversible) and `end`/`resume` (refuse) — all correct.
- **Security** — no findings. `session_id` is opaque end to end: compared for
  equality only, never parsed, never interpolated into a shell command or SQL,
  never echoed to console or JSON (`test_the_payload_never_carries_the_identity_itself`
  holds it). `append_event` writes it through `json.dumps`, so no injection via
  a crafted identity string. No new file, no new subprocess, no new network call.
- **Architecture** — one finding (WARNING above, `build_report` call-site
  inconsistency). Otherwise fits the existing shape: `session_open_for` reuses
  the append-only-log pattern `session_started`/`opens_a_new_sitting` already
  use, `PipelineReport` gains two defaulted fields so every existing
  construction keeps compiling, and the caller-identity boundary matches the
  accepted `session-identity-comes-from-the-caller` record (no derivation from
  environment inside `_session.py` — that stays in `cli.py`'s `_caller_identity`).
- **Readability** — comments are dense with rationale, matching the repo's
  style; the one specific defect is the misleading comment at `cli.py:316-320`
  ("Resolved once, here, and passed down... reach every branch below by the
  same path") — the very next line (`build_report` at 322) does not receive it,
  so the comment overclaims what the code does. Names (`caller`, `holder`,
  `identity`) are clear; no nested ternaries or deep nesting introduced.
- **Performance** — no findings. `session_open_for` adds one more O(n) scan of
  `events.jsonl` per `build_report` call, same shape as the existing
  `session_started`/`opens_a_new_sitting`/`_last_resolved` reads over the same
  file; branch-scoped event logs are small (tens to low hundreds of lines), and
  this is consistent with the file's existing read pattern rather than a new
  cost class.
- **Over-engineering** — no findings. `identity`, `last_session_id`,
  `session_open_for`, `_caller_identity`, `_identity_kwarg` are each one-purpose,
  single-caller-shape functions with no speculative parameters; `session_open`/
  `session_holder` on `PipelineReport` are defaulted rather than given a second
  optional-config path. Nothing here is a layer for a second implementation
  that doesn't exist.
