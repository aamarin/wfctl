## BLOCKER

**`wfctl/cli.py:378-388` — `start` can never take a branch back from an ended
session with the same caller identity, contradicting its own printed remedy and
the accepted design's read-side semantics.**

The takeover guard is:

```python
holder = last_session_id(agent_dir, branch)
if caller is not None and holder != caller:
    ...takeover...
```

`last_session_id` (`_session.py:133`) returns the identity on the most recent
`start` line and ignores whether an `end` followed it. So once a caller runs
`start --session-id X` then `end`, and later runs `start --session-id X` again
in the *same* conversation (no `/clear`, so the host's session id is unchanged —
exactly the case `docs/architecture/design/200-session-id-rides-on-the-start-event.md`
was written to handle), `holder == caller` and the takeover branch is skipped.
`opens_a_new_sitting` also returns `False` (no `resume` occurred between the
`end` and this `start`), so nothing is appended at all — the command prints
`ℹ Already initialized (use --force to reset)` and exits 0 having changed
nothing.

But `report.session_holder` for that exact caller is `"other"`
(`_session.py:190`, since `ended=True`), and `status`'s own new warning
(`cli.py:574-577`) tells that reader: `"another conversation holds this branch —
`/start-session` takes it over"`. Running the suggested remedy does not work:
`resume` and `end` both keep refusing with `_HELD_ELSEWHERE` ("a different
[conversation]" — untrue, it is the same one), and the branch is wedged until
someone remembers `--force`, which the `start` option's own help text
(`cli.py:295`) and its inline comment (`cli.py:369-370`, "taking the branch over
is the ordinary move here, not an override") explicitly say should not be
necessary for a takeover.

Reproduced against an isolated tmp git repo (not the working tree):

```
start --session-id mine   → ✓ Session started
end                       → ✓ Session closed
status --json             → session_open: false, session_holder: "other"
start --session-id mine   → ℹ Already initialized (use --force to reset)
status --json             → session_open: false, session_holder: "other"   ← unchanged
resume                    → ✗ No wfctl session for this conversation … (exit 1)
start --session-id mine --force → only this recovers it
```

No test in the four new files exercises "same caller, start → end → start again
with no resume in between" — every takeover test uses a *different* id
(`test_start_with_a_new_id_appends_a_start_event`,
`test_a_branch_recorded_before_identities_accepts_the_first_one`), and the one
`end`-then-read test (`test_a_wrapped_up_session_no_longer_reads_open_to_itself`)
stops at `session_open_for`, never calling `start_cmd` afterward. This is also
consistent with the design record's own append condition in
"200-session-id-rides-on-the-start-event.md" § Decision — "there is no session
on the branch, … `opens_a_new_sitting()` is true, or … the id presented differs
from the last one recorded" — which has no fourth clause for "the last sitting
was ended." The code faithfully implements that three-way condition; the
condition itself is missing a case the design's own read-side rule (`"and no
`end` event follows it"`) already states.

**Fix**: `_holder_since_last_boundary` (`_session.py:89`) already computes both
`holder` and `ended` in one scan — it's the natural place to fix this instead of
adding a fourth ad hoc check in `cli.py`. Either expose it (or extend
`last_session_id`'s contract) so `start_cmd` can condition on
`caller is not None and (holder != caller or ended)`, or add a corresponding
change to the Decision's append condition and re-derive `cli.py` from it. Either
way this needs a regression test: `start(id) → end → start(same id)` must append
a fresh `start` line (a takeover, or an equivalent "reopened" message), not
silently no-op.

## WARNING

**`wfctl/agents/skills/start-session/SKILL.md:35` — the shipped shell expansion
is dead weight, and the prose built on it is wrong.**

```bash
wfctl start ${WFCTL_SESSION_ID:+--session-id "$WFCTL_SESSION_ID"}
```

`--session-id` is declared with `envvar="WFCTL_SESSION_ID"` (`cli.py:294-300`),
so typer/click already reads the variable when the flag is omitted — confirmed
by invoking `wfctl start` (no flag) with only `WFCTL_SESSION_ID` set in the
environment: the identity is recorded exactly as if `--session-id` had been
passed explicitly. Bare `wfctl start` would do the same thing on any host that
exports the variable. The `${VAR:+--flag "$VAR"}` shape exists for `--agent`
(`cli.py:3325`, no `envvar=` — required by `no-hardcoded-agent` to keep the host
name out of committed config) and was copied here without checking whether
`--session-id` needed it. It didn't: `WFCTL_SESSION_ID` is wfctl's own variable
name, not a host's, so wiring it via `envvar=` in code is exactly what the
accepted record permits.

Worse, the SKILL.md text asserts something false about its own mechanism:
"**That expansion is the whole of how wfctl learns which conversation this
is.**" It isn't — the `envvar=` binding is, and would work with the expansion
deleted. `test_no_regression_unwired.py`'s docstring even says `_caller_identity`
(used by `resume`/`end`/`status`) "reads only `WFCTL_SESSION_ID`" via
`os.environ.get` directly, underscoring that the whole feature already treats
the bare environment variable as sufficient; `start`'s option just formalizes
that through `envvar=`.

This isn't just a style nit: `test_session_identity_rules.py::
test_start_session_names_no_host_variable` pins the literal expansion string, so
a future cleanup that removes the redundancy will fail a test that reads as
load-bearing but is asserting an implementation detail with no behavioral
effect. Recommend simplifying the skill to plain `wfctl start` (or keeping the
expansion only if there's a reason not surfaced in the diff — e.g. wanting the
flag to *not* silently pick up a variable set by something other than the
skill's own profile mapping — but that reason isn't stated anywhere in the
comments, the design records, or the commit history).

## NIT

- `wfctl/cli.py:380` — `last_session_id(agent_dir, branch)` is a second full
  scan of `events.jsonl` inside `start_cmd`, on top of the scan `build_report`
  already ran via `session_open_for` two lines above it (`cli.py:322`). Trivial
  at today's log sizes and not worth blocking on, but if the BLOCKER above is
  fixed by threading `ended` through, this is also the natural point to collapse
  both reads into one (e.g. have `build_report`/`PipelineReport` carry the raw
  holder value, or have `start_cmd` call `_holder_since_last_boundary` directly
  instead of both `session_open_for` and `last_session_id`).

- `docs/architecture/design/200-session-id-rides-on-the-start-event.md` §
  Verification's "start/end/start" case is about a log that *already* holds a
  second `start` line; it doesn't cover the case the BLOCKER above is about
  (whether `start` itself appends that second line for a same-id caller after an
  `end`). Worth adding to the record's Verification list once the fix lands, so
  the two are impossible to re-diverge silently.
