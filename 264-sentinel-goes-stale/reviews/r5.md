### Findings

WARNING  wfctl/_completion.py:L163 — a new task can hide behind an accepted
incomplete task that has since been ticked, if both have the same
description. → Also count every task line in both lists, and treat any
instance the copy never held as new work.

`new_incomplete` subtracts incomplete counts only. So it cannot see the case
where an accepted incomplete task gets ticked and a new task with the same
description arrives in the same edit: the incomplete count for that
description stays at 1.

Scenario, reproduced against the PR's module:

```
copy:  - [x] T001 Build it
       - [ ] T002 Run the quickstart validation      accepted, done outside the skill
live:  - [x] T001 Build it
       - [x] T002 Run the quickstart validation      ticked later
       - [ ] T003 Run the quickstart validation      new work
new_incomplete(live, copy, quoted_out)  ->  {}      (same with T009 [US2] on the new line)
```

`_tasks_open` returns False. With no definition of done, `implement` reads
done and the story reads complete beside `2/3 done`, which is the #264
symptom coming back by a narrower route. With a definition of done
configured, `next` routes to `wfctl verify` and not to the new task. This is
the direction the module says it never fails in ("the one direction every
rule here is built never to fail in", `test_completion_record.py:166`). It
is not a regression, since main hides this case and every other case like
it. The trigger is narrow: two tasks whose text is identical once the ID and
tags are stripped, which is most likely for generic tasks such as validation
or docs passes repeated across phases.

It implements FR-005 and FR-006 as written. The spec's count rule only
covers the case where the copy held one incomplete task and the live list
holds two. So the fix also needs one sentence in FR-006. Suggested shape:

```python
def _tasks(raw, quote) -> tuple[Counter[str], Counter[str]]:  # (incomplete, every task line)
    ...  # same zip, plus a Counter over lines carrying any box

def new_incomplete(live, copy, quote):
    live_open, live_all = _tasks(live, quote)
    copy_open, copy_all = _tasks(copy, quote)
    added = live_all - copy_all            # instances the copy never held
    return (live_open - copy_open) | (added & live_open)
```

I ran this shape in a scratchpad probe against ten cases: the new one, and
each case the suite pins. All ten gave the expected answer. Ticking an
accepted task gives `added = {}`, so the step stays closed. Rewording or
noting a ticked task leaves nothing incomplete, so it stays closed. A tag
change or a renumber keeps the descriptions equal, so it stays closed. A
task unticked since the copy gives `live_open - copy_open`, so it reopens.
Duplicates while the old task is still open still reopen. The new case
reopens through `added & live_open`. Add
`test_a_new_task_sharing_a_ticked_accepted_tasks_description_reopens_the_step`
with the fixture above.

NIT  wfctl/_completion.py:L42 — `_SPAN` spells `_evidence._blanked`'s
inline-span regex (`_evidence.py:485`, inline literal) a second time. The
comment names the drift and its safe direction, but `_blanked` holds the
pattern as an anonymous literal, so nothing at that site points back here.
→ Give `_blanked` a module-level name too, or add a one-line pointer at
`_evidence.py:485`, so a future edit there finds its twin.

### Out of scope, not a finding

`resolve_spec_dir` falls back to the parent feature for a sub-issue branch
whose key `delivery.md` names (`_paths.py:733-736`). Every sub-issue of a
decomposed epic therefore shares one `tasks.md` and one completion record.
When sub-issue A runs `step complete`, its copy accepts B's unticked tasks
too. Main has the same hazard with the hand-written sentinel, and this PR
does not make it worse. It may be worth an issue of its own if epics are
decomposed this way in practice. Unverified whether they are.

   recomputed from disk on every read, with no mtime and no carried state.
   It fits `pipeline-state-is-one-payload`: one `tasks_open` feeds the
   `implement` and `decompose` readers and the routing. `step complete`
   sits beside `step none` and `sign-off`, as the design record argues. No
   new dependency. Nothing found beyond the NIT.
4. **Readability.** Names are honest (`copy_of`, `new_incomplete`,
   `RECORD`). The functions are short, and the docstrings explain why each
   shape was chosen, in the house style. The wrapper prose in
   `speckit.implement.md` says when to run the command, why, and what a
   refusal means. One NIT (the duplicated regex).
5. **Performance.** `_tasks_open` now runs `quoted_out` up to three more
   times per inference (the live list, the copy, and one tally that
   duplicates `build_evidence`'s). Each is linear in the size of `tasks.md`
   (hundreds of lines), and `status` runs once per session start. It is
   well under a millisecond. Not a finding.
6. **Over-engineering.** `_lines` (two callers, with a reason in its
   docstring), the injected `quote`, the `RECORD` constant and the tally
   line the command prints each earn their place. No dead code, no unused
   flexibility, no hand-rolled stdlib. `Counter` is already the stdlib
   answer.

Tests: they test behaviour, not implementation. The two arms named in the
