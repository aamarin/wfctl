## Review: PR #570 at 1fd89ff (264-sentinel-goes-stale)

Reviewer r6. I read the PR body, the full diff, AGENTS.md, and the 14 accepted
records from `wfctl arch context`. I read the tests before the code, and I traced
`_blanked`, `task_tally`, `_file_exists`, `_md.walk_lines`, `opens_fence`,
`closes_fence`, `build_report`, `next_step_content`, `_current_step_name`, the
`tasks`, `decompose`, and `implement` readers, and `write_atomic`. I did not run
the suite, as instructed.

### Passes run

1. **Correctness.** I checked the line pairing in `_incomplete` against how
   `_blanked` splits and joins. Both sides split with `splitlines` and join on
   `\n`, so the indexes line up, including around form feeds and HTML comments.
   I also checked the fence round trip in `render` and `copy_of`. Both split on
   `\n` alone. The fence is one longer than any marker of either character, and
   `closes_fence` needs the same character and no info string. `read_text`
   normalises CRLF on both the write and the read. I traced the refusal gate in
   `step complete` through `build_report`. `current` is None only at story
   complete, because every `_STEPS` row has a command and a manual pass returns
   `step.pass`. I also traced the routing for a record with no copy, which led to
   the WARNING below. Finally, I checked the PR's claim that every feature
   holding a completion record also holds `delivery.md`. It holds for all 42
   records in `wfctl-specs` and `pfms-specs`.
2. **Security.** The new input is `tasks.md` text and the record. Nothing is
   executed or shelled out. The three regexes (`_BOX`, `_SPAN`, `_ID_AND_TAGS`)
   are linear, with no nested ambiguous quantifier. The step name is escaped
   before it reaches rich markup, and the record is created `0600` by
   `write_atomic`. I found nothing.
3. **Architecture.** The import direction is `cli → _completion`,
   `_evidence → _completion → _md`, with no cycle, and the view and the
   layers block are updated. The command reads position from `build_report`,
   which matches `pipeline-state-is-one-payload`. The record is re-read on every
   inference, which matches `session-state-is-re-derived`. There is no new
   third-party dependency, so the dependency lookups do not apply. One finding
   comes under `a-rule-is-expressed-as-a-check` (the WARNING).
4. **Readability and simplification.** Names match their roles, and the
   rename of the sentinel to the completion record is applied consistently. The
   comments explain why the code takes its shape. There are two NITs.
5. **Performance.** Each inference now runs `quoted_out` over `tasks.md` twice
   and over the copy once, and walks the record once. These files are a few KB,
   so the cost is well under a millisecond and does not scale with anything
   larger. I found nothing.
6. **Over-engineering.** I found one candidate, the `quote` parameter. It is
   listed below as the author's call.

### Findings

WARNING  wfctl/_evidence.py:L609-614 (with `implement` at L1575-1576) — A
completion record with no copy, over open boxes, reopens `implement` with no
reason and `auto: true`. Nothing tells the agent that the record was set aside
or which command closes the step again.
- Scenario: take a branch whose record was written before this change, with
  boxes left unticked because the work was done outside the skill.
  `pfms-specs/555-taxonomy-redesign` has 46 such lines, and about 14 of the 42
  records in the two spec stores carry at least one, counted roughly by grep.
- Result: once wfctl is upgraded, `_tasks_open` returns
  `done < total` = True. `implement` returns `Assessment("in_progress", None,
  tally)`, and `next_step_content` reaches the `_STEPS` row, which is
  `/speckit.implement` with `_AUTOMATIC`. So an unattended loop re-enters
  implementation on a story that shipped, and nothing in `status` or `next`
  names the record or `wfctl step complete implement`.
- Gap in the wrapper: the new paragraph in `speckit.implement.md` covers a story
  reopened by a re-run of `/speckit.tasks`, where the copy held a task ticked.
  It does not cover a record with no copy, so the agent has no instruction to
  check the tree before redoing those tasks.
- The same silence applies to a record written by hand. That happens when an
  agent follows the derived skill's step 9b ("Write a one-line summary") rather
  than the wrapper.
- Under `a-rule-is-expressed-as-a-check`, a violation of "the record is written
  by `wfctl step complete`" is visible in an artifact, a record with no copy, so
  the rule should not stay as wrapper prose alone.
- Fix: carry the record-without-copy case out of `_tasks_open`, either as a
  tri-state or as a second field on `Evidence`. Then give `implement` a reason
  in that case, such as "completion record holds no copy of tasks.md; check the
  work is in the tree, then run `wfctl step complete implement`". A reason makes
  `next_step_content` route to `/speckit.implement` with `auto: false`, so a
  person or an attended agent decides. This leaves the ordinary mid-implementation
  case (no record at all) automatic. Pin the change with an assertion on `auto`
  in `test_a_record_with_no_copy_and_an_incomplete_task_leaves_implement_current`,
  which today checks only the command.

NIT  wfctl/cli.py:L2127-2131 — The docstring justifies the refusal by saying
"a record written then would copy every task as incomplete … the story would
read complete with nothing built". That outcome is still reachable once
`implement` is current. Right after `decompose`, with every box unticked,
`wfctl step complete implement` succeeds and prints "(2 tasks, 2 incomplete)",
and with no definition of done the story reads complete. Refusing that case
would break the legitimate case where all the work was done outside the skill,
so the gate is right. Only the stated reason overreaches. Fix: say that the
gate stops a record from being written before the pipeline routes to
implementation, and that the incomplete count it prints is the agent's check on
the rest.

NIT  docs/architecture/design/264-the-task-copy-lives-in-the-completion-record.md:L86
— In both halves of the diagram, the `archive` box's "copies" arrows point at
the `step complete` box, which reads as the archive copying the command. Fix:
point the archive arrows at the record and copy boxes, the files it actually
copies (`_archive.py:70`).

NIT  wfctl/_completion.py:L130, L153 — `yagni:` the `quote: Callable[[str], str]`
parameter exists only to avoid importing `_evidence.quoted_out`. Every caller
passes that one function, and the test helper passes it too. A function-local
`from wfctl._evidence import quoted_out` inside `new_incomplete` follows the
pattern `cli.py` uses throughout, and it would drop the parameter from two
signatures, their docstring lines, and the helper. The module docstring argues
against this deliberately, so this one is the author's call.
