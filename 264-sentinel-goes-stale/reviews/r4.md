### WARNING 1: `new_incomplete` can hide new work

`wfctl/_completion.py:163` returns `_incomplete(live) - _incomplete(copy)`. A
task the copy accepted as incomplete keeps covering its description after it
has been ticked. So a new incomplete task with the same description is
absorbed.

Failure scenario. I reproduced it with the PR's own `new_incomplete`, using an
identity quote, since the input has no fences or spans:

```
copy (at step complete):  - [x] T001 Build it
                          - [ ] T002 Update docs      accepted, done outside the skill
live (later):             - [x] T001 Build it
                          - [x] T002 Update docs      ticked afterwards
                          - [ ] T003 Update docs      new task
new_incomplete(live, copy) -> {}                      the step stays closed
```

With no definition of done, that is #264 itself, a story reported complete
beside `2/3 done`, reached by a narrower route. It also contradicts the
record's claim at `docs/architecture/new-task-reopens-implement.md:175`, that
"matching by description can only reopen the step when it did not need to".
Generic descriptions such as "Update docs" or "Run quickstart validation" are
where it bites. The incidence is low, but it is in the direction the
`test_a_line_whose_first_box…` docstring calls "the one direction every rule
here is built never to fail in".

Fix. Count ticked lines per description as well, and stop letting a copy
entry cover a description once a tick has been added for it since:

```python
accounted = copy_incomplete - (live_ticked - copy_ticked)
return live_incomplete - accounted
```

This still passes the PR's Story 3 cases. Ticking T002 removes it from
`live_incomplete`. Rewording a ticked task adds a ticked description that no
copy entry carries. An unchanged list cancels because `live_ticked ==
copy_ticked`. Add a test for the scenario above, and correct the record's
sentence or keep it true.

### WARNING 2: a copy-less record reopens the step silently

`_tasks_open` returns `done < total` for a record with no copy
(`_evidence.py:613-614`). `implement()` then returns `Assessment("in_progress",
None, tally)` (`_evidence.py:1575`), and the snapshot row
`tasks-open-but-implemented` pins `reason: null`. Status shows `implement ▶
1/2 done`, next `/speckit.implement`, `auto: true`, and gives no hint that a
record exists and was discounted.

Failure scenario. This is the window the PR's own Deployment Notes describe.
wfctl is upgraded but `install-skills` has not run, or a host loads
`speckit-implement/SKILL.md` without the wrapper. The derived skill's step 9b
(`SKILL.md:179-182`) still says to write the one-line file by hand. Take a
story whose open boxes were done outside the skill. The agent writes the
record and `implement` stays current and automatic. `speckit-orchestrate`
re-runs `/speckit.implement`, which reaches 9b and writes the same copy-less
file again. Nothing changes until `_stall` counts repeats. A person reading
`status` sees a record on disk and an open step, and nothing connects the two.

Under `a-rule-is-expressed-as-a-check` (accepted), the rule "write the record
through `wfctl step complete`" is violated visibly in an artifact the work
already produces: the record lacks `## Tasks at completion`. Today that
violation is acted on but never reported.

Fix. When the record exists, `total > 0`, `copy is None` and boxes are open,
give `implement` a reason such as "completion record has no task copy; run
`wfctl step complete implement`". Routing then keeps `/speckit.implement` but
with `auto: false`, which `next_step_content` already does for a held
`implement` with open tasks, and that breaks the unattended loop. Pin it in
the snapshot row.
