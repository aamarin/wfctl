## Review: 1582ac7 (`fix(pipeline): a task is what finishes the tasks step, not a file`) — Closes #308

Reviewer: r3

### Context gathered
- Issue #308 (`uv run wfctl issue view 308`): `tasks.md` read `done` on any non-empty
  file; `_tasks_open` spelled "finished" as *no open checkbox remains*, so a
  checkbox-free file satisfied both `tasks` and `implement` (`0/0 done`). The issue
  left open whether a checkbox-free `tasks.md` is ever legitimate.
- `wfctl/_pipeline.py` in full, plus its step-table doc comment (rungs 1–7),
  `_tasks_open`, `_implement_verdict`, `_infer_steps`'s loop, `next_step_content`,
  `build_report`, and `cli.py`'s generic rendering of `annotation`/`reason`/`remedy`
  (confirms no second, hand-maintained render path needs updating for the new
  `tasks` reason).
- Project `CLAUDE.md`: `uv run` bar, ruff/mypy rules, comment style (why, not what),
  test-naming convention.

### Passes run

**1. Correctness (adversarial)**
- Traced `_task_tally` → `_tasks_open` → `_implement_verdict` and the `tasks` arm in
  `_infer_steps` by hand against several inputs: empty file, prose/no checkboxes,
  all-ticked, mixed, and prose-with-`implement-complete.md` sentinel present.
  All resolve as intended: checkbox-free now reads `tasks: in_progress` with
  annotation `tasks.md holds no task`, and `_tasks_open` returns `True` for that
  case (`bool(tasks_text)` on the `total == 0` branch), which correctly keeps
  `implement` off `done` via `_implement_verdict`.
- Checked the sentinel is deliberately *not* consulted by the `tasks` arm itself
  (only by `_tasks_open`/`implement`) — matches the docstring's stated reason
  (`implement-complete.md` asserts implementation is done, not that this step
  produced tasks) and the commit's audit claim (23 files / 30 `specs-trunk`
  versions, all ≥12 boxes) that a checkbox-free `tasks.md` has never been a
  legitimate degrade path.
- Checked cascade interaction: `tasks: in_progress` does not set `cascade = True`
  (only `pending` does), so `decompose`/`analyze`/`implement` are still evaluated
  on their own evidence — same as before the fix, and covered directly by
  `test_a_delivery_plan_does_not_carry_a_task_free_file_into_implement`.
- Checked `next_step_content`/`build_report` wiring: `tasks_reason` flows through
  the same `reason` dict as `implement_reason`/`design_reason`/`decompose_reason`,
  so `_current_step_name` stops at `tasks`, and `next_step_content` returns
  `(/speckit.tasks, auto=False)` for the blocked case — matches
  `test_the_tasks_step_is_not_automatic_while_its_file_holds_no_task`.
- Minor observed (not a defect): when `tasks.md` is checkbox-free, the `implement`
  row itself now renders with `state=in_progress` and `annotation=None` (no reason,
  since `_implement_verdict` returns `("in_progress", None)` before reaching
  `verification_block`). This is deliberate per the commit message ("`0/0 done`...
  beside any state it reads as a count of work rather than as the absence of
  anything to count") and the pipeline's `current` step (which carries the actual
  reason) is `tasks`, not `implement`, so nothing is unexplained to a caller
  reading the report as a whole — noting it only because a reader looking at the
  `implement` row in isolation sees a blank annotation.
- Ran the actual suite rather than trusting the diff: `uv run pytest -q` → 1283
  passed. `uv run ruff check wfctl/ tests/` → clean. `uv run mypy wfctl/` → clean
  (21 files, no issues).

**2. Security** — N/A. No external input, no secrets, no auth surface touched;
change is pure local-file-content inference.

**3. Architecture**
- `_task_tally` consolidates what was two independent regex readings (`tasks`
  arm's old `tasks_text` truthiness check and `implement`'s tally block) into one
  function used at three call sites — directly addresses the duplication class
  #262 named, fits the file's existing pattern of small pure predicates
  (`_file_exists`, `_unkeyed_issues`) fed into the `_infer_steps` loop.
- New `in_progress` + reason shape for `tasks` matches the shape already used by
  `brainstorm` (`design_reason`) and `decompose` (`decompose_reason`) — no new
  pattern introduced, an existing one extended consistently (own local, own slot
  in the `reason` dict, own branch in the annotation `if/elif` chain).
- Confirmed via `blocks()`'s own contract (`verdict == "unsatisfied"` blocks
  regardless of `source`) that skipping a `blocks(...)` call for `tasks` and
  hardcoding `in_progress` is not a silent divergence from the `Verdict`/`Source`
  framework: `tasks` has no `inconclusive` branch (file is read or absent), so
  the call would be a no-op wrapper around a constant `True`. The doc comment
  above `_STEPS` says exactly this. No architecture concern.
- `cli.py` renders `annotation`/`reason`/`remedy` generically off the step
  dict (`_pipeline.py`'s `PipelineReport`) — verified no cli.py change was needed
  and none was skipped; grepped the whole tree for `0/0 done`/`_task_tally`/
  `TASKS_EMPTY` and found no other consumer assuming the old shape.

**4. Readability & simplification**
- Comment style matches the file's existing density and "why" focus (dense
  rationale, references to #262, #308, #300, #69 by number, matching
  `CLAUDE.md`'s stated convention).
- New test file `tests/test_tasks_hold_a_task.py`: names are sentences, docstrings
  say why the test exists and what it would have caught pre-fix, per
  `CLAUDE.md`'s testing-conventions section. Verified the `spec_tree` fixture's
  signature (`tests/conftest.py:260`) actually supports the `content={...}`
  usage the new tests rely on (it does).
- No nesting/complexity issues; the new `tasks` arm and the `_task_tally` helper
  are each well under the 50-line/3-level guidance.

**5. Performance** — `_task_tally` runs 2 `re.findall` passes over `tasks.md`'s
text, called up to ~3 times per `_infer_steps` invocation (once via the
precomputed `tasks_open`, once in the `tasks` arm, once in `implement`'s
annotation block, plus once more inside `_tasks_open` for `implement`'s verdict).
`tasks.md` is a small, already-in-memory string, so this is negligible — not
worth flagging given the file's own stated preference (`_task_tally`'s docstring)
for three independent call sites over threading one tally through the loop.

**6. Over-engineering** — Nothing to flag. `_TASKS_EMPTY_REASON` is one constant,
used once, with its privacy explicitly justified against the file's own naming
rule (names cross out only where `cli` imports them). The tally consolidation
*reduces* duplication rather than adding a new layer. The diff's size is mostly
comments/docstrings and a new, well-targeted test file — no unused flexibility,
no config nobody sets, no abstraction with a single caller.
