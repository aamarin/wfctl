### Pass 1 — Correctness (adversarial)
Traced the fix by hand and confirmed against the actual functions (not just
the new tests):

- `tasks` arm now requires `_task_tally(tasks_text)[1] > 0` (≥1 checkbox) to
  read `done`; a non-empty, checkbox-free file reads `in_progress` with
  `tasks_reason = "tasks.md holds no task"`. Correct per spec.
- `_tasks_open` now falls back to `bool(tasks_text)` when the tally is `0/0`
  (no sentinel), so a checkbox-free `tasks.md` reads *open* rather than
  *closed* — closes the `implement` half of the bug. Verified by direct call
  (not just via the new pytest file):
  ```
  tasks.md = "prose, no checkboxes\n" (no sentinel)
  → _implement_verdict → ("in_progress", None)   # was ("done", None) pre-fix
  ```
- `_current_step_name`/`build_report`/`next_step_content` routing verified by
  reading the code path end to end: `tasks` in_progress → `blocked` is truthy
  → `next_step_content` returns `("/speckit.tasks", False)` — matches the new
  `test_the_tasks_step_is_not_automatic_while_its_file_holds_no_task`.
- **cascade is not triggered by `in_progress`, only by `pending`** — this is a
  pre-existing pattern (`brainstorm`/`specify`/`clarify` already do this), so
  `analyze`/`decompose`/`implement` are still independently evaluated after a
  checkbox-free `tasks.md`. Confirmed this is intentional and matches the
  existing design, not a new hole introduced here.

**WARNING** `wfctl/_pipeline.py:263` (`_tasks_open`) — the sentinel check runs
*before* the zero-tally fallback, so when `checklists/implement-complete.md`
exists **and** `tasks.md` holds zero checkboxes, `_tasks_open` returns `False`
(not open) purely on the sentinel, bypassing the new "zero tasks written" rule
entirely. Reproduced directly against `_infer_steps` (no test-harness
involved):
```
spec.md/plan.md/analysis-report.md present, tasks.md = "prose, no checkboxes\n",
checklists/implement-complete.md present, no def-of-done configured
→ tasks:     in_progress   "tasks.md holds no task"
→ implement: done          None            # no annotation — total is 0, so
                                            # the new `if total:` guard even
                                            # suppresses the old "0/0 done" tell
```
`implement`'s own row silently reads `done` off a file that produced no task —
the second half of #308, reproduced through the sentinel escape hatch instead
of through the tally. It doesn't regress the reported symptom (the *pipeline*
still doesn't complete — `tasks` blocks first via `_current_step_name`, and
`next_command`/`current` correctly stay on `/speckit.tasks`), but `report.steps`
and the console table (`cli.py:449-455`, keyed off each step's own state, not
gated by the current step) will show `implement ●` with zero evidence and no
annotation to explain it — which is exactly the shape #300's audit exists to
catch, on a step this diff didn't touch. Untested (no test combines a sentinel
with a checkbox-free `tasks.md`), and not present in any real spec dir today
per this diff's own docstring claim (23 on disk, all ≥12 boxes) — but it's the
issue's own "not decided here" case turning into silent, wrong evidence. Either
gate the sentinel branch on `total` too (`_tasks_open` should not let the
sentinel stand in for a `tasks.md` that never wrote a task), or file it as the
follow-up the issue deferred, explicitly.
