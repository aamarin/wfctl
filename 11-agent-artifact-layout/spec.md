# Feature Specification: Agent Artifact Layout

**Feature Branch**: `11-agent-artifact-layout`  
**Created**: 2026-08-05  
**Status**: Draft  
**Input**: Consolidate the agent artifact layout — move `.agent/` (singular) into `specs/<branch>/`, and give project overrides a committed home at `AGENTS.md`.

## Clarifications

### Session 2026-08-05

- Q: Does this feature's scope cover the tooling changes in the second repository, or are those tracked separately? → A: One issue spans both repos — they are co-dependent, and neither half is complete alone.
- Q: Should tooling read both the old and new artifact locations during a transition, or should a component version mismatch be reported instead? → A: Report it. No dual-path reading; the health check names the skew and the fix.

## User Scenarios & Testing _(mandatory)_

### User Story 1 - One directory holds a branch's artifacts (Priority: P1)

A developer working a branch through the pipeline finds every artifact that
branch produced in one place. There is no second directory whose name differs
from the tooling directory by one letter, and nothing about which of the two a
given file belongs to has to be remembered.

**Why this priority**: This is the defect the issue exists for. `.agent/` and
`.agents/` are one letter apart and hold unrelated things — one is generated by
`wfctl install-skills`, the other is the branch's working state. Confusing them
fails silently. Every other story is smaller.

**Independent Test**: Run the pipeline from `/brainstorm` through `/speckit.plan`
on a fresh branch. Confirm `.agent/` is never created and that the design doc,
brief, escalation record, spec, and plan all land in `specs/<branch>/`.

**Acceptance Scenarios**:

1. **Given** a fresh worktree, **When** `/brainstorm` completes, **Then** the
   design document exists at `specs/<branch>/design.md` and no `.agent/`
   directory exists.
2. **Given** a branch with a design document, **When** `/speckit.specify` runs
   its pre-specify gate, **Then** it finds the design at
   `specs/<branch>/design.md` and proceeds without prompting.
3. **Given** a worktree mid-pipeline, **When** the worktree is removed, **Then**
   the archive contains `1-design.md` through `11-analysis-report.md` with no
   gaps and no `extra/design.md`.
4. **Given** a branch whose design document exists, **When** `wfctl start` runs,
   **Then** it reports the pipeline step as `specify`, not `brainstorm`.

---

### User Story 2 - Project overrides survive being committed (Priority: P2)

A repository maintainer writes instructions that apply to every agent session in
that repo, commits them, and they are still there for the next contributor and
the next agent.

**Why this priority**: Independent of Story 1 and shippable alone, but lower
value — it affects repos that want overrides, whereas Story 1 affects every repo
on every branch. Today an override is impossible to commit: both candidate
directories are gitignored in a consumer repo.

**Independent Test**: In a repo with a root `AGENTS.md` containing a
distinguishing instruction, run `/brainstorm` and confirm the instruction is
read and applied.

**Acceptance Scenarios**:

1. **Given** a repo with a committed root `AGENTS.md`, **When** `/brainstorm`
   starts, **Then** its contents are loaded as project overrides.
2. **Given** a repo with no `AGENTS.md`, **When** `/brainstorm` starts,
   **Then** it proceeds without error and without creating one.
3. **Given** a fresh clone of a repo whose maintainer committed overrides,
   **When** a contributor runs the pipeline, **Then** the overrides are present
   without any local setup step.

---

### User Story 3 - Each artifact has exactly one writer (Priority: P3)

A developer's design document is not destroyed by a later step of the same
command, and an agent's scope contract is not overwritten by the planner.

**Why this priority**: Pure deletion, no dependency on Stories 1 or 2 — it could
ship first. Lower priority only because the failures are intermittent: they
require the specific step sequence that triggers them.

**Independent Test**: Run `/brainstorm` to completion and confirm the approved
design survives the idea-refine step. Separately, write a brief, run
`/speckit.plan`, and confirm the brief is unchanged.

**Acceptance Scenarios**:

1. **Given** `/brainstorm` has written an approved design, **When** the
   sharpening step completes, **Then** the design document still contains the
   approved design.
2. **Given** a branch with an agent brief, **When** `/speckit.plan` completes,
   **Then** the brief is byte-identical to before.
3. **Given** any pipeline artifact, **When** the skills are searched for writers
   of that path, **Then** exactly one is found.

---

### Edge Cases

- **Tooling updated out of order.** A repo updates the skills but not wfctl, or
  the reverse. The skills-first case must degrade to a visible, recoverable
  wrong state rather than a silent one.
- **Design document written before the spec directory exists.** `/brainstorm`
  runs earliest in the pipeline; its destination directory may not exist yet.
- **A repo that already has `AGENTS.md`.** The file is a cross-tool convention
  and may already hold unrelated content. Nothing may overwrite or truncate it.
- **A worktree removed before any spec directory exists.** Teardown must not
  fail when there is nothing to archive.
- **A consumer repo carrying the old gitignore entry.** A stale `.agent/` line
  must not break anything after the directory stops being produced.
- **An existing `.agent/` directory from a previous session.** Files already on
  disk at the old path when the change lands.

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: No skill, command, or tool MUST write to `.agent/` (singular).
- **FR-002**: The design document, agent brief, and escalation record MUST live
  in `specs/<branch>/` alongside the rest of that branch's pipeline artifacts.
  The escalation record MUST NOT reuse a name the tooling already uses for an
  unrelated concept.
- **FR-003**: The pre-specify gate MUST locate the design document at its new
  path and proceed without prompting when it exists.
- **FR-004**: Project overrides MUST be readable from a repository path that can
  be committed, and `/brainstorm` MUST read them from there.
- **FR-005**: Reading project overrides MUST be tolerant of the file's absence.
- **FR-006**: Writing to the project override file MUST preserve all content the
  file already had. _No component in this feature writes it — this constrains
  whatever later gains that ability, and is deliberately carried without an
  implementation task here._
- **FR-007**: Archiving a branch MUST produce a continuous, gap-free numbered
  sequence including the design document, from any point in the pipeline.
- **FR-008**: Pipeline step inference MUST recognize a completed brainstorm from
  the design document's new location.
- **FR-009**: Each pipeline artifact MUST have exactly one writer across all
  skills and commands.
- **FR-010**: The brainstorm handoff MUST name exactly one destination across
  every skill and command that references it.
- **FR-011**: No instruction MUST require committing a path that is
  conventionally gitignored.
- **FR-012**: `/brainstorm` MUST create its destination directory when absent.
- **FR-013**: Tooling MUST read exactly one artifact location — the new one. No
  component reads both.
- **FR-014**: The health check MUST detect a version mismatch between the
  artifact-producing and artifact-consuming components, and report it with the
  action that resolves it.

### Key Entities

- **Design document**: The approved output of brainstorming. First artifact in
  the pipeline sequence; the handoff contract that specification consumes.
- **Agent brief**: A task-scoped constraint file — what an agent may touch, what
  stops it, what "done" means. Read at session start, never modified during a
  session.
- **Escalation record**: Written when an agent hits a hard stop and needs a
  human. Terminal — the agent stops after writing it. Named to avoid colliding
  with the tooling's existing, unrelated "checkpoint" concept.
- **Project overrides**: Repository-wide agent instructions, authored by a
  maintainer and committed. Distinct from per-branch artifacts in both lifetime
  and audience.
- **Branch archive**: The snapshot of a branch's artifacts taken at worktree
  teardown, numbered in pipeline order and outliving the worktree.

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: A search of the repository for the old artifact location returns
  zero results.
- **SC-002**: A developer locates any artifact a branch produced by looking in
  exactly one directory.
- **SC-003**: A branch archived at any pipeline stage yields a numbered sequence
  with no gaps and no unclassified entries.
- **SC-004**: A maintainer's project overrides survive a fresh clone with no
  local setup step.
- **SC-005**: Running the full pipeline on a fresh branch produces no directory
  whose name differs from the tooling directory by one character.
- **SC-006**: Every pipeline artifact has exactly one writer, verifiable by
  search.
- **SC-007**: A repo that updates one component but not the other is told so by
  the health check, with the action that fixes it — the mismatch is never left to
  be inferred from a stalled pipeline.

## Assumptions

- Pre-specify design context loaded from `.agent/spec.md`.
- **The feature spans two repositories and they are co-dependent.** The skills
  repository holds the artifact producers; the tooling repository holds the
  archive and the pipeline-step inference that read them. Neither half delivers
  the outcome alone: skills alone strand inference at the brainstorm step, and
  tooling alone changes nothing a user sees. One issue therefore covers both, its
  tasks carry the ordering constraint explicitly, and it is done only when both
  merge.
- **No migration of existing artifacts.** Files already at the old path when
  this lands are per-branch scratch, already snapshotted at teardown by the
  existing archive. They are left alone rather than moved.
- **The override file is read, not created.** Absent an override file, the
  pipeline proceeds; nothing scaffolds one into a consumer repo. This mirrors
  today's behaviour for the old override path.
- **The spec directory is gitignored**, as it is today. Moving the design
  document into it does not make it committable, which is why the instruction to
  commit it is dropped rather than repointed.
- **The existing teardown archive is the durability mechanism.** No new
  snapshotting is introduced; artifacts stay in the workspace where agents read
  them by plain path, and the existing teardown hook preserves them.
- **`AGENTS.md` is the override path**, chosen because it is the cross-tool
  convention other agents already read and needs no gitignore exception.
- **No migration affordance in the read path.** A consumer that upgrades one
  component but not the other is told by the health check rather than
  transparently accommodated. This trades a brief broken state for no
  compatibility code and nothing to remember to delete later — the health check
  already tracks both component versions, so detection is close to free.
- **Scope is the artifact layout only.** Four adjacent efforts are deliberately
  excluded, because a planner reading this spec alone could otherwise pull them
  in: removing one project's content from the shipped templates; adopting the
  upstream extension system and populating the override file's managed region;
  making the spec directory's location configurable; and reconciling branch
  creation with the upstream tooling's own branching mechanism. Each is tracked
  on its own issue. This feature moves artifacts and gives overrides a committed
  home — nothing more.
- **The installer never seeds an override file.** Decided 2026-08-05. A consumer
  repo gains one only when its maintainer writes one, so installing the tooling
  never adds a committed file to a repository. Any later mechanism that manages a
  region inside that file must therefore handle its absence, which is the same
  case as a repo whose override file predates the mechanism — one code path, not
  two.

## Validation Strategy

- **Automated**: the existing archive test suite passes with the design document
  arriving from its new path, plus a case asserting the numbered sequence is
  gap-free.
- **Automated**: a repository-wide search for the old artifact location returns
  nothing.
- **Automated**: a search for writers of each artifact path returns exactly one
  per artifact.
- **Manual**: run the pipeline end to end on a fresh branch in a repo with a
  committed override file; confirm the override is read and no `.agent/`
  directory appears.
- **Manual**: remove a worktree mid-pipeline and confirm the archive is complete.
- **Manual**: confirm step inference advances past brainstorm once the design
  document exists.
- **Manual**: with a deliberately mismatched pair of component versions, confirm
  the health check reports the skew and names the action that resolves it.
