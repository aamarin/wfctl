## Step 4 — the six passes

### 1. Correctness (adversarial)

Traced `wfctl/_declared.py`'s new `needs_person` parsing and
`wfctl/_pipeline.py`'s `_pass_states`/`_read_pass`/`build_report` changes by
hand against `tests/test_pipeline_needs_person.py`'s nine cases (skip +
reason, no file written, cascade continues past the skip, `next_command`
moves on, evidence beats the skip in either mode, a claim beats the skip in
either mode, the flag off skips nothing, payload carries the flag for every
pass). Walked the logic myself rather than trusting the tests:

- Claim precedence, own-step-state gating, and the needs_person branch are
  checked in the order the docstring in `_pass_states` claims (claim →
  own-state skip → own-state not-done → cascade → evidence → needs_person).
  Verified this against the code at `wfctl/_pipeline.py:428-451` — the order
  matches.
- The needs_person skip branch does not set `cascade`, so a normal pass after
  a skipped needs_person pass is still read on its own evidence (confirmed
  against `test_a_skipped_pass_does_not_hold_back_the_pass_after_it`, and by
  reading the code: the `continue` in the needs_person branch bypasses the
  `cascade = True` line entirely).
  `_ordered`/`_toposort` are unmodified by this diff and a `needs_person`
  pass flows through them like any other `SubStep`; no interaction found.
- `build_report`'s reordering of `granted = read_auto_approve(agent_dir)`
  ahead of `_infer_steps(...)` (previously computed after) is correct and
  necessary: `_infer_steps` now needs the mode to decide the needs_person
  skip, and the docstring's justification ("two reads of one file... can
  disagree while it is being written") is sound — this removes a
  time-of-check/time-of-use gap rather than introducing one.
- `wfctl.json`'s own new declaration (`plan.plan-walkthrough`, command +
  evidence + `needs_person: true`, no `manual`) is a schema-valid entry per
  `_load_step`'s rules — checked every branch it must pass (`has_command`,
  not `manual`, `needs_person` boolean, not manual+needs_person together).

### 3. Architecture

- `_read_pass` factors five previously-duplicated `_PipelineSubStep(...)`
  constructions into one function — a real simplification, not new surface.
- The `needs_person` field defaults `False` on `SubStep` and
  `_PipelineSubStep`, so every existing caller and every built-in pass reads
  unchanged; confirmed by `test_no_built_in_pass_needs_a_person` and
  `test_all_does_not_change_the_json_payload` (updated to assert the new key
  rather than silently passing).
- **Finding A (WARNING)** — `plan-walkthrough` is not added to
  `wfctl/cli.py`'s `_MIRRORED_SKILLS`, and this diff does not touch
  `wfctl/cli.py` at all. `docs/architecture/scans/500-clarify.md` explicitly
  deferred this exact question: *"whether the skill needs an entry in
  `_MIRRORED_SKILLS`. The mirror test named in that set's comment decides it
  during implementation."* That comment's own test (`wfctl/cli.py:2824` and
  surrounding entries) is: a skill is mirrored when its description triggers
  on natural language with no command typed — e.g. `brainstorm` and
  `fanning-out-code-review`, whose comments say almost exactly this. The
  shipped `plan-walkthrough/SKILL.md` frontmatter description reads: *"Use
  when the person runs `/plan-walkthrough`, or **asks to be walked through,
  quizzed on, or challenged about a plan** or a finished change..."* — a
  natural-language trigger of the same shape. By the test the repository
  itself named as decisive, this skill should have joined the set; nothing in
  the diff records a decision either way (no `Considered` entry rejecting it,
  no code change). This reads as the deferred item being silently dropped
  rather than resolved. Concretely: a person who says "quiz me on this plan"
  under Claude will not reach this skill — only literally typing
  `/plan-walkthrough` will.
- No cyclic imports introduced (`_declared` still only reaches back into
  `_pipeline` at function scope, unchanged).

- `docs/reference.md`'s new section is concrete, has a runnable example, and

- **Finding B (WARNING)** — `docs/architecture/autonomous-agent-skips-human-checks.md`
  (`status: proposed`, i.e. the currently-live record for this decision) line

  commit. Given how much this repository's culture leans on citations being
  literally checkable ("comments... explain *why this shape*", the whole
  `wfctl arch context` / scan-file citation discipline), a stale line number
  in the record that *introduces* the feature is a real defect, not a nit.
- **Finding C (NIT)** — the rejected design doc
  `docs/architecture/design/autonomous-skip-is-a-claim.md`'s "Verified"
  section carries several more citations (`_declared.py:202`,
  `_pipeline.py:400-403`, `_pipeline.py:426`, `_pipeline.py:748-749`,
  `_pipeline.py:511`) that are now stale against the final state of this same
  branch — its own git history shows it was committed (`bbd6fee`) before the
  later commits (`e4b680c`, `f949f54`) that shifted both files' line numbers.
  Lower severity because it's an explicitly `rejected` historical record, and
  this repo's convention may not require a rejected doc's citations to track
  code forever — but it is still checkable-and-wrong today, in the same
  branch that made it wrong.
- **Finding D (WARNING)** — `docs/architecture/plan-walkthrough-is-private.md`'s
  "Owns truth" section states: *"wfctl owns 'has this check been run against
  the current plan?'. The evidence in the feature folder answers that..."*
  Checked the actual mechanism: `build_file_exists_reader` (`wfctl/_evidence.py:229-247`,
  unchanged by this PR) is a pure existence+non-empty check. It never parses
  or compares the marker's recorded `Walked through: sha256:<hex>` line
  against a fresh hash of the current `plan.md`. So if the plan owner
  completes a walkthrough and then materially edits `plan.md`, the pass keeps
  reading `done` — nothing recomputes or checks the hash. The claim in the
  doc overstates what's actually verified ("against the *current* plan");
  what's verified is only "a walkthrough happened at some point, and its
  marker records which plan it was against, for a human to check by eye." This
  matches the known, general limitation of the `evidence` mechanism recorded
  in `AGENTS.md` ("a pass whose output is not a file at a fixed path needs a
  different mechanism, not a grep taught to `wfctl.json`") so it isn't a new
  code defect — but the new doc's wording claims a guarantee the code doesn't
  provide, which will mislead a reader who takes "owns truth" sections at face
  value.
- **Finding E (NIT)** — `plan-walkthrough/SKILL.md` step 1's refusal ("Refuse
  while auto-approve is on") is enforced purely by an LLM correctly executing
  a prose instruction; there's no code-side backstop for a person who types
  `/plan-walkthrough` directly while auto-approve happens to still be on
  (distinct from the `needs_person` pipeline-routing skip, which only ever
  prevents *orchestrate* from naming this command next). The record's own
  "Owns truth" section acknowledges wfctl can't decide this ("the skill can't
  answer it in time either"), so this is a known, inherent limit of the
  design rather than something this PR botched — noting it so it's an
  accepted risk, not a silent one.

## Verdict

**Request changes.** Nothing here is a correctness bug, security hole, or
data-loss risk — the `needs_person` pipeline mechanism itself is correct and
well tested. The reason to send this back rather than approve-with-notes is
that Finding A is a decision this repository's own process (the clarify scan)
explicitly promised would be made during implementation, and it silently
wasn't — either add the entry or write down why not. Finding B is a stale
citation in the very record that is supposed to be the authoritative,
currently-`proposed` explanation of this feature, in a repo whose whole
architecture-doc discipline depends on citations being literally checkable.
Both are small, mechanical fixes; Finding D is worth a one-line wording
correction in the same pass.
