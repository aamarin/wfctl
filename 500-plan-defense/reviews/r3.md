## Correctness

Traced the whole new mechanism: `wfctl.json`'s `steps[].needs_person` →
`_declared._load_step` (validation) → `SubStep.needs_person` →
`_pipeline._pass_states`'s skip branch → `build_report`'s threading of
`auto_approve` into `_infer_steps` → the JSON payload's `needs_person` key →
`docs/architecture/autonomous-agent-skips-human-checks.md`'s stated contract
("the run skips it and keeps going").

**Finding (high confidence, confirmed by repro) — `wfctl next` disagrees with
`wfctl status`/`wfctl resume` on a `needs_person` pass, and would send an
autonomous run straight into it.**

`wfctl/cli.py`'s `next_cmd` (the `next` command) builds its own step list at
line 817:

```python
steps = _infer_steps(spec_dir, repo_root, ev)
```

`build_report` (used by `status` and `resume`) was correctly updated to read
`auto_approve` before inference and thread it through:

```python
granted = read_auto_approve(agent_dir)
raw = _infer_steps(spec_dir, repo_root, ev, auto_approve=granted)
```

`next_cmd` was not. It does call `read_auto_approve(agent_dir)`, but only
seven lines later, and only as the `auto_approve=` argument to
`next_step_content` — which uses it solely to decide whether an *already
outstanding, already-has-a-command* pass gets `auto=True`. It never reaches
`_infer_steps`, so `_pass_states`'s `needs_person` skip branch (`wfctl/
_pipeline.py`, the `if reading.state != "done" and sub.needs_person and
auto_approve:` line) never fires on this path. The pass reads `in_progress`
here, not `skipped`, `_outstanding_pass` picks it up, and `next_step_content`
routes to it — with `auto=True`, because auto-approve is on and the pass has a
command.

Reproduced end to end (declared a `needs_person: true` pass with no evidence,
under `decompose`, with auto-approve granted):

```
STATUS: sub_step "walk" = {'state': 'skipped', 'annotation': 'needs a person; auto-approve is on', ...}
STATUS: next_command/auto = None, None

NEXT:   → Next step: /walk (auto: true)
next-step.md:
  Next step: /walk
  auto: true
  Run this command to continue.
```

`status` correctly reports the pass skipped and moves the payload's
`next_command` on. `next` — a separate, documented command that writes the
same `next-step.md` file an autonomous/orchestrated run actually acts on —
tells the agent to run the walkthrough automatically. That is exactly the
outcome this whole feature exists to prevent: an unattended agent answering
its own comprehension-check questions, producing (per
`plan-walkthrough-is-private.md`) invalid evidence, and per
`autonomous-run-stop-condition.md`'s explicit promise ("a check that needs
human intervention isn't on the list... the run skips it and keeps going")
this is a documented contract the code breaks on this call path.

This is not dead code superseded by `resume`: `next` is a real, separately
tested command (`wfctl/cli.py:790`), and nothing in the diff or the existing
suite exercises it against a `needs_person` pass — `tests/
test_pipeline_needs_person.py`'s nine tests all go through `build_report`
directly or via `status --json`; none call `next`.

Fix shape: thread `auto_approve=read_auto_approve(agent_dir)` into the
`_infer_steps(...)` call at `wfctl/cli.py:817`, reading it before that call
(matching `build_report`'s own comment about why the read has to precede
inference), rather than only at the `next_step_content` call seven lines
later.

No other correctness issues found. Specifically checked and found sound:

- `_declared.py`'s three new validations (`needs_person` non-bool,
  `needs_person` + `manual` together, and that both are checked *before* the
  entry is otherwise accepted) — order matches the tests, and the "manual
  already stops a run" rejection reasoning is sound and matches
  `autonomous-agent-skips-human-checks.md`.
- The check-order inside `_pass_states`: claim → own-step-skipped →
  own-step-not-done → cascade → evidence-read → `needs_person`-skip. Evidence
  is read before the `needs_person` skip is applied (confirmed by
  `test_evidence_counts_whichever_mode_is_on`), so a walkthrough someone
  finished still counts even with auto-approve back on — matches the record's
  stated ordering ("Purposely skipped? ... Already done? ... Needs human
  intervention?").
- `_outstanding_pass` only matches `state == "in_progress"`, so a
  `needs_person`-skipped pass (state `skipped`) is correctly never picked up as
  the blocking pass in the `build_report` path — this is what makes
  `report.attention is None` and `report.next_command != "/walk"` hold there.
- `STATUS_PAYLOAD_VERSION` bump 1.0 → 1.1, mirrored in `wfctl/contracts/
  status-payload.json`, and the new `needs_person` key added to both the dict
  literal in `build_report` and the JSON contract — checked they list the
  exact same key set.
- `read_auto_approve`'s conservative-on-failure default (absent/malformed file
  reads as `False`, never as granted) is unchanged and still governs both call
  sites — the bug above is a threading omission, not a fallback-safety issue.

## Readability

comments explaining *why this shape*, not what the line does — consistent with
`AGENTS.md`'s "Comments inform... they do not narrate" rule. The `_read_pass`

`docs/reference.md`'s new "Declaring your own passes" section is clear, has a
worked example matching the shipped `wfctl.json` declaration verbatim, and its
field table is accurate against `_declared.py`'s actual validation. The skill's
`SKILL.md` and its five reference files (`interrogation-lenses.md`,
`question-quality.md`, `artifact-contract.md`, `examples.md`, `source-map.md`)
are well organized, each with a single clear job, and the "explain, don't
reopen" framing is repeated consistently everywhere it matters so the skill
can't drift into re-litigating settled architecture decisions.

No readability issues found in the diff otherwise.

## Architecture

The three architecture records added (`plan-walkthrough-is-private.md`,
`autonomous-agent-skips-human-checks.md`, and the rejected
`design/autonomous-skip-is-a-claim.md`) are coherent with each other and with
the code: ownership question, rejected baseline, decision, and a `Verified`/
`Considered` trail that actually matches the line numbers and behavior in
`_pipeline.py` and `_declared.py` as shipped. The rejected design record is
correctly kept with `status: rejected` rather than deleted, which is the right
call for auditability.

The one architectural gap is the correctness finding above restated as a
boundary problem: `pipeline-state-is-one-payload` and
`autonomous-run-stop-condition.md` both assert that there is exactly one
inference (`build_report`) that every view renders. `next_cmd` calling
`_infer_steps` directly, separately from `build_report`, is a second inference
path that already required its own duplicate `auto_approve` read before this
PR — this PR's `needs_person` feature is the first case where that
duplication actually produces a different answer than the one true payload.
That the two paths could disagree was latent before; this diff is what makes
it observable. Worth a note in `autonomous-agent-skips-human-checks.md`'s
`Consequences` (or a follow-up issue) if `next_cmd` isn't fixed in this PR,
since the next reason added to `_pass_states` has the same chance of being
threaded through one call site and not the other.

`plan-walkthrough` shipping with no place in the default pipeline (opt-in via
`wfctl.json`) is a good fit for what the record argues: it's a personal check,
not a gate, and the built-in-step alternative is explicitly considered and
rejected in `plan-walkthrough-is-private.md` for sound reasons.

## Security

Checked the write paths the new skill and code introduce:

- `_declared.py`'s pass-name validation (`name != Path(name).name or name ==
  ".."`) already existed before this diff and is unaffected; `needs_person`
  adds no new user-controlled string that reaches a filesystem path.
- The skill's file writes (`artifact-contract.md`) are anchored to `$(wfctl
  state-dir)/walkthrough/` and `FEATURE_DIR`, both wfctl-resolved paths, not
  attacker- or model-controlled paths; the answers-file name is built from a
  fixed `<mode>-<timestamp>` pattern with `<mode>` constrained to `plan` or
  `change` by the skill's own step 2.
- No new shell-outs in the Python diff. The skill's own instructions to the
  agent (`sha256sum plan.md`, `git rev-parse HEAD`) are prose the agent
  executes as separate tool calls, not string-interpolated into a shell
  command the code builds — no injection surface added here.
- The privacy boundary the two architecture records exist to establish (answers
  stay on the plan owner's machine, never in the feature directory that gets
  committed/archived to `specs-trunk`) is enforced entirely by *instructions to
  the agent* in `SKILL.md`/`artifact-contract.md`, not by any code-level
  check — there is nothing in `wfctl` that would stop a future edit to the
  skill (or an agent improvising) from writing answers into `FEATURE_DIR`
  instead. That's consistent with wfctl's general model (skills are trusted
  prose, not sandboxed), so not a new class of risk this diff introduces, but
  it's worth naming: the privacy guarantee here is a convention enforced by two
  tests (`test_the_skill_writes_answers_outside_the_feature_directory`, which
  only checks that the contract file *mentions* `wfctl state-dir` and
  `walkthrough/`, not that nothing in the skill directs a write elsewhere) and
  the record's own prose, not by wfctl refusing the write.

No exploitable issue found; the one item above is a design note, not a
vulnerability.

## Performance

Nothing in this diff touches a hot path with new I/O or unbounded work.
`_pass_states`'s new branch is an `if` inside the same one-pass loop over a
step's declared passes it already ran; no new file reads or subprocess calls
beyond what a pass already made when read (`sub.reads(ev)`, unchanged). The
`needs_person` payload field is one more boolean per sub-step dict, no
measurable cost. No performance issues found.

## Test coverage note (not a blocking finding, folded in since it explains why correctness's finding wasn't caught)

`tests/test_pipeline_needs_person.py`'s nine tests are thorough for the
`build_report` path (skip, evidence-wins, claim-wins, mode-off recovery, the
payload key) but none of them invoke `wfctl next` — only `status --json` via
`build_report` directly. That's why the `next_cmd` gap shipped with green CI: a
test asserting `next-step.md`'s content (or `next_cmd`'s `auto`) for a
`needs_person` pass under auto-approve would have caught it, the same way
`test_check_config_reports_both_needs_person_mistakes` exists to catch
`check config` drift.

## Over-engineering metric

Surface added: 1 new field (`needs_person`) threaded through 3 layers
(`wfctl.json` → `_declared.py` → `_pipeline.py`) plus 1 new skill/command pair
and 3 new architecture records. Every layer the field passes through is
exercised by a real caller (`check config`, `status`, `resume`, the JSON
contract) — nothing here is speculative generality; the design explicitly
rejected broader mechanisms (`optional: true`, a new pipeline state, a
built-in step) in favor of the smallest addition that a real, named pass
(`plan-walkthrough`) actually needs. The one thing not fully wired is not
excess machinery — it's a wiring gap (`next_cmd`) in the mechanism that does
exist. Verdict on this axis: not over-engineered.

## Verdict: Request changes

The `wfctl next` / `build_report` divergence is a real, reproduced correctness
bug that defeats this PR's own stated guarantee on a documented, tested
command. Fix (thread `auto_approve` into `next_cmd`'s `_infer_steps` call,
plus a test pinning `next` and `status` to agree for a `needs_person` pass)
before merge. Everything else in the diff — the declaration validation, the
pipeline inference change as consumed by `build_report`, the skill content,
and the architecture records — is sound and well-tested.
