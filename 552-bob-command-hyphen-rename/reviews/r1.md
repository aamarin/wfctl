WARNING  wfctl/cli.py:L2985-2988, tests/test_install_skills.py:L617-621, docs/reference.md:L279, docs/architecture/mirror-supersedes-the-wrapper.md:L120. The stated reason for the change does not match Bob Shell's source. All four places say Bob "registers each file there as a skill, never as a slash command", the test docstring says a hyphen rename "would still reach no menu", and it says Bob "lists it beside the skill it points at". I read the installed Bob Shell (2.0.4 at `~/.volta/.../bobshell/dist/bob.js`; the commit cites 2.0.5, which I could not inspect). Here is what it does:
  - `CommandMigrator._loadLocalCommands` globs `{.bob,.agents,.claude}/**/commands/*.md`. It is not limited to `.bob/commands/`. `_writeSkills` then writes each file as `.bob/skills/<name>/SKILL.md` with `metadata.user-invocable: true`, and skips any name whose SKILL.md already exists. This runs from `BobUserConfig.initialize()` on startup.
  - `getWorkspaceCommands()` returns every skill with `userInvocable !== false` as a workspace command. Bob's own bundled create-skill guide says the same: `user-invocable: false` means "no `/` command", and `disable-model-invocation: true` means "runs only when the user types `/<skill-name>`". So a migrated command does become a `/name` command.
  - The wrappers stay dead for other reasons. A dotted name fails `isValidSkillName` (`^[a-z0-9]+(-[a-z0-9]+)*$`), and Bob skips the directory as invalid. A hyphenated name is skipped when the skill it points at already holds that name. And `findFiles` applies `.gitignore` exclusions by default (`respectGitIgnore: true`), which likely hides wfctl's gitignored installs from the migrator altogether. Empirically, pfms has a 2.x-era `.bob/commands/` and no migrated skill directories, which is consistent with that.

  Consequence: the conclusion holds, since the `.bob/commands/` copy is dead. But a false reason now sits in an architecture record and in the user reference. #552's actual complaint is only partly addressed, and this text tells the next reader it cannot be addressed. Pipeline steps with a same-named skill (`/speckit-plan` and the like) are reachable in Bob as skills. `speckit.decompose`, `speckit.brief` and `wfctl` have no same-named skill, so they have no route in Bob. Nor do the wrapper-only scan-file instructions in `speckit.analyze`/`speckit.clarify`, which AGENTS.md says live only in the wrapper. All of that was already broken before this change (the old copies were dotted, so invalid), so it is not a regression. But the text asserts it is impossible to fix, when a valid, non-colliding, non-ignored name would reach `/`.

  Fix: restate the reason in all four places. Something like: "Bob 2.x migrates command files into `.bob/skills/` rather than registering them as commands. A dotted name fails its skill-name rule, and a hyphenated one is skipped when the skill it points at already holds the name." Drop "would still reach no menu". Also file or keep open a follow-up for the wrappers that have no same-named skill, rather than closing #552 as fully resolved. One live check in a scratch repo (`bob` started with a non-ignored `.bob/commands/x-y.md`) would settle the 2.0.4/2.0.5 question.
