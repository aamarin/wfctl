## Findings

### WARNING — `wfctl/agents/commands/speckit.plan.md:12` — plan still cannot reach its own Write

`speckit-plan/SKILL.md:59` opens the workflow with:

> 1. **Setup**: Run `.specify/scripts/bash/setup-plan.sh --json` from repo root

The wrapper's grant is `Read Glob Write Bash(wfctl feature-paths*)`. There is no
`.specify/scripts` entry on it, and `setup-plan.sh` is granted nowhere in the
shipped tree. Every other step that calls a `.specify` script carries the grant
for it — tasks, implement, analyze, clarify and checklist all have
`Bash(.specify/scripts/bash/check-prerequisites.sh*)`. Plan is the only one that
calls a script it was never given.

So the unattended run this commit exists to fix still stops at plan, and it
stops *one tool call earlier than before* — at Outline step 1, before the
workflow ever reaches the Write that was added. The commit message's claim
("the command resolves, the workflow starts, and it stops one tool call later
with nobody there to answer") is accurate about the defect and unresolved for
one of the four steps it names.

Fix: add `Bash(.specify/scripts/bash/setup-plan.sh*)` to the same line the diff
already edits.

### WARNING — `wfctl/agents/commands/speckit.implement.md:4` — the sentinel is granted, the evidence is not

`speckit-implement/SKILL.md` step 9b writes the sentinel, and the skill's own
text about it reads: **"This sentinel is not evidence."** Step 9c then runs
`wfctl verify`, and that is what `_predicates.implement` reads —
`ev.verification` is the only thing that moves the step from `in_progress` to
`done` once the checkboxes close. `wfctl-runs-the-verification` is an accepted
record saying exactly that: "the agent never certifies its own completion."

The wrapper grants no `Bash(wfctl verify*)`. The diff therefore pre-approves the
write of the artifact the skill calls non-evidence and leaves unapproved the
command that produces the evidence. Unattended, implement ticks every box,
writes the sentinel, and halts on a permission prompt at the one step that
decides whether the work is actually done.

Fix: add `Bash(wfctl verify*)`.

(Separate and not a finding: implement also executes the project's tasks, which
means running arbitrary build and test commands that no grant can enumerate in
advance. Implement is never going to be prompt-free. That does not weaken the
two grants above — `wfctl verify` is a fixed, enumerable command, and it is the
one the predicate reads.)

### WARNING — `wfctl/agents/commands/speckit.specify.md:12` — no `Bash(mkdir*)`

`speckit-specify/SKILL.md` step 3 is a bash block ending

### NIT — the `Edit`-for-`implement` argument is not obviously narrower than plan's case

The commit's stated reason for `Edit` on implement is that `tasks.md` already
exists and rewriting it whole is the operation most likely to drop what was
there. `plan.md` has the same property and the repo says so in
`wfctl/_predicates.py:1001`: `setup-plan.sh` runs `cp plan-template.md plan.md`,
so the file exists, carries every required heading, and the plan step fills it
in and then re-evaluates the Constitution Check section after Phase 1.
`required-sections-are-wfctls` plus `_REQUIRED_PLAN_SECTIONS` make a dropped
heading a step that reads `in_progress` with no obvious cause.

I think implement's case is still genuinely stronger — the implement turn ticks
boxes in a file a *different* step authored and may never have read whole,
whereas the plan turn composes plan.md's content itself in the same turn. That
is a real distinction and a fine reason to grant `Edit` to one and not the
other. It just isn't written down anywhere, and the docstring is where the next
editor will look for it. Either grant `Edit` to plan or add the one sentence
that says why implement is the only file-already-exists case.

### NIT — `tests/test_skill_cross_references.py:333` — bare `next()` turns a missing key into `StopIteration`

`next(ln for ln in ... if ln.startswith("allowed-tools:"))` has no default. A
step wrapper that omits the key entirely errors with an unadorned
`StopIteration` rather than failing with the step's name. I confirmed this
against a mutated copy of the agents tree in the scratchpad:

```

implement loses Edit: ['specify', 'implement (Edit)']
```

Nothing in the suite guarantees a step wrapper carries the key — the
`assert "allowed-tools" in front` at `:588` is about `start-session`'s SKILL.md,
not about step wrappers. So this is reachable, and by exactly the omission the
test was written to catch a variant of: a ninth step authored without thinking
about grants.

Fix folds into the next finding.

## The panel's specific questions

**Is each widening the minimum needed?** Yes, in the sense that matters: `Write`
is the smallest unit the harness offers. There is no path-scoped form of it the
way there is for `Bash(...)`, so "specify may write `spec.md`" is not
expressible — the grant is repo-wide file write, pre-approved, for an
unattended turn. That cost is real and it is unavoidable at this granularity;
brainstorm and decompose already pay it. Worth saying out loud only so the
framing stays honest: `Edit` on implement does not *narrow* `Write`, it is
additive, and implement now holds both. That is right for its workflow, but the
least-privilege story here is about capability coverage, not restriction.

**Is anything granted that the step's workflow does not use?** No. I traced all
four. Specify writes `spec.md` and `checklists/requirements.md`; plan writes
`research.md`, `data-model.md`, `contracts/`, `quickstart.md`; tasks writes
`tasks.md`; implement writes source files and the sentinel, and edits `tasks.md`
to tick boxes. Every added tool is exercised. No over-grant.

**Is anything still missing?** Yes — three things, all above: plan's
`setup-plan.sh`, implement's `wfctl verify`, specify's `mkdir`.

**Does the new test assert the right invariant, and does it fail when it
should?** The invariant is right and it is the right shape — walking `_STEPS`
rather than naming four files is what makes a ninth step fail here instead of
in production, and that is `a-rule-is-expressed-as-a-check` applied correctly.
It does fail when it should; I proved both arms (Write dropped from specify,
Edit dropped from implement) against a mutated tree. The one gap in its failure
behavior is the `StopIteration` case above.

What the test does *not* assert, and should not be read as asserting: that the
grant works. It proves the substring is present in a file wfctl ships. Which
brings me to the verification gap.

## Verification gap

`wfctl/agents/` changed, so CLAUDE.md's rule applies: "A change to anything
under `wfctl/agents/` is not verified by the test suite alone: run
`uv run wfctl install-skills` and exercise the thing you changed." That step is
unusually load-bearing for this particular diff, because the entire change *is*
a runtime permission grant — the property under test can only be observed by
running one of the four commands and watching whether the write prompts. The
green suite is evidence that the string ships, and nothing more.

One thing I could not verify from anything in the repo, flagged for the author
rather than as a finding: the grant is written space-separated
(`Read Glob Write Bash(...)`) with Bash patterns in the form
`Bash(wfctl status*)`. If the host parses `allowed-tools` as a comma-separated
list, the whole value is one unmatched entry. This is format-wide and predates
this commit by a long way — it cannot block this diff, and #240's decompose
widening presumably confirmed the format works. Exercising specify once after
`install-skills` settles it either way.
