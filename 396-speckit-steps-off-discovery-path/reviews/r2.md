## Findings

### BLOCKER — `wfctl/cli.py:L2762-2810`, `wfctl/agents/skills/speckit-{clarify,analyze}/SKILL.md:L4`

Mirroring `speckit-clarify` and `speckit-analyze` creates a route on which no scan file is ever
written, and the suite guarantees it cannot be fixed inside the SKILL.md.

The commit's own premise is that a mirrored skill invoked by name never reads its wrapper. The scan
instruction lives only in the wrapper — `speckit.clarify.md:L177` and `speckit.analyze.md:L303`,
both `## Write the scan file` — and `tests/test_scan_files.py:L233-245`
(`test_no_review_skill_carries_the_instruction`) asserts that `"## Write the scan file"` is *not* in
either SKILL.md, on `vendor-upstream-skills`' "prefer layering to editing". So the two halves are now
in direct conflict: this commit makes the SKILL.md the reachable entrance, and a test in the same
suite keeps the instruction out of it.

Nothing downstream notices. `_predicates.analyze` reads `checklists/analysis-report.md` in
`FEATURE_DIR`; `_predicates.clarify` reads `## Clarifications` in `spec.md`. Neither reads the scan
file. `FEATURE_DIR` resolves outside the working tree, which is the whole reason `scans/` exists —
CLAUDE.md's sentence is "a scan that found six problems and one that never ran are the same pull
request". After this commit an unattended run produces exactly that, silently.

The copied grant is the tell. `speckit-clarify/SKILL.md` and `speckit-analyze/SKILL.md` now carry
`Write Edit … Bash(wfctl arch-root*) Bash(wfctl arch check*) Bash(mkdir*) Bash(git add*)
Bash(git commit*)` — which is, name for name, the list
`test_each_review_wrapper_allows_the_commands_the_scan_file_needs` (`tests/test_scan_files.py:L259`)
requires *for that instruction*. The permission shipped; the instruction did not.

The same defect in lesser degree covers three more steps, and one of them says so in its own text:

| Step | Wrapper-only section | In the SKILL.md? |
| --- | --- | --- |
| `plan` | `## Read this feature's design records` (`speckit.plan.md:L24-38`) | no |
| `tasks` | `## Read this feature's design records` (`speckit.tasks.md:L23-36`) | no |
| `implement` | `## Read this feature's design records`, `## Report a host refusal` (`speckit.implement.md:L22-57`) | no — "Here rather than in `speckit-implement/SKILL.md` (#364)" |
| `decompose` | "If the user provides a custom grouping instruction … honour it" | no |

`design-md-indexes-the-records` (proposed) is the record those three sections implement. `wfctl
blocked` is what keeps `implement` from reporting done over a write the host refused.

The repo already holds this rule and already has the worked example.
`tests/test_install_skills.py:L368-400`, `test_no_suppressed_wrapper_carries_more_than_a_pointer`:
"A wrapper that is suppressed must hold nothing its skill does not… `start-session.md` was the other,
and #204 mirrored it — by moving the key onto the SKILL.md first, which is what this test asks for.
It is the worked example of paying the price rather than exempting the name." This commit moved the
key and left the instructions. The seven speckit wrappers escape that test only because
`speckit.analyze` and `speckit-analyze` differ by a dot — a naming coincidence, not an argument, and
the same dot the commit relies on to keep the typed route alive.

Three shapes of fix, in the order I'd weigh them:

- **A.** Each mirrored SKILL.md names its wrapper's repo-policy sections by path, the way the
  wrappers already name skills. A pointer is not the in-place edit `vendor-upstream-skills` is
  written against, and the commit's own argument applies: a pull that drops the pointer fails a test
  rather than passing silently. Needs that test.
- **B.** Move the wrapper-only sections into wfctl-owned layering skills both entrances name. This is
  literally what `vendor-upstream-skills` asks for — "add a skill that layers over it" — and
  `writing-a-scan-file` and `reading-design-records` already exist as half of it.
- **C.** Drop `speckit-clarify` and `speckit-analyze` from `_MIRRORED_SKILLS` and resolve their
  `next_command` some other way. Narrowest, and it leaves #396 half-open on exactly the two review
  steps.

### BLOCKER — four of the seven copied grants cannot perform their step's core write

On the semantics this commit asserts and the repo states in two other places (`allowed-tools:` is a
ceiling on the whole turn — `tests/test_scan_files.py:L261`,
`tests/test_unattended_pause_rules.py:L268`, `docs/architecture/scans/352-analyze.md:L165`):

| Mirrored skill | Grant now on its SKILL.md | What its own body does |
| --- | --- | --- |
| `speckit-specify` | `Read Glob Bash(wfctl status*) Bash(wfctl issue view*) Bash(git branch --show-current*)` | step 6: "Write the specification to SPEC_FILE" |
| `speckit-plan` | `Read Glob Bash(wfctl feature-paths*)` | Phase 0/1: generate `research.md`, `data-model.md`, `contracts/`, `quickstart.md` |
| `speckit-tasks` | `Read Glob Bash(.specify/…check-prerequisites.sh*) Bash(wfctl feature-paths*)` | step 4: "Generate tasks.md" |
| `speckit-implement` | `Read Glob Bash(…) Bash(git rev-parse*) Bash(wfctl feature-paths*) Bash(wfctl arch context*) Bash(wfctl arch-root*) Bash(wfctl blocked*)` | step 9b writes the sentinel; marking a task done edits `tasks.md`, which `_predicates.implement` reads |

None of the four carries `Write` or `Edit`. So `/speckit.specify` — the command in the commit
message's first line, the one #396 is named for — now resolves to a skill that starts the workflow
and is refused at step 6. That is the commit's own second paragraph, shipped: "the name would
resolve, the workflow would start, and the first `Write` would be refused. That is further into a run
before stopping than no route at all."

The commit notices the narrowest case and files it as a curiosity: "The grant nobody would guess is
`speckit-implement`'s: it is the narrowest of the seven, with no `Write` and no `git commit` at all."
It is not a curiosity. It is the step that writes code.

This is pre-existing on the typed route — the wrappers have the same grants — so the commit does not
create the defect. What it does is inherit it onto the route #396 exists to open, which means the
issue's stated outcome (an unattended run advances past brainstorm) is not delivered and `Closes
#396` overstates. The parity test, equality rather than subset, now also forbids repairing the skill
alone; both surfaces must widen together. That is the right shape and I would not change it — but it
is work this commit leaves undone and does not file.

CLAUDE.md is explicit that the suite would not catch this: "A change to anything under
`wfctl/agents/` is not verified by the test suite alone: run `uv run wfctl install-skills` and
exercise the thing you changed." Nothing in the diff or the message shows that was done, and it is
what would have surfaced this on the first step.

### WARNING — `tests/test_skill_cross_references.py:L390-402`: parity passes on `None == None`

`grant()` returns `None` when no `allowed-tools:` line is present, and the comparison is
`if wrapper != mirrored`. A step whose wrapper *and* skill both lack the grant is green. That is the
silent success the test was written against, and it is the symmetric-deletion hole that
`test_brainstorm_allows_the_commands_its_records_need` names in its own docstring — the same commit
having just removed the parity assertion from that test, leaving brainstorm's by-name pins as the
only defence and none at all for the other six. `test_decompose_allows_the_commands_its_notify_gate_needs`
covers decompose; specify, clarify, plan, tasks, analyze and implement have nothing.

Fix: fail when either side is `None`, not only when they differ —
`if wrapper != mirrored or mirrored is None: drifted[skill] = {...}`.

### WARNING — `tests/test_skill_cross_references.py:L312-334`: the third invariant was left pinned

`test_brainstorm_is_findable_from_the_command_status_hands_out` still names brainstorm. Its own
docstring says carrying the literal command in the description "is what makes it the obvious hit",
and that rewording it leaves "an agent resolving `next_command` … back to finding nothing — #361 with
every other guard in this file still passing." None of the seven new descriptions carries its command
(`speckit-specify`: "Create or update the feature specification from a natural language feature
description…"). The commit generalises two of the three walk-of-`_STEPS` invariants in this file and
leaves the third — which is precisely the critique it levels at the mirror test in its own message,
applied to the function three above the one it rewrote.

Either generalise it, or write down why exact-name resolution makes the description route moot for
these seven and brainstorm's pin is now redundant. One of those two, not silence.

### WARNING — `wfctl/cli.py`, new comment block: "Five of the seven" is six

`vendor-upstream-skills`' table lists `speckit-analyze`, `speckit-clarify`, `speckit-implement`,
`speckit-plan`, `speckit-specify` and `speckit-tasks` as `github/spec-kit`-derived. Of the seven
skills this commit adds, only `speckit-delivery-plan` is wfctl's own. So six, not five — in both the
comment and the commit message. The count is the load-bearing part of that paragraph, since it is
what scopes the `vendor-upstream-skills` argument to a subset, and a comment that miscounts the
subset teaches the next reader that one of the six is safe to edit freely.

### WARNING — capability widening on the two skills with no instruction behind it

All seven wrappers carry `disable-model-invocation: true`, the key
`test_no_suppressed_wrapper_carries_more_than_a_pointer` glosses as "one to say a human types it".
The mirror removes that for all seven on the Claude layer. That is the intent of #396 and I do not
object to it.

What the risk paragraph in the new block weighs is only `Bash(wfctl issue create*)`, and it weighs it
correctly: `wfctl issue create` refuses on its own unless the branch holds notify authority, and the
gate does not ask which entrance called it. What it does not weigh is `Bash(git add*)` and
`Bash(git commit*)`, which `speckit-analyze` and `speckit-clarify` now hand to a model-initiated
turn. Nothing gates `git commit`. And per the first BLOCKER, those two skills contain no instruction
that uses them — the grants exist for a section the SKILL.md is forbidden to carry. Whichever way
that BLOCKER is resolved decides this too: the instruction arrives, or those three grants come off
both surfaces.

### NIT — `tests/test_skill_cross_references.py:L396`: unguarded wrapper read

`grant(_AGENTS / "commands" / f"{spec.command.lstrip('/')}.md")` raises `FileNotFoundError` when a
step has no wrapper, instead of the assertion message the test composed.
`test_every_pipeline_step_reaches_a_skill_an_agent_can_invoke` guards this with `wrapper.exists()`
three functions above. Same walk, same set, two behaviours on the same missing file.

### NIT — `tests/test_skill_cross_references.py:L390`: frontmatter parsed by `split("---")`

`wfctl._arch._frontmatter` already parses frontmatter and `tests/test_install_skills.py:L392` imports
it for this exact job. `split("---")[1]` is this module's existing idiom, so it is consistent rather
than wrong — flagging it as the cheaper reuse, author's call.

## Over-engineering

`net: −0 lines possible. Lean already.`

The diff is mostly comment and docstring, which is this repo's declared style, and the rationale is
dense rather than narrative. `_skill_for` has three callers and earns its extraction. Nothing here is
speculative flexibility, a one-implementation abstraction, or a hand-rolled stdlib function. The
honest note is that the right repair for the first BLOCKER adds lines rather than removing them.

## Verdict

**Request changes** (2 blockers).

The direction is right and the mechanism is the correct one — membership in `_MIRRORED_SKILLS` plus a
walk of `_STEPS` is how this invariant should have been written in #361. What is missing is the other
half of #204's price: the instructions that live only in the wrappers, and grants that let four of
the seven steps actually write the artifact they exist to produce. Until those land, the change moves
the stopping point from "specify cannot be found" to "specify is found and cannot write", and drops
the clarify and analyze scan files off the automated path with nothing to notice.
