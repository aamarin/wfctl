## Findings

WARNING  wfctl/cli.py:L3738-3750 — a repo-supplied `source` steers an install
that `/start-session` runs unattended → treat a recorded source inside the repo
as untrusted (skip the `--from` remedy, or make that layer a warning instead of a
finding), and say so in AGENTS.md *Safety* and the record's *Consequences*.

`.wf-skills-manifest.json` is gitignored *by convention*, not by any check —
nothing stops a repo from committing one. Before this change a hostile manifest
could make `doctor` print at most `update: wfctl install-skills [--agent X]`,
which copies from the trusted wheel. Now the same file chooses the bytes: set
`content_hash` to any wrong value plus `"source": "<repo>/vendor-bundle"`, and
`doctor` prints `update: wfctl install-skills --agent claude --from
<repo>/vendor-bundle`. The shipped `start-session` skill (step 2, and the
paragraph this diff *adds*) instructs the agent to run exactly that line, with
`--yes`, before it reports to the user. What lands is `.agents/skills/*` — files
whose whole purpose is to instruct the agent — and `.specify/scripts/*`, which
speckit commands execute. This is a new path from repo content to executed
content, and it is the one path in the design that is explicitly *not* read by a
human first. Narrow (needs a cloned hostile repo) and adjacent to a hazard
AGENTS.md already names for hooks — hence WARNING, not BLOCKER — but it is new
with this diff and unmentioned in the record's *Consequences*, which is where a
trust boundary this feature opens belongs.

WARNING  wfctl/cli.py:L3747, L3731, L3738, L3722, L2314, L1868, L1832 — paths
interpolated into rich markup unescaped; a bracketed directory name is silently
deleted from a command line meant to be executed → `from rich.markup import
escape` and wrap `recorded_source` / `source` / `prior_source`, exactly as
`_check_arch_records` (L3417-3425) and the spec-root block (L1948-1960) already
do for the same reason.

Demonstrated, not theoretical:

```
$ console.print('    update: wfctl install-skills --from /Users/x/[old]/wfctl')
    update: wfctl install-skills --from /Users/x//wfctl
```

`[old]` parses as a style tag and vanishes. The remedy line is the one string in
this feature whose contract is "running it repairs the install" (FR-008, SC-003),
and `/start-session` runs it unattended — a mangled path either fails the repair
or, if `/Users/x/wfctl` happens to exist, installs from a bundle nobody named,
which is the failure mode #146 opens with. The same swallow hits `✓ Installed
from …` (L2314), where the line's stated purpose in its own comment is that the
reader can match it against what they typed. The codebase has already reached
this conclusion twice; the new sites did not inherit it.

WARNING  wfctl/cli.py:L1861-1862 — the comment's example is false: an agent
install *does* rewrite base's record → "…a run without `--agent` leaves an agent
layer's record, and its source with it."

"Scoped to the layers this run rewrites — an agent install leaves base's record,
and its source with it." `layered` (L1994-1998) always includes `_BASE_TARGETS`,
so `items` always contains `base` and L2141-2148 always rewrites it. The branch's
own test proves it: `test_a_named_source_is_recorded_absolute_and_a_default_records_nothing`
runs `--agent claude` and asserts `source` on **both** `base` and `claude`. What
the `{_BASE_LAYER, agent}` scoping actually excludes is *other* agent layers —
the inverse of what the comment says. The code is right; the sentence would send
the next reader of this block the wrong way about the one thing it exists to
explain, and AGENTS.md is explicit that comments here carry rationale rather than
narration.

WARNING  wfctl/cli.py:L2002-2011 — the "broken wheel" message and its comment are
now reachable from a partial `--from` source and misattribute it → branch the
wording on whether `source` was named ("missing from the source you named
(<path>)" vs. today's text), or state in the comment that a named source can
reach it too.

`content_hash` and `resolve_root` both accept a root with *one* tree ("a partial
bundle is a real state during a re-sync"), so `--from` a directory holding
`agents/` but not `specify/` passes validation and then prints "Expected

the bundle ships with the package, so a missing source means the wheel lost files
rather than that the user asked for something that does not exist." That premise
is exactly what `--from` removes, and the message sends a user to reinstall
wfctl for a defect in the path they typed.

## Passes that found nothing (what was checked)

**Correctness.** Traced `resolve_root` → `install_skills_cmd` → manifest write →
`doctor_cmd` cold. The four contract states map one-to-one onto the branches at
L3711-3751, exit codes match the table (`source changed` → 1; `source is gone`
leaves `exit_code` alone), and the unreachable case `continue`s before touching
it. Ordering is right where it matters: `resolve_root` runs before `get_repo_root`
and before any copy, so a bad `--from` leaves the repo with no `.agents/` and no
manifest (asserted). `source` is written only inside the `items` loop, so a layer
this run did not install keeps its own record — which is what makes the mixed
base-default/claude-named case in the remedy test come out right. Absence-means-
default needs no migration and I could not construct a pre-existing manifest that
reads wrong under it. FR-012 verified by reading the prune diff: it reads
`prior_layer_items` against the plan, and the plan is built from `bundle_root`,
so it follows the named source with no code — and the branch added a test that
pins that, which is the right response to a requirement that holds by accident.
`digest_of`'s cache is keyed on the resolved root, so two layers from one source
walk it once and a source equal to the wheel at most walks twice. No off-by-one,
no swallowed exception (both `FileNotFoundError` catches re-raise or report), no
state left half-written on any failure path I could find.

**Architecture.** Fits `layer-model` (source changes where trees are *read from*,
never what is authoritative), `session-state-is-re-derived` (the manifest stores
only the caller's choice at copy time — the one thing re-derivation provably
cannot reach, and the record's *Owns truth* argues that in full: two installs
from different sources can be byte-identical), and `install-modes` (orthogonal).
No new module, no new dependency, no abstraction with one implementation. The
public `resolve_root` is the correct call under the proposed
`the-underscore-is-the-module-contract`, and the commit explains why. `_bundle`
still has no typer/rich import; the dependency direction `cli → _bundle` is
unchanged and acyclic.

**Readability.** Names say what they hold (`bundle_root`, `recorded_source`,
`source_hash`, `digest_of`); no nesting past two levels; no function grew past
the split threshold; the new comments explain *why this shape* rather than what
the line does — except the one flagged above.

**Performance.** The only new cost is `doctor` hashing one tree per *distinct*
recorded source instead of exactly one. Bounded by the number of layers (two or
three in practice), memoized, over a few hundred small files at session start.
Nothing added to the install hot path.

**Over-engineering.** Nothing speculative: one flag, one optional key, one
function, three branches inside an existing loop. No dead flexibility, no config
nobody sets. The only shrinks available are the two NITs above.

**Tests.** Read before the implementation. 13 new tests; names are sentences and
docstrings name the failure each exists to catch, per convention. They assert
behavior, not implementation — the headline test asserts installed *content*
rather than the summary line, and says why. Coverage matches the spec's stated
strategy: resolution (given/nested/precedence/neither/absolute), the record
(absolute, per-layer, absence on default), and all four `doctor` states including
that the remedy is right for a named layer *and* a default layer in the same run.
The relative-path test changes directory between install and check, which is the
only shape that actually reaches FR-004. Gaps, none of them blocking: no test
that `✓ Installed from` prints the path *as typed* (a deliberate decision with a
comment defending it), none for `--tracker github --from`, and none for the
running-tool-as-named-source edge case — but that one has no agreed behavior yet
(NIT above).
