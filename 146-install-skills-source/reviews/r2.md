## Pass 1 — Correctness (adversarial)

Traced `resolve_root`, `content_hash`, `install_skills_cmd`'s plan/copy/record
path, `_layer_keys`, `_agent_flag`, `_recorded_items`, and `doctor_cmd`'s loop.
Exercised the CLI end-to-end in throwaway repos (scratchpad, not this tree).

**Verified working:**

- FR-001/002/011 — `--from` copies from the named root; a bare run is unchanged;
  a checkout root probes one level in. `bundle_root` threads through all four
  reads (`layered` src, tracker src, `content_hash`, the missing-tree message);
  `grep BUNDLE_ROOT` shows the only remaining uses are `install-config` (L2636,
  correctly out of scope per the contract) and doctor's default digest (L3689).
- FR-003/014 — the key is written only when `source is not None` (L2147) and the
  layer entry is replaced wholesale, so a bare install drops it; layers this run
  does not rewrite keep theirs. Confirmed by
  `test_a_named_source_is_recorded_absolute_and_a_default_records_nothing`.
- FR-004 — `resolve_root` returns `.resolve()`; `test_a_relative_source_still_
  resolves_from_a_different_directory` is the right test (asserting absoluteness
  alone would not have caught storing-as-typed).
- FR-006/007/009 — doctor's three new branches are correct and the unreachable
  branch does not touch `exit_code`. Verified empirically: a moved source gives
  `⚠ … source is gone, can't check` and exit 0.
- FR-010 — the resolve happens at L1823, before `get_repo_root()` and long before
  any write; a bad `--from` leaves no `.agents/` and no manifest. Confirmed.
- FR-012 — `--prune` reads the plan, not the bundle; the new test pins that,
  which is worth more than the code change it guards (there is none).
- FR-015 — the notice is outside every `--yes` guard and is scoped to
  `{_BASE_LAYER, agent} & layers`, which is the right set.

**Defect W1 (confirmed by running it).** With a source path containing a space:

```
⬆ base: source changed since install — …/scratchpad/my src
    update: wfctl install-skills --from …/scratchpad/my src
```

Running that verbatim: `Error: Got unexpected extra argument(s) (src)`. The
justification for the whole `--from`-in-the-remedy design is that `/start-session`
runs the printed line unattended; for any path with a space it cannot. Fails
loudly rather than destructively, hence WARNING not BLOCKER. Fix is one call:
`shlex.quote(recorded_source)` at L3748.

**Defect W2 (confirmed by running it).** `resolve_root` accepts a root holding
*either* tree, so a directory with only `agents/` is a valid source. Installing
from one prints, three times:

```
⚠ Expected 'agents/commands' missing from this wfctl install (…/scratchpad/src) — skipping
```

then `✓ Installed from …` and success. Two problems. The message tells the user
their *wfctl install* is broken when the fault is in the path they typed, and the
comment above it at L2001 states the invariant that made that wording correct —
"Reachable only from a broken install — the bundle ships with the package" —
which `--from` has just falsified. AGENTS.md is explicit that comments carry
rationale; this one now carries a false one. Under `--prune --yes` (the shape
`/start-session` runs) a partially-populated source will also delete the recorded
paths it does not ship, while blaming the wheel. Same class, lower stakes: the
`--tracker github` fallback at L2045 still reports `_wfctl_version()` even though
`tsrc` now comes from `bundle_root` (L2036).

**Defect W4 (spec deviation).** spec.md Edge Cases: *"The named source is the
running tool. Naming the same location the default would have used must behave
exactly as the default does, including its output."* Not implemented — L2147
branches on `source is not None`, not on whether the root is the running bundle,
so `--from <BUNDLE_ROOT>` yields `✓ base: skills current (from /…/site-packages/
wfctl)` instead of `(wfctl 0.16.0)`, and after a `uv tool upgrade` reports
`source changed since install` instead of `skills stale — installed by wfctl X,
running Y`. There is a real counter-argument (a consumer doing `uv run --project
<checkout> wfctl install-skills --from <checkout>`, quickstart step 8, *wants* the
record kept), so this may be a spec amendment rather than a code fix — but it is
currently an unimplemented, unremarked requirement, which is the thing to close.

**Checked and clean:**

- The `⚠ installed before content hashing` branch runs before the source branch,
  so a pre-hashing record is not misread as a source state.
- `digests` keyed on `Path` — `_bundle.BUNDLE_ROOT` is not `.resolve()`d while
  recorded sources are, so a symlinked wheel path hashes twice. Correctness
  unaffected; not worth a finding.
- Legacy `none` layer key: `rewritten` would include it, but a pre-layer-split
  manifest cannot carry a `source` key, so the spurious notice is unreachable.
- Path traversal via a malicious source: `dest = dst / item.name`, and `item.name`
  cannot be `..`. Clean.

## Pass 2 — Security

`--from` is the trust-boundary change. Before it, `install-skills` could only copy
files that were already installed on the machine as part of wfctl; after it, it
copies from any directory the caller names — including `specify/scripts/*`, which
land in `.specify/scripts/` and are executed by the pipeline. The realistic
scenario is the one the spec is written around: "install the skills from this PR
so you can try them." AGENTS.md already has a Safety paragraph for the adjacent
case ("Hooks seeded into a repo execute shell commands … read them before running
an unfamiliar one"); the analogous sentence for `--from` is missing from the help
text (L1801) and from the docs. Fix is documentation, not code — hence WARNING,
not BLOCKER.

No secrets, no injection surface, no network. The recorded source is a path
written into a gitignored file, and `_recorded_path` (L1194) still guards every
delete against an absolute or `..`-bearing manifest row. Nothing in the diff
reaches it.

## Pass 5 — Performance

`doctor` now hashes up to one tree per distinct recorded source instead of exactly
one. The cache is keyed correctly and the common case is one entry; the worst
realistic case is two. Each walk is a few hundred small files at session start.
`content_hash` reads whole files into memory one at a time — unchanged, and the
bundle is small. Nothing else in the diff runs in a loop over I/O. No finding.

## Pass 6 — Over-engineering
