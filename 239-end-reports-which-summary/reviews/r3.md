### WARNING — `wfctl/agents/skills/end-session/SKILL.md:67-68`

> The state dir is per branch, so this is the normal case on a long-lived branch
> like `main` **and never happens in a fresh worktree.**

It happens in a fresh worktree on the repo's own documented path for making one.
`wfctl/agents/skills/worktree-handoff/SKILL.md:122` is:

```bash
wm add <branch> --background --prompt-file "$HANDOFF" &&
  cp "$HANDOFF" "$(wfctl state-dir --branch <branch>)/session-summary.md"
```

So the branch has a `session-summary.md` before its first `wfctl start`, and the
first `end` in that worktree prints the ⚠ line. This is not a corner the review
found — it is the premise of the change: `wfctl/_session.py:101` cites it as why
mtime cannot discriminate, and `tests/test_end_reports_which_summary.py:95`
(`test_a_handoff_written_before_the_first_session_is_not_called_stale`) exists
for no other reason. The sentence tells the worktree agent holding a handoff
that the line it is looking at cannot occur.

Fix: `…the normal case on a long-lived branch like `main`, and it also happens on
the first `end` in a worktree whose handoff `worktree-handoff` copied in.`

### WARNING — `wfctl/agents/skills/end-session/SKILL.md:70-73`

> Read it before step 4 — the `**Step**` / `**Boundary**` / `**Tree**` lines in it

Two sentences earlier the same paragraph correctly says the kept file is "either

### WARNING — `wfctl/agents/skills/end-session/SKILL.md:79-84`

Step 3 now says to *replace* three lines in the kept case. Step 4 — the block an
agent actually copies from — was not touched and still says the opposite:

```markdown
# Session Summary: {YYYY-MM-DD} — {branch}

**End time:** {timestamp from step 1}
**Step**: {left as `wfctl end` wrote it}
**Boundary**: {left as `wfctl end` wrote it}

```

In the kept case `wfctl end` wrote none of them. An agent that reads step 4
literally leaves the previous writer's readings standing, which is the failure
#239 reports. And neither step 3 nor step 4 mentions the two fields the issue
actually named — the `# Session Summary: {YYYY-MM-DD}` header and `**End**` —
"twice a session on `main` wrote by hand over a file **headed with the previous
day's date**". The new guidance corrects three lines and leaves the dateline that
started this untouched.

I read the "the summary template is out of scope; `end-session` owns it"
constraint as scoping the *scaffold `_render_session_summary` writes*. This diff
chose to add per-line editing instructions to `end-session`, which is what opens
this: either cover the header and `**End**` too, or drop the "replace them"
clause and say only "the readings in a kept file are not this session's".

Fix: in step 4, `**Step**: {this session's reading — `wfctl end` wrote it only on
a run that printed no ⚠ kept line}` (and likewise for the two below it), plus a
line naming the date header.

### WARNING — `wfctl/cli.py:408`

```python
mtime = datetime.fromtimestamp(summary_path.stat().st_mtime)
…
f"last modified {mtime:%Y-%m-%d %H:%M}."
```

Naive local time, with no zone marker. Every other timestamp wfctl writes or
prints is UTC with a `Z` — `_session.py:32`, `_io.py:52`, `_verify.py:174`,
`_archive.py:149` — including the `**End**:` line and the
`# Session Summary: YYYY-MM-DD` header *inside the file this line points at*.
West of UTC after ~17:00 local the printed date and the file's own header date
differ by a calendar day, and the comparison #239 asks the reader to make
("headed with the previous day's date") is exactly that one. Anywhere east of
UTC the same mismatch appears in the morning.

Fix: `datetime.fromtimestamp(summary_path.stat().st_mtime, tz=timezone.utc)` and
render `%Y-%m-%dT%H:%MZ`, matching the file it describes. If local time is
deliberate for a human reader, say the zone (`%Z`) — an unlabelled wall clock
next to a UTC file is the one combination that cannot be reconciled by eye.

### WARNING — `tests/test_end_reports_which_summary.py:72`

`assert "last modified" in output` is the whole assertion on the mtime. A line
that printed a hardcoded date, `datetime.now()`, or another file's mtime passes
this suite. The test's own docstring says the mtime "is the one thing that lets
the reader decide whether the file belongs to this session's work" — that claim
is untested. It is also why the local-vs-UTC question above went unnoticed: no
test renders a known instant.

Fix: `os.utime(path, (1757110440, 1757110440))` before the second `end`, then
assert the exact rendered substring. That pins the format, the zone, and that
the timestamp comes from *this* file, in one line.
