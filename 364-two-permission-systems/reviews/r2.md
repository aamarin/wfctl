## Findings

### 1. [High] `wfctl next` never applies the block hold — the file an agent actually reads ignores it

- **Where**: `wfctl/cli.py:690-752` (`next_cmd`), committed HEAD.
- **What**: `build_report` (used by `status` and `resume`) calls
  `_apply_block_hold` after `_infer_steps`, so a standing block overrides a
  step's own reading there. `next_cmd` does not — it calls `_infer_steps`
  directly, computes `step_name` from `_current_step_name(steps)`, and never
  calls `_apply_block_hold` or `build_report`. Confirmed via
  `git diff main...HEAD -- wfctl/cli.py`: no `_apply_block_hold` reference
  appears anywhere in the diff, and `git show HEAD:wfctl/cli.py` shows
  `next_cmd`'s import list lacks it.
- **Why it matters**: `next_cmd` writes `next-step.md` and prints "→ Next
  step: …" — per the code's own comment two lines above (`# this is the file
  an agent acts on`), this is the file an unattended agent reads, not
  `status`. So: an agent files `wfctl blocked push --reason "..."` against
  `decompose` (already `done` in its own artifacts); `wfctl status --json`
  correctly reports `decompose` held at `in_progress`, but `wfctl next` still
  reads `decompose` as `done`, advances to whatever step comes after it, and
  writes that step's command to `next-step.md` — sending the agent straight
  past the hold. This is the exact disagreement the plan calls out as the
  thing FR-016's asymmetry depends on *not* existing ("`status` showing the
  hold while `next` sends the agent to re-run the refused step is the
  disagreement FR-016's asymmetry depends on not existing" — language that
  appears verbatim in the *uncommitted* working-tree fix's new comment,
  confirming the implementer already identified this after committing).
- **Test gap**: The committed `test_the_next_action_for_a_held_step_is_the_steps_own_command`
  only exercises `status --json`'s `next_command` field (built from
  `build_report`), never `wfctl next` itself. No committed test invokes the
  `next` command with a standing block in place.
- **Confidence**: verified by direct source inspection of `git show
  HEAD:wfctl/cli.py`; not a guess.

### 2. [High] `wfctl blocked`'s own console output crashes on agent-supplied `action` containing markup syntax

- **Where**: `wfctl/cli.py:463,468,472,496,503` (`blocked_cmd`), committed HEAD.
- **What**: Every `console.print(f"...{action}...")` in `blocked_cmd`
  interpolates the raw `action` argument into a `rich` markup string with no
  `escape()`. `action` is free text supplied by the agent
  (`data-model.md`: "`action` | free-text string | the agent"), so nothing
  constrains its characters.
- **Reproduced**:
  ```
  >>> from rich.console import Console
  >>> Console(no_color=True).print(f"[green]recorded: {'issue-comment[/green]INJECTED'} blocked[/green]")
  rich.errors.MarkupError: closing tag '[/green]' at position 54 doesn't match any open tag
  ```
  An action string containing an unmatched `[...]` sequence (plausible —
  nothing here restricts what an agent passes, e.g. a host's own bracketed
  error id echoed back) crashes `wfctl blocked <action> --reason "..."` and
  `wfctl blocked <action> --clear` with an unhandled `MarkupError`, not a
  cosmetic swallow.
- **Contrast**: this same diff *does* add `escape()` at the equivalent
  `next_cmd` remedy line (`console.print(f"  [dim]{escape(blocked)}[/dim]")`)
  and the new test `test_a_held_steps_remedy_reaches_the_console_escaped`
  proves that path is expected to be safe — the gap is specifically in
  `blocked_cmd`'s own five `console.print` calls, which the diff introduces in
  the same commit set and left unescaped.
- **Status**: already fixed in the uncommitted working tree (`from rich.markup
  import escape` + wrapping all five call sites) — but that fix is not part
  of the committed diff under review.

### 3. [Medium] A host block on `implement` mid-task is routed to `wfctl verify`, not to continuing implementation

- **Where**: `wfctl/_pipeline.py:373-407` (`next_step_content`), unchanged by
  this diff but newly reachable with a step it wasn't designed for.
- **What**: `next_step_content`'s existing special case —
  `return ("wfctl verify" if step == "implement" else _STEPS[step].command), False`
  — was built (per its own docstring) for "every task is already ticked and
  the verdict is what is missing." `data-model.md` documents `step` on a
  `blocked` event as "the step current when the report was made" — which,
  per `blocked_cmd` (`step = ... build_report(...).current`), can be
  `implement` at any point during implementation, ticked or not. A block
  filed mid-implementation (e.g. the agent's host refuses an `issue-comment`
  while several `tasks.md` items are still unchecked) holds `implement` at
  `in_progress` via `_apply_block_hold`, and `next_step_content("implement",
  blocked=reason)` unconditionally returns `wfctl verify` — telling the
  person/agent to verify a feature whose implementation isn't finished,
  instead of continuing `/speckit.implement`.
- **No test covers this**: every test in `tests/test_blocked_holds_step.py`
  blocks `decompose` or `plan`; none blocks `implement` with incomplete
  tasks. `plan.md`'s own "review question" list flags the *general* risk
  ("the last [assertion] is the one that fails if the hold is ever wired as a
  predicate `implement` alone consults") but that assertion is about
  `block_reason` being bypassed, not about this specific `implement`→`verify`
  reroute; this exact interaction isn't named anywhere in
  spec.md/plan.md/data-model.md.

### 4. [Low] Cross-branch collision in `notify-action` release matching (documented precedent, but worth flagging)

- **Where**: `wfctl/_session.py:479-529` (`standing_blocks`).
- **What**: `blocked` and `block-cleared` events carry `branch`;
  `notify-action` (unchanged by this feature) does not, so
  `data.get("branch") not in (None, branch)` treats every `notify-action`
  line as matching every branch. Under a shared `WFCTL_STATE_DIR` — a
  configuration this codebase explicitly supports (`_stall.py:132`,
  `_tracker.py:88`, and this same function's own docstring reasoning) —
  branch A's `wfctl blocked push --reason ...` can be silently released by
  branch B's unrelated successful `wfctl notify push`, because both share the
  action name `push` and the release event carries no branch.
- **Mitigating context**: this is called out in the function's own docstring
  as intentional, mirroring an existing precedent — "the same rule
  `_last_resolved` already applies to a `notify-resolved` line written before
  this field existed." So this isn't a new bug introduced carelessly; it's a
  known, pre-existing gap that this diff extends to a new event kind by
  design, for consistency with the established rule. Flagging as a design
  note rather than a defect: worth a second look only if the two-branches-one-
  state-dir case for `blocked`/`notify` specifically is expected to be common
  (rather than the general branch-independence property most of this file
  otherwise assumes).

### 5. [Low] `_predicates.block_reason` is dead code (self-tested only)

- **Where**: `wfctl/_predicates.py:564-578`.
- **What**: `grep -rn "block_reason" wfctl/ tests/` finds exactly one caller —
  its own test (`test_block_reason_answers_for_the_step_the_block_named` in
  the committed `tests/test_blocked_holds_step.py`). `_apply_block_hold` in
  `_pipeline.py` (the actual production hold) bypasses it entirely, and says
  so in its own docstring: "Reads `standing_blocks` once rather than calling
  `_predicates.block_reason` per step... a second read of the same log... is
  a window this file was built to close." `data-model.md` documents
  `block_reason` as "the derived value: the held step" — i.e. as the shipped
  API — but nothing in production calls it.
- **Impact**: not a runtime bug, a maintenance cost — two implementations of
  "does a block hold this step" (`block_reason`'s per-step scan and
  `_apply_block_hold`'s batch dict) that can silently diverge, with only the
  second one live.

### 6. [Info, not filed as a defect] Malformed `step` field is not type-checked before being used as a dict key

- **Where**: `wfctl/_session.py:479-529` (`standing_blocks`) /
  `wfctl/_pipeline.py:316` (`_apply_block_hold`).
- **What**: `standing_blocks` validates `action` (`isinstance(action, str)`)
  and `reason` (`isinstance(reason, str)` in the return filter) but passes
  `step = data.get("step")` through with no type check. `_apply_block_hold`
  does `by_step = {b.step: b for b in standing_blocks(...) if b.step is not
  None}` — a dict comprehension keyed on `b.step`.
- **Reproduced**: writing one malformed-but-JSON-valid line —
  `{"event": "blocked", "action": "push", "reason": "x", "step": ["bad"]}` —
  into `events.jsonl` and calling `_apply_block_hold` raises
  `TypeError: unhashable type: 'list'`, crashing `wfctl status` / `wfctl
  next` / `wfctl resume`. This directly contradicts `standing_blocks`'s own
  documented contract: "Malformed lines are skipped rather than raised...
  every command appends here, so a truncated final write must not crash the
  reader that answers whether the pipeline may advance."
- **Downgraded to Info**: under normal operation `record_blocked` only ever
  writes `step` as `None` or a step-name string sourced from
  `build_report(...).current`, so wfctl itself cannot produce this input.
  Reaching it requires a hand-edited or externally-corrupted `events.jsonl` —
  a narrower window than the "truncated final write" scenario the docstring
  is actually defending against (a truncated JSON line fails
  `json.loads` and is already caught two lines earlier). Worth a one-line
  `isinstance(step, str)` guard for defense in depth, but not blocking.
