## Findings against the committed diff

### 1. [High] A block filed after the pipeline reads "complete" holds nothing — exactly the scenario the feature's own documentation uses as its example

- **Where**: `wfctl/cli.py:343` (`blocked_cmd`), reading
  `wfctl/_pipeline.py:586` (`build_report`'s `current=name if command else
  None`, unchanged by this diff — the field already existed; this diff is the
  first thing to consume it from `blocked_cmd`).
- **What**: `blocked_cmd` resolves the step to hold with
  `step = None if spec_dir is None else build_report(spec_dir, repo_root,
  agent_dir).current`. `build_report.current` is set to `name if command else
  None`, where `name = _current_step_name(raw)`. Once every step is `done` or
  `skipped`, `_current_step_name` returns the sentinel `"complete"`, and
  `next_step_content("complete", ...)` returns `("", False)` because
  `"complete"` is not a key in `_STEPS` — so `command` is empty and `current`
  becomes `None`. `blocked_cmd`'s `step` is therefore `None`, indistinguishable
  from the no-feature-branch case, and it prints "no step is being held" and
  records `step: null`.
- **Reproduced** (direct call, no CLI needed):
  ```python
  from wfctl._pipeline import _current_step_name, next_step_content, _PipelineStep
  steps = [_PipelineStep(name=n, state="done", annotation="", reason=None, remedy=None)
           for n in ("brainstorm", "specify", "plan", "tasks", "implement")]
  name = _current_step_name(steps)                    # "complete"
  command, _ = next_step_content(name, None)           # ("", False)
  current = name if command else None                  # None
  ```
- **Why it matters**: `wfctl/agents/skills/end-session/SKILL.md:197-212` gives
  this command as its own worked example — an agent whose host refuses
  `issue close` runs `wfctl blocked issue-close --reason "..."`, and the doc
  promises: "It holds the step this session was on so the next one reads it
  as unfinished rather than as done." Step 7 (issue close) runs after
  implementation and verification are finished, which is exactly when the
  pipeline reads `"complete"`. In that state the promised hold silently does
  not happen — the session ends, the issue is still open, and nothing in
  `wfctl status`/`next`/`resume` reflects it, because there was no step left
  to attach the block to. This is a real gap between the documented behavior
  and what the code does, in the one place the docs point an agent to.
- **Test gap**: `tests/test_blocked_cli.py::test_a_branch_with_no_feature_still_stores_the_report`
  covers the *no spec dir at all* case (a trunk branch) printing "no step is
  being held" — that's a different, intentional, tested path
  (`spec_dir is None`). No test exercises a feature branch whose pipeline is
  fully `done`/`skipped` (a *resolved* spec dir, `current == "complete"`).
  `spec.md`'s acceptance scenario 2 ("a step whose own artifacts are all
  present... reports held rather than finished, even though a later step
  reports finished") addresses a non-terminal step being blocked while a
  later one is done — not the terminal case where there is no later step at
  all. This exact terminal case isn't named in spec.md, plan.md, or
  data-model.md.

### 2. [Medium] A standing block can be released by an unrelated success on a different branch, when branches share a state dir — contradicts FR-021

- **Where**: `wfctl/_session.py:522` (`standing_blocks`'s branch filter,
  `data.get("branch") not in (None, branch)`), combined with
  `record_notify_action` (`wfctl/_session.py:398-406`, pre-existing,
  unchanged by this diff per its own FR-019 note) never writing a `branch`
  field.
- **What**: `standing_blocks` treats an event with no `branch` key as matching
  *every* branch it's asked about. `blocked` and `block-cleared` (both new in
  this diff) always carry `branch`; `notify-action` (old, and FR-019
  explicitly forbids changing it) never does and never will. Since a
  `notify-action` event is one of the three kinds that can be "the most
  recent event for an action" (FR-020's free release), a success recorded for
  one branch releases a standing block filed under the same action name on
  *any other branch reading the same state dir*.
- **Reproduced**:
  ```python
  from wfctl._session import record_blocked, record_notify_action, standing_blocks
  record_blocked(d, "branch-A", "issue-comment", "host refused on A", "decompose")
  standing_blocks(d, "branch-A")   # -> [StandingBlock('issue-comment', 'host refused on A', 'decompose')]
  record_notify_action(d, "issue-comment")   # unrelated success, no branch, recorded for branch B's work
  standing_blocks(d, "branch-A")   # -> []   <- branch A's block silently cleared
  ```
- **Why it matters**: `spec.md`'s own clarification log states plainly — "What
  is a block scoped to? → The branch's own session state, like every other
  event" — and **FR-021** requires "A block MUST be scoped to the branch it
  was reported on." A shared state dir across branches/worktrees is not a
  hypothetical here: it's the exact scenario `standing_blocks`'s own docstring
  reasons about ("a state dir shared across worktrees holds every branch's
  events"), and `tests/test_blocked_events.py::test_a_block_on_one_branch_does_not_hold_a_step_on_another`
  tests precisely this property for `blocked`/`block-cleared` — but not for
  the `notify-action` release path, which is the one gap that breaks the
  guarantee.
- **Not a fresh defect from nothing**: the docstring explicitly frames this as
  intentional, by analogy to `_last_resolved`'s handling of pre-migration
  `notify-resolved` lines that predate the `branch` field. That analogy is
  weaker than it reads: `_last_resolved`'s case is a shrinking population of
  *old* events written before a schema field existed; `notify-action` has no
  `branch` field *by design, permanently* (FR-019 keeps it that way), so this
  isn't a migration compatibility shim — it's a standing hole in the
  branch-scoping guarantee this diff otherwise builds carefully (see the
  scoped test above). Given FR-021's flat "MUST," I'd flag this as a real gap
  rather than accepted debt, though the fix is a scoping question for
  whoever owns the design (e.g., should `record_notify_action` start taking
  `branch`, breaking the "unchanged" promise in FR-019 — a real tradeoff, not
  a one-line fix) — I'm not asserting the code should change without that
  conversation happening first.

### 3. [Low] A malformed non-string `step` field crashes the reader that must not crash

- **Where**: `wfctl/_session.py:524-528` (`standing_blocks`) /
  `wfctl/_pipeline.py:321` (`_apply_block_hold`'s dict comprehension keyed on
  `b.step`).
- **What**: `standing_blocks` validates `action` is a `str` and (in the return
  filter) that `reason` is a `str`, but passes `step = data.get("step")`
  through with no type check. `_apply_block_hold` does
  `{b.step: b for b in standing_blocks(...) if b.step is not None}` — a dict
  keyed directly on `b.step`.
- **Reproduced**: writing one syntactically-valid-JSON, semantically-malformed
  line to `events.jsonl` —
  `{"event": "blocked", "branch": "b1", "action": "push", "reason": "x", "step": ["bad"]}`
  — and calling `standing_blocks`/`_apply_block_hold` raises
  `TypeError: unhashable type: 'list'`. This crashes `wfctl status`, `wfctl
  next`, and `wfctl resume` (all three eventually call `build_report` →
  `_apply_block_hold`).
- **Why it matters, and why only Low**: `standing_blocks`'s own docstring
  promises "Malformed lines are skipped rather than raised... a truncated
  final write must not crash the reader that answers whether the pipeline may
  advance" — this line violates that stated contract. But under normal
  operation `record_blocked` only ever writes `step` as `None` or a
  step-name string sourced from `build_report(...).current`, so wfctl itself
  cannot produce this input; reaching it needs a hand-edited or
  externally-corrupted `events.jsonl`, a narrower window than the truncated-
  write scenario the docstring is actually defending against (a truncated
  line fails `json.loads` two lines earlier and is already caught). Worth an
  `isinstance(step, str)` guard for defense in depth, not a blocker.

## Already remediated, uncommitted (not filed as open findings)

Verified by diffing `HEAD` against the working tree (`git diff` with no
range) and confirming the fixes actually change behavior:

- `wfctl next` (`wfctl/cli.py`, `next_cmd`) did not call `_apply_block_hold`
  in committed `HEAD` — it inferred steps directly, so `next-step.md` (the
  file an agent actually acts on) could disagree with `wfctl status` about
  whether a step was held. The uncommitted diff adds the same
  `_apply_block_hold` call `build_report` makes, with a comment naming the
  disagreement this closes.
- `blocked_cmd`'s five `console.print` calls interpolated the raw,
  agent-supplied `action` string into `rich` markup with no `escape()` — an
  action containing an unbalanced `[...]` (plausible: a host's own bracketed
  error text echoed back) would raise `rich.errors.MarkupError` or render
  garbled output. The uncommitted diff wraps every occurrence in `escape()`.
- `_apply_block_hold`'s `by_step = {b.step: b for b in standing_blocks(...)}`
  dict comprehension relied on `standing_blocks` returning entries ordered by
  an action's *most recent* qualifying event, but the committed
  `standing_blocks` only reassigned a key's value on repeat sightings without
  moving its position — so when two different actions both held the same
  step, the "winner" was decided by which action's name happened to appear
  *first* in the log, not which was blocked *most recently*. The uncommitted
  diff adds `latest.pop(action, None)` before each reassignment so repeat
  sightings move to the end, and updates the docstring/tests accordingly
  (`tests/test_blocked_holds_step.py::test_two_actions_blocked_against_the_same_step_report_the_latest`).
- `_predicates.block_reason` (committed) duplicated the same
  standing-block-lookup `_apply_block_hold` performs inline, was called from
  no production code, and risked silently diverging from the real
  implementation if one were changed without the other. The uncommitted diff
  deletes it and its test, replacing the test with one that exercises the
  actual hold behavior end to end.

I did not independently discover these — I found the same underlying issues
via a first read-through and confirmed, on inspecting `git diff` (uncommitted),
that fixes for exactly these four already exist in the working tree. Listing
them here for completeness of the picture, not as new findings.
