## Findings

**BLOCKER  wfctl/cli.py:L2844 — the issue's stated symptom is unchanged; the new tests do not
reach it.**

`install-config` refuses to run when `.workmux.yaml` already exists, and `--force` overwrites it
with the bundle template. So `worktree_dir()` never reads a repo's own config — it only ever reads
the file this command just copied out of the bundle. Exercised for real, exactly as the handoff's
DoD asks:

```
$ printf 'worktree_dir: trees\nagent: claude\n' > .workmux.yaml
$ uv run wfctl install-config workmux
✗ Would overwrite existing file(s): .workmux.yaml. Pass --force to overwrite (git is your undo).
$ uv run wfctl install-config workmux --force
✓ Seeded workmux config (1 file(s)) from wfctl 0.17.0
$ cat .gitignore
wt/
$ grep ^worktree_dir .workmux.yaml
worktree_dir: wt          # worktrees land in ./wt/<handle> (gitignored by installer)
```

The handoff's acceptance criterion is literal: *"a repo with `worktree_dir: trees` must end up with
`trees/` gitignored and not `wt/`."* It still ends up with `wt/`. Issue #35's A1 effect line — "A
non-default `worktree_dir` is never gitignored; `wt/` is gitignored though nothing uses it" — is
still true after this commit.

What the change *does* fix is real and worth keeping: template↔code drift, the "the moment either
moved they disagreed" half of the commit message. If wfctl (or a fork) ships a template with a
different `worktree_dir`, the gitignore now follows it. That is a genuine single-source fix.

The tests hide the gap rather than expose it. `_install(bundle, yaml=...)`
(`tests/test_install_config.py:L17-28`) writes `yaml` into **`bundle/agents/configs/workmux/`** —
the shipped template, not the repo. So `test_gitignores_the_directory_the_config_names`
(`:L54`) proves "a different *template* is honoured", while its docstring — "A config declaring
anything else must be what gets ignored" — reads as the repo's config, which is the scenario #35
describes and the one still broken.

→ Fix, pick one and say which in the PR:
  (a) Preserve the repo's declared `worktree_dir` across a `--force` reseed, and gitignore that —
      then the test can seed the *repo* and the issue's scenario passes;
  (b) Read the repo's existing `.workmux.yaml` for the gitignore decision even when the seed is
      refused/forced;
  (c) Keep the scope as-is, but narrow the claim: this closes template↔code drift, not A1 as the
      issue words it. Then `Refs #35` must not become `Closes #35` on A1's strength, the commit
      body and the two test docstrings need to say "the template", and A1's residue needs a
      written follow-up. The handoff explicitly permits narrowing — "say which you chose and why;
      do not silently narrow" — and right now the narrowing is silent.

**WARNING  wfctl/_workmux.py:L38 — a value workmux documents as legal becomes a dead `.gitignore`
line, written silently.**

`workmux config reference` for `worktree_dir`: *"Can be relative to repo root or absolute. Supports
`~` for home directory and `{project}` for the main worktree's directory name, e.g.
`~/.workmux/{project}`."* Every one of those is returned verbatim and concatenated into a pattern.
Measured against real git:

| declared value | line written | effect |
|---|---|---|
| `~/.workmux/{project}` | `~/.workmux/{project}/` | never matches; dir is outside the repo anyway |
| `wt-{project}` | `wt-{project}/` | gitignore has no brace expansion — matches only a dir literally named `wt-{project}` |
| `/abs/trees` | `/abs/trees/` | root-anchored at repo root; `check-ignore` exits 128, so the write is not even suppressed |
| `../trees` | `../trees/` | same; outside the repository |

This is the exact failure the `else` branch's own comment forbids — *"an ignore for a directory
nothing uses, with the real one left tracked"* — except here the code writes it instead of warning.
The absent case is guarded loudly; the unusable case is not guarded at all.

→ Reuse the warning branch. Guard before writing: if the value is absolute, starts with `~`, starts
with `../`, or contains `{`, it is not a repo-relative path — print the same ⚠ (worded "worktree_dir
`<v>` is not inside the repo — nothing gitignored") and write nothing.

**WARNING  wfctl/_workmux.py:L38 — `\S+` truncates a quoted value at its first space, gitignoring
the wrong directory silently.**

`worktree_dir: "my trees"` → `worktree_dir()` returns `my` → `.gitignore` gets `my/` → `my trees/`
is confirmed still untracked. Verified:

```
worktree_dir: "my trees"  -> 'my'
worktree_dir: 'my trees'  -> 'my'
```

The diff adds `test_worktree_dir_reads_a_quoted_value` (`tests/test_workmux.py:L110`), which puts
quoting in scope deliberately — and the one thing a quoted YAML scalar exists for is a value
containing a space. The test picks `'trees'`, which quoting was never needed for, so it passes while
the case quoting is *for* fails. That is the same shape as the bug this commit exists to fix: a
declared value, misread, and a different directory ignored with no evidence.

→ Match the quoted forms before the bare one:
`r"""^worktree_dir:[ \t]*(?:'([^']*)'|"([^"]*)"|(\S+))"""`, taking the first non-None group, and
drop the `.strip("\"'")` (which also silently accepts mismatched `'foo"`). Add
`worktree_dir: "my trees"` as the test case.

**NIT  wfctl/_workmux.py:L38 — two more inputs the regex mis-reads.**

- `worktree_dir:   # not set on purpose` → returns `"#"` → writes `#/`, which git parses as a
  *comment*: nothing ignored, one junk line added. The `\S+` guard against commented keys only
  looks at column 0.
- `worktree_dir: wt/` (a trailing slash a hand-editor will write) → returns `wt/` → `f"{wt}/"`

→ The regex fix above kills the first (`#` is not a quoted or bare scalar under a
`(?!#)`-style guard, or reject a value starting with `#`); `wt.rstrip("/")` at `cli.py:L2846`
kills the second.

default the change exists to stop assuming, so the branch below reads "if wt". `worktree_dir` (or
`wt_dir`) says what it holds; the rubric's naming pass and the change's own thesis point the same

**NIT  wfctl/_workmux.py:L34-37 vs L113-119 — the `\S+`/trailing-comment rationale is stated twice,
