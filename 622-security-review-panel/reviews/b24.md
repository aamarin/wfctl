## Findings

WARNING  wfctl/_review.py:L226-L237 — A shallow clone can still let a merge's own edit go unreviewed. The `merge-base` check only catches a clone that cut every commit the two parents share. If the clone still holds an older shared commit, `merge-base` exits 0 and returns that commit, and `merge-tree` redoes the merge against it instead of the real base. A file that was added after that older commit, deleted on `main`, and kept by the merge then looks like a plain addition. The redo matches the merge, so the merge is dropped. This is the same failure the commit sets out to fix.

I reproduced it in /private/tmp/claude-501/-Users-andremarin-Development-wfctl-wt-637-review-records/077a9c68-d821-43d1-b2ef-8f9d00e15caf/scratchpad/b24/partial_cut.py. The setup is the new test's merge, plus a side branch merged into `main` that reaches an older commit X in two hops, cloned with `--depth 4`:

```
full: merge kept = True
full: merge-base(parents) = c02d27f B = c02d27f X = 15aa9ad
shallow: true
shallow: merge-base exit 0 15aa9ad
shallow: merge kept = False
```

This isn't a regression. The parent commit gave the same answer here, so 3b1b9c4 is still a strict improvement. But the docstring and R3 both say a shallow clone that cut the shared history is handled, and only the clone that cut all of it is. → Fix: ask `git rev-parse --is-shallow-repository` once per `commit_range`, and in a shallow repository keep every two-parent merge. That's one call per range rather than one per merge, and it covers both shallow cases. Keep the `merge-base` check for orphan merges. Then reword the docstring and R3 so they claim only what the code does, and add this topology as a test beside `test_range_keeps_a_merge_whose_shared_history_a_shallow_clone_cut`.
