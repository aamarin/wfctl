## Findings

### WARNING: the trunk value has no producer, and one ref is narrower than wfctl's range

Commit 6c14a5a added a fourth value to "What you're given", the trunk branch, and the git commands use it as `--not origin/main`. Nothing on the #622 plan supplies it:

1. `contracts/cli.md` shows the output of `wfctl review start`. It prints the base, the head, the reports folder, and the reviewer ids, but not the trunk.
2. Plan item 2.1 for `fanning-out-code-review` (#638) gives each reviewer "the commit range and the reports path", and nothing more.
3. No CLI prints `_paths.trunk_branch`. A launcher would have to guess `origin/main`, which is wrong whenever `trunk` is set in `wfctl.json`.

The commands also differ from wfctl's own range. Research R3, which T009 item 5 tests, defines the range as `git rev-list --no-merges <base>..<head> --not <trunk refs>`. The trunk refs are the remote ref and the local branch of the same name, so the command becomes `--not origin/main main`. The skill passes one ref. When a branch merged a local `main` that is ahead of the local `origin/main` ref, the reviewer reviews commits that wfctl doesn't count. Its report then still counts, so the run completes over a different set of commits than the ones the reviewer read.

This matters for #637 and #638 because the skill now encodes a second definition of "the run's commits", and that definition has to be kept in sync with `_review.py` by hand. The fix that removes the duplicate is for the reviewer to read the commit list wfctl already computes. The spec says the run record lists those commits. Have `wfctl review start` print the shas, or the path to the run record, and change the skill to run `git show --stat <sha>` and `git show <sha>` for each one. The trunk value then drops out of the skill. If that's out of scope here, at least add the trunk to `review start`'s output in #637, pass both refs, and record the dependency in #638's task list.

### WARNING: the agent-instruction carve-out doesn't reach the sub-tasks

L59-64 says the prompt's exclusion of "findings in documentation such as markdown files" doesn't apply to agent instructions. The prompt's own steps, though, send its text into sub-tasks verbatim:

1. Step 1 says "In the prompt for this sub-task, include all of the above." That text includes hard exclusion 16, "Do not report any findings in documentation files such as markdown files."
2. Step 2 sends every finding to a filter sub-task that receives "everything in the FALSE POSITIVE FILTERING instructions", which also includes exclusion 16.

L67-68 tells the reviewer to change only one thing in those prompts, the git section. This means the sub-task path, which is the default in Claude Code, finds and then filters out anything in a `SKILL.md`, a command wrapper, or a hook written in markdown. In this repository most security-relevant changes are of that kind, and this PR is an example. The carve-out that 6c14a5a added only holds when the reviewer can't launch sub-tasks.

Fix: extend L67-68 so that each sub-task's prompt carries the git output and also the carve-out sentence, which says that a skill, a command, or a hook an agent runs is code and is not covered by the documentation exclusion.

### WARNING: per-commit patches surface problems the head has already fixed

`git log -p` prints each commit's patch in turn. When one commit in the run adds a vulnerability and a later commit in the same run removes it, the reviewer sees the vulnerability and may report it, and the prompt's false-positive filter has no rule against that. The plain `git diff base..head` that would show the net change is ruled out on purpose, since it brings in trunk merges, so per-commit output is the right input. What's missing is one sentence: a finding must still be present at the head, so check it with `git show <head>:<path>` before reporting it. The prompt's Phase 1 also reads files from the working tree, which may not be at the head when the author keeps working during the review. The same sentence covers that case.

### NITs

1. **Second broken checklist path.** `hardening-patterns.md` cites the checklist three times as `../../../references/security-checklist.md` (L5, L9, L208). From the installed references folder that resolves to `.agents/references/`, which doesn't exist. L80-83 corrects only the `../../references/` spelling from `SKILL.md`, so a reviewer who follows the destructive-path pointer in `hardening-patterns.md` may not connect the two. The record's new paragraph names only the `../../` citation too.
2. **Dead filter in the path test.** The pattern `` `((?:\.\./)?[a-z0-9-]+/...\.md)` `` allows one leading `../`, so `../../references/security-checklist.md` never matches. I ran the pattern over the skill, and it returns three paths with no `../../` among them. The line `cited = {p for p in cited if not p.startswith("../../")}` therefore filters nothing. The docstring's "is left out" is true only by accident of the regex.
3. **Missing anchor.** The module docstring says the anchors pin the text the skill overrides. Since 6c14a5a, the skill also overrides exclusion 16 ("Insecure documentation"), and no anchor pins it. If an upstream re-pull drops or rewords that exclusion, the test stays green.
4. **Dangling skill names.** The vendored `security-and-hardening` mentions two upstream skills that wfctl doesn't ship. `test_skill_cross_references` only matches `.agents/skills/<name>` paths, so it doesn't see them. The file stays unedited, so the fix is a sentence in the record, not an edit.
