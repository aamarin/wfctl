### Findings

BLOCKER  wfctl/_review.py:L235 (`_has_own_edits`), and `commit_range` above it. The fix covers a shallow clone that cuts all of the parents' shared history, but not one that cuts only part of it. When the cut leaves an older common ancestor reachable from both parents, `git merge-base` exits 0 with that stale commit instead of exiting 1. `merge-tree` then redoes the merge against the stale base, and the same hole the commit describes comes back. R3 and the new docstring both say a shallow clone is handled, and this case is a shallow clone that cut the parents' shared history.

Reproduction (`/private/tmp/claude-501/-Users-andremarin-Development-wfctl-wt-637-review-records/077a9c68-d821-43d1-b2ef-8f9d00e15caf/scratchpad/b26/partial.sh`, about 25 lines of git):
1. `main` has `s0`, then `S`. The branch forks at `S` and makes 6 commits. `main` adds `f` (commit `M`). The branch merges `main` (commit `X`), then makes 6 more commits.
2. A topic branch forks at `S` with one commit, and the branch merges it. That merge gives the branch tip a short path back to `S`.
3. `main` deletes `f` and adds `t`. The branch merges `main` and restores `f` by hand (commit `Y`).
4. `git clone --depth 4 --no-single-branch`, then check out the branch.

In the full clone, `merge-base Y^1 Y^2` is `M`, the redo deletes `f`, and `commit_range` keeps `Y`. In the shallow clone, `M` is present but the branch side can't reach it, so `merge-base` returns `S`. Against `S`, the redo keeps `f`, matches `Y`'s tree, and `commit_range` drops `Y`.

The same clone shows a second let-through that predates this commit. `commit_range` lists 4 commits in the shallow clone against 14 in the full clone, with the same base. Commits `b1` to `b10` sit beyond the cut, so `rev-list` never sees them. A run started there completes on 4 commits and moves the group's last reviewed commit to the head, and the other 10 are never reviewed. That breaks `review-covers-unreviewed-commits`.

Fix: in `commit_range`, ask `git rev-parse --is-shallow-repository` once, and raise `ReviewError` when it prints `true`, naming `git fetch --unshallow`. A shallow clone can't answer which commits are unreviewed, at the merge level or the range level, so refusing is the only answer that lets nothing through. It costs one git call per range rather than one per merge. Keep the per-merge `merge-base` check for a merged orphan branch, and drop the shallow-clone sentences from the docstring and from R3, replacing them with the refusal. The test then becomes "a shallow clone is refused", and the existing scenario works as its fixture.

A key holding a newline prints a `check config` line nobody wrote. Every one of these refuses the run, so the effect is a confusing finding rather than a forged roster.
