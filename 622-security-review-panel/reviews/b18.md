### Findings

WARNING  wfctl/_review.py:L233-L236 — In a shallow repository, the flag turns a loud failure into a merge dropped from the range without a word.

A shallow boundary can cut the ancestors two merge parents share. Git then treats the parents as unrelated histories, and the flag makes `merge-tree` redo the merge against an empty base. An empty-base redo takes any file that only one side has, so it can't tell when a merge kept a file that the other side deleted. That is the case where someone undoes `main`'s deletion of a file while merging. The redo then matches the merge's tree, and `_has_own_edits` returns False. R3 says the range "lets nothing through", and this breaks that.

I reproduced it end to end through `commit_range`, with scripts under `/private/tmp/claude-501/-Users-andremarin-Development-wfctl-wt-637-review-records/077a9c68-d821-43d1-b2ef-8f9d00e15caf/scratchpad/b18/` (`shallow.sh`, `shallow2.sh`, `run.py`). In the setup, `main` deletes `guard.py`, and the feature branch merges `main` but keeps `guard.py`. The merge is clean, so nothing conflicts.

| clone | `commit_range` from the merge base |
|---|---|
| full | `4be28f6 merge main, resurrect guard`, `c85efe5 feat1` |
| `--depth 2` | `c85efe5 feat1` only. The merge is missing. |
| `--depth 2`, before this commit | `git merge-tree failed: fatal: refusing to merge unrelated histories` |

It is not a BLOCKER because it needs a shallow clone with the boundary inside the range, and the workmux-from-a-full-checkout flow doesn't make one. It is a failure that lets a merge through, though, and it comes from this diff.

The flag earns little in return. A real `git subtree add` merge stays in the range with or without the flag: subtree reads the history in under a prefix, so the redo puts the files at the root and its tree differs (`subtree.sh`: redo `64691a7`, merge `c5d75c4`). The only merges the flag drops are a merged orphan branch at the root, whose commits are in the range anyway, and the false positives in a shallow clone.

→ Fix: when the two parents share no commit (`git merge-base <p1> <p2>` exits 1), keep the merge in the range. You can limit that to a shallow repository (`git rev-parse --is-shallow-repository`, asked once per range) if dropping orphan merges matters. Add a test that clones the fixture with `--depth` and asserts that the merge which kept the file stays in the range.
