## Findings

BLOCKER  wfctl/_review.py:L181-L184 — `commit_range` fails in any repository whose root holds a file or folder named after the local trunk branch → end the `rev-list` arguments with `--`.

`trunk_refs` adds the local branch, such as `main`, to the refs, so `commit_range` runs `git rev-list --no-merges <base>..<head> --not origin/main main` with `cwd=repo_root`. git checks every bare revision argument against the worktree. When a path named `main` exists, git exits 128 with `fatal: ambiguous argument 'main': both revision and filename`. `_git` turns that into `✗ git rev-list failed: …`, so `wfctl review start` can never write a run in that repository.

The path doesn't need to be tracked. An untracked build output counts, such as a Go or C binary named `main`, and so does a `dev/` folder in a repository whose trunk is `dev`. A bare layout is exposed even without `origin/`, since `_bare_head` returns the plain local name. Once #638's guard calls this function, the same error refuses every `gh pr create` in that repository, and the only workaround is to delete or rename the path.

I confirmed this in a scratch repository with a `main/` folder on a feature branch. `git merge-base HEAD main` succeeds, `git rev-list --no-merges <base>..HEAD --not main` exits 128, and the same command ending in `--` exits 0 and lists the commit. The fix is to append `"--"` after `*refs`, and add a range test that creates a `main` path in the fixture repository.

WARNING  wfctl/_review.py:L459-L490 and wfctl/cli.py (`review_check_cmd`) — a run that is already complete can print `incomplete` and exit 1 while its records still mark it complete → when `completed_at` is set, report the run as complete, or say it was completed earlier.

`check` judges the reports again on every call but writes only on the first completion. When a report is deleted or edited after completion, the roster shows ✗ and the last line reads `incomplete: 1 of 3 expected reports missing` with exit 1. Meanwhile `last-reviewed.json` has already moved to the run's head, so the group counts as reviewed for the next `start` and for #638's guard. The output and the records disagree about the one thing the command reports. Either print `complete (recorded at <completed_at>)` when the record says so, or keep the roster honest and add a line saying the run was completed earlier and the group's last reviewed commit already moved. A test that deletes a report after completion would pin whichever answer you choose.
