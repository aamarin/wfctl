### Findings

WARNING  wfctl/_review.py:L208-217 — `_has_own_edits` misses the most common hand resolution. `--cc` drops a hunk with two variants when the merge picks one of them unchanged, so a conflict resolved by keeping one side prints nothing and the merge leaves the range. I reproduced four merges of `origin/main` into a branch where both sides edited the same line. Blending the two lines kept the merge in `commit_range`. Resolving with `git checkout --ours f`, resolving with `git checkout --theirs f`, and `git merge -s ours origin/main` each printed 0 bytes from `diff-tree --cc` and gave `commits == ()`. The `--ours` case silently reverts main's change to that line, and `-s ours` reverts all of main's work, and with this change nobody reviews either one. The docstring ("a hand-resolved conflict prints the resolution"), the `commit_range` docstring, the test docstring at tests/test_review.py:L269 and the commit message all claim the resolution is covered. → Use `git show --remerge-diff --format= <merge>` (git 2.36+), which diffs the automatic re-merge against the recorded result. It printed 213 to 226 bytes for all four cases and 0 for a clean merge from main. `git diff-tree --remerge-diff` hits `BUG: log-tree.c:1059: did a remerge diff without remerge_objdir` on 2.44, so it has to be `show` or `log`. Add a test that creates a real conflict and resolves it with `--ours`. If you keep `--cc`, correct the three docstrings and R3 so they say a side-picking resolution is not covered.

WARNING  wfctl/_review.py:L52 — The `\b` boundaries reject verdicts that counted before this commit. `_` is a word character, so underscore emphasis now fails, and so does a past-tense verdict. Checked with `judge`: `**Verdict:** _Approve_`, `Verdict: __Approve__` and `Verdict: _Request changes_ (1 blocker)` all return `no verdict at the end`, and so does `Verdict: Approved`. R2 says reusing the anchor "keeps every spelling reviewers already write", and `_REVIEWED` explicitly allows `_` decoration, so underscore emphasis is an expected shape. The result is a run that stays incomplete over a well-formed report. Meanwhile `Verdict: Do not approve` still counts, so the stated aim of keeping verdicts outside the rubric's two from counting isn't met either. → Use `(?<![A-Za-z])(?:Approve|Request changes)(?![A-Za-z])` if `Disapprove` is the only target. That still accepts `_Approve_`, but it still rejects `Approved`, so decide on that word deliberately. Add the underscore spellings to the parametrized test.

WARNING  wfctl/_review_config.py:L123-142 — The newline rule covers model names but not commands. The comment at L39-40 says a model name is restricted because `review start` "prints it in lines the panel skill reads one at a time". `review start` prints `command` on that same line (cli.py, `line += f" {r['command']}"`), and `_commands` accepts a newline in it, because `shlex.split` treats `\n` as whitespace. `{"codex": "codex exec\nreports: /tmp/elsewhere/\ns9 claude"}` loads with no problems (checked with `_review_config.load`), so it injects a second `reports:` line and a fake `s9 claude` roster line. That is the same injection the new `model-name-with-a-newline` test guards against. A committed command already runs arbitrary code, so the extra risk is limited to misleading the coordinator. But the stated rule is enforced on only one of the two fields it covers. → In `_commands`, report a command containing `\n` or `\r` (or any control character), and add the matching row to `contracts/config.md` and a test case.
