### Findings

WARNING  wfctl/_review_config.py:L99 — If two entries in `groups` share a name, the last one silently wins. `{"group": "money", count 2}` followed by `{"group": "money", count 1}` loads one reviewer and reports no finding, and the first-letter clash check iterates the deduplicated dict, so it never sees the pair either. The `check config` docstring says "Nothing here is dropped silently", and `_declared.py:L151` already reports "declared twice under one step" for the same mistake in `steps`. → Before line 99, add a finding when `name in declared`, such as `review group 'money' is declared twice`, and cover it in `test_each_bad_declaration_is_a_finding_in_the_words_check_config_prints`.

WARNING  wfctl/_review_config.py:L71,L126 — Unknown keys are dropped without a finding. `"review": {"group": [...]}` (missing `s`) and `{"group": "security", "reviewer": [...]}` (missing `s`) both load as the defaults, three Claude reviewers per group, with no problems. A repository that meant to add two Codex reviewers to `security`, or cut it to one, gets three Claude ones, and `check config` prints ✓. This breaks the same "dropped silently" rule, and `_declared` already reports an unknown step name. → Report any key outside `{commands, groups}` under `review`, and outside `{group, skill, reviewers}` in a group entry, as a finding such as `review group 'security': unknown key 'reviewer'`.

WARNING  wfctl/_review.py:L467-471 — `check` writes `completed_at` into run.json before it writes `last-reviewed.json`. If the second write fails (disk full, a permission error, an interrupt), run.json says the run is complete, and the guarded `completed_at is None` means no later `check` writes `last-reviewed.json` again. The group's last reviewed commit stays behind with nothing to show why. The only recovery is a new `start` and a whole new round of reviewers. → Write `last-reviewed.json` first and run.json second. A failure between the two then leaves `completed_at` null, and the next `check` repeats both writes, which is harmless. Or, when the run is already complete, re-write `last-reviewed.json` when it doesn't name `run.head`.

WARNING  wfctl/_review.py:L332 (with L257-262) — `start` numbers the next run by calling `latest_run`, which parses the newest run.json. A run directory with no run.json, or with a damaged one, raises `can't read …/run.json` from `start`, `check` and `relay` alike, and the group stays wedged until a person deletes the directory by hand. A start interrupted between `path.mkdir()` (L337) and `write_atomic` leaves exactly that directory, and so does a second `start` reading the folder while the first is still writing (I reproduced the error with an empty `runs/001/`). Reading a run's contents to find the next free number is also more than numbering needs. → In `start`, take the number from the directory names alone, using the `mkdir` loop that's already there, so a broken earlier run never blocks a new one. `check` and `relay` can keep the strict read.

NIT  wfctl/_review.py:L381 — The roster reason for a report whose sha is a correct but too-short prefix reads `names 9f8e7d, not 9f8e7d6`, which tells the reviewer it read the wrong commit when it read the right one. A full 40-digit sha naming another commit is printed in full, not at the 7 digits the contract example shows. → Print `named[-1][:_MIN_SHA]`. The cli.md reason list is closed, so keep the short-prefix wording unless the contract changes, but say in `judge`'s docstring that a prefix shorter than seven digits reads as "names", on purpose.
