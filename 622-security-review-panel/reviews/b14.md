## Findings

WARNING  wfctl/_review.py:L228 — `merge-tree --write-tree` refuses two parents with no common ancestor and exits 128. `_git` turns that into a `ReviewError`, so `commit_range` fails, and `review start` and `review check` both fail on every call for that branch. The old `diff-tree --cc` call answered for the same merge without error. A branch gets such a merge from `git subtree add`, from `git merge --allow-unrelated-histories`, or from merging an orphan branch such as `specs-trunk` by mistake. The only way out is to rewrite the branch's history or sign off by hand. `_archive.py:L195` already passes `--allow-unrelated-histories` to the same command for this reason, and its comment says so. I reproduced it on git 2.44: a branch with one reviewed commit, a merge of an unrelated `vendor` history, and one more commit gives `ReviewError: git merge-tree failed: fatal: refusing to merge unrelated histories`. → Pass `--allow-unrelated-histories` in `_has_own_edits`, and add a test that builds this branch and asserts the range. The vendored commits are not on the trunk, so `rev-list` still lists each one, and a clean redo of the merge can safely leave the merge commit out.

NIT  wfctl/_review_config.py:L236 — The cap check returns `None` as soon as the total passes 20, so the reader doesn't check the group's later entries in that run. The total also counts only the entries that were valid so far. For example, `[{codex, 15}, {claude, 15}]` with no command for `codex` reports only the missing command, and the cap finding shows up after that fix. → Add each entry's `count` to a running total before the command check, set `ok = False` when it passes 20, and report the cap once per group rather than returning early.
