The commit is a real improvement. The old `diff-tree --cc` test let a conflict resolved by keeping the branch's side, and `git merge -s ours`, drop out of the range unreviewed. The new test closes both, and the regression tests pin each case. One regression comes with it: a merge of unrelated histories now makes `review start` fail outright, where R3 says that merge is kept. That is the one blocker. The rest are small.

BLOCKER  wfctl/_review.py:L228 — `merge-tree --write-tree` refuses a merge whose parents share no history, and exits 128 with "refusing to merge unrelated histories". `_git` only accepts 0 and 1, so it raises `ReviewError`, and `commit_range` fails for the whole branch. `git subtree add` makes exactly this kind of merge, and so does `git merge --allow-unrelated-histories`. I reproduced it in a scratch repo: `ReviewError git merge-tree failed: fatal: refusing to merge unrelated histories`. Before this commit, `diff-tree --cc` handled that merge without an error.

This means a branch carrying such a merge can never start a run for any group, so `last-reviewed.json` can never move past the merge. Once the guard lands, that branch can't open its PR either. It fails closed, so nothing slips through unreviewed, but the only way out is rewriting the branch. It also contradicts R3, which says a merge "git can't redo unaided" is kept. → Pass `--allow-unrelated-histories`, the same way `_archive.py:L195` already does. The redo then merges against an empty base. A subtree add then produces a tree that differs from the merge's own tree, so the merge stays in the range. Add a regression test beside `test_range_keeps_a_merge_that_discards_mains_changes`.

NIT  wfctl/_review_config.py:L44 — `_CONTROL` covers `\x00-\x1f` and `\x7f`, but not the other characters Python's `str.splitlines()` treats as line breaks: `\x85`, ` ` and ` `. A command such as `"codex  s9 claude"` passes `load`. The `judge` function and the CLI tests both split output with `splitlines()`, and they read it as two lines, which is the forged roster line this check exists to stop. The risk is low, because a repo that controls `review.commands` already controls a command the review runs. → Use `not command.isprintable()`, which also rejects C1 controls and the Unicode line and paragraph separators.

NIT  wfctl/_review_config.py:L236 — The group cap counts only the entries that passed. An entry rejected later in the loop, for example one with no `review.commands` entry, adds nothing to `found`. NIT  wfctl/_review.py:L132 — The docstring says "a tag on an older commit made the branch's own work read as already on the trunk." NIT  wfctl/_review.py:L234 — Each merge costs a second git call, `rev-parse <merge>^{tree}`, only to read the merge's tree. → Optional.
