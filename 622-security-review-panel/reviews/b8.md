The commit fixes four things in `wfctl review` and adds a set of smaller config checks. ### Findings

BLOCKER  wfctl/_review.py:L203-L217 — `_has_own_edits` reads a conflict resolved by taking one side as a clean merge, so the merge is dropped and nobody reviews it → classify a merge with `git show --remerge-diff` instead of `--cc`.

`--cc` keeps only the hunks that differ from every parent. When a person resolves a conflict by keeping the branch's side, the result matches the first parent in that hunk, so `--cc` prints nothing. The same is true of `git merge -s ours main` and `-X ours`, which throw away `main`'s changes without a conflict. In each case the merge drops work that `main` already has, and the drop exists only in the merge commit. This is the gap the commit message describes ("a conflict resolved by hand, which exists only in the merge, was never reviewed. A branch whose only new commit was that merge read as up to date"), and it is still open for the most common way people resolve a conflict.

I ran `commit_range` (scratch script `b8-scripts/repro3.py` under this session's scratchpad) on a branch whose last reviewed commit is `feat1`, followed by `git merge -s ours main`, where `main` had added `fix.txt` ("security fix"):

- `commit_range(repo, head, reviewed).commits` returned `()`, so `review start` prints "up to date".
- `git diff --stat main feat` shows `fix.txt | 1 -`. Landing the branch deletes `main`'s fix, and no group reviewed that change.

`git show --remerge-diff` re-runs the automatic merge and diffs the recorded result against it, so it prints nothing for a clean merge and prints the resolution for any conflict, whichever side was kept. Here is how the three probes classified five merge shapes (`b8-scripts/repro4.sh`, git 2.44):

| Merge | `--cc` output | `--remerge-diff` output | Should stay in the range |
|---|---|---|---|
| Clean, edits on lines 1 and 3 of one file | 126 B | 0 B | No |
| Clean, edits in different files | 0 B | 0 B | No |
| Conflict, resolved with `checkout --ours` | 0 B | 232 B | Yes |
| Conflict, resolved by hand-editing | 137 B | 240 B | Yes |
| `-s ours`, drops `main`'s new file | 0 B | 126 B | Yes |

`--remerge-diff` gets all five right, and `--cc` gets two wrong. Some notes for the fix:

1. Use `git show` or `git log -1`, not `diff-tree`. `git diff-tree --remerge-diff` aborts on 2.44 with `BUG: log-tree.c:1059: did a remerge diff without remerge_objdir`.
2. `show` is porcelain and reads user config, so pass `-c log.showSignature=false --no-ext-diff --no-textconv --format=`. Otherwise a signed commit or an external diff tool could print output for a clean merge.
3. `--remerge-diff` needs git 2.36 or later. It writes its temporary objects to a scratch object directory and removes them afterward. A second option is `git merge-tree --write-tree p1 p2` (git 2.38), compared against `<merge>^{tree}`, with a conflict exit meaning "keep it". That one is plumbing, but it writes the merged objects into the repository.
4. research.md R3 states the `--cc` rule and its rationale ("`--cc` ... prints nothing for a clean merge"), so R3 changes along with the code.
5. The new test at tests/test_review.py:L266 covers only a resolution that differs from both sides. Add cases for `checkout --ours`, `-s ours`, and the nearby-edit clean merge in the next finding.
