## Review: 2387e7b (r4)

fix(spec-store): read the code checkout named as the spec root as in_repo.
Files: `wfctl/_spec_store.py`, `tests/test_spec_store.py`.

The fix works only when the agent is in the main checkout. In a linked worktree, which is how this project runs every feature, `"spec_root": "."` still reads as `store`. I reproduced it: `wfctl store specs` committed the spec dir onto `main` and pushed `origin/main`.

## Findings

BLOCKER  wfctl/_spec_store.py:L188 — The new check compares the root with the top of `repo` only. A `"spec_root": "."` relative value is anchored to the directory of the manifest that declared it (`_paths._manifest_root`), and `install-skills` and `wfctl spec-root` record it in the main checkout's manifest. As a result, from a linked worktree `spec_root(wt)` resolves to the main checkout, while `repo_root` is the worktree. `top == top_level(repo)` is false, so `owns_branch(main_checkout, worktree)` runs. It leaves the main checkout out of the branches already taken, finds `main` held by no other worktree, and passes. That is FR-011 broken in the layout the fix was written for.

  Reproduced in a scratch repo, with a bare `origin`, a main checkout on `main` declaring `{"spec_root": "."}`, and a linked worktree `wt-42` on `42-feature`:

  | call | result |
  |---|---|
  | `layout(main, main)` | `in_repo` (the commit's case, fixed) |
  | `layout(wt, wt)` | `in_repo` |
  | `spec_root(wt)` | the main checkout |
  | `layout(spec_root(wt), wt)` | `store`, remote `origin`, upstream `origin/main` |
  | `store(<main>/42-feature, "42-feature", wt)` | `stored`. `main` HEAD moved to `specs(42): store spec.md`, and `origin/main` moved |

  → Turn away the main checkout as well as `repo`'s own top. Those are the only two places a relative `spec_root` can resolve to, since it is anchored to either `repo_root` or `main_checkout(repo_root)`. git always lists the main worktree first in `git worktree list --porcelain`, so a stdlib-only helper can read it there (`_paths` should not be imported, given the module's guard-import constraint):

  ```python
  if top in (top_level(repo), _main_worktree(repo)):
      return Layout("in_repo", root)
  ```

  Add `test_the_main_checkout_named_from_a_linked_worktree_is_in_repo`, which asserts `layout(project, <linked worktree>).kind == "in_repo"`. Also add one `store()` test from the worktree that asserts `not_applicable` and an unmoved `project` HEAD, because that is the outcome the commit message promises.

WARNING  wfctl/_hook.py:L123 — The worktree guard's docstring says it applies "the same rule the store applies before it commits on its own, so the guard never refuses a hand commit in a folder where the store commits, or the other way round". After this commit the two disagree. `layout` turns the code checkout away, but the guard's `owns_branch(main_checkout, here)` still passes. That means the guard counts the main checkout as a shared store root and allows writes there from a worktree. The commit message gives a good reason not to put the check inside `owns_branch`, because the guard passes it whatever directory the agent stands in. However, the guard already calls `top_level` per target, so it can apply the same main-checkout exclusion to its `shared` roots. → File a follow-up, or fix it alongside the blocker so the guard and the store keep one rule.

NIT  wfctl/_spec_store.py:L156-159 — Docstring item 2 now says "and so is the code checkout itself". Once the blocker is fixed, say "the main checkout or this worktree's own checkout", so the next reader knows a sibling worktree of the code repository is not covered (see the note under Correctness).
