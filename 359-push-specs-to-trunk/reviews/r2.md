## Review: ea9efe1..e425ffa (#359, store spec dirs in the spec store) — reviewer r2

The change does what the spec and `contracts/cli.md` promise, and I found no
blocker. One warning should be fixed. A store can fail for no real reason
when another session's `wfctl status` or `check specs` runs at the same
moment, because the read side takes git's index lock and the store's own lock
doesn't cover it. The rest are nits.

Checks run against the head:

- `uv run pytest -q`: 2650 passed.
- `uv run ruff check wfctl/ tests/`: clean.
- `uv run mypy wfctl/`: clean.
- I also built throwaway repos in my scratchpad, with a local bare remote, to
  reproduce the findings below. I ran nothing that writes into the worktree
  or the real spec store. The reads I timed against the real store ran with
  `GIT_OPTIONAL_LOCKS=0`, so they didn't rewrite its index.

### Findings

WARNING  wfctl/_spec_store.py:L47-52, L220-223 — The readers take git's index lock, and the store's flock doesn't cover them, so a store can fail with `index.lock: File exists` → add `"GIT_OPTIONAL_LOCKS": "0"` to `_quiet_env`.

- **Scenario:** two worktrees are past `implement`. In worktree A, the
  removal hook runs `wfctl store specs`. At the same moment, worktree B runs
  `wfctl status`, `next`, or `resume`, or someone runs `wfctl check specs`.
  All of those call `unstored()`, which runs a plain `git status` in the
  same spec store. By default, `git status` refreshes the index and writes it
  back while holding `.git/index.lock`. If A's `git add`, `git commit`, or
  `git merge` lands inside that window, git refuses to run and the store
  returns `git_failed`. By hand that is exit 1, and at removal it is a
  warning that leaves the files uncommitted.
- **Why the flock doesn't help:** `_lock` serialises store against store
  only. Research R5 rejected retrying on `index.lock` because the flock
  covered the whole sequence. That holds between stores, but not between a
  store and a reader.
- **How I confirmed it:**
  1. In a scratch repo, I touched two tracked files and ran a plain
     `git status --porcelain -- a`. The mtime of `.git/index` changed
     (1792096543 → 1792096545), so status rewrote the index under the lock.
     With `GIT_OPTIONAL_LOCKS=0`, a second status left the mtime unchanged.
  2. With `.git/index.lock` present, `_spec_store.store(...)` returned
     `git_failed | fatal: Unable to create '.../store/.git/index.lock': File exists.`
     Once the lock file was gone, the same call returned `stored`.
- **Impact:** a rerun clears it and nothing is lost, which is why this is a
  warning and not a blocker. The window is milliseconds, but every view calls
  `build_report`, and the store-specs pass runs `git status` in the shared
  store on every one of those calls once `implement` is done.
- **Fix:** the env var only affects optional locks. The store's own
  writes still take the lock they need, and the reads stop taking one.

NIT  wfctl/_spec_store.py:L229, L242 — `check specs` lists a file at the top of the store as if it were a spec dir, and no wfctl command can clear it → in `unstored`, count only paths that contain `/`.

- **Scenario:** you edit the store's `.gitignore`. `check specs` then prints
  `.gitignore    uncommitted: 1 file` and exits 1. `store specs` commits
  only a branch's folder, so it never clears the entry, and the only way
  out is a hand commit, which the end-session text advises against.
- **How I confirmed it:** I ran `unstored(store, ["."])` after editing
  `.gitignore` in a scratch store. It returned
  `[Unstored(name='.gitignore', uncommitted=1, ...), Unstored(name='7-x', ...)]`.
  The real store tracks `.gitignore` at its top.

NIT  wfctl/_spec_store.py:L540, L735 — The store prints `✓ stored 0 files` when its unpushed commits cancel out → fall back to the names from `log @{u}..HEAD`, or leave the count out when `files` is empty.

- **Scenario:** two unpushed commits in the spec dir, one that adds `b.md`
  and one that removes it. `unstored()` reports the spec dir as unpushed,
  but the diff against `@{u}` is empty.
- **How I confirmed it:** in a scratch repo, `store()` returned `stored` and
  printed `['✓ stored 0 files → origin/trunk (00e0c34)']`.

NIT  wfctl/_spec_store.py:L709-710 — The commit subject names `files[0]`, but `files` is the diff against `@{u}`, so the named file can come from an earlier unpushed commit rather than this one → build the subject from `diff --cached --name-only HEAD -- <dir>`, or accept the inaccuracy and say so in the docstring.

NIT  wfctl/_spec_store.py:L19 — `import fcntl` at module scope makes every `wfctl` command fail to import on a platform without fcntl, since `_evidence` imports `_spec_store` at its top and the guard imports it too → move the import into `_acquire` or `_lock`.

### Passes run

**1. Correctness.** I traced `store` → `_store` → `_merge_failure` and
`_network_failure`. I also traced the pass reader through `_pass_states`, the
roll-up, and `next_step_content`'s new `block_action` arm, in both
`build_report` and `next_cmd`, and `check_specs_cmd` through
`worktree_branches` and `resolve_spec_dir`. Then I checked the code against
FR-001 to FR-027 and every output block in `contracts/cli.md`. Things I
confirmed hold:

- `git commit -- <dir>` (`--only`) leaves other staged paths staged, and it
  commits deletions after `add -A`.
- The `MERGE_HEAD` check runs before the index check, so a conflict is always
  aborted.
- A merge left in progress is reported, not aborted.
- `[rejected]` does not match `[remote rejected]`.
- Fetch and push each have a 60-second timeout.
- A git failure in the pass reads `in_progress`, never `done`.
- The pass reader runs only once `implement` reads `done` (R14).
- `committable`'s refactor onto `owns_branch` keeps the old behaviour, early
  returns included.

The two failures I found, the index-lock race and the zero-file count, are
listed above. Test coverage is broad: about 60 new tests cover each merge
failure kind, the lock wait and the lock timeout, the no-upstream and
detached layouts, the "In progress" split, and the removal paths.

**2. Security.** I found nothing to report:

- Every git call is an argv list, so no shell is involved.
- Pathspecs come from existing folder names, and git ref names can't hold
  pathspec magic characters.
- `GIT_TERMINAL_PROMPT=0` and ssh `BatchMode` stop an unattended run from
  waiting on a credential prompt.
- `core.sshCommand` is kept rather than replaced.
- Output is printed with `markup=False`, so a path can't inject rich markup.
- `_check_remote` and the conftest fixture stop tests from pushing to a real
  remote.

One residual risk is outside this diff. A spec root that a committed
manifest sets could point at an unrelated repository with an upstream, and
removal would then commit and push a folder named for the branch there. That
only happens if the folder exists, and AGENTS.md already warns about
committed manifests.

**3. Architecture.** `_spec_store` sits in the domain band. It imports
`_paths` and `_tracker` inside `_subject` only, and it imports nothing from
`cli`, `typer`, or `rich`, which `test_the_commit_path_never_imports_typer_or_rich`
checks. Moving the ownership rule out of `_hook` removes a duplicated copy,
and the guard and the store now share one rule. The diff adds no third-party
dependency. The one drift I found is that the layout wording is split across
three tables: `_NOT_APPLICABLE`, `_ROOT_LAYOUT`, and `_evidence._STORE_SKIPPED`.
The module docstring says the wording lives in one place, but that's not
quite true. I left this as a note rather than a finding, because each table
words a different context.

**4. Readability.** Names are accurate, and the comments explain why, as
AGENTS.md asks. The only findings here are the positional `StoreResult`
construction and the length of `_store`, both listed above. `report_lines`
is long, but it reads as a table of outputs, and splitting it wouldn't help.

**5. Performance.** I timed the reads against the real store (55 unstored
spec dirs, with `GIT_OPTIONAL_LOCKS=0`):

| Read | Time |
|---|---|
| `layout` | 36 ms |
| `unstored` for one spec dir | 19 ms |
| `unstored` for the whole root | 71 ms |

So the pass adds about 55 ms to `status`, well inside SC-006's 0.5 seconds.
`check specs` costs 2 git calls however many spec dirs there are. The guard
path now runs `_common_dir(here)` and `worktree list` once per shared root
instead of once in total. There are 2 shared roots and this path only runs on
a refusal, so the cost is negligible.
