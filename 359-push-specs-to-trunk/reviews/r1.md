### Findings

WARNING  wfctl/_spec_store.py:L562 — `git merge --no-edit @{u}` takes its
behaviour from the spec store's git config. With `merge.autoStash=true` set,
the merge stashes other branches' edits and then pops them back, which breaks
FR-004 ("never stashes") and SC-005 ("byte-for-byte unchanged").
*Failure:* the remote edits `other/f.md`, and another branch has an unstaged
edit to the same file. Without the setting, the store correctly returns
`merge_refused`. With it, the store returns `stored` and prints
`✓ stored 1 file → origin/trunk`. Afterwards `other/f.md` holds conflict
markers, `git status` shows `UU other/f.md`, and `stash@{0}: autostash` holds
the other branch's edit. Every later store from any branch then fails at
`git commit` because the index has unmerged entries, and nothing tells the
user why. `merge.ff=only` breaks it a second way: every store ends
`git_failed` with "Not possible to fast-forward".
*Confirmed:* `t_autostash.py` in my scratchpad, run once with the setting and
once without.
→ Pin the merge's behaviour on the command line:
`git("merge", "--no-edit", "--no-autostash", "--ff", "@{u}")`. Add a
regression test that sets `merge.autoStash` in the fixture store.

WARNING  wfctl/_spec_store.py:L169-179, wfctl/_evidence.py:L1567 — `layout()`
treats a spec store with a detached HEAD as a layout chosen on purpose. The
`store-specs` pass then reads `skipped`, which does not block, so the pipeline
moves past an unstored spec dir. A store in that state is broken for the
moment, for example during an interrupted `git rebase` or after
`git checkout <sha>`.
*Failure:* in the pfms layout, where the spec store is a worktree of the code
repo, a detached HEAD falls through to `in_repo`.
`store specs` then prints `ℹ <store>/1-a is inside the code repository — not
committed, not backed up` and exits 0. Both halves of that line are false: the
folder is outside the code repo, and its branch has an upstream. The pass
reads `skipped` with "inside the code repository; not backed up", and
`implement` reads done. In a clone of its own, the same state reads
`unmanaged`, which prints "not backed up anywhere". The spec says unattended
runs must store their own specs (SC-001), and here the run passes the step
while storing nothing. Any other failed git read in `layout`, such as a
`safe.directory` refusal, also comes back as `unmanaged` and so as `skipped`.
*Confirmed:* `t_detached.py` in my scratchpad prints
`detached: Layout(kind='in_repo', …)` and then `store: not_applicable exit 0`
with the line above. The existing test
`test_a_clone_of_its_own_with_a_detached_head_is_unmanaged` pins the clone
case on purpose, and no test covers the worktree case.
→ Keep "the store does not commit here", but make it a failure rather than a
layout. When `top == realpath(root)` and the root has its own repository or
its own worktree, but no branch is checked out, return a kind such as
`store_detached`. Have `store` return a failing outcome for it (`git_failed`
with "the spec store has no branch checked out" would do) and have the pass
read `in_progress`. The rule that a broken read must never come out as `done`
should also cover `skipped`.

WARNING  wfctl/cli.py:L1534-1545 — `delete:`/`yagni:` this branch can never
run. It sits inside `if … not _archive.is_inside(repo_root, spec_dir)`, and
`stops_removal` is true only when `inside_worktree` is true, so it is false
here every time. The comment above it says so ("false for every result here
today"). It is guarding against #40, which has not merged.
`test_removal_reads_stops_removal_and_not_the_exit_code` covers it only by
faking a `StoreResult` this code cannot produce. If it ever fired, it would
print "N spec file(s) could not be archived", which is wrong for a spec dir
nobody tried to copy.
→ Delete the branch and its test. Add the rule in #40, where a spec dir
inside the worktree reaches this code. `stops_removal` and `inside_worktree`
can go too, since nothing on this branch reads them except their own tests.

NIT  wfctl/_spec_store.py:L57-60 and L220-222 — the readers' `git status` takes
`index.lock` to refresh the index. The pass runs it on every `wfctl status`
once `implement` is done, in every worktree. If a store's `git add` runs at
the same moment, it can fail with "index.lock: File exists" and end
`git_failed`. → Set `GIT_OPTIONAL_LOCKS=0` in the environment of the read-only
calls (`_read` and `unstored`'s status call), not in `_Git`'s.

NIT  tests/test_check_specs.py:L230 —
`test_git_missing_from_path_is_a_one_line_failure_not_a_traceback` tests a
path that a missing git cannot reach. `get_repo_root` runs git first, and
`layout()` turns an `OSError` into `unmanaged` before `unstored` is called.
The test gets there only by patching `unstored`. The `except` it covers is
reachable by a failing `git status` in a store that `rev-parse` accepted.
→ Rename the test after that case, or drive it with a store whose index is
unreadable.

NIT  wfctl/_spec_store.py:L512-515 — `result()` builds `StoreResult` from
twelve positional arguments. Swapping two adjacent fields of the same type
(`folders` and `paths`, or `sha` and `message`) would type-check and silently
swap the values. → Pass them by keyword.

NIT  wfctl/_evidence.py:L1531 — `_STORE_SKIPPED` is a third table of layout
wording, next to `_NOT_APPLICABLE` and `_ROOT_LAYOUT` in `_spec_store`, and it
is keyed by `str` rather than `LayoutKind`. The module docstring says the
wording lives in one place so that it cannot drift. → Move it next to the
other two as `dict[LayoutKind, str]`.

NIT  pyproject.toml:L57 — an unrelated edit removes the space in
`"real_install_origin: reads"`. pytest still parses the line. → Restore the
space.

NIT  docs/architecture/views/current-state.md:L31 — the drawing gives
`_spec_store 237`, but the module has 844 lines. → Change it to 844.

NIT  wfctl/agents/commands/store-specs.md:L3 — `allowed-tools` pre-approves
`wfctl store specs*`, which is a push. Section 2 says the host is the only gate
on a push. In a host that honours frontmatter allows, the refusal path in
section 2 never runs. `speckit.analyze.md` does the same for
`wfctl issue create*`, so this matches existing practice. → Leave it if that
is intended. Otherwise drop the pre-approval so that the host's classifier

### Passes run

1. **Correctness.** I compared the code with spec.md FR-001 to FR-027,
   contracts/cli.md and data-model.md. I traced `store` → `_store` →
   `_merge_failure`, `_network_failure`, `unstored`, `layout`, `owns_branch`
   and `_lock`, and the CLI paths `store_specs_cmd`, `check_specs_cmd` and
   `archive_specs_cmd`. I also traced `next_step_content`'s new `block_action`
   rule through both callers, `build_report` and `next_cmd`, and checked that
   pass readers only run once `implement` is `done` (`_pass_states`). In
   throwaway repos I confirmed that `git log -z --format= --name-only` puts no
   stray newline before path names, so the folder names are clean. I also
   reproduced the autostash and detached-HEAD findings. Exit codes match the
   data-model table. The commit pathspec leaves other staged paths staged.
   `[rejected]` does not match `[remote rejected]`. The `MERGE_HEAD` check
   comes before the index check, so a conflict is never misread as staged
   files. The R15 case where an `already_stored` result leaves a
   `store-specs` hold standing is a documented decision, so it is not raised.
2. **Security.** All subprocess calls take argument lists, and none goes
   through a shell. Paths are printed with `markup=False`. `GIT_TERMINAL_PROMPT`
   and `BatchMode` stop the store from hanging on a prompt. The conftest
   guard's `pytest.fail` is a `BaseException`, so the store's `except` cannot
   swallow it. I checked whether a `GIT_DIR` exported in the shell could
   redirect the commit into the code repo. `owns_branch` then sees the code
   branch checked out in another worktree and refuses, so it cannot. I checked
   hooks in pfms: the relative `core.hooksPath` (`.husky/_`) does not exist in
   `pfms-specs`, so no code hooks run on spec commits. The pre-approved push is
   the only item, filed above as a NIT.
3. **Architecture.** `_spec_store` sits in the domain band and imports only
   downward (`_paths` and `_tracker`, lazily). `_hook` reaches it only on the
   refusal path, and the module has no `typer` or `rich` at module scope.
   Moving `_hook.committable` onto `owns_branch` keeps its old behaviour
   (`test_guard_entry` passes). Layout wording is spread over three tables,
   filed above as a NIT. I added no dependency.
4. **Readability and simplification.** `_store` is about 80 lines but reads in
   order, step by step. `report_lines` is a long `if` ladder that matches the
   contract one block per outcome, and a dispatch table would not make it
   shorter. The comments explain why each rule exists, as AGENTS.md asks. The
   positional `StoreResult` call is filed above.
5. **Performance.** Once `implement` is done, the pass costs about nine git
   subprocesses per `status`: about seven in `layout` and `owns_branch`, and
   two in `unstored`. That is well under SC-006's 0.5 s. `check specs` makes
   two git calls for the whole root, plus one `resolve_spec_dir` per worktree.
   `_hook.committable` now repeats `worktree list` and `_common_dir(here)` for
   each shared root, one or two extra git calls on the refusal path only. That
   is not worth a finding. The index-lock contention is filed above.
6. **Over-engineering.**
   - `wfctl/cli.py:L1534: delete: stops_removal check that cannot be true on
     this branch. Nothing replaces it, and #40 adds it where it can fire.`
   - `wfctl/_spec_store.py:L313-345: yagni: inside_worktree and stops_removal,
     read only by the dead branch above and their own tests. Drop them with it.`
   - `tests/test_archive_specs.py:L628: delete: test of a StoreResult the code
     cannot produce.`
   - `_check_remote` (a no-op in production) and `lock_timeout` are test seams
     that guard against pushing to a real remote and against 10-second waits.
     They are kept, not flagged.
