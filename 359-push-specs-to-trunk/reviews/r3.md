### Findings

WARNING  wfctl/_spec_store.py:L220 (with L47 `_quiet_env`) — The readers take the spec store's `index.lock`, so a store that runs at the same moment fails with `git_failed`.

`unstored()` runs `git status`. Unless `GIT_OPTIONAL_LOCKS=0` is set, git takes the index lock for the whole call so that it can refresh the stat cache. The pass runs this read on every `wfctl status`, `next`, and `resume` from any worktree that has finished `implement`, and `check specs` runs it over the whole root. None of these reads takes the store's `wfctl-store.lock`. When one of them overlaps a store's `git add`, `git commit`, or `git merge`, git fails at once with `fatal: Unable to create '.../index.lock': File exists.`, and the store reports `✗ store failed`. The worst case is removal. There the failure is only a warning, removal goes ahead, and the branch's last files stay uncommitted with no branch left to store them, which is the gap #359 exists to close.

Confirmed in a scratch store with 3,000 files: a background thread called `unstored(store, ["."])` in a loop while 40 stores ran. 21 of the 40 stores ended `git_failed` on `index.lock`. With `GIT_OPTIONAL_LOCKS=0` set, all 40 ended `stored`.

Fix: set `GIT_OPTIONAL_LOCKS=0` in the environment the read-only calls use (`_read` and `unstored`). Git provides this variable for exactly this case, a background `git status`.

WARNING  wfctl/_spec_store.py:L164-179, wfctl/_evidence.py:L1566-1568 — When git cannot answer, the pass reads `skipped` instead of `in_progress`, and the test that claims to cover this does not.

The reader's docstring says "A git failure reads `in_progress` … The one answer a broken read must never give is `done`." But `layout()` turns every git failure into `unmanaged`, because `_read` returns None and the code falls through to the last branch. As a result, the pass reads `skipped` with "not backed up anywhere: <root>". `skipped` doesn't block the pipeline, so an unattended run finishes with the spec dir unstored. The guarded `try` around `unstored()` is never reached, because `layout()` already absorbed the failure.

`test_git_missing_from_path_is_a_one_line_failure_not_a_traceback` monkeypatches `unstored` alone. With git really missing, `layout` would already have answered `unmanaged`, and `check specs` would print the `ℹ … nothing there can be pushed` line and exit 0. The scenario that test names can't reach the code it asserts on. A realistic trigger is git's `safe.directory` "dubious ownership" refusal on a spec store owned by another user.

Confirmed: `layout(store, code)` returns `store`. With `PATH=/nonexistent`, the same call returns `unmanaged`.

Fix: have `layout` tell "git answered: not a repository" apart from "git failed". For example, raise, or return a distinct kind when `rev-parse --show-toplevel` exits with an error other than "not a git repository". The pass and `check specs` would then read that as `in_progress` or exit 1. Rewrite the test to break git under `layout` and not to patch `unstored`.

NIT  wfctl/_spec_store.py:L536-543 — The commit subject can name files that aren't in the commit.

`files` is everything that differs from `@{u}`, which includes files from an earlier unpushed commit, and `_subject` builds the subject from it. Confirmed: with `359-x/a.md` committed but not pushed and `359-x/b.md` new, the store's commit holds only `b.md` and is titled `specs(359): store a.md and 1 other`. The output line is right, since it describes the push. The commit history is wrong.

Fix: build the subject from `git diff --cached --name-only HEAD -- <dir>` and keep `files` for the output.

NIT  wfctl/_spec_store.py:L797-799 — The `git_failed` headline can be a hint line instead of the error.

`report_lines` prints the first line of git's text. With `merge.ff=only` configured and a diverged remote, the first line is `✗ store failed: hint: Diverging branches can't be fast-forwarded…`, and the `fatal:` line is buried nine lines down. Confirmed in a scratch store.

Fix: prefer the first `fatal:` or `error:` line for the headline, or pass `-c advice.diverging=false`. Passing `--ff` to the merge would also stop a global `merge.ff=only` from breaking every store.

NIT  wfctl/_spec_store.py:L229, L242 — A file at the top of the spec store is listed as a spec dir.

`_folder()` takes the first path component, so an untracked or edited top-level file, such as a `README.md` or a changed `.gitignore`, shows up in `check specs` as `✗ 1 spec dir not stored` with the file's name, and the command exits 1. Confirmed with an unignored `.DS_Store`: the output was `.DS_Store    uncommitted: 1 file`. Both real stores ignore `.DS_Store`, so today this needs some other top-level file.

Fix: skip entries with no `/` in `unstored`, or list them under their own heading.

NIT  wfctl/_spec_store.py:L309, L361, L527, L762; wfctl/_evidence.py:L1530 — The comments cite plan-review IDs (`PR-009` to `PR-015`).

These are the first plan-review IDs in Python source. In code, `PR-010` reads as a pull request number. The IDs are also numbered per feature, so the next feature's `PR-010` will mean something else, and the file they point at lives on `specs-trunk`, outside the repository. The `research R7` citations follow an existing convention, but these don't.

Fix: drop the IDs and keep the reasoning, which the comments already state in full.

NIT  pyproject.toml:L57 — An unrelated edit deleted the space after `real_install_origin:`.

Pytest still parses the marker name, so nothing breaks, but the line is an accidental change in a diff that has no reason to touch it.

Fix: restore `real_install_origin: reads`.

NIT  tests/conftest.py (`_spec_store_reaches_only_the_tests_own_remote`) — The guard runs after the commit.

`_check_remote` is first called after `git add`, `git commit`, and the `branch.*.merge` read. A test that resolves the developer's real spec store has already committed in it before the guard fires, and the next real store pushes that commit. In practice the commit would hold the real branch's own files, so the damage is small.

Fix: call the check once, before the lock, on the push URL.

NIT  wfctl/cli.py:L1541-1545, wfctl/_spec_store.py:L330-345, L433 — yagni: removal checks a condition that can't be true.

`archive_specs_cmd` calls the store only when `not _archive.is_inside(repo_root, spec_dir)`. `StoreResult.inside` is computed with the same containment rule, so `stops_removal` is always False there, and the comment says so. The data model asks for the property ahead of #40, so I'd keep the property. The `_ArchiveIncomplete` raise and its `rglob` count in `cli.py` are dead until #40 lands, and the containment rule is now written in two places.

Fix: compute `inside` with `_archive.is_inside` so the rule exists once, and drop the dead raise until #40 needs it.

2. **Security.** Every subprocess call takes an argument list, so no shell is involved, and branch names reach git only through `-m` and pathspecs. Ref-name rules forbid `*`, `?`, and `[`, so a branch name can't inject pathspec magic. `_quiet_env` adds `BatchMode` without dropping a configured `GIT_SSH_COMMAND` or `core.sshCommand`, and `GIT_TERMINAL_PROMPT=0` keeps a removal hook from hanging on a credential prompt. Push is never forced, and it goes only to the remote and branch the spec store tracks.

   The `/store-specs` wrapper pre-approves `wfctl store specs*`. `decompose` and `end-session` already pre-approve outward `wfctl` verbs the same way, so this isn't new exposure. The test seam `_check_remote` is a no-op in production. No findings beyond the conftest ordering NIT.

3. **Architecture.** `_spec_store` sits in the domain band, uses only the standard library at module scope, and imports `_paths` and `_tracker` lazily. `_hook` imports it lazily too, so the guard's import cost is unchanged, and `current-state.md` adds the module to its `layers` block and its box art. The readers and the store share one definition of "stored". `report_lines` and `check_lines` keep the plain output in the module for removal and the CLI to share. That puts strings in a domain module, but the docstring explains why, and I accept it. The project has no new dependency. The one duplication is the containment rule (NIT above).

4. **Readability and simplification.** Names are honest and comments explain why. `_store` (85 lines) and `report_lines` (78 lines) run past the 50-line guideline. Each reads as a straight sequence of steps, so I didn't flag them. I flagged the plan-review ID citations and the stray `pyproject.toml` edit.

SC-006's 0.5-second budget holds, and the pass is evaluated only once `implement` reads done. The guard's `committable` now runs `worktree list` once per root instead of once per call.
