# Review r8: commit 8f63fc2

Target: `git show 8f63fc2`, which touches `wfctl/_spec_store.py`, `tests/test_spec_store.py` and `wfctl/agents/commands/store-specs.md`.

The change does what it says. A file that an ignore rule keeps out of the store is now named in a final `ℹ` line, and both cases from the commit message are covered by a test. I found no blocker. The main open point is that on Andre's real spec store the new line fires for `.DS_Store` on every store of a folder Finder has opened, and the spec's contract files were not updated to match.

## Findings

WARNING  `wfctl/_spec_store.py:L853-856` and `store-specs.md:L61-63`: the line fires on deliberate rules every run, and the commit does not say so. The real store at `/Users/andremarin/Development/wfctl-specs` ignores `.DS_Store` through its own `.gitignore:1`, and `git ls-files --others --ignored --exclude-standard` lists 15 spec dirs (plus the root) holding one today. Every store of those folders will end with `ℹ 1 file not stored, ignored by the store's rules: .DS_Store`, and the wrapper tells the agent to relay it each time. The commit keeps ignored files out of `check specs` because a deliberate rule such as `*.tmp` is something wfctl can do nothing about. The same reasoning applies at lower cost to a line that repeats forever: the reader learns to skip it, which removes the value it has for the rule written by mistake. wfctl cannot tell the two kinds of rule apart, so this is the author's call. The bounded fix is either to accept the noise and say so in the `ignored` docstring with `.DS_Store` as the example, or to print the matching rule from `git check-ignore -v` (for example `.gitignore:1:.DS_Store`) so a person can see at a glance which rule is deliberate.

WARNING  `contracts/cli.md:L7-117` and `data-model.md:L48` in the spec dir: the contract the code cites was not updated. `report_lines` says it prints what "`contracts/cli.md` gives", and `StoreResult` cites `data-model.md §Store result`. Neither file mentions ignored files (`grep -i ignor` finds nothing in either, or in `spec.md`), and the `/store-specs` section at `cli.md:L212` does not cover the wrapper's new paragraph either. Add the `ℹ` line to the `store specs` output section, add `ignored` to the Store result table, and note it under `/store-specs`.

NIT  `store-specs.md:L61`: "Any of those" scopes the line to the exit-0 outcomes, but `report_lines` appends it to every outcome reached inside `_store`, the exit-1 failures included. It also never appears for `not_applicable`, which is one of "those", since that outcome returns before `_store` runs. Write "Any outcome can end with an `ℹ` line ...".

NIT  `store-specs.md:L62`: "never will be" overstates it. Removing the rule, or `git add -f`, would store the file. Write "and the store will not take them while the rule stands".

NIT  `wfctl/_spec_store.py:L605-607`: an ignored directory expands to every file under it on one line. In a scratch repo with `drafts/` ignored, `ls-files` printed `drafts/one.md` and `drafts/deep/two.md` separately, so a stray `node_modules/` or `.venv/` in a spec dir would print thousands of names. Cap the list the way `_subject` does ("a, b and 37 others"), or pass `--directory` and count entries rather than files.

NIT  `tests/test_spec_store.py:L576-616`: the docstring claims the line appears "whatever the outcome", but only `stored` and `already_stored` are tested. A one-line unit test of `report_lines(StoreResult("conflict", ..., ignored=("x.log",)))[-1]` would pin the claim cheaply, and one for `committed_not_backed_up` would cover the no-upstream path that also computes `ignored`.

## Passes

1. Correctness. I traced `_store`, `_read`, `_in_folder`, `unstored`, `report_lines` and both `report_lines` callers in `cli.py` (`store specs` at L5874, removal at L1533). The read runs under the lock and before `unstored`, so `already_stored` carries the list too. `_read` strips whitespace, but `-z` output ends in `\0`, so a file name ending in a space survives. In a scratch repo, names with a space, a non-ASCII character and nested ignored folders all came back correctly relative to the spec dir. A failed `ls-files` reads as `None`, which becomes an empty tuple, so it cannot fail a store. Tracked files that match a rule are not listed, which is correct, since `git add -A` still stages them. Exit codes and `stops_removal` are unchanged. The ignored list is read before the merge, so if the upstream changed `.gitignore` the line describes this run's commit rather than the merged state, which I consider correct. `uv run pytest tests/test_spec_store.py -q` gives 79 passed. `ruff` and `mypy` on the changed files are clean.
2. Security. File names reach the terminal through `_print_plain`, which prints with `markup=False` and `highlight=False`, so a name such as `[red]x.log` cannot inject rich markup. The new git call takes no input from outside the store and runs under `_quiet_env` like every other call in the module. Nothing found.
3. Architecture. The change adds one field with a default to `StoreResult` and splits `_outcome_lines` out of `report_lines`, so the outcome wording stays in one place and the appended line cannot be forgotten by any branch. `unstored` and `check specs` are left untouched on purpose, and the docstring explains why. No new dependency. The only architectural gap is the contract drift above.
4. Readability and simplification. Names are clear (`ignored`, `_outcome_lines`). The comment at L603-604 explains why a failure reads as none, which is the "why" the project asks for. The new docstring paragraphs follow the module's style. L856 runs to about 110 characters, which matches other lines in the file and is not checked by the lint rules. The clean-code catalog gave no further finding.
5. Performance. One extra local `git ls-files` per store, with no network, cost in the low milliseconds. The output is unbounded for a large ignored directory, which is the NIT above.
6. Over-engineering. The code is minimal: one call, one field and a five-line wrapper. In the wrapper, "Include the line when you report." repeats section 1's "Report what it printed, word for word", so it can go, while the sentence saying it is not a failure is worth keeping.

`store-specs.md:L63: delete: "Include the line when you report." Section 1 already requires the output word for word.`
