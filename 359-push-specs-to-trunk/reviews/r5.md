## Findings

BLOCKER  wfctl/_spec_store.py:L188 — the fix covers `"spec_root": "."` only when the manifest that declares it sits in the same checkout as `repo_root`. The ordinary wfctl case is a linked worktree whose own manifest has no `spec_root`, so `_paths._root_declaration` falls back to the main checkout's manifest. There `"."` resolves to the main checkout (`_manifest_root` anchors a relative value to the declaring directory). `top_level(repo)` is the worktree, so the new guard does not fire, `owns_branch(main, worktree)` passes because no other worktree holds `main`, and `layout` returns `store`. `store()` then commits the feature dir onto `main` and pushes `origin/main`. This is the exact failure the commit message describes, and it still happens → reject the main checkout as well as the caller's own top. `_root_declaration` reads a manifest from exactly those two places, so those are the two checkouts `"."` can name:

```python
code_tops = {top_level(repo)}
common = _common_dir(repo)
if common and os.path.basename(common) == ".git":
    code_tops.add(os.path.dirname(common))
if top in code_tops:
    return Layout("in_repo", root)
```

The `.git` basename test is the same one `_paths.main_checkout` uses to keep bare layouts out. Add a test: `layout(project, worktree_of_project)` must be `in_repo`.

Evidence, from a scratch run of the code at 2387e7b (`r5_store_probe.py` in the review session's scratchpad). Main checkout on `main` tracking a bare `origin`, a linked worktree `project-359` on `359-feature`, and `{"spec_root": "."}` in the main checkout's manifest only:

```
layout: Layout(kind='store', root='.../project', remote='origin', upstream='origin/main')
store outcome: stored
origin/main log:
2fb33e5 specs(359): store spec.md
359-feature/spec.md
ff50339 init
```

The same probe without an upstream gives `store_no_upstream` for that root, and `in_repo` for `layout(main, main)` and `layout(wt, wt)`. So the commit fixes the in-place case and leaves the linked-worktree case open.

WARNING  tests/test_spec_store.py:L279 — the regression test covers only `layout(project, project)`, the one shape the fix handles. It would not have caught the BLOCKER above. Its docstring also says the store "committed the feature directory onto the code branch and pushed it", but the test exercises `layout`, not `store`, and does not show a push → add the linked-worktree case beside it (see the BLOCKER). Optionally, add one `store()` assertion that the outcome is `not_applicable`, so the test proves the claim its docstring makes.

NIT  wfctl/_spec_store.py:L152-159 — the docstring's numbered kinds read as precedence: `store` first, then `in_repo` "when the first kind did not hold". The code now settles `in_repo` for the code checkout before the store rule and before `detached`. That ordering is deliberate, and it changes one outcome. A code checkout mid-rebase, named as the root, used to come back `detached` (the store failed with "check out its branch"). Now it comes back `in_repo` (`not_applicable`). That is the better answer, but the list does not say it → in item 1, add "and is not the code checkout" to the conditions, so the order of the list matches the order of the checks.

Residual, not a finding against this diff: a `spec_root` that names a *sibling* code worktree by explicit path (`../project-400`) still reads as `store`. In the probe, `layout(sibling, wt)` gave `store_no_upstream`. git forbids two worktrees on one branch without `--force`, so `owns_branch` passes for every worktree of the code repo. Git alone cannot tell a sibling code worktree from pfms's `specs-trunk` worktree. That needs a different mechanism, and it is worth a follow-up issue rather than this commit.

## Passes run

1. **Correctness.** I traced `layout`, `top_level`, `_checkout_top`, `owns_branch`, `_common_dir`, and both callers: `store()` at L490 and `_evidence` at L1568. I also traced how `spec_root` resolves (`_paths.spec_root`, `_root_declaration`, `_manifest_root`, `main_checkout`). Both sides of the new comparison are `realpath`-resolved, so symlinked roots compare correctly. `top_level` returning None (repo not in git) makes the comparison false and falls through as before. With `repo_root` given as a subdirectory, the result is still `in_repo` (probe case E). `<repo>/specs` now exits earlier with the same `in_repo` answer as before. Before the fix, `layout(project, project)` returned `store_no_upstream`, so the new test does fail without it. That leaves the linked-worktree hole (BLOCKER), confirmed end to end with a real push to a scratch remote.
2. **Security.** No new input surface. `spec_root` is manifest data and was already untrusted. The security-relevant consequence is the BLOCKER: an unattended `store specs` pushes straight to the default branch, outside PR review. No secrets, nothing logged, no shell strings built.
3. **Architecture.** The check sits in `layout` and not in `owns_branch`. The commit message's reason holds: the worktree guard calls `owns_branch(r, here)` with whatever directory the agent stands in (`_hook.committable`, L123). This makes `layout` stricter than the guard for the code checkout. The guard docstring promises they agree, and the disagreement is harmless here, because it only ever refuses the store in a place where the agent may already commit. No new dependency, so the dependency questions do not apply.
4. **Readability & simplification.** The new comment explains why it sits before the `owns_branch` rule, which is what the next reader needs. The test name is a sentence and its docstring names the failure, as `AGENTS.md` asks, though it overclaims what it covers (WARNING). The docstring precedence point is the NIT. No naming issues.
5. **Performance.** One extra `git rev-parse --show-toplevel` per `layout` call, which is a few milliseconds. `layout` runs once per `store` and once per `status` evidence read, so this is not a hot path. The fix proposed above adds one more `rev-parse --git-common-dir`. That one is already paid later in the same function on the fall-through path, so it could be hoisted and reused.
6. **Over-engineering.** Six added lines of logic and comment, one test of four lines. No dead code, no speculative flexibility, no hand-rolled stdlib.
