## Review: 8f63fc2, r9

The change does what it says. A spec dir that holds a file an ignore rule keeps out now ends its output with a line naming that file, on every path through `_store`, and exit codes and `unstored()` are unchanged. `uv run pytest tests/test_spec_store.py -q` passes (79 tests), and ruff and mypy are clean on both files.

The weak point is how often the line fires. Both real spec stores on this machine already hold ignored files in most recent spec dirs, from rules their owners wrote on purpose, so the line will show up on most stores and the one case it exists for will read like the rest.

## Findings

WARNING `wfctl/_spec_store.py:L853-857`. The line fires for deliberate rules on most stores, which buries the accidental case it was written to catch. The evidence comes from read-only `git ls-files --others --ignored --exclude-standard` runs on the two real stores:

1. `pfms-specs` has 137 spec dirs, and 61 of them hold an ignored file. Sixty of them, and almost every dir from 619 onward, hold `reviews/.dispatched`, which `fanning-out-code-review` writes into every reviewed spec dir and which the store's `.gitignore:5` ignores on purpose. Seven dirs also hold `.DS_Store`.
2. `wfctl-specs` has 163 spec dirs, and 15 of them hold an ignored `.DS_Store` (from its `.gitignore`).

After this commit, any branch that ran a review panel in pfms prints `ℹ 1 file not stored, ignored by the store's rules: reviews/.dispatched` on every store and on every worktree removal. `/store-specs` then tells the agent to repeat it. The commit message argues that a deliberate rule such as `*.tmp` shouldn't leave `check specs` red, and the same argument applies here: a line that names a deliberate rule on every run gives the person nothing to do, and they learn to skip it. When a rule like `*.md` or `reviews/` swallows a real artifact, it lands in a line people have stopped reading.

A bounded fix is to name only files that the store's committed `.gitignore` files do not account for. `git ls-files -z --others --ignored --exclude-per-directory=.gitignore -- <name>` lists the files those committed files ignore. Subtract that set from the current `--exclude-standard` set, and what is left was ignored by `.git/info/exclude` or a global excludes file, which is the rule a store owner never agreed to and the surprising one. If the full set is wanted anyway, the alternative is to keep it but print the line only when an ignored file is not a dotfile. That is cruder, and I would take the first option.

WARNING `wfctl/_spec_store.py:L605-607, L856`. The list has no upper bound, and an ignored directory expands to every file inside it. I confirmed this in a scratch repo: with `node_modules/` ignored, `ls-files --others --ignored` without `--directory` lists each `node_modules/a/b/f1.js` and so on separately. A spec dir that holds a prototype with an ignored `node_modules/`, `.venv/` or `__pycache__/` then prints one line with thousands of names, which `/store-specs` reports "word for word" and removal prints as well. The fix is to cap the names the way `_subject` already does, for example the first five and then `and {_count(n - 5, 'other')}`. `--directory` collapses ignored dirs too, but it also emitted an extra `359-x/sub/` entry for an untracked dir holding an ignored file in the same run, so the cap is the safer choice.

WARNING `contracts/cli.md` (spec dir). `report_lines` says it prints what `contracts/cli.md` gives, and the contract has no `ℹ … not stored, ignored by the store's rules` line. Neither `contracts/cli.md` nor `data-model.md §Store result` mentions `ignored`. The fix is to add the line to the contract's `store specs` output section and the field to the data model's Store result.

NIT `wfctl/_spec_store.py:L856`, "ignored by the store's rules". A file ignored by the global excludes file, or by a `.gitignore` inside the spec dir itself, is not ignored by the store's rules. A person who reads this line, opens the store's `.gitignore` and finds no match has nowhere to go next. "ignored by git in the spec store" is accurate for every source. The `StoreResult` docstring (L385, "an ignore rule of the store's") has the same wording.

NIT `wfctl/agents/commands/store-specs.md:L61-63`. "Any of those" points back at the exit-0 outcomes, but the line also ends exit-1 output. "Never will be" is not true either, since a file is stored as soon as the rule is removed. "Include the line when you report" repeats section 1, which already says to report the output word for word. A suggested rewrite:

```diff
-Any of those can end with an `ℹ` line naming files the spec store's ignore rules
-left out. They were never stored and never will be, and it is not a failure.
-Include the line when you report.
+Any outcome can end with an `ℹ` line naming files an ignore rule kept out of
+the spec store. They are not stored while the rule stands, and it is not a failure.
```

NIT `tests/test_spec_store.py`. The docstring says the line comes last "whatever the outcome", and the tests cover only `stored` and `already_stored`. One case on a failing outcome, such as `not_pushed`, or on `committed_not_backed_up` would pin that claim. There is also no test that a failed `ls-files` reads as no ignored files, but that is a one-line `or ""` and I would not ask for one.

NIT `wfctl/_spec_store.py:L866-867`. When every file in a spec dir is ignored, the first line still reads `✓ spec dir already stored on origin/specs`, for a dir that has never reached the store. The `ℹ` line under it makes the situation clear, so this is acceptable, but a distinct first line such as "nothing to store" would be accurate on its own.

NIT `wfctl/_spec_store.py:L856`. The line is 113 characters long, while the code around it wraps near 100. Lint does not flag it, since E501 is not selected.

## Passes

1. **Correctness** ran. I traced `_read` (it strips output, which is harmless here because every `-z` entry starts with `<name>/`), `_in_folder`, `unstored`, and the early `already_stored` and `committed_not_backed_up` returns, and checked the following:
   1. Tracked-and-ignored files are excluded by `--others`, which is correct because `git add -A` still updates them.
   2. A path with a space or a non-ASCII character comes through intact with `-z` (scratch run with `sub/we ird.log` and `naïve.log`).
   3. A `.gitignore` inside the spec dir counts too (scratch run with `*.md` caught `spec.md`).
   4. Outcomes returned by `store()` before `_store` runs (`locked`, `not_applicable`, `detached`) never compute `ignored`, which is fine because nothing is stored there.
   5. `ignored` is read before the merge, so a `.gitignore` change pulled in from upstream is not reflected, which is an edge case and not worth a finding.

   The findings are the noise, the unbounded list and the all-ignored first line.
2. **Security** ran. Names print through `_print_plain` with `markup=False`, so a file name cannot inject rich markup. The `ls-files` call takes a fixed argument list with `--` before the pathspec, and no shell is involved. Nothing new reaches the network. Nothing found.
3. **Architecture** ran. The change keeps `unstored()` as the single source for `check specs` and the pass, and adds the information only to the store's result, which fits the existing split. Pulling `_outcome_lines` out of `report_lines` avoids appending at about 15 return sites and is the right shape. No new dependency. The finding is the contract drift.
4. **Readability and simplification** ran against the `clean-code` catalog. The names (`ignored`, `_outcome_lines`) say what they hold, and the comment on the `ls-files` call explains why a failure reads as none, which is the right kind of comment. The findings are the wording NITs and the wrapper paragraph.
5. **Performance** ran. The change adds one `git ls-files` per store and per worktree removal, scoped to one spec dir by pathspec, which costs a few milliseconds normally. It walks into ignored directories, so cost and output grow with an ignored `node_modules/`, which is the output side of the second WARNING.
6. **Over-engineering** ran. `_outcome_lines` is not over-engineering, since it replaces 15 edits with one. The only cut is the wrapper's last sentence, which repeats section 1.
