### Findings

WARNING  `wfctl/_spec_store.py:L603-607`. In the real spec store the line names nothing except `.DS_Store`. → Decide which rule sources count before merge.

The store's own committed `.gitignore`, line 1, is `.DS_Store`. 15 of the store's ~106 spec dirs hold one, among them `102-reply-over-explains`, `69-machine-checked-done` and `86-architecture-knowledge-lifecycle`. Every ignored file in the whole store is a `.DS_Store`; there is nothing else. I ran the commit's read on `102-reply-over-explains` and got `('.DS_Store',)`. `report_lines` then prints `ℹ 1 file not stored, ignored by the store's rules: .DS_Store`.

So on this machine, every time the line fires it names a file the store owner meant to leave out. That is the "deliberate rule such as `*.tmp`" the commit itself gives as the reason not to flag ignored files in `check specs`. The wrapper tells the agent to include the line in every report, and removal prints it as well. A line that is always noise teaches the reader to skip it, and then it says nothing on the day a real file stays behind, which is the case it was added for.

Recommended fix: name only files whose matching rule is not in the store's committed root `.gitignore`. That root file is the store owner's declared, shared policy, which is the same argument the commit makes for `check specs`. Rules from `info/exclude`, the global excludes file, or a `.gitignore` inside the spec dir would still be named. It costs one call, `git check-ignore -v -z --stdin` over the listed paths; its source field tells `.gitignore` at the root apart from the rest. If the author would rather keep every rule source, say so in the commit, along with the `.DS_Store` consequence, so the next reader does not "fix" it.

WARNING  `wfctl/_spec_store.py:L855-856`. The list has no bound. → Cap it the way `_subject` already does.

`ls-files --others --ignored` with no `--directory` descends into every ignored directory. In the scratch repo, an ignored `.venv/` of 2,000 files under a spec dir made the `ℹ` line about 49 KB on one line. The wrapper asks for that line word for word. Ignored directories are exactly where large trees live, which is not true of the `files` list this copies its `", ".join` from.

Fix: print the first few names and then `and {_count(n - k, 'other')}`, the same form `_subject` uses at L830. I tried `--directory` as a way to collapse directories and it is not a clean fix: git also printed `359-x/contracts/`, a folder that is not ignored but holds an ignored file. For a spec dir ignored as a whole it printed `360-y/`, which `_in_folder` turns into an empty name.

WARNING  `wfctl/_spec_store.py:L385-389` and `L843-851`. The output no longer matches the contract the code cites. → Update the spec artifacts.

### Passes

**1. Correctness: ran, with no defect in what the commit claims.**

- `--exclude-standard` covers all three rule sources in the scratch repo. It recurses into ignored subfolders, and it lists a spec dir that is ignored as a whole file by file. That last case comes back `already_stored` and names everything in the dir, which is right.
- `-z` with `_read`'s `.strip()` is safe. The output starts with `<dir>/` and ends with `\0`, so no whitespace at the edge of a filename gets stripped.
- The read runs inside `_lock` and before `git add`, and it does not change any later step.
- Treating a failed read as no ignored files is the right choice for an informational line.
- `unstored()`, exit codes and `stops_removal` are untouched. In the removal path, ignored files in a spec dir outside the worktree survive on disk, so the new line does not cover up a loss.
- Observation, not a finding, and older than this commit: `git merge` silently overwrites an ignored untracked file when the upstream tracks the same path. In that case the line, computed before the merge, would name a file that the merge has since replaced. It needs another clone that has no such rule, so it is unlikely. I did not reproduce it.

**2. Security: ran, nothing found.** There is no new input boundary. Paths come from git and are printed with `markup=False`, so rich does not read them as markup. A control character in a filename passes through to the terminal, as it already does for `files`. That is not new, and the names are the person's own files.

**3. Architecture: ran, nothing found.** The new field follows the existing `StoreResult` pattern, and the single `result()` closure carries it to every outcome that `_store` builds. The `_outcome_lines` extraction is the smallest way to append a line to every outcome. `unstored` stays the one source of truth for `check specs` and the pass. There is no new dependency, so the dependency checks do not apply.

**4. Readability and simplification: ran.** I checked against the clean-code review catalog: the "comments and documentation" section and the "intent and consistency" section. The result is the docstring contradiction, the "store's rules" wording and the wrapper scope NITs above. The new comment at L603-604 explains why, as the repo's convention asks. The names `ignored` and `_outcome_lines` say what they hold.

**5. Performance: ran.** The change adds one `git ls-files` subprocess per store, a few ms on a spec dir. Unlike `git status`, it descends into ignored directories, so its cost and its output grow with the size of an ignored tree. The 2,000-file case cost nothing measurable. The output size is the real cost there, and the second WARNING covers it.
