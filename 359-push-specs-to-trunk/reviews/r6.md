### The blocker, reproduced

`_paths.spec_root` resolves this repo's manifest first, then the main checkout's.
A relative value is anchored to the directory of the manifest that declared it
(`_manifest_root`, `_paths.py:276`). The manifest is gitignored, and
`install-skills` writes no `spec_root` into a fresh worktree when the main
checkout already declares one (`_spec_root_question_answered`). So in a worktree
session, which is where this project does its work, `"."` resolves to the
**main checkout**. It does not resolve to the worktree.

I ran this in scratch repos under my scratchpad, against the commit under review:

| Case | `layout(...)` | Result |
|---|---|---|
| A: root = repo = main checkout (what the new test covers) | `in_repo` | fixed |
| A, with the new rule stubbed out | `store_no_upstream` | the new test does fail before the fix |
| B: root = main checkout, repo = linked worktree, no upstream | `store_no_upstream` | `store()` returned `committed_not_backed_up` and committed `specs(100): store spec.md` onto `main` |
| B, with `main` tracking a bare `origin` | `store` (`origin/main`) | `store()` returned `stored`, and `origin/main` on the remote moved to `specs(100): store spec.md` |
| C: root = repo = linked worktree | `in_repo` | fixed |
| D: root = repo = detached main checkout | `in_repo` | was `detached` before, which would have said "the spec store has no branch checked out" about the code checkout |

In case B I confirmed that `_paths.spec_root(linked_wt)` resolves to the main
checkout when only the main checkout's manifest holds `{"spec_root": "."}`. The
commit message describes this exact failure ("committed the feature directory
onto the code branch and pushed its upstream"), and it still happens in the
layout this repo runs day to day. The data model defines `in_repo` as "git, run
in the root, finds the code repository's own checkout" (`data-model.md:18`),
and the main checkout is that checkout.

**Fix.** In `layout`, turn away the main worktree as well as `top_level(repo)`.
The main worktree is the first `worktree` line of `git worktree list --porcelain`
run in `repo`. Or reuse `_paths.main_checkout(repo)` through a function-level
import, which `_subject` already does for `_paths`. `layout` is not on the
guard's hot path, so the stdlib-only rule at module scope still holds. Then add
`test_the_main_checkout_named_from_a_worktree_is_in_repo`, which sets up
`git_repo` plus `_worktree(project, ..., "-b", "100-feature")` and asserts
`layout(project, wt).kind == "in_repo"`.

One cost needs a decision. A spec store that is itself the main worktree of the
code repository's common dir, with code worktrees hanging off it, would then
read `in_repo`. No doc in this feature describes that layout, and the real
`wfctl-specs` is a separate clone (`--git-common-dir` is its own `.git`), so it
is not affected. If that layout has to keep working, the check could instead
compare the root's branch with the branch of the main worktree's `HEAD`, or
`resolve` could refuse a spec root equal to its declaring directory. Either is a
larger change than this commit.

The same hole reaches the worktree guard. `committable` (`_hook.py:122`) calls
`owns_branch(main_checkout, here)`, which passes, so a commit in the main
checkout is exempt from the guard when `"."` is the spec root. That code is not
in this diff, but putting the rule in `owns_branch` would close both holes at
once. The commit says it kept the check out of `owns_branch` because the guard
passes "whatever directory the agent stands in". Comparing
`top_level(root)` with `top_level(here)` handles that, so the reason holds for a
raw path comparison and not for a rule written that way. I am not asking for
that move; I mention it so the fix is chosen knowing about both callers.

### Passes run

**1. Correctness.** I traced `layout` → `_checkout_top`, `top_level`,
`_local_branch` and `owns_branch`, and `store` → `layout` → `_store`. I also
traced resolution through `_paths.spec_root`, `_root_declaration`,
`main_checkout` and `_manifest_root`. Edge cases:
- Root inside the code checkout (`<repo>/specs`): still `in_repo`. It now
  returns earlier, with the same result.
- A nested separate clone at `<repo>/specs`: its top is its own, so nothing
  changes.
- A symlinked root: both sides go through `realpath`.
- `repo` not a git repo, or git failing there: `top_level` returns None, the
  check does not fire, and `owns_branch` returns False as before. That is the
  safe direction.
- A detached code checkout: case D above.

Finding: the BLOCKER.

**2. Security.** No new input boundary. The spec root comes from a manifest the
repo controls, and the change narrows where the store may write. There is no
shell interpolation, since git is called with argv lists. Nothing found.

**3. Architecture.** The rule is placed in `layout` rather than `owns_branch`.
That fits how `layout` already layers its checks (top of checkout, then detached,
then `owns_branch`). There is no new dependency, and no new import at module
scope. The guard's docstring claims parity ("the same rule the store applies",
`_hook.py:98`) and now drifts by one rule. That is harmless for the fixed case,
since the guard never refuses an agent's own worktree. For the unfixed case it
is part of the blocker. No separate finding.

**4. Readability & simplification.** The new comment at L184-187 says why the
check exists and why it has to come first, which matches the house style. The
test name is a sentence, and its docstring names the failure it caught.
Finding: the NIT about docstring item 3.

**5. Performance.** One more `git rev-parse --show-toplevel` subprocess on every
`layout` call where the root is in a repository. That means once per
`store specs`, `check specs`, and the `_evidence.py:1568` pass on `wfctl status`.
It costs one git spawn, a few milliseconds, and is not in a loop. Nothing found.

**6. Over-engineering.** The diff adds two lines of code, a four-line comment and
a nine-line test. Nothing can be deleted, nothing is speculative, and there is no
stdlib or native substitute.
