WARNING  wfctl/cli.py:L1689-1699 — The hook and the store now disagree about what "inside the worktree" means, and the main checkout falls between them. `_spec_copy.inside_worktree` says a spec dir in the main checkout is not inside, so the hook sends it to `_spec_store.store`. `StoreResult.inside_worktree` (`_spec_store.py:L518`) is plain path containment with no main-checkout exception, so it says the same dir is inside, the layout is `in_repo`, and `stops_removal` (`_spec_store.py:L428`) comes back True. The probe ran `wfctl hook worktree-remove <main> main` with `<main>/specs/main/spec.md` present. The hook exited 1, printed only `ℹ … is inside the code repository — not committed, not backed up` with no `✗ removal stopped` header, and then printed `Remove anyway: git worktree remove --force <main> && git branch -D main`. Both parents exit 0 here. #40 returned `not_applicable` with `inside=False`, and #359 never ran the store for a dir under `repo_root`. The comment #359 had on this line said the property was read so that removal and the store "cannot disagree about when to stop if the store's idea of 'inside' ever moves". The merge dropped that comment and created exactly that disagreement. Two tests pin the stale premise. `tests/test_worktree_remove.py:L431` stubs the store to return an inside `not_applicable`, which the merged hook can now reach only through this misfire. `tests/test_spec_store.py:L916` is named "inside the worktree", but its repo is a main checkout. → Gate the store branch on raw containment rather than on the copy result: run the store only when `not _spec_copy._is_inside(spec_dir, repo_root)`, so the main checkout's spec dir prints the copy-out "nothing to copy" line and goes on to `_save_unsaved`. Alternatively, make `StoreResult.inside_worktree` use the same rule as `_spec_copy.inside_worktree`. Add a hook-level test for the main checkout, and rename or retarget the two tests above.

WARNING  wfctl/cli.py:L5993 — `store specs` now picks the copy-out by path before it asks git, which goes against the accepted record ("wfctl decides whether a spec dir is stored by asking git") and against #359's behaviour for a spec store whose root sits inside the worktree. The probe cloned a `specs-trunk` store to `<wt>/specstore` with `WFCTL_SPEC_DIR` pointing at it. `_spec_store.layout` reported `kind='store'` with `origin/specs-trunk`. `store specs` exited 0, took the copy-out path (`to_unsaved` here, because the override is process-global), and committed nothing: the store still showed `?? 40-feature/`. The layout is rare, but the dispatch rule is the record's central claim. → Dispatch on git's answer. Call `_spec_store.store` first, and fall back to `copy_out` only when it returns `not_applicable` with `layout.kind == "in_repo"` and `_spec_copy.inside_worktree(found, repo_root)` holds. Or check `layout(found.parent, repo_root).kind` before choosing. The removal hook can keep its path rule, since a dir inside the worktree is deleted either way.

WARNING  wfctl/cli.py:L1697-1710 — The commit, merge and push now run before `_save_unsaved`, and nothing between them catches what `_spec_store.store` does not. `store` catches only `OSError` and `CalledProcessError`. Anything else, such as a `UnicodeDecodeError` from `text=True` decoding a `-z` listing that holds a non-UTF-8 file name, reaches the hook's catch-all at L1713. The catch-all prints "continuing so the removal is not blocked" and exits 0, and the untracked files are never saved. #40's `_spec_copy` comment (FR-028) names this exact failure for the copy-out. That is what the record already says a failed store at removal does. Or run `_save_unsaved` before the store branch, since `extra` depends only on the copy result.
