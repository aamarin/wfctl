## Findings

**BLOCKER  wfctl/cli.py:1055 — `is not True` collapses `None` into failure, and
then reports a cause that is not the cause.**

`touched_on_this_branch` returns three states on purpose; its own docstring says
so, and `cli.py:297-299` writes the project's rule for this exact function into a
comment: *"`is False` — never a falsy check. `touched_on_this_branch` returns
None when git cannot answer (no trunk, or a root outside the tree) … the gate
refuses only on evidence."* The new caller refuses on absence of evidence, and
prints a message whose two named causes are both false in that state.

Reproduced — a repo whose trunk is named anything but `main`/`master`/`dev` with
no `origin/HEAD` published, record committed on a feature branch, in the tree,
not ignored, present in `HEAD`:

```
$ git init -b trunk . && … && git checkout -b feat && git commit docs/architecture/design/1-x.md
$ wfctl arch check docs/architecture/design/1-x.md
⚠ docs/architecture/design/1-x.md is not part of the change under review — git is
  ignoring it, or nothing on this branch touches it. No reviewer will see it.
EXIT=1
```

The record is correct and the command tells the agent to move it. Per
`SKILL.md:83-85` the agent then re-commits or relocates a file that is already
where it belongs, in a loop nothing breaks.

The same `None` swallows two further states, each reported with the same wrong
sentence:

- `WFCTL_REPO_ROOT` pointing at a directory that is not a repository.
  `get_repo_root` returns `Path(override)` unvalidated, so `SystemExit` is never
  raised, the no-git exemption at 1032 is **unreachable**, and every git call
  under it fails → `None` → "git is ignoring it". (Two of the suite's own
  fixtures, `agent_dir` and `storyctl_dir`, set this variable.)
- A record inside a submodule. `git status --porcelain -- sub/path` errors with
  *"Pathspec is in submodule"* → `None` → same sentence.

→ Fix: branch on the three states. `is False` keeps the current message; `is
None` says git could not answer and names why (no trunk to compare against, or a
path git refuses to answer for), and the exit code for that state gets chosen
deliberately rather than inherited. One change repairs all three reproductions.

**BLOCKER  wfctl/cli.py:1030-1041 — `except SystemExit` is the exit-128
conflation this commit says it removed, moved one layer down and now failing
open.**

`get_repo_root` raises `SystemExit` from a bare `except subprocess.CalledProcessError`,
so it cannot distinguish *"not a git repository"* from any other reason
`git rev-parse --show-toplevel` exits 128. The handler treats all of them as the
benign exemption and exits **0**. Reproduced:

```
$ git init --bare .            # fatal: this operation must be run in a work tree
$ wfctl arch check 1-x.md
ℹ No git repository here, so no change carries this record and no
  reviewer is waiting for it. Not a failure.
EXIT=0

$ echo "gitdir: /nonexistent/here" > .git   # fatal: not a git repository: /nonexistent/here
$ wfctl arch check 1-x.md
ℹ No git repository here … Not a failure.
EXIT=0
```

The third member of that set is `detected dubious ownership in repository`
(`safe.directory`), which is ordinary in CI containers and shared checkouts —
there, `wfctl arch check` becomes a no-op that reports success for every record
in the repository. The commit message argues that `git ls-files`'s 128 "could not
be told from the failure it exempts nothing from"; that is still true here, only
the set of confused failures is different, and the new one fails *open* where
`ls-files` failed closed.

The catch is textually narrow — only `get_repo_root()` is inside the `try` — but
semantically over-broad, because `SystemExit` is the only signal that function
gives. → Fix: require positive evidence of "no repository" before exempting.
`git rev-parse --git-dir` exits 0 in a bare repo and non-zero with no repository,
so returncode 0 there separates the bare/work-tree-less case cleanly; for the
rest, match git's `not a git repository` on stderr and otherwise exit 1 printing
git's own message. Either way the exemption should be reached by proof, not by
default.

**WARNING  wfctl/cli.py:1068-1071 — `git cat-file -e HEAD:<path>` answers "does
HEAD contain this path", not "does HEAD contain this record".**

The comment above it and the commit message both call this axis "whether the
write reached a commit". A record committed and then edited in the working tree
passes:

```
$ git commit docs/architecture/design/1-x.md     # "# v1"
$ printf "# v2 totally different\n" > docs/architecture/design/1-x.md
$ wfctl arch check docs/architecture/design/1-x.md
✓ docs/architecture/design/1-x.md is committed on this branch
EXIT=0
```

This is the same defect class as staged-never-committed — the reviewer reads text
the author has already replaced — one step removed. `touched_on_this_branch`
returns `True` precisely *because* the file is dirty, so the two checks cancel.
→ Fix: add `git diff --quiet HEAD -- <path>` (or compare `git hash-object` against
`git rev-parse HEAD:<path>`) and report the difference; or narrow the success
line to what is actually proven.

**WARNING  tests/test_arch_check.py — the four tests each fail for the reason
their docstring claims, but the states this diff actually gets wrong are the
untested ones.**

I checked the discrimination individually, and it holds: each assertion matches a
substring emitted by exactly one branch, so none of the four can pass for an
unrelated reason.

- `test_a_record_in_another_checkout_fails` — `"outside this working tree"` is
  the `is_in_tree` branch alone. Sound.
- `test_no_repository_is_not_a_failure` — asserts exit 0 and the exemption text.
  It is also the test that *cannot* distinguish the exemption from BLOCKER 2's

Missing, in order of what the diff gets wrong: (a) `touched_on_this_branch`
returning `None` (BLOCKER 1); (b) a bare or unreadable repository not taking the
exemption (BLOCKER 2); (c) a **gitignored** record — the SKILL names "ignored by
git" as one of the three failures the command reports and no test exercises it,
though the branch does work (verified by hand).

The record's Verification section says the file "covers the four states". The
command has more reachable outcomes than four.

`NO_COLOR` is handled — `tests/conftest.py` sets it at import time, so this file
inherits it correctly and does not need its own pin.

## Passes with nothing to report

- **Security.** All three subprocess calls use argv lists, no shell. The
  user-supplied path reaches git only as an argv element or inside
  `HEAD:<path>`, so a leading `-` cannot become an option. Rich markup injection
  is handled — `_arch_location` escapes, and it is the only thing interpolated
  into a `console.print`. No secrets, no network, no untrusted parse.
- **Architecture.** The change does what the panel asked: one command wrapping
  `touched_on_this_branch` instead of a second weaker copy, registered on the
  existing `arch_app`, reusing `is_in_tree`, `_arch_location` and `get_repo_root`.
  The function-local `import subprocess` matches six other sites in `cli.py`.
  The declaration's claim that adding a second caller of an existing authority
  draws no boundary is sound.
- **Performance.** One to three `git` spawns per invocation, called once per
  design session. Nothing to say.
- **Over-engineering.** No speculative flexibility, no new abstraction, no
  dependency. The command is the smallest thing that answers the question.
