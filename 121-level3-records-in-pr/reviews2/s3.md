## Findings

**BLOCKER** `wfctl/cli.py:1043-1051` — the "committed" check only asks whether
*a* version of the path exists at `HEAD`; it never compares that content to the
working tree. A record committed once and then edited (uncommitted) reports
`✓ ... is committed on this branch` and exits 0, even though the reviewer would
see only the stale committed version — exactly the silent failure this whole
feature exists to close.

Reproduced live (outside the worktree):
```
git init -qb main; git commit ...          # base
git checkout -qb feat
echo v1 > docs/architecture/design/1-x.md; git add .; git commit -qm "record v1"
echo "v2 UNCOMMITTED EDIT" > docs/architecture/design/1-x.md   # no commit
wfctl arch check docs/architecture/design/1-x.md
# → "✓ ... is committed on this branch", exit 0
```
`git status --porcelain` at that point shows ` M docs/architecture/design/1-x.md`
— the tool already has the signal and doesn't use it for this check.

→ Fix: replace the `git cat-file -e HEAD:<path>` check with
`git diff --quiet HEAD -- <path>`. It subsumes both cases the current code
tries to separate — no zero-byte diff *and* the path existing at `HEAD` are the
same fact `git diff` already reports — verified against all three states:
staged-never-committed (exit 1), clean-committed (exit 0), and
committed-then-edited (exit 1). This is a one-line replacement, not a new
branch, and removes the need for the separate comment justifying `cat-file` over
`status --porcelain`.

Also add a regression test for this exact state (commit, then edit
uncommitted) to `tests/test_arch_check.py` — none of the four shipped tests
cover it, which is how the gap passed this panel's own predecessor.

**NIT** `docs/architecture/design/121-visibility-is-asked-of-git.md` — cites
"`wfctl/_paths.py:283` `touched_on_this_branch`"; the function's `def` line is
