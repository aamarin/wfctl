**WARNING** `wfctl/agents/commands/speckit.analyze.md:184–188` — pass G's coverage
row values are not statuses, and the file says two paragraphs earlier that they
must be. `writing-a-scan-file/SKILL.md` (which this wrapper explicitly names as
the owner of the file's shape) says: "**Status**, per coverage row — exactly one
of `Clear`, `Resolved`, `Deferred`, `Outstanding`." The wrapper repeats that at
`:169–171`: "That row carries a percentage rather than one of the four statuses,
**and it is the only row that does**." The new block then gives pass G four values
— `N CRITICAL`, `N warning`, `None listed`, `No design.md` — none of which is one
of the four statuses. So the wrapper's own sentence is false about the table it
describes, in the same section, in the same commit.

This is the exact failure the same file names at `:148`: "a wrapper that silently
contradicts the skill it points at teaches the reader to discount both." The
read-only override *is* declared out loud; this one is not declared at all.

Fix: keep the status vocabulary and put the count in the parenthetical, matching
the `Clear (N records read)` form the diff already uses:

```
| G · Design-record contradiction | Clear (N records read)     |
| G · Design-record contradiction | Outstanding (N CRITICAL)   |
| G · Design-record contradiction | Outstanding (N warning)    |
| G · Design-record contradiction | Clear (none listed)        |
| G · Design-record contradiction | Deferred (no design.md)    |
```

The last one is arguably the point of the whole row and `Deferred` is the skill's
word for "a row you did not reach", with the reason on it. Whichever mapping is
chosen, either the four values become statuses or `:170`'s "only row that does"
sentence has to change. Right now both stand and they cannot both be true.

**WARNING** `speckit.plan.md:77`, `speckit.tasks.md:69`,
`speckit.implement.md:60`, `speckit.analyze.md:57` — "outside the working tree" is

the working tree… That property is about the **reviewer**… The consumers here are
pipeline steps running locally." The implementation then applies to the records
the exact argument its own record just rejected for `design.md`.

Fix: drop the location clause. "A listed path that will not read — missing, or
unreadable — gets its own line…". If out-of-tree reads are genuinely meant to be
refused for sandboxing reasons, that is a different rule and needs its own
sentence, plus a note that a repo with an out-of-tree `arch_root` gets no records
at all.

## On the two questions I was asked and did not turn into findings

**Are the new tests tautological?** No, but they are a narrow kind of real. Every
assertion is a string-presence check against a prose file the same author wrote,
which cannot fail on the day it is written — that is characterization, and it is
the only thing available, since the suite cannot execute an instruction to a
model. What makes them carry weight is that they fail on *removal*, and the module
docstring is honest about that being the point ("`install-skills` copies it, no
test reads it, and a wrapper that lost a rule would ship green"). Three of them
are documented as having failed on first run, which is the strongest evidence
available that they are not decorative. `_record_section`'s isolation is the right
call and is what stops
`test_pass_g_sits_between_inconsistency_and_the_measurement` from passing on the
pass-G heading further up the file — its docstring records exactly that near-miss.
`test_every_consumer_may_run_feature_paths` is the only one asserting something
the prose alone could not tell you, and it is the best test in the file.

The gap is the producer/consumer contract: nothing ties the literal
`"## Software design decisions"` in `test_design_records_downstream.py:75` to the
one in `test_skill_cross_references.py:158`. A rename does fail both, so it is
caught — two independent constants rather than one shared one is a maintenance
observation, not a hole.

**Does the bullet-only rule hold against this repo's `design.md`?** Yes, and it is
load-bearing here rather than hypothetical. `design.md:112–114` is the one bullet
and it names the level-3 record; `:116–119` is prose that names
`docs/architecture/design-md-indexes-the-records.md`, a **level-2** record. A
consumer reading "the paths listed in the section" would load the level-2 record
as level-3 and bind against something that binds nothing — the failure the rule
describes, present in the very first file the rule is applied to. That earns the
rule. See the WARNING above for why it is not yet guaranteed by the writer.

**Is anything claimed in a commit or a record untrue of the code?** Everything I
could mechanically check holds: six passes A–F, step 8 as an offer, `_arch.py`
containing zero `design` references, `load_records` being a non-recursive
`root.glob("*.md")`, `feature-paths` printing `FEATURE_DIR`, brainstorm writing
the heading, `_paths.SCANS_DIR` existing with no `DESIGN_DIR` beside it (#327, and
correctly carried forward as a consequence rather than fixed here). Both records
match their templates section-for-section. The three untrue-or-stale things I
found are the "seven records" count, the "only row that does" sentence, and the
`Verification` bullet that cannot run — all above.
