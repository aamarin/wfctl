## Findings

### BLOCKER

**B1 — `speckit.{plan,tasks,implement,analyze}.md` (each § *Read this feature's
design records*) — a listed record path has no stated resolution base, and the
one design.md that exists lists relative paths.**

The parse rule is `Every **list item** of the form `- <path> — <text>` names a
record; read each one.` Nothing says what `<path>` is relative to.

The two candidate bases disagree, and the wrong one is the natural reading:

| Base | Resolves to | Exists |
| --- | --- | --- |
| `design.md`'s own directory (`FEATURE_DIR`) | `/Users/andremarin/Development/wfctl-specs/121-level3-records-in-pr/docs/architecture/design/326-…md` | no |
| `REPO_ROOT` | `<worktree>/docs/architecture/design/326-…md` | yes |

`FEATURE_DIR` resolves *outside* the working tree in this repo
(`wfctl feature-paths` → `/Users/andremarin/Development/wfctl-specs/121-level3-records-in-pr`),
and a path found inside a document is normally read relative to that document. A
model that does so gets nothing.

This is not hypothetical. The feature's own `design.md:112` is the exemplar the
whole change is built on, and it is relative:

```
- `docs/architecture/design/326-contradiction-is-a-seventh-pass.md` —
  contradiction detection is a seventh pass inside analyze, …
```

Worse, the two producers disagree with each other. `speckit.brainstorm.md:95`
mandates `- <arch-root>/design/<issue>-<decision>.md — <the decision in one
line>`, and `wfctl arch-root` prints an **absolute** path
(`/Users/…/121-level3-downstream/docs/architecture`). So the template says
absolute, the one real instance is relative, and the four new consumers specify
neither.

The failure is silent by design: `A listed path that will not read — missing, or
outside the working tree — gets its own line, `<path> — listed, not found`, and
does not stop the step.` and `Pass G produces **no finding** for such a record`.
So the headline path of the feature degrades to a `listed, not found` line and a
clean pass G, on the only feature that exercises it.

*Fix:* one sentence in each of the four sections — "A listed path is resolved
against `REPO_ROOT` when relative; `wfctl feature-paths` prints it." Better,
also relax the form to tolerate the backticks and the line wrap the real entry
carries: "` - `<path>` — <text>`, where the path may be backticked and the text
may wrap."

**B2 — `speckit.{plan,tasks,implement,analyze}.md` — the fourth empty state is
unnamed, and it is the majority state today.**

Three states are specified:

```
Design records: N listed in design.md
Design records: none — design.md records no level-3 decision
Design records: unknown — no design.md at <FEATURE_DIR>
```

A `design.md` that exists but carries **no `## Software design decisions`
heading at all** is a fourth state, and it is left to the model — which will
emit `none — design.md records no level-3 decision`, a positive assertion that a
design pass ran and decided nothing.

That assertion is false for most existing features. Counted, not sampled:

```
19 of 27 design.md files under the spec root carry no `## Software design
decisions` heading (grep -c '^## Software design decisions').
```

It is reachable in a fresh repo too. `speckit.brainstorm.md` says the one-pager
"gains a section `idea-refine` does not itself carry" — so any `design.md`
written by `idea-refine` outside the brainstorm wrapper, or by a wfctl older
than #121 item 5, has no section. And the brainstorm wrapper already rules on
what a missing section means: "a missing section reads as a level nobody ran" —
i.e. semantically `unknown`, not `none`.

This is exactly the conflation the change exists to prevent. The wrapper argues
"A step that reports neither reproduces #307's defect one directory over" and
then leaves the commonest empty state to collapse into the wrong one of the two.

*Fix:* name it. `Design records: unknown — design.md at <FEATURE_DIR> has no
## Software design decisions section`, and a matching pass G coverage value.
Add the assertion to `test_every_consumer_names_all_three_record_states`
(and rename it to four).

### WARNING

**W1 — `speckit.analyze.md:70-77` — `warning` is not a severity `speckit-analyze`
has.**

The skill's step 5 defines exactly four: `CRITICAL`, `HIGH`, `MEDIUM`, `LOW`.
Pass G's table introduces `CRITICAL` / `warning` — one from that scale, one from
outside it, in different case. Step 6's report table has a `Severity` column and
mandates "stable IDs prefixed by category initial", so every pass G finding must
be rendered with a severity from the four; the wrapper never says which
`warning` maps to. Two runs will pick `HIGH` and `MEDIUM`, and the scan file's
`Critical: N` count has no home for it either.

*Fix:* say `HIGH` (or `MEDIUM`) instead of `warning` in the table and in the
coverage-row text, or state the mapping explicitly.

**W2 — `speckit.analyze.md:80-88` — a pass G finding's shape matches neither
destination.**

The prescribed shape is a markdown bullet with `Record:` / `Decision:` / `Task:`
lines. It is not a row of step 6's report table (`| ID | Category | Severity |
Location(s) | Summary | Recommendation |`, IDs like `G1`), and it is not the scan
file's Findings shape either (`- **<pass>, <severity>** — what was wrong.` then
`→ Fixed:` / `→ Accepted:`, per the wrapper's own § *Section shape*). A model has
three plausible destinations — step 6's table, `analysis-report.md`, the scan
file's `### Findings` — and no instruction picks one.

*Fix:* say where it goes. If the scan file, fold `Record:`/`Decision:`/`Task:`
under the existing `- **<pass>, <severity>** — …` bullet so one shape holds; if
step 6's table, give the ID prefix and put the quoted halves in `Location(s)` /
`Summary`.

**W3 — pass G CRITICAL vs. the step verdict — "never gates" and the verdict rule
pull opposite ways.**

does. Also note `Scanned:` still reads "spec.md, plan.md, tasks.md — all three
present and read"; the record list is a fourth input and is not represented

*Fix:* one clause — "a pass G CRITICAL counts toward the verdict / does not" —
and extend the `Scanned:` line shape to name the record list.
