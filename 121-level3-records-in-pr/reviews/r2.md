### Findings

**WARNING** `wfctl/agents/skills/software-design-decisions/SKILL.md:74` —
"Write the file, commit it, then ask" is the only instruction for the commit
step, and it's prose, not a literal command — unlike the `git ls-files
--error-unmatch <path>` step three lines later, which is pinned exactly. The
command's `allowed-tools` grants unscoped `Bash(git add*)` and `Bash(git
commit*)` (`speckit.brainstorm.md:9`), so an agent following "commit it" is as
likely to run `git add -A && git commit -am ...` as a scoped `git add <path> &&
git commit -m "..." -- <path>`. In a repo mid-brainstorm with other dirty files
(exactly the state this pipeline runs in — code hasn't been written yet, but
other WIP can exist), that sweeps unrelated changes into what's supposed to be
an isolated docs commit. `CLAUDE.md`'s own git-safety protocol says to prefer
adding files by name over broad adds for the same reason. → Give the commit
step the same literal-command treatment as the `ls-files` check: a fenced
`git add <path> && git commit -m "..."` block naming the record path explicitly.

**WARNING** `wfctl/agents/commands/speckit.brainstorm.md:81` — the
`## Software design decisions` example hardcodes the path form
`docs/architecture/design/<issue>-<decision>.md`, but `arch_root` is
per-repo configurable (`.wf-skills-manifest.json`; `<repo>/docs/architecture`
is "the default, not the truth" — the exact phrase `software-design-decisions/SKILL.md:55`
uses about this same fact). An agent copying the example literally in a repo
with a non-default `arch_root` writes a path into `design.md` that doesn't
resolve to where the record actually landed — the precise failure this whole
feature exists to close, reintroduced in the one section whose entire job is
listing record paths for a reviewer. → Either say "the path `wfctl arch-root`
printed, plus `design/<issue>-<decision>.md`" instead of a literal example
path, or add one clause noting the leading segment is this repo's default and
not to be assumed.

**NIT** `wfctl/agents/skills/software-design-decisions/SKILL.md:74-101` — the
paired design record's own "Assumed" section flags "committing a record
mid-design is acceptable in a consumer repo. Falsified by a repo whose hooks
reject a docs-only commit" as an open, unresolved risk — but the shipped skill
text gives exactly one remedy for *any* non-zero exit from the check: "the
record has to move before the design continues." That's the right remedy when
`arch_root` resolved outside the tree; it's the wrong diagnosis when the file
never got committed because a hook rejected it (moving the file changes
nothing about the hook). Not blocking — the case is explicitly named as
unresolved by the authors, not silently missed — but the checklist item at
:147 restates only the pass condition, not what to do on this specific failure
shape. Worth a one-line branch ("if the commit itself was rejected, the record
still exists on disk — fix what the hook is objecting to, not the path") the
next time this file is touched.
