## Findings

**BLOCKER** `wfctl/agents/skills/software-design-decisions/SKILL.md:72-101,146-148` — the check proves the
record is *staged*, not that it was *committed*, and the skill's own text overstates what it shows. Verified
directly:

```
git add bar.txt
git -c commit.gpgsign=true -c gpg.program=/bin/false commit -m "should fail"   # exit 128, no commit made
git ls-files --error-unmatch bar.txt                                          # exit 0 anyway
```

`git ls-files --error-unmatch` only asks "is this path in the index," which `git add` alone satisfies —
it says nothing about whether `git commit` actually succeeded. This repo's own `CLAUDE.md` git-safety
section names both a rejected pre-commit hook and (implicitly, via "never bypass signing") a GPG failure as
real, anticipated ways a commit can fail after staging succeeds. In that exact case the skill's claim —
"Exit 0 and the record is in this working tree's index, which is the whole property: a reviewer opening the
branch reads it beside the code" — is false: nothing was committed, nothing reaches the reviewer, and the
new safety net reports success anyway. That is the identical failure class this whole feature exists to
close ("the file is on disk, the session reports success, and the reviewer sees nothing"), just moved one
step later and past the new check rather than caught by it. Neither the design record's `Verified` nor
`Assumed` section considers a failed commit.
→ Check what actually landed in a commit, not what is staged, e.g. `git rev-parse --verify HEAD:<path>`
(fails with a non-zero exit until the commit exists) or `git log -1 --format=%H -- <path>` (empty until
committed), instead of or in addition to `git ls-files --error-unmatch`.

**WARNING** `docs/architecture/design/121-visibility-is-asked-of-git.md` (`## Assumed`) — already names
"Committing a record mid-design is acceptable in a consumer repo. Falsified by a repo whose hooks reject a
docs-only commit" as an assumption, but doesn't connect it to the BLOCKER above: a rejected commit isn't
just an acceptability question, it's the exact scenario the chosen check silently passes. Once the check is
fixed to test `HEAD` rather than the index, this assumption line should say what happens on that failure
(record stays staged, design cannot continue) rather than leaving it as an open "falsified by" bullet.

are dense with rationale — match that"), and every factual claim in it checked out against the real
`arch-root` output and real git behavior for a second checkout of the same repo.

## Verdict

**Request changes** (1 blocker) — the mechanism this PR adds is sound in the case it was built for (wrong
directory, wrong checkout, gitignored path) but gives a false "landed" verdict in the specific case the
project's own workflow already anticipates (a commit that fails after staging). Fix the check to assert
against `HEAD`, not the index, and the WARNING resolves as a side effect.
