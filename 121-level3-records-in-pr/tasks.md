# Tasks: level3 downstream

**Input**: Design documents from this feature's directory — `wfctl feature-paths`
prints it; it is not `specs/<branch>/` in this repository
**Prerequisites**: plan.md, spec.md, research.md, data-model.md, contracts/
**Issue**: #326 (child of epic #121, scope item 6)

**Tests**: This feature ships no runtime code, so the automated suite can only
assert that the four wrappers ship and cross-reference correctly. Every user
story therefore carries a Verification subsection naming the manual exercise that
actually tests it, per the spec's Validation Strategy and `AGENTS.md`: *"A change
to anything under `wfctl/agents/` is not verified by the test suite alone."*

**Organization**: Grouped by user story. US1 is a coherent reviewable slice on its
own; US2 is a second; US3 is a property of both and is verified across them
rather than implemented separately.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel — different files, no dependencies
- **[Story]**: US1, US2, US3
- Paths are repository-relative from the working tree root

## Path Conventions

Source is committed package data under `wfctl/agents/` (`layer-model`). Every
dotted directory at the repository root is generated by `install-skills`,
gitignored, and never edited by hand — so an edit goes to
`wfctl/agents/commands/`, and `uv run wfctl install-skills` is what puts it
somewhere runnable.

## Dependencies & Execution Order

### Phase Dependencies

- **Setup (T001–T002)**: no dependencies
- **Foundational (T003–T004)**: depends on Setup — **blocks all three stories**,
  because it is the wording the four wrappers copy
- **US1 (T005–T011)**: after Foundational. No dependency on US2 or US3
- **US2 (T012–T019)**: after Foundational. Independent of US1 — analyze resolves
  the record list itself — though worth less while the plan those tasks came from
  was written blind
- **US3 (T020–T025)**: after Foundational, and its checks read the wrappers US1
  and US2 edit, so it verifies last even though it implements almost nothing
- **Polish (T026–T029)**: after every story that is shipping

### Within each story

- The wrapper edit precedes its test, which precedes its manual exercise. The
  test asserts the instruction shipped; only the exercise asserts it works
- T008 comes after T005–T007 deliberately: the rationale is written once the
  three edits exist, so it describes what is there rather than what was planned

### Parallel opportunities

- T005, T006, T007 are three different files with no shared state — fully
  parallel
- US1 and US2 can proceed in parallel once Foundational lands
- T023, T024 and T025 each need a scratch fixture and can be prepared in parallel

## Logical PR boundaries

Two coherent slices, and this feature is small enough that one PR is defensible:

| Slice | Tasks | Demonstrable alone |
| --- | --- | --- |
| Records reach plan, tasks, implement | T001–T011, T020–T024 | yes — the loop closes |
| Analyze reports contradictions | T012–T019, T025 | yes — the check fires |

Recommendation: **one PR**. The two slices share the Foundational wording, both
touch only wrapper prose, and splitting them puts the same four-file review in
front of a reviewer twice. Split only if T017 falsifies pass G, in which case
slice one ships and slice two returns to design.

## Implementation Strategy

Wrapper prose first, tests second, exercises third — and the exercises are not
optional. `AGENTS.md` is explicit that the suite checks skills ship and
cross-reference rather than that they read well, so T010, T011, T017, T018, T023
and T024 are the only tasks here that verify the feature does what it claims.
Every one of them requires `uv run wfctl install-skills` first, and `uv run` is
what makes that install the tree being edited rather than the released wheel.

## Notes

- Every edit is Markdown under `wfctl/agents/commands/`. Nothing under `wfctl/`
  outside that directory is touched — no predicate, no constant, no CLI verb —
  which T026 measures.
- Tests asserting console output pin `NO_COLOR`; `conftest.py` explains the
  presence-only semantics.
- Test names are sentences and docstrings say why the test exists, naming the
  failure it caught rather than restating the assertion.
