## BLOCKER

**BLOCKER  `wfctl/_pipeline.py:132` — `next_command` for a blocked design step is
an unrunnable template, and running it verbatim permanently defeats the gate.**

`DESIGN_BLOCK_COMMAND = 'wfctl arch none --reason "<why>"'` is returned from
`next_step_content` (`_pipeline.py:648`) into three machine-read slots that did
not carry it before this diff:

- `next-step.md`, written by `next` (`cli.py:333-336`) and `resume`
  (`cli.py:375-381`), whose last line is literally `Run this command to continue.`
- `report.next_command`, which `status --json` emits
- `speckit-orchestrate` step 5, `auto is false` branch: *"Display: Next: run
  `{next_command}` when ready."*

Scenario, end to end:

1. Branch has `specs/<b>/design.md`, no arch record. `status` → `brainstorm ▶`,
   `next: wfctl arch none --reason "<why>"`.
2. An agent reads `next-step.md`:
   ```
   Next step: wfctl arch none --reason "<why>"
   auto: false
   why: no architecture record for this change
   Run this command to continue.
   ```
3. It runs the command as written. `arch_none_cmd` (`cli.py:960`) only rejects an
   *empty* reason — `"<why>".strip()` is truthy — so it writes
   `docs/architecture/declarations/<branch>.md` containing the body `<why>`,
   `touched_on_this_branch` returns `True`, and the command prints a green ✓.
4. `design_block` now returns `None` forever. The gate is cleared by a committed
   declaration that says nothing, which is the exact failure `arch_none_cmd`'s
   own empty-reason guard exists to stop.

This diff also widens `speckit.brainstorm.md`'s `allowed-tools` with
`Bash(wfctl arch none*)`, so the agent standing at the blocked step is now
permitted to execute it. Before this change the placeholder appeared only inside
`DESIGN_GATE_REFUSAL`, a human-facing message surrounded by prose ("or state that
it draws none:"), and `next-step.md` was never written at all on that path. The
change moved a template into the executable slot.

Second half of the same defect: of the two legitimate remedies, `next_command`
names only `arch none` — the "this change draws no boundary" one. The population
it is named for is precisely the population that *has* a `design.md`, i.e. the
one that already went through a design pass. So the field an unattended loop acts
on steers the blocked step toward the answer least likely to be true, and the
other remedy is not in the payload at all (see WARNING 1).

Fix, any of:
- reject a placeholder reason in `arch_none_cmd` (`^<.+>$`, or a `<`-leading
  reason) with the same shape as the empty-reason guard, **and**
- carry both remedies in the payload rather than one command string — e.g. a
  `remedies: [...]` on the step, or `arch_root` as a payload field so the JSON
  reader can build the record path — and let the skill present them; **and/or**
- make `next_command` for this step something that is safe to run verbatim.

## WARNING

**WARNING  `wfctl/cli.py:275-282` — the record remedy is computed inside the
console view; the JSON view never sees it. `pipeline-state-is-one-payload`
(accepted, in force) forbids exactly this.**

`status_cmd` resolves `arch_root(repo_root)` and formats `DESIGN_BLOCK_HELP` in
the non-JSON branch, after `if as_json: … return` at `cli.py:212-235`. The record
being reviewed against says, in *Considered*: *"a fact added to the printing
branch reaches the human and silently not the agent"*, and in *Consequences*:
*"Annotations become payload fields rather than strings assembled while printing,
because a fact that exists only inside a view is the thing the dashed edges
forbid."*

Concrete: a human running `wfctl status` learns they may write
`docs/architecture/<slug>.md`. An agent running `wfctl status --json` — the view
that record created for it — gets `reason: "no architecture record for this
change"` and `next_command: 'wfctl arch none --reason "<why>"'`, and has no way
to reach the other remedy or the per-repo directory. `wfctl next` prints the
reason but not the help either (`cli.py:337`), so the shortest path to green for
every non-console reader is the false declaration in the BLOCKER above.

The comment defending it — "the directory to write it in is resolved per repo, so
it cannot live in a constant" — is true and is an argument for putting
`arch_root` *in the payload*, not for computing it in the renderer.

Fix: add the resolved arch location (and/or both remedies) to the payload; keep
`_arch_location`'s escaping at the print, which is a rendering concern.

**WARNING  `wfctl/cli.py:338` and `wfctl/cli.py:382` — new unescaped
interpolation into rich markup; a bracketed definition-of-done command is
silently dropped or crashes the command.**

Both new lines are `console.print(f"  [dim]{blocked}[/dim]")`. For `implement`,
`blocked` is `verification_block`'s string, which interpolates the *failed
command lines* out of `wfctl.json` (`_pipeline.py:280-286`).

Verified against rich in this environment:

| `blocked` contains | result |
|---|---|
| `ruff check wfctl/[a-z]*` | `[a-z]` silently swallowed — the command name the user needs is gone |
| `pytest -k "not [/slow]"` | `MarkupError: closing tag '[/x]' doesn't match any open tag` → `wfctl next` traceback |

The silent case defeats SC-006, which `verification_block`'s own comment cites:
*"Name the commands, not just the count: SC-006 requires a blocked user to learn
which one failed from `status` alone."* This repo already knows this failure mode
— `_arch_location` (`cli.py:819-833`) exists for it and has a dedicated
regression test — and `escape` is already imported in `cli.py`.

Fix: `console.print(f"  [dim]{escape(blocked)}[/dim]")` at both sites. (The
pre-existing `ann = f"  [dim]{step['annotation']}[/dim]"` at `cli.py:264` has the
same hole and is worth fixing in the same pass, since this diff is what routes
`verification_block`'s text through it more often.)

**WARNING  `wfctl/_pipeline.py:515` — `reason` means two different things
depending on the step, so a consumer cannot use it to mean "why this step is not
done".**

`reason = {"implement": implement_reason, "brainstorm": design_reason}.get(name)`
omits `decompose`, whose blocking reason (`decompose_reason`, set at
`_pipeline.py:483`) reaches the payload only as `annotation`.

Concrete: a branch with `delivery.md` carrying two unkeyed rows and tasks still
open renders

```json
{"name": "decompose", "state": "in_progress",
 "annotation": "2 issue rows without a key", "reason": null}
```

while `brainstorm` blocked renders `annotation` and `reason` identical. The
`_PipelineStep.reason` docstring says "the unrendered half of `annotation`" —
here the whole of `annotation` *is* the reason and `reason` is null. A reader
branching on `reason` to decide "is this step held" gets the wrong answer for
`decompose` on the very first case that has one.

Fix: set `reason` for `decompose` too (the routing branch at `:648` must then
learn a third arm rather than falling through to `DESIGN_BLOCK_COMMAND` — see the
next finding), or rename the field to something that does not promise a general
"why".

Related latent trap at `_pipeline.py:648`:
`return ("wfctl verify" if step == "implement" else DESIGN_BLOCK_COMMAND), False`
— any step that is ever given a truthy `blocked` and is not `implement` routes to
`wfctl arch none`. That is safe only because `reason` is currently populated for
exactly two steps. It is the same fail-open shape the `Source` Literal comment at
`_pipeline.py:21-25` argues against ("an unrecognised source would take the
ambient branch and proceed"), applied inconsistently one function later. Make it
an explicit two-arm dispatch with no `else` fallback.

**WARNING  `wfctl/_pipeline.py:33` + `:276` + `:574` — the source label is chosen
at the gate, not at the reader, so the record's central argument is not what the
code does.**

`promised-evidence-blocks-on-silence.md`, *Owns truth*: *"Asked at the gate, it is
re-derived per gate and drifts; asked at the source, it is answered once."* And
*Consequences*: *"The evidence source has to be nameable at the point it is
read."*

In the code, `design_block` hard-codes `"ambient"` at its call to `blocks` and
`verification_block` hard-codes `"repo-declared"` at its own. Nothing ties either
literal to the thing that actually produced the evidence
(`_paths.touched_on_this_branch`, `_verify.load_record`). A third gate reading git

eliminated, moved one level down. The `Source` Literal catches a *typo*; it
cannot catch `design_block` passing `"repo-declared"`, and no test would either.

`touched_on_this_branch`, `REPO_DECLARED: Source = "repo-declared"` next to
`_verify.load_record` — so a gate cites the source rather than asserting one. Or
have the reader return `(verdict, source)`.

Judged against `.agents/skills/architecture-decisions/SKILL.md`, the record itself
passes every checklist item: slug filename with no number, all six required
sections, `Owns truth` in question form with both halves, a concrete `Direct
baseline`, four real alternatives each losing on fit, a dated `proposed` log line,
no `supersedes`. Correctly `proposed`, correctly at the arch root (not `design/`).
The gap is between the record and the code, not inside the record.

**WARNING  `wfctl/_pipeline.py:276` — `verification_block` asserts a verdict it
has not computed.**

```python
if blocks("inconclusive" if record["inconclusive"] else "satisfied", "repo-declared"):
```

A record with `inconclusive: False, exit: 1` is passed as `"satisfied"` — one
line before `if record["exit"] != 0` discovers it failed. Behaviour is unaffected
(`blocks` only branches on `"inconclusive"`), but the record makes this vocabulary
load-bearing: *"A gate reads evidence and returns one of `satisfied`,
`unsatisfied`, `inconclusive`."* Here the gate fabricates one. The next reader
adding a `"unsatisfied"` arm to `blocks` will find this site lying to it.

Fix: compute the verdict honestly, or narrow the call —
`if record["inconclusive"] and blocks("inconclusive", "repo-declared"):` — which
also makes it visible that the wiring is only load-bearing for one of the three
values.

## What is right

Not padding — these are the parts I tried to break and could not:

- The `spec.md` guard in `design_block` (`:534`) is exactly equivalent to the old
  `step != _AFTER_DESIGN` trigger. I traced it: `specify` is `in_progress` only
  when `has_markers`, which forces `clarify` to `in_progress`, which makes
  `_current_step_name` skip `specify` — so the old gate could never fire with
  `spec.md` present. Same window, fewer moving parts.
- `_implement_verdict` genuinely collapses the two-site composition; the
  `_step_block` implement arm reproduces `_infer_steps`' read exactly (including
  the empty-`tasks_text` case) rather than approximating it as the old
  `next_step_content` did.
- "A blocked step is never automatic" is the right resolution of table-vs-gate,
  and `test_a_blocked_design_step_is_never_automatic` asserts the premise
  (`_STEPS["brainstorm"][1] == "automatic"`) separately from the rule, so it
  cannot pass by the table changing underneath it.
- Several tests were correctly hardened against the fact that `next` now always
  exits 0 (`:242-250`, `:322-330`, `:345-351`), with docstrings that name the
  mutation that would otherwise survive. That is the discipline the exit-code
  removal required and it was not skipped.
- The ADR passes its own skill's checklist item for item, including the one that
  is usually dropped (the second half of `Owns truth`).
