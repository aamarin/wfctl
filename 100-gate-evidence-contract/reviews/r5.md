## Detail

### W1 — `next` and `resume` name only the escape hatch (`_pipeline.py:L132`, `cli.py:L326-L338`, `cli.py:L370-L382`)

`DESIGN_BLOCK_COMMAND` is `wfctl arch none --reason "<why>"`, and that is the
whole of what a blocked design step puts in front of an agent on the two paths
that write state:

```
Next step: wfctl arch none --reason "<why>"
auto: false
why: no architecture record for this change
Run this command to continue.
```

The old refusal printed **both** branches — write a record, *or* declare none —
and `_pipeline.py:L101-L115` still argues, in the comment above
`DESIGN_BLOCK_HELP`, that offering only one "turns those into records that say
nothing". After this change only `wfctl status` prints both. `next` and `resume`
print the reason and the `arch none` command; `speckit-orchestrate` step 5's
`auto is false` arm displays `Next: run {next_command} when ready.` — again the
escape alone.

Scenario: a change that genuinely moves a boundary reaches the gate. The agent
reads `next-step.md`, sees one command, and runs `wfctl arch none --reason
"..."`. It has now written a durable declaration that the change draws no
boundary, and the gate — whose stated purpose (FR-010a, quoted in
`design_block`'s own docstring) is "to stop the question going unanswered" — has
been answered wrong by default, by the path of least resistance the tool itself
laid down. `auto: false` keeps a human nominally in the loop, but the human is
being handed a one-option prompt.

Fix: put both remedies in the file. The reason `DESIGN_BLOCK_HELP` is not
already there is that it needs `{location}`, which only `cli` can resolve — but
`cli` is the one writing the file, so it can format it there just as it does for
the console at `cli.py:L279-L282`. `next_command` can stay the safe single
command; the `why:` block is where the second branch belongs.

### W2 — `decompose`'s reason never reaches the payload (`_pipeline.py:L515`)

```python
reason = {"implement": implement_reason, "brainstorm": design_reason}.get(name)
```

`decompose_reason` is set at `_pipeline.py:L482` and, when `tasks_open`, sets
`state = "in_progress"` — a third blocking step, in the same function, four
lines above. It is not in the dict and no comment says why.

Concrete result: a delivery plan with unkeyed issue rows and open tasks makes
`decompose` the current step. `status` renders `decompose  ▶  3 issue rows
without a key`. `next` looks up `s.reason` (`cli.py:L316`), gets `None`, and
writes:

```
Next step: /speckit.decompose
auto: false
Run this command to continue.
```

That is verbatim the failure the new comment at `cli.py:L328-L331` claims to
have fixed — "Without it this file says 'run this to continue' over a step that
is blocked". The `_PipelineStep.reason` comment ("The unrendered half of
`annotation`") is also false for this step: `annotation` is populated and
`reason` is null, in the same payload.

This is the drift `_implement_verdict` was extracted to prevent, reproduced one
level up in the field that was added to prevent it. Either add
`"decompose": decompose_reason` (and then W4 becomes load-bearing, see below),
or state in the comment that `reason` means "reason a gate holds this step",
which decompose's row-count is not.

### W3 — markup injection in the two new console lines (`cli.py:L338`, `cli.py:L382`)

```python
console.print(f"  [dim]{blocked}[/dim]")
```

`blocked` for `implement` is built at `_pipeline.py:L280-L286` from
`" ".join(c)` over the repo's own `wfctl.json` commands. Verified against rich:

```
input : failed — 1 of 1 at abc1234: pytest -k not [slow]
output:   failed — 1 of 1 at abc1234: pytest -k not
input : failed at abc1234: npm run test [/x]
raises: MarkupError: closing tag '[/x]' at position 39 doesn't match any open tag
```

The first case silently eats the command name — which SC-006 requires a blocked
user to learn from this output (`_pipeline.py:L283`). The second is worse: in
`next_cmd` the `console.print` at L338 runs *before* `next_step_md.write_text`
at L342, so a repo whose verify command contains a `[/…]` token gets a
traceback, a non-zero exit, and a **stale** `next-step.md` — the exact
"event log and next-step.md disagree after a command that reported failure"
state that `test_a_refused_resume_does_not_advance_state` exists to document.

The project already knows this hazard and has the fix: `_arch_location`'s
docstring (`cli.py:L830-L834`) explains it and calls `rich.markup.escape`. The
status-page annotation print shares the flaw and pre-dates this diff, so fixing
all three together is the right shape. Per the review skill's security pass,
config is untrusted input.

### W4 — the blocked branch's `else` is "every step that is not implement" (`_pipeline.py:L648`)

```python
return ("wfctl verify" if step == "implement" else DESIGN_BLOCK_COMMAND), False
```

Today this is safe only because `reason` is populated for exactly two steps.
The moment anyone acts on W2 and adds `"decompose": decompose_reason`, a
delivery plan with unkeyed rows routes the agent to `wfctl arch none --reason
"<why>"` — a false architecture declaration written in response to a missing
issue key. Nothing in the type system or the tests stands in the way; the change
is one dict entry.

Write it as the two-way branch it is (`if step == "implement": … ; if step ==
"brainstorm": …`) and fall through to the table otherwise, so a third blocking
step is a compile-time-visible omission rather than a silently wrong remedy.

### W5 — `verification_block` feeds `blocks` a verdict it has not computed (`_pipeline.py:L276`)

```python
if blocks("inconclusive" if record["inconclusive"] else "satisfied", "repo-declared"):
```

A record with `exit != 0`, or stale against HEAD, is labelled `"satisfied"`
here and only later found unsatisfied by the six checks below. The expression
reduces to `record["inconclusive"]`, so it is behaviour-neutral today — which is
also why the "wired through `blocks` so the two gates cannot drift again"
comment (L270-L275) overclaims: the only rule change this call site can absorb
is one that stops `repo-declared` blocking. A rule change touching `satisfied`
or `unsatisfied` (which the record's own `Source` axis invites — `human`
approval that is advisory rather than binding, say) reads this site as saying
verification passed when it failed.

Either compute the real verdict once and route all seven outcomes through
`blocks`, or accept that this gate resolves `inconclusive` locally and say so —
but do not centralise a rule by handing it a value that is not the gate's
answer.

### W6 — a test name that is now a false sentence (`tests/test_pipeline_commands.py:L479`)

`test_a_refused_resume_does_not_advance_state` — this diff's whole point is that
`resume` no longer refuses. The body has been rewritten and its docstring says
so honestly ("neither is written past a refusal that no longer happens"), but
the name is what shows in a failure report. `CLAUDE.md`: "Test names are
sentences." This one asserts something the code cannot do.
`test_resume_is_gated_too` (L353) has the same issue in milder form — nothing is
"gated" any more in the sense that word carried.
