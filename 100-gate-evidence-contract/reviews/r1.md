# Review: `git diff origin/main..HEAD` — 100-gate-evidence-contract (reviewer r1)

Target: `wfctl/_pipeline.py`, `wfctl/cli.py`, `wfctl/agents/skills/speckit-orchestrate/SKILL.md`,
`docs/architecture/promised-evidence-blocks-on-silence.md`, tests.

The core move is right: a gate that reports through the payload instead of
refusing beside it removes the exact `status` says X / `next` does Y drift
`pipeline-state-is-one-payload` forbids, and `_implement_verdict` collapsing two
independently-composed copies of "is implement done" is a real health win. The
findings below are about what the refusal carried that the annotation does not,
and about a rule the record claims is applied at three sites and the code applies
at one.

---

BLOCKER  wfctl/_pipeline.py:605 — a blocked `brainstorm` routes to
`/speckit.brainstorm`, and the reason never reaches `next-step.md` or the console,
so the only action that unblocks the step is unreachable from the two commands
that write the agent's instruction.

Scenario. Branch has `specs/<b>/design.md`, no `spec.md`, no record under the
arch root. `design_block` returns `DESIGN_BLOCK_REASON`, `brainstorm` reads
`in_progress`, `_current_step_name` returns `brainstorm`, and
`next_step_content` takes the `blocked` branch at :605 → `_STEPS["brainstorm"][0]`
= `/speckit.brainstorm`, `auto=False`. `cli.py:306` then writes

```
Next step: /speckit.brainstorm
auto: false
Run this command to continue.
```

and `cli.py:307` prints `→ Next step: /speckit.brainstorm (auto: false)`.
`cli.py:339` prints the same for `resume`. The reason string exists only as
`steps[].annotation` in the payload, which `next` and `resume` never render.

Three things are wrong with that destination, and the docstring at :601–604
asserts the opposite of each ("its own command is where that gets written"):

1. `wfctl/agents/commands/speckit.brainstorm.md:9` — `allowed-tools` is
   `… Bash(wfctl arch-root*) Bash(wfctl arch check*) …`. `wfctl arch none` is not
   in it. For the `design-levels`-excluded change — the case `DESIGN_BLOCK_REASON`
   and the old refusal comment both name as legitimate — the declaration is the
   *only* correct answer, and the routed command is not permitted to write it.
2. `speckit.brainstorm.md:87` — the records that command writes on the way out are
   `<arch-root>/design/<issue>-<decision>.md`, and `_pipeline.py:527` passes
   `exclude=arch / "design"`. Its own level-3 output cannot satisfy the gate that
   routed to it.
3. `speckit.brainstorm.md:126-129` — "**Output:** `specs/<branch>/design.md`,
   written by `idea-refine` … a second write to that path destroys the approved
   design." The tool now instructs "Run this command to continue" against a
   `design.md` that already exists.

Compare the `implement` arm, which the docstring cites as the parallel: it routes
to `wfctl verify`, the thing that *produces* the missing evidence, not to
`/speckit.implement`. `brainstorm` should get the same treatment.

Fix (either, or both): return the reason from `next_step_content` (or read it off
`report.steps` in `cli`) and render it under the `Next step:` line in
`next-step.md` and on the console, so `wfctl arch none --reason "<why>"` is
visible where the agent reads; and/or route a blocked `brainstorm` to the
producing command the way `implement` routes to `wfctl verify`. As written, the
change moved the reason into the payload and dropped it from the two writers,
which is a strictly worse instruction than the exit-1 message it replaced.

WARNING  wfctl/cli.py:301 — `next` recomputes the block it already has, so
`wfctl next` runs the gate twice and takes a second, independent inference read.

`next_cmd` calls `_infer_steps` at :293 (which populates `_PipelineStep.reason`),
then calls `next_step_content(step_name, repo_root, spec_dir)` without the
`blocked` argument, so `_step_block` re-derives it. On an `implement` step that
is `verification_block` twice — config read, record load, and `_verify.code_identity`'s
`git rev-parse` + `git status`. On a blocked `brainstorm` it is
`touched_on_this_branch` twice, up to three `subprocess.run` calls each.

`build_report:684` was changed specifically to avoid this, and its own comment
says so ("Recomputing it here is the one call this seam was meant to collapse").
`next_cmd` is the remaining site that has the answer and throws it away — and it
is the one place two reads of the same artifacts can now disagree, which is the
failure `PipelineReport`'s docstring (:630–635) and `pipeline-state-is-one-payload`
exist to prevent: a `wfctl verify` finishing between :293 and :301 makes the
state table and the routed command disagree inside a single `next`.

Fix: `blocked = next((s.reason for s in steps if s.name == step_name), None)` at
:300 and pass it, exactly as `build_report` does. Better still, have `next_cmd`
call `build_report` — it is now the only pipeline writer that does not.

WARNING  wfctl/_pipeline.py:27 — `blocks(verdict: Verdict, source: str)` types the
verdict as a closed `Literal` and the source as an open `str`, and the open half
is the one whose typo fails silently in the unsafe direction.

`blocks("inconclusive", "repo-declaraed")` returns `False` — proceed — and mypy
accepts it, because `_PROMISED` membership at :42 is a runtime set test over an
untyped string. The record's own Consequences say "The evidence source has to be
nameable at the point it is read"; naming it in the type system is what makes
that enforceable rather than conventional. This is the one place a future gate
author can silently opt out of the rule the whole record exists to centralise.

Fix: `Source = Literal["repo-declared", "accepted-record", "human", "ambient"]`,
`def blocks(verdict: Verdict, source: Source) -> bool`, and keep `_PROMISED` as
the subset.

WARNING  wfctl/_pipeline.py:24, :531, :202 — `promised-evidence-blocks-on-silence`
is written as a rule over three gates and implemented at one, and the one it is
implemented at is the one whose behaviour did not change.

The record's Decision says a gate "returns one of satisfied/unsatisfied/inconclusive.
It does not resolve `inconclusive`", and its Consequences call for "something at
each read site saying which class the source belongs to". In the tree:

- `design_block:531` is the only production call to `blocks`, and it always
  passes `"ambient"`. With `source` fixed, `blocks` reduces to
  `verdict == "unsatisfied"` — which is what the old `design_gate` already did.
- `verification_block:233` still resolves `inconclusive` inside the gate
  (`if record["inconclusive"]: return "inconclusive — re-run \`wfctl verify\`"`),
  produces no `Verdict`, and names no source. It is the gate the record's Context
  opens with.
- `_arch.parse_record` is unchanged, which the record states outright.

So `_PROMISED`'s three members (`repo-declared`, `accepted-record`, `human`) are
reachable only from `tests/test_pipeline_commands.py:1115-1117`. The rule is real
and worth having; what is in the tree is the rule's declaration without its
adoption, and the mechanism that would have caught a fourth gate re-deriving the
policy (a `Verdict` at each read site) is not wired to any site but one.

Fix, smallest version that makes the record true: express `verification_block`'s
record read as a `Verdict` and route it through `blocks(v, "repo-declared")`, so
the two gates share the call and not just the prose. Otherwise re-scope the record
to the one gate it changes, and drop `_PROMISED` until the second caller lands.

**Answers to the four things flagged for attention**

- *Does any reachable state now report something untrue?* No. `brainstorm ▶` with
  `design.md` present and no record is an accurate reading, and it is more honest
  than the old `brainstorm ● / specify ○ ← current / next: /speckit.specify`
  followed by an exit-1 from `next`. What is untrue is the *instruction*: see the
  BLOCKER.
- *Can the design gate fire when it should not, or fail to fire when it should?*
  I could not construct either. The old trigger was `step == _AFTER_DESIGN`
  ("specify") with `design.md` present; `specify` is current only when it is
  `pending` (with markers it is `in_progress`, which implies `clarify` is too, and
  `_current_step_name:547-552` skips it), and `specify` is `pending` exactly when
  `spec.md` is absent. So old and new triggers are the same set:
  `design.md` present ∧ `spec.md` absent. The `spec.md` guard at :513 is a faithful
  restatement of `_AFTER_DESIGN`. Note it is no longer *derived* from `_STEP_NAMES`,
  so inserting a step between brainstorm and specify no longer moves the gate with
  it — the comment at :514-518 acknowledges this and I accept the trade.
- *Does the `blocked` sentinel recompute or skip wrongly?* The sentinel itself is
  sound: `_RECOMPUTE` correctly separates "no verdict" from "verdict is None", and
  every `build_report` path passes a value that matches what `_step_block` would
  have computed. The defect is a caller that does not use it — see the `cli.py:301`
  WARNING.
- *Did the deleted cli refusal remove behaviour nothing replaced?* Yes, two things.
  The escape-hatch text with the resolved arch root (WARNING on :95), and the
  reason reaching `next-step.md` at all (BLOCKER). The exit code and the
  no-event-past-refusal property are deliberate and adequately re-covered by the
  rewritten `test_a_refused_resume_does_not_advance_state`.

**Tests.** The new tests read behaviour, not implementation, and
`test_a_blocked_design_step_is_never_automatic` pins the exact regression its
docstring names. Two gaps: nothing asserts the reason reaches `next-step.md` or
`next`'s console output (which is why the BLOCKER is invisible to the suite — the
tests assert the *step name* in `next-step.md` and the *reason* in `status`, never
both in the same place), and nothing covers `design_block` with `spec.md` present
and no record, the guard at :513 that keeps a shipped story from reopening.

net: −20 lines possible (`Verdict`/`_PROMISED`/`blocks` collapse to
`verdict == "unsatisfied"` until a second production caller exists; the :472 dict
folds into the two arms above it)
