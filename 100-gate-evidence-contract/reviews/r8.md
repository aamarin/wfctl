## Findings

### WARNING `wfctl/cli.py:339` (and `:397`) — `next-step.md` puts the pasteable remedy directly above "Run this command to continue."

`a85e360` folds `remedy` into the file body between `why:` and the closing sentence.
Rendered (verified by composing the real constants):

```
Next step: /speckit.brainstorm
auto: false
why: no architecture record for this change
  Either record the boundary this change draws:
      docs/architecture/<slug>.md
  or state that it draws none:
      wfctl arch none --reason "<why>"
Run this command to continue.
```

Two defects in one:

1. The remedy block is the only field in this file with no key. `Next step:`,
   `auto:` and `why:` are all `key: value`; the `how` variable is named but writes
   nothing, so an unlabelled indented block lands in the middle of a keyed record.
2. `Run this command to continue.` no longer unambiguously refers to `Next step:`.
   The command physically nearest that sentence is
   `wfctl arch none --reason "<why>"` — the exact string `9085a1c` removed from
   `next_command` one commit earlier, on the argument that it is "a remedy a reader
   can paste back to fake the answer". It is now back, in the file an agent acts on
   rather than in a field a human reads via `status`.

Two mitigations keep this off BLOCKER, and I want them stated rather than implied:
`arch none` now refuses the literal `<why>` (`cli.py:987`), and a fabricated
declaration is a committed file a reviewer sees. But the failure that survives both
is the one-substitution version: an agent reads the imperative, sees the placeholder,
and supplies a reason it invented — permanently satisfying the gate. Under
`auto_approve: true` nobody is there to notice. The defect is the framing, not the
presence of the remedy.

Fix: move `Run this command to continue.` above the remedy block, or key the block
(`how:\n{remedy}`) so the trailing imperative binds to `Next step:`. `status` already
gets this right — the remedy there follows `next:` with no imperative attached.

### WARNING `wfctl/_pipeline.py:664-668` — `repo_root` and `spec_dir` are now dead parameters that are still passed

Deleting `_step_block` and `_RECOMPUTE` left `next_step_content` accepting two
arguments it never reads. The docstring paragraph that explained them

Both production call sites (`cli.py:328`, `_pipeline.py:761`) still pass them, which
reads as though they matter.

The "~30 call sites" premise does not survive checking either: `grep -rn

population of positional callers to preserve.

`ruff`'s enabled rule set (`E4,E7,E9,F`) does not include `ARG`, so this passes lint
silently.

Fix: `def next_step_content(step: str, blocked: str | None = None)` and drop the two
arguments at both call sites. `delete:` 2 params.

### NIT `wfctl/_pipeline.py:529-530` — two-phase construction of `_PipelineStep`

### NIT `wfctl/_pipeline.py:524-528` — a `done` decompose step now ships a non-null `reason`

The comment says "Every arm that can set `state = "in_progress"` from evidence puts
