## Findings

### WARNING  `wfctl/_pipeline.py:112-117` + `wfctl/agents/commands/speckit.brainstorm.md:117` — the fix guards one half of the placeholder and ships the other half further

`9085a1c` correctly identified that `wfctl arch none --reason "<why>"` was a string a
reader could paste back to fake the answer, and added `cli.py:983` to refuse it.
`a85e360` then moved the *whole* `DESIGN_BLOCK_HELP` block — both branches — into
`next-step.md`, the file an agent acts on. The other branch is:

```
  Either record the boundary this change draws:
      docs/architecture/<slug>.md
```

Nothing refuses a literal `<slug>.md`. Worse, it is *cheaper* than the path that was
just closed. `touched_on_this_branch` (`wfctl/_paths.py`) checks
`git status --porcelain` **before** `trunk...HEAD`, so an **untracked** file under the
arch root satisfies the gate — no `wfctl` command, no `git add`, no commit.
`speckit.brainstorm.md`'s `allowed-tools` grants `Write`. `arch check` only asks
"committed and unmodified", not "is this a placeholder", and `status`'s
unreadable-record notice warns rather than refuses.

So the diff's own argument — "a reader who pastes the example back gets … a
permanently answered gate" — applies verbatim to the branch it left unguarded, and
the diff is what put that branch in front of the agent.

**Fix:** mirror the `arch none` guard on the record side. Cheapest form: have
`design_block` discount records whose stem matches `<.*>` (or, symmetrically, teach
`arch check` to refuse one), so the two answers to the gate carry the same guard.
A rename of the placeholder alone (`<slug>` → something obviously not a filename)
narrows the window without closing it.

### WARNING  `wfctl/_pipeline.py:664-668` — `repo_root` and `spec_dir` are now dead parameters that silently disable the gate

After the `_RECOMPUTE`/`_step_block` deletion, `next_step_content`'s body reads only
`step` and `blocked`. `repo_root` and `spec_dir` are accepted and ignored, and the
docstring paragraph that used to describe them was replaced — so nothing in the
function tells a reader they do nothing. Both remaining call sites
(`_pipeline.py:761`, `cli.py:328`) still pass them.

This is the exact hazard the deleted `_RECOMPUTE` sentinel existed to prevent, inverted:
`next_step_content("brainstorm", repo_root, spec_dir)` now returns
`("/speckit.brainstorm", True)` for a blocked step, silently, with no way for the caller
to tell it was never gated. Neither ruff (`E4,E7,E9,F` only — no `ARG`) nor
non-strict mypy will catch a future caller doing this.

**Fix:** drop both parameters — `def next_step_content(step: str, blocked: str | None = None)` —
and update `_pipeline.py:761`, `cli.py:328` and `tests/test_pipeline_commands.py:1194`.

### WARNING  `wfctl/cli.py:445` → `wfctl/cli.py:478` — the fourth unescaped repo-supplied site, in `end`

`9085a1c` names three sites where repo-supplied text reached rich unescaped and fixes
them (`status` annotation, `next` reason, `resume` reason). `_observe` builds
`step = f"{current['name']} {current['annotation']}"` and `end_cmd` prints it through
`console.print` at line 478 with no `escape()`. `implement`'s annotation embeds
`verification_block`'s failure reason, which joins the repo-declared commands verbatim:

```
failed — 1 of 2 at abc1234: pytest [unit]      → prints "…pytest " (silently truncated)
failed — 1 of 2 at abc1234: pytest [/x]        → rich.errors.MarkupError
```

Confirmed against rich directly. The MarkupError fires *after* `_session.end()` has
already written the summary, so `wfctl end` writes state and then reports failure —
the same write/print disagreement `next_cmd` was just reordered to avoid.

Pre-existing code, but it is the same class of defect the diff set out to close and it
sits one function away from a site the diff did fix. Leaving it makes the claim
"repo-supplied text reached rich unescaped at three sites" false in the file.

**Fix:** `console.print(f"[green]✓[/green] Session closed — {escape(observed.step)}, …")`.
(`observed.step` also goes into the summary file, which is plain text and fine.)

### WARNING  `wfctl/_pipeline.py:98-111` — two comments now contradict the code they sit on

`DESIGN_BLOCK_HELP`'s header still says the caller formats it "with a location only
`cli` can resolve and escape" (:100) and that it "stays where `_arch_location` can
escape it, and the payload carries the fact instead" (:110-111). After `a85e360`
`_pipeline.arch_location` resolves it, `_design_remedy` formats it, and the payload
carries the *rendered remedy*, not "the fact instead". Per `CLAUDE.md` ("Existing
comments are dense with rationale — match that"), a comment asserting the opposite of
the design is worse than none: the next reader will look for the resolution in `cli`.

**Fix:** rewrite both sentences to name `_design_remedy` / `_pipeline.arch_location` and
`cli._arch_location` as the escaping wrapper.

### WARNING  `wfctl/agents/skills/speckit-orchestrate/SKILL.md:113-131` — the consumer the change is justified by never reads the new field

`a85e360`'s stated reason for moving the remedy into the payload is that
"the consumer that acts on the block — `speckit-orchestrate` — reads JSON". Step 4 of
that skill reads only `next_command` and `auto`; nothing in it reads `reason` or
`remedy`. So in the `auto: false` branch (step 5) an orchestrated run now emits:

> Next: run `/speckit.brainstorm` when ready.

with no statement that the step is blocked, why, or how to clear it — where before the
diff `next_command` was at least the (bad) `wfctl arch none …` string that hinted at the
remedy. Step 2 displays `wfctl status`, which does print both, so the information is on
screen; but the line the skill is instructed to emit as its answer carries none of it.

**Fix:** add `reason` and `remedy` to what step 4 reads, and have step 5's `auto: false`
branch render them under the "Next:" line. Without that, `remedy` is a payload field
whose only consumers are the two console/file views that already had access to
`arch_root` — which is a thinner justification than the commit message claims.

### NIT  `next-step.md` trailer no longer matches its body

For a blocked design step the file now reads:

```
Next step: /speckit.brainstorm
auto: false
why: no architecture record for this change
  Either record the boundary this change draws:
      docs/architecture/<slug>.md
  or state that it draws none:
      wfctl arch none --reason "<why>"

```

"Run this command to continue." now sits under a remedy that names two things, neither
of which is the command on line 1 — and by the diff's own argument the command on line 1
is *not* what clears the gate. The remedy is also the only unkeyed multi-line block in an
otherwise `key: value` file. → make the trailer conditional, e.g. "Answer the above, then
re-run this command." when `remedy` is present.

### NIT  `wfctl/_pipeline.py:518-527` — the comment overstates what the map holds

"Every arm that can set `state = "in_progress"` from evidence puts its reason here" — but
`decompose_reason` is set at `_pipeline.py:481` whenever rows are unkeyed, including the
`tasks_open == False` path where `state` stays `"done"`. So `status --json` can carry
`{"name": "decompose", "state": "done", "reason": "3 issue rows without a key"}`. Harmless
today (`_current_step_name` never selects a `done` step, so it can't reach `blocked`), but a
JSON consumer that reads `reason` as "why this step is blocked" — which is what the field
name and every other arm imply — will be wrong. → say "its reason, blocking or not", or
gate the map entry on the state.

### NIT  `wfctl/cli.py:983` — the placeholder guard has no link to the string it guards

`re.fullmatch(r"<[^>]*>", …)` lives in `cli.py`; the `<why>` it exists to catch is written
in `DESIGN_BLOCK_HELP` in `_pipeline.py` and in `speckit.brainstorm.md`. Change the
placeholder spelling in either of those and the guard silently stops matching, with the
test (`test_a_placeholder_reason_is_refused`) still green because it hardcodes `<why>`
too. → derive or cross-reference; at minimum a comment in `DESIGN_BLOCK_HELP` naming the
guard.

net: −13 lines possible (−12 orphan comment, −2 dead params, −1 struct→field, +2 for the
two `escape()` calls)

**Verdict: Request changes** — 0 blockers, 5 warnings. The change definitely improves code
health: one computation feeding four views, one rule for silence, and a genuinely dangerous
