BLOCKER  wfctl/_pipeline.py:605 — a blocked design step routes to `/speckit.brainstorm`, and running that command against an existing `design.md` destroys it → route to what actually unblocks the step

`return ("wfctl verify" if step == "implement" else _STEPS[step][0]), False` sends
a blocked `brainstorm` to `/speckit.brainstorm`. `next_cmd` then writes
`Next step: /speckit.brainstorm\nauto: false\nRun this command to continue.` and
`speckit-orchestrate` step 5 (`auto` is `false`) displays
`Next: run /speckit.brainstorm when ready.`

`wfctl/agents/commands/speckit.brainstorm.md:105` says of `design.md`: *"a second
write to that path destroys the approved design."* The command carries no
"design.md already exists, stop" guard — it re-runs `design-levels` →
`brainstorming` → `idea-refine` and `idea-refine` writes `design.md` at the end.
So the pipeline's own recommended next action, in the one state where the design
step is blocked, is the action that overwrites the approved design.

Worse, the thing being asked for is not there. Per
`wfctl/agents/skills/design-levels/SKILL.md:254`, a level-2 record is written with
`architecture-decisions` under `wfctl arch-root`; per
`speckit.brainstorm.md:87`, what that command's *own* output section names is a
level-3 record at `<arch-root>/design/<issue>-<decision>.md` — the subtree
`design_block` explicitly **excludes** (`exclude=arch / "design"`,
`wfctl/_pipeline.py:521`). An agent that obeys `next_command` literally can
destroy `design.md`, write a `design/` record, and still be blocked.

The code comment at `_pipeline.py:601-603` asserts the opposite —
*"`brainstorm`'s is a missing record, and its own command is where that gets
written"* — and `speckit-orchestrate/SKILL.md:107-109` repeats it: *"`next_command`
names what unblocks it rather than what the gate would refuse."* That is true for
`implement` → `wfctl verify` and false for `brainstorm`.

Scenario: `specs/<branch>/design.md` exists, no record, no `spec.md`. `wfctl next`
exits 0, writes `/speckit.brainstorm`, agent runs it, approved design gone, step
still blocked on the next pass.

Fix: name an action that produces the missing evidence. The deleted
`DESIGN_GATE_REFUSAL` already had both —
`{location}/<slug>.md` or `wfctl arch none --reason "<why>"`. Either return
`wfctl arch none --reason "<why>"` as `next_command` (the `wfctl verify`
precedent shows a non-slash command is legal on this wire), or keep
`/speckit.brainstorm` only when `design.md` is absent.

WARNING  tests/test_pipeline_commands.py:233, :277, :316 — three gate tests now assert a condition that is unconditionally true, so they pin nothing

Under the old shape `assert runner.invoke(app, ["next"]).exit_code == 0` meant

  the vacuous assertion.

This is the "quietly dropped coverage" case: the diff rewrote the *negative* gate
tests to assert on `status` output and left the *positive* ones asserting an exit
code that no longer varies. Fix: assert `"brainstorm   ●"` / `"next: /speckit.specify"`
(or `"no architecture record" not in out`) the way the rewritten
`test_resume_is_gated_too:352` already does.

By contrast `test_the_gate_is_one_transition_not_the_rest_of_the_pipeline:329-330`
survives, because it also asserts `"/speckit.plan" in result.output`.

WARNING  wfctl/_pipeline.py:27 — `blocks()` has one caller passing a literal, and the two gates the record is about never consult it

`blocks(verdict, source)` is called exactly once, at `_pipeline.py:530`, with the
constant `"ambient"`. Substituted, the whole apparatus reduces to
`return DESIGN_BLOCK_REASON if touched is False else None` — which is what
`cli.py` did before, spelled `is False`.

`verification_block` (`_pipeline.py:202`) — the gate the record names as the other
policy — still hardcodes its own answer (`if record["inconclusive"]: return
"inconclusive — re-run wfctl verify"`, `:229`). `_arch.parse_record`
(`wfctl/_arch.py:112`) still hardcodes its own. So two of the three
`"repo-declared"`/`"accepted-record"` members of `_PROMISED` (`:24`) are strings
no caller ever passes, and `"human"` is a source nothing reads at all.

The record's own **Consequences** states the structure it forces: *"something at
each read site saying which class the source belongs to."* One of three read
sites has it, and nothing — not a test, not a type — stops the fourth gate from
re-deriving, which is the failure the record was written to prevent.

Fix (minimum): route `verification_block`'s three unavailability cases
(`errs`, `record is None`, `record["inconclusive"]`) through
`blocks(..., "repo-declared")` so the rule has a second caller, or mark
`_PROMISED`'s unused members explicitly as not-yet-read and drop `"human"` until
something reads it (`yagni`).

Related, and a real failure-open path: `source: str` is untyped while
`verdict: Verdict` is a `Literal`. `blocks("inconclusive", "repo_declared")`
(underscore) returns `False` — promised evidence silently proceeds — and mypy
cannot see it, because the project runs without `--strict` and `str` accepts
anything. Fix: `Source = Literal["repo-declared", "accepted-record", "human",
"ambient"]`.

does not happen. This is the same class, in the same suite. Fix:
`subprocess.run(["git", "init", "-b", "main", str(tmp_path)], ...)`.
