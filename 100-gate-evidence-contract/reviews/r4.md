BLOCKER  wfctl/_pipeline.py:L132 — the routed remedy is a literal placeholder, and following it defeats the gate → refuse a placeholder reason in `arch none`

`DESIGN_BLOCK_COMMAND = 'wfctl arch none --reason "<why>"'` is now the value of
`next_command` in the JSON payload, of the `next:` line in `status`, and of the
`Next step:` line in `next-step.md` — the field whose whole contract is "run this
verbatim". `cli.py:L333` writes:

```
Next step: wfctl arch none --reason "<why>"
auto: false
why: no architecture record for this change
Run this command to continue.
```

Run it as written and `arch_none_cmd` (`cli.py:L961`) accepts it: the only guard
is `if not reason.strip()`, and `<why>` is non-empty. It writes
`<arch-root>/declarations/<branch>.md` containing the single line `<why>`, prints
a green ✓, and — because `design_block` counts anything touched under the arch
root outside `design/` — the gate is satisfied permanently. The boundary question
is now recorded as answered by a file that says nothing.

This is the exact failure the epic exists to prevent, reached through wfctl's own
instruction. It is worst under `auto_approve: true`, which
`speckit.brainstorm.md` describes as the mode where "each gate's answer goes into
its record" with no human present — there the literal-execution path is the
designed one. `wfctl-runs-the-verification`'s own principle applies against it: a
declaration is an unfalsifiable self-report, and this promotes it from one of two
prose escapes to *the* routed next action.

The prior shape did not have this. `DESIGN_GATE_REFUSAL` carried `<why>` inside
explanatory prose under "or state that it draws none:", never in a field an agent
executes.

Worse, the tests lock the defect in: `tests/test_pipeline_commands.py:L1198`
asserts `command == 'wfctl arch none --reason "<why>"'`, and
`tests/test_pipeline_commands.py:L382` asserts `next-step.md` starts with it.

Fix (cheapest, and it reuses the argument already written at `cli.py:L960`):

```python
if not reason.strip() or re.fullmatch(r"<.*>", reason.strip()):
    console.print("[red]✗[/red] --reason cannot be empty: say why no boundary changed.")
    raise typer.Exit(1)
```

A placeholder is the same silent omission an empty reason is, with a command in
front of it. Alternatively keep `next-step.md`'s `Next step:` line as a command
that is safe to run verbatim (`wfctl status`, which already prints both remedies)
and carry the two escapes in the `why:` body — but the input guard is needed
either way, because a blocked agent can type the placeholder from `status` too.

WARNING  wfctl/cli.py:L338, L382 — `blocked` is interpolated into rich markup unescaped; `next` crashes and leaves `next-step.md` stale → `escape()`, and move the print after the write

`blocked` for `implement` is built from repo config: `verification_block`
(`_pipeline.py:L282`) returns `f"failed — … : {', '.join(failed)}"`, where
`failed` is the commands out of `wfctl.json`. Those reach
`console.print(f"  [dim]{blocked}[/dim]")` unescaped. Verified against the
installed rich:

| `wfctl.json` verify entry | what happens |
|---|---|
| `["npm","test","--","--grep","[unit]"]` | `MarkupError: closing tag '[/unit]' … doesn't match any open tag` — command aborts |
| `["pytest","-k","[slow]"]` | prints `failed — pytest -k` — the command name and everything after it silently vanish |

The second case breaks SC-006 (a blocked user learns *which* command failed from
`status` alone). The first is worse in `next_cmd`, because the ordering there is
print-then-write (`cli.py:L336-338` before `L343`): the exception aborts before
`next_step_md.write_text(content)` and before `append_event`, so `next-step.md`
holds whatever was true on the last successful run and the agent acts on a stale
step. `resume_cmd` writes first (`L377`) and prints second (`L382`), so the two
new sites are inconsistent with each other as well.

The project already has the answer and documents it: `_arch_location`'s docstring
(`cli.py:L830`) — "Escaped here rather than at each print, because one caller
forgetting is silent." These are two callers forgetting.

```python
from rich.markup import escape
...
next_step_md.write_text(content)          # write first, as resume does
if blocked:
    console.print(f"  [dim]{escape(blocked)}[/dim]")
```

(`status_cmd`'s annotation print at `cli.py:L266` has the same hazard on `main`;
this diff does not introduce the class, but it extends it to the two commands
that write session state, where the consequence is a stale file rather than a
missing line.)

WARNING  wfctl/agents/commands/speckit.brainstorm.md:L45-49 — the file claims the gate holds the step, and the same file's front matter walks past it

New prose: "`wfctl`'s design gate holds a design step that produced no record —
in both modes … `status`, `next` and `resume` all say so."

Four lines above, in the same file's front matter:

```yaml
handoffs:
  - label: Start Specify
    agent: speckit.specify
    prompt: The design document is ready in specs/<branch>/design.md. Run specify.
```

`send: true` dispatches specify when brainstorm ends, consulting no wfctl command.
Specify writes `spec.md`, and `design_block` (`_pipeline.py:L557`) returns `None`

present, no record, spec.md present), and nothing observes it. Either soften the
claim to what is true ("the next `status`/`resume` reports it"), or make the
handoff conditional on the gate.

NIT      docs/architecture/promised-evidence-blocks-on-silence.md:L57 — `Owns truth` names an owner the code does not give it to

Against `architecture-decisions`' checklist the record passes on every mechanical
item: slug filename, both halves of `Owns truth`, the owned thing as a quoted
question, a concrete `Direct baseline`, four real alternatives with true reasons,
a dated `Log` line for `proposed`, all required sections present. The substantive
gap is the claim itself:

> The evidence source owns "what does it mean that this evidence is unavailable?"
> … Asked at the gate, it is re-derived per gate and drifts; asked at the source,
> it is answered once.

The code does not ask at the source. `_paths.touched_on_this_branch` and
`_verify.load_record` say nothing about their class; each *gate* asserts it as a
string literal at the call site — `blocks(verdict, "ambient")` at
`_pipeline.py:L575`, `blocks(…, "repo-declared")` at `L276`. The record's own
`Consequences` concede this ("something at each read site saying which class the
source belongs to"), which contradicts the `Owns truth` paragraph two sections
up. The `Literal` type stops a typo, not a miscategorisation: a third gate
reading a verify record and passing `"ambient"` type-checks and fails open.

Either move the classification to the source (e.g. `touched_on_this_branch`
returning its source tag, or a `SOURCE_OF` map keyed by reader) so `Owns truth`
is true of the code, or rewrite `Owns truth` to name the rule — not the source —
as the owner, which is what `blocks` actually is. The record is `proposed`, so
the body is still editable; per the skill it has to carry this before it can be
accepted.

## Verdict

**Request changes** (1 blocker, 6 warnings).

The restructure is the right shape and it improves code health: one three-valued
verdict, one rule, the design gate reporting through the payload instead of
beside it, `_implement_verdict` as a single owner, and a blocked step that is
never `automatic` — that last one is a genuine bug the merge caught and fixed
before it shipped. The blocker is not the architecture; it is that the remedy the
new routing hands to an agent is a placeholder that, executed as instructed,
silently satisfies the gate this whole branch exists to enforce. Guard the input
in `arch none` and that goes away. The escaping and the `reason`/`decompose`
inconsistency are both small and both in the payload contract, which is the part
of wfctl other repos parse.
