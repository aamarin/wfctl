WARNING  wfctl/cli.py:L340 — `wfctl notify <x> --declined --reason ...` records a
decline on a run that was **refused**, and prints "may notify people, but
skipped" over a run that may not. The action path guards this exact hazard three
lines down ("the log is the report, so a false line there is a false report");
the decline path does not check `resolved_notify` at all. Reproduced: after
`wfctl start --deny-notify`, the command exits 0 and writes
`{"event": "notify-declined", ...}`. FR-011 exists to keep *declined* apart from
*refused for want of a grant*, and this inverts it in the flattering direction —
the report claims the agent held authority and chose not to use it, which is the
one signal that says the grant should be widened. By the change's own standard
(`a-rule-is-expressed-as-a-check`) this belongs as a check: the violation is
visible in an artifact the work produces.
→ gate the decline on `resolved_notify(agent_dir).granted` the same way the
action path is; on a refused run print `_notify_line(grant.source, None)` and
`raise typer.Exit(1)`, or record `notify-refused` instead. Add the test the
sibling case already has (`test_an_ungranted_run_cannot_record_an_action…`).

WARNING  wfctl/_session.py:L201 — "could not determine the trunk branch" is
reported as `unreadable`, whose console line is "couldn't reach the issue tracker
to check". That names a cause that is not the cause — the same defect the
contract already corrected once ("couldn't reach GitHub"), and the same
collision the contract argues `corrupt` must not share with `unreadable`.
Reproduced in a repo whose trunk is `develop` with no `origin/HEAD`:
`wfctl start --allow-notify` writes the grant, then prints *couldn't reach the
issue tracker* with **no tracker configured at all**, and the feature is
unreachable on every branch of that repo — the trunk check sits above the local
file read, so `--allow-notify` can never take. Fail-closed is right; the reason
is wrong and the blast radius is a whole repo shape (`_trunk_branch` only knows
`main`/`master`/`dev`).
→ give it its own source (e.g. `unknown-trunk`) and its own ≤72-char line
("will not notify anyone — couldn't tell whether this is the trunk"), and add
the case to `test_the_refusals_are_distinguishable_from_each_other`. The
`_trunk(root)` helper in `test_notify_grant.py` asserts the fixture *has* a
trunk, so this path is currently untested.

WARNING  wfctl/_tracker.py:L375 — `notify_grant` can raise, contradicting the
invariant its own docstring states ("Never raises"). `_load_tracker_config`
validates nothing beyond "is a dict", so a config declaring `"labels": 3` (or a
string) reaches `for tok in config["verbs"]["labels"]`. Reproduced: `wfctl start`
dies with `TypeError: 'int' object is not iterable` and a traceback. dispatch has
the same latent hole, but there it costs one command; here it is on the
session-open path.
→ `argv = config["verbs"]["labels"]`; `if not isinstance(argv, list) or not all(isinstance(t, str) for t in argv): return None, f"'labels' is not a list of strings"`.
Same shape `validate_config` already reports.

WARNING  wfctl/_tracker.py:L69 — FR-008 is enforced at resolve time only; the
gate re-reads the log and never re-asks the branch. With the documented flat
`WFCTL_STATE_DIR` override, a grant made on `418-feature` is honoured on the
trunk: reproduced — `wfctl issue comment` ran the backend on `main` (exit 0) and
`wfctl status` there printed "may notify people". `notify_grant`'s comment claims
the assertion "survives the state dir changing shape"; it does not, because the
enforcement point is `_refuse_notifying`, not the resolver. Narrow (the override
already collapses other per-branch state) but the comment overstates what the
code buys.
→ either re-ask `on_trunk(repo_root, resolve_branch(repo_root))` in
`_refuse_notifying` — a git call, no tracker round-trip, so it costs nothing —
or soften the comment to say the property holds only while the state dir is
per-branch.

WARNING  wfctl/cli.py:L282 / wfctl/_session.py:L376 — `notify-unread` duplicates
a fact `notify-resolved` already carries, and it defeats the idempotence the code
beside it argues for. `record_notify_resolved` skips an unchanged answer so
"a second run must leave the log byte-identical"; `record_notify_unread` right
next to it appends unconditionally. Reproduced with an unreachable tracker:
three `wfctl start` runs → one `notify-resolved`, **three** `notify-unread`,
carrying the same detail string. The existing idempotence test only covers
`unset`, where `detail` is None, so the broken half is unasserted.
→ delete `record_notify_unread` and its call (`notify-resolved` already holds
`granted`/`source`/`detail`), or move the call inside the dedup so both events
follow one rule. Then extend
`test_a_second_start_that_resolved_the_same_answer_appends_nothing` to a failing
read.

NIT  wfctl/_tracker.py:L347,L351 — the `read_issue_labels` docstring names the
wrong verb twice ("through the backend's own `view` verb", "one that declines
`view`"), while the code checks `"labels" not in config.get("verbs", {})`. This
is the exact `view`-vs-`labels` distinction the contract records as the fix; the
prose kept the pre-fix wording. In a repo whose AGENTS.md makes comments
load-bearing, this one will mislead the next reader.
→ s/`view`/`labels`/ in both places.

NIT  wfctl/_session.py:L174 — `notify_grant`'s docstring justifies never raising
because "a raise here breaks `status`, `start`, `resume` and `end` at once". Only
`start` calls it; the others read `resolved_notify`. The reasoning is right, the
caller list is not.
→ name `start`, and say the other three read the recorded answer.

NIT  wfctl/_tracker.py:L103 — the remedy line hard-codes `authority:notify` while
`_session.NOTIFY_LABEL` is the declared home of that string ("which label means
*may notify* is this module's business").
→ f-string it from `NOTIFY_LABEL`, imported in the same deferred import two lines
above.

NIT  wfctl/_session.py:L338 — `yagni: count: int = 1` has no producer. dispatch
passes one action per call, `wfctl notify` passes one, and the contract argues
*against* counts in the rendering ("the number contradicts the reason"). Only a
test supplies it.
→ drop the parameter; add it back when something counts.

NIT  wfctl/_tracker.py:L346-L390 — `read_issue_labels` re-implements dispatch's
manifest → config → identity → `_substitute` → `subprocess.run` pipeline (~20
lines) because dispatch returns an exit code rather than stdout.
→ extract `_run_verb(repo_root, section, verb, params) -> tuple[int, str, str] | None`
and let both call it; the notifying gate and the event append stay in dispatch.

NIT  wfctl/_tracker.py:L390 — the label read is the first network call wfctl
makes on the `start` path and has no `timeout=`. A wedged `gh` now wedges
`wfctl start`, which is the command an unattended run opens with. dispatch is
equally untimed, so this is consistent rather than new — but the consequence is
worse here.
→ `subprocess.run(..., timeout=…)`, treating `TimeoutExpired` as a failed read
(`unreadable`, which is already the right verdict).

NIT  wfctl/cli.py:L305 — `--reason` without `--declined` is silently ignored: the
command falls through to the action path and records `notify-action` with the
reason dropped.
→ refuse the combination, or fold `--reason` into `--declined`'s presence.

NIT  wfctl/cli.py:L1467 — `wfctl issue --help` still says only "Degrades
gracefully (exit 0) when no tracker is configured"; it does not mention that
`comment`, `create` and `label` now refuse by default and exit 1. AGENTS.md was
updated, the help text a user actually hits was not. The refusal message itself

## What each pass checked, including where it found nothing

**Correctness.** Walked all fifteen FRs against the code, not the tasks file.
FR-001/002/003/004/005/006/007/010/012/013/014 hold and are tested from the
granted side where the ungranted side would pass vacuously — the test suite is
unusually disciplined about this and the docstrings say why. FR-008 holds by
construction and fails under the flat state-dir override (above). FR-011 holds in
one direction and not the other (above). FR-015 holds for four of five refusals
and collides for the fifth (above). FR-009 is deliberately untested and the spec
argues that correctly. Checked the `changes` section for a bypass: it is
read-only (`ALLOWED_CHANGES = {list, view}`), so no notifying verb escapes the
gate through it. Checked that `close` is genuinely ungated in both directions and
records no `notify-action`. Checked the label match is whole-line (an issue body
naming `authority:notify` cannot grant itself) — it is, with a test.

**Security.** No shell interpolation anywhere new: argv lists, within-token
`_substitute`, and the existing inert-token test now grants first rather than
being exempted, which is the right way to keep it. No secrets logged — the
tracker's stderr goes to the event log, which is the deliberate split, and
`test_no_tracker_stderr_reaches_the_console` pins that it never reaches stdout.
The self-grant surface is accepted in the spec and argued in the record; nothing
here widens it. The one integrity hole is the decline path (W1), which lets an
actor write a claim about its own authority.

**Architecture.** `_session` ↔ `_tracker` is now a genuine import cycle, broken
with function-level imports on both sides — the house pattern (`_pipeline` does
the same and says why), so not a finding, but it is now two-way. The policy split
reads right: which label means *may notify* lives in `_session`, how to read
labels lives in `_tracker`; the one leak is the hard-coded label string in the
remedy line. `labels` as a declared verb rather than parsing `view` output is the
correct call and the contract's argument for it holds.

**Readability.** Names are accurate (`NotifyGrant.source`, `_NOTIFY_LINES`,
`_refuse_notifying`). No deep nesting, no boolean-flag params, no nested
ternaries. Comment style matches AGENTS.md — they explain *why this shape*, and
the ones that narrate a change ("Amended during `implement`") are in the contract
file where they belong, not in the source. Two comments state more than the code
delivers (W4, N2) and one names the wrong verb (N1).

**Performance.** One tracker round-trip per `wfctl start`, and the resolution
order genuinely spends none on the common paths — a local grant or deny returns
before the tracker is asked, with a test that fails the backend to prove it.
`build_report` now reads and parses `events.jsonl` twice per call
(`session_started` + `_last_resolved`); logs are tens of lines, so this is noise,
but a single pass returning both would be free if either grows. No N+1, no
unbounded fetch. The only real latency risk is the missing timeout (N6).

**Over-engineering.** The diff is dense but little of it is speculative. The
second file rather than a second key on `mode.json` is argued and cheaper than
the merge logic it avoids. The tri-state flag is required, not clever. What can
go: `record_notify_unread` (duplicate truth, W5), `count` (no producer, N4), and
the duplicated config→argv pipeline (N5).

net: −35 lines possible
Verdict: **Request changes** (0 blockers, 5 warnings — W1 and W2 are the two that
falsify a report or a cause, and both are small fixes)
