## Findings

BLOCKER  wfctl/_session.py:219 — `if issue is None` never fires from the only
production caller, so a branch with no issue key is filed as a *failed tracker
read*. `_resolve_context` (cli.py:117-130) types `issue` as `str` and
`extract_issue_key` returns the string `"unknown"`, never `None` — cli.py:1482
already handles this with `if issue == "unknown"`. Reproduced on branch
`hotfix-typo` with a tracker configured:

```
$ wfctl start
will not notify anyone — couldn't reach the issue tracker to check
```
```json
{"event": "notify-resolved", "granted": false, "source": "unreadable",
 "detail": "invalid issue format: \"unknown\""}
{"event": "notify-unread", "detail": "invalid issue format: \"unknown\""}
```

The tracker was reachable; there is simply no issue to read a label off. This
is the conflation FR-015 exists to forbid ("a failure to read the grant MUST be
distinguishable from a grant that was read and found absent") and it costs an
unnecessary tracker round-trip on every `wfctl start` on such a branch. It fails
closed, so it is not a safety hole — but the distinction the feature was built
to make is inverted for this whole class of branch, and the contract's own text
("`issue` is `None` where the branch carries no issue key") describes a
precondition nothing establishes.
→ `if issue is None or issue == "unknown": return NotifyGrant(False, "unset")`,
or normalize to `None` in `_resolve_context`. Add a CLI-level test — the unit
tests pass `None` explicitly, which is why this survived them.

WARNING  wfctl/_session.py:198 — `on_trunk` returning `None` is filed as
`unreadable`, whose console line names the issue tracker as the cause. A repo
where no trunk can be named prints a false cause, including when no tracker is
configured at all. Reproduced in a repo whose only branch is `418-feature`
(no `origin/HEAD`, no `main`/`master`/`dev`, no `.wf-skills-manifest.json`):

```
$ wfctl start
will not notify anyone — couldn't reach the issue tracker to check
```

This is the same defect `contracts/notify-grant.md` split `corrupt` out of
`unreadable` to avoid — "sharing `unreadable` with it would mean printing
*couldn't reach GitHub* over a damaged local file, naming a cause that is not
the cause." The argument holds; it was just not applied to this third case.
→ Give it its own source (`untrunked`) and line, or route it to `corrupt`'s
"couldn't read the setting for this work", which at least does not name a
subsystem that was never consulted.

WARNING  wfctl/_pipeline.py:585-608 — `wfctl status` on the trunk branch, before
any `wfctl start` has run there, prints the `unset` line rather than the `trunk`
line. `build_report` reads the resolution back from the event log, and on `main`
there usually is none. Reproduced with a clean state dir on `main`:

```
$ wfctl status
will not notify anyone — nobody has allowed it for this work   # says a grant is possible
$ wfctl start
will not notify anyone — only feature branches can be granted this
```

The `trunk` source exists precisely so a reader is not sent "hunting for the
flag that turns it on" (contract, Read section), and `main` with no session is
the most common way to meet that line. Unlike the label read, `on_trunk` is a
local git call with no network cost, so the read-back argument in the comment at
`_pipeline.py:606` does not cover it.
→ Short-circuit in `build_report`: when `on_trunk(repo_root, branch)` is True,
report `notify_source="trunk"` regardless of what the log holds.

WARNING  wfctl/_tracker.py:337 — `read_issue_labels`' first docstring line says
"through the backend's own `view` verb". It uses the `labels` verb; the rest of
the same docstring explains at length why `view` was abandoned. A reader who
stops at the summary line takes away the thing the paragraph below exists to
correct.
→ "through the backend's own `labels` verb".

WARNING  wfctl/agents/commands/end-session.md:4 — `allowed-tools` was not updated
for the `wfctl notify` calls this diff added to `end-session/SKILL.md:157-162`.
The list carries `Bash(wfctl status*)`, `Bash(wfctl end*)`, `Bash(wfctl issue
view*)` and no `Bash(wfctl notify*)`, so `wfctl notify push` and `wfctl notify
push --declined --reason …` are outside the declared set. Unattended is exactly
where FR-010's push record matters, and a push is the one notifying action no
wfctl verb performs — which is the stated reason `wfctl notify` was built. (In
fairness: `wfctl issue comment/close/create` are also absent and step 7 has
always needed them, so this list is already not maintained as a complete
permission set. That is an argument for fixing both, not for leaving this one.)
→ Add `Bash(wfctl notify*)`.

NIT  wfctl/_session.py:378 — `delete:` `record_notify_unread` writes a `detail`
the log already carries. `record_notify_resolved` puts `detail` on the
`notify-resolved` event, and `report_notify` (cli.py:277-286) then writes the
same string again as `notify-unread` — verified byte-identical in a live
`events.jsonl` above. The contract's claim that this is "the only place the
cause survives" was true of an earlier shape in which `notify-resolved` carried
no detail. Keep one: either drop `detail` from `notify-resolved` (it is read
only by the dedupe comparison in `record_notify_resolved`) or drop this function
and its call site. ~18 lines including the docstring and its test.

NIT  wfctl/_session.py:338 — `yagni:` `count: int = 1` has no production caller

`record_notify_action(agent_dir, verb)`; `notify_cmd` calls

`test_notify_grant.py` passes 6, and `data-model.md`'s `{"count": 6}` example is

exists.

NIT  wfctl/_tracker.py:97 — the refusal prints the raw source token

NIT  wfctl/agents/skills/end-session/SKILL.md:40 — "issues to reconcile in step

NIT  wfctl/cli.py:174 — `_IRREVERSIBLE_NOTICE` reads "that is always yours, no
setting for it"; the pinned wording in `contracts/notify-grant.md` is "there is
no setting for it". The contract records two deliberate rewrites during
`implement` (the GitHub naming, the trunk line) and this third one is not among

NIT  wfctl/_session.py:193,222 — the deferred imports create a genuine

`_paths.py:500,576` establishes the convention for this and annotates it
(`# lazy: avoids import cycle at module load`); these two carry no such marker,
and the `on_trunk` one at :193 is deferred without a cycle to justify it. One
comment each, matching the existing form.

NIT  wfctl/_tracker.py:365 — `read_issue_labels` runs a repo-supplied argv with
`subprocess.run(...)` and no timeout, and it is now on the `wfctl start` path,
which `/start-session` runs unattended on every handoff. A wedged backend hangs

`wfctl/` sets a timeout today, so this matches practice — but `plan.md` states a
one-round-trip budget and nothing bounds it. Worth a follow-up issue rather than
a change in this diff.

## Passes with nothing to report

**Security.** argv is a list throughout — `_substitute` is within-token and the
issue key reaches `{id}` as one inert argument, so the malicious-body test at
`test_tracker.py:74` covers the new verb by construction. No secrets, no shell,
no new untrusted parse beyond one-label-per-line with `.strip()` and whole-string
comparison (`test_a_label_is_matched_whole_and_never_as_a_substring` pins the
substring case, which the earlier `view`-header implementation would have
failed). The one thing worth naming and not a finding: `wfctl start` now
executes a repo-supplied tracker command where it previously touched no tracker.
The reachable path to a hostile `labels` argv is a committed
`.wf-skills-manifest.json` naming a malicious `--from` source, which `AGENTS.md`
already warns about under Safety; this adds a second moment at which that
already-warned-about content runs.

**Performance.** The design's own claim holds. A local `granted` or `denied`
returns before any tracker call (`test_a_local_grant_needs_no_second_opinion`
asserts it against a backend that would fail if consulted), the label read
happens once per `wfctl start` rather than per command, and `build_report` reads
back. `_last_resolved` scans the whole `events.jsonl` per call, matching
`session_started` beside it; per-branch logs are small enough that this is not
worth changing. The only measurable waste is the round-trip the BLOCKER causes
on keyless branches.

**Architecture.** The gate sits at the one funnel every tracker write passes
(`dispatch`, after the config checks and before argv), which is the placement
`a-rule-is-expressed-as-a-check` argues for and which the diff's own comment
defends correctly. `close` outside `_NOTIFYING_VERBS` is right and the reasoning
in both the code and `test_notify_declined.py` is sound —
`approval-mode-is-stored-intent` does establish that wfctl cannot tell a human
from an agent, so gating `close` would land on the wrong actor.
`notify.json` as a second file rather than a second key on `mode.json` is
correctly argued from `write_json_atomic` replacing wholesale. The new
`notify_source` on `PipelineReport` respects `pipeline-state-is-one-payload`
(one payload, views transform it). `session-state-is-re-derived` is respected in
substance: the answer is re-read from the event log, an artifact, rather than
cached in a file — the docstring at `record_notify_resolved` makes that argument
explicitly and it survives scrutiny.

**Tests.** Unusually strong, and the property that makes them so is stated in
each module docstring: the refusal claims are asserted from the *granted* side,
so they cannot pass against a resolver that returns False unconditionally
(`test_a_grant_written_on_the_trunk_branch_is_still_refused`,
`test_no_grant_value_changes_the_irreversible_notice`,
`test_a_granted_run_reaches_them`). `test_notify_dispatch.py` asserts on a
marker file the backend writes rather than on the exit code, which is the only
assertion that catches a gate that prints a refusal and runs the command anyway.
The 72-character line test and the no-wrap assertion on rendered output are both
carrying real weight. FR-009's deliberate absence of a test is argued in the
spec and I agree with the argument — a test there could only assert the rule is
documented. The one gap is the BLOCKER's: every `notify_grant` test constructs
`issue` by hand, and none goes through `_resolve_context`.

**Contract divergences.** All four claimed divergences were checked and three
hold. The four-argument signature is forced (FR-008 needs repo and branch;
`_resolve_context` computes all four together). `trunk` and `corrupt` as
separate sources are forced by the same argument the contract makes, and I would
add that the argument extends to the trunk-unknown case it does not cover
(WARNING 2). The `labels` declared verb over parsing `view` output is correct
and the reasoning is the stronger half — the substring hazard is real (#280's
own body names the label) and a `gh`-shaped header would have silently read as
"no labels" on every other backend. The `close`-is-not-gated divergence from
T024 is correct and better than what T024 asked for. The one claim that no
longer holds is `record_notify_unread` being the only place the cause survives
(NIT 1).
