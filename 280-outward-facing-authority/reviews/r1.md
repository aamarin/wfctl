## Findings

### BLOCKER

**`wfctl/_session.py:218` + `wfctl/cli.py:267` — a branch with no issue key
resolves to `unreadable`, blaming a tracker that is fine.** *(proven)*

`notify_grant` guards the no-issue case with `if issue is None`. No caller ever
passes `None`: `_resolve_context` is typed `tuple[Path, Path, str, str]` and
`extract_issue_key` returns the sentinel string `"unknown"` when the branch
carries no key (`_paths.py:41`). So the guard is dead from the CLI, and the
keyless branch falls through to `read_issue_labels(repo_root, "unknown")`, which
shells out to the backend, gets a non-zero exit, and returns a `detail` — which
`notify_grant` turns into `NotifyGrant(False, "unreadable", …)`.

Reproduced on a fresh repo, branch `no-key-branch`, GitHub tracker configured:

```
$ wfctl start
will not notify anyone — couldn't reach the issue tracker to check

events.jsonl:
{"event": "notify-resolved", "granted": false, "source": "unreadable",
 "detail": "invalid issue format: \"unknown\""}
```

The detail is the proof: the sentinel reached `gh` as an issue number. Three
things are wrong at once —

1. **FR-015 is violated in its own terms.** "A failure to read the grant MUST be
   distinguishable in the record from a grant that was read and found absent."
   Here a grant that is simply absent (there is no issue to carry a label) is
   recorded as a failed read. This is the exact misfiling the requirement exists
   to prevent, and the contract's `detail`-splits-by-destination argument makes
   it worse, not better: the event log now carries a tracker error for a state
   that is not a tracker error.
2. **The console line states a falsehood.** The tracker was reached and answered
   correctly; the branch has no issue.
3. **It spends the run's one budgeted tracker round-trip** (`plan.md`: 1.4s) on
   every `wfctl start` for such a branch, to ask a question that has no answer.

wfctl supports keyless branches explicitly — `issue_cmd` handles `"unknown"` at
`cli.py:1482` and calls it "a worktree made outside the naming rule" — so this
is a reachable ordinary state, not a corner.

The verdict stays *refused*, so nothing unsafe happens; the defect is that the
run misreports why, on the one axis this feature was built to get right.

→ **Fix:** normalise the sentinel at the call site,
`notify_grant(agent_dir, repo_root, branch, None if issue == "unknown" else issue)`
(`cli.py:267`), keeping the sentinel knowledge in `cli.py` where
`_BRANCH_SCOPED_VERBS` already checks for it. Add a test that a keyless branch
resolves `unset`, not `unreadable` — the current suite only exercises the
`issue=None` path that production never takes.

### WARNING

**`wfctl/_paths.py:102` + `wfctl/_session.py:200-201` — an unnameable trunk is
also filed as `unreadable`, blaming the tracker in a repo that may not have
one.** *(proven)*

`on_trunk` returns `None` when `_trunk_branch` finds neither `origin/HEAD` nor a
local `main`/`master`/`dev`. `notify_grant` maps that to
`NotifyGrant(False, "unreadable", "could not determine the trunk branch")`, and
`_NOTIFY_LINES["unreadable"]` reads *"couldn't reach the issue tracker to
check"*. Reproduced on a `develop`-only repo **with no tracker configured at
all** — the line still blames the issue tracker.

This is the same mistake the change itself corrects twice elsewhere: the label
read stopped parsing `gh`'s header because it named one backend, and the console
wording dropped "GitHub" for the same reason. The contract's own argument for
splitting `trunk` and `corrupt` off `unset` — *"folding that into `unset` would
send a reader hunting"* — applies here verbatim.

→ **Fix:** a sixth source (`"no-trunk"`) with its own line, e.g.
`will not notify anyone — couldn't tell which branch is the trunk`. Under 72
chars, so the pinned-width test still holds.

**`wfctl/cli.py:337-343` — `wfctl notify <action> --declined` never consults the
grant, so an ungranted run can file a decline and claim it had permission.**
*(proven)*

```
$ wfctl start                                     # nothing granted
will not notify anyone — nobody has allowed it for this work
$ wfctl notify push --declined --reason "not my call"
may notify people, but skipped push — not my call     # exit 0
events.jsonl: {"event": "notify-declined", "action": "push", …}
```

The run's own `notify-resolved` line two entries above says
`granted: false, source: "unset"`. The non-declined branch at `cli.py:350-352`
refuses for precisely this reason — *"the log is the report, so a false line
there is a false report"* — and the declined branch above it does not.

FR-011 requires the report to distinguish *declined* from *refused for want of a
grant*. Two event kinds exist, but nothing stops a refused run writing the
declined kind, and `end-session` step 8 then renders it as a run that had
authority and chose not to use it. The failure is in the direction that
overstates authority, which is the worse of the two.

→ **Fix:** in the `declined` branch, read `resolved_notify(agent_dir)` first;
refuse (exit 1, printing `_notify_line`) when not granted — or record it as
`notify-refused` and say so. Add the ungranted case to
`test_the_decline_line_leads_with_the_permission_it_had`, which currently grants
first and so cannot see this.

**`wfctl/cli.py:285-287` — `notify-unread` is appended outside the dedupe, so
the one state that repeats is the one that grows the log.** *(proven)*

`record_notify_resolved` (`_session.py:281`) skips the append when the answer is
unchanged, with a stated reason: *"`/start-session` runs `wfctl start` on every
handoff, so an unconditional append would make the log grow with lines that say
what the previous one said."* `report_notify` then calls `record_notify_unread`
unconditionally. Three `wfctl start` runs against a persistently unreadable
grant:

```
{"event": "notify-resolved", "source": "unreadable", "detail": "…"}
{"event": "notify-unread", "detail": "…"}
{"event": "notify-unread", "detail": "…"}     # identical
{"event": "notify-unread", "detail": "…"}     # identical
```

It is also redundant on its face: `notify-resolved` already carries `detail`, so
`notify-unread` adds no fact. The `detail`-splits-by-destination argument is
satisfied by `notify-resolved` alone.

→ **Fix:** delete `record_notify_unread` and its call (~14 lines including
docstring); the cause already survives in `notify-resolved.detail`. If a
dedicated event kind is wanted, move the call inside the dedupe.

**`wfctl/_session.py:222` ↔ `wfctl/_tracker.py:88,340` — a new bidirectional
module dependency, and the contract's caller claim is now false and unrecorded.**

`_session` imports `read_issue_labels` from `_tracker`; `_tracker` imports
`resolved_notify`, `record_notify_refused` and `record_notify_action` from
`_session`. Both directions are function-local imports, which is an established
pattern here (`_pipeline` → `_session`, `_tracker` → `_paths`) — but those are
one-way. This is the first cycle.

`contracts/notify-grant.md` says of the boundary: *"these are internal to wfctl,
and `cli.py` is the only caller."* That is no longer true, and unlike every other
`implement`-time divergence in that file, this one is not recorded. The
neighbouring note about `dispatch` being "one caller added" records the gate, not
that it inverted the dependency.

→ **Fix:** either record the divergence in the contract with its argument, or
have `dispatch`'s caller pass the resolved grant in as a parameter, leaving
`_tracker` free of `_session`.

## The recorded divergences — do the arguments hold?

The parent asked specifically. Taking `contracts/notify-grant.md` in order:

| Divergence | Holds? |
|---|---|
| `notify_grant` gains `repo_root`, `branch` | **Yes** — FR-008 cannot be asked without them. But *"Both callers already hold all four"* is stale: there is exactly one caller (`start_cmd`); `build_report` calls `resolved_notify`. |
| Sources `trunk` and `corrupt` added | **Yes.** Distinct events, distinct lines, and the tests assert the five refusals render five different strings. This is the strongest part of the change. |
| `detail` splits console vs. log | **Yes**, and `test_no_tracker_stderr_reaches_the_console` pins it properly. |
| `labels` as a declared verb, not `view` parsing | **Yes, emphatically.** Both stated reasons check out, and `test_a_label_is_matched_whole_and_never_as_a_substring` covers the one an attacker would reach for. |
| `_tracker.dispatch` as a gate | **Yes** on the rule side (`a-rule-is-expressed-as-a-check` applies cleanly, and exit 1 vs. exit 0 is argued correctly and tested). See the cycle warning for what it did to the boundary claim. |
| `close` outside the gated set | **Yes.** Asserted from the granted side, which is the only side that can fail. |
| Console wording rewritten (generic tracker, shorter trunk line) | **Yes** — though `_IRREVERSIBLE_NOTICE` was *also* trimmed ("there is no setting for it" → "no setting for it") to fit 72 chars, and that one is not recorded, in a section that says the strings are "the wording, not a paraphrase of it". |

**The largest divergence is not recorded at all.** The contract's Read section
describes `notify_grant` as the read; the implementation added
`record_notify_resolved` / `resolved_notify` and a `notify-resolved` event, and
every command except `wfctl start` reads a *recorded verdict* rather than
resolving. Neither the function nor the event appears in the contract or in
`data-model.md`'s three event kinds.

Its defence against `session-state-is-re-derived` (`_session.py:274-279`) does
not hold on that record's own terms. The record forbids treating a written value
as authoritative *for a value that can be recomputed*, and this one can —
`notify.json` plus the label. The comparison to `session_started` fails for the
same reason: *whether a session started* is not recomputable from anything else,
whereas this is. The honest framing is that FR-014 buys a deliberate exception
for a stated cost (one round-trip per run, not per command), which is a good
trade — but it is an exception to an **accepted** record, and nothing writes it
down as one.

One concrete consequence: `data-model.md` says returning to unset is deleting
`notify.json`. Deleting it does not take effect until the next `wfctl start`,
because `resolved_notify` never consults the file. `--deny-notify` covers the
practical case, so this is small — but it is the kind of thing the record exists
to keep visible.

1. **Correctness** — traced `notify_grant` through `on_trunk`, `_read_notify_file`
   and `read_issue_labels`; `resolved_notify` through `_last_resolved`;
   `dispatch`'s gate placement relative to the config checks and argv build;
   `start_cmd`'s two exits. Exercised keyless branches, no-trunk repos, ungranted
   declines and repeated `start` in scratch repos. Found the blocker and three of
   the warnings this way, not by reading.
2. **Security** — argv-only substitution, no shell, free text stays one inert
   token (existing test still passes with the grant added); label compared as
   whole-line set membership, substring case tested; the sentinel that reached
   `gh` is regex-constrained; grant is tamper-evident by design and the record
   says so. One durable-log NIT.
3. **Architecture** — checked against the nine accepted records via
   `wfctl arch context` plus the proposed `a-rule-is-expressed-as-a-check`,
   `session-state-is-re-derived`, `knowledge-placement`,
   `the-underscore-is-the-module-contract`. Two findings (the cycle, the
   unrecorded read-back).
4. **Readability** — comment style against AGENTS.md's inform-don't-narrate rule
   (three sites), one self-contradicting docstring, one stale skill
   cross-reference. Naming is good throughout; `_notify_line`, `_refuse_notifying`
   and `NotifyGrant` all say what they hold.
5. **Performance** — the wasted round-trip per `wfctl start` on keyless branches
   (folded into the blocker); the unbounded `notify-unread` growth; `_last_resolved`
   parses the whole `events.jsonl` on every `build_report` and every gated
   dispatch, which is milliseconds at realistic sizes and not worth changing.
6. **Over-engineering** — `record_notify_unread` (redundant with
   `notify-resolved.detail`), the unused `count` parameter. The `section ==
   "verbs"` guards are defensively redundant but cheap and I would leave them.
   Docstring density is high, but AGENTS.md asks for exactly that and I am not
   flagging it.

**Tests** — read first, as the skill asks. Coverage is genuinely good and the
"assert from the granted side" discipline is applied consistently and for the
right reason. The grid test, the trunk pair, the substring test and
`test_a_refused_action_records_nothing` all earn their place. Two gaps, both
named above: the keyless-branch path is untested (the tests exercise `issue=None`,
which no caller produces), and the ungranted `--declined` path is untested.
