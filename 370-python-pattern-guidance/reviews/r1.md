## Findings

### BLOCKER  wfctl/agents/skills/python-pattern-selection/SKILL.md:L179 — the ported skill ships with no attribution line, no `NOTICES.md` entry, and no row in `vendor-upstream-skills`

This is a derived work by the project's own definition, and near-verbatim.
Against the upstream lines #370 quotes from `python-architecture-design`:

| #370, quoting upstream | shipped SKILL.md |
|---|---|
| "Prefer direct construction and named arguments before Factory or Builder machinery." | identical |
| "`pickle` is used for untrusted or durable external data." | identical |
| "'Pythonic' is used as a substitute for a trade-off." | identical |
| "Prefer a function or callable before a Strategy or Template Method hierarchy." | + "class" |
| "Treat an ORM/session transaction as a viable baseline before adding Repository or Unit of Work wrappers." | "ORM session" |
| "Reject hidden Singleton access; give process-wide dependencies an explicit construction and lifetime owner." | split into two sentences |

`vendor-upstream-skills` is explicit that drift is not a threshold: *"Attribution
is owed on a rewritten derivative work exactly as on an untouched copy."* It is
equally explicit about when: *"A skill added later is declared when it is added,
by whoever adds it: a file taken from elsewhere gets its line and its row in the
same change that brings it in, and its upstream gets an entry in `NOTICES.md` if
it has none. There is no later pass that sweeps for missed ones."*

The accepted record in this very diff states the same obligation as its own last
Consequence — *"Attribution is owed under `vendor-upstream-skills`… declared in
`wfctl/agents/skills/NOTICES.md` with the upstream named on the file's own last
line"* — and the commit that was supposed to discharge it does not.

The suite does not catch this, by design. `tests/test_skill_attribution.py`'s
docstring: *"A file arriving with no line **and** no row is invisible to both
directions."* That is #213 recurring, in the exact shape the record says the
checks cannot close.

Aggravating: the branch never establishes the upstream's identity. #370 locates
it at `~/Downloads/python-architecture-design/` — no repository, no licence, no
copyright holder. `MANIFEST.in` grafts `wfctl/agents` whole, so every release
distributes this text. `_LINE` requires all four facts (upstream, URL, licence,
holder) and `test_every_attribution_line_agrees_with_its_notice_entry` compares
them against `NOTICES.md`, so the line cannot be written until the upstream's
repo and licence are actually known.

→ Fix: establish the upstream repository, licence and copyright holder; add the
`Derived from [...](...) (MIT, © YYYY Holder).` line as the file's last line, a
`## <upstream>` section in `wfctl/agents/skills/NOTICES.md`, and a row in
`vendor-upstream-skills`'s first table (which makes it an `amended` Log line on
that accepted record — the one edit its own rules permit). If the upstream's
licence cannot be established, the port cannot ship.

### NIT  docs/architecture/level-4-reasoning-gets-its-own-shelf.md:L98-106 — the "no code change" claim is right on the mechanics and loose on one judgment

I verified this claim, since it was called out. The mechanics are correct:

- `_arch.load_records` is `sorted(root.glob("*.md"))` — one level. A fourth
  subdirectory stays out of the `wfctl arch context` projection exactly as
  `design/`, `declarations/` and `views/` do. ✓
- `records_on_this_branch` passes `[str(arch)]` to git, which is recursive, and
  reduces hits to `Path(p).stem`. An `implementation/` file is listed. ✓
- `_observe` calls `touched_on_this_branch(arch, exclude=arch / SCANS_DIR)`, so
  an `implementation/` file makes `boundary` read `answered`. ✓ mechanically.

I also checked the reader the record does not name — `_predicates.fact_architecture_accepted`
— and it is safe: it intersects `records_on_this_branch` with `load_records`, and
the one-level glob drops the new shelf, so the fact returns `n/a  no level-2
record on this branch`. That is the correct answer.

What is loose is *"which is correct here"* for `_observe`. `CLAUDE.md` describes
that field as saying *"whether the boundary question was answered"*, and a
level-4 mechanism note answers no boundary question — which is the same shape as
the `scans/` problem the exclusion was added for. `cli._observe`'s own comment
flags the identical open question one directory over: *"The pre-existing question
of whether a level-3 record under `design/` should count here — `design_block`
excludes it and this call does not — is older than this change and is left where
it was found."* The record asserts correctness where the code records an
unresolved question about the same shape.

Two smaller notes on the same paragraph. `records_on_this_branch` prints
`record: <stem>`, so an implementation note appears in the auto-approve listing
indistinguishable from a top-level record. And `fact_architecture_accepted`'s
docstring warns that slug matching is on bare stems, so a file under a
subdirectory sharing a stem with a top-level record reads as that record being
touched; the `<issue>-<slug>.md` convention makes a collision unlikely (top-level
records carry no issue number by `architecture-decisions`' own naming rule), and
`design/` and `declarations/` already carry the same exposure.

→ Fix: soften to what is demonstrable — the shelf is counted by `_observe` the
way `design/` already is, and whether either should be is the older question
`_observe` already names.
