## Findings

### BLOCKER — `wfctl/agents/skills/python-pattern-selection/SKILL.md`:L179 — a derived file ships with no attribution line, no notice entry, no record row, and its upstream is named nowhere in the tree

The change's own accepted record states the obligation and the change does not
discharge it. `docs/architecture/level-4-owns-pattern-selection.md`:L92:

> Attribution is owed under `vendor-upstream-skills`: a ported artifact is
> *derived*, declared in `wfctl/agents/skills/NOTICES.md` with the upstream named
> on the file's own last line, and `tests/test_skill_attribution.py` checks the two
> against each other.

What the diff actually contains:

- `SKILL.md`'s last line is `      code would ask why.` — no `Derived from […](…) (MIT, © …).` line.
- `wfctl/agents/skills/NOTICES.md` — untouched.
- `docs/architecture/vendor-upstream-skills.md` — untouched; no row for `python-pattern-selection`.
- `grep -rni "derived from|upstream|third-party|ported"` over both new files: the
  upstream repository is **never named**. Not its owner, not its URL, not its
  licence. The commit message cites "The source's line 108" without saying whose
  line 108 it is.

`MANIFEST.in` grafts `wfctl/agents` into the wheel, so every release distributes
this file. A derived work whose upstream cannot be identified cannot have its
MIT obligation assessed, let alone discharged.

**The green suite is not evidence here, and the test says so itself.**
`tests/test_skill_attribution.py`'s module docstring:

> What neither pair can do is notice #213 itself. A file arriving with no line
> *and* no row is invisible to both directions.

I confirmed this: the full suite — 1594 tests — passes with the file in the tree. This is #213
reproducing in the exact shape the record predicted, and `vendor-upstream-skills`
names the countermeasure: *"A skill added later is declared when it is added, by
whoever adds it: a file taken from elsewhere gets its line and its row in the
same change that brings it in."* Precedent is in the tree — #361's addition of
`speckit-brainstorm` touched `vendor-upstream-skills.md` even though that skill
is wfctl's **own**, in order to say so.

**Fix:** name the upstream repository, its licence and its copyright holder;
append the attribution line as `SKILL.md`'s last line; add the row to
`vendor-upstream-skills`' first table; add a `## <owner>/<repo>` section to
`wfctl/agents/skills/NOTICES.md` if that upstream has none. If the source is not
MIT, the permission block in `NOTICES.md` does not cover it and the port needs a
second licence block — `_licence_the_notices_carry()` will reject it otherwise.
If the port is genuinely not derived (independent restatement of public pattern
advice), say that in the record and delete the sentence at L92 that says it is.

### WARNING — `docs/architecture/level-4-reasoning-gets-its-own-shelf.md`:L96–L104 — "No reader of the arch root needs a code change" enumerates three readers; there are five, and the one it misses is a gate

The record verifies its claim against `load_records`, `records_on_this_branch`
and `_observe`. Two more readers of the arch root exist:

- `wfctl/_predicates.py`:L606 — `design_block` calls
  `touched_on_this_branch(repo_root, arch, exclude=arch / "design")`. Its
  exclusion list is `design/` **and nothing else**. Its own docstring gives the
  reason `design/` is excluded: *"it holds level-3 records, which govern one
  feature and are barred from drawing a boundary."* That argument applies to
  `implementation/` with more force, not less — level 4 is further from a
  boundary than level 3. A file under the new shelf therefore **satisfies the
  level-2 design gate**. The `spec.md` guard at L597 makes this unreachable in
  normal pipeline order (an implementation note is written during `implement`,
  after `spec.md` exists), which is probably why nothing broke — but the record
  claims completeness and never mentions the guard, so the claim is unverified
  rather than true.
- `wfctl/cli.py`:L5432 — `_check_arch_records`' docstring enumerates the tiers
  that stay out of link-integrity checking as "`<arch-root>/design/` and
  `declarations/`". Behaviour is correct (it goes through `load_records`), the
  enumeration is now incomplete.

Separately, the record asserts `_observe` counting the new shelf is *"correct
here"* and gives no argument. `_observe`'s field is `boundary`, defined at
`cli.py`:L708 as *"whether the boundary question was answered"*. A level-4
mechanism note answers no boundary question — that is this record's own thesis.
The #307 argument it cites against `scans/` applies verbatim: *"a scan file
counted here makes `boundary` constant-true and the observation stops carrying
anything."* The honest version of this paragraph is the one the code already
carries three lines above that call (`cli.py`:L740–743): the `design/` question
is open and pre-existing, and `implementation/` extends it one level further
down.

**Fix:** enumerate all five readers; state the `spec.md` guard as the reason
`design_block` needs no `:(exclude)`, or add one; replace "which is correct
here" with the argument, or attach `implementation/` to the open `design/`
question the code comment already names.

### WARNING — `wfctl/agents/skills/python-pattern-selection/SKILL.md`:L85, L178 — the shipped skill routes to a destination defined only in a `proposed` record, contradicting accepted `knowledge-placement`

`level-4-reasoning-gets-its-own-shelf` is `status: proposed`. Per

**Fix:** either get record 2 accepted in this change (the repo's hand-promotion
baseline, documented in `a-human-accepts-a-decision`'s Direct baseline, is
available — record 1 used it), or hold the two `<arch-root>/implementation/`

### WARNING — `design-levels` is not updated, so the canonical answer to "where does level 4 land" is now wrong

`.agents/skills/design-levels/SKILL.md` is untouched and still says, in three
places:

- gate table: `| 4 implementation | unchanged — the verification skills own it |`
- §4 heading: *"Implementation — covered by the existing verification skills … Nothing new here."*
- *Where the levels land*: *"Level 4 → belongs to the plan and to `speckit.tasks`, not to the design."*

`architecture-design`:L272 names *Where the levels land* as the single place
this question is answered: *"Where this iteration's output lands is answered
once, by `.agents/skills/design-levels`' 'Where the levels land' — read it
there."* After this change there are two answers and the canonical one omits the
new shelf and the new skill.

Two consequences the change should decide about rather than inherit:

1. The new skill is reachable **only** by description-trigger. The repo has a
   recorded failure of exactly this shape — a description-triggered skill that
   an unattended run silently skips. `design-levels` §4 is the one surface that
   would route to it deterministically and it currently says "Nothing new here."
2. In a *consuming* repo the situation is worse. `install-skills` mirrors
   `agents/skills`, `agents/commands`, `specify/scripts`, `specify/templates` and
   nothing else — `docs/architecture/` never ships. So a project receives the
   instruction to write `<arch-root>/implementation/<issue>-<slug>.md` and
   receives no definition of the shelf, no statement that it is a sibling of
   `design/`, and no rule for telling them apart.

`CLAUDE.md`'s Architectural constraints section — which enumerates `design/`,
`declarations/`, `views/` and `scans/` for an agent working on wfctl — is also
not updated, and per accepted `knowledge-placement` (*"guidance for the worker →
AGENTS.md"*) that is where the shelf convention belongs for this repo.

I am **not** flagging the absence of a check for the convention:
`a-rule-is-expressed-as-a-check` asks whether a violation is visible in an
artifact the work already produces, and nothing produces an implementation note,
so prose is the right form here. The finding is placement and reach, not form.

### WARNING — `docs/architecture/level-4-reasoning-gets-its-own-shelf.md` — the retrieval advantage over the direct baseline is asserted, not shown, and the `design/` vs `implementation/` test is not operable

Two halves.

**Retrieval.** The record rejects the commit-message baseline on retrieval:
*"`git log -S` over a file's history is a search, not a shelf."* But nothing in
the change indexes an implementation note from the code either.
`design-md-indexes-the-records` (proposed) exists because filename-derived
lookup for `design/` was judged insufficient, and `design.md` has a
`## Software design decisions` section for level-3 records; there is no
analogue for level 4, and `design.md` is gitignored anyway. A reader standing in
front of a wrapper asking *why is this here* reaches `git blame` → commit
message in one step, and reaches `implementation/370-foo.md` only by already
knowing the shelf exists and guessing which issue introduced the line. The
argument for the shelf may still be right, but as written it loses on its own
stated criterion.

**The sorting rule.** *"The shelf is chosen by the level the reasoning was
produced at"* is not a test a writer can apply to the common case. The record's
own worked material — a Repository wrapper over an ORM session — is
simultaneously a structural choice with a credible alternative (level 3,
`design/`) and a mechanism choice (level 4, `implementation/`). The skill sends
it to `implementation/`; `software-design-decisions` would claim it whenever an
alternative was genuinely weighed; and record 2's *Considered* rejects
`software-design-decisions` on the grounds its *Not for* excludes unweighed
choices — which says nothing about the weighed ones. The two shelves have no
stated boundary for the overlap, which is where every real case lands.

**Fix:** give one discriminating sentence with an example on each side, and say
what indexes a note back to the code it explains (the note naming the file and
symbol would be enough).

## Verdict

upstream unnamed anywhere, while the change's own accepted record states the
