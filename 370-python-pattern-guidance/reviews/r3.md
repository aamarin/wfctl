## Findings

### BLOCKER 1 — a derived skill ships with no attribution, and the tests cannot see it

`wfctl/agents/skills/python-pattern-selection/SKILL.md` is a port. Its own commit
message says so ("Ported from a third-party skill"), issue #370 names the source
(`python-architecture-design`), and the constraint list is the source's lines
169-183 and 211-226. The diff adds:

- no attribution line — the file's last line is `      code would ask why.`
- no entry in `wfctl/agents/skills/NOTICES.md`
- no row in `docs/architecture/vendor-upstream-skills.md`

All three are required, and this change is where they are owed.
`vendor-upstream-skills` (accepted): *"A skill added later is declared when it is
added, by whoever adds it: a file taken from elsewhere gets its line and its row
in the same change that brings it in… There is no later pass that sweeps for
missed ones."* This branch's **own accepted record** states it as a non-optional
consequence, and #370 lists it under Open.

The suite is green anyway, by design.
`tests/test_skill_attribution.py`'s module docstring: *"A file arriving with no
line **and** no row is invisible to both directions."* This is #213 arriving a
second time, in the one change that had the record in front of it.

Worse, it may not be dischargeable as written. The attribution line format
requires four facts — `Derived from [<repo>](<url>) (<licence>, © <year>
<holder>).` — and the source has none of them on record: #370 locates it at
`~/Downloads/python-architecture-design/` with no repository, no licence and no
holder, and that directory is unreadable from this process (`Operation not
permitted`). Shipping it means putting a derivative of an unknown-licence
third-party work into an MIT wheel that `MANIFEST.in` grafts into every release.

**Fix:** establish the upstream repository, licence and copyright holder before
merge. Then add the last-line attribution, the `NOTICES.md` section, and the
`vendor-upstream-skills` row in this change. If provenance cannot be
established, the port cannot ship — rewriting the constraints from first
principles is the alternative, and it has to be a real rewrite, not a reword.

### BLOCKER 2 — the skill is reachable by nothing

The commit subject is "python-pattern-selection fires where nothing else is
awake". Nothing can fire it:

- it is absent from `_MIRRORED_SKILLS` (`wfctl/cli.py` L2359-2437), so
  `install-skills` never puts it on the native `.claude/skills/` discovery path;
- there is no wrapper at `wfctl/agents/commands/python-pattern-selection.md`;
- `grep -rn` over the repo finds **zero** references to it outside its own
  frontmatter — `design-levels` does not name it, `architecture-design` does
  not, no command wrapper does.

`cli.py` states the rule verbatim in the `software-design-decisions` entry
comment: *"No wrapper under `agents/commands/`, so the mirror is the only route:
a skill absent from both is reachable only by an agent already reading
`design-levels` as text, which is the shape of #198 one hop down the pointer
chain."* `python-pattern-selection` is absent from both **and** unnamed by
`design-levels`, so it is one hop worse than #198 — there is no pointer to read.
`test_skill_cross_references` cannot catch this: it checks that referenced
skills ship, never that a shipped skill is referenced.

**Fix:** add `"python-pattern-selection"` to `_MIRRORED_SKILLS` with the comment
the set's convention requires, **and** name it from `design-levels` § 4 (finding
3). One without the other leaves a route that depends on which way the agent
reached, which is the fork that entry comment exists to remove.

### WARNING 3 — `design-levels` still says level 4 has nothing new

The accepted record's entire argument is that level 4 now owns pattern selection
and has a skill to own it with. The shipped `design-levels/SKILL.md` was not
touched and still reads:

- gate table: `| 4 implementation | unchanged — the verification skills own it |`
- § 4 heading: *"Implementation — covered by the existing verification skills …
  Nothing new here."*

Meanwhile the new skill's description says *"Use during design-levels level 4"*.
Two shipped files now contradict each other, and the one an agent actually reads
at level 4 is the one that says there is nothing to read.

**Fix:** update `design-levels` § 4 and the "where the answer lands" row to name
the new skill, in the same change.

### WARNING 4 — "no reader of the arch root needs a code change" is under-verified

`level-4-reasoning-gets-its-own-shelf` § Consequences enumerates three readers
(`load_records`, `records_on_this_branch`, `_observe`) and concludes the new
subdirectory needs no `:(exclude)`. Two of the three check out. The third does
not, and a fourth is missed:

| Reader | What a file under `implementation/` does | Record's claim |
|---|---|---|
| `_arch.load_records` | excluded — glob is `*.md`, one level | correct |
| `records_on_this_branch` | listed as a `record:` slug in `wfctl status` | stated, defensible |
| `_observe` / `boundary` (`cli.py` L744) | flips the session handoff's **Boundary** to `answered` | claimed "correct here", with no argument |
| `design_block` (`_predicates.py` L610) | **not enumerated at all** — excludes only `design/`, so a file here satisfies the level-2 gate | missing |

Level 4 is by the record's own definition the level where *the boundary is
already settled*. A level-4 note therefore answers no boundary question, and
reporting `Boundary: answered` off it is precisely what
`test_scan_files.py::test_a_scan_file_alone_does_not_answer_the_boundary_question`
exists to prevent — its docstring calls naming a missing answer "answered" the
kind of claim #70 is about. `design_block` is narrower in practice (it only
reads before `spec.md` exists, and implementation notes are normally written
after), but it is a reader of the whole root that the record does not mention.

The precedent is uncomfortably exact. `test_scan_files.py`'s module docstring:
*"Three panel reviewers independently found that two callers read the arch root
recursively and had begun counting scan files as architecture records — the
record's own `Consequences` had enumerated the readers and missed these two."*

**Fix:** either argue in the record why `boundary` counting a level-4 note is
right (it is not obviously wrong — the argument just is not there), or exclude
`implementation/` from the `_observe` call and `design_block` the way `scans/`
is excluded, and name it beside `SCANS_DIR` in `_paths.py` as the fourth reader's
one place to find out.

### WARNING 5 — a new shipped convention with no check

`a-rule-is-expressed-as-a-check` (accepted): *"is a violation of it visible in an
artifact the work already produces? … yes ──► the rule is expressed as a check

`…is_not_a_record_this_branch_decided`, `…alone_does_not_answer_the_boundary_question`).
This change ships none.

**Fix:** at minimum, the boundary-question check and an `arch context` exclusion
check over `implementation/`, mirroring the three named above. If the answer to
finding 4 is "counting it is correct", then that is the assertion to write down.

### WARNING 6 — the accepted record was amended in the commit that created it, and the amendment breaks two quotations

`architecture-decisions`: *"Once a record is `accepted`, exactly two things ever
change: status … and Log: one line appended. **The body is never edited.**"* The
justification given for tolerating amendments at all is *"Git holds the edit
history."*

Here both the body edit and the `amended` Log line landed inside commit `5cf29d9`,
the commit that created the file. Git holds no pre-amendment text — the
unamended third consequence exists nowhere in history, and the Log line claims an
edit whose subject cannot be recovered.

That is not cosmetic, because the sibling record quotes the deleted sentence
twice, verbatim:

- `level-4-reasoning-gets-its-own-shelf.md:23` — *"It gets no hand-off targets of
  its own. It informs a choice; it records none."*
- `level-4-reasoning-gets-its-own-shelf.md:92` — the same sentence again.

`grep -rn "it records none" docs/architecture/` matches **only those two lines**.
The accepted record now reads *"It informs a choice, and routes to neither
`architecture-decisions` nor `software-design-decisions`."* A reader who follows
the quotation to its source finds text that does not exist.

The narrowing is already stated in the proposed record's own Consequences, which
is where the format puts it.

**Fix:** restore the accepted record's third consequence to the text the sibling
quotes and drop the `amended` Log line — the sibling record carries the
narrowing on its own. (Precedent for `amended` lines exists in
`vendor-upstream-skills`, but there they add rows to a table of facts; here the
edit rewrites a Consequence claim and orphans two quotations.)

### WARNING 7 — shipped behaviour rests on a record that is not in force

`SKILL.md` tells agents, today, to write departures to
`<arch-root>/implementation/<issue>-<slug>.md`, and says
*"`level-4-reasoning-gets-its-own-shelf` is the record behind the destination"*
without noting that its status is `proposed`. Per `architecture-decisions`'
status table, `proposed` is **not in force**, and the skill's own Authority
section says *"accepted architecture records outrank these constraints"* —
so it cites a non-binding record as if binding. This ships into every consumer
repo, where the directory convention was never even proposed.

**Fix:** get the record accepted before the skill instructs anyone to act on it,
or have the skill route departures to the commit message only until it is.

### WARNING 8 — the skill's commands are not grantable at the moment it fires

The Authority section says *"Read the in-force set with `wfctl arch context`"*
and the departure section says *"`wfctl arch-root` prints the parent"*. Level 4
is `/speckit.implement`, whose wrapper grants
`Read Glob Bash(.specify/scripts/bash/check-prerequisites.sh*) Bash(git
rev-parse*) Bash(wfctl feature-paths*)` — neither `wfctl arch context` nor
`wfctl arch-root`. This is the failure mode `cli.py` already documents against
`architecture-design`: *"`speckit.implement`'s ceiling grants none of the
commands its Authority section needs."*

**Fix:** widen `speckit.implement`'s `allowed-tools` to cover
`Bash(wfctl arch context*)` and `Bash(wfctl arch-root*)`, or drop the
instructions the ceiling cannot honour.

### NIT 9 — stem collision under the new shelf

`records_on_this_branch` returns bare stems (`Path(p).stem`), and
`fact_architecture_accepted` intersects them with top-level record slugs. The
`scans/` exclusion comment names this hazard explicitly: *"it matches on bare
stems, so a scan file sharing a stem with a top-level record would read as that
record being touched."* `implementation/<issue>-<slug>.md` shares the naming
scheme with `design/<issue>-<decision>.md`, so the two collapse into one slug in
that listing. Low likelihood, and unmentioned in the record.

### NIT 10 — one 197-character line

`level-4-reasoning-gets-its-own-shelf.md:111` is 119. The remaining long lines
