## WARNING — the fix holds in this repo and degrades to the pre-fix behaviour in most others

`wfctl/agents/skills/opening-a-change/SKILL.md`:L44-49

> **Its reconciled disposition table is content for the body, not a side effect.**
> It goes in the description under the section the template gives it.

That sentence presupposes a template with a `## Review Panel` section. The two halves
of this fix reach installs by different channels, and only one of them updates:

| half | channel | reaches an existing install? |
|---|---|---|
| Step 1, "run the panel, put the table in the body" | `install-skills` — a **managed mirror**, re-run every `/start-session` | yes, on the next refresh |
| the `## Review Panel` section | `install-config github` — **seed-once** | **no** |

`install_config_cmd` (`wfctl/cli.py`:L2752-2757) states it outright: *"Unlike
install-skills (a managed mirror), this is seed-once: the copied files become the
repo's own, committed and owned — no manifest/backup/uninstall. Refuses to overwrite
an existing file unless --force."* And `doctor` reports drift for the skills mirror,
not for seeded configs. So a repo that ran `install-config github` last month keeps a
template with no Review Panel section, forever, while its `opening-a-change` picks up
a step that tells it to file the table under a section that does not exist. A repo
with its own hand-written template is in the same position and always will be.

The skill gives that case no resolution, and forbids both escapes:

- Step 4 (L112-113): *"Every section the template has, in its order. A section you have
  nothing for gets 'None' or 'N/A' — never silent deletion."* A foreign template has no
  such section, so following Step 4 literally drops the table.
- The Red flags (L269): *"Editing the template because a section did not fit. The
  template is the project's file; a change to it is its own change."* So the agent may
  not add the section either.
- Step 3 (L98-105), the no-template case, lists four sections — *Summary · What changed ·
  How it was tested · Issue links* — and the panel is not among them.

An agent that hits this either drops the table or invents a section against an explicit
red flag. Dropping it lands exactly where the commit message says the change must not:
*"a step that can be skipped without leaving a trace is the same silence in a new place."*
The trace only exists where wfctl's own template is installed.

**Why this is not a BLOCKER:** wfctl's own PRs get the section (this diff hand-edits the
repo copy, and `test_shipped_github_config_matches_this_repos_own_copy` keeps the two
honest), so the behaviour is correct here. It is the consumer path — which is what
`install-skills` exists for, and what #147 is driving toward — that degrades silently.

**Concrete fix.** Give the skill a fallback it owns, in Step 1:

> Where the template has a section for the panel, the table goes there. Where it has
> none — most repositories, since `install-config github` is seed-once and does not
> update an already-seeded template — append it under a `## Review Panel` heading of
> your own at the end of the body. This is the one section this skill supplies rather
> than reads, because it is the one whose content this skill produced.

and add it as a fifth item to Step 3's default shape. This does not contradict *"This
skill does not carry a section list of its own, and must never grow one"* (L91-95) —
that rule is about not keeping a second copy of *the project's* sections; this is a
section the skill authors.

(`wfctl/cli.py`:L2895) reads the file, prints findings, and exits 1. Its docstring even

**Concrete fix**, either one:
- add the check — `_shape.body_findings` (or a sibling that `check_body_cmd` also calls)

  shipped blank row; or
- if the rule is judged to sort onto the prose side, say so in the commit message or the
  skill with the reason, and file it under #221. Right now the sort was not performed,
  which is the failure mode the record was written the day before to prevent.

## WARNING — applying findings invalidates the verification record, and the step names only the push

`wfctl/agents/skills/opening-a-change/SKILL.md`:L53

> Findings you apply change the branch. Push again before Step 5 — a PR is opened from
> what is on the remote, not from what is in your tree.

Correct as far as it goes, and it is a good catch. It stops one step short. Under
`wfctl-runs-the-verification`, the record binds a verdict to the tree it ran against —
`wfctl/_verify.py`:L185: *"Identity is `(sha, dirty)`"*, and L182: *"a verdict against a
moving tree describes"* nothing usable. `finishing-a-development-branch` Step 1 ran the
suite before the push; a finding applied at Step 1 of this skill advances the sha after
it. The recorded verdict now attests to a tree that is not the one the PR opens.

The skill already makes this exact argument one screen up, in its own words (L33-34):

> Its Step 1 still applies in full. A description written against a failing suite
> describes something that does not work yet.

That reasoning does not weaken when the edits come from the panel instead of from
implementation. And #187's own text says this change adds a fourth item to #147's
acceptance test alongside *the verification record* — so the body will carry a verify
record and a panel table that can now disagree about which tree they describe, with
nothing saying so.

**Concrete fix** — one clause:

> Findings you apply change the branch. Re-run `finishing-a-development-branch` Step 1
> and push again before Step 5 — a PR is opened from what is on the remote, and
> `wfctl verify`'s record is bound to the sha it ran against, which your fix has moved.

## WARNING — the template placeholder renders as an answer, not as an unanswered section

`wfctl/agents/configs/github/.github/pull_request_template.md`:L152-156 (and the
byte-identical `.github/pull_request_template.md`)

```
| # | Reviewer | Finding | Disposition |
|---|---|---|---|
|   |          |         |             |

roster:
```

Two problems, both against the section's own stated purpose (L148-149: *"An empty
section here and a panel that never ran read identically, and the second is what this
section exists to make visible."*).

**It renders as filled.** The comment block is invisible on github.com. What a reviewer
sees for a skipped panel is a well-formed table with one blank row and the word
`roster:` — which reads as *answered, and the answer was nothing*, not as *nobody
touched this*. Compare the sibling sections, which leave a visible unanswered shape:
`- Closes #(issue number)` and `### Changes Made` / `-` / `-` / `-`.

**It breaks the convention Step 4 keys on.** Every other visible placeholder in this
file is bracketed — `[What the thing is, for a reader who has never seen it…]`,
`[The capability added or changed…]`, `[The gap it closes…]`, `[Who benefits…]` — and
Step 4 of `opening-a-change` (L114-115) says *"Placeholders in brackets are replaced,
not left."* The blank row and the bare `roster:` are in no brackets, so the one rule
that would have forced them to be filled does not reach them. An agent obeying Step 4 to
the letter can leave this section exactly as shipped and be compliant.

**Concrete fix** — bracket it, and pre-fill one row so the shape is legible:

```
| # | Reviewer | Finding | Disposition |
|---|---|---|---|
| 1 | [r1] | [what it raised] | [applied / accepted / rejected — with the reason] |

roster: [r1 ✓  r2 ✓  r3 ✓ — and which, if any, were re-asked]
```

Optional and cheap, in the same spirit as the rest of the file: a `## Checklist` line,
`- [ ] A review panel ran over this diff and its disposition table is above`. The
checklist is this template's existing tick-shaped observability device, and an unticked
box is, in the template's own words at L134-136, *"information a reviewer can act on."*

## WARNING — the numbering test does not guard the failure its docstring names

`tests/test_opening_a_change_panel.py`:L52-57

```python
def test_the_steps_are_numbered_in_order_from_one() -> None:
    """Two steps of this skill are referred to by number from inside it, and the
    panel step was inserted ahead of five that already existed. A renumbering
    that misses one leaves the file pointing a reader at the wrong step, which
    reads as correct until it is followed."""
    assert [n for n, _ in _steps()] == list(range(1, len(_steps()) + 1))
```

`_HEADING` is `^## Step (\d+): (.*)$`, so `_steps()` sees **headings only**. The
docstring names the *reference* failure — "pointing a reader at the wrong step" — and
the assertion covers the *heading* failure. Mutation check, by inspection: revert
L129 to `attribute Step 5 cannot set` and L156 to `The sidebar is Step 5`, leave the
headings alone, and the file now sends a reader to "Open it" for the sidebar rules —
and this test still passes, as does the whole suite. The one thing it claims to catch
is the one thing it does not.

Under this repo's testing conventions (`CLAUDE.md`: *"docstrings say why the test exists,
usually naming the failure it caught"*) this is worse than a docstring that merely
restates its assertion: it tells the next reader that a hazard is covered when it is not.

It is not hypothetical. The diff missed exactly this class of reference one file over —
see the NIT below.

The complication is real: L31 (*"its Step 4 menu"*) and L33 (*"Its Step 1"*) refer to
`finishing-a-development-branch`, so a blanket "every `Step N` resolves to a heading here"
would false-positive. Scope it semantically instead:

```python
def test_the_in_file_step_references_point_at_the_step_they_name() -> None:
    text = _SKILL.read_text()
    by_title = {title.lower(): n for n, title in _steps()}
    assert f"Step {by_title['fill the sidebar']} cannot set" in text
    assert f"The sidebar is Step {by_title['fill the sidebar']}" in text
    assert f"Push again before Step {by_title['open it']}" in text
```

Three references, all three checked, and each fails loudly on a missed renumber.
