BLOCKER  wfctl/agents/skills/opening-a-change/SKILL.md:L47 — the rule this change ships ("the panel's reconciled disposition table goes in the body") is delivered as prose with nothing observing it, which `a-rule-is-expressed-as-a-check` (accepted, printed by `arch context`) names as the rule's absence rather than a partial implementation → express it as a check over the body.

The record's test is one question: *is a violation visible in an artifact the
work already produces?* The artifact here is the PR body, which the record names
explicitly in its "already produces" list. A body with no `## Review Panel`
content is exactly the observable violation.

The change's own commit message argues this: *"a step that can be skipped without
leaving a trace is the same silence in a new place."* Its answer is a template
section — but a section is prose too. An unattended agent that never ran Step 1
produces a body with the section absent or blank, and nothing in the repo looks
at the body afterwards. The failure #187 describes is reproduced two files over,
in the artifact the record was written about.

Two mechanisms already exist and neither is invented for this:

- `wfctl check-body <path>` (`cli.py:2895`, `_shape.body_findings`) already reads
  the body file, already runs at Step 5 of this same skill, and its module
  docstring already makes this exact argument: *"a correct rule with nothing to
  check it gets crossed a fifth time the way it was crossed the first four."*
  A second finding — no `## Review Panel` heading, or a heading with no table row
  and an empty `roster:` — is a dozen lines beside `body_findings`.
- `wfctl hook worktree-guard` (`cli.py:3179`) is already a `PreToolUse/Bash` hook,
  so intercepting `gh pr create --body-file <path>` is a mechanism the repo ships.

The record explicitly does not decide *which* mechanism carries a check, so either
discharges it. What it does decide is that shipping this one as prose alone is the
gap. This is also the first rule shipped after that record was accepted (657c0f6,
two commits back), so the precedent set here is the one it was written to stop.

WARNING  wfctl/agents/skills/opening-a-change/SKILL.md:L114 — Step 4's "None"/"N/A" bullet is a standing authorization to fill the Review Panel section without running a panel → exempt this section by name, or state that a missing panel is written as "panel not run: <reason>".

Step 4 says: *"A section you have nothing for gets 'None' or 'N/A' — never silent

any presence check written naively, and reads to a human as a considered

This is the single cheapest way the change's whole mechanism gets defeated, and
it is defeated by another rule in the same file.

WARNING  wfctl/agents/skills/opening-a-change/SKILL.md:L53 — applying findings moves the tree after the verification gate, and only the push half is addressed → say to re-verify, not just re-push.

The `## Order` section (L20-35) has the reader arrive here after
`finishing-a-development-branch` Step 1 verified the suite and Option 2 pushed.
Step 1 then applies findings, and says *"Push again before Step 5."*

`wfctl-runs-the-verification` records the verdict bound to a commit sha and a
dirty flag — *"a tree that moved after the run reads stale rather than passing."*
So after findings are applied, the recorded verdict is stale by construction, and
the template's `How Has This Been Tested?` section (L124) gets filled from a run
that predates the fixes. `fanning-out-code-review` already treats that record as
load-bearing — it forbids reviewers from running `wfctl verify` because doing so
*"replaces the parent's proof of done with one taken mid-review"* — but nothing
tells the parent to refresh it once the review is over.

Fix is one clause: "Findings you apply change the branch. Re-run the verification
and push again before Step 5 — a PR is opened from what is on the remote, and the
recorded verdict binds to the tree it ran against."

WARNING  tests/test_opening_a_change_panel.py:L49 — the docstring names a failure the assertion cannot catch → assert the in-prose references, or rewrite the docstring to claim only what is checked.

The docstring: *"Two steps of this skill are referred to by number from inside it

"The sidebar is Step 6" (L156) — are not read by any test. A future insert that

Step 6 = "Fill the sidebar"), so this is an uncovered rule, not a live defect.

and assert the titles are the intended ones — e.g. the number in "Push again
before Step N" is the step titled "Open it". Per `CLAUDE.md` a test's docstring
should name the failure it caught; here it names a failure it does not cover.

WARNING  wfctl/agents/skills/opening-a-change/SKILL.md:L38 — the panel is now unconditional for every change with no word on cost or scope → state the bound deliberately.

`fanning-out-code-review` defaults to three reviewers over the whole diff, and
this step attaches that to every PR this skill opens, including a copy edit.
`CLAUDE.md` records the opposite instinct elsewhere — *"Not every change needs the

change "counts", silently — and a decision made silently per run is the failure
class this change exists to remove.
