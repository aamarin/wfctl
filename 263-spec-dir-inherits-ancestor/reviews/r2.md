## What each pass checked

**1. Correctness.** Verified the fix against the issue's own reproduction, built from
scratch in a scratch dir: `resolve_spec_dir('200-child', repo)` → `None` (was
`specs/100-parent`), and `resolve_spec_dir('100-parent', repo)` still returns its own
dir, so the removal did not overshoot into the exact-name leg. Read the diff for logic
changes to the two surviving legs — there are none; the `_paths.py` changes are the
deletion of `_ancestor_branches`, the deletion of the `for ancestor in …` loop, and
docstring/comment text. The change is therefore strictly answer-removing: it can turn a
`Path` into `None`, never one `Path` into another.

Quantified the blast radius rather than trusting the commit message's "0 of 18": loaded
`origin/main`'s `_paths.py` side by side with `HEAD`'s and ran both `resolve_spec_dir`
over every local branch of the main checkout — **18 branches, 0 differing**. The
commit's measurement holds. The branch the issue named (`249-key-pattern-typeerror`) is
gone, which is why the count is 0 and not 1.

Checked the rendered views the commit claims are unchanged. On the repro branch,
`wfctl status` prints `(no spec dir found)` with `brainstorm ← current` and
`next: /speckit.brainstorm` — loud and correct. `wfctl feature-paths` returns
`FEATURE_DIR=…/specs/200-child` via the `spec_root(repo_root) / branch` fallback at
`cli.py:724`, so the write-path hazard the issue described (a review panel writing over
another session's reports) is closed, not merely reported differently.

Traced every caller of `resolve_spec_dir` (`cli.py` L140/164/267/308/385/606/608/718,
`_archive.py`) — all already handle `None`. Checked that
`wfctl/specify/scripts/bash/common.sh` holds no second copy of the resolution; it
delegates to `wfctl feature-paths`, as its header says.

Checked the SKILL.md claim "A resolved dir whose key is not this branch's is now one
thing only: an epic whose grouping map names this issue" against the code: the
exact-name and key-glob legs both return a dir whose leading key equals the branch's by
construction, so only the claim leg can produce a differing key. Accurate.

**2. Security.** No new input handling, no new subprocess construction (the diff only
deletes subprocess calls), no secrets, no path built from untrusted text. The one
security-adjacent property is the write path, and it improves: `feature-paths` no longer
hands a foreign feature's directory to whatever runs next.

**3. Architecture.** The architecture record is the right instrument for a change that
retires a convention, and it matches the `architecture-decisions` format: `Context`,
`Direct baseline`, `Decision`, `Owns truth`, `Considered`, `Consequences`, `Log` all
present, and `Owns truth` carries both required halves (who owns it, and why git cannot
compute it) rather than the role assignment the skill warns about. `status: proposed` is
correct per the skill's own table ("Write `proposed` while a human still has to agree")
and is the majority state in `docs/architecture/` (7 of 16); `wfctl arch context`
consequently does not list it, which is the intended behavior of the status field, not
an omission. Both records it cites by slug — `session-state-is-re-derived`,
`a-rule-is-expressed-as-a-check` — exist.

Applied Chesterton's Fence to the deleted leg: read `_ancestor_branches` and its
`carries_own_work` rationale in full, and #120's narrowing, before accepting the
removal. The record's "Direct baseline" is the argument that matters and it holds — every
candidate narrowing is computed from ancestry plus the ancestor's directory name, and
neither differs between the convention's tree and the bug's tree. I could not construct
a third fact git records that separates them.

Checked the retired convention has no live instruction anywhere in what wfctl ships:
`AGENTS.md` says `workmux add <issue>-<slug> --base main`; no skill under
`wfctl/agents/skills/` instructs `--base <epic-branch>`; `speckit-delivery-plan`'s

record's "no live user in this repo" stands.

**4. Readability.** Where the four WARNING/NIT text findings above come from. The
`_paths.py` and SKILL.md docstrings the diff *did* rewrite are good — they state the
rule and name the record, and `resolve_spec_dir`'s docstring now matches its code

**5. Performance.** Strictly faster. `_ancestor_branches` ran one `for-each-ref` plus,
per candidate branch, a `merge-base --is-ancestor`, a `rev-list --count` against the
branch and a `rev-list --count` against the trunk — O(branches) subprocesses on every
miss, on a path `feature-paths` sits on for every speckit script invocation. That is the
~270ms `cli.py:601` cites, and it is gone. No new work added.

**6. Over-engineering.** The diff's own net is −31 lines, which is the right direction.
