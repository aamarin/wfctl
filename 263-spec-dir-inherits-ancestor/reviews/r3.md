### WARNING — `tests/test_paths.py` L325, L383, L395, L404: four test docstrings still argue from the deleted mechanism

The commit rewrote the production rationale in two places and left its mirror in
the tests untouched. `wfctl/_paths.py:L22-25` — the `_GROUPING_HEADING` comment —
was correctly updated from "a feature that claims nothing is one the ancestor walk
still inherits" to "every sub-issue the map names loses its only route to the epic".
The test that pins that exact behavior was not:

- `test_delivery_issue_keys_reads_a_heading_that_carries_a_suffix` (L404):
  *"A map claiming nothing is one the ancestor walk still inherits, so a heading
  the exact-line match missed … would have let #120 back in through a typo."*
  There is no ancestor walk. The real reason it still matters is the one now in
  the source comment.
- `test_delivery_issue_keys_separates_no_map_from_an_unreadable_one` (L325):
  *"The distinction the ancestor guard turns on … only the second is safe to
  inherit."* This one directly contradicts the `delivery_issue_keys` docstring
  the same commit wrote — *"No caller separates the two today."*
- `..._fails_closed_on_a_delivery_md_it_cannot_decode` (L383): *"returns None —
  the *inheritable* answer — so an ancestor whose delivery.md is not UTF-8 gets
  handed back."*
- `..._returns_none_when_there_is_no_delivery_md` (L395): *"has not been
  decomposed and is still inheritable, so this one case must stay None."*

Why this is a WARNING and not a NIT: `CLAUDE.md` says docstrings say *why the test
exists*, and these four now assert a why that is provably false — the next reader
who checks the claim finds no ancestor guard and has no way to tell whether the
test is stale or the code is. It is also the specific failure mode `CLAUDE.md`
warns about ("a claim from prior context is not evidence"), reproduced inside the
suite. Fix: give each the reason that survives — for L325/L383/L395, the one the
new `delivery_issue_keys` docstring already states (a later caller acting on a
claim's absence needs to know which absence it has); for L404, the sentence the
source comment now carries.

### WARNING — `wfctl/cli.py:L602-606`: stale cost model on the double-lookup guard

```python
# Only fall back to `branch` when it differs — a miss walks every
# ancestor branch, which is ~270ms of git, and repeating it is free of
# any new answer.
spec_dir = resolve_spec_dir(story, repo_root)
if spec_dir is None and story != branch:
    spec_dir = resolve_spec_dir(branch, repo_root)
```

The guard is still correct; its stated reason is not. I measured a resolution
miss against this repo, old code vs new, same repo root:

```
origin/main   345.7 ms
this branch     7.8 ms
```

The comment tells the next reader that a redundant call costs ~270ms, which is now
off by a factor of ~44. Per `CLAUDE.md` ("existing comments are dense with
rationale — match that"), a comment whose whole content is a rationale that no
longer holds is worse than none. Fix: either restate it ("the second lookup is
cheap since #263 — kept because an explicit handle is the better answer, not
because the fallback is expensive") or delete the cost clause. In scope: this
commit is what invalidated it.

### WARNING — `speckit-orchestrate/SKILL.md:L58-61`: `null` gained a new cause with no remedy given

The skill now tells the agent: *"`null` there is the resolver saying no feature
claims this branch. Do not go looking for one."* Before this commit, a child
worktree cut from an un-decomposed epic resolved to the epic. It now resolves to
`null`, `wfctl status` falls to `brainstorm`, and the agent — following this
skill correctly — starts a second pipeline for a feature that already has one.

The arch record's *Consequences* names the remedy ("the epic claims its children
by decomposing"), but the record is not what the agent reads at that moment. The
record measured no live user for the convention *in this repo*; `install-skills`
ships this skill into other repos, where that measurement does not apply. Fix:
one sentence after "Do not go looking for one" — *if this branch is a sub-issue
of an epic, the epic claims it by running `/speckit.decompose`, which writes the
grouping map; until then the branch genuinely has no feature.*

Softest of the three — reasonable to defer with a follow-up issue.

### NIT — `tests/test_paths.py:L195-208`: four params, one code path

All four `ancestor_delivery` values reach the same three lines of
`resolve_spec_dir` and none of them is read: with the ancestor leg gone, nothing
opens the ancestor's `delivery.md` at all. The docstring argues the cases are
kept because "what fails if ancestry comes back is a class, and a class needs its
cases", which is a real argument and I am not asking for it to be reversed — but
note it is now a *hypothetical-regression* net, not a coverage net, and mutation
testing will show all four params killing the same mutants. Author's call.

### NIT — `tests/test_paths.py:L164-192` vs `L231-247`: `_stacked_repo` re-implemented inline

The `decomposed-claiming-other-issues` param rebuilds, line for line, the tree
`_stacked_repo` already builds (same branch name, same `tasks.md`, same
`_delivery_map("**#575** …", "**#576** …")`), differing only in the intermediate
`576-transaction-entry-form` checkout. Extracting the parametrized test's setup
and having `_stacked_repo` call it would save ~14 lines and keep one definition
of "#120's shape".

Related and inert: `_stacked_repo`'s intermediate `git checkout -b
576-transaction-entry-form` existed to exercise nearest-first ancestor ranking,
which no longer exists. Its docstring ("Its planning branch is an ancestor of
`567-…` because worktrees branch off the branch below them in the stack") now
describes a fact nothing reads.

### NIT — `speckit-orchestrate/SKILL.md:L81`: "it inherited one"

The paragraph above it was rewritten to say a resolved foreign-key dir is "a
claim somebody wrote". Four lines later: *"Different keys mean it inherited
one."* The record is titled *a branch is claimed, never inherited*; using
"inherited" for the surviving claim leg is the vocabulary the change is trying to
retire. → "Different keys mean an epic claims it, and then:".

### NIT — `wfctl/_paths.py:L344-352`: a distinction with no caller

`delivery_issue_keys` returning `None` vs `set()` is now unobservable — the sole
caller writes `delivery_issue_keys(d.parent, pattern) or set()`, collapsing them.
The docstring is honest about this and gives a forward-looking reason to keep it.
Flagging only because the over-engineering pass requires naming it: this is
speculative flexibility with zero current consumers. It costs nothing already
written, so keeping it is defensible; I would not delete it.

## What each pass checked, and what it found

**1. Correctness** — traced all three surviving legs of `resolve_spec_dir` (exact
dir → key glob → single `delivery.md` claimant) against every test in the diff.
Confirmed the removal cannot change the answer for a branch that resolves by name
or key, and that the multi-claimant `return None` guard is untouched. Verified the
new SKILL.md claim *"a resolved dir whose key is not this branch's is now one thing
only: an epic whose grouping map names this issue"* is exactly true: legs 1 and 2
both return a directory whose leading key equals the branch's by construction, so
a key mismatch can only come from leg 3. Checked the `key == "unknown"` path (no
claimant scan, name match only) — unchanged and correctly re-documented.
Confirmed `_trunk_branch` survives with a live caller (`_paths.py:L324`, the
in-tree-records check) and is not orphaned by the removal; `_ancestor_branches` has
no remaining references anywhere in `wfctl/`, `tests/`, or `docs/`. No bug found.

**2. Security** — the removal deletes four `subprocess.run` call sites and adds
none. All were argv-form (no shell), so neither the old nor the new code was
injectable via a branch name. No secrets, no new input surface, no auth. Nothing
to report.

**3. Architecture** — the record conforms to `architecture-decisions`: slug names
the decision not the issue, no sequence number, `Owns truth` carries both halves
with the owned thing phrased as a question in quotes ("which feature claims this
branch?" / "Git cannot compute it: a base records where a worktree was cut from,
which is provenance"), `Direct baseline` is concrete enough to compare against,
`Considered` carries three alternatives each losing on fit rather than on an
invented weakness, `Log` line is dated and matches `status: proposed`. `proposed`
is correct for a fresh record and matches 7 of the 18 records in
`docs/architecture/`. Note it is therefore *not* in the `arch context` projection
(accepted only) while three shipped files already cite it as settled — normal for
this repo, but worth an eventual accept. Confirmed no shipped skill instructs
cutting a child worktree from an epic's planning branch, so the retired convention
has no shipped guidance left dangling (only the gap in WARNING-3).

**4. Readability** — the rewritten `resolve_spec_dir` docstring is shorter than
what it replaces and drops the "one shape stays open rather than guessed at"
paragraph, which was the honest description of a bug and is correctly gone.
Naming of the renamed tests reads as sentences per `CLAUDE.md`. The three stale-
rationale findings above are all in this pass.

**5. Performance** — strictly better, measured: a resolution miss on this repo
goes 345.7ms → 7.8ms, because `resolve_spec_dir` now issues no git subprocesses of
its own on the miss path (it previously ran one `for-each-ref`, plus a
`rev-list --count` against trunk and a `merge-base --is-ancestor` per local
branch — O(branches) processes). This is a real win on `wfctl status`, `resume`,
`feature-paths` and the archive hook, and nothing in the diff claims it.

**6. Over-engineering** — the diff gets shorter (−265/+234, and −139 net in
`_paths.py`), which is the right direction. The two test NITs and the
`None`-vs-`set()` NIT are the only candidates; all three are documented choices,
so `net: −25 lines possible` is offered, not urged.
