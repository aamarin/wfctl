### WARNING — `wfctl/_paths.py:L377-386`: the except-block comment argues from the removed leg

The comment inside `delivery_issue_keys`' second `except` still reads:

> `# ... None is the inheritable answer — which hands a foreign feature back`
> `# exactly the way #120 did, on any repo with one unreadable file under the`
> `# spec root.`

There is no inheritable answer any more. Both `None` and `set()` collapse at the
one live call site (`resolve_spec_dir` L462-470: `key in (delivery_issue_keys(...)
or set())`), which the change's own docstring edit at L346-352 states plainly.
This matters more than a normal stale comment because it is the *only* argument
in the file for why the two `except` clauses are split, and it is now a false
one — the next reader either merges the clauses (losing the `UnicodeDecodeError`
containment that keeps `status`/`resume`/`feature-paths` from raising over one
unreadable file) or re-derives the ancestor leg to make the comment true again.

Note the author did rewrite exactly this reasoning 20 lines up and again at
`_GROUPING_HEADING` (L18-21), so this is a missed spot, not a considered keep.

**Fix.** Rewrite the comment to the surviving reason: the file is present and
unreadable, so it is an unanswered question rather than an absent one, and
raising would take three commands down over a file nobody asked about. Drop the
`#120`/inheritance sentence.

### WARNING — `wfctl/_paths.py:L364-367`: the "generous cell prefix" rationale is inverted

> `Generous here is safe in a way it is not inside the row — an unread row is a`
> `silent claim dropped, and a dropped claim is what makes a foreign feature look`
> `inheritable.`

Post-change, a dropped claim does not make a foreign feature look inheritable —
it makes the *real* epic fail to claim its sub-issue, so the branch resolves to
nothing. That is precisely the failure the change wrote into the
`_GROUPING_HEADING` comment ("every sub-issue the map names loses its only route
to the epic"). Two comments in one file, same premise, one updated and one not.

**Fix.** End the sentence with the L18-21 wording: a dropped claim is a
decomposed feature reading as unresolved.

### WARNING — `tests/test_paths.py:L224-226`: the merge justification is factually wrong

> `They are one test because resolution no longer reads any of it: the four`
> `cases reached four branches of the ancestor guard, and there is no guard`

Resolution still reads three of the four. `resolve_spec_dir`'s claimant leg does
`root.glob("*/delivery.md")` and calls `delivery_issue_keys` on every hit, so:

- `never-decomposed` — no file, genuinely unread. ✔ the sentence holds
- `decomposed-claiming-other-issues` — read; exercises "map present, key absent"
- `map-the-parser-cannot-read` — read; exercises the second parse tier returning `set()`

claimant scan has to survive reading, not in which ancestor branch they take.
