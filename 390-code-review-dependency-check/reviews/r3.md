### Findings

WARNING  SKILL.md:L89 — "License compatible with the project's" can produce a
finding that Step 5's severity table has no row for. BLOCKER is "incorrect
behavior, security hole, or data-loss risk"; WARNING is "degrades quality,
maintainability, or robustness". A GPL dependency in a product that cannot ship
GPL is neither — it is a ship-stopper, and a reviewer reading the table honestly
has to file it as a WARNING, which the Honesty section names as its own failure
("a downgraded BLOCKER is a shipped bug"). The other four questions house
cleanly: a known CVE is a security hole, size and abandonment degrade
maintainability. → widen the BLOCKER row to "Incorrect behavior, security hole,
data-loss risk, or a licence the project cannot ship", or settle it in the bullet
itself: "License compatible with the project's — an incompatible one is a
BLOCKER."

WARNING  SKILL.md:L88 — `pip-audit` is not only a query. Given a requirements
file or a project path, it resolves the tree by building a temporary virtualenv
and installing into it, which runs the build backend of the very diff under
review. The skill's own pass 2 says to treat everything arriving from outside as
untrusted, and a review of an untrusted PR is exactly when this bullet fires. The
fix is a clause, not a redesign: point at the artifact rather than the run —
"Known vulnerabilities — the advisory database for the pinned versions; note that
an audit tool may install the tree to answer." `npm audit` does not have this
shape, so scoping the caution to the Python tool is accurate. Filed as WARNING
rather than NIT because what it degrades is the robustness of the review itself,
not its wording; low probability, one-clause fix, author's call on severity.

NIT  SKILL.md:L83–89 — this is the only nested list in the file, and in the
sibling review skills (`fanning-out-code-review`, `receiving-code-review`) there
are none. Step 4's other bullets are flat one-liners, so Architecture now reads
as three bullets plus an indented block — a sub-pass in everything but the
numbering, which is the shape #390 asked to avoid without using that word. I do
not think flattening is clearly better: five checks in one comma-separated line
is easier to skim past than five lines, and the questions are the content. Raised
so the nesting is a decision rather than a default. → if flattened: "A new
dependency is outward coupling — it earns its place by what the stack can't
already do, its size and transitive tree, live maintenance, a clean advisory
record, and a licence that fits."

NIT  SKILL.md:L83–84 — the framing sentence is the only wrapped bullet in Step 4,
and its continuation (`  earn its place:`) sits at exactly the indent of the
sub-bullets beneath it, so in the raw file it reads as the first of them.
Markdown renders it correctly; an agent reading the source is the audience here.
Dropping two words fits it on one line at 86 characters, which this file already
exceeds elsewhere unwrapped (L96 is 96). → `- A new third-party dependency is
coupling pointed outward — it has to earn its place:`

NIT  SKILL.md:L85 — "Does the existing stack already do this?" overlaps pass 6's
`native:` tag, "dep/code doing what the platform already does". A reviewer who
runs both passes can file the same dependency twice under two tags, in a file
whose opening promises "one review instead of four overlapping ones". The
distinction that saves it is that "existing stack" is broader than "the
platform" — it includes dependencies the project already carries and its own
modules — and that is a defensible reading, just not a stated one. → no change
needed if the breadth is deliberate; if you want it airtight, "Does the existing
stack — platform, stdlib, a dep already carried — already do this?"
