## Findings

**BLOCKER** `wfctl/_pipeline.py:L30` — the flip's own mitigation is false, and the
exposure is live today, not after #100.

The commit body says: *"This extends the unattended run by zero steps. `clarify` and
`analyze` both sit earlier in the table and both still stop (#100), so no run reaches
decompose."* That reads the halt as covering the steps *after* it. It does not.
`speckit-orchestrate` runs **after a speckit step completes** (SKILL.md frontmatter,
and steps 3–5), and `auto: false` on `analyze` stops the run *at* analyze — i.e. it
declines to auto-run `/speckit.analyze`. The moment a human runs analyze, the next
orchestrate invocation re-reads `wfctl status --json`, finds `current = decompose`,
and now reads `auto: true` → `EXECUTE_COMMAND: speckit.decompose`.

The commit's own new test is the proof. `test_a_feature_with_no_delivery_plan_yet_advances_unattended`
stages `checklists/analysis-report.md` (analyze complete) with no `delivery.md`, and
asserts `(current, next_command, auto) == ("decompose", "/speckit.decompose", True)`.
That is exactly the post-analyze state, and it is exactly the payload that makes
orchestrate emit `EXECUTE_COMMAND`. Confirmed independently against `build_report`
on an equivalent fixture.

So this adds one step to the unattended run today, and that step is the one the change
itself calls outward-facing:

- `wfctl/agents/commands/speckit.decompose.md` description: *"Writes delivery.md **and
  creates GitHub issues** using the grouping plan."*
- `wfctl/agents/skills/speckit-delivery-plan/SKILL.md` workflow diagram: decompose →
  `delivery.md` **+ GH issues**; Step 5: *"then write `delivery.md` and create GitHub
  issues"*; Verification Checklist: *"[ ] GitHub issues created and numbered"*.
- Same skill, Red Flags: *"File-touch matrix shows 8+ files → L/XL scope; flag for user
  discussion before proceeding"* — a stop-and-ask branch inside a step now marked
  auto-advance.

That contradicts the change's own stated invariant in two places: `next_step_content`'s
new docstring (*"only one of them may be taken without a human, because creating the
issues is outward-facing"*) and `_unkeyed_issues`'s (*"creating them is outward-facing
and waits for a human"*). It also contradicts the repo's own safety rule about
confirming before anything outward-facing.

Note the second-order consequence: if `/speckit.decompose` does create the issues in the
same run, then the guard's target state (unkeyed rows) is only ever reached after a
*partial or failed* run — the "write the plan, halt, human creates the issues" model the
guard is built on is not the flow the shipped skill describes. One of the two is wrong,
and the flip is what makes the disagreement load-bearing.

`allowed-tools: Read Glob` in the command frontmatter is not a mitigation:
`speckit.implement.md` carries the same list and plainly writes code.

Fix — pick one:
- (a) Revert `decompose` to `False` until `speckit-delivery-plan` is split so that
  writing `delivery.md` and creating the issues are two steps, and only the first is
  auto. This is the smallest change and keeps the useful half of the commit (the
  `next_step_content` guard, which is correct and should stay either way).
- (b) Keep the flip, and amend `speckit-delivery-plan` Step 5 / its Verification
  Checklist / `speckit.decompose.md`'s description so the command stops after writing
  the plan with placeholder keys, and issue creation becomes an explicitly human-gated
  action. Then the guard is what resumes the run, and the commit's model is true.
- (c) If the intent really is that issue creation may proceed unattended, then say so and
  delete the guard's premise — but that contradicts `_unkeyed_issues` and the repo's
  outward-facing rule, so it needs an argument, not silence.

Either way the commit message's "extends the unattended run by zero steps" paragraph
must be corrected; it is currently the reason a reader would not look here.

**WARNING** `wfctl/_pipeline.py:L519-521` — `_tasks_open` was extracted so the two arms
"cannot come to disagree about what a finished task list is", and the one arm that
already disagreed was left on its own spelling.

`next_step_content`'s `implement` arm still asks `tasks_text and not
_has_open_checkboxes(tasks_text)`. `_tasks_open` is `open boxes AND no
`checklists/implement-complete.md``. Those diverge whenever the sentinel exists while a
`[ ]` remains anywhere in `tasks.md` (a leftover box, or a `[ ]` in a fenced example —
`_has_open_checkboxes` scans the whole file).

Reproduced against this HEAD, with a definition of done configured in `wfctl.json` and
`tasks.md` = `- [x] T001` / `- [ ] T002` plus the sentinel:

```
implement  in_progress  1/2 done  unverified — run `wfctl verify`
build_report -> current=implement  next_command=/speckit.implement  auto=True
```

`status` prints a step blocked on verification, and the same payload hands orchestrate
`auto: true` for `/speckit.implement`. That is the identical failure class this commit
fixes for decompose — the state name is not the halt, `auto` is — and it is #69's
regression re-opened through the routing path.

Pre-existing, not introduced here. But the helper that fixes it is created by this diff,
the fix is one line, and the seam is the one the commit is refactoring:

```python
if step == "implement" and repo_root is not None and spec_dir is not None:
    tasks_md = spec_dir / "tasks.md"
    tasks_text = tasks_md.read_text() if _file_exists(tasks_md) else ""
    if tasks_text and not _tasks_open(spec_dir):        # was: not _has_open_checkboxes(tasks_text)
        if _verification_block(repo_root):
            return "wfctl verify", False
```

(`tasks_text` must stay in the condition — `_tasks_open` is also `False` for a missing
or empty `tasks.md`, where the current arm deliberately does nothing.)

Fix here, or file it — but the comment at `L279` currently asserts it is already done
(see NIT below), so leaving it silent is the option that is not available.

**NIT** `wfctl/_pipeline.py:L378` vs `L528` — the same predicate is spelled in opposite
operand order in the two arms it was unified for: `if decompose_reason and tasks_open`
in `_infer_steps`, `if _tasks_open(spec_dir) and _decompose_block(...)` in
`next_step_content`. Behaviourally identical (the guard's order is the better one — it
short-circuits before the tracker config read). Matching the order would make the "these
two ask the same question" claim visible rather than inferred.

**NIT** `wfctl/_pipeline.py:L275-279` — `tasks.md` is now read twice per `_infer_steps`:
once into `tasks_text`, once inside `_tasks_open`. Plus a third read in
`next_step_content` per `build_report`. Cost is negligible (four extra small file reads
and one extra `delivery.md` regex scan per `wfctl status`; `configured_key_pattern` is
JSON only, no subprocess or network). Flagged only because `PipelineReport`'s own
docstring makes the argument against two reads of one artifact. The shape is the price
of the helper taking `spec_dir` rather than the text, which is what lets both callers
use it — worth keeping.

## What each pass checked

**1. Correctness.** Traced `_STEPS` → `_infer_steps` → `_current_step_name` →
`next_step_content` → `build_report` → `cli.next_cmd`, and out into
`speckit-orchestrate/SKILL.md` steps 3–5 and `speckit-delivery-plan/SKILL.md`. Verified
the new guard's predicate is exactly equivalent to the `in_progress` condition in
`_infer_steps` (`_decompose_block` re-guards on `delivery.md` existing, so the two match
in every branch). Enumerated every state in which `decompose` can be `current`: `pending`
(no `delivery.md`, tasks open) → `auto: true`, and `in_progress` (unkeyed rows + tasks
open) → `auto: false`. Both are pinned by the two new tests; no reachable third. Confirmed
the `done`/`skipped` decompose states move `current` to a later step, so the guard is
never consulted for them. Confirmed the only two call sites of `next_step_content`
(`build_report` L577, `cli.py` L279) both pass `repo_root` and `spec_dir`, so no
agent-facing `auto` bypasses the guard. Confirmed `decompose_reason` still reaches the
annotation on the tasks-closed path, unchanged. Confirmed `re.compile(key_pattern)`
cannot raise (`load_key_pattern` validates and degrades), so the second call adds no new
traceback path. Two findings above came out of this pass.

**2. Security.** No new external input. `_decompose_block` reads `delivery.md` text and a
repo-local `key_pattern`; both were already read on this path by `_infer_steps`, and the
compile is validated upstream. No secrets, no shell, no network — `configured_key_pattern`
is a manifest + JSON read. The one security-shaped issue is the BLOCKER: an outward-facing
action (tracker issue creation) moved behind an auto-advance flag, which is the repo's own
"confirm before anything irreversible or outward-facing" rule.

**3. Architecture.** The `_decompose_block` / `_verification_block` symmetry is the right
call — same signature shape, same two callers, same documented reason for re-deriving
rather than threading an answer through a signature ~30 call sites pass neither half of.
Verified that claim: 30-odd `next_step_content` call sites in tests pass no repo/spec.
Extracting `_tasks_open` is correct and under-applied (WARNING). No new pattern, no cycle,
no layering violation. The commit correctly identifies that the table flag alone was the
whole answer for this step and that `state` is not read by the consumer.

**4. Readability & simplification.** Comments explain *why this shape*, matching the
file's density; the moved comments are moved intact rather than reworded. Names are
accurate (`_tasks_open` reads as a predicate, `_decompose_block` mirrors its sibling).
No nesting added, no function over 50 lines, no clever tricks. Applied Chesterton's Fence
to the `False` being flipped: read #148's reason in the commit body, confirmed
`_unkeyed_issues` now performs the check that reason named, so the fence is genuinely
retired — the flip's premise is sound; its *routing consequence* is what the BLOCKER is
about. Three NITs above.

**5. Performance.** Quantified in the last NIT: ~4 extra small file reads and one extra
regex scan of `delivery.md` per `wfctl status`, on a command that runs at session start
and after each step. Sub-millisecond, no subprocess, no network, no unbounded loop, no
N+1. Not worth changing.

**6. Over-engineering.** Nothing to delete. Both helpers have two real callers today (and
`_tasks_open` should have three). No speculative flexibility, no config nobody sets, no
abstraction with one implementation. The `+117/−41` in `_pipeline.py` is largely comment
relocation, not new logic. The only shrink available is collapsing the duplicate
`tasks.md` read, which would cost the helper the shape that makes it shared.

**Tests.** Read them first. Both new tests assert behaviour (`auto` on the payload), not
implementation, and both carry docstrings naming the failure they exist to catch. The
pairing is the right one: the negative alone would pass against a `decompose` arm
hardcoded to `False`, and the commit cites `87d9205` as that mutation surviving one step
later. Existing `_states`/`_annotation` tests already cover the state names, so the new
pair adds exactly the missing dimension. `_EXPECTED_STEPS` in `test_pipeline_commands.py`
pins the bare `next_step_content("decompose")` (no repo/spec) at `True`, so the
optional-argument path is covered too. Full suite: **1035 passed**. `ruff check wfctl/
tests/`: clean. `mypy wfctl/`: clean. (`wfctl verify` deliberately not run — it writes
outside the worktree.)

**Verdict: Request changes** — 1 blocker, 1 warning.

The guard is good work and should ship regardless of how the blocker is resolved; it is
the correct diagnosis (`auto`, not `state`, is what the consumer reads) in the correct
shape. What must not ship as-is is the pairing of `auto: true` on `decompose` with a
`/speckit.decompose` that its own skill documents as creating tracker issues, under a
commit message that tells the reader no run can reach it.
