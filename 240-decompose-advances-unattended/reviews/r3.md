### WARNING `wfctl/_pipeline.py:L515` — the reason given for the halt is the reason the *other* branch does not halt

The new docstring says decompose's two states "want the same instruction — write the
plan, or fill the table it already holds — and only one of them may be taken without a
human, because creating the issues is outward-facing." Both branches emit the same
command, `/speckit.decompose`. What that command does, per the bundle this repo ships:

- `wfctl/agents/commands/speckit.decompose.md` frontmatter: "Writes delivery.md **and
  creates GitHub issues** using the grouping plan."
- `speckit-delivery-plan/SKILL.md:89`, Step 5: "then write `delivery.md` and create
  GitHub issues."
- `speckit-delivery-plan/SKILL.md:204`, Verification Checklist: "[ ] GitHub issues
  created and numbered" — an item the step is not complete without.

So the branch that *may* be taken without a human is the branch that runs the issue
creation. The module asserts the opposite twice, and #8's whole design rests on the
assertion:

    wfctl/_pipeline.py:97   "...filled in once the issues are created, because
                             creating them is outward-facing and waits for a human."

Two readings, and the change is only correct under one of them:

- **The skill is authoritative.** Then `auto: true` on the no-plan branch authorizes an
  unattended orchestrate run to create issues in a live tracker with no human ever
  seeing the grouping plan — and `_pipeline.py:97` is a stale premise that the `#8`
  check is built on. That is a defect, latent only because no run reaches decompose
  today.
- **`_pipeline.py:97` is authoritative** — the command stops after writing the plan,
  and the `_(TBD)_` state is by design. Then the flip is fine and the *skill* is the
  document that is wrong, since it makes issue creation part of the same run.

Either way one of the two is wrong, and this commit is the one that turns the code
comment into an authorization. I could not find a third document that settles it;
nothing outside `_pipeline.py` and its tests uses the phrase "outward-facing", and
`wfctl issue create` (`cli.py:1105`) dispatches with no prompt, so there is no enforced
"outward-facing ⟹ human" invariant elsewhere to appeal to.

Not raised to BLOCKER because no run can reach decompose today and the policy call is
the maintainer's. It should be answered in the PR body rather than discovered when #100
lands. Note also `speckit-delivery-plan/SKILL.md:126` and `:187`, and
`speckit-specify/SKILL.md:225`, which put explicit "stop and flag it to the user"
branches inside the step — those survive `auto: true` (the flag governs whether
orchestrate *starts* the command, not whether the command may pause), so they are not
themselves a finding, but they are more evidence that the `False` encoded more than
#148's completeness check.

**Fix:** decide which document is authoritative. If the skill is, either keep decompose
`False` or split issue creation out of the auto branch. If `_pipeline.py:97` is, correct
`speckit-delivery-plan/SKILL.md` Step 5 and the checklist item so the premise the flip
rests on is written where the agent reads it.

### WARNING `wfctl/_pipeline.py:L522` — `_tasks_open` was extracted to stop exactly this drift, and the one caller that has it was left behind

The commit message: "`_tasks_open` comes out with it so the two arms cannot come to
disagree about what a finished task list is." It fixes the two arms inside
`_infer_steps`. It leaves the implement arm of `next_step_content` on the old,
checklist-blind spelling:

    L522   if tasks_text and not _has_open_checkboxes(tasks_text):

`_tasks_open` treats `checklists/implement-complete.md` as closing the task list over a
box left open; `_has_open_checkboxes` alone does not. So for a story that has the
sentinel *and* an open box, the two functions disagree — and the disagreement drops the
`False` that #148 exists to carry. Reproduced against this HEAD (temp repo, `wfctl.json`
with a `verify` command, no verify record, `tasks.md` = one `[x]` + one `[ ]`,
`checklists/implement-complete.md` present):

    _tasks_open        : False
    implement state    : ('in_progress', '1/2 done  unverified — run `wfctl verify`')
    current step       : implement
    next_step_content  : ('/speckit.implement', True)

`wfctl status --json` reports the story blocked on an unverified definition of done and
hands orchestrate `auto: true` for `/speckit.implement` — `EXECUTE_COMMAND` on the exact
state `test_a_blocked_implement_does_not_advance_unattended` pins against. That test
does not catch it because the `gated` fixture ticks every box, so `_has_open_checkboxes`
and `_tasks_open` agree there.

This is **pre-existing** — the diff does not touch L522 — and as a standalone defect it
is blocker-severity. It is filed here as a WARNING because the skill's own rule is not
to smuggle out-of-scope fixes into a feature diff. But this commit is the one that
introduces the helper which is the fix, and the one that claims the drift is closed.

**Fix:** a separate commit replacing L522's condition with `if not
_tasks_open(spec_dir):`, plus a test with the sentinel and an open box. If that is
deferred, the commit message's "the two arms cannot come to disagree" should be narrowed
to the two arms it actually unified, and an issue opened.

### NIT `wfctl/_pipeline.py:L530` — the guard's first conjunct is dead, and it is the half that fails open

    L530   if _tasks_open(spec_dir) and _decompose_block(spec_dir, repo_root):

Enumerating the states in which `_current_step_name` can return `"decompose"`:

- `in_progress` ⟹ `delivery.md` exists ∧ `_decompose_block` truthy ∧ `tasks_open`.
- `pending` ⟹ `delivery.md` missing (⟹ `_decompose_block` is `None`) ∧ `tasks_open`
  (with no `tasks.md` the `tasks` step is current instead, so decompose is never
  reached).

So in every reachable state `_decompose_block(...)` truthy already implies
`_tasks_open(...)`. Confirmed by probe: with unkeyed rows and every box ticked,
decompose reads `done`, `current` is `complete`, and `next_step_content("decompose")` is
never called.

The conjunct is not merely redundant — it is the direction that breaks. If #100 ever
lets decompose block with tasks closed, `_infer_steps` would say `in_progress` while
this guard short-circuits to `False` and falls through to the table's `True`: an
`EXECUTE_COMMAND` for a state the inference just called blocked. `_decompose_block`
alone is strictly more conservative and behaviour-identical today.

**Fix:** `if _decompose_block(spec_dir, repo_root):`. Verified safe against the current
suite by state enumeration above (also removes the extra tasks.md read on the decompose
step).

### NIT `wfctl/_pipeline.py:L280` — tasks.md is now read twice per `_infer_steps`

L276–277 reads `tasks_text`; L280 calls `_tasks_open(spec_dir)`, which opens the same
file again. Two reads of one file inside one inference, which is the property
`PipelineReport`'s docstring is careful about. Negligible cost, but the second read is
free to avoid.

**Fix:** `def _tasks_open(spec_dir: Path, tasks_text: str) -> bool` and pass the text
already in hand; `next_step_content` does its own read (and would do so anyway once the
L522 fix above lands).

## Passes run

**1. Correctness (adversarial).** Enumerated every state in which decompose can be
`_current_step_name`'s answer, and checked the `auto` each produces — see the L530
finding for the enumeration. The guard fires in exactly the blocking state and nowhere
else; the flip's positive branch (`pending`, no `delivery.md`) is the only one returning
`True`. Verified both by probe against this HEAD. Traced the called functions rather than
the changed lines: `_decompose_block` → `_unkeyed_issues` → `_ISSUE_MAP_SECTION` /
`_TABLE_SEPARATOR`; `_tasks_open` → `_has_open_checkboxes` / `_file_exists`;
`_current_step_name`; `build_report`; `cli.next_cmd` and `cli.resume_cmd`, the two
writers of `next-step.md`; `speckit-orchestrate/SKILL.md:109–128`, which confirms the
premise that only `auto` is read off the payload. Checked the refactor for behaviour
change against the pre-image: `decompose_reason` assignment, the `delivery.md` existence
check now made twice (structural, not redundant — the helper is also called cold), and
the `if decompose_reason and tasks_open` condition are all equivalent to what they
replaced. Edge cases checked: no `spec_dir`, no `repo_root`, empty `tasks.md`, zero-row
Issue Grouping Map, `unkeyed == 0` vs `None` (`if not unkeyed` handles both), plural
boundary at 1. The drift found is WARNING-2.

**2. Security.** No secrets, no user-facing input crossing a boundary, no subprocess or
network introduced — `configured_key_pattern` is disk-only (manifest + tracker JSON).
Checked whether the second `_decompose_block` call site widens the `re.error` crash
surface for a config-supplied `key_pattern`: it does not, because `_infer_steps` runs
first in both `build_report` and `next_cmd` and would raise before `next_step_content`
is reached. `delivery.md` is repo-local and already parsed by the pre-image. No finding.

**3. Architecture.** The guard is placed where the handoff argued it belongs
(`next_step_content`, not `_infer_steps`) and mirrors `_verification_block`'s shape, so
it introduces no new pattern. Re-deriving rather than threading the answer through
`next_step_content`'s optional signature is the trade `_verification_block` already
makes and is argued in the docstring; Chesterton respected, not a finding. It does mean
`auto` for two of eight steps is computed on a second read of the same artifacts, which
softens `PipelineReport`'s "one inference" claim — accepted as precedent rather than
raised. No dependency direction changed; `_pipeline` still imports only `_tracker` at
module scope.

**4. Readability & simplification.** Naming is consistent with the file
(`_verification_block` / `_decompose_block`, `_tasks_open`). No nesting increase; the
decompose arm of `_infer_steps` gets ~20 lines shorter and reads better. Comment volume
(~40 lines for ~20 of code) matches what CLAUDE.md asks of this file and every comment
explains *why this shape*, not what the line does — except the L515 docstring, whose
*why* is attached to the branch it does not describe (WARNING-1). Applied git blame /
history to the flipped `False` (`git log -S`, `ced8e17`, `87d9205`, #148) before
accepting the Chesterton's Fence argument; the fence has a second post the commit does
not account for, which is WARNING-1.

**5. Performance.** The change adds, only when the current step is decompose, one extra
read each of `tasks.md`, `delivery.md`, `.wf-skills-manifest.json` and the tracker JSON,
plus one `re.compile` — all local, on a command that runs once per session start. It
also adds one unconditional extra `tasks.md` read per `_infer_steps` call (NIT above).
No loops, no N+1, no unbounded reads. Not material; recorded rather than raised.

**6. Over-engineering.** Nothing speculative: no new abstraction with one caller (both
helpers have two), no config nobody sets, no dependency. `shrink:` the dead conjunct at
L530; `shrink:` the duplicate read at L280. Nothing to `delete:`, `stdlib:` or `native:`.

**Tests (read first, per Step 2).** Both new tests assert behaviour through
`build_report` — the one inference every view renders — not through internals. They pin
the halting branch and the advancing branch, which is the pair `87d9205` exists to
require; each kills the mutation the other survives (a hardcoded `False` in the decompose
arm passes the negative test alone; deleting the arm passes the positive alone).
Docstrings name the failure they exist to catch. `_EXPECTED_STEPS` in

raised: there is no CLI-level assertion that `next-step.md` carries `auto: false` for
decompose, the way `test_a_blocked_implement_does_not_advance_unattended` does for
implement — acceptable, since `next` and `resume` both route through the covered
`next_step_content`. The one gap that matters is the *missing* test described in
WARNING-2, which no fixture in the suite reaches.
