## Findings

WARNING  wfctl/agents/skills/speckit-delivery-plan/SKILL.md:L128 — Step 7 ("Create the
issues and write their keys back") never names the command that creates an issue, and no
reference under `speckit-delivery-plan/references/` does either. Before this flip a human
sat at the decompose pause, so the step's only guard being prose cost nothing. After it,
step 6's prose is the *first* line of defence and there is no second one unless the agent
happens to reach for `wfctl issue create`, which `_refuse_notifying` (`wfctl/_tracker.py:77`)
actually refuses; `gh issue create` bypasses the check entirely and is what an agent given
no command will plausibly type. `end-session/SKILL.md:194` already names `wfctl issue
create --title … --body …` for exactly this reason. This is the one place
`a-rule-is-expressed-as-a-check` bites: the rule is enforceable by a check that already
ships, and the skill routes around it by silence.
→ Name `wfctl issue create --title "<title>" --body "<context>"` in step 7, so the machine
refusal stands behind the prose. Small, in-scope, and it is the guard the flip leans on.

WARNING  wfctl/_predicates.py:L600-608 — The new annotation paragraph asserts "Two steps
run automatic over a rung this low, and neither is a gap left open", and names an unkeyed
map as what still stops the step. It is silent on the two readings the paragraph three
lines above it names as reaching `ambient` and proceeding: no tracker configured, and a
plan carrying no map or no rows. The first is harmless (no tracker, nothing outward-facing).
The second is not, and the flip changes it: a `delivery.md` whose Issue Grouping Map
heading is absent or misspelled — a file the same unattended run just wrote — returns
`None` from `_unkeyed_issues`, reads `done` at rung 1 (file is non-empty), and the loop now
advances to `implement` with nobody having looked. That case used to hit the human pause.
→ Either name it in the annotation as accepted and say why (a plan predating the table is
indistinguishable from a malformed one, which is #314's reason), or file it. As written the
comment claims a completeness it does not have, in the one file whose comments this repo
treats as load-bearing.
