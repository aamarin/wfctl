## W1 — `auto: true` on `decompose` authorizes unattended tracker-issue creation

`wfctl/_pipeline.py:L30`, justified at `L513–517`.

The new docstring's own reason for the guard is *"only one of them may be taken
without a human, because creating the issues is outward-facing."* The branch that
now returns `auto: true` — no `delivery.md` yet — is the branch whose command
creates the issues.

Evidence, from the bundle this repo ships:

- `wfctl/agents/commands/speckit.decompose.md` (frontmatter `description`):
  *"Writes delivery.md **and creates GitHub issues** using the grouping plan."*
- `wfctl/agents/skills/speckit-delivery-plan/SKILL.md:88–89` (Step 5, the last
  step): *"then write `delivery.md` **and create GitHub issues**."*
- Same file, `L204` (Verification Checklist, required before decompose is
  complete): *"GitHub issues created and numbered."*
- Nothing in that skill's five-step process, its Red Flags list, or its checklist
  pauses before creating them.

And `_unkeyed_issues`' own docstring, unchanged by this diff, states the opposite
premise the flip rests on (`_pipeline.py:L96–99`):

> The Issue Grouping Map is authored with placeholder keys and filled in once the
> issues are created, **because creating them is outward-facing and waits for a
> human.**

So `speckit-orchestrate` emitting `EXECUTE_COMMAND: speckit.decompose` hands an
unattended agent a skill instructed to create tracker issues. The guard is a
*backstop* for the case where that agent stops at placeholders — it is not a gate
in front of the creation, because by the time `delivery.md` exists the issues were
supposed to already exist.

Severity, honestly placed: **WARNING, not BLOCKER.** It is unreachable today
(`clarify` and `analyze` are both `False` and sit earlier in the table), the
outcome depends on agent behaviour rather than on a deterministic path in this
diff, and it may well be the intended design. But it must be settled rather than
left implicit, because #100 is what makes it live, and this diff is the one that
records the answer.

Three ways out, author's call:

- **A.** If issue creation may happen unattended, the flip is right and
  `_unkeyed_issues`' "waits for a human" sentence and the new
  `next_step_content` docstring are both now wrong and should say so.
- **B.** If it may not, `speckit-delivery-plan` needs a stop before Step 5's
  creation half, and the SKILL change belongs in this commit (per `CLAUDE.md`, a
  change under `wfctl/agents/` is not verified by the suite — it needs
  `uv run wfctl install-skills` and an exercise).
- **C.** Defer the flip's *fresh-plan* branch to #100 and ship only the guard,
  which stands on its own.

## W2 — the `_tasks_open` extraction stops one call short, and the gap is reachable

`wfctl/_pipeline.py:L519–522` (the `implement` arm of `next_step_content`).

The commit message says `_tasks_open` "comes out with it so the two arms cannot
come to disagree about what a finished task list is." There were three arms, not
two. The `implement` guard ten lines above the new `decompose` guard still asks
the old, *different* question:

```python
if tasks_text and not _has_open_checkboxes(tasks_text):   # L522
```

`not _tasks_open(spec_dir)` is `(no open boxes) or (implement-complete.md exists)`.
The inline form drops the sentinel half, so the two disagree exactly when a
sentinel sits beside an open box — which `speckit-implement/SKILL.md:179–181`
names as a supported state ("when checkbox state is unavailable, e.g. tasks were
executed outside this skill").

Reproduced (temp repo, definition of done configured, never verified, `tasks.md`
= one `[x]` + one `[ ]`, sentinel present):

```
implement    in_progress  1/2 done  unverified — run `wfctl verify`
current: implement
next_step_content: ('/speckit.implement', True)
```

`_infer_steps` says the work is done and only verification is missing;
`next_step_content` says run `/speckit.implement`, `auto: true`. With every box
ticked the same repo correctly returns `('wfctl verify', False)`. This is the
precise failure #240 exists to prevent — a `state` the orchestrator never reads
disagreeing with the `auto` it does — one step further down the same table.

**Pre-existing**, not introduced here. But the fix is now a one-line application
of the helper this commit added for this exact purpose:

```python
if tasks_text and not _tasks_open(spec_dir):
```

(All-ticked case is unchanged: `_has_open_checkboxes` False ⇒ `_tasks_open` False
⇒ same branch. I did not run the suite against this edit — the worktree is
shared and I was asked to change nothing.)

If the author prefers to keep the diff scoped, that is legitimate and the skill
says so ("file it, don't smuggle it") — but then file it, and narrow the commit
message's claim, which currently asserts a unification the code does not have.

## W3 — the "~30 call sites" rationale is false

`wfctl/_pipeline.py:L180–182`. The new `_decompose_block` docstring re-states it as
the reason both callers re-derive rather than one carrying the answer:

> carrying one answer between them would have to travel through a signature ~30
> call sites pass neither half of.

Counted across the repo, `next_step_content` has **4** call sites: `_pipeline.py:577`
(`build_report`), `cli.py:279` (`next_cmd`), and three in
`tests/test_pipeline_commands.py` (L111, L121, L122). Both production callers pass
both arguments. The claim was never true either — at `c1a82d2^`, the commit that
introduced it, `git grep -c` finds 7 occurrences across 4 files.

This matters in *this* repo specifically. `CLAUDE.md` makes comments the carrier of
rationale ("explain *why this shape*"), and the global working rules name claims
propagating unverified across handoffs as a known failure. A future reader
declines a valid simplification on the strength of a number that is an order of
magnitude off. The trade being defended is sound on its own terms — the optional
signature and the `_verification_block` precedent — so the number can simply go.

## NITs

- **`_pipeline.py:L513–517`** — *"Its two states want the same instruction — write
  the plan, or fill the table it already holds."* Two other comments in the same
  file say the opposite: `L378` ("`/speckit.decompose`, which does not backfill a
  table") and the new test at `test_decompose_issues.py:L275`. The emitted command
  is unchanged and pinned by the pre-existing test at L216, so this is prose only —
  but a reader now has to pick a winner among three comments.
- **`_pipeline.py:L530`** — the `_tasks_open(spec_dir) and` term cannot change the
  result for any caller that passes the *current* step name, and both production
  callers do. No test calls `next_step_content("decompose", repo, spec)` directly,
  so a mutation deleting the term survives the suite. Defensible as symmetry with
  `_infer_steps`; worth a word saying so, or a test that pins it.
- **`_pipeline.py:L276 + L280`** — `_infer_steps` reads `tasks.md` at L276 for the
  annotation, then `_tasks_open` reads it again at L280; `next_step_content`'s two
  arms read it a third time. Perf is irrelevant (three reads of a small file,
  sub-millisecond) — the note is that a refactor whose stated purpose is one
  spelling left three reads. `_tasks_open(spec_dir, tasks_text)` or deriving
  `tasks_text` inside would close it.
- **`_pipeline.py:L173–177`** — "Three shapes return None and each is a deliberate
  degrade, argued at `_unkeyed_issues`". Only the no-map case is argued there; the
  no-tracker case is argued here and at `_tracker.configured_key_pattern`, and the
  no-plan-yet case is not a degrade at all — it is the `pending` state. A fourth
  shape (`_unkeyed_issues` returns None for a map with a header and no rows) is
  unlisted.
- **`tests/test_decompose_issues.py:L295–298`** — the positive test re-spells
  `_feature`'s artifact list (`design.md`, `plan.md`, `checklists/analysis-report.md`,
  `CLEAN_SPEC`, tasks) because `_feature` always writes `delivery.md`. If the staged
  set changes, this test drifts silently — `_feature(spec_tree, delivery=None)` would
  keep one spelling, which is the theme of the diff itself.

## What each pass checked

**1. Correctness (adversarial).** Traced `_decompose_block`, `_tasks_open`,
`_unkeyed_issues`, `_verification_block`, `_tracker.configured_key_pattern` /
`load_key_pattern` / `load_manifest`, `_current_step_name`, `build_report`,
`cli.next_cmd`, `cli.resume_cmd`, `cli.status_cmd`. Verified the extraction is
behaviour-preserving: `_decompose_block` returns `None` for every path the old
inline code left `decompose_reason` unset (no `delivery.md`, no pattern,
`unkeyed` falsy), so the annotation and the `in_progress` condition are
unchanged, and `if not unkeyed` correctly collapses `None` and `0`. Enumerated
the guard's state matrix: no plan → `_decompose_block` returns `None` before
touching the tracker → `auto: true`; plan with unkeyed rows + tasks open →
`in_progress`, guard fires, `auto: false`; unkeyed rows + tasks closed → `done`,
decompose not current, guard unreachable; earlier step blocking → guard
unreachable. Confirmed both production callers pass `repo_root` and `spec_dir`,
so the `is not None` short-circuit cannot silently hand back the table's `True`.
Confirmed no new exception path: `_tracker.configured_key_pattern` is already
reached via `_infer_steps` on every `build_report`, and `load_key_pattern`
swallows an uncompilable pattern. Found and reproduced W2. `uv run pytest -q`:
**1035 passed**, 99s.

**2. Security.** No external input, no secrets, no auth surface, no shell or SQL.
The one untrusted value is `key_pattern` from repo config, compiled as a regex —
pre-existing surface, unchanged by this diff, and `load_key_pattern` rejects
uncompilable patterns before `_unkeyed_issues` sees them (pinned by the
inline-flag test at L244). The security-shaped question here is authorization,
not input: W1 is that an `auto: true` authorizes an outward-facing, hard-to-undo
action (creating tracker issues) with no human in the loop.

**3. Architecture.** `_decompose_block` mirrors `_verification_block` — same
return shape (reason-or-`None`), same two callers, same re-derivation trade —
so it fits an established pattern rather than inventing one. Checked against
`docs/architecture/`: `pipeline-state-is-one-payload` forbids a *view* computing
state, and this does not cross that line — `auto` still lands in the single
`PipelineReport` that `build_report` constructs, and the console and `--json`
branches remain two formats over one inference. The record's "computed once"
spirit does argue against deriving `_decompose_block` twice per `build_report`;
the commit names that trade explicitly and `_verification_block` set the
precedent, so this widens an accepted pattern rather than breaking a rule. No
new dependency, no cycle: `_pipeline → _tracker` already existed.

**4. Readability & simplification.** Names are accurate (`_tasks_open`,
`_decompose_block` both say what they return). No nesting added — the guard is a
flat two-condition `if`. Applied Chesterton's Fence to the `False` being flipped:
traced it to #148, confirmed via `_unkeyed_issues` and its test file that the
reason it encoded was removed by #8, so the fence is genuinely down. Against
`CLAUDE.md`'s comment policy the new comments inform rather than narrate — with
the exceptions in W3 and the first two NITs, where the rationale is inaccurate or
contradicts a neighbour.

**5. Performance.** Quantified rather than asserted: on a `build_report` for a
decompose-current feature the diff adds one extra `tasks.md` read plus a second
`_decompose_block` (one `delivery.md` read, one regex scan, and — uncached —
`load_manifest` twice plus one tracker-config JSON read). Roughly eight extra
small-file stats/reads, sub-millisecond, on a command that already shells out to
git elsewhere. Not a finding; recorded so the NIT at L280 is not mistaken for a
perf claim.

**6. Over-engineering.** Both helpers have two real callers, so neither is a
speculative layer — `yagni` does not apply. No stdlib or platform duplication.
The only `delete:` candidate is the redundant `_tasks_open` term in the guard
(NIT), and removing it would cost the symmetry with `_infer_steps`, so it stays.
The diff is already the shorter form: it removes 24 lines of inline logic and
comment from `_infer_steps` for 43 lines of two reusable helpers, and the net
growth is docstring.

**Tests (read first, per Step 2).** Both new tests are behavioural — they go
through `build_report`, not the helper — and named as sentences with docstrings
that say why they exist, matching `CLAUDE.md`. The pair is deliberately
complementary and the positive half is load-bearing: without it, a `decompose`
arm hardcoded to `False` passes, which is the mutation `87d9205` is cited for.
The negative test pins the guard (delete it and `_STEPS` returns `True` and the
test fails); the command the guard emits is covered by the pre-existing test at
L216, which now runs through the guard. No `NO_COLOR` pin needed — neither test
touches console output. Gap noted in the NIT at L530.
