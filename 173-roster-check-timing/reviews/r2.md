## Findings

**WARNING  `wfctl/_body.py`:L391-398 — when both markers are present the remedies
lose their marker, and the joined sentence reads as one instruction sequence.**

The change's stated purpose is that `MISSING` and `RUNNING` "need opposite
responses". With both in the roster, the shipped string is:

```
… the roster records ['MISSING', 'RUNNING']: 'r1 MISSING  r2 RUNNING  r3 ✓'.
fanning-out-code-review Step 3 calls that a failure rather than a pass — ask
that reviewer again for its findings; wait for it to come back, then read the
roster again. …
```

The marker→remedy correspondence survives only as positional agreement between
two independently rendered `sorted()` orders, which the reader cannot see. Worse,
the joined clause has a coherent wrong reading — "ask that reviewer again; wait
for it to come back, then read the roster again" parses as a *sequence for one
reviewer*, which is exactly the "ask a working reviewer again" behaviour the
commit says it is removing. The new test only exercises the single-marker case
(`roster: r1 ✓  r2 RUNNING`), so the case where the pairing breaks is untested.

→ Pair them and drop the now-redundant bare list:

```python
f"opening-a-change Step 1 — the roster records "
f"{'; '.join(f'{m} → {FAILURE_MARKERS[m]}' for m in matched)}, in "
f"{roster!r}. …"
```

and add a roster carrying both markers to
`test_each_failure_marker_carries_its_own_remedy`, asserting each remedy appears
adjacent to its own marker.

**WARNING  `wfctl/agents/skills/fanning-out-code-review/SKILL.md`:L130 — the
fence now ships a hard-coded assertion about *state*, and a stale one re-creates
#173 silently.**

`RETURNED="r1 r2"` is not a placeholder in the way `for id in r1 r2 r3` is. The
roster line is obviously wrong until edited — it names reviewers that do not
exist. `RETURNED` is a claim about *when* it was last read, and it looks correct
after the ids are substituted and stays correct-looking forever. Two failure
modes follow, neither visible in the output:

- Agent edits the `for` list, leaves `RETURNED` stale → reviewers that have not
  come back are checked against the disk and print `MISSING`. That is precisely
  the fabricated-MISSING #173 was filed for, reintroduced through the mechanism
  that fixes it.
- Agent edits `RETURNED` to be the whole roster once and re-runs later → same.

Prose covers the substitution ("Both lists are **yours to substitute**") but
never names what a stale `RETURNED` costs, and no artifact records it — the
output looks identical either way, which is the shape
`a-rule-is-expressed-as-a-check` is uneasy about.

I do not think the default can simply become `RETURNED=""`: the fixture runs the
fence verbatim with nothing injected, so an empty default would make the
`reported`/`MISSING` branches unreachable from the test. The cheap fix is the
comment, which is the only line that has to change:

```
RETURNED="r1 r2"   # re-type this on every read; a stale list prints a fabricated MISSING
```

Related, same line: membership is matched on single-space boundaries. A
`RETURNED` built with tabs or newlines (plausible when assembling it from a list
of completion notifications) matches nothing and prints `RUNNING` for every
reviewer — a silent stall rather than an error. Worth a word in the same comment.
