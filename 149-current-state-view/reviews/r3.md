## The warnings in full

### W1 — the view ships a wrong line count, and two different ones

`current-state.md:L10` says "Derived from `wfctl/*.py` at `5ba013e`". At that
commit `cli.py` was 3568 lines, which is the number at L68. The drawing at L16
says 3566. At the branch tip being merged (`0a02937`) it is **3627** — `24beb3e`
grew it by 59 lines and the view was not re-derived.

Every other count in the drawing is exact at HEAD (`_pipeline 442`, `_arch 359`,
`_archive 339`, `_guard 286`, `_verify 245`, `_tracker 227`, `_workmux 191`,
`_settings 173`, `_session 102`, `_bundle 92`, `_paths 446`, `_manifest 42`,
`_io 66` — all verified against `wc -l`). So the one stale number is the one the
document builds an argument on: "`cli` is 3568 lines because it is the one place
all thirteen meet."

This is not pedantry about a number. L144 already concedes that line counts go
stale silently, and the file demonstrates it on the commit that introduces it —
including disagreeing with itself two paragraphs apart. Issue #149's own body has
`cli.py 2867` for the same reason. **Fix:** re-derive at the merge commit, state
`cli` once (or state it as "over half the tree" and give the number only in the
drawing), and either update the "Derived from" sha or drop it in favour of "at
merge".

### W2 — "a fifth private crossing turns the drawing red" is form-dependent

`_graph()` collects private crossings in exactly one branch — the
`from wfctl._paths import _X` / `from ._paths import _X` form at L56-63. The
branch above it, which handles `from . import _paths` and `from wfctl import _paths`,
`continue`s before any private collection, and `ast.Import` never collects at all.

Measured on the current tree, `cli`'s 13 edges break down like this:

```
   from wfctl._mod import ...   _paths _pipeline _manifest _io _archive _session
   from wfctl import _mod       _tracker _bundle _settings _verify _arch _guard _workmux
```

For those seven, a new `_settings._SOMETHING` or `_arch._SOMETHING` attribute
access is a private crossing the check cannot see. (No such access exists today —
I grepped for `_<mod>._<name>` across `wfctl/*.py` and got nothing — so the "four"
is factually complete right now. The guarantee, not the count, is what's weak.)

Three places state the guarantee without the qualifier:

- `current-state.md:L140-142` — "a fifth private crossing … turns the drawing red"
- `the-underscore-is-the-module-contract.md` Consequences — "fails on a fifth crossing"
- `AGENTS.md:L101` — "is what keeps it true"

**Fix, cheapest first:** in `_graph`, also record `(src, mod, attr)` for
`ast.Attribute` nodes whose `.value` is a `Name` matching a module in `mods` and
whose `.attr` starts with `_`; roughly four lines and it closes the form gap
entirely. Failing that, say "a fifth private *import*" and note that attribute
access past a module object is not covered — the record is already careful to say
"It enforces the count, not the rule", so the honest half of this exists; it just
doesn't reach the sentence a reader will quote.
