## The four questions, answered

### Is there a reachable state in which the flip is wrong or unsafe?

**In the code, no.** I traced it rather than trusting the commit message.
`_predicates.clarify` (`_predicates.py:L1011`) returns `Reading` with no reason in
all four arms — `done`, `in_progress` (markers), `skipped` (the pre-gate spec,
which carries an *annotation*, deliberately not a reason), and the trailing
`in_progress`. `_predicates.analyze` (`:L1097`) is a one-liner with no reason at
all. `_infer_steps`' cascade appends `_PipelineStep(name, "pending", None)`, so a
cascaded step carries none either. So `blocked` is `None` whenever either step is
current, the override never fires for them, and `auto` is `True` — which is
exactly FR-003/FR-004. Reproduced the `skipped` arm directly:

```
[('brainstorm','skipped',None), ('specify','done',None), ('clarify','skipped',None),
 ('plan','done',None), ('tasks','pending',None), …]   current: tasks
```

`_current_step_name` skips `skipped`, so the flipped value is never read there.

**In the skills, two places.** These are the states the table cannot express:

1. `analyze`'s verdict gates nothing (first WARNING). `speckit.analyze.md:L62-63`
   defines `unsatisfied` as "at least one CRITICAL finding is open", and
   `speckit-analyze/SKILL.md:L222` tells the run "If CRITICAL issues exist:
   Recommend resolving before `/speckit.implement`" — a recommendation to a
   reader who, after this change, is the agent that then runs
   `speckit-orchestrate` and reads `decompose: automatic`. Nothing in wfctl reads
   the scan file (`_paths.SCANS_DIR` is excluded from `load_records`,
   `records_on_this_branch` and `_observe`), and `_predicates.analyze` reads only
   existence. Before the flip a human at least invoked the step and saw the
   findings in-session; now the first human who sees a CRITICAL is the PR
   reviewer, after `implement` has run on it. `blocks(verdict, source)` is the
   mechanism #287 shipped for precisely this and `analyze` is the one review step
   that does not call it.

   Scope note: this is a pre-existing property of the predicate, not something
   the diff introduced. I am raising it because #325's whole argument is that the
   evidence is now sufficient, and the sharpest piece of that evidence — the
   verdict — is written and never read. I checked the open issue list: #330
   (scan structure unchecked), #331 (analyze step 8), #332 (no loop bound) do not
   cover it, and neither scan file for this feature raises it.

2. `clarify` has no unattended rule (fourth WARNING). `speckit.brainstorm.md`
   handles this properly: it reads `auto_approve` off the payload and gives a
   four-row table saying what each upstream pause becomes, citing
   `a-human-accepts-a-decision`. `speckit.clarify.md` has no equivalent, and the
   skill it wraps is unambiguously interactive. Its one mention of an unattended
   run is the closing paragraph about recording rejected options, which says the
   rule is *not* conditional on the mode — good, but that is the evidence layer,
   not the answering layer. The analyze half of this is filed (#331) and named in
   `docs/architecture/scans/325-analyze.md`'s Deferred section, which also states
   plainly that SC-002 is unverifiable until #331 lands. The clarify half is in
   neither.

   Note that FR-007 forbids making the *table* conditional on a runtime value, so
   the fix belongs in the command wrapper, not in `_STEPS`. No conflict.

### Is the `next_step_content` override sufficient, and reached on every path?

Sufficient, and reached. There is exactly one computation of the flag —
`_pipeline.py:L347-L353` — and the `blocked` guard sits above the table lookup,
so no table value can reach a caller past it. The three consumers all go through
it: `build_report` (`_pipeline.py:L486`), `cli.next_cmd` (`cli.py:L563`), and
`resume` via `build_report`. Each computes `blocked` the same way, as
`next((s.reason for s in steps if s.name == name), None)` over the list
`_infer_steps` already produced, so there is no second inference to disagree.

The new `test_the_reported_flag_is_the_table_and_nothing_else` pins both halves
over all eight rows, which is the right shape for FR-005/FR-006. One limit worth
naming: it constrains `next_step_content` only. A second site added in `cli` or
in `build_report` would not break it. Not worth a test — the signature already
makes a branch on anything but `(step, blocked)` impossible — but the docstring's
"a branch reading anything else has nowhere to hide" is a property of the
signature, not of the assertion.

### Anything still pinning the old values that the change missed?

One, and the suite structurally cannot see it: **`README.md:L189` and `L193`**.
The Example Session block renders `analyze` as current with `auto: false` and
`auto=False`. Since `_predicates.analyze` never returns a reason, that is now
output wfctl cannot produce. This is the `a-rule-is-expressed-as-a-check` gap in
its documentation form — the value is pinned in prose, in a fenced block, with no
check over it.

Everything else is clean. Swept `README.md`, `docs/`, `wfctl/agents/` and
`wfctl/` for `review_required`, `_REVIEW_REQUIRED`, `auto: false`, `auto=False`
and `auto=false`: the only remaining hits are the four test docstrings that name
`review_required` correctly in the past tense,
`docs/architecture/required-sections-are-wfctls.md:L93` (about `specify`/`plan`,
untouched by this change), `docs/architecture/design/314-…:L34` (the `Literal`'s
declaration, still accurate), and `docs/architecture/scans/325-clarify.md:L53`
(an accurate record of a rejected option, not a claim about current behavior).

so no regeneration was needed.

  declaration rather than a record is the honest form — `_STEPS` already owned
  the value, the flip moves nothing.

  either prohibition could have been written as.

  corrected away, is the kind of thing that makes a spec worth re-reading.
