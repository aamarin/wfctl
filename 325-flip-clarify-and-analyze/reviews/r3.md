## Detail

### 1. README.md:189,193 — the change falsifies the project's flagship example

`README.md`'s **Example Session** is the only end-to-end rendered output in the
repository, and it is built entirely around `analyze`:

```
analyze      ○  ← current

$ wfctl resume
↺ Resumed — step: analyze, next: /speckit.analyze (auto: false)

$ wfctl log
2026-07-15 11:03  resume      step=analyze  command=/speckit.analyze  auto=False
```

`_predicates.analyze` (`wfctl/_predicates.py:1097`) is
`Reading("done" if report exists else "pending")` — it never returns a reason.
`build_report` derives `blocked` from the current step's `reason`
(`wfctl/_pipeline.py:486`), so for `analyze` `blocked` is always `None`, and
`next_step_content` now falls through to `row.continuation == _AUTOMATIC` →
`True`. `cli.py:630` renders `(auto: true)` and `cli.py:649` logs `auto=True`.

So this is not "wrong in some states". After this change, **`analyze` cannot
produce `auto: false` in any reachable state**, and the README depicts a run
wfctl will never emit.

Two things make this worth a WARNING rather than a NIT:

- These are the only two rendered `auto` literals anywhere in `README.md`,
  `docs/` or `wfctl/agents/` (swept). The blast radius is exactly two lines,
  and the fix is two characters each.
- Nothing checks it. No test reads the repository README (the eight test files
  matching `README` all write fixture READMEs or test unrelated paths). Under
  `a-rule-is-expressed-as-a-check`, the question is whether a violation is
  visible in an artifact the work already produces — here it is, in `wfctl
  resume`'s own output, and no check holds it, which is why a two-token table
  edit falsified the front page silently.

### 2. The evidence the flip rests on is produced only in the mode the flip is not for

The commit body's central argument is:

> Since #307/#320 both steps commit a scan file naming what they covered, so a
> pass that found nothing and a pass that never ran are no longer the same pull
> request.

`wfctl/agents/commands/speckit.analyze.md:44` then says:

> **Write it after step 8**, not after step 6b. `Acted on` and `Accepted` are
> not knowable until remediation has been settled […]

Step 8 (`speckit-analyze/SKILL.md:227`) is `Ask the user: "Would you like me to
suggest concrete remediation edits…"`. Step 9 — `Invoke speckit-orchestrate` —
is *after* it.

Trace an unattended run that reaches `analyze` after this change:

| | pre-flip | post-flip |
|---|---|---|
| where the run stops | orchestrate prints `Next: run /speckit.analyze when ready` and stops | inside `/speckit.analyze`, at step 8 |
| `checklists/analysis-report.md` | not written | **written** (step 6b) — predicate reads `done` |
| `<arch-root>/scans/<issue>-analyze.md` | not written | **not written** — wrapper says after step 8 |
| pipeline advanced | no | no — step 9 never runs |

The post-flip stop is the worse of the two. It leaves the pipeline's own
sentinel saying `analyze` is complete while the reviewer-facing attestation is
absent — which is precisely the #307 defect ("a scan that *could not run*
looking identical to one nobody started"), reinstated on the one step whose
scan file the commit body cites as earning the flip.

**Was scoping #331 out defensible?** Yes, and I want to be explicit about that.
#331 is a genuinely good issue: it has a definition of done, a stated policy, a
placement decision that respects `vendor-upstream-skills`, and it says outright
that #325 is not blocked by it. The analyze scan (`scans/325-analyze.md`,
committed at `0461734`) names #331 as the reason SC-002 is unverifiable and says
it is "carried to the pull request rather than left to be discovered there".
That is the repo's own convention — `the-scan-is-attested-where-the-reviewer-reads`
— working as designed. I found it where the repo says to look.

**What is missing** is this ordering consequence specifically. #331 worries
about *what* the agent decides at step 8 ("the counts are written; the policy
that produced them is not"). It assumes the run gets past step 8. It does not
consider the run that stalls *at* step 8, where the wrapper's own "after step
8" rule means no scan file at all. That is new information relative to what the
author had in front of them, and it is one sentence in #331 or one relaxation
in the wrapper.

Neither commit message mentions #331 or #332 by number. The scans do, and under
this repo's placement rules that is the right home — so this is not a finding
against the diff, just worth noting that a reader of `git log` alone gets the
claim "clarify and analyze may run unattended" with no pointer to the fact that
`analyze` does not, yet.

### 3. The clarify loop is deterministic, not merely reachable

The author's claim — that `brainstorm` already made an unbounded loop reachable
since #283 — **is true**, and I verified it independently rather than taking
#332's word for it. `brainstorm`'s pending arm fires when neither `design.md`
nor `spec.md` exists; the step is then current, unblocked, and `auto: true`, so
a pass that produces no `design.md` routes straight back into itself. So the
"this is not new" half of the argument holds.

But the two loops are not comparable in likelihood, and the difference matters
to whether #332 can wait.

`brainstorm`'s loop needs the command to **fail** — to produce no `design.md`.
Under `auto_approve: true`, `speckit.brainstorm.md`'s pause table explicitly
forbids that ("Do not wait. […] write `design.md`"). Once `design.md` exists the
step is `done` or *blocked* (`design_block`), and blocked ⇒ `auto: false` ⇒ the
loop stops. So brainstorm's loop is an abort path.

`clarify`'s loop is a **success** path. Chain the three facts:

1. `_predicates.clarify:1027` — `done` requires `scanned and not ev.has_markers`.
2. `speckit-clarify/SKILL.md` never mentions `[NEEDS CLARIFICATION` anywhere.
   Nothing in the vendored workflow targets the markers wfctl's predicate keys on.
3. `speckit-clarify/SKILL.md:213` — "If no meaningful ambiguities found **(or
   all potential questions would be low-impact)**, still record that the scan
   ran: add the `## Clarifications` section […] then respond: 'No critical
   ambiguities detected worth formal clarification.' and suggest proceeding."
   And `:207` defines `Outstanding` as "still Partial/Missing but low impact" —
   i.e. deliberately left standing.

So: a spec carrying one low-impact `[NEEDS CLARIFICATION` marker. `/speckit.clarify`
runs to completion, reports success, changes nothing the predicate reads. The
predicate returns `in_progress` with **no reason**, so `blocked` is `None` and
`auto` is now `true`. Orchestrate emits `EXECUTE_COMMAND: speckit.clarify`
against identical inputs. Identical outcome. Forever.

The skill's own wfctl-authored addendum already names the shape — "the pipeline
will keep routing back here" — written when that sentence terminated at a human.
It no longer does.

#332 characterises this as "a pass that *fails* to resolve a marker", which
reads as flaky or adversarial. It is neither: it is the specified behaviour for
a marker the prioritisation heuristic declines to ask about. I'd put that
sentence into #332, because it changes the priority.

**A cheaper fix than #332's exists, and it sits in this angle's territory.** The
loop needs orchestrate to have a bound *only* if `clarify` cannot be made to
converge. It can: one paragraph in `wfctl/agents/commands/speckit.clarify.md`
requiring that a marker the step declines to ask about be rewritten into prose
and recorded as Outstanding in the scan file. That is the wrapper-layering
pattern the file already uses twice, it respects `vendor-upstream-skills`
(no edit to the derived skill), it needs no new state so
`session-state-is-re-derived` is untouched, and it makes the predicate converge
without touching orchestrate at all. Worth raising on #332 as an alternative to
the repeated-step check.

### 4. The commit body's biconditional

> after this, a run reports `auto: false` if and only if the current step has
> not finished.

The ⇒ direction holds: `auto: false` ⇒ `blocked` ⇒ not finished. The ⇐
direction does not: `clarify` with markers standing has not finished and reports
`auto: true` — which is finding 3, and is the case #332 exists for. (`specify`
with markers is the same shape and predates this change.)

The test gets this right — `test_resume_reports_the_auto_flag_of_the_step_it_
resumed_to`'s docstring says "a run only reports `auto: false` when the current
step is blocked", one direction, correct. Only the commit body overstates it.

That matters more here than it would elsewhere. The body says, in its own words,
"Said here because the next person flipping a flag will read this as precedent",
and `AGENTS.md` makes commit bodies the durable home for reasoning not visible in
the diff. A future reader taking the biconditional at face value would conclude
the loop in finding 3 cannot exist.

### 5. `test_no_step_still_waits_for_a_human_once_it_has_finished` carries nothing

Its docstring argues:

> A test asserting the new dict passes just as well against a table that gained
> a ninth `review_required` step alongside the two it lost.

It does not. The test above it asserts
`{name: step.continuation for name, step in _STEPS.items()} == {…eight keys…}` —
exact dict equality. A ninth key of any value breaks it. The only case where the
two tests diverge is a ninth *automatic* step, and there the dict test must be
updated anyway. The count-of-zero is already proved by the assertion directly
above.

Under this repo's own convention — "a test that only restates its assertion in
prose is not carrying its weight" — this is `delete:`, −10 lines. If it stays,
the docstring's claim needs correcting, because a false justification in a
docstring is worse than none.

### Judgment

The change is right. Everything it claims about `_pipeline.py` holds, the test
work is unusually thorough (the six-tests-beyond-the-design finding in the commit
body is real and well told), and the scans and the two filed issues are what a
good scope decision looks like rather than a hand-wave.

What it did not do is walk the flip out into the tree it changes the behaviour
of. Two artifacts outside `_pipeline.py` are now false or unreachable —
`README.md`'s example, and the analyze scan file's write ordering — and one loop
that the author correctly identified as pre-existing is materially more likely
than the precedent they compared it to. All three are cheap.

I would approve the moment `README.md:189` and `:193` are corrected; the rest can
travel on #331 and #332 with the two sentences above added to them.
