## Findings

WARNING  wfctl/_archive.py:L142: The commit check stops `workmux merge` even though local trunk already holds the work. `workmux merge` merges the branch into local `main` and then runs `pre_remove` (its `--no-hooks` help says so). The branch's commits are not on a remote yet, and in a clone `trunk_branch` resolves to `origin/main` from `origin/HEAD`. That trunk doesn't hold the merge, so the merge check changes the tree and the removal stops with "this worktree holds work saved nowhere else", which isn't true. I reproduced this: a clone, a worktree with one commit, `git merge --no-ff` into local `main`, then `archive unsaved` exits 1 and names the commit. As a result, every `workmux merge` stops until `main` is pushed. The fix is to also exclude commits that other local branches still reach, since those branches survive the removal: `git log HEAD --not --remotes --exclude=<branch> --branches`. The pattern goes without `refs/heads/`, because git ignores a prefixed pattern after `--branches`. I checked it on the same fixture, and it lists nothing, so the removal goes ahead.

WARNING  wfctl/_archive.py:L142: In a repository with no remote, the stop block lists trunk's whole history as "commits on no remote that aren't merged into main". `--not --remotes` excludes nothing when there are no remotes. I reproduced this with three trunk commits and one branch commit, and all four were printed. In a real repository that is thousands of lines, plus a `git log` over the full history on every removal. The decision itself is still right, because the merge check is what refuses. The same `--exclude=<branch> --branches` change fixes it. On that fixture it lists only the branch commit.

WARNING  wfctl/cli.py:L1598-L1602: The hook builds the differing-spec-files part of the stop block by parsing the store's printed lines. It strips `"✗ "`, removes `" for {branch}"`, and slices `lines[1:-1]` on the assumption that the last line is the `--overwrite` hint. If someone adds or reorders a line in `_spec_store.store`, the stop block quietly shows the wrong rows. The stop decision is unaffected, since it reads `stops_removal`. The fix is to have `StoreResult` carry the differing paths and their diffs as data, such as `different: dict[str, str]` from the `CopyPlan`, and let both callers format from that.

WARNING  wfctl/_archive.py:L263: When a `save_on_remove` folder holds the spec dir, the whole folder is skipped with a warning. Say a repository lists `docs/` and sets `spec_root` to `docs/specs`. Every ignored note under `docs/` is then deleted, and the only trace is one warning line in a removal that goes ahead. FR-018 only asks for the spec dir to be left out. The fix is to copy the folder with `shutil.copytree(..., ignore=...)` so it drops the spec dir path, and keep the skip only for a listed folder that sits inside the spec dir.

NIT      wfctl/cli.py:L1672-L1686: The hook repeats `_print_removal_stop` line for line: the red header, the groups loop, the blank line, and `_print_manual_route` with the keep route. `_print_removal_stop` already takes `keep_route`, so a single call to `_print_removal_stop(repo_root, branch, groups, keep)` replaces about 9 lines. That also brings `worktree_remove_cmd` back under 50 lines.

NIT      wfctl/cli.py:L1489-L1496: `archive_unsaved_cmd` builds the same three groups that `_remove_stop_groups` builds at L1589. If `_remove_stop_groups` accepts `dry_store: StoreResult | None`, the command can call it, which saves about 8 lines and keeps the two headings from drifting apart.

NIT      wfctl/_spec_store.py:L40: `_is_inside(spec_dir, worktree)` duplicates `_archive.is_inside(worktree, path)` with the arguments reversed. The plan says the store reuses `is_inside`. Two predicates with the same meaning and opposite argument order are easy to call the wrong way round, so use `_archive.is_inside`.

NIT      wfctl/_spec_store.py:L26: `StoreResult.outcome` is a bare `str`, and `cli.py` compares it to the literals `"differs"` and `"to_unsaved"`. A `Literal[...]` alias would let mypy catch a misspelled outcome, which matters more once #359 adds outcomes of its own.

NIT      wfctl/_copy_out.py:L73,L102: A symlink on the destination side is followed. If the main checkout's copy of a spec file is a symlink, `is_file()` compares the link's target, and `--overwrite` then has `copy2` write through the link, possibly outside the spec dir. A dangling link reads as missing, and the copy then creates the file at the link's target. The fix is to check `target.is_symlink()` first and replace the link instead of writing through it.

NIT      wfctl/_archive.py:L35 and spec FR-013: When the untracked listing fails, the code stops the removal (`listing_error`, "#600 item 5"). FR-013 and the proposed record `worktree-removal-requires-saved-work` both still say that a check git can't answer warns and goes ahead. The code's choice is the safer one. Add a line to the spec, or an exception in the record, so the next reader doesn't "fix" the code to match the prose.

NIT      wfctl/_workmux.py:L84: The comment says `WIRED_PRE_REMOVE` is "kept identical to wfctl's own reviewed config". The repository's `.workmux.yaml` now keeps `archive-specs` on purpose (its comment at L106 says so), so the two differ. Change the comment to name the bundled template, which `test_the_bundled_template_seeds_exactly_the_remove_hook` checks.

NIT      .workmux.yaml:L128: The repository's own fallback still prints "specs in $WM_WORKTREE_PATH not archived". The template now prints "unsaved work in $WM_WORKTREE_PATH was not saved", and the old wording names a numbered archive that no longer exists.

NIT      docs/ponytail-debt.md:L58: The line anchors `cli.py:1578,1639` and `_workmux.py:60` are off by about three lines. The definitions are now at `cli.py:1581,1642` and `_workmux.py:61`.

NIT      wfctl/_archive.py:L64: `_utc_now` is a one-line wrapper that no test patches. Inline `datetime.datetime.now(datetime.timezone.utc)` at L379.

NIT      wfctl/_archive.py `_staging_files`: The saved count, and the first 20 paths printed, include every file inside a nested repository's `.git`. One reference clone makes the summary read "saved 2,000 files", with `.git/objects/...` taking up the visible list. You could count a nested repository as one entry, matching how git lists it.
