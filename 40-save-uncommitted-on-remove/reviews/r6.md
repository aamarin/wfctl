## Findings

BLOCKER  wfctl/cli.py:L1664 — An error in the spec dir lookup skips the edit and commit checks, and the removal goes ahead. `resolve_spec_dir` runs before `_archive.check`, and `load_manifest` raises `JSONDecodeError` on a malformed `.wf-skills-manifest.json`, which it is designed to do. The catch-all at L1700 turns that into exit 0. Reproduced: a worktree with an uncommitted edit to `README.md` and a manifest reading `{not json` prints `⚠ worktree-remove failed (Expecting property name …) — continuing so the removal is not blocked` and exits 0. workmux then deletes the edit. This breaks SC-001 ("100% of forced removals … with an uncommitted edit … the worktree and branch are still present"). It is not the risk the plan accepted either. That risk was a bug inside the check phase, and here the checks never ran because of a lookup they don't need. A plausible trigger is a committed manifest left with merge conflict markers, which is exactly when the worktree also holds an unfinished merge. The same hole exists one step later: the dry-run `store()` at L1671 reads the main checkout's manifest through `spec_root(main)`, so a raise there throws away a `found` that already refused. → Resolve the spec dir inside its own `try` that falls back to `None` with a warning. Then run `_archive.check`, and wrap the dry-run store so an exception becomes a stop group ("couldn't check the spec files") rather than reaching the catch-all. Add a test with a malformed manifest and an uncommitted edit that expects exit 1.

WARNING  wfctl/_archive.py:L155 — A local-only commit on an orphan branch is deleted with nothing more than a warning. `git merge-tree --write-tree` exits 128 with `fatal: refusing to merge unrelated histories`, and the code treats every exit code other than 0 and 1 as "git can't answer". Reproduced: an orphan branch with one unpushed commit prints `⚠ couldn't check for unmerged commits (fatal: refusing to merge unrelated histories) — removal goes ahead` and exits 0. Git did answer here, since trunk can't hold work from a history it shares nothing with. This repository already uses one orphan branch (`specs-trunk`). → Pass `--allow-unrelated-histories`, which git 2.38 accepts with `--write-tree`. I checked that the resulting tree differs from trunk's, so the existing comparison then stops the removal. Add a test for the orphan case.

WARNING  wfctl/_archive.py:L142 — The stop lists trunk's own commits as "commits on no remote that aren't merged into main". `HEAD --not --remotes` excludes only remote refs. In a repository with no remote, or one whose trunk is a local branch with unpushed commits, every trunk commit is named. Reproduced: a repository with no remote and one feature commit lists `feature work` followed by all five trunk commits. In a real repository with no remote, that is the whole history in the stop block. FR-010 asks for the branch's commits. → Once `found.trunk` is known, list the commits with `git log --format=%h\ %s HEAD --not --remotes <trunk>`. I checked that this prints only `feature work`. ## Passes

1. **Correctness.** I traced the hook from the argument defaults through `resolve_spec_dir`, `_archive.check` (status, log, merge-tree, ls-files, declared folders), the dry-run and real `store()`, `_copy_out.plan` and `apply`, and `_archive.save`'s staging, move-aside, and rename, as well as `trunk_branch`, `is_main_checkout`, `main_checkout`, and `resolve_agent_dir`. I checked the porcelain `-z` rename format, that 3.11's `rglob` doesn't follow directory symlinks, `copytree(symlinks=True)`, the `typer.Exit` re-raise ahead of the catch-all, and the FR-002 ordering. The findings are the blocker and the first three warnings, all reproduced, plus the symlink and pruned-worktree nits. Staging, promotion, and failure cleanup are sound.
2. **Security.** Every route is quoted with `shlex.quote`. Paths are printed with `markup=False` or `escape`. A `save_on_remove` entry is resolved before the containment test, so a symlink pointing out of the repository is rejected. Untracked symlinks and links inside copied folders are copied as links, never followed. Nothing is built into a shell string. The only finding is the write through a destination symlink. A committed `wfctl.json` in an unfamiliar repository can make the hook copy any folder inside that repository into the state dir with no size cap, which the spec accepts.
3. **Architecture.** The dependencies point one way: `cli` uses `_spec_store` and `_archive`, `_spec_store` uses `_copy_out` and `_paths`, and `_archive` uses `_paths`. `current-state.md` places the two new modules in the right bands. There is no new third-party dependency, so the dependency questions don't apply. The findings are the coupling to `StoreResult.lines`, the duplicated stop block, the duplicated containment check, and the ponytail note that can't fire. The plan's ownership claims hold: `stops_removal` is a property, and trunk comes from `trunk_branch`.
4. **Readability and simplification.** Names are honest and the comments explain why. The findings are the duplicated stop block, the flag parameter, the missing `save_on_remove` docs, the stale echo line, and the line references that are off by three.
5. **Performance.** The checks are four or five git calls, and the dry run reads the spec files twice, which is negligible. In a repository with no remote, `log HEAD --not --remotes` walks and prints the whole history; the third warning fixes it. A nested repository is copied with no size cap, as the spec accepts.
6. **Over-engineering.** Folding the hook's inline stop block into `_print_removal_stop` saves about 8 lines. One shared helper for the three `found` groups saves about 9. Reusing `_archive.is_inside` saves 3. `dry_run` on `store()` earns its place, since FR-002 depends on it. `_relative` is needed too, because `WFCTL_SPEC_DIR` can be relative.
