### WARNING — cli.py:L2212 the fill fires for a backend the copy loop cannot install

The new branch sets `tracker = recorded` for *any* recorded backend, using
`_tracker_files(recorded)`, which answers for a hand-authored tracker
(`(f"{name}.json",)`) as readily as for `github`. The copy loop it feeds is
still `if tracker == "github"` (L2389). So for a repo whose manifest records a
custom tracker whose config is not on disk, the fill:

- installs nothing (the copy loop does not take that arm), and
- makes `tracker` non-`None`, which reaches L2531–L2537 and prints
  `⚠ selected tracker 'acme' but no .agents/trackers/acme.json found — author it
  with /scaffold-tracker` — on a run that selected nothing.

Verified rather than reasoned. Same script against `9d84f09~1` and `9d84f09`,
two installs into a scratch repo (`--tracker acme --yes`, then bare
`install-skills --yes`):

```
9d84f09~1  run2 (bare): no tracker line at all
9d84f09    run2 (bare): ⚠ selected tracker 'acme' but no .agents/trackers/acme.json found
```

`/start-session` runs the bare `--yes` form, so this is once per session start,
indefinitely, in the yellow-warning channel — for a state that is reachable
(`--tracker <name>` records the name before the config is authored; the warning
at install time is the design, and `scaffold-tracker` writes the config after).
The worktree flavor of this state is not new — the pre-change inheritance branch
reached the same message when a worktree's custom config was untracked — but the
same-checkout repeat-install flavor is new with this commit.

The wording is the part that matters against this project's own bar: the repo
carries a test named `test_the_replacement_notice_is_future_tense` and an
`origin_label` whose whole job is naming the right party to blame. "selected
tracker" is now false on the path the fix opens.

The same class, one step further out: L2396's
`⚠ --tracker github, but agents/trackers/<f> is missing from <origin>` is also
now printable from a bare run (confirmed with a partial bundle). Rarer — it takes
a bundle without the tracker tree — and the same one-word inaccuracy.

Fix, either half:
- gate the fill on a backend this bundle can actually supply — today
  `recorded == "github"`, more durably "at least one missing file exists under
  `bundle_root/agents/trackers`"; or
- keep the fill's intent in its own flag and gate L2531's warning on the run
  having named a tracker, so it stays a statement about `--tracker`.

### WARNING — README.md:L517 documents the pre-change rule

> Once a repo has a tracker, later installs leave the choice and your edits to
> its config alone — re-copy the shipped one with an explicit `--tracker github`.

Half of that is still exactly right (edits are left alone — `tracker_skip_existing`
is what makes it so), and the paragraph that follows about `start`/`stop` arriving
only with `--tracker github` is still right, because that is an in-place config
change. What is now wrong by omission is the sentence's implied "later installs
copy nothing": a bare install now delivers backend files the repo is *missing*,
which is the entire behavior change. One clause covers it — "…leave your edits
alone and add only the files the backend is missing; an in-place change to an
installed file still travels by `--tracker github`". `--tracker`'s help text
(cli.py:L2050, "Omit to leave unchanged") reads the same way.

The commit is otherwise unusually careful about writing the reasoning down —
it is a 25-line comment block on a 7-line branch — which makes the user-facing
copy the one place the reasoning did not land.

### WARNING — no test for the non-github fill

`test_a_bare_install_delivers_a_backend_file_the_repo_is_missing` and
`test_a_bare_install_leaves_a_hand_edited_backend_file_alone` are both good
tests: named as sentences, docstrings that say what failure they exist to catch,
and both genuinely fail against `9d84f09~1` (the first on the restored file, the
second on its last assert). Neither exercises `_tracker_files`' other arm. A
third — a repo recording `acme`, a bare install, assert the output says nothing
about a tracker this run did not select — is what turns finding 1 into a red test
rather than a session-start annoyance nobody attributes.

### NIT — cli.py:L2216 duplicated rationale

`# Fill the gap without touching what is there. The file a project committed is
the reason the check above is not a plain overwrite…` argued something the
reader could not see from the old site, where the "Missing files only" paragraph
was a block away and behind a different branch. After the move the two are ten

### NIT — cli.py:L2212 an unvalidated manifest value in a path

`recorded` comes from `.wf-skills-manifest.json`, which `CLAUDE.md`'s Safety
section explicitly treats as attacker-adjacent in an unfamiliar repo ("a repo can
commit one anyway… read a committed manifest before the first `doctor`"). It is
joined into `trackers_dir / f"{name}.json"` with no containment check, unlike
`_recorded_path`, which exists for exactly this and refuses a path that escapes
the repo. Bounded: nothing is written, because the copy is still gated on
`tracker == "github"`, so the reachable effect is a `stat()` outside the repo and
a path echoed into the warning. Pre-existing at L2532; this commit is what makes
it reachable without a flag, on the `--yes` path.

## What each pass checked

**1. Correctness.** Traced the whole `tracker` variable's life, not just the
changed lines.

- Ordering holds: the inheritance branch writes `manifest["tracker"]` one block
  above, so the moved fill reads it there and #184's case is unchanged. Confirmed
  by `test_install_skills_inherits_the_tracker_from_the_main_checkout` (both
  parametrizations) and `test_inherited_tracker_leaves_a_committed_config_alone`
  still passing untouched.
- Falsy recorded values fall out correctly: a declined tracker (`None`) and an
  absent key both skip the walrus. `--tracker none` never reaches it (`tracker`
  is `"none"`, not `None`), and `--tracker github` leaves
  `tracker_skip_existing` `False`, so the explicit form still refreshes the lot.
- The interactive prompt at L2224 cannot be shadowed by the new branch: its own
  `"tracker" not in manifest` guard is already false whenever the fill fires.
- Backups: verified the commit message's load-bearing claim against L2438–L2442 —
  `if rel_dest in prior_items: backup_rel = prior_items[...]["backup"]`, so a
  recorded path is overwritten with **no** new backup. "Missing files only" is
  therefore the correct call, not a conservative one: a presence-based refresh
  would destroy a hand edit with nothing to restore from.
- No new foreign-overwrite entries: with `skip_existing`, existing files never
  enter the plan, so the TTY-less-hook abort and the silent `--yes` replacement
  both stay closed.
- Record-keeping: the filled file lands in base `items`; the skipped siblings
  keep their prior records through the #209 carry-forward at L2557, so `--prune`
  (which `/start-session` runs) sees no orphan.
- The one defect found is finding 1.

**2. Security.** No new external input beyond the manifest value (NIT above). No
secrets, no shell construction, no network. The files copied come from the
bundle, not from the repo.

**3. Architecture.** The change removes a special case rather than adding one:
one condition now covers both the inherit-and-fill and the already-recorded case.
It fits the file's existing shape (a plan-then-copy pipeline with `tracker` as
the "this run installs the backend" flag), and the comment says so explicitly.
The one seam it leaves is the asymmetry in finding 1 — the fill asks
`_tracker_files(name)` (backend-agnostic) while the copy loop asks
`tracker == "github"` (backend-specific).

**4. Readability.** Names carry: `recorded` reads correctly at both use sites,
`tracker_skip_existing` unchanged. No nesting added. Comment volume is high but
that is this file's deliberate register; only the duplication is worth cutting.
The commit message states the decision it took, the one it refused, and the
ceiling that buys — which is what `CLAUDE.md` asks of a body.

**5. Performance.** At most three `stat()` calls per install, in a command that
already walks and hashes a whole bundle tree. Nothing.

**6. Over-engineering.** Nothing speculative: no new flag, no new helper, no
abstraction with one caller. `_tracker_files` was already there and is reused,
not re-derived. The only shrink available is the duplicated comment (−4).
