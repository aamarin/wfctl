### WARNING README.md:L517-528 — the user-facing contract for this behavior is now stale

> "Once a repo has a tracker, later installs leave the choice and your edits to its
> config alone — re-copy the shipped one with an explicit `--tracker github`."

and, immediately after:

> "That last rule is the upgrade path for `start`/`stop`: a repo that installed the
> GitHub backend before they existed keeps the config it has, so the verbs arrive
> only with an explicit `--tracker github`."

After this commit a bare `install-skills --yes` **does** write into `.agents/trackers/`.
Verified: a repo whose manifest records `github` with nothing on disk gets the whole
backend from a bare `--yes` run, and the summary line says so —
`base  1 skill · 1 command · 3 tracker`.

"your edits to its config alone" is still true. What is no longer true is the
implication the two paragraphs carry together, that a bare install does not touch that
directory at all. And the `start`/`stop` paragraph is now half-describing a state it
does not name: a bare install delivers `github-board.sh` while leaving the stale
`github.json` that does not point at it, which is a shape the README's two-outcome
story (keeps everything / explicit `--tracker github` refreshes everything) has no
sentence for.

The commit body reasons the trade out carefully. None of that reasoning reached the
document a user reads. **Fix:** one sentence after L519 — later installs deliver a
backend file the repo is *missing*, and only that; an in-place change to a file that is
already there still needs `--tracker <name>`. That is the same "ceiling" the code
comment at L2205-2211 already states; the README is where a user finds it.

### WARNING cli.py:L2396 — a warning that names a flag the run did not pass

```python
f"[yellow]⚠[/yellow] --tracker github, but "
f"agents/trackers/{fname} is missing from "
f"{origin_label} — nothing installed for it"
```

The copy loop is now reachable with `tracker` set from the manifest rather than from
argv, so this message can attribute the run to a flag nobody typed. Reproduced against
HEAD (recorded `tracker: github`, `--from` bundle missing one backend file, bare
`install-skills --yes`):

```
⚠ --tracker github, but agents/trackers/github-issue-create.sh is missing from …
```

Pre-change this text was reachable only through the inherit branch — first install in a
worktree, main checkout recording a tracker. It is now reachable on **every** bare
install in **every** repo with a recorded tracker, which is `/start-session`.

**Fix:** phrase it off the resolved backend rather than the flag —
`f"backend '{tracker}', but agents/trackers/{fname} is missing from …"`.

### WARNING cli.py:L2535 — a per-session nag for custom trackers, on a new and untested path

Same root cause. With `tracker: jira` recorded and no `jira.json` on disk, the fill
branch sets `tracker = "jira"`, the copy loop skips it (`tracker == "github"` is the
only case the bundle ships), and control reaches the `elif tracker is not None:` arm.
Reproduced against HEAD:

```
⚠ selected tracker 'jira' but no .agents/trackers/jira.json found — author it with /scaffold-tracker
```

Three things about this, in order of weight:

1. **It is new output on the `/start-session` path, and nothing tests it.** Both new
   tests cover `github`. The custom-tracker branch is where the fill does no work at
   all — it only sets a variable that reaches a warning — and it has no test.
2. **"selected" is false** in the same way as L2396: the run selected nothing.
3. **It is tracker drift reporting**, arriving through `install-skills` for custom
   backends only. Issue #260 names that as decision (2) and this change deliberately
   takes decision (1) only. Half of (2) has shipped as a side effect, asymmetrically:
   a missing `github` file is silently repaired, a missing custom config warns forever
   with no repair the tool can perform.

The warning is *truthful* — a config-less custom tracker is genuinely broken — so
keeping it is defensible. What is not defensible is shipping it unnamed and untested.
**Fix:** either gate it on the flag (`if cli_tracker is not None`), restoring the
pre-change surface, or keep it, reword it, and add the test.

**Root cause of both warnings, and the one fix that closes them:** `tracker` now carries
two meanings on one name — "what the caller typed" and "what this run installs" — and
the L2188-2190 comment says so in as many words. Split it:

```python
install_backend = tracker if tracker not in (None, "none") else None
# fill branch sets install_backend, never tracker
if install_backend == "github":          # L2389
```

leaving `tracker` to mean the caller's selection at L2527-2537. That removes both
misleading messages and the NIT below in one move.

### NIT cli.py:L2212 — a manifest holding the string `"none"` is now silently cleared

`--tracker none` is the CLI spelling for "clear it", and `wfctl/agents/skills/scaffold-tracker/SKILL.md:L148`
tells a user they may set the key by hand instead of using the flag — so `"tracker": "none"`
in a hand-edited manifest is a reachable mistake. It is truthy, so the new branch fires,
`_tracker_files("none")` looks for `none.json`, it is absent, and `tracker = "none"` flows
to L2527 `if tracker == "none": manifest.pop("tracker", None)`. Verified: the key is gone
after a bare `install-skills --yes`.

Both the before and after states are broken (`_tracker.py` cannot load `none.json` either),
so this is small — but the *before* state was inert and the *after* state mutates a repo's
recorded config on a run that named nothing. The `install_backend` split above removes it
without a special case.

### NIT cli.py:L2216-2219 — the inner comment restates the block comment

The block comment's second paragraph (L2194-2199) already gives the reason: not
gitignored, a project can commit and hand-edit, a planned write over that reads as a
foreign overwrite. The comment kept on `tracker_skip_existing = True` says the same
thing in shorter form. It earned its place when it sat inside the inheritance branch and
had no block comment above it; it does not now. **Fix:** drop it (−4 lines).

### NIT CLAUDE.md Safety — the committed-manifest enumeration is now one item short

> "In an unfamiliar repo, read a committed manifest before the first `doctor` … what it
> can install is agent instructions and `.specify/scripts/`, which speckit commands execute."

After this commit a committed manifest carrying `"tracker": "github"` also causes a bare
`install-skills --yes` to write `.agents/trackers/*.sh` with no prompt (verified — probe
case D installs all three files into a repo that had never installed a tracker, purely on
the strength of the manifest key). The scripts come from wfctl's own trusted bundle, not
from anything the manifest names, so the risk is near zero — but that sentence exists to
be exhaustive about what a committed manifest can cause to be written, and it no longer
is. One clause.

## What each pass checked, and what it found clean

**1. Correctness.** Traced `tracker` from argv through every consumer (L2389 copy loop,
L2527-2537 record + warn) — those are the only three reads; nothing else in
`install_skills_cmd` branches on it. Case-analysed the new guard:

| Recorded | Flag | Fill fires | Result | Correct |
|---|---|---|---|---|
| absent | — | no (falsy `.get`) | first-install question unchanged | ✓ |
| `null` (declined) | — | no (falsy) | decline still honored | ✓ |
| `github`, all files present | — | no | nothing copied, record carried forward | ✓ |
| `github`, one file missing | — | yes | only the missing file planned, `skip_existing` protects the rest | ✓ |
| `github`, nothing on disk | — | yes | whole backend repaired | ✓ |
| `github` | `--tracker github` | no (`tracker` not None) | full refresh, foreign-overwrite prompt intact | ✓ |
| `github` | `--tracker none` | no | key popped, unchanged | ✓ |
| inherited from main | — | yes, reading the key the inherit branch just wrote | identical to pre-change | ✓ |
| custom, config missing | — | yes | no copy (bundle ships only github) + warning | see WARNING above |
| `"none"` string | — | yes | key silently popped | see NIT above |

Ordering is sound: the fill sits after the inherit branch (which writes the key it
reads — the commit body's claim, and it holds) and before the first-install question,
which can only fire when no key is recorded and so cannot collide. `tracker_skip_existing`
makes the fill incapable of generating a `foreign_overwrites` entry, because it `continue`s
on any path that exists — so the TTY-less-abort failure mode the old inheritance branch
guarded against cannot be reached from the new one either. `dest.parent.mkdir(parents=True)`
at L2434 covers a repo with no `.agents/trackers/` at all. The record carry-forward at
L2557 still sees the filled file in `items[base]`, so `--prune` does not orphan it — the
#209 mis-read is not reintroduced.

**2. Security.** `recorded` comes from `.wf-skills-manifest.json`, which CLAUDE.md says a
repo may commit. A traversal value (`"../../evil"`) reaches `trackers_dir / f"{name}.json"`
for an `.exists()` call and `repo_root/.agents/trackers/{name}.json` for another — both
reads, never a write, and the copy loop is pinned to the literal `"github"` with sources
from `bundle_root`. No new write primitive, no new execution primitive; the manifest could
already steer `_tracker.py` dispatch before this commit. Only finding is the enumeration
NIT above. No secrets, no injection surface, no untrusted data reaching a shell.

**3. Architecture.** The change fits the existing shape rather than inventing one: it
moves a guard, keeps the flag→copy-loop plumbing, and adds no module or indirection. The
one architectural smell is real but pre-existing and now doubled — `tracker` as both
input and derived state — covered under the WARNINGs with a concrete split. No new
coupling, no cycle, no duplication introduced.

**4. Readability.** Names are good (`recorded`, `tracker_skip_existing`). The walrus reads
cleanly and its scope is the two lines below it. Nesting stays at two levels. The 24-line
comment block over a 7-line branch is high, but CLAUDE.md sets that norm explicitly
("existing comments are dense with rationale — match that"), and every paragraph answers
*why this shape* rather than narrating the diff — including the "ceiling that buys"
paragraph, which is the one a future reader will most need. Only the duplicated inner
comment is surplus.

**5. Performance.** Three `stat` calls per install, once, guarded by a `tracker is None`
short-circuit. Nothing.

**6. Over-engineering.** Nothing speculative. No hand-rolled stdlib. No abstraction with
one implementation. The branch is the minimum that closes both gates named in the issue,
and the "missing files only" restriction is the smaller of the two available fixes rather
than the more general one. Only `−4` lines available, from the duplicate comment.

## Tests

Both new tests are behavior tests on the path the issue names, and their docstrings say
why they exist rather than restating their assertions — the file's convention, and they
meet it. `test_a_bare_install_delivers_a_backend_file_the_repo_is_missing` asserts the
record as well as the file, which is what stops `--prune` regressing. The local
`import json` and the split-subscript formatting match the neighbouring tests verbatim,
so both are house style here, not drift.

Coverage gap: the custom-tracker branch (WARNING above) — the one case where the fill
does no work and only produces output. Softer gap: nothing asserts that a bare install
with the backend *complete* plans no tracker copy at all; `test_a_later_bare_install_keeps_the_backend_on_record`
exercises that run but asserts only on the record, so a future change turning the fill
into a refresh would leave it green.
