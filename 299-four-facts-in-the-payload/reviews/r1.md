WARNING  wfctl/_predicates.py:L782 — `records_on_this_branch(repo_root, arch)` is called with no `exclude`, making this the fourth reader of the arch root and the only one that skips `scans/`. `cli.py:469` and `cli.py:691` both pass `exclude=arch / SCANS_DIR`, and `CLAUDE.md` states the rule for exactly this case ("A fourth reader added later has to make the same exclusion, and `_paths.SCANS_DIR` is where it finds out"). The docstring argues the `load_records` intersection excludes every subtree for free — true by *slug*, and slugs are bare stems, so it fails on a stem collision: a branch that touches only `docs/architecture/scans/foo.md` while a top-level `foo.md` sits at `proposed` reports `architecture accepted ○ foo (proposed)` about a record the branch never touched, and holds the branch on it. Every branch that runs `/speckit.clarify` writes into `scans/`, so the input is not exotic — only the name collision is. → `from wfctl._paths import SCANS_DIR, records_on_this_branch`, then `records_on_this_branch(repo_root, arch, exclude=arch / SCANS_DIR)`. It also narrows two git pathspecs, which is free. (The `design/` same-stem case is a separate residue; the docstring and `tests/test_four_facts.py:L156` already name it, so leaving it is a recorded choice, not a miss.)

## What each pass checked, and what it did not find

**Correctness.** Walked all four derivations against FR-001…FR-015 and the
data-model's per-fact table; they match, including the two that read oddly and are
right: `_RULED_ON` admitting `superseded`/`rejected`/`retired` rather than
`accepted` alone (L123, with the test at `test_four_facts.py:L128`), and
`fact_integration_authorized` routing through `blocks(verdict, "human")` rather
than mapping sources to values, which keeps `promised-evidence-blocks-on-silence`
the only copy of that rule. Checked the `cli` grant correction for behaviour
change: old `notify = report.notify and notify_source == report.notify_source`
and new `_corrected_grant` agree on all seven sources, and nothing outside
`cli.status_cmd:L404` reads `report.notify` (`start` uses its own `notify_grant`,
`_observe` reads only `steps`), so moving it into `build_report` changes no
gate. Checked `record["sha"]` for a `KeyError`: `load_record` rejects any record
missing a `_RECORD_FIELDS` entry, so the index is safe; the `if record else ""`
fallback is not dead either, since a repo with no commits yields `sha == ""` on
both sides and passes. Checked `not ev.spec_text` as a proxy for "absent" against
`_quoted_out`: blanked fence lines survive as newlines, so a spec that is entirely
a code block still reads as written — the only false "missing" needs a
single-line file that is entirely one inline span. Checked that the `implement`
predicate's `verification_block` and the fact's cannot disagree within one run
(same tree, microseconds apart, and both would have to lose the same race). The
`if report.facts:` guard at `cli.py:L493` can only be false for a hand-built
report, and `build_report` always fills four.

**Security.** No new input boundary. The one injection-shaped surface is rich
markup: `escape()` is applied to `fact.detail`, which is the field carrying
repo-supplied text (record slugs, `wfctl.json` paths, verify command names via
`verification_block`); `fact.name` is one of four module literals and needs none.
No secrets, no network call added — confirmed by the git-shim trace, which shows
only local invocations. `_GRANT_DETAIL` leaks nothing the existing `_NOTIFY_LINES`
does not already print.

**Architecture.** `pipeline-state-is-one-payload` is respected and, in the grant's
case, repaired: the console no longer composes a payload field. `Fact` sits beside
`steps` rather than inside a step, which is right for three facts that are about
the branch. `_predicates` still imports nothing from `_pipeline`. The new
vocabulary (`FactValue`) is deliberately disjoint from `State` and `Verdict` and
`test_the_pipeline_still_has_exactly_four_step_states` pins the disjointness.
`_FACT_GLYPH` as a sibling of `_STATE_GLYPH` rather than a widening is the right
call for the stated reason. The one architectural rule broken is the `scans/`
exclusion — WARNING 1.

**Readability.** Names are accurate; functions are short; no nesting past two
levels; comments explain why and not what, at the density `CLAUDE.md` asks for.
Two exceptions above (the dict-join and the nested ternary) and one comment that
is now false about its own function (WARNING 2).

**Performance.** Quantified above; nothing algorithmic, no N+1, no unbounded read.
The cost is five extra `git` forks per `build_report`, paid by three commands that
never render the result.

**Over-engineering.** Nothing speculative: no unused parameter, no abstraction with
one caller that is not already the shape the payload needs, no config nobody sets.
The `ev` parameter added to `_infer_steps` is optional precisely so no existing
call site had to be rewritten, which is the smaller diff. Test file is 393 lines
for 16 tests, each with a docstring naming the failure it catches — not bloat by
this repo's convention, and the two structural pins (FR-003 by signature, FR-008
by glyph-table identity) are the cheap way to hold rules that examples cannot.
The one soft test is `test_no_fact_is_derived_from_a_step`, which string-matches
`inspect.signature` and would still pass if a derivation called `_infer_steps`
internally; it pins the shape, not the rule, and its docstring is honest about
that.

net: −6 lines possible
Verdict: **Approve** (0 blockers, 4 warnings). WARNING 1 is one argument and
should land before merge; WARNING 2 and 4 are one small hoist plus two corrected
paragraphs; WARNING 3 is a test the diff is otherwise thorough enough to deserve.
