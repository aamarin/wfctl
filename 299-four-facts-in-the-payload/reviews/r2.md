## Findings

**WARNING** `wfctl/_predicates.py:L782` — FR-013 is unimplemented for
*architecture accepted*. `records_on_this_branch` returns `[]` both for "nothing
was touched" and for "git could not be asked", and the derivation reads the
second as the first, reporting `n/a  no record on this branch`. Two reproductions,
run against this tree:

| Situation | Reported | Truth |
| --- | --- | --- |
| Committed `proposed` record, branch `feature-x`, no `origin/HEAD` and no local `main`/`master`/`dev` (`_trunk_branch` → `None`, so the `diff trunk...HEAD` half never runs) | `n/a` — `no record on this branch` | one record is waiting |
| `WFCTL_ARCH_DIR` pointing outside the worktree (`is_in_tree` → `False`, early `return []`) — a configuration `arch_root`'s own docstring says is honoured | `n/a` — `no record on this branch` | the fact is permanently dead for that repo |

This is the collapse the feature exists to undo, one level down: "the question
does not arise" is being used to mean "the answer could not be read". It is also
internally inconsistent inside the block it prints — `fact_integration_authorized`
routes the *same* missing git answer (`on_trunk` → `None`) to `unmet` through
`blocks("inconclusive", "human")`, exactly as FR-013 asks, while the fact one row
above it reports `n/a`.

Fix: give the derivation the distinction the helper collapses — check
`is_in_tree(arch, repo_root)` and `_paths._trunk_branch(repo_root)` before
trusting an empty listing, and return
`Fact(name, "unmet", "cannot read this branch's record set")` through
`blocks("inconclusive", "accepted-record")`, which is `True` and is the existing
rule rather than a new one. `records_on_this_branch`'s docstring asserts "no
caller can act differently on them"; this change is the first caller for which
that stopped being true, and the docstring is now stale either way.

**WARNING** `wfctl/_predicates.py:L749` with `wfctl/_pipeline.py:L475` —
`verification_block` is now computed twice per `wfctl status`. `_infer_steps`
already runs it inside the `implement` predicate, and `fact_definition_of_done`
runs it again; each pass is a `load_config`, a `load_record` and a
`code_identity` (2 git subprocesses). The comment four lines above the new call
in `build_report` says this in so many words — *"`verification_block` reads the
config, loads a record and shells out to git, and `status` runs on every session
start. Recomputing it here is the one call this seam was meant to collapse."*
The change reintroduces the recomputation the comment is guarding.

Fix: `build_report` already holds the implement step's `blocked` reason
(`raw`/`blocked` at L475–477). Pass it into `facts()` and have
`fact_definition_of_done` take `blocked: str | None` alongside `repo_root`, so
the config read stays (it is what distinguishes "nothing to run" from "passed")
and the git work does not repeat. That keeps FR-003 intact — a verification
reason is not a step state, and `blocked` is already a payload field the console
renders.

**WARNING** `wfctl/cli.py:L469` vs `wfctl/_predicates.py:L782` —
`records_on_this_branch` is now also computed twice per `wfctl status`, with
*different* arguments, and the two answers are printed 15 lines apart in the same
output contradicting each other. Rendered on this branch right now:

```
  record: 299-facts-render-as-a-block
  record: readiness-is-not-a-step-state
────────────────────────────────────
…
architecture accepted  ○  readiness-is-not-a-step-state (proposed)
```

The header lists two records on the branch; the fact then names one and reports
the other as neither met nor waiting. Both statements are correct under their own
rule (`design/` is excluded from the fact by FR-009, and the header excludes only
`SCANS_DIR`), and nothing in the output says so — a reader's first move is to
open an issue about it.

This is also the second derivation of one answer inside one command, which is the
shape `pipeline-state-is-one-payload` (accepted) forbids and which the branch's
own `readiness-is-not-a-step-state` cites. The console loop predates this change,
so the defect is not introduced here — but the change added a second derivation
beside it instead of converging them, and the disagreement is new.

Fix: resolve the touched-record slugs once in `build_report`, carry them on
`PipelineReport` the way `steps` and `facts` are carried, and have both the
`record:` loop and `fact_architecture_accepted` render from that one list. That
removes ~3 git subprocesses, removes the disagreement, and is the same move
`_corrected_grant` makes in this very diff for the grant.

**WARNING** performance, quantified against the plan's own budget. `plan.md`
states: *"`wfctl status` gains at most two local git invocations for the branch's
record set, alongside the two it already makes for `on_trunk`."* Measured on this
worktree by wrapping `subprocess.run` and calling `build_report` on the real
branch:

| | git subprocesses | wall |
| --- | --- | --- |
| with `_predicates.facts` stubbed out (pre-#299 shape) | 10 | 47 ms |
| as shipped | 19 | 118 ms |

+9 subprocesses and ~2.5× on the one call every view of pipeline state makes, and
which `/start-session` runs on every handoff. Roughly 3 are the record set (the
budgeted cost, plus `_trunk_branch`), 2 are the duplicated `code_identity` from
the finding above, and ~3 are `resolve_branch` re-resolving inside
`fact_definition_of_done` (`git branch --show-current` +
`git rev-parse --git-common-dir`, five and six times respectively across the
call). Fixing the two duplications above brings this close to the budget the plan
wrote down; the `resolve_branch` repetition is cheap to fix by threading the
branch that `build_report` already holds at L455.

**WARNING** `wfctl/_predicates.py:L821` — the grant detail can contradict the
value it sits beside. `_GRANT_DETAIL.get(source, _GRANT_DETAIL["unset"])` falls
back on the *refusal* wording regardless of what `blocks` decided, while
`NotifyGrant.source` is `str(data.get("source", "unset"))` read unvalidated out
of `events.jsonl` (`_session._last_resolved:L376`) — so a source this wfctl does
not know (a log written by a newer build, a hand-edited line) is reachable.
Verified:

```
fact_integration_authorized(True, "some-future-source")
  → Fact(name='integration authorized', value='met',
         detail='nobody has allowed it for this work')
```

`met` beside "nobody has allowed it" is worse than either alone, and the detail
is the half FR-005 says a reader acts on. `cli._notify_line`'s identical fallback
is safe only because it renders no boolean next to it. Fix: make the fallback
follow the value — `_GRANT_DETAIL.get(source) or (f"allowed by {source}" if
granted else _GRANT_DETAIL["unset"])`.

**NIT** `wfctl/_predicates.py:L123` — `_RULED_ON` restates `_arch.STATUSES` minus
`proposed` by hand, and hardcodes the value of `_arch.IN_FORCE` as a literal. A
status added to `_arch.STATUSES` later would silently report every branch that
uses it as unmet. The comment already names `_arch.STATUSES` as the authority, so
derive it where `_arch` is imported: `ruled_on = _arch.STATUSES - {"proposed"}`
inside `fact_architecture_accepted`.

**NIT** `wfctl/cli.py:L90` — the comment justifies `_FACT_NAME_WIDTH` as "the
block and its tests both need it", and no test references it (single use, L497).
Nothing pins it to `max(len(n) for n in FACT_NAMES)` either, so a renamed fact
misaligns the column with a green suite. Either add the assertion the comment
claims exists, or compute the width from the names.

**NIT** `contracts/facts-payload.md` vs `wfctl/cli.py:L499` — the contract's

**NIT** console redundancy — `nobody has allowed it for this work` now prints

**NIT** `wfctl/_predicates.py:L721` — `", ".join(written)` joins a dict's *keys*.

## Passes that found nothing

**Security.** Every fact detail reaches the console through
`escape()` (`cli.py:L499`) and reaches `--json` raw, which is the right split and
matches `arch_location`'s documented rule. No new external input, no secrets, no
new subprocess argument built from repo-supplied text — `records_on_this_branch`
passes the arch root as a pathspec after `is_in_tree`, unchanged. Note the
`record:` slugs at `cli.py:L470` are printed *un*escaped, but that is pre-existing
and outside this diff.

**FR conformance, item by item.** FR-001/004/006/007 hold (four entries, fixed
order, non-empty details, block printed in every state — verified on a real
`wfctl status` and on `build_report(None, tmp, tmp)`). FR-002/003 hold, and
`test_no_fact_is_derived_from_a_step` enforces FR-003 structurally rather than by
example, which is the right shape. FR-008 holds (`_STATE_GLYPH` unchanged, sets
disjoint). FR-009 verified live: `299-facts-render-as-a-block` sits under
`design/` and is correctly absent from the fact while present in the header
listing. FR-010/011/012 hold. FR-014 holds and is pinned across all eight
verdict/source pairs. FR-015 holds — every string the console prints is present
in `--json`. FR-005 is the weakest of the set: `_GRANT_DETAIL["label"]` says "you
allowed it on the issue" without naming which issue, where `_notify_line` builds
that name deliberately; acceptable on a `met` row, worth knowing.

**Over-engineering.** Nothing to delete. `_UNREADABLE_GRANT`'s three members and
`_GRANT_DETAIL`'s seven are all reachable; the optional `ev` parameter on
`_infer_steps` is the mechanism for the single-read guarantee and not
speculative; the `if report.facts:` guard prevents a bare separator on a
default-constructed report. The comment-to-code ratio in the new `_predicates.py`
block is high, and it is the ratio the surrounding file already keeps — that is
the house convention, not bloat.

**Tests.** Read first, as the rubric asks. `tests/test_four_facts.py` tests
behavior through the CLI rather than the derivations, docstrings name the failure
each test caught rather than restating the assertion, and
`test_a_proposed_record_and_an_accepted_one_do_not_read_the_same` is the reported
defect stated as one assertion — which is the test that had to exist. `NO_COLOR`
is inherited from `conftest.py` as the project requires.

**Correctness, elsewhere.** Traced `_corrected_grant`'s move out of `cli`: the old
expression `report.notify and notify_source == report.notify_source` is
equivalent to the new `granted=False` on `trunk`/`unknown-trunk`, `report.notify`
has no consumer outside `status_cmd`, and `_session.notify_allowed` — which is
what actually gates `wfctl issue comment` — reads `resolved_notify` directly and
is untouched. `wfctl next`, `resume` and the `_observe` path now pay two
`on_trunk` git calls they did not, which `plan.md` names and accepts.
`_verify.load_record` returns `None` unless every field is present, so
`record["sha"]` at L753 cannot `KeyError`. `fact_artifacts_written` requiring all
three files is safe against the pipeline's `skipped` arms — `tasks`' skipped arm
runs only with non-empty `tasks_text`, and no arm makes `plan.md` optional.
