### Findings

**WARNING** `wfctl/_predicates.py:782` — `records_on_this_branch(repo_root, arch)` is called
without `exclude=arch / SCANS_DIR`, and this is the "fourth reader" the repo's own
`AGENTS.md` warns about: *"A fourth reader added later has to make the same exclusion, and
`_paths.SCANS_DIR` is where it finds out."* The docstring argues the intersection with
`load_records` makes the exclusion free. It does not — it makes it *usually* free. The git
pathspec is recursive, so `scans/`, `design/`, `views/` and `declarations/` all enter
`touched` as bare stems, and the intersection is on stems alone. A branch touching
`scans/<X>.md` or `design/<X>.md` while a top-level `<X>.md` exists reports that top-level
record as touched: unmet on a record the branch never wrote (a false blocker with no action
that clears it), or met on a record it never wrote. The docstring even names the mechanism
("a level-3 record and a top-level one of the same name look identical to it") and then
relies on it. → pass `exclude=arch / SCANS_DIR` as `cli.py:469` already does, or intersect
on resolved paths rather than stems. One keyword argument; the sibling call site is the
precedent.

**WARNING** `wfctl/_predicates.py:749` + `wfctl/_pipeline.py:487` — the definition-of-done
fact calls `verification_block(repo_root)` unconditionally on every `build_report`, which
is the exact recomputation the comment three lines above it in `build_report` says the seam
exists to prevent ("`_infer_steps` has already asked; … Recomputing it here is the one call
this seam was meant to collapse"). Measured on this worktree: `_predicates.facts()` costs
**5 git subprocesses / ~56 ms**, against `_infer_steps()` at **1 call / ~14 ms** — a report
that was ~20 ms is now ~78 ms. That measurement is with `verification_block` short-circuiting
at `unverified`; with a verification record present it also runs `code_identity` (`git
rev-parse HEAD` + `git status --porcelain` over the whole tree), and when `implement` is
reached the whole block runs **twice** per report, plus a third read of the record for the
sha at `:753`. `plan.md` budgets "at most two local git invocations"; the actual figure is
five to nine. Three of the four `build_report` call sites (`start` cli.py:262, `next`
cli.py:607, `end` cli.py:715) never render a fact and now pay all of it — and `next` is what
an agent calls on every turn. The spec deferred this measurement to implementation and no
measurement was recorded. → hoist `verification_block(repo_root)` in `build_report` and pass
it to both consumers, the way `ev` is now hoisted (same pattern, no FR-003 problem: it is the
fact's own owner-read, not a step's verdict); or make `facts` a `cached_property` on the
frozen report so non-rendering callers don't pay. If neither, record the measured number as
an accepted cost.

**WARNING** `wfctl/_pipeline.py:425` — `_corrected_grant` is a third copy of the trunk rule.
`_session.action_grant` (`_session.py:258`) already computes exactly this: `on_trunk` →
`None` ⇒ `unknown-trunk`, `True` ⇒ `trunk`, else the recorded grant — down to the same
"two local git calls" argument in its docstring. The change correctly removes the copy that
lived in `status_cmd` and then adds a new one beside the one that remains, and neither
docstring mentions the other. A fourth trunk state, or a change to what `None` means, must
now be made in two places. → `granted, source = (g.granted, g.source)` from
`action_grant(agent_dir, repo_root)`, dropping `_corrected_grant` *and* `build_report`'s own
`resolve_branch`/`resolved_notify` lines. If the two must stay separate (the gate and the
report are different questions), say so in `_corrected_grant`'s docstring and name
`action_grant` — otherwise the next reader deletes the wrong one.

**WARNING** `wfctl/_predicates.py:794` — the `met` detail lists slugs with no status, so a

### Checked and found sound

- **Correctness.** All four `n/a` paths are right for the stated owner, and the
  `_RULED_ON` set (not `accepted` alone) is the correct call for a superseding branch —
  the test naming it is the strongest in the file. `fact_artifacts_written` reads the
  three `Evidence` texts and no step verdict, so FR-003 holds structurally. Sharing one
  `Evidence` between `_infer_steps` and the fact closes a real read-skew window rather
  than only saving a read. `_infer_steps`' new parameter is optional and defaulted, so
  every existing caller and test is untouched. The corrected-grant move is
  behaviour-preserving for `status`: `report.notify and notify_source ==
  report.notify_source` and the new `_corrected_grant` agree on all seven sources, and
  `report.notify` has no consumer outside `status_cmd` (the action gate reads
  `_session.action_grant` directly), so nothing else observes the payload field changing
  meaning.
- **Security.** No new input boundary. Every detail string is `escape()`d on the console
  path, which is the right call — record slugs and `verification_block`'s embedded
  command list are repo-supplied and `[wip]` is legal in both. No secret, no shell string
  built from repo text, `load_config`'s no-splitting rule untouched.
- **Architecture.** `pipeline-state-is-one-payload` is *better* held than before: the one
  view-side composition (the trunk correction in `status_cmd`) is deleted. `FactValue` is
  a closed `Literal` beside `State`/`Verdict` with the vocabularies kept disjoint, and the
  disjointness is pinned by a test. `blocks()` is untouched (FR-014) and pinned across all
  eight verdict/source pairs. `_FACT_GLYPH` is a sibling table, not a widened one. No new
  module, no fifth step state, snapshot needed no regeneration.
- **Performance.** Only the `verification_block`/`facts` cost above; no network call added,
  `load_records` is a bounded one-level glob, no N+1.
- **Over-engineering.** The diff is comment-dense but the comments carry rationale rather
  than narration, which is this repo's documented standard. Only the four items above shrink.
